# 06 · 平衡树、B 树、Trie 与索引结构

## 本课目标

学完后，你应该能够：

- 说明“有序”不能保证 BST 高度小，以及平衡树维护的真正不变量；
- 比较 AVL 与红黑树的平衡严格度、旋转成本和常见取舍；
- 解释 B 树/B+ 树为什么匹配块设备或页缓存，而不是把它们当作“更多叉的二叉树”；
- 用 Trie 的前缀路径解释查找与补全，并认识其空间成本；
- 把索引选择连接到文件系统、缓存、RAG 文本/向量检索的不同访问模式。

> [!tip] 首读核心闭环与按需选读
> **首读核心闭环**是：普通 BST 的“键有序”不足以限制高度（第 1 节）→ 用旋转维持局部键区间（第 1 节图）→ 根据查询单位选择页式范围索引（第 3、4 节）或前缀索引（第 5 节）。能用这条链解释“为什么不是所有查询都用同一棵树”即可。
>
> **按需选读**：AVL 与红黑树的具体取舍（第 2 节）、B 树分裂/删除细节（第 3 节）以及第 6 节的 RAG 多索引组合，留到需要实现内存有序容器、页式存储或检索系统时再读。

## 1. 平衡不是“画得对称”

上一课的普通 BST 只维护键的左右顺序，可能高到 `n - 1`。平衡搜索树增加形状不变量，使高度维持在 `O(log n)`，于是查找、插入、删除也得到最坏 `O(log n)` 的高度边界。它并不要求每层节点数完全相同；重点是防止一侧长期过深。

基本修复动作是**旋转**。右旋把一个左孩子提升、原根下沉到右边，同时移动一棵中间子树；只要正确保留键的区间归属，BST 排序不变量不变。旋转重排的是局部指针/引用关系，不是把全部元素重新排序。

```text
右旋前：        8             右旋后：       5
               / \\                          / \\
              5   C                        A     8
             / \\                              / \\
            A   B                            B   C

要求：A < 5 < B < 8 < C；旋转后仍成立
```

## 2. AVL 与红黑树：同一目标，不同维护强度

**AVL 树**通常维护每个节点左右子树高度差（平衡因子）在很小范围内，例如 `-1、0、1`。插入或删除破坏条件后，通过单旋或双旋恢复。它限制更严格，树往往更矮，适合读操作非常密集且希望较短查找路径的场景；但更新可能触发更多高度维护与旋转。

**红黑树**给节点附加颜色，并维护一组颜色/黑高规则，例如根与空叶的约定、红节点不连续、任一路径的黑节点数量一致。它也保证对数高度，但允许比 AVL 更松的形状；插入/删除常用重新着色配合有限旋转修复，工程中常在读写均衡的有序映射/集合实现里出现。

要检查一棵具体红黑树，必须先固定完整约定。一组常见定义是：每个节点为红或黑；根为黑；所有空子树都视为黑色哨兵叶；红节点的两个孩子均为黑；从任一节点到其所有后代哨兵叶的路径都含有相同数量的黑节点。固定黑高为 `b` 时，每条向下路径至少由这些黑节点贡献相应长度；由于红节点不能相邻，任一路径也不会长于约 `2b`。再由黑高为 `b` 的子树至少含有 `2^b-1` 个内部节点，可推出树高为 `O(log n)`。

AVL 与红黑树的局部修复都还有同一项义务：旋转前后必须保留每棵中间子树的键区间。AVL 的单旋处理外侧失衡，双旋先修正内侧折线再提升新根；修复后还要自底向上重算高度。插入只会增大一条路径，删除则可让多层祖先继续失衡；不能用“会旋转”代替对更新路径上元数据与不变量的完整检查。

| 问题 | AVL | 红黑树 |
| --- | --- | --- |
| 平衡约束 | 更严格地限制左右高度差 | 用颜色与黑高维持较松的对数边界 |
| 常见倾向 | 搜索路径更短，维护元数据更直接 | 更新修复常较灵活，适合通用有序容器 |
| 不能据此断言 | “一定比红黑树快” | “一定插入更快” |

常数、内存布局、分支预测、键比较成本、并发和实际读写比都会改变结果。若你只需成员测试而不需有序遍历、前驱后继或范围查询，哈希表可能更直接；它的碰撞和对抗输入边界见 [[计算机知识/50-数据结构与算法/04-哈希表集合与冲突处理|哈希表、集合与冲突处理]]。

## 3. B 树：把一次访问换成更多分支

内存中的二叉树每个节点常只带少量键和指针；若一个节点访问意味着一次昂贵的磁盘/SSD/网络页读取，走很多层会放大延迟。**B 树**让一个节点容纳多个已排序键和多个孩子指针，使树的分支因子很高、总高度很低。节点通常按存储系统的页或块大小设计，但不是说“页大小固定为某个普适数字”。

一个概念性节点可写成：

```text
[ k1 | k2 | k3 ]
  c0   c1   c2   c3

c0 的键 < k1；c1 在 k1 与 k2 之间；……；c3 的键 > k3
```

节点内部在有序键中定位区间，再读取对应孩子。节点满时分裂：把中间分隔键上推到父节点，左右部分成为两个节点；删除则可能借相邻节点的键或合并。这些操作维护“各节点键有序、孩子区间正确、所有叶在相同深度、节点占用满足最小/最大规则”等不变量。最小占用规则避免大规模空节点使高度膨胀。

若每个非根内部页至少有与页容量同阶的分支数 `B ≥ 2`，一次根到叶查找经过的页数是 `O(log_B n)`；这说的是**页访问层数**，不等于把页内比较、缓存命中、预读、写回或事务成本都变成常数。根页或上层页已在缓存时，实际慢 I/O 可能更少；页很稀疏、`B` 只是最大而非最小分支数时，也不能直接把 `log_B n` 当作保证。

## 4. B+ 树：把范围扫描变成叶链扫描

术语在不同资料中有细节差别；学习时先抓住常见实现模型：B+ 树的内部节点主要保存分隔键与孩子指针，完整记录或记录指针放在叶节点；叶节点按键顺序相连。精确查找从根到叶，范围查询定位下界叶后，沿叶链顺序扫描到上界。

```text
内部页： [ 20 | 50 ]
          /     |     \
叶页： [5,12] ⇄ [20,31,44] ⇄ [50,68]
```

因此 B+ 树很适合“找 `20 ≤ key < 50` 后连续取很多记录”：上层导航少读几页，叶层顺序访问又能利用预读与页缓存。B 树/B+ 树的优势不是抽象大 `O` 自动更小，而是减少慢层 I/O 次数、让一次页读取携带更多有用比较信息，并让范围访问连续。缓存、工作集和连续访问的物理原因见 [[计算机知识/30-计算机系统/04-缓存局部性带宽与延迟|缓存、局部性、带宽与延迟]]。

文件系统也有目录项、inode、页缓存、挂载和不同实现策略；不要声称“所有文件系统都用 B+ 树”或把数据库索引结构直接等同于 Linux VFS。正确的共同问题是：怎样用有限的块/页读取，定位名字或键与其元数据/数据位置。参见 [[计算机知识/20-操作系统/01-Linux/03-目录结构挂载与文件系统|目录结构、挂载与文件系统]]。

## 5. Trie：用路径表达前缀

**Trie（前缀树）**把键拆成符号序列，从根沿每个字符/字节/token 的边向下走；节点表示前缀，终止标记表示一个完整键。存储 `to`、`tea`、`ten` 的概念图：

```text
root → t → e ──前缀（本例 `te` 不是完整键）
             ├→ a ──终止："tea"
             └→ n ──终止："ten"
       └→ o ──终止："to"
```

查找、插入会处理键的 `L` 个单位，但总成本还取决于“在当前节点如何定位下一条边”。固定小字母表的直接数组可使每步为 `O(1)`、总计 `O(L)`，代价是每个节点保留整个字母表的槽位；哈希孩子表通常只给出期望 `O(L)`；平衡有序孩子表的每步可为 `O(log degree)`；无序边序列则最坏要扫描当前度数。因此更完整的口径是 `O(Σ transition_cost)`；只在边转移可当作常数时才简写为 `O(L)`。它自然支持前缀查询、自动补全、字典枚举和路由前缀等任务。

空间代价是 Trie 的关键反例：若每个节点为一个很大的字母表预分配孩子数组，稀疏词表会浪费大量空指针；即使用映射存边，也会有许多节点和对象开销。压缩 Trie（radix tree/Patricia trie）把只有单一孩子的长路径压成一条带片段的边，以减少节点数，但会让边内比较、分裂和实现复杂度上升。字符编码、Unicode 归一化、大小写规则和 token 边界也都是实际“前缀相同”之前必须确定的语义。

## 6. 索引选择：先定义查询，再选结构

| 查询或约束 | 可考虑的结构 | 不能忽略的边界 |
| --- | --- | --- |
| 内存中精确 ID 查找 | 哈希表 | 没有范围顺序；要处理碰撞与不可信键。 |
| 动态有序键、范围/前驱后继 | AVL 或红黑树 | 节点、比较器、更新和并发成本。 |
| 大量页式持久数据、范围扫描 | B 树/B+ 树 | 页布局、写放大、事务/恢复由存储引擎决定。 |
| 前缀匹配与补全 | Trie/压缩 Trie | 稀疏分支的空间、编码与排序规则。 |
| RAG 的语义近邻 | 向量索引（如近似近邻结构） | embedding 距离、过滤、召回/延迟权衡；不是普通 Trie 或 B+ 树。 |

RAG 的最小端到端链路见 [[AI/20-LLM/70-工程应用与工具链/02-Embedding-Chunking与最小RAG|Embedding、Chunking 与最小 RAG]]。它提醒我们同一系统可能并用多个索引：哈希表按 chunk ID 找元数据，B+ 树按时间或权限范围筛选，向量索引按语义候选检索；最终合并逻辑必须写明过滤发生在何时、可能牺牲多少召回，而不是笼统地称为“数据库查询”。

对 C++ 而言，标准有序/无序容器可帮助使用这些思想，但不替你实现持久 B+ 树或向量检索系统；请先掌握 [[计算机知识/10-编程语言/02-C++/05-struct类模板与STL|struct、类、模板与 STL]] 中的容器、所有权和失效规则。

## 练习

1. 画出插入 `1` 到 `7` 的普通 BST，再写出至少一种旋转或重平衡会解决的高度问题；说明旋转前后哪些键区间必须不变。
2. 一棵 B+ 树叶页依次为 `[4, 9] ⇄ [13, 18, 21] ⇄ [30, 42]`。查询 `13 ≤ key < 30` 时，先定位哪个叶页？随后怎样扫描？
3. 为词表 `car, card, care, dog` 画 Trie，并找出哪些单孩子路径可被压缩。压缩后必须保留什么信息才能区分 `car` 与 `card`？
4. 为“公司内部知识库的 RAG 检索”列出精确 ID、权限范围、标题前缀、语义相似四类查询，并为每类选择一个候选索引及一项验证指标。

## 成功标准

- 你能说明 AVL 和红黑树都保证对数高度，但维护策略和常数取舍不同；
- 你能从页/块读取成本解释 B/B+ 树的高扇出和叶链，而不把它简化成“磁盘版 BST”；
- 你能说出 Trie 的时间随键长变化及至少两种空间/语义代价；
- 你能为一个 RAG 系统的不同查询明确区分元数据、范围、前缀与向量索引。
