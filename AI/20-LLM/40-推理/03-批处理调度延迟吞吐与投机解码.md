# 批处理、调度、延迟、吞吐与投机解码

<!-- deep-review-02 -->

## 本课目标

- 区分静态 batching 与 continuous batching；
- 理解队列、调度、抢占、chunked prefill 和公平性；
- 正确报告 TTFT、TPOT、端到端延迟和吞吐；
- 解释延迟与吞吐为什么经常需要折中；
- 说明投机解码何时能加速、何时会失败。

## 从一条请求扩展到许多请求

单请求生成的 decode 每步只新增一个 token，设备不一定被充分利用。服务引擎会把多条活跃序列在同一轮执行，使一次矩阵运算处理更多 token。与此同时，每条序列的提示长度、输出长度、到达时间和 KV cache 大小不同，调度器必须持续决定：

```text
新请求 ──> 等待队列 ──> 选择 prefill / decode 工作 ──> 设备执行
               ▲                    │                     │
               └── 抢占/恢复/拒绝 ──┴── KV 内存预算 <────┘
```

## 静态 Batching

静态 batch 先收集一组请求，把它们组成固定批次，再一起完成。长度不同常需 padding；短请求可能等最长请求，或等批次凑齐才启动。

优点是概念简单、shape 稳定、离线任务容易获得高吞吐。缺点是在线请求到达不齐、长度不一时，等待和 padding 浪费明显。

适合场景：固定数据集的离线生成、同长度基准、允许等待的批量任务。

## Continuous Batching

continuous batching（也称 iteration-level scheduling）在每轮 token 迭代重新组成活跃批次：

1. 已完成的序列立刻退出并释放槽位；
2. 新请求在资源允许时加入 prefill；
3. 仍在生成的序列继续 decode；
4. 调度器每轮根据 KV 空间和策略重新选择工作。

这样能减少“短请求等长请求”的空转，通常更适合在线服务。但它引入页式 KV 管理、请求状态、抢占、恢复和公平性等复杂度。continuous batching 不是“batch 永远越大越好”：过多并发会增加 KV 内存、排队和单请求 token 间隔。

## 调度器在权衡什么

调度器常用的预算单位是 **token 或 KV block**，不只是“请求数”。两个请求可能分别带 16 与 16,000 个 prompt token；把它们统称为 batch size 2 会隐藏真实工作量。一轮执行至少要区分：

| 记账量 | 它回答什么 | 不能代替什么 |
| --- | --- | --- |
| 活跃序列数 | 有多少条 request/sequence 驻留 | 本轮 token 总数 |
| scheduled prompt tokens | 本轮接纳了多少 prefill/chunk | 生成序列数 |
| scheduled decode tokens | 本轮为多少个位置继续生成 | 逻辑 batch 上限 |
| logical batch | 一次 API/调度决定包含的总输入 | 底层一次 kernel 的实际 shape |
| micro-batch/physical batch | 运行时如何切分逻辑 batch 执行 | 并发 request 总数 |

基准中把“batch=32”改写为上述记账，才能解释两个引擎为何在同样请求数下拥有不同的 TTFT 与 ITL。

### Prefill 与 Decode 的竞争

长 prompt 的 prefill 一次可占用很多计算；若直接插入，正在 decode 的用户可能看到 token 间隔突然变大。常见策略包括：

- **prefill 优先**：尽快让新请求得到首 token，但可能干扰正在生成的请求；
- **decode 优先**：保持流式输出平滑，但新请求可能长时间等首 token；
- **chunked prefill**：把长提示拆成多个块，与 decode 交错执行；
- **预算调度**：限制一轮处理的 token 数或 KV 增量。

### 队列顺序与公平性

- FCFS 简单，但超长请求可能造成队头阻塞；
- 短任务优先能改善平均延迟，却可能让长任务饥饿；
- 优先级队列适合服务等级，但必须限制高优先级滥用；
- age、配额或加权公平可降低饥饿风险。

### 内存不足时

引擎可能拒绝新请求、抢占低优先级请求、把 KV swap 到主存，或稍后重算被丢弃的状态。swap 节省显存但引入传输延迟；重算省主存但消耗算力。策略名称相同也不代表实现相同。

## “快”必须拆成指标

设请求发送时刻为 $t_0$，第一个输出 token 到达为 $t_1$，最后完成为 $t_{end}$，共生成 $N$ 个 token。

### TTFT：Time To First Token

$$
TTFT=t_1-t_0.
$$

它通常包含网络/入口、排队、tokenization、prefill、首 token 的采样与 detokenize/UTF-8 缓冲，以及首个流式发送。标准 decoder-only 循环中，prefill 已产生首 token 的 logits；把这个 token 再送入生成阶段的第一次 decode，是为了产生**第二个**输出 token 的 logits，不应算作首 token 的必要模型前向。某些 API 也把 prefill batch 交给名为 `decode` 的函数，报告时必须按阶段语义区分，而不能只看函数名。若只在引擎内部计时，还必须明确不含哪些部分。

### TPOT：Time Per Output Token

一种常见聚合定义为：

$$
TPOT\approx\frac{t_{end}-t_1}{N-1},\qquad N>1.
$$

它描述首 token 后的平均生成节奏。更精确的在线报告会记录 inter-token latency（ITL）的 p50、p95、p99，因为平均值会隐藏卡顿尖峰。

### 端到端延迟

$$
Latency_{e2e}=t_{end}-t_0.
$$

它是用户等到完整回答的时间。输出越长，即使 TPOT 不变，端到端延迟也会增长。

### 吞吐

在测量窗口 $\Delta t$ 内：

$$
Throughput_{out}=\frac{\text{完成的输出 token 总数}}{\Delta t}.
$$

也可以报告 request/s 或输入+输出总 token/s，但它们不能混用。高吞吐可能来自更大 batch，同时让某个请求的 TTFT/TPOT 变差。

## 一份合格的基准报告

至少固定并报告：

- 完整模型 ID、revision、tokenizer、聊天模板；
- 引擎版本、配置、量化、精度、并行方式；
- CPU/GPU、内存、驱动/后端、功耗或频率限制；
- 输入长度、输出长度、长度分布；
- 请求到达模式、并发数、持续时间和 warm-up；
- TTFT、ITL/TPOT、端到端延迟、输出吞吐的 p50/p95/p99；
- 失败、超时、拒绝、抢占和 OOM 数量；
- 测量边界是否含网络、tokenization、排队和流式传输。

只报“100 tokens/s”无法判断是单请求 decode、全服务输出吞吐，还是把输入 prefill token 也算进去了。

## 投机解码：让小模型先提案

投机解码用一个便宜的 draft 模型一次提出多个候选 token，再由 target 模型并行验证。概念流程：

1. draft 自回归提出 $k$ 个 token；
2. target 用一次前向计算这 $k$ 个候选位置以及其后下一位置的分布；
3. 按算法接受连续匹配/通过检验的前缀；
4. 在第一个拒绝位置按校正分布采样，并回滚未接受的 KV；
5. 若 $k$ 个候选全部接受，标准算法通常还从 target 的下一位置分布再采样一个 token；
6. 提交本轮接受的 token/KV，重复直到停止。

若采用带接受—拒绝校正的标准算法，目标是保持 target 原本的采样分布，而不是简单“draft 猜对就抄、猜错就改”。greedy 场景可用更直观的 token 匹配；随机采样场景需要正确的概率校正，不能自行省略。

先用“审稿”直觉理解接受长度：draft 一次写 4 个 token，target 从左到右审查。若前 3 个通过、第 4 个被拒绝，本轮只能提交连续的前缀；不能跳过第 4 个去保留更右侧的候选，因为它们的条件上下文已经改变。

记录时不要只写一个“acceptance rate”，应同时保留：`accepted_draft_tokens / proposed_draft_tokens`、每轮连续接受长度的分布、target 调用数、最终 emitted tokens，以及 draft/target 各自耗时。“平均接受 3 个”仍不等于 3× 加速，因为还有 draft、验证、校正、KV 提交/回滚和调度开销。

### 为什么可能更快

target 一次验证多个位置，比逐 token 启动多次 target 前向更有效；当 draft 便宜且接受率高，平均每次 target 调用可确认多个 token。

### 为什么可能更慢

- draft 与 target 分布差异大，接受率低；
- draft 本身不够便宜，额外计算超过节省；
- target 已经算力饱和或 batch 很大，验证没有优势；
- KV 回滚、同步和调度开销较高；
- 长上下文、采样参数或任务域改变接受率；
- 显存还需容纳 draft 权重和额外状态。

因此要同时报告 acceptance rate、平均接受 token 数、端到端指标和额外内存，不能只看理论 $k$。

## 常见误区

- continuous batching 提高设备利用率，不保证每个请求都更快。
- TTFT 不是纯 prefill 时间，除非测量明确排除了队列、网络等部分。
- TPOT 的倒数只在口径一致时近似单序列输出速度，不能直接等同服务总吞吐。
- p50 好看不代表尾延迟好；在线服务至少关注 p95/p99 与错误率。
- 投机解码不是把小模型输出当答案；target 仍负责验证和最终分布。
- benchmark 中固定长度的合成 prompt 不能代表真实长度分布和到达模式。

## 练习

1. 某请求在 0 秒发送，2 秒收到首 token，6 秒结束，共 101 个输出 token。求 TTFT、平均 TPOT 和端到端延迟。
2. 为什么把并发从 1 提升到 32 后，总吞吐可能上升，而单请求 TPOT 变差？
3. 设计一个避免 100k-token prompt 长时间阻塞普通对话的调度策略，并说出它的代价。
4. draft 每轮提案 5 个 token，但平均只接受 0.8 个。列出决定投机解码是否值得的四项测量。

<details>
<summary>核对提示</summary>

1. TTFT 2 秒，TPOT 约 $(6-2)/(101-1)=0.04$ 秒，端到端 6 秒。2. 更大 batch 提高设备利用率，却增加竞争、排队和每轮工作量。3. 可用 chunked prefill 加 decode 预算与防饥饿机制；代价是新长请求 TTFT 变大、调度更复杂。4. 至少包括 draft 成本、target 验证成本、接受率/接受长度、端到端 TTFT/TPOT/吞吐和额外显存。

</details>
