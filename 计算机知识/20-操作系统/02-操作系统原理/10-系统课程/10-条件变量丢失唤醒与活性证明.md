## 条件变量等的是谓词，不是一条永久保存的通知

设共享队列为空，消费者不能取元素。真正的条件是“队列非空或者队列已关闭”，不是“过去有人调用过 notify”。条件变量帮助线程在状态尚不满足时等待；通知本身不累计成可以无限保留的业务令牌。需要令牌计数时，信号量可能是不同的工具。

共享状态由互斥锁保护。标准条件变量等待会释放互斥锁并进入等待，再在返回前重新获得锁；与其他线程持有同一互斥锁并发出通知的协议配合，避免在“检查完条件”与“开始睡眠”之间漏掉改变。[^cond]

## 把错误时间线写出来

错误做法是：消费者加锁检查为空，自己解锁，然后调用一个不与该检查原子衔接的睡眠操作。就在解锁与睡眠之间，生产者入队并通知，此时没有等待者；消费者随后睡下。如果没有后续生产，就可能一直等，尽管队列中已有元素。

修复不是“多 notify 几次”或“睡眠前再猜一次”，而是使用条件变量所提供的释放锁并等待协议，并把谓词检查放在同一把锁下。通知不需要记住历史，因为谓词本身保存了能否继续执行的状态。

## 为什么一定要 while，不只为了虚假唤醒

考虑两个消费者同时等待一个元素。生产者放入一个元素并唤醒两个消费者。第一个拿到锁并取走元素；第二个随后返回 wait，队列已经再次为空。即使没有任何虚假唤醒，第二个仍不能凭“我被唤醒了”直接 pop。

```text
lock(mutex)
while queue.empty() and not closed:
    condition.wait(mutex)
if queue.empty() and closed:
    unlock(mutex)
    return end_of_stream
item = queue.pop()
unlock(mutex)
return item
```

wait 的返回只意味着应重新检查共享谓词，不意味着被通知时的条件为你保留。POSIX 也允许虚假唤醒，进一步要求重复检查。超时同样可能与条件变真竞态，必须在重新持锁后检查真实状态。[^cond]

## 安全性、不死锁与不饥饿分开证明

安全性可用不变量表达：队列大小始终在 0 与容量 K 之间；每个元素最多被一个消费者移除；关闭后不再接受新元素。每个修改分支都应在锁下保持这些不变量。

不死锁还要看等待关系：消费者等待生产者改变谓词时，必须释放生产者需要的互斥锁；若拿着另一把锁阻塞，而生产者也需要它，仍可能死锁。单个条件变量用对，不会自动清除整个系统的环形等待。

不饥饿则需要调度、公平锁或业务轮转等假设。notify_one 不保证一定选中某个最久等待线程；互斥锁也不必提供严格先来先服务。能证明“不发生错误消费”，不等于能证明“每个消费者在有限时间内必定拿到任务”。

## 同一条件变量上放不同谓词的风险

有界队列的生产者等“未满”，消费者等“非空”。采用两个条件变量分别通知常更清楚。如果把多种彼此不同的谓词混在一个条件变量上，只 notify_one，可能唤醒一个谓词仍不满足的线程，而真正可以前进的线程继续睡眠。在没有未来状态变化时，系统可能失去进展。

notify_all 再让各线程检查谓词可避免选错等待类别，但带来竞争和惊群。正确选择取决于状态机与等待者类别，不是“notify_one 永远更高效”的口号。

通知时是否必须持锁？修改和检查谓词必须遵守正确同步。很多正确模式允许更新后解锁再通知，也可在锁内通知；具体 API 合同、对象生命周期与析构竞态仍需核对。把“锁内通知”当公平性或无饥饿证明也不成立。

## 关闭协议是并发 API 的一部分

队列关闭后，已入队元素是否继续消费？阻塞生产者如何收到失败？等待消费者在队列耗尽时如何退出？这些要写成状态迁移。关闭通常需要唤醒所有可能因关闭而改变等待结果的线程，而不是只通知一个。

关闭标志本身即使是 atomic，也不能代替整个队列协议。多个字段的一致性仍由共同不变量约束，关联 [[计算机知识/10-编程语言/02-C++/10-系统课程/11-原子发布线性化与回收边界|原子操作的组合边界]]。异步 Queue 的 task_done 也是另一套完成计数，不能代替这里的资源和业务状态，见 [[计算机知识/10-编程语言/01-Python/10-系统课程/10-异步取消异常组与有界流水线|有界流水线]]。

## 如何测试而不靠 sleep 赌运气

实验可以用 Event 或 Barrier 控制关键阶段：确认线程已经进入“准备等待”的协议，再改变谓词；人为让多个消费者竞争一个元素；关闭时确保所有等待者退出。固定 sleep 往往只验证当前机器恰好怎样调度，不验证必须发生的次序。

本轮使用有超时上限的受控线程测试和小状态模型，验证实际条件变量守护的谓词与退出行为。有限测试不证明所有调度中的活性，因此报告将“模型检查的不变量”“实际线程运行通过”与“公平性假设”分开列出。
