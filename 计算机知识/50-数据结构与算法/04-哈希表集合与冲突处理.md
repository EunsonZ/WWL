# 04 · 哈希表、集合与冲突处理

## 本课目标

学完后，你应该能够：

- 说明哈希表如何把“按键找值”转成数组位置，并区分键、哈希值、桶和槽位；
- 用不变量解释 `put`、`get`、删除和扩容，而不是把平均 `O(1)` 当成魔法；
- 比较链地址法与开放定址法，并知道墓碑、探测序列和负载因子的作用；
- 识别碰撞、可变键、对抗性输入和哈希洪泛造成的边界；
- 把这一层连接到 Python 的 `dict`/`set`、C++ 标准库、缓存局部性及 RAG 元数据索引。

## 1. 哈希表在解决什么问题

数组可用整数下标很快地访问位置；但应用更常问“订单号 `A17` 对应什么记录？”或“这个词是否已出现？”。**哈希表**把任意可哈希的键映射到有限个数组槽位：

```text
键 key ──哈希函数 h──> 非负整数 hash ──取模/掩码──> 桶下标
"tea"  ────────────>  41                 ────────>  1（假设有 5 个桶）
```

哈希函数不需要也不可能把无限多的键映射到不同位置；不同键落到同一桶叫作**碰撞（collision）**。正确性不依赖“绝不碰撞”，而依赖碰撞后仍保存并比较原始键。

一张映射表的核心不变量是：每个已存储键至多有一个逻辑条目；从该键的初始桶，按该表的冲突规则寻找，能找到与它相等的键及其当前值。集合可看成“只有键、没有有意义值的哈希表”，因此同样天然去重。

## 2. 手算一张小表：碰撞不是错误

假设表有 5 个桶，教学用哈希值如下：`h(ann)=7`、`h(bob)=12`、`h(cy)=2`。下标为 `h(key) mod 5`：

| 键 | 哈希值 | 初始桶 |
| --- | ---: | ---: |
| `ann` | 7 | 2 |
| `bob` | 12 | 2 |
| `cy` | 2 | 2 |

三者都落入桶 2。用**链地址法（separate chaining）**时，桶 2 可以存一个小序列：`(ann, 90) → (bob, 83) → (cy, 96)`。查询 `bob` 时，先算出桶 2，再逐项比较键；键相同才读取值。若再次写入 `(bob, 88)`，应更新已有条目，而不是添加第二个 `bob`。

桶碰撞不是完整哈希碰撞：这里 7、12、2 两两不同，只是模 5 后都为 2。反过来，即使教学哈希函数让两个不同键得到同一个完整哈希值，也仍须比较原始键；例如两个不等键 `p`、`q` 都有 `h=9` 时，链地址桶必须保留两条记录，不能把 `q` 写成更新 `p`。

```text
PUT(table, key, value):
    bucket = table[h(key) 映射后的下标]
    若 bucket 中存在相等的 key：把其 value 更新为 value
    否则：把 (key, value) 加入 bucket
    若负载过高：在更大的表中按新容量重新放置所有条目

GET(table, key):
    在 h(key) 对应的 bucket 中逐项比较 key
    找到相等 key 则返回它的 value；否则报告不存在
```

这里“比较键相等”不可省略：仅比较取模后的桶下标会把 `ann`、`bob` 和 `cy` 错认成同一键。完整哈希值碰撞的不同反例同样必须比较原始键。

## 3. 两类冲突处理

### 链地址法：桶里再放小容器

优点是删除直观：从相应桶中删掉该键即可；表不是特别满时，桶通常很短。这里“特别满”不能误读为 `α < 1`：链地址法允许 `n > m`，即 `α = n/m > 1`，此时平均桶长度仍约为 `α`，只是查询的期望比较次数会随它线性增长。缺点是每个条目或链节点常有额外指针/对象开销，内存不连续时也可能不利于 [[计算机知识/30-计算机系统/04-缓存局部性带宽与延迟|缓存局部性]]。

### 开放定址法：所有条目都住在数组中

开放定址只使用一个数组；初始槽被占时，按**探测序列**继续找另一个槽。例如线性探测依次检查 `i, i+1, i+2 ...`（按表容量回绕）。它有连续数组带来的局部性，但临近满表会形成长串占用区，使查找和插入变慢。

删除是常见反例。若线性探测中 `ann` 在槽 2、`bob` 因碰撞在槽 3，直接把槽 2 清空，查询 `bob` 从槽 2 一见空位就会错误地说“不存在”。常用办法是标记为**墓碑（tombstone）**：查询继续穿过墓碑，插入可在合适时复用它；墓碑过多时需要重建表。二次探测、双重哈希等会改变探测序列，目标都是减少聚集，而不改变“按规则走到键或真正空槽”的不变量。

## 4. 负载因子、扩容与复杂度

链地址法可用一个负载因子；开放定址法则至少要区分“活条目”和“曾占用槽”：

```text
链地址法：        α = 活条目数 n / 桶数 m（可大于 1）
开放定址（live）： α_live = 活条目数 n / 槽位数 m（必须小于 1）
开放定址（occupied）：α_occupied = (活条目数 n + 墓碑数 t) / 槽位数 m
```

链地址中 `α` 上升会拉长平均桶；开放定址中，探测次数既受 `α_live` 影响，也受墓碑抬高的 `α_occupied` 影响，后者接近 1 时即使活条目并不多也可能很慢。实现会设置阈值，在超过阈值后建立更大的底层数组，或为清除墓碑以原/新容量重建，并用**目标容量**重新计算每个键的位置；只复制旧数组而不重新放置是错误的。

一次扩容或清除墓碑的重建，扫描全部 `m` 个槽并搬移 `n` 个活条目的基本工作为 `Θ(m+n)=Θ(m)`（开放定址中 `n≤m`）；重新插入的散列、比较和探测成本还要另计。若 `n` 个键都从同一槽开始线性探测，即使新容量为 `2n`，插入探测数也可为 `1+2+…+n=Θ(n²)`，因此低负载不保证重建的确定性线性总成本。在均匀散列、目标负载受控且键处理成本可忽略的模型下，重新放置的期望成本为 `O(n)`；配合成倍扩容和受控的墓碑重建触发，相关维护工作才可按**更新序列**分析期望摊还成本。扫描/搬移的线性工作、碰撞探测的期望假设和扩容触发的摊还分析是三个不同前提，不能合成“单次更新永远常数时间”。

在哈希分布均匀、负载受控且键比较成本可忽略的模型下，查找、插入、删除的**期望**成本为 `O(1)`；这是对散列/输入分布的假设，不是扩容分析。遍历是 `O(n + m)` 或至少与表的实际扫描范围有关。最坏情况下，所有键可落进同一桶或走过长探测序列，单次操作会退化为 `O(n)`。复杂度还没有计入字符串比较、对象分配、缓存未命中或安全缓解的成本。

## 5. 选择好哈希，也要保护边界

“好”通常意味着：相等键必须得到相同哈希；典型输入分布下尽量均匀；计算不应过度昂贵。它不意味着哈希值等于唯一身份，也不意味着不同键必不相同。

面向网络的服务不能假设输入友善。攻击者若能构造大量碰撞键，可能把请求处理从近似常数拉向线性，形成**哈希洪泛**型拒绝服务风险。现实运行时和库可能使用带随机种子的哈希、在长桶中采用更强结构、限制输入或另有防护；具体策略依语言、版本和键类型而变。安全边界应当是：限制请求/键大小和资源，使用受维护实现，不把“某语言有随机化”当作唯一防线。

另一个反例是可变键。键放入表后若其相等关系或哈希依据被改变，表仍在旧路径上，之后可能查不回它。Python 为什么要求字典键和集合元素可哈希，以及 `dict`/`set` 的语言层语义，见 [[计算机知识/10-编程语言/01-Python/04-容器迭代器生成器与推导式|Python 容器、迭代器、生成器与推导式]]；不要依赖某一次 `set` 的显示顺序来表达业务顺序。

## 6. 从语言容器到真实索引

| 需求 | 合适的起点 | 需要继续问的问题 |
| --- | --- | --- |
| 内存中按唯一 ID 找对象 | 哈希映射 | 键是否稳定？是否需要排序范围查询？ |
| 只判断是否见过某项 | 哈希集合 | 误判能否接受？若可，Bloom filter 是另一种权衡。 |
| C++ 中键值映射 | `std::unordered_map` | 负载、重哈希、迭代器失效和自定义哈希的契约是什么？ |
| 磁盘/网络上的大量记录 | 常常是 B+ 树等页式索引 | 不能把内存哈希表的随机访问模型直接套过去。 |
| RAG 的文档元数据 | 哈希表可按文档 ID 定位 | 向量近邻检索、过滤和召回是不同索引问题。 |

`std::unordered_map` 与 `std::unordered_set` 是哈希容器，但具体桶策略和失效规则要查标准库文档；C++ 的所有权、容器和迭代器背景见 [[计算机知识/10-编程语言/02-C++/05-struct类模板与STL|struct、类、模板与 STL]]。RAG 中 embedding、chunk 与检索分层见 [[AI/20-LLM/70-工程应用与工具链/02-Embedding-Chunking与最小RAG|Embedding、Chunking 与最小 RAG]]：文档 ID 查找不等于“从向量中找语义最近段落”。

## 练习

1. 对上面的三键表，分别用链地址法和线性探测画出最终状态；再写出查询 `cy` 访问的桶/槽顺序。
2. 假设容量为 8、已存 6 项，计算负载因子。解释若阈值为 `0.75`，下一次成功插入前后实现可能做什么，以及为什么必须重新哈希。
3. 设计一个“修改键后查不到”的抽象例子：键的哪个字段参与哈希与相等？修改后旧查找路径与新查找路径为何不同？
4. 给“用 URL 做 RAG 文档 ID 查元数据”和“按 embedding 找相似段落”各写一句索引需求，说明为什么前者可用哈希表而后者不能只靠哈希表完成。

## 成功标准

- 你能在纸上处理碰撞，并说明查询必须比较原始键；
- 你能解释负载因子、扩容与摊还复杂度，且不把平均 `O(1)` 误说成最坏 `O(1)`；
- 你能指出开放定址中“直接清空中间槽”会破坏什么不变量；
- 你能为不可信输入列出至少一种哈希洪泛以外的资源限制措施。
