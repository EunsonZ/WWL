# 模糊测试、Sanitizer 与崩溃归因

> [!abstract] 本页解决的问题
> 怎样把“解析器面对坏输入会怎样”变成有输入合同、资源预算和可复核结果的实验？只处理本包自有小程序，不生成利用链，不运行陌生二进制。

## 1. 三种检查解决不同问题

确定性测试用人为挑选的边界输入检查已知合同；模糊测试自动产生或变异大量输入，寻找未覆盖路径；Sanitizer 在编译及运行时插入检查，帮助发现某些内存错误或未定义行为。三者互补。程序返回非零可能是正确拒绝坏格式，不是崩溃；程序退出 0 也不保证没有逻辑错误。AddressSanitizer 的检测范围和开销取决于插桩、运行时与执行路径，未报错不是内存安全证明。[^v2-clang-asan]

覆盖引导模糊测试通常保留能带来新覆盖的输入，以便后续变异，而不是把随机字节数量当作学习进展。覆盖率高仍可能漏掉断言不表达的业务错误，或者绕不过校验和、认证、复杂状态等前置条件。AFL++ 文档分别讨论目标插桩、输入语料和运行设置。[^v2-afl-depth]

## 搜索策略、覆盖反馈与错误判据是三个部件

覆盖引导模糊测试不是“随机输入直到程序报错”的同义词。以 libFuzzer 为例，语料提供当前样本，变异产生候选，插桩反馈哪些程序部分被触达，再选择值得保留的输入。错误判据（oracle）则回答什么算失败，它可以来自崩溃、Sanitizer 报告或明确的语义不变量。这些功能彼此互补，但覆盖反馈本身并不等于正确性判据。[^v5-libfuzzer]

原创反例：解析器对所有合法输入都稳定返回错误数值，但不越界、不崩溃，而且所有分支都被触达。只有结构覆盖率的流程可能很满意；独立的语义参照或不变量会发现问题。另一个例子是只进入长度检查的拒绝分支：执行了一百万次仍可能没有触达核心解析逻辑。运行次数、执行速度、代码边覆盖、值特征和语义覆盖分别回答不同问题。

## ASan 与 UBSan 为什么不能互相代替

ASan 的主要目标是检测一类运行时内存访问错误，例如越界与释放后使用；UBSan 检查所启用的未定义行为类别，例如某些越界、错位访问与有符号溢出。两者都依赖构建、插桩范围和实际到达的执行路径，不能因为某次运行没有报告，就证明所有内存安全或所有 C/C++ 语义都正确。UBSan 的具体检查组也不是“一切看起来危险的数值变化”：无符号模运算与有符号溢出的语言语义不同。[^v5-asan][^v5-ubsan]

这解释了旧实验为什么保留普通构建与不同 Sanitizer 构建的区别：报告类别变化，是观察机制改变，不是把同一个错误自动变成多个独立漏洞。本轮只深化解释，没有重新运行旧版编译或模糊测试。

## 2. 先定义一个足够小的解析合同

代码真源为 [[计算机知识/Kali/07-综合实验/代码/length_record.c|length_record.c]]。输入来自标准输入，格式只有两个头部字节与 0 至 32 字节载荷：首字节必须为 ASCII `L`，第二字节为无符号载荷长度，之后必须恰好有声明数量的字节，不接受尾随数据。

例如十六进制 `4c 03 41 42 43` 表示三个载荷字节 ABC，合法；`4c 00` 是合法空载荷；空文件、仅有 `4c`、声明 3 字节却只有 2 字节、声明超过 32，以及合法记录后追加一个字节，都必须拒绝。求和只对已经验证长度的载荷执行，结果是无符号十进制整数和换行。AB 的值为 65+66=131，不把字节当成以零结尾的字符串。

程序最多读取 35 字节，足以区分最大合法记录的 34 字节与额外尾随内容。它不是通用文件格式解析器，不处理压缩、网络或多个连续记录。这里的上限是设计输入域，不是碰到失败后临时加上的限制。

## 3. 编译、观察、比较

在已复制本包代码的普通用户工作目录中：

```bash
cc -std=c11 -Wall -Wextra -Werror -O1 -g \
  -fsanitize=address,undefined -fno-omit-frame-pointer \
  length_record.c -o length_record_asan
printf 'L\002AB' | ./length_record_asan
# 预期正常输出 131，退出 0。printf 的 \002 是一个长度字节，不是字符“2”。
printf 'L\003AB' | ./length_record_asan
# 预期错误信息发往 stderr，退出 2；这是格式拒绝，不是内存崩溃。
```

编译器必须支持对应 Sanitizer，链接时也需要相同的插桩设置。GCC 与 Clang 都有相应选项，但工具链和运行时版本必须记录，不能认为在一者成功等于另一者实测。[^v2-gcc-instrument]

本包的 `test_reasoning_lab.py` 检查 Python 推理模型；C 编译与输入输出检查是独立验收项。具体命令是否在当前容器实际运行、是否启用了 ASan 或 UBSan，以 [[计算机知识/Kali/90-来源与维护/05-v3深度审阅与变更记录|v3 验收记录]] 为准。

## 4. 有限预算的模糊测试应该保存什么

本包不自动安装或启动 AFL++。在已经授权的隔离环境中准备：固定版本的插桩编译器、自有源码、少量有效与无效种子、单个输入超时、总运行预算、内存边界、输出目录，以及停止和清理方式。AFL++ 默认的标准输入模式适合本例；只有目标从文件路径读取时才需要相应文件占位形式。不要把两种输入接口混写。

记录结果时把普通拒绝、超时、操作系统信号终止、Sanitizer 报告和模糊器自身失败分开。超时可能是算法复杂度问题，也可能是资源争用；相同崩溃输入在未插桩构建中表现不同并不自动否定报告。保存触发输入、输入哈希、编译选项、运行环境、stderr 和退出状态，再用同一版本单独重现。

最小化输入是寻找保持同一失败条件的更短样本，不是删掉日志中不方便解释的部分。修复后应同时回归触发样本、邻近长度、合法最大值、空载荷及原有正常路径。若修复只是把所有输入拒绝，虽然不再崩溃，却违反功能合同。

## 最小化与去重保留什么，可能丢掉什么

最小化必须指定要保留的失败谓词。例如“仍然退出异常”和“仍然触发同一内存错误位置”强度不同；仅保留前者，缩小样本过程中可能转而触发另一种错误。按堆栈去重也只是候选分组：同一根因可能因调用路径不同得到多个堆栈，不同根因也可能在同一公共错误点结束。

一份有说服力的结论要把输入、构建身份、触达路径、错误证据、最小化条件和修复后的不变量接起来。与 [[计算机知识/Kali/06-取证逆向与检测/05-GhidraRadare2与静态逆向|静态控制流与数据流]] 对照，可以形成可反驳的根因解释；与 [[计算机知识/Kali/00-导航与方法/04-从观察到结论的安全方法|观察到结论的方法]] 对照，则能防止将“找到一个崩溃”跳写为“已证明可利用”。

## 5. 从崩溃到结论还差哪些证据

崩溃说明某个运行条件产生了错误终止；它不自动说明可远程到达、可控制指令指针或可获得权限。需要分别确认输入可达性、具体根因、影响范围和实际部署条件。本课程止于安全的根因分析、修复与回归，不把每个异常都包装成可利用漏洞。

自检：`4c 00` 被修复后的程序拒绝，是否属于成功加固？不是，本合同明确允许空载荷。`4c 20` 后有 32 个 `ff` 字节时预期和是多少？32×255=8160；这也给出当前求和范围的上界。返回 2 的短输入是否应该放进“崩溃样本”？不应，除非伴随独立的异常或检查器报告。
