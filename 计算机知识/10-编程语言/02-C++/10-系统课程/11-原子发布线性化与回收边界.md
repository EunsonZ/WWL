# 原子操作之间缺了什么：发布、线性化与内存回收

> **本页要解决**：所有字段都是 atomic，为什么整体操作仍可能错误？
>
> **先修**：[[计算机知识/10-编程语言/02-C++/10-系统课程/06-原子内存序与并发设计|从数据竞争到 happens-before：并发正确性怎样建立]]。
>
> **阅读入口**：[[计算机知识/10-编程语言/02-C++/10-系统课程/00-C++系统课程索引|本学科主索引]] · [[计算机知识/00-开始/全局导航/11-难点导读与研究证据|全局难点导读]]。

**版本、模型与证据边界**：示例以 C++20 编译；标准条文采用固定草案 N4861，库契约与特定实现性能分开讨论。

## 三种“顺序”先不要混在一起

线程内的求值顺序描述本线程的操作关系；原子对象的 modification order 为该对象的修改提供顺序；happens-before 则连接跨线程的可观察语义。它们都不是墙上时钟或两条日志的先后。一个没有建立所需同步的普通共享变量，不会因为测试时写线程先跑完就自动安全。[^cpp-race]

再区分“没有语言层数据竞争”和“满足业务规格”。每个字段都为原子可以避免对应单次访问的数据竞争，但多字段关系、操作组合和资源寿命仍可能错误。

## 一次性发布的证明应该长什么样

初始 `ready=false`，仅一个发布者写 `payload`，消费者只在读到此次 `true` 后读取，而且发布后不再修改 `payload`。

```cpp
int payload = 0;
std::atomic<bool> ready{false};
// 线程 P
payload = 42;                                      // A
ready.store(true, std::memory_order_release);       // B
// 线程 Q
if (ready.load(std::memory_order_acquire)) {        // C
    use(payload);                                 // D
}
```

证明不是“release 刷新缓存”：A 在线程内先于 B；当 C 读到 B 所写的发布值时，B 与 C 建立 synchronizes-with；C 在线程内先于 D。传递得到 A happens-before D，因而这份协议中 D 能安全观察被发布数据。若消费者读到 `false`，该路径不读取 payload；若发布后又有无保护修改，前提已被破坏。[^cpp-order]

把 B/C 都换为 `relaxed` 会保留 ready 自身的原子性，却不再提供上述发布边。重复使用同一个布尔标志还会出现“这次 true 对应哪一轮数据”的问题，需版本号、槽位协议或更简单的锁。一次性例子的证明不能直接移植成可复用队列。

## 为什么“加载，再存储”不是原子递增

```cpp
counter.store(counter.load(std::memory_order_relaxed) + 1,
              std::memory_order_relaxed);
```

两个线程都可能读到 0，然后都存 1。这段代码没有对 counter 的非原子访问，却丢了一次更新。`fetch_add` 将读改写合成一个原子操作，消除了这个特定交错。注意还需规定计数范围、溢出语义，以及计数是否要同时发布旁边的数据。

“库存大于零再扣减”也同理。一次 load 检查后再 fetch_sub，仍可能让两个线程同时通过检查。需要 CAS 循环把“检查状态并替换”绑到同一版本，或直接用锁保护整个不变量。

## 线性化点是操作规格的桥

一个并发操作若能等效为在调用与返回之间的某一点瞬间生效，且这些点排成的顺序符合顺序规格，就具有相应的线性化解释。成功 CAS 常可作为某个操作的候选线性化点，但必须证明它确实完成全部抽象效果，而不是只更新其中一个字段。

例如转账要同时满足 A 减少、B 增加、总额不变。两次原子加减之间，观察者可看到暂时少钱；即使都用 `seq_cst`，也只是给这些独立原子操作更强排序，不会创造不存在的“转账整体原子点”。用一个互斥锁覆盖转账和读取总额，反而更容易得到简单证明。对照 [[计算机知识/55-数据库/10-系统课程/10-MVCC快照写偏斜与重试协议|事务隔离]] 时，要进一步区分可串行化是否要求遵守真实时间顺序。

## ABA 与回收为什么是两个问题

线程甲读到头指针 A 后暂停；乙把 A 移出、操作其他节点，再让头值回到 A。甲的 CAS 只比较当前值，无法得知中间变化。这是 ABA。

给指针附带计数能帮助识别某些变化，但计数回绕和打包原子宽度仍有边界。更重要的是，甲在 CAS 前读取 A 的字段时，A 可能已经被释放。即使最终 CAS 因版本不同而失败，之前的释放后访问已经不合法。**检测“状态变过”不等于确保“旧对象还活着”。**

hazard pointer 的核心责任是发布保护、重新验证仍指向同一候选对象，再读取；回收者只有确认没有保护后才释放。epoch 类机制等待可能持有旧引用的读者离开相关时期。这里给的是协议动机，不是一份可直接投产的无锁实现。教学实验只模拟交错，不对未审计裸指针回收代码做安全背书。

## 无锁也不等于人人会完成

系统中总有某个操作推进的 lock-free 保证，比每个操作在有界步骤内完成的 wait-free 保证弱；某个线程仍可能反复 CAS 失败。互斥锁的死锁自由、公平性和优先级问题又是不同维度。[[计算机知识/20-操作系统/02-操作系统原理/10-系统课程/10-条件变量丢失唤醒与活性证明|活性证明]] 会要求明确调度公平与通知条件，不能从“压力测试没挂”推出活性保证。

性能方面，竞争失败、缓存行迁移和回收协议都可能超过轻量锁的成本。先给定争用率、线程数、对象大小、吞吐和尾延迟，再比较方案。不要把 lock-free 当成“更快”的缩写。

## 验收

先枚举两个线程各自执行 load/store 的所有合法交错，找到最终值为 1 的反例；再用不可拆分的读改写模型得到 2。这个模型验证的是操作组合问题，不模拟完整 C++ 弱内存执行。

实机正向实验使用 release/acquire 一次发布并对最终内容做断言。通过测试只是与证明一致的证据，不能证明所有平台、所有执行上的无竞争。最终应能指出：发布例子靠哪条边成立；转账例子缺哪个整体规格；ABA 例子为什么还需要独立回收协议。
