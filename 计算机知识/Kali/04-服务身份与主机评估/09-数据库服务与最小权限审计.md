# 数据库服务与最小权限审计

## 为什么 SQL 注入之外还需要数据库审计

先修 [[计算机知识/Kali/03-Web与API安全/06-SQL注入原理与sqlmap限界验证|输入与 SQL 语法边界]]、[[计算机知识/Kali/03-Web与API安全/08-认证会话越权与API测试|身份与授权]]。本页研究即使 SQL 已参数化，服务监听、账户映射、对象权限、加密和默认角色是否仍超出业务需要。

本包没有启动 PostgreSQL、MySQL 或 Redis。所有连接模板均为另行自建服务的参考，不自动尝试默认口令、匿名访问或真实数据库。口令不写入参数、URL 或笔记；连接前核对客户端/服务端版本和专用测试身份。

## 共同的四层边界

先确认网络暴露范围，再确认连接时采用的身份认证；随后检查该主体对库、schema、表/键和管理命令的授权；最后以极少合成记录验证业务需要。应用账户应与迁移/管理账户分开。TLS 保护传输，不会自动限制 SQL 或键命令权限。

审计结果按“能建立连接、识别到哪个数据库主体、能读取哪项对象、不能执行何操作”记录。操作系统同名用户、数据库用户和 Web 登录用户可能是三个身份，不能仅靠名字关联。

## PostgreSQL：连接规则不等于对象授权

`pg_hba.conf` 根据连接类型、数据库、用户和地址等匹配，采用第一条匹配记录；某条认证失败不会继续尝试后续更宽松记录。因此排序也是策略。Unix socket 和 TCP 连接还可能走不同规则，`localhost` 与未写 `-h` 的行为不能想当然等同。[^v2-pghba]

```bash
# 参考：自建回环 5432，已有 labreader 与 kali_lab；-W 交互提示口令。
# psql -X -W -h 127.0.0.1 -p 5432 -U labreader -d kali_lab \
#   -v ON_ERROR_STOP=1 -c 'SELECT current_user, session_user;'
```

`-X` 避免加载个人启动文件影响可复现性；`ON_ERROR_STOP` 让脚本错误明确停止，而不继续制造看似完整的输出。进入客户端后可审阅 `\conninfo`、`\du`、`\dn+` 与针对获批表的 `\dp schema.table`，输出仍需按最小范围保管。[^v2-psql]

CONNECT、schema 的 USAGE、表的 SELECT 等权限是不同条件。角色继承、对象所有者与 PUBLIC 授权会影响有效权限；只看应用账户的直接 GRANT 可能漏掉间接能力。实际运行还可能涉及行级策略，审计时明确是否启用及其适用主体。[^v2-pgpriv]

## 登录角色、继承权限与当前角色不应合成一个名字

本段按本轮读取的 PostgreSQL 18 文档解释；迁移到其他主版本应重新核对成员选项。角色成员关系可以提供继承普通权限的路径，也可以允许切换角色，两者分别受 INHERIT 与 SET 等条件约束。某条继承链中断时，间接成员关系并不自动让全部下游权限即时可用。[^v5-pg-membership]

原创推演：Alice 属于 ReportReaders，同时可切换到 ExportJob。前者的继承权限与切换后的当前角色不是同一状态。在评估同一查询时，应记录登录主体、当前有效角色、成员链和对象拥有者；否则“同一个 Alice 为什么得到不同结果”可能只是上下文被遗漏。

连接池使这类问题更隐蔽：应用用户与数据库连接身份可能不是一对一，复用连接也不自动完成应用租户上下文的重置。这是架构层推论，而非 PostgreSQL 会自动替应用实现租户隔离的保证。应用身份、数据库主体和对象租户需要明确映射，连接 [[计算机知识/Kali/03-Web与API安全/08-认证会话越权与API测试|应用授权模型]]。

## PostgreSQL 行级策略：看得到和写得进去要分别判断

行级安全（RLS）把条件应用到行的可见性或写入检查。表上的普通权限仍然需要；开启 RLS 不等于自动授予 SELECT，也不替代连接认证。`USING` 主要约束现有行的可见/可操作范围，`WITH CHECK` 约束写入后的新行能否被接受。没有适用策略时的默认拒绝与未开启 RLS 是不同配置状态。[^v3-pgrls]

用红蓝租户推演：Alice 可见红租户报告，不意味着她能把一行的 tenant 改成 blue。只验证 SELECT 阴性会遗漏 UPDATE 的新值检查；只验证 INSERT 拒绝，又不能证明现有行读隔离正确。对照至少包括同租户读取、跨租户读取、合法写入、试图改变范围字段、无匹配行与事务回滚。

### 不要用管理员身份验收普通用户策略

超级用户和带 BYPASSRLS 属性的角色可绕过行策略；表拥有者通常也绕过，`FORCE ROW LEVEL SECURITY` 可使拥有者受到策略约束，但不等于限制所有特权角色。多个策略的 permissive/restrictive 组合还会改变结果，因此应读取实际生效策略，不从单条定义推断全部权限。[^v3-pgrls]

验收应使用应用实际使用的连接角色，并记录 `session_user`、`current_user` 与角色切换。若应用通过连接池以单一数据库角色代表多个租户，数据库不会自动知道 HTTP 用户是谁。由应用提供的租户上下文必须有可信设置、生命周期与连接复用清理；允许用户自己设置的字段不能直接成为安全边界。

本页不安装或连接 PostgreSQL。实验 L 使用真实 SQLite 事务验证应用层授权与原子性，**没有模拟 PostgreSQL 的 RLS、MVCC 或连接池**。它提供问题拆解方法，不提供 PostgreSQL 配置已通过的证据。生产侧验证还需版本、扩展、视图/函数权限和实际连接配置，按既有 [[计算机知识/Kali/08-模板与速查/03-发现与复测模板|复测模板]] 保存。

## 行级策略是一个附加判定层，不是对象授权的替代品

对象级权限决定能否执行相应操作，RLS 再约束适用行；策略中的读取条件和写入条件也各有职责。默认拒绝、拥有者或特殊角色的旁路，以及启用和强制行为都需要按对象与角色核对。[^v5-pg-rls]

从集合角度看，可读行不是“所有行减去被隐藏的字符串”，而是当前主体与当前策略计算得到的集合。查询返回零行可能是没有匹配数据，也可能是行级策略排除了数据；缺乏对象权限则可能在更早阶段报错。这三种状态应在报告中区分，不能用空结果统一解释。

工具分工也随之清楚：psql 等客户端展示当前会话与查询结果，目录视图帮助核对角色和策略，应用代理记录上层请求，数据库日志提供执行背景。任何一层都不应单独承担端到端最小权限的证明。

## MySQL：核对实际匹配的账户与角色

```bash
# 参考：已有自建回环 MySQL 与专用账户；-p 后不跟口令。
# mysql --host=127.0.0.1 --port=3306 --user=labreader -p \
#   --execute='SELECT USER(), CURRENT_USER(); SHOW GRANTS;'
```

`SHOW GRANTS` 提供指定/当前账户授权信息，角色及其启用状态需要一并理解；某些角色展开可用 `USING` 相关语法，按服务端版本核对。网络登录身份与用于权限检查的匹配账户不应混淆；不要把一个主机来源的成功结果外推到所有来源。[^v2-mysqlgrants]

审阅库/表范围与管理能力，正常只读应用不应因方便而使用全局管理账户。验证写入拒绝需另设可回滚的合成对象，不在实际业务表上试一次删除来证明权限。

## Redis：命令、键和发布订阅通道分别授权

Redis ACL 可以限制用户可执行命令和可访问键模式，发布订阅通道又有对应控制。仅限制某些命令不一定限制了数据范围；仅限制键也不代表所有管理能力都被收紧。先根据应用需求列出最小命令族和命名空间。[^v2-redisacl]

```text
# 仅在你已安全认证的自建 Redis 交互客户端中审阅：
ACL WHOAMI
```

这个命令本身也可能被当前 ACL 拒绝，拒绝不等于服务不存在。负责人可在最小必要权限下核对规则，不将包含口令哈希等敏感字段的完整 ACL 导出到分享库。PING 成功只说明获准完成该命令，不证明整个数据集可读或服务安全。

## 可复核的最小验收矩阵

准备一个允许读取的教学对象、一个明确禁止的教学对象，并由负责人确认它们真实存在。专用账户读前者成功、读后者失败；应用需要的正常查询保持可用；不得拥有不必要管理能力；日志能关联本次测试但不泄露查询秘密。网络端再确认只有预期来源能到达服务。

这一页补的是数据库服务边界，不替代每种数据库的完整管理员手册。版本默认、具体密码策略、TLS 参数和集群权限需要针对实际部署进一步核查。
