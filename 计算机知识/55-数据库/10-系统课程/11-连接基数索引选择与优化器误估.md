# 执行计划为什么选错：连接基数、索引代价与统计相关性

**版本、模型与证据边界**：并发隔离等具体行为以 PostgreSQL 17 文档为例；本轮真实 SQL 运行使用 SQLite，PostgreSQL 双会话脚本未执行。

## 优化器优化的是估计代价，不是 SQL 的字数

关系表达式决定允许的结果，物理执行计划决定如何得到它。优化器在可考虑的计划空间里，根据行数、分布、索引、排序、内存与成本参数选择估计较便宜的方案。计划不好可能来自估计失真、可选路径受限、参数变化或资源差异，不必先假定“优化器不会用索引”。[^explain]

## 连接基数公式先写假设

设 R 有 100000 行、连接键有 1000 个不同值；S 有 50000 行、连接键有 500 个不同值。在键值均匀、两边值域按常见包含假设重叠、无 NULL 且只做单键等值连接的粗略模型下，可估计

$$
|R\Join S|\approx\frac{|R||S|}{\max(V_R,V_S)}=5000000.
$$

这不是普遍恒等式。若两个值域完全不相交，真实结果为 0；若少数热点键在两边都出现大量次，结果可以远大于均匀估计。主键外键连接又可利用更强的约束，不能把所有 join 一概估成两个表行数的笛卡尔积再凭感觉打折。

优化器的错误会沿计划传播。某个中间结果从预计 100 行变成 100000 行，原本合适的嵌套循环、内存哈希表或排序可能变成大量重复访问或磁盘溢写。

## 列相关性可以造成两个数量级的误估

有一百万行，字段 country 的某值占 1%，currency 的对应值也占 1%。若当作独立条件相乘，估计同时匹配 100 行；若二者在这份数据里完全对应，实际为 10000 行，相差 100 倍。

PostgreSQL 的扩展统计可以表示某些多列依赖、不同值计数及常见值组合，帮助改善特定查询估计。它不是自动理解一切业务语义的证明器；支持的谓词类别、连接条件与数据变化仍有限制，需要依文档和执行计划确认。[^stats]

```sql
-- PostgreSQL 17 示例：需要在自己的隔离测试表上运行。
CREATE STATISTICS orders_country_currency (dependencies, mcv)
ON country, currency FROM orders;
ANALYZE orders;
```

这里是说明统计对象的用法，不是在不知道你数据库规模与权限的情况下建议直接对生产库操作。本轮未执行这段 PostgreSQL SQL。

## 有索引为什么还可能全表扫描

在一个有 10000 个数据页的简化模型中，筛出 10000 行，若行均匀散布，每次访问的页面近似随机，则不同页数的期望为

$$
10000\left(1-(1-1/10000)^{10000}\right)\approx6321.
$$

随机访问 6321 个页加上索引访问，可能比顺序扫描 10000 页更贵；如果这些行物理上集中在 100 页，索引路径却很有优势。同样的选择率不代表相同 I/O 成本。缓存、预取、存储介质与回表访问方式还会改变比较。

覆盖索引也不自动等于零回表。在 PostgreSQL 的 index-only scan 中，MVCC 可见性还可能要求访问 heap，visibility map 中相应页的状态会影响真正省下多少访问。索引写入与维护也有成本，不是每加一列索引都只带来好处。[^indexonly]

## 连接算法没有脱离输入条件的冠军

嵌套循环适合外侧少且内侧查找便宜的场景；哈希连接适合能用哈希键组织并有足够内存或可接受分批处理的场景；归并连接可利用已有排序，并支持某些顺序处理优势。总行数、键分布、输出顺序要求和内存预算共同决定代价。

对需要输出数百万结果的查询，即使查找部分接近最优，传输和序列化也有不可忽略成本。LIMIT 是否能提前停止、ORDER BY 是否需要全局处理、谓词是否可下推，都是数据依赖问题，和 [[计算机知识/50-数据结构与算法/20-算法设计系统课程/09-动态规划状态充分性与优化前提|动态规划与代价模型]] 的状态选择相通。

## 先确认语义，再研究计划

`LEFT JOIN ... ON b.active=true` 保留左表所有行，对不匹配者生成 NULL 扩展；把同一条件移到 WHERE 可能过滤掉这些行，变成只保留有活跃匹配的左行。这不是“优化写法”，而是改变结果。

同样，左连接后按左键分组，COUNT(*) 对没有匹配的左行仍会计入一条 NULL 扩展行；COUNT(b.id) 在 id 非 NULL 的合同下才统计真实匹配。NOT IN 的子查询含 NULL 时还会遇到三值逻辑，改写需检查目标语义而不只看速度。

## 正确阅读 EXPLAIN ANALYZE

普通 EXPLAIN 给估计计划；EXPLAIN ANALYZE 会实际执行语句。对会写数据的语句，不能把它当无副作用的查看命令。事务回滚可以撤回很多数据库变化，但序列推进、外部函数等效果不一定全部回滚，最好使用隔离测试环境。[^explain]

实际行数与 loops 要一起读：重复执行结点的逐次统计不能误当整个查询总输出。排查时从最早明显的估计偏差开始，再看它怎样影响上游选择。BUFFERS、临时文件、排序方式、过滤行数与执行时间分别提供不同证据。不要只看到一个 Seq Scan 字样就开始强迫使用索引。

本轮验证基数模型、相关性误差、页面访问期望，以及 SQLite 上标准 SQL 子集的 NULL/外连接结果。不生成伪造的 PostgreSQL 执行计划，也不报告未实测的毫秒数。

[^explain]: PostgreSQL 17 官方 [Using EXPLAIN](https://www.postgresql.org/docs/17/using-explain.html)，估计、实际执行、loops 与写语句边界。
[^stats]: PostgreSQL 17 官方 [Statistics Used by the Planner](https://www.postgresql.org/docs/17/planner-stats.html)，扩展统计的类型与限制。
[^indexonly]: PostgreSQL 17 官方 [Index-Only Scans and Covering Indexes](https://www.postgresql.org/docs/17/indexes-index-only-scans.html)，visibility map 与 heap 可见性检查。
