# Kali定位与安装校验

## 从“装一个系统”转向“建立可信测量仪器”

Kali Linux 是面向渗透测试、安全研究和审计的 Linux 发行版，而不是能自动判断漏洞的机器。它把许多工具及其依赖组织在一起；同一工具往往也能在其他系统运行。学习收益来自协议、权限和证据解释，而不是桌面主题或工具数量。官方也明确把它定位为专业安全工作环境。[^s1]

可以把一次安全评估理解为测量实验：系统镜像相当于仪器来源，软件包版本相当于校准条件，网络位置相当于测量位置。若镜像被替换，后续扫描输出即使很漂亮也不再可信。这就是安装校验必须先于工具使用的原因。

## 选择部署方式

对一般学习，优先考虑**单独虚拟机**：方便快照、隔离和恢复，同时保留真实 Linux 用户空间。资源分配取决于宿主机与任务；作为本课程的教学起点，可尝试 2–4 个虚拟 CPU、4–8 GiB 内存及约 40–80 GiB 可扩展磁盘。这些是课程配置建议，不是官方最低配置，也不保证能运行大型图数据库或内存取证任务。

Live USB 适合需要直接接触硬件的场景，但证据设备与启动介质必须区分。裸机安装会增加误分区、驱动和恢复成本。容器共享宿主机内核，不等价于完整 Kali 虚拟机；WSL 的服务管理、原始套接字和无线硬件条件取决于具体配置，不能照搬无线章节。ARM、amd64 与虚拟化平台必须匹配，不把所有 `.iso`、`.7z` 和虚拟磁盘文件当成相同产物。

## 下载、完整性与真实性

只从官方入口选择镜像及其对应的校验文件，并查阅官方当时的签名验证流程。[^s2] **可靠 SHA-256 校验相同是字节一致性的强工程证据，不能单独证明发布者身份，也不是两个字节串必然相同的逻辑证明。** 固定长度摘要不是单射；抗碰撞描述寻找不同输入但同摘要在计算上不可行，不代表已发现实际 SHA-256 碰撞。详见 [[计算机知识/Kali/06-取证逆向与检测/01-取证流程镜像与时间线#哈希的三种保证不能混在一起|哈希、采集完整性与真实性的区别]]；依据为 [NIST 抗碰撞定义](https://csrc.nist.gov/glossary/term/collision_resistance)。 若镜像和哈希列表同时来自被替换的页面，单纯比对仍会接受伪造材料。

可复核的步骤是：先确认官方发布密钥的指纹及其可信来源，再验证校验列表的签名，最后用已验证列表检查镜像。以下命令说明操作形态，文件名需换成你实际下载的对应文件，不应凭本笔记记忆复制一个过期的密钥指纹：

```bash
# 只读取本地文件；需先按官方说明获得并核验发布密钥
# SHA256SUMS.gpg 必须对应同一个 SHA256SUMS
gpg --verify SHA256SUMS.gpg SHA256SUMS
sha256sum --check --ignore-missing SHA256SUMS
```

必须读完命令输出。`--ignore-missing` 用于只下载了部分镜像的情况，不意味着缺少目标镜像也算完成；应确认所选镜像那一行明确显示通过。GPG 的“签名数学上正确”与“这把密钥确实属于官方”是两个独立检查点。

## 第一次启动后的记录

```bash
cat /etc/os-release
uname -a
id
ip -br address
ip route
lsblk -o NAME,SIZE,TYPE,MOUNTPOINTS
```

记录安装来源、镜像 SHA-256、架构、网络适配器模式和时间。系统内核版本不等于发行版镜像版本，工具版本又是另一层。不要在报告里只写“Kali 最新版”。预制镜像可能有初始账户设置；按当前官方说明处理并立即设置你自己的口令，不在公开笔记中保存实际凭据。

完成最小初始化后做一份“干净基线”快照，下一步读 [[计算机知识/Kali/01-系统与网络基础/02-虚拟机快照与网络隔离|虚拟机隔离]] 与 [[计算机知识/Kali/01-系统与网络基础/03-APT软件源与Python环境|软件源和环境管理]]。不要第一次开机就安装全部工具、升级所有插件，再试图定位网络故障。

## 反例与自检

“我从社交平台获得了镜像，SHA-256 与同一帖子的值相同，所以一定是官方镜像。”错误在于缺少独立的发布者认证，而不是 SHA-256 算法本身失效。

“容器里能运行 Nmap，所以能进行任何无线采集。”错误在于把用户空间程序可运行推成了设备、驱动、权限和内核能力都存在。检查点见 [[计算机知识/Kali/01-系统与网络基础/02-虚拟机快照与网络隔离|虚拟化与隔离]]、[[计算机知识/Kali/05-密码无线与专门领域/04-WiFi协议与Aircrackng离线分析|无线硬件与离线分析]]。

## 镜像、元包、工具和数据版本如何衔接

镜像是某个时间点的安装入口；软件仓库是之后获得包的渠道；元包是依赖集合；真正执行的是具体二进制；扫描模板、规则和字典又是输入数据。把这五层分开，就能解释“同一镜像装出来，为什么两个同学结果不同”。一人更新了工具，另一人只更新了规则，已经不是相同测量仪器。

`kali-linux-default` 与 `kali-tools-web` 这样的名称代表不同的安装集合，而不是两种不同扫描引擎。安装“everything”既不能替你获得授权，也不让所有工具自动配置完成。需要 Web 工作流时先确认 curl、浏览器代理和一个可恢复的测试服务；需要取证时再准备镜像工具与存储空间。[^v2-kalimeta]

可把首次验收拆成五个问题：镜像摘要是否与已验证清单一致；架构是否匹配；来宾机是否从预期磁盘启动；网络是否仅接入计划中的虚拟交换网络；普通账户能否完成本机只读检查。每题保存独立证据，不把“桌面出现了”当成五题全过。

## 安装后异常的诊断树

启动失败先确定故障阶段。固件找不到启动介质，应查启动顺序、镜像挂载和架构；已经出现内核日志但无法挂载根文件系统，应查虚拟磁盘与控制器；已进入登录界面但桌面失败，才关注图形会话。不要在磁盘尚未识别时反复更换桌面环境。

网络也一样：网卡不存在、接口未启用、没有地址、路由错误、DNS 失败、TLS 验证失败是不同分支。后两者不会通过重装整个操作系统必然解决。将首次只读输出作为基线，之后每次只改变一个可解释条件，并在 [[计算机知识/Kali/01-系统与网络基础/06-TCPIP路由DNS与TLS|分层网络模型]] 中定位。

> [!question] 迁移检查
> 重装之后同一工具恢复正常，是否已经找到根因？没有。重装同时改变了包版本、配置、缓存和权限，只能说明新环境下现象未复现。有效记录仍应保留旧日志以及哪些变量发生了变化。
