# 02 · 词法分析、正则自动机、Unicode 与源位置

## 本课目标

学完后，你能说明 lexer 为什么把字符流变成 token 流；能用 maximal munch（最长匹配）解释 `>=` 与 `>` 的切分；能区分字节、码点、字素簇、编译器 token 与 LLM token；并能为诊断保留明确的 span，而不把“第 10 列”当作脱离编码和显示规则的事实。

## 直觉：解析器不应该反复从字节里猜关键字和数字

源文本先是一串字节。解码后，词法分析器按语言的词法规则把它分组为关键字、标识符、字面量、运算符、分隔符及文件结束标记；语法分析器才在这些 token 上识别表达式、语句和声明。这样 `ifx` 是一个标识符而不是 `if` 加 `x`，`123.45` 是一个数值字面量而不是五个无关字符，错误也能报告“哪个 token/span 不合法”。

```text
UTF-8 字节 ──解码与输入策略──> 码点流 ──lexer──> token 流 ──parser──> CST/AST
                                      │
                                      └── 每个 token 保存原始文本与源位置 span
```

词法分析不等于“按空格切词”。空格可能被跳过，也可能在 Python 式缩进语言中产生结构性 token；字符串内的空格不应分隔 token；`==`、`>=`、注释、转义和数值后缀都有语言专属规则。

## 1. token 的最小契约

一个 token 通常至少包含：

| 字段 | 例子 | 用途 |
| --- | --- | --- |
| kind | `Identifier`、`IntLiteral`、`GreaterEqual` | 给 parser 的类别 |
| lexeme/span | 源中的 `total` 或 `>=` 的范围 | 报错、重构、保留拼写 |
| 起止位置 | `[start, end)` | 半开区间，方便长度和拼接 |
| 可选值 | `42` 的数值、已解码字符串 | 后续语义/常量处理 |

半开区间 `[start, end)` 表示包含 `start`、不包含 `end`。相邻 token 能无缝拼接，长度为 `end - start`；空文件的 EOF span 也有自然位置。若允许错误恢复，非法字符或未闭合字符串同样应有 span，不能只抛出没有定位的“invalid input”。

### 一个完整但抽象的例子

考虑源片段：

```text
if (count >= 10) total = total + 1;
```

一种 token 序列为：

```text
Keyword(if) LParen Identifier(count) GreaterEqual IntLiteral(10) RParen
Identifier(total) Assign Identifier(total) Plus IntLiteral(1) Semicolon EOF
```

空白未成为 token，因为这门假想语言把它当作分隔符。`>=` 必须是一个 `GreaterEqual`：若先消费 `>`，留下 `=`，后续规则可能得到错误 token 序列。这正是最长匹配策略解决的典型冲突。

## 2. 正则语言与有限自动机：为何适合大部分词法规则

许多 token 类可写成正则语言：标识符是“首字符属于某类，后续字符属于某类的重复”；整数是“可选符号加一个或多个数字”；空白和行注释也可描述为有限状态模式。正则表达式、NFA（非确定有限自动机）和 DFA（确定有限自动机）在表达能力上等价：它们都只能用有限状态记住有限种过去信息。

一个实务概念图：

```text
词法规则（正则） → NFA → DFA/压缩状态机 → 扫描器
                                  │
                         接受状态标注 token kind
```

不必手工为每条规则构造 DFA 才能理解 lexer。扫描器从当前位置开始沿状态转移读取输入，并记录“最近一次到达接受状态的位置和 kind”。当再读一个单位无法转移时，它回到最近接受位置，输出那个 token，再从那里继续。这就是 maximal munch 的操作含义。

```text
扫描一个 token：
    从当前位置置为初始状态；最近接受位置为空
    只要当前状态能消费下一个输入单位：
        消费该单位并转移
        若到达接受状态：记录当前位置与 token kind
    若有最近接受位置：
        回退到它，输出对应 token
    否则：报告当前位置的非法输入，并按恢复策略前进
```

这个伪代码展示策略，不承诺某个生成器采用回退还是等价的前瞻实现。真实语言还要定义关键字优先级、注释、转义、数值溢出、Unicode 标识符和错误恢复。正则在编译器中的典型用法，与面向用户的正则搜索不同；后者的捕获、反向引用、环视和性能边界见 [[编程知识/10-基础/01-正则表达式/08-性能安全与可维护性|正则性能、安全与可维护性]]。

## 3. maximal munch 不是唯一规则：优先级与上下文仍须规定

给定规则 `>`、`>=` 和 `>>`，对输入 `>>=`，最长匹配先得到 `>>`，剩余 `=`；若语言另有 `>>=` token，则应整体输出它。相同长度的候选必须再有优先级，例如把关键字 `if` 与标识符规则都视为候选时，可先按最长匹配，长度相同再按规则优先级，使 `if` 成为 `Keyword(if)`；`ifx` 因标识符更长而成为一个 `Identifier(ifx)`。

反例是 `1-2`。词法层可以稳定切成 `IntLiteral(1) Minus IntLiteral(2)`，但不能只靠“数字前的 `-`”断定负号还是减号：`a-2`、`return -2` 与 `x * -2` 的可接受性取决于语法上下文。常见实现把 `-` 固定为运算符，由 parser/AST 的一元与二元规则判断；也有语言把带符号数值作为词法规则。两者都可行，关键是语言规范与诊断的一致性。

> [!warning] 不要把回溯型用户正则直接当 lexer 规范的性能保证
> 正则的数学语言模型与某个正则引擎的实现并不相同。含反向引用等扩展的模式可能超出正则语言，某些回溯引擎还可能对恶意输入退化。编译器 lexer 通常使用受限规则/自动机或手写状态机，并明确线性扫描与错误恢复的边界。

## 4. 五种容易被混称为“字符/词”的单位

| 单位 | 是什么 | 与 `é` 的关系 | 适合的任务 |
| --- | --- | --- | --- |
| byte | 编码后的 8-bit 值 | UTF-8 预组合形式常为两个字节 | 文件读取、字节偏移、哈希 |
| Unicode code point | Unicode 抽象编号 | `U+00E9` 是一个码点；分解形式常为两个 | 解码后的语言规则、标识符属性 |
| grapheme cluster | 用户通常视为一个书写单位 | 预组合与分解形式可各显示为一个字素簇 | 编辑器光标、显示列、用户长度 |
| compiler token | 由某门语言 lexer 按规则切出的语法单位 | 可能是标识符的一部分文本，也可能没有任何 Unicode 对应 | parser、语义分析、诊断 |
| LLM token | 某个 tokenizer/词表的可变片段 | 可把同一字素拆成多个 token，或与邻近文本合并 | 模型 ID、上下文预算 |

字节、码点、字素簇的定义、UTF-8 合法性、规范化和行尾约定由 [[计算机知识/60-数据编码与媒体系统/02-字符编码Unicode-UTF-8与换行|字符编码、Unicode、UTF-8 与换行]] 负责。本课只增加一个编译器选择：词法规范须明确它接受的输入编码、解码错误策略、Unicode 版本与标识符策略。若“看起来相同”的标识符能由不同码点序列组成，是否拒绝、规范化或保留原文都是安全与兼容性决策，不能让 lexer 暗中猜测。

LLM token 也不能拿来估计语言的 token 数：它依赖模型的 tokenizer、词表、特殊 token 和版本；详见 [[AI/20-LLM/10-原理/01-文本Unicode-Token与词表|文本、Unicode、Token 与词表]]。对于正则里的 `\w`、`.` 或边界，单位与 Unicode 行为还取决于引擎和标志，见 [[编程知识/10-基础/01-正则表达式/07-Unicode与引擎差异|Unicode 与引擎差异]]。

## 5. source location：span 是证据，line/column 是一种视图

内部位置常优先保存从文件开头计的 byte offset，或在已验证解码后保存 code-point offset；token 的原始 `[start, end)` span 可用于切片和高亮。面向人的 line/column 则要从行起点计算，且必须声明：列按 byte、代码单元、码点、显示宽度，还是 grapheme cluster 计数？制表符的 tab stop、东亚宽字符、组合字符和 emoji 都能使这些计数不同。

```text
源：  let 名 = 1;
字节：  ASCII 部分各 1；“名”的 UTF-8 占多个字节
诊断：  “Identifier 的 span 是 [4, 7)” 可以是字节范围（示意）
显示：  第几列要按编辑器的 Unicode、tab 与宽度规则重新投影
```

上例的具体数字取决于起点、编码和是否包含行尾，故故意只说明关系。可靠诊断应保存原始范围及文件版本，再在展示端统一转换；不要只存“第 5 列”，然后换编码或插入前缀后期待它仍正确。

当 lexer 遇到未闭合字符串，可报告“字符串从开引号的 span 开始，到行尾/EOF 结束”；当 parser 发现少一个 `)`，可把主诊断放在当前 token 或 EOF，并把开 `(` 的 span 作为关联信息。这样用户得到的是可行动的来源证据，而不是模糊的“parse failed”。

## 错误边界与反例

1. **最长匹配并不等于语法正确**：`a >>> b` 可被 lexer 正确切分，但目标语言是否允许该 token 序列，要由 parser 判断。
2. **token 的长度不是屏幕字符数**：一个标识符的 byte span、码点数与显示宽度可不同；把 byte offset 直接画成列会错位。
3. **关键字不能用简单子串查找**：若先匹配 `if`，输入 `ifx` 会被误切；最长匹配与同长优先级缺一不可。
4. **正规化不是无损修复**：把原始标识符改写后，可能改变符号名字、源码哈希、工具互操作或安全审计证据。需要明确语言/项目策略。

## 练习

1. 对规则 `=`、`==`、`=>`、标识符与空白，手工切分 `name==x => ifx`。写出为什么 `ifx` 不是关键字 `if` 加 `x`。
2. 给 `<=`、`<`、`<<`、`<<=` 设计最长匹配和同长优先级规则；说明输入 `<<=` 如何切分，并给出一个“最长匹配仍不够”的同长候选。
3. 选择“限制变量名为 32”的需求，分别解释 32 bytes、32 code points 与 32 grapheme clusters 会怎样不同；再说明编译器 token 与 LLM token 为什么都不是这条规则的自然替代物。
4. 为未闭合字符串设计一条诊断：写出主 span、关联 span、恢复后 lexer 应从哪里继续，以及你的策略会遗漏什么信息。

## 成功标准

- [ ] 我能从字节/文本输入说明 lexer 输出 token 流的职责，并能解释 token 的 kind、lexeme 与半开 span。
- [ ] 我能用“最后接受状态”解释 maximal munch，并说明关键字优先级和 `-` 的上下文为何另需规则。
- [ ] 我能区分 byte、code point、grapheme cluster、compiler token 与 LLM token，且按问题选择计数单位。
- [ ] 我能为错误保留稳定的原始 span，并说明 line/column 必须依赖编码与显示策略。
