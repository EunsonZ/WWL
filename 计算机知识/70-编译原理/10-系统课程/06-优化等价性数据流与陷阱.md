# 优化必须保持什么：别名、溢出、异常与浮点

> **学习位置**：[[计算机知识/00-开始/课程地图/12-编译原理-课程地图|编译原理课程地图]] · **适用边界**：教学语言与教学 IR；不把简化模型等同于 LLVM 全语义。

## “结果看起来一样”不足以证明变换合法

优化需要先规定可观察行为：返回值、外部 I/O、内存访问、异常、并发交互以及语言允许观察的其他效果。对某组测试输入结果相同，只是证据，不是覆盖全部合法输入的证明。编译器可利用语言契约，也可能因错误地假定契约而产生错编译。

常量折叠在编译期计算确定表达式，常量传播把已知值传到使用点，死代码删除去掉无可观察影响的计算。共同子表达式消除要求中间没有改变相关值或内存的操作；看起来相同的两次函数调用可能读全局状态或产生 I/O，不能随意合并。

## 一个别名反例

```c
int f(int *p, int *q) {
    int a = *p;
    *q = 9;
    return a + *p;
}
```

若 p 与 q 可以指向同一对象，不能把最后的 `*p` 总替换为 a。若语言中的合法契约能证明它们不别名，优化才有相应依据。`restrict` 等承诺不是“建议编译器尽量快”，违反承诺会改变程序是否仍属于有定义输入。

## 循环优化需要处理执行次数与异常

循环不变量外提把循环中不变的计算搬到外面；但原循环可能一次都不执行，外提后的除法却可能除零或触发其他可观察异常。需要证明安全或加守卫。强度削弱把昂贵运算替换为递推更新，也要检查溢出语义和最终可见值。

归纳变量、循环展开、融合、分块、向量化和并行化依赖不同条件。数组访问存在循环携带依赖时，不能仅看到语句相同就 SIMD 化。分块改变缓存局部性，不自动减少渐近运算次数。

## 浮点代数不是实数代数

`(a+b)+c` 与 `a+(b+c)` 可能因舍入不同；NaN、无穷、带符号零和异常环境还会影响其他看似显然的恒等式。例取 a=1e16、b=-1e16、c=1，在常见二进制双精度求值模型下，两种括号可得到 1 与 0。允许 fast-math 类假设是改变可用变换前提，不能在需要严格数值语义时无说明开启。

整数也分数学无界整数、模算术和存在未定义溢出的有符号运算。`x+1>x` 的可简化性依语言与类型而变。优化错误有时来自前端错误地把源语言环绕运算标成“不可能溢出”。

## LLVM 的精细语义不能随意简化

LLVM 区分即时未定义行为、poison、undef 等概念，并有 freeze 等操作；它们不是任意互换的“垃圾值”。给指令添加 `nsw`、`nuw`、nonnull 等标注是在提供语义承诺。本文仅建立为什么这些前提重要的直觉，具体变换必须按适用版本的 IR 参考逐条核对。

## 怎样测试优化器

用解释器作参考，对随机生成且有定义的程序比较优化前后结果；加入性质测试、变异测试、最小化失败用例，并区分生成器错误、语言未定义行为和编译器错误。翻译验证对每次变换后的程序做等价或精化检查，能够减少对整个优化实现的盲目信任，但仍依赖模型和求解范围。

**练习**：删除一个没有使用返回值的函数调用是否总安全？不安全。该函数可能写文件、抛异常、修改内存或不终止。死结果不等于死行为，必须分析效果及语言的可观察性规定。
