# 网络：DNS、TLS、HTTP 与端到端请求语义

> 阅读定位：协议以明确 RFC 为依据；模型例题注明假设。返回 [[计算机知识/00-开始/课程地图/09-计算机网络-课程地图|计算机网络 · 课程地图]]；全域入口 [[计算机知识/00-开始/全局导航/00-总学习地图|计算机知识库 · 总学习地图]]。

## 域名到服务不是一步

DNS 的递归解析器替客户端追问，权威服务器回答其负责区域的数据；缓存与 TTL 降低重复查询，但也影响变更可见时间。A/AAAA、CNAME、MX、TXT 等记录用途不同。DNS 常见于 UDP 和 TCP，也有加密传输方案；不能简单说“DNS 就只用 UDP”。

DNS 返回地址后，还需要选路、建立传输连接、进行适当安全握手，再发送应用消息。TLS 认证、密钥协商与记录保护分别负责不同功能。证书验证包含信任链、名称、有效期等，关闭验证不是合理的通用修复。

## TLS 加密不证明业务可信

TLS 1.3 保护相应传输内容，但仍可能暴露连接元数据，端点被攻陷也不在它的解决范围内。0-RTT 等机制有重放风险和使用限制，不应承载无法安全重复的操作而不加额外设计。密码学协议不宜手写，理解握手与验证边界比发明自己的加密更重要。

## HTTP 的方法、状态和缓存

HTTP 是应用语义，不是某种固定 socket 调用方式。GET 等方法的安全性语义与幂等性不同；幂等表示重复相同请求的预期效果与一次相同，不要求每次返回完全相同。POST 通常不能假设天然幂等，业务可以通过幂等键实现更可靠的重试。

状态码类别传递协议结果，但 200 不保证业务数据符合需求；4xx/5xx 也不自动给出是否可重试的完整结论。条件请求使用 ETag/Last-Modified 等验证缓存；Cache-Control、Vary 与认证上下文影响缓存能否共享。缓存键漏掉用户维度可能造成数据泄露。

HTTP/1.1、HTTP/2 和 HTTP/3 的消息组织与底层传输不同。HTTP/2 的多个流仍共享一条 TCP 字节流，TCP 丢失可能阻塞其后字节交付；QUIC 的多流交付可避免这种跨流传输层队头阻塞，但共享拥塞控制和同一应用依赖仍存在。不能据此宣称 HTTP/3 在任何网络都更快。

## 端到端重试的关键反例

服务端已经扣款并提交事务，响应在回程丢失。客户端超时后重发，会不会扣两次？TCP 的可靠性无法回答，客户端取消也无法撤回已提交事务。应让业务标识、幂等记录和扣款处在正确的原子边界里，或通过查询状态确认，而不是只延长超时。

练习：按时间线画出 DNS、连接、TLS、HTTP、数据库提交、响应丢失和重试。标记每一步的可观察证据与不可推断内容，尤其区分“请求已发送”“数据已接收”“业务已提交”。
