# 推理引擎与服务选择

<!-- deep-review-02 -->
> [!tip] 本轮深化：从当前概念继续追问
> 先固定模型、输入长度、并发、精度和质量要求，再比较引擎。某个内核更快未必改善排队延迟或首 token 时间，缓存复用还须满足权限与状态条件。 深化与验证：[[AI/12-PyTorch/09-性能剖析编译动态形状与内存账本|性能剖析编译动态形状与内存账本]]；[[AI/20-LLM/40-推理/09-KV缓存分页滑窗与前缀复用|KV缓存分页滑窗与前缀复用]]。


## 本课目标

- 从任务目标选择 Transformers、llama.cpp、Ollama、vLLM 或 SGLang；
- 区分研究库、本地运行器与高并发服务引擎；
- 为模型、格式、硬件、API、性能和安全建立验证清单；
- 设计从最小本地验证到生产服务的可回退路线。

## 先选目标，再选工具

“哪个引擎最好”缺少必要条件。先回答：

1. 是阅读模型内部、写 Python 实验，还是给用户提供 API？
2. 主要用 CPU、单 GPU、多 GPU，还是 mixed offload？
3. 模型权重是什么格式、量化方案和架构？
4. 单用户交互优先，还是多用户吞吐和尾延迟优先？
5. 是否需要结构化输出、前缀缓存、多 LoRA、分布式或多模态？
6. 能接受多复杂的依赖、运维、网络和升级成本？

## 五类工具的定位

| 工具 | 最适合从哪里开始 | 主要优势 | 主要边界 |
| --- | --- | --- | --- |
| Transformers | Python 研究、模型内部观察、原型与评测 | 模型/分词器抽象丰富，便于拿 hidden states、改 generation 与接训练生态 | 不是默认面向高并发的完整服务系统；性能和内存取决于后端与配置 |
| llama.cpp | CPU/多后端本地推理、GGUF、低依赖部署、源码学习 | C/C++ 生态、量化与跨平台后端，本地 CLI/服务入口 | 模型/量化/后端支持随版本变化；GGUF 元数据和转换来源必须核对 |
| Ollama | 快速本地体验、模型生命周期和简单 API | 安装与本地工作流相对集成，适合先验证交互 | 抽象会隐藏底层细节；模型标签、默认 context、监听地址和资源策略要复核 |
| vLLM | GPU 上的多请求在线服务 | 面向吞吐与服务的调度、KV 管理和 API 路径 | 硬件、模型、量化、并行和功能支持有版本边界；需要现场压测 |
| SGLang | 高性能模型服务、复杂生成/缓存与服务工作流 | 面向语言/多模态服务，提供调度、缓存和并行能力 | 部署栈与功能变化快；模型、后端、API 和分布式拓扑需固定版本验证 |

这些是课程定位，不是排他分类：llama.cpp 也能提供服务，Transformers 也能批处理，Ollama 也有 API。关键是它们的默认抽象和工程重点不同。

## Transformers：看得见模型内部

适合：

- 学习 tokenization、logits、attention、KV cache 与 generation config；
- 读取中间张量、写自定义 logits processor、做评测或微调衔接；
- 先验证官方/发布者权重在 Python 环境能正确加载。

需要警惕：

- `device_map`、dtype、attention backend 和量化库会改变容量与行为；
- `trust_remote_code` 可能执行仓库代码，不能对未知仓库默认开启；
- 聊天模型必须使用匹配的 tokenizer 和 chat template；
- 开发服务器或简单循环不等于生产级并发、认证、限流和观测。

## llama.cpp：量化本地与系统实现路线

适合：

- 以 GGUF 在 CPU、Apple/通用 GPU 或不同后端做本地推理；
- 在资源有限设备上尝试量化与分层 offload；
- 阅读 C/C++ 调用链、算子、内存规划和服务入口。

需要警惕：

- `.gguf` 后缀不证明模型来源、安全、tokenizer、聊天模板或量化质量正确；
- 模型架构、量化类型和后端 kernel 的支持依赖具体 commit/release；
- GPU offload 层数、context、batch 与线程设置会共同改变容量和速度；
- OpenAI 风格接口是兼容目标，不保证所有字段与云服务完全相同。

## Ollama：先把本地体验跑通

适合：

- 希望用较少配置管理本地模型并通过简单 API 调用；
- 个人学习、应用原型和小规模本地工作流；
- 先验证提示、模型选择和基本资源占用。

需要警惕：

- 模型名称或 tag 不是不可变 revision；需记录实际摘要/来源与许可；
- “本地”不自动等于“永不联网、无需认证、无数据风险”；要检查下载、遥测、监听地址和代理行为；
- 默认 context、模板、keep-alive、并发与硬件策略可能随版本变化；
- 若需要底层 kernel、精确调度或复杂分布式控制，集成抽象可能不够透明。

## vLLM：把 GPU 服务吞吐作为一等目标

适合：

- 多请求在线服务、continuous batching 和 KV 内存管理；
- 需要服务 API、张量/流水并行或较系统的 GPU 吞吐评估；
- 已有固定模型、GPU 环境和压测方法。

需要警惕：

- 支持矩阵需同时核对模型架构、量化、GPU/后端、驱动和版本；
- OpenAI-compatible 不等于每个字段、错误码、流式事件和 tokenizer 计数都完全一致；
- 为吞吐预留大量 KV 可能挤压其他进程或在长上下文下触发抢占；
- 官方性能图只能说明特定测试，不能替代本机 TTFT、TPOT、p95 与错误率。

## SGLang：服务与复杂生成工作流

适合：

- 高性能语言/多模态服务；
- 需要前缀/缓存利用、服务调度、结构化生成或更复杂执行工作流；
- 愿意固定部署栈并验证快速变化的功能边界。

需要警惕：

- runtime、模型支持、硬件后端、并行拓扑和 API 行为需按 release 复核；
- 高级缓存只在前缀、模型、适配器和执行条件兼容时才可安全复用；
- 多节点收益受网络拓扑、通信和故障恢复影响；
- 功能存在不等于目标模型上的质量、性能或稳定性已经验证。

> [!prerequisite] 服务性能与硬件先修
> TTFT、TPOT、吞吐、continuous batching 和调度见 [[AI/20-LLM/40-推理/03-批处理调度延迟吞吐与投机解码|批处理、调度、延迟、吞吐与投机解码]]；容量与 offload 见 [[AI/20-LLM/40-推理/04-推理显存量化与硬件路线|推理显存、量化与硬件路线]]；GPU 平台边界见 [[计算机知识/40-并行与异构计算/01-CUDA/00-CUDA-MOC|CUDA MOC]]。

## 选择矩阵

| 你的首要目标 | 首个候选 | 第二候选 | 先验证什么 |
| --- | --- | --- | --- |
| 看 logits/hidden states、改 Python 生成逻辑 | Transformers | llama.cpp 源码路线 | 模型 revision、dtype、模板、最小前向 |
| 无独显/CPU 为主的量化本地推理 | llama.cpp | Ollama | GGUF 来源、CPU 指令、内存、tokens/s |
| 最快建立个人本地 API 原型 | Ollama | llama.cpp server | 监听地址、模型 tag/摘要、context、资源 |
| 单/多 GPU 多人在线服务 | vLLM | SGLang | 支持矩阵、KV 预算、TTFT/TPOT/p95/吞吐 |
| 复杂服务生成、缓存或结构化工作流 | SGLang | vLLM | API 语义、缓存正确性、模型/后端支持 |
| 需要跨引擎可比性 | 至少两个最小基线 | — | 相同权重/量化是否可能、模板、停止与指标口径 |

这张表只生成候选，不做最后决定。若目标模型仅被某引擎支持，或安全/许可/运维边界不满足，应改变候选。

## 从最小验证到服务上线

### 第 1 层：来源与兼容

- 固定模型 ID、revision、文件哈希、tokenizer、chat template 和许可；
- 固定引擎 release/commit、依赖、OS、后端、驱动和硬件；
- 对需要执行远程模型代码、安装脚本或自定义扩展的步骤单独审查。

### 第 2 层：最小正确性

- 单请求、短 prompt、短输出成功；
- EOS、stop、最大输出与取消有效；
- 对已知提示检查乱码、模板重复、空输出和异常终止；
- 记录实际权重/KV/峰值内存，而非只看模型文件。

### 第 3 层：任务质量

- 用目标任务回归集比较精度/量化/引擎差异；
- 对代码、数学、长上下文、结构化输出分别测；
- 检查随机种子和非确定性边界，不凭一个样例下结论。

### 第 4 层：性能与稳定

- warm-up 后测 TTFT、TPOT/ITL、端到端延迟、吞吐与 p95/p99；
- 覆盖真实输入/输出长度分布和到达模式；
- 记录 OOM、拒绝、超时、抢占、重启和资源释放；
- 逐步增加 context 或并发，一次只改一个变量。

### 第 5 层：服务安全

- 默认只绑定 loopback，外部访问前再设计认证、TLS、限流和审计；
- 不把 prompt、输出、token、私有模型路径或密钥写进公开日志；
- 设请求大小、生成长度、并发、队列和超时上限；
- 测试客户端断开、异常输入和服务重启后的资源回收；
- 保留停服、回退版本和恢复配置的方法。

## 常见误区

- “OpenAI-compatible”不等于字节级、字段级和错误行为完全一致。
- “本地工具”不等于无需检查网络监听、下载来源、遥测和日志。
- “支持模型家族”不等于支持该 family 的每个新代际、模态或量化文件。
- 单请求 demo 成功不等于多并发服务稳定。
- 某引擎 benchmark 获胜不等于你的模型、长度分布和硬件上仍获胜。
- 更换引擎时若同时换了权重、量化和聊天模板，就无法归因性能或质量差异。

## 练习

1. 你要在无独显笔记本上阅读量化模型的本地输出，首选哪个候选？写出仍需验证的五项。
2. 你要给 50 个内部用户提供单 GPU API，为什么不应只用单请求 tokens/s 选引擎？
3. 设计 Transformers 与 vLLM 的公平对比：哪些模型、模板、长度、采样与计时边界必须一致？
4. 对一个“默认监听所有网卡”的本地服务写出最小安全回退方案。

## 成功标准

- 能用目标、硬件、格式、并发和运维约束筛选五类工具；
- 能说出每个工具至少一个优势和两个版本相关边界；
- 能设计来源→正确性→质量→性能→安全的五层验证；
- 能明确记录核验日期、未验证项和回退方法；
- 不会用“最流行”“兼容 API”或一张公开 benchmark 代替现场证据。
