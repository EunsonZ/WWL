# 06 · 断言与上下文

> [!info] 这是进阶选修
> 环视的可移植性低于字符类、分组和完整匹配 API。目标是 RE2 类引擎，或当前只需要基础搜索与校验时，可以先跳到 [[编程知识/10-基础/01-正则表达式/07-Unicode与引擎差异]]；需要“检查上下文但不把它放进结果”时再回来。

## 本课目标

在不把前后文纳入最终结果的情况下约束匹配，并判断环视是否值得使用、是否被目标引擎支持。

## 断言检查位置，不消费字符

`^`、`$`、`\b` 都是位置断言。环视则检查当前位置前后是否出现某种模式：

| 形式 | 名称 | 含义 |
| --- | --- | --- |
| `(?=...)` | 正向先行断言 | 后面必须符合 |
| `(?!...)` | 负向先行断言 | 后面不得符合 |
| `(?<=...)` | 正向后行断言 | 前面必须符合 |
| `(?<!...)` | 负向后行断言 | 前面不得符合 |

环视内的模式用于判断，但通常不会成为完整匹配的一部分。

## 先行断言示例

从文本中只提取位于 `USD` 前面的金额数字：

```regex
[0-9]+(?:\.[0-9]{2})?(?=\s*USD\b)
```

输入：

```text
19.90 USD, 120 CNY
```

结果是 `19.90`，不包含空格和 `USD`。

负向先行断言可排除特定后缀。匹配不以 `.tmp` 结尾的简单文件名：

```regex
^(?!.*\.tmp$)[A-Za-z0-9_.-]+$
```

不过，对文件系统安全规则而言，仅靠正则通常不够；仍要处理保留名、路径穿越、规范化和平台差异。

## 后行断言示例

只提取 `ID:` 后的四位数字：

```regex
(?<=ID:)[0-9]{4}
```

输入 `ID:2048` 时，结果只包含 `2048`。

很多引擎要求后行断言是固定长度；有些引擎完全不支持后行断言。若目标环境不确定，可以捕获上下文：

```regex
ID:([0-9]{4})
```

然后读取第 1 组。这通常更兼容，也更容易让初学者维护。

## 用断言组合多个条件

先只加一个条件：完整匹配一个 8 到 20 位、只含 ASCII 字母、数字或下划线，而且至少含一个数字的标识串：

```regex
^(?=.*[0-9])[A-Za-z0-9_]{8,20}$
```

确认这一版的正例、反例都符合预期后，再增加“至少一个 ASCII 字母”，得到：

```regex
^(?=[A-Za-z0-9_]{8,20}$)(?=.*[A-Za-z])(?=.*[0-9])[A-Za-z0-9_]+$
```

逐段理解：

- 第一个先行断言同时限定字符集与总长度；
- 第二个要求至少一个字母；
- 第三个要求至少一个数字；
- 最后一段实际消费字符串。

这是展示组合条件的例子，不是密码策略。密码不应被限制为狭窄 ASCII 字符集，也不能只靠复杂度正则保障安全。

## 环视何时会降低可维护性

如果捕获上下文后在代码中取组就能解决，环视不一定更好。选择时考虑：

1. 目标引擎是否支持；
2. 团队是否能快速读懂；
3. 是否需要匹配结果排除上下文；
4. 是否能用两步字符串处理表达得更直接；
5. 环视内部是否又含宽泛量词，导致性能难以判断。

## 练习

输入：

```text
ticket=1234 ticket=98765 ref=4321
```

目标：只提取紧跟 `ticket=` 的**恰好四位**数字。

1. 写一个使用捕获组的兼容版本；
2. 写一个使用后行断言的版本；
3. 确保 `98765` 不会只截取前四位；
4. 写明两个版本的完整匹配结果有什么不同。

把结果写入 [[编程知识/30-实践/01-正则表达式实验区/02-练习场#练习 6 · 上下文断言|练习场]]。

## 成功标准

- 我能解释断言为什么不消费字符。
- 我能用捕获组改写一个依赖后行断言的模式。
- 我会检查数字字段左右边界，避免只截取较长数字的一部分。
- 我知道环视属于需要核对引擎支持的能力。
