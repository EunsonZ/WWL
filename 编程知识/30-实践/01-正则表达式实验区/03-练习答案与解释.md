# 正则表达式练习答案与解释

> [!warning] 先完成，再对照
> 正则通常有多种写法。参考答案的价值在于约束、测试和解释，不在于字符最少。你的答案若通过更多边界测试并更容易维护，完全可以不同。

## 练习 1 · 三位错误码

第 1 课最小答案：

```regex
ERR-[0-9]{3}
```

用**全部查找**运行样本 A 时，它会找到 `ERR-404`、`ERR-500`，也会从 `ERR-1234` 中截取 `ERR-123`，共 3 个结果。第三个结果是本阶段有意保留的缺口：先让学习者看见边界问题，而不是提前依赖尚未学习的断言。

学完第 6 课后的严格版：

```regex
ERR-[0-9]{3}(?![0-9])
```

负向先行断言避免从更长数字中截取前三位；样本 A 此时只得到 `ERR-404` 与 `ERR-500`。这里没有擅自加入 `\b`，因为题目尚未定义左侧允许哪些字符，而且 `\b` 会随引擎的 `\w` 语义变化。若业务要求“独立 token”，应先明确定义左右允许字符，再补对应边界与样本。

## 练习 2 · 标识符

```regex
^[A-Za-z][A-Za-z0-9_]{2,11}$
```

首字符单独消费 1 位，后面 2 到 11 位，因此总长度是 3 到 12。使用 `[A-Za-z0-9_]` 明确限制 ASCII，而不是依赖 `\w` 的引擎语义。严格完整校验在 Python 中应使用 `re.fullmatch`；JavaScript 示例需保持无 `m` 的两端锚定并测试最终换行。不要再无意叠加会扩大 Unicode 大小写折叠的 `i` / `IGNORECASE` 标志。

## 练习 3 · 订单编号

```regex
^(?:PO|SO)-[0-9]{4}-[0-9]{4}$
```

前缀分组只负责选择，不需要捕获，所以使用 `(?:...)`。调用完整匹配 API 可避免接受额外前后缀；只使用 `^...$` 时还要测试目标引擎对最终换行与多行标志的处理。

## 练习 4 · 日志字段提取

Python：

```regex
^(?P<date>[0-9]{4}-[0-9]{2}-[0-9]{2}) level=(?P<level>INFO|WARN|ERROR) code=(?P<code>[A-Z][0-9]{3}) message=[^\r\n]+$
```

Python 替换：

```text
\g<level>/\g<code> @ \g<date>
```

现代 JavaScript：

```regex
^(?<date>[0-9]{4}-[0-9]{2}-[0-9]{2}) level=(?<level>INFO|WARN|ERROR) code=(?<code>[A-Z][0-9]{3}) message=[^\r\n]+$
```

JavaScript 替换：

```text
$<level>/$<code> @ $<date>
```

如果日志真实字段顺序可变，应使用日志解析器或先解析键值对。

## 练习 5 · 引号字段

```regex
".*"
".*?"
"[^"]*"
```

第一条可能从第一个引号跨到最后一个引号；第二条从最短闭合位置开始尝试，因而在当前样本中得到更小、较接近目标的局部结果；第三条明确排除引号，更直接。要观察两个字段，必须使用全部查找 API。三者都没有完整处理反斜杠转义引号。

## 练习 6 · 上下文断言

兼容捕获版：

```regex
ticket=([0-9]{4})(?![0-9])
```

后行断言版：

```regex
(?<=ticket=)[0-9]{4}(?![0-9])
```

兼容版的完整匹配包含 `ticket=`，目标数字在第 1 组；后行版的完整匹配只有数字。右侧负向断言阻止从 `98765` 截取 `9876`。这里的“兼容”只表示避免了后行断言，仍然使用负向先行断言；RE2 不支持这一断言，所以这不是 RE2 兼容版。在 RE2 宿主中可先匹配 `ticket=([0-9]{4})`，再检查完整匹配结束位置：若右邻存在且是 ASCII 数字 `0` 到 `9`，拒绝该候选；否则取第 1 组。右邻检查由宿主完成，不消费右邻字符。限制见 [RE2 官方语法的 Empty strings 表](https://github.com/google/re2/wiki/Syntax)。

## 练习 7 · Unicode 对照

### 参考趋势（不是固定答案）

- Python 3 `re` 默认 Unicode 字符串中，`\w` 通常能匹配 `hello_42`、`中文`、`１２３`、`café`；`\d` 通常也能匹配全角数字 `１２３`；
- JavaScript 中，`\w` 和 `\d` 不会自动变成覆盖所有 Unicode 文字或数字的通用类别，即使使用 `u` 也不能把 `\w` 当成自然语言单词类；
- 显式 ASCII 模式 `[A-Za-z0-9_]` 在两个环境中都只接受 `hello_42`。

最能观察匹配单位差异的是：

- Python 3 默认 `^.$` 通常能匹配 `🙂`，但不能把由 `e` 与组合附加符号组成的 `é` 当作一个点号；
- JavaScript 中，`^.$` 对 `🙂` 的结果会受 Unicode 标志影响；即使按码点匹配，也不等于按完整字素簇匹配；
- Python 默认 `^\w+$` 通常能匹配预组合的 `café`，却可能不匹配分解形式的 `é`，因为组合附加符号不一定属于 `\w`；
- NFC 规范化可能让预组合与分解形式趋于一致，但是否允许规范化取决于业务，且字素切分仍应使用平台的 Unicode API。

必须以你记录的实际语言、版本、引擎与标志运行结果为准。若要按 Unicode 属性匹配，查目标引擎的 `\p{...}` 支持。

## 练习 8 · 性能审计

### `^(a+)+$`

嵌套量词可用多种方式切分同一串 `a`，近似失败输入是若干 `a` 后跟一个不允许字符。等价需求可写为：

```regex
^a+$
```

练习场第一行已经填成完整示范：风险信号是嵌套且重叠的量词，短近似失败输入可用 `aaaa!`，而输入长度限制仍然不能省略。

### `^([A-Za-z]+\s?)+$`

外层重复与内层 `+`、可选空白形成多种分割路径，而且 `\s` 可能接受换行。若需求是以单个普通空格分隔的 ASCII 单词：

```regex
^[A-Za-z]+(?: [A-Za-z]+)*$
```

仍应限制输入长度。

### `^.*\.log$`

若只是判断固定后缀，使用字符串 `endsWith(".log")` 或等价 API 更清晰。必须用正则且输入限制为单行时，可写：

```regex
^[^\r\n]*\.log$
```

这不代表可以取消输入长度上限。

## 综合实战参考

### 任务 A · 日志

Python 命名组版本：

```regex
^(?P<timestamp>[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z) level=(?P<level>INFO|WARN|ERROR) code=(?P<code>[A-Z][0-9]{3}) message=(?P<message>[^\r\n]+)$
```

JavaScript 只需把命名组开头换为 `(?<name>...)`。时间戳仍需交给日期时间库做真实解析；若日志格式允许转义或字段乱序，应换正式解析器。

要追踪字节、解码、完整匹配、日期与单位验证怎样接成同一条链，读 [[编程知识/30-实践/01-正则表达式实验区/07-同一日志从字节到业务记录|同一日志从字节到业务记录]]；其中采用单独声明的原创版本化格式，不改变本任务的样本接口。

### 任务 B · 日期

```regex
^([0-9]{2})([/-])([0-9]{2})\2([0-9]{4})$
```

Python 替换：

```text
\g<4>-\g<3>-\g<1>
```

JavaScript 替换：

```text
$4-$3-$1
```

第 2 组捕获分隔符，`\2` 要求第二个分隔符完全相同。替换后仍要使用日期库验证。

### 任务 C · 姓名

```regex
^([^, \r\n](?:[^,\r\n]*[^, \r\n])?),[ ]+([^, \r\n](?:[^,\r\n]*[^, \r\n])?)$
```

JavaScript 风格替换：

```text
$2 $1
```

Python 风格替换：

```text
\g<2> \g<1>
```

两个捕获组都要求首尾是“非逗号、非普通空格、非换行”字符，所以会拒绝行首空格、行尾空格、逗号前空格与纯空格姓名；内部普通空格仍可保留。它只按本练习中的普通空格定义边界，不是全球姓名解析器。

更容易维护的工程方案通常是两步处理：先确认每行恰好有一个分隔逗号，再拆成两个字段、分别 `trim` 并拒绝空字段。这样比继续扩张单条姓名正则更容易处理制表符、多个空格和业务例外。

### 加分任务 · 重复单词

Python 字符串模式须同时使用忽略大小写与 ASCII 标志：

```regex
\b([A-Za-z]+)[ \t]+\1\b
```

```python
re.search(r'\b([A-Za-z]+)[ \t]+\1\b', text, flags=re.I | re.ASCII)
```

只用 Python `re.I` 时，`[A-Za-z]` 的 Unicode 大小写折叠还会接受 `İ`、`ı`、`ſ`、`K`；例如 `K K`、`İ İ`、`ſ ſ` 都能匹配。因此原来的“忽略大小写就只接受 ASCII”承诺需要上述 `re.ASCII` 限定。此时 `\b` 以 ASCII `\w`（字母、数字、下划线）与非词字符的交界定义边界：`中文The the中文` 中也能找到 `The the`；这不是自然语言的分词规则。标志与额外字符的规则见 [Python re 的 IGNORECASE 与 ASCII](https://docs.python.org/3/library/re.html#re.IGNORECASE)。

JavaScript 必须另记标志，不能套用 Python 结果。Node.js 26.8.1 / V8 14.6.202.34-node.28 对同一模式的实际结果是：`i` 对 `K K`、`İ İ`、`ſ ſ` 均不匹配；`iu` 匹配 `K K`、`ſ ſ`，但不匹配 `İ İ`；两种标志都匹配 `The the`。若需求严格限定 ASCII，可去掉 `u` 并核验目标引擎；或者在宿主中明确核验捕获内容全为 ASCII。反向引用不被 RE2 支持，这个重复词模式不能直接迁入 RE2。

## 最终检查

如果你的答案不同，逐项比较：

1. 接受集合是否相同；
2. 捕获内容是否相同；
3. 引擎与标志是否相同；
4. 对边界输入是否有意外截取；
5. 是否存在更大的回溯空间；
6. 哪一个更容易向维护者解释。
