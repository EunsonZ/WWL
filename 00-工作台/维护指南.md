# 维护指南：先解决读者的问题

稳定约定见 [[AGENTS|AGENTS.md]]。本页说明知识内容与人的使用；任务交接、并发及费用集中在 [[00-工作台/并行协作与模型路由|并行协作与模型路由]]，不在这里复制第二张模型表。日常阅读不需要先读维护文件。

## 内容、入口与记录各司其职

学科目录保存课程与知识正文；`Clippings/` 保留原文；`资料/` 登记参考材料；`TaskNotes/` 管理真实任务；`00-工作台/` 捕获疑问与实际尝试；`Logs/` 保留变更证据。默认沿用，不为一轮 AI 改进重排全库。

一个主解释可以出现在多条路线里，不需要复制成多篇。完整证明与源码保持清楚的真源，应用页保留足够上下文。历史原稿不是等待自动“修好”的草稿。正文、可选视图和个人学习记录不能互相冒充。

人从 [学科入口](../README.md)、[[00-工作台/按问题找知识|问题入口]]、搜索与相邻正文进入。[[00-工作台/知识目录.base|知识目录]] 只是辅助视图；未启用或不能显示时，普通 Markdown 和原生搜索仍应可用。[1][2]

## 一次修改应让哪里更好

先写一个具体卡点，例如“公式里的头数能否直接代入这页的显存预算”，而不是“全面提升这篇质量”。找已有说明，能回答就返回准确定位；确有缺口再修改。

审校时核对：读者能否识别对象与符号；关键跳步是否有依据；例子能否复算；条件改变后结论是否仍适用；来源是否支持所写断言。以上是问题，不是要求每页复制的固定标题。

数学看定义域与推导合法性；代码看输入、边界及可执行对照；性能看工作负载、硬件和测量口径；统计看目标量、分母、不确定性与失败处理；历史、文化与组织分析看时期、比较单位、替代解释和反例。不要把争议修成无条件定论。

提升可读性优先用必要的段内澄清、一个针对性例子、一条有理由的连接。少写维护口号，不把每段改成列表，不要求统一各学科的所有记号。没有确定改善就保留原文。

## 连接要兑现阅读承诺

链接前说明目的：前提、进一步证明、应用、比较或反例。检查目标段落实际提供承诺的内容，而不只检查文件存在。跨域歧义使用精确路径和可读别名；不要手工维护反向链接。[3]

重命名和标题修改会影响已有阅读位置，先核对入链、嵌入、标题或块引用及练习答案。可以保留旧标题或兼容入口；不要用大批重定向笔记掩盖一次没有必要的迁移。

去重必须检查最终组合：不能 A 删定义让读者读 B，同时 B 也删定义让读者读 A。新建、合并和改别名时，发布前再查相关目录与候选，因为任务启动后可能有人新增了同义解释。不同概念同名时做消歧，不强行合并。

## 属性只记录真实含义

| 字段 | 使用约定 |
| --- | --- |
| `content_status` | 按需用 `draft`、`usable`、`deprecated`；不代表事实核验完成。 |
| `evidence_status` | 按需用 `unreviewed`、`partial`、`reviewed`；核验范围与证据须可追溯，不能借局部审阅认证整页。 |
| `aliases`、`sources` | 列表；只加真实同义表达和能定位的来源。 |
| `prerequisites` | 真正必要的先修链接列表，不是所有相关文章。 |
| `stage` | 保持数字；旧 `type`、`domain`、`status` 不批量清洗。 |
| `subject_note` | 按需关联真实学习记录的主题，不推算用户掌握度。 |

属性缺省表示未记录。旧 `status: ready/reviewed` 不自动转换成已核验。不要批量补今天的日期、学习时长或完成率。已标 reviewed 的页新增未核验的实质断言时，记录受影响范围并按实际覆盖改为 partial；仅修标点不抹掉有效的历史证据。核验日期不是永远有效的认证。属性结构一致不代表概念关系正确。[4]

## 实际改进与验证

普通小修用一条任务消息说明问题、范围、原版本和验证即可。多人改动使用库外候选与必要交接记录；人不需要填计划 JSON。源码改动要同步相关测试与 `code-sync` 镜像。

维护入口已在库根实现。当前本地依赖安装在独立 `.venv` 中；从库根执行：

```bash
.venv/bin/python -B scripts/check_vault.py --require-yaml
.venv/bin/python -B -m unittest discover -s scripts/tests -v
```

实际命令与诊断等级以 [[scripts/CHECKS|维护检查说明]] 为准；环境安装、复建和版本见 [[scripts/ENVIRONMENT|本地维护与绘图环境]]。换机后入口不存在时先查库内已有维护工具；没有可复用实现则按当前任务做只读检查与人工/代理复核，不宣称全库验收。PyYAML 缺失就如实记录对应层未运行，不自动安装。各作者只运行相关轻量检查，集成边界再做适用全库检查；测试结果可在输入、输出、检查版本和环境条件不变时复用，注明复用，不假称重跑。

验收分别写清静态结构、相关执行、语义与来源、真实 Obsidian 显示、人的阅读体验。模型模拟读者只能发现候选问题，不能证明人已经理解。已有精确历史诊断不等于免修，新错误不得通过扩大白名单隐藏。

## 人的编辑与恢复

人可照常阅读、捕获疑问、写原稿和编辑非目标页。用户只需在必要时确认目标页已保存并暂时不在其他设备编辑，不需要理解哈希或线程。只在确实需要发布时协调本组目标的短窗口；无法确认未保存缓冲区、其他设备或插件写入时，保留补丁，不要求人为一批研究长时间停用整个库。[5]

本库已按用户授权初始化本地 Git；当前是否有提交以 `git status` 和历史为准，初始化本身不是可恢复快照。提交仍须按明确任务范围选择文件，不能用全库暂存代替检查。无提交基线的文件仍保存相关修改前副本与差异。迁移先在独立本地副本核对。回滚只恢复自己改过且没有更新的文件，不用旧整库覆盖现场。

日常插件保持现状，职责与按需恢复见 [[00-工作台/插件取舍|插件取舍]]。不为管理 agents 新装任务或同步平台；插件权限不等于按代理划分的安全隔离。[6]

## 停手与以后

当读者问题得到回答、关键证据匹配、必要连接完整且适用验证完成，就交付。`no_change`、有理由的争议保留和准确的未验证项都比虚构改进更有价值。

每批只留一份实际结果，[[CHANGES|CHANGES.md]] 写简短入口；候选、预算记录和代理聊天不成为人的知识页面。只有反复出现且已有反例证明必要的规则才进入长期手册，旧规则同步删改，不逐轮叠加。
