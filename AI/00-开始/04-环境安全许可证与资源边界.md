# 环境、安全、许可证与资源边界

<!-- deep-review-02 -->
> [!tip] 本轮深化：从当前概念继续追问
> 从[[AI/20-LLM/70-工程应用与工具链/09-Agent状态机幂等执行与提示注入边界|工具授权与状态机]]理解为什么生成文字不等于获准执行，从[[AI/20-LLM/80-研究拓展/04-隐私记忆成员推断与机器遗忘|隐私威胁模型]]区分私有部署、数据最小化和形式化隐私保证。


AI 实验中最容易被忽略的不是模型代码，而是边界：文件从哪里来、谁能读到、进程能连到哪里、许可证允许怎样使用、机器和费用由谁承担。本页给出面向学习与本地实验的默认策略；它不是法律意见，也不能替代组织的安全、隐私或采购政策。

## 默认边界：先小、先本地、先可清理

| 资产或行为 | 默认 | 改变默认前必须确认 |
| --- | --- | --- |
| 代码与公开配置 | 可进入 Git | 许可证、第三方来源和是否含敏感路径/标识 |
| 权重、数据集、缓存、实验输出 | 不进入 Git | 来源、许可证、大小、访问人群、保存周期与删除方式 |
| 密钥、token、cookie、私有 URL | 绝不进入 Git 或笔记 | 用受控的本地密钥机制；若疑似泄露，立即撤销/轮换并查历史 |
| 容器挂载 | 只挂精确输入目录（优先只读）与独立输出目录 | 是否会暴露宿主目录、私钥、Docker socket 或其他项目 |
| 网络端口 | 默认不发布；本地服务默认 loopback | 访问者、网络范围、认证、TLS、日志、速率限制和关闭方式 |
| GPU/云资源 | 小规模、有限时间、明确预算 | 费用上限、数据所在区域、保留策略和责任人 |

## 容器优先，不等于容器无风险

容器适合把代码、依赖和启动命令一起记录，避免每个项目都改宿主 Python。但容器仍共享宿主内核，能访问你挂进去的目录，可能使用 GPU、网络和 CPU，也可能因为错误的权限或挂载影响宿主。

开始一个容器实验前，逐项核对：

1. 镜像来自何处，是否有明确版本或摘要，是否符合项目许可证；
2. 只挂载本实验所需的精确路径；输入默认只读，输出单独存放；
3. 不挂载 Docker socket、私钥目录、凭据目录、整个家目录或不相干数据盘；
4. 不使用特权模式，不为了“好用”扩大 capability；
5. 不发布端口；确需本机服务时只监听 loopback；
6. 为下载、缓存、输出和日志设定容量与清理计划；
7. 记录镜像、依赖、硬件和执行入口，使同一实验能从干净目录重建。

## 本地服务与 Heretic：网络边界先于功能

若学习或实验使用 Heretic，一律把它视为可能读写模型、数据并接收请求的服务，而不是普通命令行工具。

**默认：只监听 loopback。** 也就是只允许同一台机器访问；不暴露到 LAN，更不能直接暴露到公网。默认不发布容器端口，也不通过路由器端口转发、反向代理或隧道绕过这条边界。

只有确实需要 LAN 访问时，才开启下面全部门禁：

| LAN 门禁 | 必须能回答的问题 |
| --- | --- |
| 必要性 | 为什么本机访问不够？预期用户是谁？ |
| 范围 | 精确网段、接口、端口和最短使用时段是什么？ |
| 身份与权限 | 有认证吗？不同用户能访问哪些模型、数据和工具？ |
| 传输保护 | LAN 是否可信？是否需要 TLS 或其他加密通道？ |
| 输入与工具 | 请求是否可能触发文件、shell、浏览器、下载或外部调用？这些能力是否默认关闭？ |
| 日志与隐私 | 日志会记录提示词、文件名、token 或个人数据吗？谁能读，何时清理？ |
| 关闭与恢复 | 如何停止服务、撤销访问、移除端口规则并确认不再监听？ |

“LAN 已经受信任”“临时开一下”“没有公网 IP”都不是跳过门禁的理由。若不能逐项回答，保持 loopback。公网暴露不属于本学习路线的默认范围；需要对外服务时，应由拥有网络、安全和运维授权的人完成独立设计与评审。

## 许可证与来源：模型、代码、数据分别核对

不要把“开源模型”当成一个统一许可证。至少分别记录：

| 对象 | 要核对的内容 |
| --- | --- |
| 代码 | 许可证文本、依赖许可证、修改与分发义务、商用限制 |
| 模型权重 | 模型卡、使用限制、地域/领域限制、再分发和衍生输出条件 |
| 数据集 | 来源、收集同意、个人数据、用途限制、删除请求与再分发规则 |
| Docker 镜像与二进制 | 发布者、版本/摘要、基础镜像、供应链与安全更新责任 |

许可证会变化，模型页与托管平台的“下载按钮”并不能代替阅读实际条款。学习记录中可保存链接、版本、核验日期和自己的使用场景摘要；不要复制受限资产或把访问令牌写进记录。

## Ubuntu、Arch 与容器各自负责什么

| 选择 | 负责的层 | 不负责的层 |
| --- | --- | --- |
| 容器 | 项目用户空间依赖、启动入口、可重建环境 | 宿主内核/GPU 驱动、网络安全、挂载数据的权限、许可证 |
| Ubuntu 原生 | APT 管理的用户空间、发行版支持周期与驱动/工具组合 | 项目依赖隔离和模型/数据许可判断 |
| Arch 原生 | pacman 管理的滚动用户空间，适合学习系统与维护实践 | 稳定 API 承诺、容器的依赖隔离、跳过整体更新策略 |

无论选择哪一种，都先学习 [[计算机知识/20-操作系统/01-Linux/08-pacman-apt-dnf与yum包管理|Linux 包管理]]和 [[计算机知识/20-操作系统/01-Linux/10-网络存储日志与故障排查|网络、存储、日志与故障排查]]。尤其在 Arch 上，避免 partial upgrade；在容器里，也要知道真正使用的是哪个宿主驱动和哪些挂载路径。

## 最小实验记录模板

每次实验至少写下以下非敏感信息：

```text
目的：要比较或验证什么？
代码与依赖：提交/版本、镜像版本或摘要、锁文件
数据：公开名称或本地分类；许可证与访问边界（不写私有链接）
资源：CPU/GPU、显存、系统内存、磁盘和运行时间上限
网络：默认离线、仅 loopback，或已通过的精确 LAN 门禁
输入/输出：挂载路径类别、保留期限、清理方式
评估：基线、指标、失败例与不能推出的结论
恢复：停止进程、撤销端口/访问、清理本次独立输出目录
```

## 练习：审阅一个“本地模型服务”计划

假设计划是“下载一个权重，用容器启动 Heretic，让朋友在局域网试用”。请列出至少五项尚未说明的边界，其中必须包含：权重许可证、数据或日志、LAN 身份与范围、端口关闭方式、容器挂载，以及服务输入能否触发外部工具。

**成功标准：** 你能明确给出“现在只能 loopback”的理由，并知道要补齐哪些授权和控制才可能进入 LAN 门禁；不会把开发便利性误当作部署授权。
