# 媒体工程安全、许可、隐私与可复现性

## 本课目标

学完后，你能：

1. 把上传的媒体、容器、字幕、路径和 URL 当作不可信输入；
2. 为解析器漏洞、资源炸弹、路径/协议/滤镜/字幕注入选择分层控制；
3. 识别媒体元数据的隐私泄漏，而不是只“去 EXIF”；
4. 设计无密钥、最小权限、资源受限的解析/转码沙箱；
5. 分开记录软件许可证、内容版权与编解码专利风险，并用 manifest 复现一次媒体产物。

> [!danger] 关键规则
> **绝不把不可信的文件名、路径、URL、metadata、字幕文本或用户给出的滤镜串拼进 FFmpeg（或任何媒体工具）的命令、协议地址或 filtergraph。** 不使用 shell 拼接，也不把“改成参数数组”误当作足够安全：若不可信内容仍能成为 `-filter_complex`、`subtitles=...`、输入 URL 或输出路径的语义，攻击面仍存在。

## 1. 先画信任边界：媒体不是“普通附件”

一个表面为 `.mp4`、`.jpg` 或 `.srt` 的对象可包含嵌套容器、异常时间戳、超大声明尺寸、损坏索引、外部引用、字体/样式、脚本式元数据或专门触发解析器缺陷的字节。扩展名和 HTTP `Content-Type` 都是发送者可控提示，不能当安全证明。OWASP 的上传指南也明确建议使用允许列表、服务端重命名、大小限制、内容验证与隔离存储，而非仅信任类型头。[OWASP File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)（核验：2026-09-03）

| 资产/边界 | 例子 | 主要风险 | 第一层控制 |
| --- | --- | --- | --- |
| 上传字节 | 视频、图片、音频、封面、归档 | 解析器漏洞、畸形容器、资源耗尽 | 隔离接收、大小/数量上限、探测与转码分离 |
| 名称与路径 | `../../x`、符号链接、Unicode 混淆 | 覆盖、越界读取、日志混淆 | 服务端随机 ID；解析后限制在受控根目录 |
| URL/协议 | `file:`, 内网 URL、playlist | SSRF、意外本地/网络读取 | 默认无网络；协议/域名/重定向允许列表 |
| 滤镜与字幕 | filtergraph、ASS 样式、外部字体 | 参数/路径注入、额外解析、资源耗尽 | 固定转换模板；不接受任意表达式/外部引用 |
| 产物与日志 | 缩略图、预览、报错 | 私人帧、位置、原路径、令牌泄漏 | 最小保留、访问控制、结构化脱敏日志 |

### 威胁例：三种“看起来只是媒体”的攻击

1. **解析器攻击**：攻击者提交畸形容器，探测阶段或缩略图服务使用有漏洞的解复用/解码库。控制是及时修补、隔离进程、最小权限和将失败对象隔离；“先用另一台服务器探测”不是修复漏洞。
2. **资源炸弹**：很小的输入声明巨大的帧尺寸、极长时长、递归 playlist 或高压缩率归档；解码后内存、CPU、磁盘或输出字节膨胀。控制是输入/输出字节、像素数、帧数、时长、并发、CPU 时间、内存、文件描述符与队列的独立上限。
3. **语义注入**：用户把一个路径伪装成字幕名，或提交一段“自定义滤镜”。即便没有 shell，工具仍可能按其自身语法解释冒号、引号、协议或外部路径。控制是只让用户选择**已定义的业务选项**（例如 `preview_720p`），后端把该 ID 映射到自有的固定参数模板；不可让原文字串进入媒体 DSL。

## 2. 接收、验证、存储：把身份同内容分开

安全的接收流程不是“正则匹配扩展名后开始转码”，而是：

```text
认证/配额 → 有界流式接收 → 随机对象 ID 的隔离存储 →
受限探测 → 策略验证 → 受限转码/生成 → 人工或自动发布门
```

- 用服务端生成的不可预测 ID 命名对象；原始文件名只作为受控显示字段，不能参与磁盘定位。
- 在写满磁盘之前拒绝：限制请求字节、每用户对象数、总存储、并发和写入速率。探测得到的时长/分辨率也要受上限，但这些字段本身来自不可信解析结果，不能单独作为安全边界。
- 对允许的容器、编解码器、像素格式、声道数、帧率、时长和输出预设采用**允许列表**。业务并不需要支持的类型就不应开放。
- 对已验收的 `asset_id`，在受控根目录的 **dirfd/目录 handle** 下原子打开目标；随后只对**同一打开的 FD/handle** 执行 `fstat`、大小/所有者/链接数与已记录 identity/hash 等验证，再把该 FD/handle 交给消费者。不能先对路径字符串做检查、再重新按路径打开；那会留下 TOCTOU 替换窗口。上传存储目录不应可执行，也不应直接作为公开 Web 根目录。
- 检测失败、超限或超时时，返回统一的用户可理解错误；把原始样本、哈希、策略命中和最少诊断送往有限权限的隔离区，**不要**把攻击字节回显到日志或工单。

## 3. 协议、路径、滤镜和字幕的四个专门边界

### 路径：字符串“在目录下”不等于文件真的在目录下

拒绝绝对路径、`..`、NUL、控制字符和未规范化编码只是起点。`realpath` 可用于日志或诊断，却是基于路径字符串的快照：它不能防止解析后替换，也不能揭示一个看似正常文件是否通过硬链接同时暴露了根目录外的对象。最稳妥的应用接口是 `asset_id`，由服务端映射到已验收的、服务端生成的对象键；不向转码 worker 传用户路径。

实际消费按能力句柄而不是路径字符串完成：

```text
打开服务独占且受控的根目录 dirfd/handle
→ 由 asset_id 取得服务端对象键
→ 相对该 dirfd/handle 原子打开对象，并拒绝不允许的链接/穿越
→ 对同一 FD/handle fstat：普通文件、设备/inode、模式、大小、链接数及已记录 hash/identity
→ 验证通过后，将该同一 FD/handle 交给探测器或转码器
```

Linux 可把 `openat2` 的 `RESOLVE_BENEATH`、`RESOLVE_NO_SYMLINKS`、`RESOLVE_NO_MAGICLINKS` 等解析约束作为一个平台实现示例；它不是跨平台承诺，其他系统需要以其目录 handle、打开语义和沙箱能力实现同一“先受控打开、后验证同一对象”的目标。即使拒绝符号链接，硬链接仍是独立边界：资产根目录必须只由服务账号写入，入库时记录并在消费 FD 上核对预期 identity；若业务要求独占对象，可要求 `st_nlink == 1`，否则要明确允许的共享策略。还要防止上传完成后仍有写者持有 FD，必要时以同一 FD 流式计算并核对已登记哈希。

若第三方工具支持受控 FD/handle 输入，就只向它传该能力句柄。若工具只能接收路径，则从已验证 FD **流式复制**到攻击者不可写的每任务私有目录，以安全创建的目标 FD 写入；对新 FD 再 `fstat`/核对长度和哈希，然后才把这个私有路径交给工具。复制前后的公开路径均不应位于用户可写目录，不能用“先 `realpath` 一次”替代这一流程。

### 协议：默认没有网络和额外读取能力

本地转码通常只需要受控文件描述符或受控 `file` 输入。若产品确实需要拉取远端媒体，另建下载服务：固定 HTTPS、解析并限制目标、阻断私有/本地地址与重定向绕过、限制 DNS 解析/连接/响应字节/时间，并把下载结果变成隔离对象后才交给解析器。FFmpeg 文档明确提供 `protocol_whitelist`，这说明协议集合应是显式配置面，而不是输入能触发什么就允许什么。[FFmpeg Protocols Documentation](https://ffmpeg.org/ffmpeg-protocols.html)（核验：2026-09-03）

### 滤镜：滤镜图是一门语言，不是普通文本字段

只允许后端拥有的预设图，例如“固定缩略图”“固定分辨率交付”。每个预设的滤镜节点、表达式、路径、字体和输出映射都应由版本控制的模板产生；用户最多传受类型/范围校验的数值（如已批准宽高中的枚举），而不是滤镜片段。把“用户自填的 filtergraph”放进 `argv` 只是避免了 shell 注入，没有避免工具自身 DSL 的路径、协议与资源解释。

### 字幕：既是文本也是富媒体输入

字幕可能含格式化、时间轴、内嵌字体/图片或样式语言；错误的时间戳会造成巨大队列或异常工作量。对不可信字幕，默认禁用 burn-in 和外部附件读取；如业务必须支持，独立解析、严格限制格式/大小/事件数/时长/样式，禁止外部字体、路径和 URL，并在同样受限的 worker 内将其规范化为可信中间表示。用户上传的字幕内容不要作为日志、命令或 HTML 直接回显。

## 4. 资源限制与沙箱：假定解析器会出错

沙箱不是一个 Docker 标签，而是一组可验证的限制：

| 层 | 最小设计 | 需要验证的证据 |
| --- | --- | --- |
| 身份 | 专用非特权 UID；只读程序与依赖 | worker 无管理员权限、无宿主敏感目录权限 |
| 文件 | 只挂载输入只读、每任务空输出与临时目录 | 无 home、SSH key、云凭据、生产配置挂载 |
| 网络 | 默认完全禁止出站/入站 | worker 无法访问内网、metadata 服务或公网 |
| 资源 | cgroup/作业级 CPU、内存、pids、FD、磁盘、时限和输出上限 | 每个超限有可观察的终止/隔离状态 |
| 系统调用/设备 | 最小 seccomp/OS 沙箱策略；不授予 GPU/摄像头等不需要设备 | 策略版本与拒绝日志可查 |
| 生命周期 | 临时目录按任务创建、结果经发布门移动 | 超时/崩溃后清理可重试且不删原始证据 |

容器和 VM 会降低影响面，却不自动解决内核漏洞、宿主挂载、网络、过宽 capability 或共享凭据。NIST SSDF 将安全实践放入整个开发生命周期；对于媒体 worker，这意味着把依赖更新、漏洞处理、构建来源、测试与事件复盘做成持续流程，而不是上线前的一次扫描。[NIST SP 800-218 SSDF](https://csrc.nist.gov/pubs/sp/800/218/final)（核验：2026-09-03）

## 5. 元数据隐私：不止 EXIF GPS

| 载体 | 可能泄漏 | 发布前处理 |
| --- | --- | --- |
| 图片 | GPS、拍摄时间、设备型号、序列号、作者/版权字段、缩略图 | 明确保留或删除字段；重新编码后复查产物 |
| 视频/音频 | 创建工具、时间、位置、章节、语言、作品/作者、编码器、轨道标签、封面 | 对每条流和容器 metadata 制定允许列表 |
| 字幕/附件 | 人名、公司、文件路径、修订痕迹、隐藏 cue、字体/附件 | 单独审计，不把“移除视频 metadata”当作已处理 |
| 日志/可观测性 | 原始路径、签名 URL、用户 ID、片段内容、错误转储 | 字段最小化、访问控制、保留期限与脱敏审查 |

隐私不是“一律删光”：版权归属、语言、无障碍字幕和拍摄许可有时必须保留。应由数据用途决定字段允许列表，形成**原始受控对象 → 脱敏公开对象**的单向发布门，并抽样复查公开下载物。切勿把秘密 URL、访问令牌或私人原路径写入 manifest、命令行或构建日志。

## 6. 许可证、版权与专利：三张不同的表

这不是法律意见，也不能用一次 `LICENSE` 扫描替代法务判断。至少分开：

| 问题 | 需要追踪的对象 | 常见误区 |
| --- | --- | --- |
| 软件许可证 | FFmpeg/库、编译选项、静态/动态链接、插件、字体、脚本、容器基础镜像 | “工具开源，所以我的分发没有义务” |
| 内容版权/授权 | 原始媒体、封面、音乐、字幕、训练/测试片段、派生交付物 | “我能下载/转码，所以我能公开发布” |
| 编解码专利/商业条款 | 实际启用的编码器/解码器、目标国家/地区、分发/流媒体商业模式 | “软件许可证允许，就没有专利或合同问题” |

SPDX 是一种用于交换软件组件、许可证和版权元数据的开放标准；它有助于把已知事实结构化，但不做合规或法律解释。[SPDX 概览](https://spdx.dev/about/overview/)（核验：2026-09-03）因此 manifest 可记录 SPDX 标识、来源与审查状态，却不能写“已合规”来替代适用地区、发行方式和权利链的人工确认。许可不清、专利边界不明或内容授权缺失时，应停止外部分发并请求法务/权利人确认。

条文分析的CS消费者见[[计算机知识/75-软件工程与人机交互/09-专业沟通许可与软件可持续性#固定组件：文本版本与利用行为共同决定问题|组件—文本—行为情境]]：MIT/Apache2/GPLv3/AGPLv3分别按内部单机、分发与网络交互重算条件，再返回这里区分媒体内容/字体/编解码专利；代码许可与SPDX扫描都不替其他对象授权。

## 7. 可复现 manifest：让“同样转一次”有证据

一个媒体产物的 manifest 是事实记录，不是隐藏配置或密钥仓库。至少包括：

| 类别 | 必填字段示例 |
| --- | --- |
| 身份与来源 | 任务 ID、创建时间、操作者/自动化身份、原始对象 ID、原始字节 SHA-256、来源/授权记录引用 |
| 输入解释 | 容器/流探测摘要、时长、色彩/HDR、音频布局、字幕/附件状态；拒绝原因若未通过 |
| 工具链 | 工具版本、二进制/镜像哈希、依赖/预设版本、构建来源、沙箱策略版本 |
| 确定性配置 | 预设 ID、固定参数模板版本、随机种子（如有）、线程/硬件/驱动、时区与时间基处理 |
| 执行边界 | 网络是否禁用、资源上限、开始/结束、退出类别、输入/输出字节与哈希 |
| 质量与发布 | 已用指标/模型版本、评测数据/对齐规则、人工复核引用、许可/隐私检查状态、输出对象 ID 与 SHA-256 |

不要记录 token、密码、私有签名 URL、完整个人路径或原始私人帧。不要声称字节级可复现，除非已控制编码器版本、硬件/驱动、线程、随机性、时间戳、metadata 和构建环境，并以输出哈希实际验证。做不到时，应如实标为“配置可复现”或“语义可复现”，并报告允许差异与验收方法。

## 练习：为一个公开预览服务写发布门

场景：用户上传一个视频和一个可选字幕文件，服务只提供 720p 预览。写出：

1. 五项明确的允许列表/数值上限；
2. 一个以 `asset_id` 而非用户路径驱动的状态流转；
3. 协议、filtergraph、字幕分别如何被禁止或映射到固定模板；
4. worker 的 UID、挂载、网络和资源限制，以及某一限制失败后的隔离动作；
5. 公开产物的 metadata 允许列表、三类权利记录和最小 manifest 字段。

### 成功标准

- [ ] 我的设计没有让不可信字符串成为命令、URL、路径或滤镜/字幕 DSL 的一部分。
- [ ] 我会在受控 dirfd/handle 下原子打开，再对同一 FD/handle `fstat` 与核对 identity；不能接收 FD 的工具只获得攻击者不可写任务目录中的受控副本。
- [ ] 我同时限制了输入大小、解码工作量、输出大小和并发，而不是只检查扩展名。
- [ ] 我能解释为什么无网络、无密钥、非特权身份和资源上限缺一不可。
- [ ] 我分开记录软件许可证、内容授权与专利/合同边界，并在不确定时停止外部分发。
- [ ] manifest 不含秘密或个人路径，且能定位确切输入、工具链、配置与输出哈希。

## 导航与恢复边界

本页快速事实已于 **2026-09-03** 核验。它没有执行上传、转码、联网抓取、发布、删除或许可证判断。若实验 worker 接触可疑媒体：停止消费该对象、保留最小证据（对象 ID、哈希、策略/版本与受限日志）、隔离产物、更新/复测解析链，再由授权人员决定是否恢复；不要把对象转存到个人目录或重新在宿主机裸跑。
