# 运行时：对象布局、栈堆、闭包、异常与 GC

## 本课目标

学完后，你应该能够：

- 从语言值语义推导对象表示：字段、对齐、object header、tagged value 与类型信息；
- 解释 activation record 如何承载参数、局部值、返回信息、异常与 GC 所需元数据；
- 判断闭包捕获何时逃逸，以及环境对象为何可能从栈语义转为堆分配；
- 比较引用计数、mark-sweep、分代与移动式 GC 的不变量、成本和组合方式；
- 解释 root、safepoint 与 write barrier 怎样让编译代码和收集器协作；
- 描述异常展开期间 RAII/finally 的清理顺序，并避免把“最终会 GC”误当作确定资源释放。

## 1. 直觉：运行时是语言承诺的执行合约

源语言可能承诺“值有动态类型”“闭包可在函数返回后继续使用捕获变量”“异常会执行清理”“对象地址是否稳定”等语义。编译器必须选择表示，运行时必须提供服务，两者通过 ABI、元数据与屏障协议配合。

```text
source value semantics
    -> compiler representation choice
    -> object/frame metadata
    -> generated load/store/call/barrier code
    -> runtime allocation, dispatch, unwind, collection
```

同一种语言语义可以有多种实现。局部对象不等于必然在机器栈上；堆分配也不等于必然由追踪 GC 管理。实现选择必须保持语言可观察行为，同时权衡吞吐、暂停、内存、代码尺寸与互操作性。

## 2. 语言对象与 object header

一个堆对象常可抽象为 header 加 payload：

```text
object:
    header:
        type_or_shape
        gc_state_bits
        optional_lock_or_hash_state
        optional_size
    payload:
        field_0
        field_1
        ...
```

header 的具体字段不是普遍真理。实现可把类型指针压缩、把若干状态位打包、用外部 side table 保存锁或 GC 信息，甚至让某类对象没有统一 header。对象布局还受字段对齐、继承、接口/虚表、数组长度和 ABI 约束影响。

编译器访问字段时依赖布局描述：

```text
address_of_field(obj, field_k):
    shape = read_shape(obj)
    offset = lookup_offset(shape, field_k)
    return obj.base + offset
```

静态已知类型可以直接使用常量偏移；动态语言可能使用 shape 检查、inline cache 或慢路径。无论快慢路径，布局版本与类型检查必须一致。

## 3. Tagged value：一个机器字承载多类值

动态语言常让一个 value 表示小整数、布尔、空值或对象引用。若对象地址对齐后低位恒为零，可借部分位作为 tag：

```text
encode_small_integer(n):
    return shift_left(n, tag_bits) OR integer_tag

decode_value(v):
    if low_bits(v) == integer_tag:
        return small_integer(shift_right_arithmetic(v, tag_bits))
    else:
        return heap_reference(mask_tag(v))
```

边界包括：

- 可直接编码的整数范围小于完整机器整数范围，溢出时可能装箱；
- 指针压缩、地址空间与硬件指针认证会约束可用位；
- GC 必须准确区分“看起来像地址的整数”和真实引用；
- 相等、哈希与算术需要处理立即值和装箱值的统一语义。

反例：仅凭“某个字落在堆地址范围”猜它是引用会产生 conservative false positive；若运行时承诺精确 GC，就必须由 tag、类型图或栈图精确识别。

## 4. Activation record：一次调用的运行时状态

每次函数激活需要保存一部分状态，抽象的 **activation record（栈帧）**可能包含：

```text
frame:
    return_continuation
    previous_frame_or_unwind_link
    saved_registers
    parameters_and_local_slots
    spill_slots
    exception_handler_metadata
    gc_stack_map_identity
```

优化后并非每个源变量都有固定槽位：它可能只在寄存器中、被常量折叠、拆成多个值或完全消失。内联也会让多个源级调用共享一个物理帧，但调试信息与异常元数据仍需重建逻辑调用链。

栈图（stack map）可在特定程序点说明哪些寄存器和槽位保存托管引用。收集器不能把任意 bit pattern 都当作精确 root，也不能漏掉仍活跃的引用。

## 5. 闭包、捕获与逃逸

闭包可抽象为代码入口与环境：

```text
closure:
    code_pointer
    environment_pointer

environment:
    captured_x
    captured_y
```

若闭包只在创建函数内部调用，环境可能被标量替换或保存在当前帧；若闭包被返回、写入全局、交给异步任务或未知调用，环境就可能在创建函数返回后仍存活。

```text
function make_counter():
    count = 0
    function next():
        count = count + 1
        return count
    return next              // closure and mutable capture escape
```

这里多个调用共享同一个可变 `count` 单元，不能简单地在每次调用中复制当前整数。实现常把捕获槽装入环境对象，或为可变捕获再建 cell。

反例：闭包语法出现不代表一定堆分配；逃逸分析若证明闭包不越过当前动态范围，可以消除分配。反过来，仅因源变量写在“局部作用域”也不能断言它安全地留在机器栈上。

## 6. 内存管理的四类策略

### 6.1 引用计数（RC）

引用计数在建立和删除拥有引用时调整计数，降为零即可回收：

```text
assign(slot, new_obj):
    old_obj = slot
    retain(new_obj)
    slot = new_obj
    release(old_obj)
```

优势是回收时机相对局部、概念直接；成本包括频繁计数更新、并发原子开销、释放级联，以及普通 RC 无法独自回收强引用环。weak reference、周期检测或与 tracing GC 混合可以补足部分问题。

### 6.2 Mark-sweep

mark-sweep 从 roots 追踪可达对象，再清扫未标记对象：

```text
mark_from_roots():
    worklist = all_roots()
    while worklist not empty:
        obj = pop(worklist)
        if not marked(obj):
            mark(obj)
            push_all_references(obj, worklist)

sweep_heap():
    for obj in heap_objects:
        if not marked(obj): reclaim(obj)
        else: clear_mark(obj)
```

它能处理环，但朴素实现需要遍历堆，可能暂停应用并留下碎片。并发、增量和分区实现会增加不变量与屏障复杂度。

### 6.3 分代 GC

分代收集利用“许多对象很快死亡”的经验假设，把新对象放入年轻代，频繁收集小区域；存活对象可能晋升到老年代。

收集年轻代时不能只扫描年轻对象：老对象可能引用年轻对象。运行时用 remembered set 记录跨代边，写屏障在指针写入时维护它：

```text
store_reference(owner, slot, value):
    slot = value
    if owner is old_generation and value is young_generation:
        remember(owner_or_slot)
```

屏障若漏记，年轻对象可能被误回收；过度记录通常保持正确但增加时间和空间成本。

### 6.4 移动式 GC

复制或压缩型收集器会移动存活对象以减少碎片、改善局部性或快速回收整块区域：

```text
move(obj):
    new_obj = copy_to_destination(obj)
    install_forwarding_pointer(obj, new_obj)
    update_all_references(obj, new_obj)
```

其核心义务是更新所有引用：roots、对象字段、寄存器、栈槽、运行时表和本地代码中的句柄。若外部原生代码长期持有裸地址，需要 pinning、handle 或互操作协议；“对象移动后旧指针自然有效”是错误假设。

这些策略可组合：例如年轻代复制、老年代 mark-sweep/compact，并辅以特定对象的引用计数或区域分配。标签描述算法家族，不足以推断具体暂停与吞吐。

## 7. Root、safepoint 与精确存活信息

**Root** 是追踪起点，常来自线程栈/寄存器中的活引用、全局变量、运行时句柄和特定 VM 表。root 集合不是“堆外所有字节”。

**Safepoint** 是运行时能够可靠解释线程状态并协调 GC 的位置。编译器在调用、循环回边或显式 poll 等位置关联 stack map：

```text
loop_backedge:
    if gc_requested:
        spill_live_references_according_to_map()
        enter_safepoint()
    jump loop_header
```

若 safepoint 太少，线程可能长时间无法停下；太密则增加 poll、元数据和优化约束。并发 GC 也不意味着完全没有 safepoint，它通常仍需要某些握手或短暂停顿来建立一致快照。

## 8. Write barrier 不只是“多执行一条指令”

屏障维持收集器的不变量。除分代 remembered set 外，并发标记可能要求在写入时标记新引用、记录旧引用或把对象加入队列：

```text
gc_aware_store(owner, slot, new_value):
    old_value = slot
    pre_write_barrier(owner, old_value)
    slot = new_value
    post_write_barrier(owner, new_value)
```

具体需要 pre、post 还是两者取决于算法。编译器可在证明写入不可能跨代、目标刚分配且尚未发布等条件下消除部分屏障，但错误省略会造成活对象丢失。屏障优化同样需要合法性证明，不能只因 profile 显示它很热就删掉。

## 9. 异常展开、RAII 与 finally

异常把控制从抛出点转移到匹配 handler。运行时根据 unwind metadata 沿调用链查找处理器，并执行沿途清理：

```text
try:
    resource = acquire()
    may_throw()
finally:
    release(resource)
```

或以 RAII 抽象：

```text
scope:
    guard = construct_resource_guard()
    may_throw()
on every scope exit:
    destroy(guard)
```

编译器必须让正常返回、显式抛出和展开路径执行语义要求的清理，而且顺序正确。内联、尾调用、代码移动和 DCE 都要保留 landing pad、cleanup edge 或等价元数据。

重要边界：

- GC 管的是托管内存可达性，通常不保证文件、锁、事务等资源在确定时刻释放；
- RAII/finally 提供词法或控制流上的清理语义，不能由“以后 finalizer 会运行”替代；
- finalizer 可能延迟、顺序不稳定、让对象复活，甚至程序退出前不执行；
- 清理自身抛异常时的规则由语言决定，不能假设总会覆盖或总会保留原异常。

## 10. 端到端例子：返回一个捕获对象的闭包

考虑：

```text
function make_reader(path):
    handle = open(path)
    buffer = allocate_buffer()

    function read_next():
        return read(handle, buffer)

    return read_next
```

实现必须分别回答：

1. `read_next` 逃逸，所以捕获环境必须活过 `make_reader` 的 activation record；
2. 环境中哪些字段是 GC 引用，必须进入类型图或对象扫描描述；
3. 若 GC 移动 `buffer`，闭包环境里的引用必须更新；
4. `handle` 是外部资源，不能只等待 GC；语言/API 应提供显式 close、RAII 或 finally 协议；
5. 若内联 `read_next`，优化器仍需保持资源和异常语义；
6. 运行期间若写入捕获字段，生成代码可能需要 write barrier。

这个例子显示：栈帧、闭包、对象布局、GC 与异常不是孤立章节，而是一组共享元数据和控制流契约。

## 11. 常见误解与反例

- “局部变量都在栈上”：寄存器、标量替换、闭包环境或堆分配都可能改变表示。
- “堆对象一定由 GC 管”：手动分配、区域分配、RC 与追踪 GC 都可能使用堆。
- “有 GC 就不会泄漏”：被全局容器意外保持的对象仍然可达，逻辑泄漏依旧存在。
- “移动 GC 会让所有指针失效”：遵守 handle/root 更新协议的托管引用会被修正；违规保存的裸地址才危险。
- “引用计数立即释放一切”：环、异步释放、批量延迟 decrement 或 finalizer 会改变时机。
- “finally 只在异常时执行”：多数语言还要求它在正常离开相应作用域时执行；精确规则以语言规范为准。
- “concurrent GC 没有暂停”：并发阶段可减少暂停，但 root 快照、重定位或线程握手仍可能需要停顿。

## 练习

1. 为“整数、布尔、空值、对象引用”设计 tagged value 伪布局，计算 tag 占用后小整数范围，并列出 GC 判别规则。
2. 画出一个 activation record：标出返回 continuation、两个 spill、一个托管引用、异常 handler 和 stack map；说明内联后哪些是逻辑帧信息。
3. 对三个闭包分别判断逃逸：立即调用、返回给调用者、提交给异步队列；说明环境可采用的表示与不可采用的表示。
4. 构造两个对象互相强引用的 RC 反例，并给出 weak edge、周期检测或 tracing 三种解决思路的边界。
5. 设计一个老年代对象指向年轻代对象的写入；模拟没有 write barrier 时一次 minor collection 如何误回收。
6. 写出异常跨越两层调用时的清理顺序，包含两个 RAII/finally 资源；再说明内联不能改变什么。
7. 对 `make_reader` 例子给出资源关闭 API，并区分“释放文件句柄”和“回收 buffer 内存”的责任。

## 成功标准

- 你能区分源级作用域、activation record 与物理栈/堆分配决定；
- 你能描述 closure 的代码指针、环境和可变捕获 cell，并用逃逸解释生命周期；
- 你能比较 RC、mark-sweep、分代和移动式 GC，指出至少一个不变量与失败模式；
- 你能从 roots、stack map、safepoint 和 write barrier 串起一次安全收集；
- 你能说明异常展开中 RAII/finally 的次序，以及为什么 GC/finalizer 不能替代确定资源释放；
- 你会把地址空间、页面与 ABI 细节链接到系统权威课程，而不在运行时课程中复制一遍。
