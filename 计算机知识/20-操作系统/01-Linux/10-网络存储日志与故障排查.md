# 网络、存储、日志与故障排查

「网页打不开」不是一个足够小的问题：网卡可能未连接，地址或路由可能不对，DNS 可能无法解析，服务也可能根本没有监听；磁盘空间不足和内核设备错误同样会让服务表现得像“网络坏了”。本课建立一条可重复的诊断路径：先观察，再定位层次，最后才讨论一项最小、可回退的改动。

## 学完能做什么

- 解释接口、IP 地址、前缀、路由、DNS、端口和 socket 分别回答什么问题；
- 用 `ip`、`ss`、`ping`、`resolvectl` / `dig` 和 `curl` 收集互不混淆的网络证据；
- 用 `lsblk`、`blkid`、`findmnt`、`df`、`du`、`smartctl` 只读地判断存储的结构、空间和健康线索；
- 用 `journalctl`、`dmesg`、服务状态及时间/启动过滤缩小日志范围；
- 按“现象 → 层次 → 证据 → 最小变更 → 回退”处理故障，而不是随机重启或复制命令。

## 1. 先把网络问题拆成层次

| 层次 | 核心对象 | 它回答的问题 | 常用观察命令 |
| --- | --- | --- | --- |
| 链路 | 接口（如 `enp1s0`、`wlan0`） | 内核是否看见设备？链路是否 `UP`？ | `ip link` |
| 地址 | IP 地址与 prefix（如 `192.0.2.10/24`） | 本机以哪个地址、哪个本地网络身份通信？ | `ip addr` |
| 转发 | 路由与默认网关 | 去往某个目标的下一跳和出口是什么？ | `ip route`、`ip route get` |
| 名称 | DNS resolver、搜索域与记录 | 名称能否按当前解析策略得到地址？ | `resolvectl`、`dig` |
| 传输 | TCP/UDP 端口与 socket | 进程是否在正确的地址/端口监听或已建立连接？ | `ss` |
| 应用 | HTTP、TLS、认证、代理 | 服务是否按应用协议作出预期回应？ | `curl` |

**接口**是内核的网络端点；物理网卡、Wi-Fi、回环 `lo`、虚拟机网卡和 VPN 都可表现为接口。**IP 地址**标识一个网络层端点。IPv4 例子 `192.0.2.10/24` 中的 `/24` 是 prefix length：对连续的 IPv4 网络掩码，它等价于 `255.255.255.0`；在路由语境中，它更直接地表达前 24 位是网络前缀，并参与判断哪些目的地可在本链路直接寻找邻居。

**路由**把目的地址映射为下一跳、出口接口和其他属性；`default` 是没有更具体匹配时的兜底规则，并不保证那个网关或互联网真的可达。**DNS** 是名称到记录的查询与策略（也可能有 VPN 的 split DNS），不是 TCP 连通性测试。**端口**是传输层的 0–65535 编号；**socket**是内核中的通信端点，至少结合协议、地址和端口，且还可关联到进程。一个 TCP 服务“在 443 端口运行”通常更精确地说是“某些 socket 正在监听某些本地地址的 TCP 443”。

## 2. 先观察接口、地址和路由

下面的 `ip` 命令来自 iproute2，均为只读查询；不加 `sudo` 即可运行。名称会随硬件、虚拟化和发行版的命名策略变化，因此不要假定一定有 `eth0` 或 `wlan0`。

```bash
# 简洁查看接口状态和地址；lo 是本机回环接口。
ip -br link
ip -br addr

# 完整路由表，以及“如果发往该文档保留地址会如何选路”。
# route get 只查询内核选路，不会发送数据包。
ip route
ip route get 192.0.2.1
```

先从输出提取事实：目标接口是否存在、是否显示为 `UP`，是否有预期的 IPv4/IPv6 地址，是否有 `default via … dev …`。再看 `ip route get <实际目标 IP>` 是否选到意外接口、VPN 或错误网关。不要把 `UP` 误读为“网络已经可用”：它只能说明管理状态，不能证明电缆、Wi-Fi 认证、DHCP、网关或 DNS 成功。

`ip addr`、`ip link`、`ip route` 是 `ip` 的不同对象视图；旧教程中的 `ifconfig` 和 `route` 在不少系统可能未安装，且不应混用来推断现代系统状态。若你只需要查看，不要执行 `ip addr add`、`ip route replace`、`ip link set down` 等改变连接的命令。

### NetworkManager 与 systemd-networkd：只说明分工

它们都是**配置/管理网络**的组件，不是诊断层本身。桌面和笔记本常由 NetworkManager 处理 Wi-Fi、VPN、用户会话与连接配置；较精简的服务器、容器或固定拓扑常使用 `systemd-networkd`。发行版也可能使用其他管理器。一个接口应由一个明确的管理者负责，避免多个服务争夺同一份地址、路由或 DNS 配置。

本课用内核可见的 `ip` 和 `ss` 收集证据，不教修改任一管理器的配置。确需改动时，先确认谁拥有该接口、记录原连接配置，并准备本地控制台或其他管理通道；远程 SSH 会话中改网络尤其容易把自己锁在门外。

## 3. DNS、ICMP 与 HTTP 各能证明什么

```bash
# 只验证本机协议栈与回环路径，不接触外部网络。
ping -c 3 127.0.0.1

# 在 systemd-resolved 正在运行时，查看它实际采用的 DNS 服务器和域。
resolvectl status
resolvectl query example.com

# 直接做 DNS 查询；不等同于“所有应用都在用同一 resolver”。
dig example.com

# 同时经过名称解析、连接、TLS 与 HTTP；HEAD 不是所有站点都支持。
curl --connect-timeout 3 --max-time 10 -I https://example.com
```

`ping` 发送 ICMP 回显请求。回环成功只证明本机协议栈的很小一段正常；对网关或远端主机的 ping 失败也不能单独证明“网络断了”，因为对方或中间网络可能过滤 ICMP。外部 ping 和 `curl` 会产生网络流量，并向目标站点暴露你的源地址及常规客户端元数据；仅在你有权测试的地址上使用。

`resolvectl` 是 systemd-resolved 的客户端：若该服务未运行、系统不用 systemd，或命令未安装，它并不适用。`/etc/resolv.conf` 也可能是指向 systemd-resolved 的 stub 文件、NetworkManager 管理的文件或静态文件，不能只凭文件内容推断最终策略。`dig` 通常来自 BIND 工具集，它显示一次查询的回答；它可能绕过应用的缓存、搜索域、split DNS 或加密 DNS 路径。要测试特定服务器可写 `dig @<DNS服务器地址> example.com`，但这验证的是该服务器，不代表系统默认解析器。

`curl` 成功才是从客户端角度更接近“该 URL 可用”的证据，但仍不等于其他应用可用：代理、SNI/TLS、认证、应用权限和服务端策略都可能不同。`-I` 请求 HTTP `HEAD`；若服务不支持它，应改为对你有权限的测试端点发普通 `GET`，并保留时间上限，避免无限等待。

### 发行版、安装包与权限边界

命令名称相同不代表每个系统都预装或功能完全一致。先用 `command -v ip ss ping resolvectl dig curl` 查看本机是否有该程序，并用 `man <命令>` 查看**本机版本**的选项。

| 工具 | 常见来源 / 差异 | 权限与边界 |
| --- | --- | --- |
| `ip`、`ss` | 通常来自 `iproute2`；极简系统可能只有 BusyBox 的简化实现 | 查询一般无需 root；`ss -p` 的进程归属对其他用户可能需要 root |
| `ping` | 常见为 `iputils`；部分系统以 capability 允许普通用户使用 | 有些旧式或受限系统需要 root；ICMP 结果受防火墙影响 |
| `resolvectl` | 仅在 systemd-resolved / systemd 工具可用时成立 | 查询通常无需 root；不代表非 systemd 系统的 DNS 状态 |
| `dig` | Debian/Ubuntu 常见包名 `dnsutils`，Fedora 为 `bind-utils`，Arch 为 `bind` | 查询无需 root；不同包名不应被当作故障本身 |
| `curl` | 各发行版通常提供 `curl` 包 | 外部请求会留下服务器访问记录；不要把令牌放进 URL 或命令行 |

## 4. 用 socket 证明服务是否真的在听

```bash
# TCP 监听 socket；-n 保留数字形式，避免额外名称解析。
ss -lnt

# UDP socket；UDP 没有 TCP 式“listen”，不要按 TCP 状态理解它。
ss -lnu

# 加 -p 尝试显示拥有 socket 的进程；部分条目需要 sudo 才完整可见。
ss -lntp

# 查看已建立的 TCP 连接及队列，适合排查某客户端是否已连上。
ss -nt state established
```

重点读 `Local Address:Port`：`127.0.0.1:8080` 只允许本机访问，`0.0.0.0:8080` 通常表示监听所有 IPv4 地址，`[::]:8080` 则关系到 IPv6；这些结论还会受应用套接字选项和防火墙影响。**没有监听 socket** 时，优先检查服务是否启动、是否读到了正确配置、是否因端口冲突退出；**有监听但外部连不上** 时，再分别检查路由、地址族、主机防火墙、上游 ACL/安全组与 DNS 指向。

不要使用 `ss -K`：该选项会尝试强制关闭 socket，不是诊断命令。

## 5. 存储：先分清设备、文件系统、挂载与空间

一块磁盘不是一个可直接使用的目录。大致链条是：物理/虚拟**块设备**（如 `/dev/sda`、`/dev/nvme0n1`）→ 分区或 LVM/RAID/加密层 → **文件系统**（ext4、xfs 等）→ **挂载点**（目录树中可见的位置）。同一逻辑文件系统也可能有 bind mount；容器看到的挂载层次又可能不同。

从目录树、块设备到挂载点的详细关系见 [[计算机知识/20-操作系统/01-Linux/03-目录结构挂载与文件系统|目录结构、挂载与文件系统]]；从硬件、驱动、udev 到块设备节点的上游链条见 [[计算机知识/20-操作系统/01-Linux/09-设备驱动内核模块与udev|设备驱动、内核模块与 udev]]。

```bash
# 设备拓扑、大小、文件系统类型和 UUID；不会挂载或修改设备。
lsblk --fs

# 读取可识别的文件系统/分区标识；有些设备信息需 sudo 才能完整显示。
blkid

# 某路径实际位于哪个挂载点；/var 只是示例，请按现象替换。
findmnt -T /var

# 已挂载文件系统的容量与 inode 使用率。
df -hT
df -ih

# 当前目录下一层的空间归因；-x 不跨越其他文件系统。
du -xhd1 .
```

`lsblk` 面向设备树，`blkid` 面向签名/UUID，`findmnt` 面向当前挂载关系，`df` 面向已挂载文件系统的可用块和 inode，`du` 则从目录树累计文件占用。它们回答不同问题：`df` 显示磁盘“满了”，不表示最大目录一定在当前工作目录；`du` 很大，也未必解释已删除但仍被进程打开的文件。两者不一致时，先记录挂载点、容器/命名空间和服务状态，再继续检查，勿贸然删除日志或缓存。

### SMART 只提供健康线索

```bash
# 仅读取指定磁盘的扩展 SMART/设备信息；必须先从 lsblk 确认精确设备名。
sudo smartctl -x /dev/sda
```

`smartctl` 来自 `smartmontools`，通常需要 root 才能访问设备；NVMe、USB 转接器、RAID 控制器和虚拟磁盘的支持、设备路径和字段各不相同。当前上游手册已不建议对 ATA 设备使用较旧的 `-a`，因为它不包含需要 48-bit ATA 命令的扩展信息；本页因此使用 `-x`。SMART 的“通过”不是数据安全保证，“失败”或持续增长的介质/错误计数也不应只靠重启解决：优先备份、保留证据，并按硬件/运维流程处理。上例只读，不包含自检触发、格式化、分区、挂载、卸载、修复或删除数据的操作；不要把 `/dev/sda` 原样复制到别的机器。

## 6. 日志：把时间、启动和服务放进同一个问题

在 systemd 系统上，journal 可按服务、时间和本次/上次启动筛选：

```bash
# 当前启动（-b）中，某服务最近 30 分钟的日志；-e 跳到末尾。
journalctl -b -u ssh.service --since "30 minutes ago" -e

# 上一次启动的内核/服务相关日志；-1 表示前一次 boot。
journalctl -b -1 -p warning..alert

# 服务当前状态、最近日志和退出码线索。
systemctl status ssh.service

# 内核环形缓冲区；访问可能因 kernel.dmesg_restrict 而需要 sudo。
dmesg --level=err,warn
```

将 `ssh.service` 换成实际单元名，并用 `systemctl list-units --type=service` 或服务文档确认名称。`systemctl status` 展示的是当前状态和有限的近期上下文，不能代替有时间范围的日志查询。`journalctl --since` / `--until` 可接受明确时间，例如 `--since "2026-09-01 09:00" --until "2026-09-01 09:15"`；排查重启后才出现的问题时，`-b` 和 `-b -1` 比“最近几百行”更有可比性。

`dmesg` 读取内核环形缓冲区，可能已被新消息覆盖，且在加固系统中会受 `kernel.dmesg_restrict` 限制；journal 是否跨重启持久保存也取决于系统配置。非 systemd 发行版可能使用 OpenRC、runit、SysV init 或其他日志设施：`journalctl` / `systemctl` 不适用，应使用该发行版的服务和日志文档，而不要为获取日志临时替换 init 系统。

日志可能含用户名、主机名、内部地址、查询参数、会话标识甚至应用误写入的秘密。分享前按最小必要原则截取时间范围并人工脱敏；不要把整份 journal、认证日志或含令牌的 `curl` 输出贴到公开位置。

### 容器和 AI 服务：先确认“在哪个网络与挂载视图里”

容器可能拥有独立 network、mount、PID namespace；同一服务名或端口在容器内、宿主回环和局域网接口上不一定指向同一对象。诊断 Python API、C++ 服务或 LLM 推理端点时，先记录请求发起位置、目标 URL、容器/宿主边界、监听地址、代理与认证是否参与，再用对应视图中的 `ip`、`ss`、`findmnt` 和最小时间窗口日志验证。容器中 `127.0.0.1` 常只表示那个容器本身；`0.0.0.0` 是监听范围描述，也不等于自动暴露到公网。

模型文件、缓存和 checkpoint 往往很大。排查“服务似乎失联”时，同时检查实际挂载、磁盘空间和 inode，避免删缓存、清日志、重建镜像或重启服务作为第一反应。部署前还要把最小监听面、认证、TLS、日志脱敏与恢复策略写清；相关应用层边界见 [[AI/20-LLM/70-工程应用与工具链/05-私有部署认证TLS与边界|私有部署认证、TLS 与边界]]，隔离层选择见 [[计算机知识/20-操作系统/01-Linux/14-Linux开发容器与AI工作负载边界|Linux 开发、容器与 AI 工作负载边界]]。

## 7. 可回退的排错流程

| 阶段 | 要做什么 | 可记录的证据 | 此阶段避免什么 |
| --- | --- | --- | --- |
| 现象 | 明确谁、何时、哪个目标、期望与实际结果 | 完整报错、时间、网络/主机范围、是否可复现 | 把“打不开”直接归咎于 DNS 或防火墙 |
| 层次 | 从链路→地址→路由→DNS→socket→应用逐层提出假设 | 对应层的一条查询输出与结论 | 同时改多处配置，失去因果关系 |
| 证据 | 用只读查询或有限测试证实/排除一个假设 | `ip route get`、`ss`、限定时间的日志、一次 DNS/HTTP 测试 | 把单次 ping 或单行日志当作最终证明 |
| 最小变更 | 只改一个已被证据支持的变量，并记录旧值、操作者与预期 | 变更前后同一测试、服务状态与时间戳 | 在远程会话中批量重启网络、清日志、删除数据 |
| 回退 | 若结果不符合预期，恢复已记录的旧值并验证原服务可达 | 回退后的同一证据、未解决问题清单 | 因为“没用”而留下半套临时配置 |

一个例子：某服务域名访问超时。先确认发生时间和受影响客户端；检查本机接口/路由；用 `resolvectl` 或 `dig` 判断名称是否得到预期地址；用 `ss -lntp` 在服务端确认监听地址；再用受控 `curl` 区分 TLS/HTTP 层。若证据显示 DNS 把域名解析到错误地址，最小变更是修正**该 DNS 记录或其权威配置**，而不是同时改本机 hosts、DNS、路由与防火墙。变更前记录旧记录和 TTL；验证后若异常，按原值回退并保留查询证据。

## 安全实验：只建“证据包”，不改系统

在自己拥有或获授权的 Linux 主机上，打开两个终端：一个执行下列只读观察，另一个作为对照。不使用 `sudo`，也不执行任何 `ip … add/replace/set`、网络服务重启、`mount`、分区、格式化、删除或 SMART 自检命令。

```bash
ip -br link
ip -br addr
ip route get 192.0.2.1
ping -c 3 127.0.0.1
ss -lnt
findmnt -T .
df -hT .
journalctl -b --since "10 minutes ago" -n 20
```

为每行输出写一句观察：例如“`lo` 为 UP”“到文档地址将走 `wlan0`”“当前目录属于哪个挂载点”。若 `journalctl` 因权限或非 systemd 失败，把它记为环境差异，不要以管理员权限绕过；若 `ping` 缺失，也只记录工具缺失。完成后不需要清理：本实验没有创建文件、修改配置或向外部网络发包。

### 练习：为一个现象设计证据链

任选一个不涉及真实生产故障的假设现象，并写出五行计划：

1. 现象：例如“本机访问 `https://example.com` 失败，但回环 ping 成功”；
2. 层次：列出至少三个要依次验证的层次；
3. 证据：为每层选择一条只读命令，并说明成功/失败各意味着什么；
4. 最小变更：仅在已有证据指向配置错误时，说明将由谁、在哪个配置所有者处改哪一个值；
5. 回退：写明旧值、验证命令和何时停止升级变更。

### 成功标准

- 能说明为什么 `ip route get`、`dig`、`ss` 和 `curl` 不能互相替代；
- 能从 `ss -lnt` 区分没有监听、只监听回环和监听全部 IPv4 地址三种情况；
- 能指出 `df` 与 `du` 的统计对象不同，并先用 `findmnt` 解释路径属于哪个挂载点；
- 能用 `journalctl -b`、`-u`、`--since` / `--until` 把日志缩到一次服务和一个时间窗口；
- 排错计划包含一个可验证的最小变更与明确回退，不含未经确认的批量重启、删除、格式化或网络配置改写。
