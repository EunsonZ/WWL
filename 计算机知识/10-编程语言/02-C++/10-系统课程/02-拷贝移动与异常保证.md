# 拷贝、移动与异常安全：为什么 std::move 可能仍然复制

> **学习位置**：[[计算机知识/00-开始/课程地图/02-C++-课程地图|C++课程地图]] · **适用边界**：C++20；ABI、容器实现与后续标准不混同。

## 表达式有类型，也有值类别

左值通常标识具有持续身份的对象；纯右值常用于产生值或初始化结果；将亡值标识可被复用资源的对象。不要用“能不能写在等号左边”完整定义它们，`const` 左值不可赋值，而某些类右值仍可以调用成员操作。

`std::move(x)` 本质上进行值类别转换，使重载决议可以选择接受右值的接口。它自身不移动字节，不清空对象，也不保证选择移动构造。命名的右值引用变量在表达式中仍是左值：函数 `void f(T&& x)` 内部的 `x` 若要传给移动接口，仍需有意识地转换。

## `const` 为什么阻止常见移动

常见移动构造签名是 `T(T&&)`，它需要修改源对象以交出资源。若 `x` 为 `const T`，`std::move(x)` 是 const 限定的右值表达式，通常不能绑定到 `T&&`，于是可能选择 `T(const T&)` 做复制。编译通过不等于发生了预期优化。

移动后对象一般必须保持可析构、可赋值等接口要求，但“有效但未指定状态”不等于空状态。标准库对具体类型可能给出更强保证，自己的类型也可明确承诺移动后为空；不能把某次观察到的 `string.empty()` 当成全部类型的规则。

## Rule of Zero 比手写五件套更重要

类若仅由正确管理资源的成员组成，通常让编译器生成特殊成员函数即可。只有直接拥有裸资源的底层封装，才需要认真决定析构、复制构造、复制赋值、移动构造和移动赋值。

用户声明析构函数等操作会影响隐式移动操作的生成规则；不要以为写了一个“只是打印日志”的析构函数，移动行为就不会变化。用 `=default`、`=delete` 明确表达设计，并通过类型特征和调用测试确认结果。

## 四种错误保证

无抛出保证表示操作不会以异常失败；强保证表示失败时可观察状态保持原样；基本保证表示不变量和资源安全维持，但值可能改变；无保证则可能连安全清理都困难。它们是接口层承诺，不是编译器自动授予的等级。

一个拷贝赋值实现可以先构造临时副本，再用不抛出的交换提交状态。这是 copy-and-swap 的核心。它便于强保证，但可能增加分配，且应检查分配器、交换与类型约束，不宜机械用于所有高性能容器。

## `vector` 扩容为何关注 `noexcept`

扩容需要把元素放入新存储。若移动可能在中途抛出且已经改变旧元素，回滚可能困难；如果复制可用，实现可以通过复制保留旧值，以满足相应异常保证。于是一个本来廉价的移动构造，若没有合适的 `noexcept` 契约，可能导致扩容时走复制路径。

但声明 `noexcept` 不是为了骗取优化。函数真的抛出时会进入终止流程，而不是给调用者一次普通捕获机会。承诺必须由成员操作和所有失败路径支持。

## 返回值优化与不必要的 move

```cpp
std::vector<int> make_values() {
    std::vector<int> values{1, 2, 3};
    return values;
}
```

这里应让语言的返回值规则工作。`return std::move(values);` 可能妨碍对具名局部对象的 NRVO。C++17 起某些纯右值初始化具有保证的消除复制语义，但 NRVO 仍需要与这些保证区分；不要把“我没看到拷贝日志”一概称为编译器可选优化。

## 推演练习

有一个只可移动的 `Token`，为什么 `std::vector<Token>{Token{},Token{}}` 可能不按期望工作？`initializer_list` 的元素具有 const 访问特征，容器从该列表构造时常需要复制元素，而 move-only 类型不提供复制。可改用 `emplace_back` 或其他明确的构造流程。

若移动赋值收到自身 `x=std::move(x)` 怎么办？不要随意假定调用永不发生。为自定义资源封装写出可接受的后置条件，保证至少不泄漏、不重复释放并维持合法状态；具体接口可选择防护或文档化限制。
