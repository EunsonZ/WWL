# 数据库：事务、隔离、锁与 MVCC 的时间线

> 阅读定位：关系理论通用；实现示例区分 SQLite 与 PostgreSQL 17。返回 [[计算机知识/00-开始/课程地图/10-数据库-课程地图|数据库 · 课程地图]]；全域入口 [[计算机知识/00-开始/全局导航/00-总学习地图|计算机知识库 · 总学习地图]]。

## 原子性不是“只有一条 SQL”

事务把一组操作作为一个成功或失败边界，隔离控制并发事务的相互观察。持久性关心已确认提交在约定故障模型下能否恢复，业务一致性由约束和正确逻辑维持。数据库返回提交成功的承诺还受配置、复制模式与存储条件影响。

两个事务都读到余额 100，然后各自减 10 再写回 90，就可能丢失一次更新。把计算改为 `UPDATE account SET balance=balance-10 ...` 常可利用数据库写入协调改善这一具体问题，但更复杂的跨行不变量仍需正确协议。

## 隔离级别的名称不等于跨产品相同行为

脏读读取未提交内容，不可重复读指重读同一数据得到变化，幻读涉及符合谓词的集合变化。快照隔离还可能出现写偏斜：两名值班医生都看到对方仍在岗，于是分别把自己改为离岗，最终无人值班，即使两次修改作用于不同记录。

PostgreSQL 的 Read Committed 通常按语句获取快照，Repeatable Read 提供较稳定的事务视图，但仍可能出现某些序列化异常；Serializable 会检测并拒绝某些不能串行化的执行。要以具体产品文档为准，而不是只背一张 ANSI 表。

## MVCC 没有消灭锁

多版本允许读取适当版本，减少某些读写阻塞，但写入冲突、DDL、显式锁和约束维护仍有协调。旧版本也需要回收，长期事务可能阻碍清理并放大存储成本。快照的“同一时刻”是数据库可见性规则，不等于跨多个独立系统的全球瞬时快照。

解决写偏斜可选择正确的串行化隔离、锁住代表不变量的资源，或重新设计成可由约束和原子更新维护的状态。锁顺序不一致会形成死锁，数据库可能中止一个事务，应用须能处理。

## 重试整个事务，而非最后一句

序列化失败后，应按产品合同重新执行整个事务，重新读取并计算。把最后的 UPDATE 单独再试一次，可能继续使用过期决策。外部发邮件、扣款和 HTTP 调用若夹在可重试事务中，会因重试重复；需要 outbox、幂等协议或其他明确的边界。

练习：画出两个医生事务的每次读写，说明为何“每行都没被同时写”仍不足以保证正确。分别用串行执行、快照隔离和合适的串行化处理解释结果。测试通过一组交错不等于穷尽所有并发执行。
