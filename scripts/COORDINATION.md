# Coordination schema 2: read-only records checker

Implementation scope: Python standard library, no scheduler, network, model calls, writes, patch application, identity authentication or lock. Only stdout/stderr are written. There is no source or verifiable wire format for schema 1 in this vault; schema 1 is explicitly `unsupported legacy`, without inventing compatibility.

## When to use this checker

This is an optional record checker for a delivery that has a concrete recovery or conflict-management need, such as a staged migration whose exact old/new bytes must be distinguished after interruption. Routine content edits follow [AGENTS.md](../AGENTS.md), the [maintenance guide](../00-工作台/维护指南.md), and the [collaboration guide](../00-工作台/并行协作与模型路由.md). Editing two independent articles does not by itself require this checker, a manifest, hash receipts, or a combination record.

Once this checker is selected for a delivery, its complete contract below applies: every multi-path group still requires the specified combination review, exact hashes and input versions; a blocked or rejected result cannot be ignored. This entry clarification changes when the tool is used, not its schema, implementation, validation strength, or meaning of success.

## Contract proposed before implementation

Plan accepts exactly C1 `schema/batch/rules/human_files/shared_files/tasks` and optional explanatory `notes`. Rules are `version/files`. Tasks accept exactly `id/kind/goal/writes/reads/risk/acceptance/review_by/forbidden/searches` and notes. Kinds are author, review, evidence; unknown roles cannot bypass review. All normal/high writes require every named independent review task. Read kinds are base or artifact, latter with producer task/path and accepted/candidate requirement. Author candidate reads require a speculative attempt and cannot release. Only artifact author dependencies form readiness edges; reviewer candidate reads create no false cycle.

A task digest uses its content contract and applicable rules, never routing, prices, notes, task order or other tasks. A snapshot includes this digest, states of its own target old bytes (file hash or explicit absent), required base input/rule states, and bounded literal-search matches. Required inputs cannot be absent. No future output hash is guessed.

Records separate `current`, `attempts`, `artifacts`, `receipts`, `release`, `checks`. Each current task names one generation/attempt. Each attempt binds contract, generation, actor and real session or null, mode/status, snapshot baseline, exact consumed artifact references, produced artifact IDs, requested/observed model and effort, usage reference, optional retry basis and notes. Actual unavailable runtime/model/cost values are unknown. A third meaningful attempt requires recorded new evidence/method/authorization; the checker does not launch attempts.

Artifacts bind a producer attempt, exact target path and actual whole-file SHA-256 or absent deletion; storage is an exact relative regular-file path under work root (null only for deletion). A candidate is a sparse overlay under a separate candidate root. It must contain exactly the nondeleted selected artifact paths, including hidden files. Deletions are explicit artifacts; moves are explicit old-path deletion plus new-path file. Any unclaimed file is rejected. No-change output must equal all original target bytes and is counted as zero improved problems.

Receipts bind producer/reviewer attempts, complete artifact set, input digest, output digest, acceptance digest, decision, basis and evidence references. All designated reviewers must accept the exact current bytes and input version. Reviewer task, session and actor must differ from the producer; this verifies declarations and consistency only, not real identity or honesty. Duplicate identical terminal record IDs are idempotent; conflicting duplicates fail. Old generations remain evidence but cannot be selected.

Release names selected tasks/artifacts, explicit publisher control declaration and a targeted combination review when more than one path is selected. Downstream prerequisites must be selected or already match current-root bytes. Unknown saved-buffer/external-writer/control/cancellation declarations block. This is not an OS or distributed lock. Recovery reports old=continue, new=already_applied, third=preserve_and_stop per target; no file is changed. Combination evidence binds final bytes, consumed input versions and acceptance criteria; software cannot determine semantic correctness.

Searches are bounded `scopes/literals/extensions/max_files/max_bytes/case_sensitive` declarations. UTF-8 literal matching in declared scopes runs on current root plus selected overlay. Only matching files and their hashes bind a negative search, so unrelated new files do not stale the task unless an explicit bound is exceeded. Relevant new matches require fresh evidence, never automatic old acceptance renewal. Scope does not claim exhaustive search of the vault.

Check reuse keys bind input hashes, proposed output hashes, check-code bytes, literal argv, and declared influential environment. Same key and prior pass may report reused; mtime is never sufficient. Records cannot prove the environment declaration complete or that a check actually ran.

Paths reject absolute/drive/backslash/dot traversal, unsafe control characters, case-fold or Unicode-normalization ambiguities, file/parent collisions, symlinks and multi-link regular files. Directory-fd relative O_NOFOLLOW opens and before/after stat plus final reread checks detect relevant in-read/input changes. They do not provide a transaction, complete sandbox, or protection after the check ends. Private content is never echoed on error.

CLI: `plan --plan P`; `snapshot --plan P --current-root R`; `audit --plan P --records J --candidate C --current-root R --work-root W`; `stale` and `release-check` accept the same five paths. Snapshot prints data for explicit coordinator capture; all other commands print versioned status/diagnostics. Each command has --help. Valid records never mean knowledge correct or permission to publish.

## Running the shipped fixtures

The example identities and review evidence are explicitly synthetic fixture data. They demonstrate record checking, not real independent sessions or authorization. Run from the vault root after copying this candidate's `scripts` files into an approved integration location. These commands do not write files:

```sh
python3 -B scripts/coordination.py --help
python3 -B scripts/coordination.py plan --plan scripts/examples/coordination-success/plan.json
python3 -B scripts/coordination.py snapshot --plan scripts/examples/coordination-success/plan.json --current-root scripts/examples/coordination-success/current
python3 -B scripts/coordination.py audit --plan scripts/examples/coordination-success/plan.json --records scripts/examples/coordination-success/records.json --current-root scripts/examples/coordination-success/current --work-root scripts/examples/coordination-success/work --candidate scripts/examples/coordination-success/candidate
python3 -B scripts/coordination.py stale --plan scripts/examples/coordination-success/plan.json --records scripts/examples/coordination-success/records.json --current-root scripts/examples/coordination-success/current --work-root scripts/examples/coordination-success/work --candidate scripts/examples/coordination-success/candidate
python3 -B scripts/coordination.py release-check --plan scripts/examples/coordination-success/plan.json --records scripts/examples/coordination-success/records.json --current-root scripts/examples/coordination-success/current --work-root scripts/examples/coordination-success/work --candidate scripts/examples/coordination-success/candidate
```

The success outputs are respectively `plan_valid`, a snapshot object, `audit_valid`, `base_matches`, and `records_valid`, with exit code 0. Every subcommand also accepts `--help`. Minimum failure examples (exit code 2):

```sh
python3 -B scripts/coordination.py plan --plan scripts/examples/coordination-failure/plan-invalid.json
python3 -B scripts/coordination.py snapshot --plan scripts/examples/coordination-failure/plan-missing-input.json --current-root scripts/examples/coordination-failure/current
python3 -B scripts/coordination.py audit --plan scripts/examples/coordination-failure/plan.json --records scripts/examples/coordination-failure/records.json --current-root scripts/examples/coordination-failure/current --work-root scripts/examples/coordination-failure/work --candidate scripts/examples/coordination-failure/candidate-unclaimed
python3 -B scripts/coordination.py stale --plan scripts/examples/coordination-failure/plan.json --records scripts/examples/coordination-failure/records-stale.json --current-root scripts/examples/coordination-failure/current --work-root scripts/examples/coordination-failure/work --candidate scripts/examples/coordination-failure/candidate
python3 -B scripts/coordination.py release-check --plan scripts/examples/coordination-failure/plan.json --records scripts/examples/coordination-failure/records.json --current-root scripts/examples/coordination-failure/current --work-root scripts/examples/coordination-failure/work --candidate scripts/examples/coordination-failure/candidate
```

They reject, in order: unknown protection field, missing required old input, unclaimed candidate file, stale task contract, and unknown saved-target declaration. Structural/filesystem failures print `error` to stderr; coherent but insufficient/stale release records print `blocked` to stdout. A caller must check exit status and the JSON status, never interpret absence of output as success. Exact file/hash records are in the success fixture; no coordinator is expected to ask humans to hand-author them.

Run deterministic tests with `python3 -B -m unittest discover -s scripts/tests -p 'test_coordination.py' -v`. They use the system temporary directory, or the explicitly supplied `COORDINATION_TEST_TMP` directory, and clean their fixtures. The checker module does no work on import.

## Exact record details

- `baseline`: `contract`, `inputs` (relative path to state), `searches` (ordered `spec` SHA-256 and `matches` path-state map). State is exactly `{"kind":"absent"}` or `{"kind":"file","sha256":"…"}`. `absent` is only valid for an old create target or explicit deletion output; required inputs and consumed new author prerequisites require actual files.
- An attempt's `artifact_inputs` entry has `task/path/require/artifact/producer_attempt/state`. The producer attempt and full state are bound in the consumer input digest; changing an upstream artifact's content cannot keep the old downstream input digest merely by reusing its ID. The declaration in `reads` must match every binding, with no missing or extra dependency.
- `input_digest` hashes `{"baseline": baseline, "artifact_inputs": sorted_bindings}`; `output_digest` hashes the sorted complete list of `id/task/attempt/path/state`; `acceptance_digest` hashes the author's acceptance list. Canonical serialization is UTF-8 JSON, sorted keys, no extra separator whitespace, Unicode preserved, no NaN/Infinity. Helper functions expose this wire definition; snapshot hashes are not recoverable backups.
- Every named `review_by` task must have a current finished review attempt with a nonnull session and actor different from the producer, candidate bindings covering every output, and a receipt binding these three digests. Its own old inputs and declared searches must remain current. `accept` plus `reject/pending` for the same current review scope blocks. Duplicate identical IDs are handled once; conflicting records sharing an ID fail. Highest declared generation wins eligibility; a newer unknown/cancelled/revoked attempt does not revive an older one.
- `evidence_refs` are a nonempty list of `{"path":"relative/work/file","sha256":"…"}`. The checker reads these files and validates their hashes; it cannot establish that the evidence says something correct or was written independently.
- A `combination` has `review_attempt/input_digest/output_digest/acceptance_digest/basis/evidence_refs/searches`. Its input digest hashes the task-to-author-input-digest map; criteria digest hashes the task-to-acceptance-list map; output digest covers the exact final selected group. Its review attempt must read every selected artifact. `searches` maps each selected task to its current-plus-overlay search result list, including empty lists. Every group with more than one target requires this review. A single-target task also needs fresh combination review if its bounded search changes, including when its own new output introduces a match. This records a new explicit review of the changed search result; it does not refresh any old receipt automatically.
- An applicable rule-file byte change invalidates existing attempts until they are rebound and reviewed. Current `human_files` and `forbidden` checks are live; current protection cannot be bypassed by an old snapshot. `shared_files` can have an author but are subject to the same single confirmed publisher declaration as every other selected target.
- `checks` bind `inputs` under current root, `outputs` under candidate root, `code` under work root, literal `argv` and a string-map `environment`, with `key/result` and optional `prior:{key,result}`. Code and command bindings must both be nonempty. Identical duplicate check IDs are idempotent; different records sharing an ID fail. The checker recomputes file hashes and the combined key. Reuse is reported only for a matching current pass and prior pass at the identical key. It never executes `argv` or claims to measure environment values; the coordinator must declare all influential environment facts and supply authentic execution evidence. Old checks with different bytes, code, arguments or declared environment cannot be reused.

## Explicit limits and conservative behavior

This implementation favors complete small task file groups. It rejects simultaneous ownership of a target; change a task's current attempt/generation for author handoff. It requires a combination receipt for every multi-file group, even if the files happen to be independent. Scope expansion or changed criteria produces a changed task contract. It supports explicit delete/create pairs for moves and checks their combined review; a consumer cannot treat a deleted file as an accepted existing input.

Paths use `/` and canonical NFC spelling. Safety comparisons include every directory component, case folding, forbidden-prefix checks, symlinks, and regular-file hard-link counts. Current, work and candidate roots must be nonoverlapping real directory trees. Root traversal and later reads use directory descriptors and no-follow opens; final verification reopens the root chain, rereads observed states and repeats bounded searches. A filesystem/API without the required POSIX primitives is unsupported. A checker cannot prevent changes after it returns or make multi-file replacement atomic. Restore each target only after confirming its old/new/third state; this tool never restores or publishes.

`max_files` bounds files enumerated inside search scopes; `max_bytes` bounds content bytes read across selected suffixes, checked before and during read. Literal terms are never executed or interpreted as regex. Names/aliases are found only when the chosen literals match UTF-8 text in the selected scopes; unsupported encodings or exceeded bounds fail rather than imply exhaustive search. JSON, normal artifact and evidence reads do not inherit the search byte bound and should be reasonably sized coordinator inputs. Avoid placing unrelated private configuration in inspected search scopes or the candidate tree.

Only exact records deduplicate terminal delivery. There is no reliable semantic problem identifier here, so the tool makes no improved-problem throughput claim and does not automatically merge two authors' similar questions. `no_change_conclusions` counts explicit no-change results, requiring every output to match its old bytes. It never counts these as article improvements.

Actual model/effort/cost are `unknown` when unavailable. A supplied supported-effort list is checked for consistency; the tool cannot discover a remote model's supported efforts or verify an alias. It does not manage monetary reservations, enforce OS cross-process mutual exclusion, stop remote requests, release unknown in-flight budgets, inspect unsaved editor buffers, or prove sync state. Those are separate coordination facts. T19 coverage is limited to fail-closed control declarations. Schema 1 remains unsupported legacy because neither implementation nor a verifiable old wire format exists in this vault; no same-schema hashing meaning was silently changed.

An unselected accepted prerequisite also retains its own bounded-search validity. A new relevant match blocks consumption even if that prerequisite has already been published. A combination receipt can refresh only the task group it explicitly covers; it cannot renew an unrelated upstream acceptance. This minimal format does not keep a historical combination registry: rebind and independently review the prerequisite, or include it in the explicit refreshed group.

Recovery of a partially applied, mutually old-base-reading group is allowed only with the unchanged exact combination review: the changed read path must be a selected target, its current bytes must equal that target's concrete expected artifact, and the consumer's old read state must equal the producer's original target binding. A missing/changed combination receipt, third-party bytes, unselected upstream or changed rule file still blocks. This reports recoverability; it applies nothing.
