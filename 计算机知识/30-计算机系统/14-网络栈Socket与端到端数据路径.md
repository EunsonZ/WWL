# 网络栈、Socket 与端到端数据路径

## 本课目标

学完后，你应该能够：

- 从应用的一次 `write` / `send` 追踪数据如何经过 socket buffer、TCP/UDP、IP、路由、网卡队列、DMA 与中断，再被对端应用读取；
- 分清 DNS、选路、建立连接、TLS 与应用协议分别解决什么问题；
- 用队列解释 backpressure、吞吐、延迟、丢包和队头阻塞，而不是把“加大 buffer”当作通用优化；
- 明确 syscall 返回、数据进入内核、数据到达对端和业务完成是四个不同完成边界；
- 用只读观察逐层缩小 Linux 网络问题，并说明 macOS、Windows、容器与虚拟机的工具差异。

> [!prerequisite] 前置知识
> 先用 [[计算机知识/20-操作系统/01-Linux/10-网络存储日志与故障排查|网络、存储、日志与故障排查]]建立接口、地址、路由、DNS、端口和日志的排错顺序；本页继续追问“一个字节究竟怎样穿过这些层”。内存映射、缓存与 DMA 的背景见 [[计算机知识/30-计算机系统/02-进程虚拟地址空间与内存映射|进程虚拟地址空间与内存映射]]、[[计算机知识/30-计算机系统/04-缓存局部性带宽与延迟|缓存、局部性、带宽与延迟]]。

## 1. 先建立端到端图，而不是背协议缩写

以应用把一段响应写入一个已经建立的 TCP 连接为例：

```text
发送端应用
  应用缓冲区中的字节
      │ write/send（或 TLS 库先生成密文 record）
      ▼
  socket 发送缓冲区
      │ TCP：字节序号、分段、确认、重传、流量/拥塞控制
      │ UDP：独立 datagram，不提供可靠、有序字节流
      ▼
  IP：目的地址、选路、下一跳、MTU
      ▼
  qdisc / 驱动 TX 队列 / NIC ring
      │ DMA 读取内存中的描述符与数据；具体是否复制/卸载依硬件与内核
      ▼
  网卡 → 链路 → 交换/路由/NAT/防火墙 → 对端网卡
      ▼
  对端 NIC RX ring / DMA
      │ 中断、轮询或混合机制通知内核处理；Linux 高负载常由 NAPI 批量处理
      ▼
  IP → TCP/UDP → socket 接收缓冲区
      │ read/recv
      ▼
对端应用解析 TLS / HTTP / 自定义协议并完成业务
```

这张图是概念主线，不是所有平台的逐函数实现。loopback 连接可能不经过物理网卡；硬件可能执行 checksum、分段或聚合卸载；zero-copy API 可能减少某些复制；虚拟机、容器、VPN 和 service mesh 又会增加虚拟设备与代理。**优化前必须先确认真实路径，不能把示意图当成本机调用栈。**

## 2. `write` 成功，只说明内核接收了一部分责任

应用中的文件描述符只是对内核对象的引用。对 socket 调用 `write(fd, buf, n)` 或 `send`，通常会经历用户态到内核态的 syscall 边界；内核检查 socket 状态与可用空间，再接收数据。这里必须守住三个边界：

1. 返回值可能小于 `n`，应用必须处理 partial write；
2. blocking socket 在发送缓冲区空间不足时可能等待，non-blocking socket 可能返回 `EAGAIN` / `EWOULDBLOCK`；
3. 返回 `n` 通常只表示这 `n` 个字节已被本机内核接收，不表示网卡已经发出、对端已经读取，更不表示对端事务已提交。

TLS 并不绕过这一点。应用通常先把明文交给 TLS 库，TLS 库形成 record、加密并把密文字节送入 socket。于是应用看到的“一条消息”、TLS record、TCP segment 与 IP packet 不是同一个边界，不能假定一次 `write` 在网络上对应一个包，也不能假定对端一次 `read` 恰好得到一次 `write` 的全部内容。

### TCP 是字节流，消息边界由应用协议定义

TCP 交付有序字节流，不保留应用的 write 边界。对端一次 `recv` 可能得到半条消息、一条消息或多条消息的连续字节。应用协议必须自行规定 framing，例如：

- 固定长度；
- 长度前缀；
- 明确分隔符并处理转义；
- HTTP 等已经定义好的协议 framing。

**反例：**“发送端一次 `send` 了 4 KiB，因此接收端一次 `recv(4096)` 一定拿到 4 KiB。”这是把 API 调用边界误当成传输协议边界；短读、多个 write 合并和分段都可能出现。

### 就绪与完成是两种交互模型，业务确认又是更强证据

readiness API 与 completion API 通常是两条不同主线：异步操作并不要求先收到 readiness 事件，普通非阻塞 `recv`/`send` 的返回也不会自动进入另一条异步 completion 链。它们最后都只能提供本地 API 结果；端到端成功仍需要更强的协议证据。

```text
readiness 模型：
select / poll / epoll / kqueue event
  → non-blocking recv/send
  → bytes / EOF / error / EAGAIN
  → 处理 partial result，并按需重新等待

completion 模型：
submit operation
  → 内核处理，必要时由驱动/设备继续推进
  → CQE / IOCP completion
  → request id + status + byte count

两条路径都不自动表示：
对端应用已读取
  → 应用协议 acknowledgement
  → 业务 commit / durability
```

它们分别回答不同问题：

1. **readiness：**`select`、`poll`、Linux `epoll` 与 BSD/macOS `kqueue` 常用于观察“现在值得尝试读/写或有错误/关闭状态”；就绪不是“下一次一定读满/写完”的承诺，多个线程、状态改变和 API 的具体语义都可能让实际调用仍短读、短写或返回 `EAGAIN`。
2. **非阻塞尝试：**调用 `recv`/`send` 后，应用处理实际返回字节数；partial result 需要保留剩余 framing，`EAGAIN` 表示此刻不能继续，随后重新等待合适事件。
3. **submission：**异步接口可先把操作交给内核队列。例如 `io_uring` 的 submission queue 提交操作，Windows 可发起 overlapped I/O；这通常只证明请求已被接口接受到某个阶段，不是对端成功。
4. **内核/设备 completion：**内核可能因 socket 缓冲状态、协议处理、磁盘/NIC 驱动完成、中断或轮询而完成操作。`io_uring` 的 CQE 与 Windows IOCP 的 completion packet 是把相应异步操作结果交给用户态的常见记录；它们说明的是该 OS 操作的完成状态和返回值，仍需检查 status、字节数与取消/超时结果。
5. **对端/业务确认：**TCP ACK、CQE 或 IOCP completion 都不是“业务已提交”。只有应用协议的响应（并按业务定义持久化、幂等性和副本确认边界）才能建立更强的端到端结论。

这些名称是教学上的主要定位，不是绝对 API 分类：例如 `io_uring` 也能提交 poll 类操作，`kqueue` 可携带更多状态，具体对象、flags 与平台版本会影响解释。诊断时应记录“观察到哪个事件、随后哪次系统调用返回什么”，而不是仅从事件循环名称推断成功。

## 3. TCP 与 UDP 在传输层承诺不同

| 问题 | TCP | UDP |
| --- | --- | --- |
| 抽象 | 有序、可靠的双向字节流 | 独立 datagram |
| 建立状态 | 通常先握手建立连接状态 | 没有 TCP 式握手；`connect()` 也可只固定默认对端与错误投递语义 |
| 丢失处理 | 检测并重传，按序交付 | 应用若需要可靠性，必须自己或由上层协议提供 |
| 流量控制 | 接收窗口保护对端接收能力 | 没有 TCP 接收窗口等价物 |
| 拥塞控制 | 发送速率受网络拥塞反馈约束 | 裸 UDP 不替应用自动解决拥塞控制 |
| 消息边界 | 不保留 | 保留单个 datagram 边界，但 datagram 仍可能丢失、重复或乱序 |

TCP 会给字节编号，结合确认、重传定时器与拥塞算法决定何时可继续发送。接收端通告窗口限制“对端还有多少接收空间”，这是**流量控制**；网络中的丢包、时延等反馈限制注入网络的速率，这是**拥塞控制**。二者都可能让发送端暂缓，但保护的对象不同。

UDP 保留 datagram 边界并减少连接状态，不等于“必然更快”或“可以无限发”。大 datagram 还会遭遇路径 MTU、IP 分片或丢弃问题；应用若自行重传、排序、拥塞控制和握手，实际上是在上层重新承担复杂性。QUIC 就是在 UDP 之上实现安全连接、可靠 stream 与拥塞控制的协议族，而不是“裸 UDP 加速开关”。

## 4. IP、路由、邻居与 MTU

传输层准备好要发送的内容后，IP 层依据目的地址查路由。路由决定出口接口、下一跳和源地址等；它不查询域名，也不保证下一跳实际可达。发送到同链路邻居时，主机还要把下一跳 IP 解析为链路层地址，例如 IPv4 ARP 或 IPv6 Neighbor Discovery。

路径上的每段链路都有 MTU。TCP 通常结合 MSS 与路径信息分段；硬件卸载可能让抓包看到的“超大 segment”与线上真实 frame 不一致。UDP 应用若交给 IP 一个过大的 datagram，结果可能是分片、返回错误或在路径中丢失，取决于地址族、socket 选项和路径。不要从一次本机抓包武断推断真实线上分片。

选路之后，Linux 还可能经过策略路由、netfilter、防火墙、traffic control / qdisc、隧道和虚拟接口。容器的 network namespace 中看到的路由表与 socket 只属于该 namespace；容器里的 `127.0.0.1` 通常不是宿主机 loopback。

## 5. 从内核队列到网卡：描述符、DMA 与通知

驱动通常维护 TX/RX ring，ring 中的描述符告诉网卡数据缓冲区在哪里、长度是多少。DMA 允许设备与内存交换数据而不让 CPU 逐字节搬运，但它不意味着“CPU 完全不参与”或“没有内存带宽成本”：

- CPU/内核仍要准备协议状态、描述符和队列；
- DMA 与 CPU/GPU 可能争用内存与互连带宽；
- 缓存一致性、IOMMU 映射、bounce buffer、scatter-gather 和 offload 都依平台而异；
- ring 满、qdisc 堆积或驱动回收不及时都可能把压力传回协议栈。

网卡收到 frame 后可将数据 DMA 到 RX buffer，并通过中断、轮询或混合方式促使 CPU 处理。纯粹“每包一次中断”在高包速率下开销很大；Linux NAPI 会在负载上来后用预算化轮询批量处理。多队列 NIC 可用 **RSS（Receive Side Scaling，接收侧扩展）**按流哈希把接收流量分散到多个 RX queue/CPU。这里的 RSS 与 [[计算机知识/30-计算机系统/02-进程虚拟地址空间与内存映射|内存统计中的 RSS（Resident Set Size，常驻集）]]同名但完全无关：前者是网卡接收分流，后者是进程主存驻留页统计。队列数更多仍不保证更快：中断亲和性、NUMA、流哈希、热点连接和内存位置都可能造成不均衡。

## 6. 对端收到包，不等于对端完成请求

接收路径大致反向进行：NIC → RX ring → IP 校验/重组 → TCP 排序或 UDP datagram 投递 → socket 接收缓冲区 → 应用 `read` / `recv`。TCP ACK 通常表示对端 TCP 栈已经接收相关字节，不表示：

- 对端应用已经调用 `read`；
- TLS 已成功解密并认证对端；
- HTTP/数据库协议已经接受请求；
- 数据已经持久化；
- 业务副作用已经提交。

若业务需要“已经入库”或“任务已完成”的保证，必须由应用协议返回明确响应，并定义超时、幂等性和重试语义。网络超时是**未知结果**的一种常见来源：请求可能没到，也可能业务已完成而响应丢失。无幂等设计的盲目重试可能制造重复扣款或重复任务。

## 7. DNS、路由、连接、TLS 与协议必须分层

访问 `https://service.example/api` 的概念顺序是：

| 阶段 | 核心问题 | 成功能证明什么 | 成功不能证明什么 |
| --- | --- | --- | --- |
| DNS | 名称按当前 resolver 策略得到哪些地址？ | 有可用记录/回答 | 地址可达、端口开放、证书正确 |
| 路由 | 去某个目标 IP 走哪个出口与下一跳？ | 本机有选路结果 | 下一跳/远端在线 |
| 连接 | TCP 握手或 QUIC 建连能否完成？ | 传输端点可建立状态 | TLS 身份、HTTP 业务成功 |
| TLS | 协议版本、证书链、主机名与密钥协商是否通过？ | 加密通道与所校验的对端身份成立 | 应用授权、数据正确 |
| 应用协议 | HTTP 状态、Schema、认证授权与业务响应是否正确？ | 该次协议交互得到定义内结果 | 所有用户、所有时刻都正常 |

**反例：**域名能解析，所以服务一定正常；端口能连通，所以 TLS 一定正确；返回 HTTP 200，所以响应内容和业务提交一定正确。每个结论都跨越了尚未验证的层。

更完整的部署边界见 [[AI/20-LLM/70-工程应用与工具链/05-私有部署认证TLS与边界|私有部署、认证、TLS 与边界]]。监听 `0.0.0.0`、防火墙、TLS、认证与授权解决的是不同问题，不能互相替代。

## 8. Backpressure：让上游看见下游已经来不及

若应用产生数据的长期速率高于链路或对端消费速率，任何有限队列最终都会满。backpressure 的核心不是“让队列永远不满”，而是**让压力沿边界可观察地传回上游，使系统减速、拒绝、降级或丢弃，而不是无限积压。**

```text
到达率 λ > 可持续服务率 μ
  → 应用队列增长
  → socket buffer / qdisc / NIC ring 或对端队列增长
  → 排队延迟上升
  → buffer 满、write 等待/EAGAIN、超时、丢包或拒绝
```

加大 buffer 只能延后满载时刻，且可能把显式失败变成更长的尾延迟，即 bufferbloat。稳健边界包括：

- 有界队列与明确容量单位（请求、字节、token 或工作量）；
- 入队超时、deadline 与取消传播；
- 并发限制和按主体配额；
- 可重试与不可重试错误分开；
- 在过载时拒绝、降级或丢弃哪类工作有明确策略；
- 同时观察队列深度、驻留时间、丢弃/重传和消费者吞吐。

TCP backpressure 也不能自动约束应用层所有对象。例如服务先把无限请求体读入内存队列，再慢慢处理，即使 TCP 最终会减速，应用内存也可能先耗尽。边界必须从网络一直设计到业务工作队列。

## 9. 队头阻塞有多种层次

**队头阻塞（head-of-line blocking）**指队首工作未完成，使其后的工作即使可以处理也被迫等待。至少区分：

- 应用单队列：一个超长任务挡住短任务；可用分级队列、公平调度或工作隔离，但要防止长任务饥饿；
- TCP 单连接：较早字节丢失时，后续已到字节通常不能越过缺口交给该有序字节流；
- HTTP/1.1 流水线：前一个响应会阻挡后一个响应；
- HTTP/2 多 stream 共用一个 TCP 连接：应用 stream 可多路复用，但底层 TCP 丢失仍可暂时影响同连接的多个 stream；
- QUIC：不同 stream 可独立有序，某个 stream 丢失不必阻挡其他 stream 的交付，但它们仍共享路径容量、拥塞控制资源和实现队列。

“多开连接”可能减少某层 HOL，也可能增加握手、状态、拥塞竞争、内存和公平性问题。先确认阻塞发生在哪一层，再决定隔离连接、拆队列、修改调度还是缩短任务。

## 10. 逐步案例：LLM 流式响应为何突然卡顿

假设浏览器调用一个自有的 LLM 服务：首 token 很快，随后偶尔停顿两秒。按边界逐步推理：

1. **应用层：**记录客户端收到每个 chunk/token 的 monotonic 时间；确认是生成停顿还是“生成了但没发”。
2. **协议层：**检查代理是否缓冲小响应、是否等到达到 chunk 大小才 flush；不要先归罪于 TCP。
3. **socket：**服务端 non-blocking send 是否反复遇到不可写？发送队列持续增长更像下游消费或网络跟不上。
4. **TCP/IP：**查看重传、RTT、拥塞窗口与接收窗口趋势；单次 retransmission 计数不能自动证明它造成了那次两秒停顿，必须按时间关联。
5. **设备/主机：**观察接口 drop/error、CPU softirq 压力与队列分布；高 CPU 也可能来自模型推理而非网络。
6. **对端：**浏览器主线程、渲染、代理/VPN、Wi-Fi 和客户端读取速率都在端到端路径上。
7. **跨层关联：**用 request/trace ID 与时间戳连接“模型 decode span、应用 send、网络状态和客户端接收”，再提出一个可证伪假设。

若证据显示模型在停顿期间根本没生成 token，调大 socket buffer 不会修复根因；应进入 [[AI/20-LLM/40-推理/03-批处理调度延迟吞吐与投机解码|批处理、调度、延迟、吞吐与投机解码]]检查 prefill/decode 竞争、调度和 KV 压力。若 token 已生成但 send 队列增长，则继续查代理、客户端读取和网络路径。

## 11. 只读观察清单与平台差异

下列命令不修改本机网络配置。它们仍可能读取敏感的地址、进程名和连接；分享前脱敏。带目标名称的 DNS/HTTP 测试还会产生网络流量并可能留下对端日志，因此本清单默认只做**本机被动查询**。

### Linux（iproute2 / procfs）

```bash
# 接口、地址、路由；route get 只做本机选路查询，不发送包。
ip -br link
ip -br addr
ip route
ip route get 192.0.2.1

# 监听与已有 TCP 连接；-m 展示 socket memory，-i 展示 TCP 内部信息。
ss -lnt
ss -ntomi

# 接口计数与协议栈累计计数；数值必须结合时间窗口比较。
ip -s link
nstat -az

# 当前启动中与某个已知服务相关的有限日志窗口。
journalctl -b -u YOUR_SERVICE.service --since "10 minutes ago" --no-pager
```

`ss -p` 查看其他用户的进程归属可能需要更高权限，本页不要求提权。`nstat` 可能未安装；`journalctl` 只适用于 systemd journal。`YOUR_SERVICE.service` 是占位符，必须换成已确认的服务单元。`ip -s link` 的累计 drop/error 增长才比孤立总数更有意义，但不要为了差分而清零计数器。

> [!warning] 抓包与主动探测边界
> `tcpdump` / Wireshark 虽主要用于观察，但可能需要特权、显著增加 I/O，并捕获凭据、内部地址或业务内容；本页练习不要求抓包。`ping`、`dig`、`curl` 会向网络发包，也不是被动读取。只有对自己拥有或获授权的目标，在限定次数、超时和数据范围后才使用；不能把“诊断”当作扫描许可。

## 12. 反例：三个看似合理、实际跨层的结论

1. **“发送队列不大，所以用户不会慢。”** 小队列可能因为到达率也很低，或阻塞发生在 DNS、TLS、应用计算、对端 UI；一个局部队列不能代表端到端延迟。
2. **“UDP 没有握手，所以一定比 TCP 延迟低。”** 应用仍可能需要安全握手、可靠性和拥塞控制；丢失后的应用重试可能更慢。
3. **“接口没有 drop，所以网络没有丢包。”** 丢失可能发生在发送前的应用队列、主机其他层、交换机、无线链路、远端或超时策略中；接口计数也受驱动和卸载语义影响。

## 练习：为一次写操作画出证据边界

不启动服务、不改配置、不向外部目标发包。选择你机器上**已经存在**的一条 TCP 连接；若当前没有，就只做纸面推演。

1. 画出“应用缓冲区 → socket 发送缓冲区 → TCP → IP/路由 → qdisc/驱动/NIC → 对端接收缓冲区 → 对端应用”。
2. 在图中标出：write 返回、TCP ACK、对端 read、业务完成四个点，写一句说明每个点不能证明什么。
3. 用本平台的只读命令记录接口、选路、监听或已有连接。只摘取必要字段并脱敏；不要尝试建立新连接来凑结果。
4. 为“发送者持续快于接收者”标出至少三个会积压的位置，并为每处写出容量、满载表现和上游策略。
5. 分别写一个 TCP 字节流 HOL、应用工作队列 HOL 和 HTTP/2-over-TCP HOL 的例子，说明修复为何不能互换。

### 成功标准

- 能按顺序解释一次应用写如何进入 socket buffer、协议栈、路由、网卡队列/DMA/通知路径并到达对端；
- 能明确 TCP 的字节流与 UDP 的 datagram 边界，不依赖“一次 write 等于一个包”的错误假设；
- 能为 DNS、路由、连接、TLS 和应用协议各写一个独立的成功/失败判断；
- 能解释 backpressure 为何需要有界队列、超时/拒绝与压力传播，而不是只增大缓冲区；
- 能指出至少三种队头阻塞，并把观察证据限制在正确的主机、namespace、时间和协议层。
