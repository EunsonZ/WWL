# 条件类型、映射类型与声明文件：类型级计算也需要规格

> **学习位置**：[[计算机知识/00-开始/课程地图/05-TypeScript-课程地图|TypeScript课程地图]] · **适用边界**：strict 模式；ES2022 运行语义；Node 与浏览器环境区分。

## 条件类型按什么分配

```ts
type Box<T> = T extends string ? { text: T } : { other: T };
type A = Box<'x' | 4>; // {text:'x'} | {other:4}
type Whole<T> = [T] extends [string] ? true : false;
type B = Whole<'x' | 4>; // false
```

当被检查位置是裸类型参数时，条件类型会对联合成员分配；用元组包起来可以让整个联合作为一个整体接受检查。这个区别会改变输出结构，不是语法装饰。`never` 在分配条件类型中可能得到让初学者意外的结果，因此处理空联合时要写专门测试。

`infer` 在条件匹配中提取类型部分，例如从函数类型提取返回值。它不是任意范围里的变量声明。递归条件类型可描述嵌套结构，但复杂递归会增加检查成本并受到编译器限制；类型报错展开成几百行，往往说明公共接口需要简化。

## 映射类型怎样保存键和值的关系

```ts
type Mutable<T> = { -readonly [K in keyof T]: T[K] };
type Optional<T> = { [K in keyof T]?: T[K] };
type Getters<T> = {
  [K in keyof T as K extends string ? `get${Capitalize<K>}` : never]:
    () => T[K]
};
```

`keyof`、索引访问类型、映射修饰符与键重映射可以组合成很强的工具。但把所有字段设为可选，未必符合业务：订单的标识和金额可能不应一起缺失。`Partial<T>` 是结构变换，不是有效更新请求的业务定义。更新协议还要明确缺失、null、清空与保持原值的区别。

常用工具包括 `Pick`、`Omit`、`Record`、`Exclude`、`Extract`、`NonNullable`、`ReturnType`、`Parameters` 和 `Awaited`。学习时每个工具都写一个输入类型与预期输出类型，不要只背名称。`Record<string, T>` 也不意味着运行时真的为所有字符串键创建了值；索引读取应配合缺失检查。

## 声明文件只陈述，不实现

`.d.ts` 告诉检查器某个模块或全局有哪些接口，但不会生成函数体。错误声明会让检查通过而运行崩溃。为 JavaScript 库编写声明时，要核对真实导出方式、可空返回、异常、回调约定、同步与异步边界。

模块扩充与全局扩充作用范围不同。随手写 `declare module '*'` 或把依赖声明成 any 会让错误消失，也会让保护消失。`skipLibCheck` 可减少声明检查成本，但不能作为解决所有依赖类型冲突的首选理由；应记录为什么启用以及遗漏了什么检查。

## 用负例检验类型接口

运行时测试检验程序行为，类型测试检验哪些调用应该允许或拒绝。使用 `@ts-expect-error` 标注故意错误的调用；如果以后它不再报错，检查器会提醒该指令失效。不要用 `@ts-ignore` 长期隐藏不理解的错误。公共库还应测试生成的声明文件，而不只测试源码在当前仓库中的解析结果。

## 练习与答案

计算 `Exclude<'a' | 'b' | 3, string>`，结果为 `3`，因为联合逐成员判断。比较 `Partial<{id:number;name:string}>` 与只允许 name 更新的 `{name?:string}`，说明前者为什么暴露了不应修改的 id。最后为一个真实 JS 函数故意写错 `.d.ts`，观察类型检查通过但运行失败；这能直观说明声明是需要外部证据支撑的承诺。
