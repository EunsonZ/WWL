# Rust：unsafe、FFI 与安全抽象究竟要证明什么

> 阅读定位：基础示例兼容 Rust 2021 edition；不把 edition 等同于编译器版本。返回 [[计算机知识/00-开始/课程地图/03-Rust-课程地图|Rust · 课程地图]]；全域入口 [[计算机知识/00-开始/全局导航/00-总学习地图|计算机知识库 · 总学习地图]]。

## unsafe 把证明责任交给作者，不取消语言规则

裸指针解引用、某些外部函数调用等操作需要 unsafe，因为编译器无法验证全部前提。你仍必须保证有效地址、正确对齐、初始化、有效生命期、合法别名和数据竞争约束。unsafe 块里发生的越界依然是错误，不能解释为“我已允许不安全”。

安全封装的公共调用者不能被要求遵守未写进类型或未声明的隐藏安全前提。若安全函数接收任意长度却在内部用裸指针无检查地访问，它可能是一个不健全的安全 API；应验证边界，或将必要前提明确放到 unsafe API 合同中。

## FFI 是两个资源协议的交接

调用 C 接口先对齐 ABI、参数布局与所有权。`#[repr(C)]` 可约束适当类型的布局规则，但不会自动把 Rust String、Vec、trait object 变成 C 能理解的结构。字符串通常需要明确编码、长度、终止符和释放方；`CString` 与 CStr 的用途不同，内含零字节也必须处理。

一个返回缓冲区的 API 应成对提供释放函数，避免跨分配器释放。回调应说明线程、调用次数、取消方式和 context 生命期。错误和 panic 不能随意穿过不允许的跨语言边界。把数据复制成拥有值有时比精巧的跨语言借用更容易证明正确。

## 进阶地图，至少知道每项解决什么

标准库还包括文件和路径、进程、环境、时间、网络、集合、数值、格式化和迭代器。`HashMap` 与 `BTreeMap` 的取舍涉及顺序、范围查询与复杂度；自定义 Hash/Eq 必须一致。`Cow` 在需要时从借用转为拥有；arena 用分组生命期降低分配管理成本；自定义 allocator、no_std 和嵌入式运行时处理更受限的环境。

宏系统、条件编译 cfg、feature、workspace、基准测试、文档发布、语义版本、跨平台 CI、Miri、模糊测试、unsafe 审计都属于工程完整性的一部分。Miri 等工具能发现部分未定义行为，不覆盖所有平台外设、FFI 和真实并发情形。更高级的类型主题包括 variance、HRTB、关联类型、auto trait、trait coherence 和 pinning。

## 最终验收

实现一个“读取有限大小配置并解析为结构体”的小工具：有明确输入上限，错误有上下文，解析与 I/O 分开，测试覆盖无效 UTF-8、语法错误、未知字段策略和数值边界。先用纯安全代码完成；只有测量或接口需要时引入 unsafe，并在每个 unsafe 位置写清哪些前提由哪一段代码保证。
