# 05 · 同步、原子操作与分支发散

> 上一站：[[计算机知识/40-并行与异构计算/01-CUDA/04-内存层级合并访问与BankConflict|内存层级与访问模式]] ｜ 下一站：[[计算机知识/40-并行与异构计算/01-CUDA/06-Stream-Event与异步流水线|Stream、Event 与异步流水线]]

## 本课目标

学完后，你能：

1. 识别 read-after-write、write-after-write 等跨 thread race；
2. 区分 execution barrier、memory visibility/order 与 atomicity；
3. 正确说明 `__syncthreads()`、warp primitive、atomic 和 kernel boundary 的作用域；
4. 分析 warp divergence，并避免用删分支破坏正确性。

## 1. Race 的本质是未排序的冲突访问

如果两个执行者访问同一位置，至少一个是写，且没有建立满足算法的顺序，就可能有 data race：

```cpp
// kernel fragment: incorrect global counter
counter[0] += 1;
```

这不是一次不可分割操作，而是 read → add → write。多个 threads 可读到同一个旧值并覆盖彼此。

先问四个问题：

1. 冲突位置在哪里：register、shared、global，还是 host/device 共享状态？
2. 参与者范围：warp、block、grid、多个 kernel、多个 device、host thread？
3. 需要什么性质：只需所有人到齐、需要发布数据、还是同一位置的 read-modify-write 必须原子？
4. 能否重写算法，先做 thread/block 私有累加，减少共享更新？

## 2. `__syncthreads()` 是 block 级 barrier

典型 shared tile：

```cpp
// kernel fragment
shared[threadIdx.x] = input[i];
__syncthreads();
const float neighbor = shared[(threadIdx.x + 1) % blockDim.x];
```

barrier 确保 block 中参与的 threads 到达，并使此前相应内存访问对 block 内 threads 可见。它**不能**：

- 同步另一个 block；
- 让多个 blocks 按 block index 顺序运行；
- 把非原子的冲突更新变成 atomic；
- 修复 host 过早读取仍在执行的 kernel 结果。

### 条件 barrier 必须全 block 一致

危险形式：

```cpp
// incorrect fragment: some threads may skip the barrier
if (i < n) {
  __syncthreads();
}
```

只有当条件对整个 block 一致时，条件 barrier 才安全。边界 thread 通常应参与协作与 barrier，只把越界 load 替换为中性值，而不是提前 return。

## 3. Warp-level primitive 需要显式参与集合

`__shfl_sync`、`__ballot_sync`、`__syncwarp` 等让 warp 内 lanes 交换或同步。`*_sync` 的 mask 描述参与 lanes；它不是装饰参数。

正确思路：

- 从当前 active lanes 得到合法 mask；
- 保证 mask 中声明的 lanes 都执行对应 primitive；
- 不依赖旧式“lockstep 所以不用同步”的直觉；
- 对跨 warp 数据仍使用 shared memory + block barrier 或更高层算法。

## 4. Atomic 只保证定义范围内的不可分割更新

```cpp
// kernel fragment
atomicAdd(counter, 1);
```

它能避免 `counter += 1` 的丢失更新，但仍有三个限制：

1. **contention**：大量 threads 更新同一地址会串行化；
2. **scope**：CUDA 提供不同 thread scope 的 atomic 接口，必须与通信范围匹配；
3. **ordering**：原子更新本身不自动发布任意其他普通 memory writes；需要按算法选择 memory order/fence/同步机制。

高性能 reduction 常先在 thread/warp/block 内归约，再由少量 atomic 合并 block 结果，而不是每个元素直接争用一个全局 counter。

### 把 atomicity、scope 与 memory order 分开写

传统 `atomicAdd()` 这类 legacy atomic 默认提供 relaxed memory ordering；无后缀、`_block`、`_system` 变体分别对应不同通信 scope，且 system scope 还受平台与内存条件约束。它们保证目标位置的 read-modify-write 在相应 scope 内原子，不等于为其他普通 load/store 自动建立 acquire/release 顺序，也不等于一次 atomic 后“所有线程都到齐”。

当算法要发布“数据已经写好”的 flag 时，应明确设计：payload 的普通写、release/publish 操作、consumer 的 acquire/等待，以及参与者 scope。较新的 CUDA C++/libcu++ atomic 接口可表达 C++ 风格 memory order 与 thread scope；具体类型、操作、架构和 Toolkit 门槛会变化，编写生产代码时以目标 Toolkit 的 CUDA C++ language extensions 与 libcu++ 文档为准。不要把 `__threadfence()` 单独当 barrier：fence 约束调用 thread 的内存操作顺序，不负责让其他 threads 到达，也不替代原子 flag 的协议。

## 5. Grid 级依赖通常用 kernel boundary 表达

普通 kernel 的 blocks 可以任意顺序执行，不能在 kernel 内实现“所有 blocks 都等在一个自制 global barrier”——未被调度的 blocks 可能永远拿不到资源，造成死锁。

常见安全分解：

```text
kernel A: 每个 block 产生局部结果
  ↓ 同一 stream 的顺序或 event dependency
kernel B: 归并局部结果
```

CUDA 也有 cooperative groups/cooperative launch 等受设备能力和 launch 条件约束的 grid 同步机制，但必须显式核对支持与资源上限，不能把它当普通 launch 的默认语义。

## 6. Divergence 是 warp 内路径分歧

```cpp
// kernel fragment
if ((threadIdx.x & 1) == 0) {
  do_a();
} else {
  do_b();
}
```

同一 warp 的 lanes 分到不同路径时，硬件可能分别执行路径并屏蔽不参与 lanes，降低执行效率。若条件按 warp 划分，例如 `warp_id < k`，每个 warp 内一致，通常不会产生同样的 lane-level divergence。

但不要把任何 `if` 都视为灾难：

- 很短分支可能被 predication；
- 边界判断只影响最后少量 lanes；
- 移除分支后做大量无用计算可能更慢；
- 数据重排能减少 divergence，却可能增加访存与预处理成本。

必须结合输入分布和 profiler 分析。

## 7. 三类问题不要互相替代

| 问题 | 主要工具 | 常见错误替代 |
| --- | --- | --- |
| threads 何时都到达 | barrier / stream/event dependency | 用 atomic 计数就认为所有数据已可见 |
| 某个共享值如何无丢失更新 | atomic 或无共享写的算法 | 只加 `__syncthreads()` |
| warp 为何吞吐下降 | 重构控制流、数据布局、测量 | 删除正确性边界判断 |

## 练习：修复 block histogram 设计

原设计让每个元素直接 `atomicAdd(&global_hist[bin], 1)`。写出改进流程：每 block 在 shared memory 建局部 histogram，再合并到 global。

回答：

1. shared histogram 如何清零？
2. 清零后为什么需要 barrier？
3. 更新 shared bins 是否仍可能需要 atomic？
4. 写 global 前为什么还要 barrier？
5. 对高度偏斜输入，瓶颈可能在哪里？

### 成功标准

- 所有 threads 参与 shared 初始化与两次 block barrier；
- block 内同一 bin 仍有冲突更新，因此不能只靠 barrier；
- global atomic 次数从“每元素一次”降为“每 block 每非零 bin 至多一次”的方向；
- 能指出 shared atomic contention、bank conflict、初始化成本和 global merge 都可能成为新瓶颈。
