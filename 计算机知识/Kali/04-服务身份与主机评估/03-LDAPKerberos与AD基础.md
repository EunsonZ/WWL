# LDAPKerberos与AD基础

**先修关系：** [[计算机知识/Kali/01-系统与网络基础/06-TCPIP路由DNS与TLS|TCPIP路由DNS与TLS]]；[[计算机知识/Kali/03-Web与API安全/08-认证会话越权与API测试|认证会话越权与API测试]]；[[计算机知识/Kali/04-服务身份与主机评估/02-SMBNFS与目录共享|SMBNFS与目录共享]]。

## 目录、认证与授权图各解决什么问题

Active Directory（AD）把对象目录、域身份认证和策略管理等能力组织在一起。LDAP 是访问目录的一种协议；Kerberos 是常见的票据认证协议；对象 ACL 与组关系影响授权。三者不能互相替代：成功查询目录并不意味着拥有远程管理员权限。

本章建立机制，不搭建真实企业域，也不导出任何真实目录。跨机例子必须在你拥有并隔离的实验域中完成。

## LDAP 的对象与搜索范围

目录对象由可区分名称（DN）定位，例如教学 DN `cn=Alice,ou=People,dc=lab,dc=test`。搜索具有基准、范围、过滤器与属性列表。范围 `base` 只针对基对象，`one` 是一层，`sub` 遍历子树；缩小范围比事后过滤整份导出更能减少不必要数据。[^s1]

```bash
ldapsearch -VV
# 扩展模板：自建、已配好可信 TLS 的目录；本包没有启动此服务
# ldapsearch -x -H ldaps://dc.lab.test -D 'cn=labreader,dc=lab,dc=test' -W \
#   -b 'ou=People,dc=lab,dc=test' -s one -l 5 -z 10 \
#   '(cn=Alice)' cn
```

`-W` 交互读取密码，`-l/-z` 限定时间与结果条数，末尾只请求 `cn`。TLS 名字和 CA 必须正确；不把证书错误通过关闭校验来绕过。LDAP 过滤器有自己的转义规则，不能把 SQL 转义函数拿来复用。

## LDAP 的搜索结果不只有条目列表

DN 标识目录位置，但重命名/移动会改变其文本；长期关联还需适合该目录实现的稳定标识。过滤器、搜索 base 和 scope 决定查询空间，属性 ACL 决定你能看到哪些字段。服务器返回的结果码、大小/时间限制以及引用（referral）同样是证据。仅看到前十条就当作完整目录，是把有限观察误认为总体。[^v2-ldap4511]

`-z 10` 限制请求结果规模，但服务器仍可能采用自己的更严格政策。分页不是扩大授权的理由；必须保持原有对象范围与总条数上限。LDAPS 与 StartTLS 都需要正确校验服务身份，StartTLS 请求也应采用要求成功而非失败后继续明文的合同。

## Kerberos 的简化流程

客户端向密钥分发中心（KDC）获得用于进一步请求的票据，再获取具体服务的票据；服务验证相关票据与认证信息后建立身份上下文。工作依赖正确的域信息、服务标识、密钥和时间等条件。[^s2]

可把简化路径写成“用户 → KDC → 服务票据 → 应用服务”，但这只是认证流程，不自动赋予应用操作权限。TGT、服务票据、账户密码与会话密钥是不同对象，不能混称“密码”。

DNS 和时间故障经常表现为身份工具失败。检查域解析、服务名称与本机时间，再讨论认证机制。`klist` 可检查当前票据缓存，`kinit` 用于在相应环境获取票据；输出与缓存是敏感身份材料，不进入分享包。

## Kerberos 中谁能解开哪一部分

简化地说，AS 阶段为客户端建立与票据授予服务交互所需的材料；TGT 面向 KDC 的票据授予服务，客户端持有它并不意味着能自行读取票据内部所有内容。TGS 阶段获得面向具体服务的票据；AP 阶段将服务票据和认证信息交给服务。服务通过其密钥与协议校验建立身份上下文，随后仍做应用授权。[^v2-kerberos4120]

认证器与时间约束参与重放防护，因此时钟偏差可能使正确凭据也失败。这里省略了不同预认证、跨域信任和具体加密类型的实现细节，不把这一简图作为协议实现说明或当代算法配置建议。

## 票据是给服务看的封装，认证器证明当前使用者持有会话材料

前面的 AS、TGS、AP 流程可以用“收件人”重新理解。在经典对称密钥的简化模型中，TGT 的加密部分面向票据授予服务，服务票据的加密部分面向目标服务；客户端还获得自己能够使用的相应会话密钥材料。客户端转交票据不需要先解密票据给服务看的那一部分。实际预认证与密钥建立可以有扩展，不能把下表当成全部实现格式。[^v5-kerberos]

| 对象 | 谁需要使用其中的秘密信息 | 它主要解决什么问题 |
| --- | --- | --- |
| TGT | 票据授予服务 | 让客户端后续向 TGS 请求服务凭证 |
| 服务票据 | 目标服务 | 使服务取得受保护的身份及会话上下文 |
| 客户端持有的会话材料 | 客户端 | 支持后续认证器等协议计算 |
| 认证器 | 持会话密钥的一方生成，服务验证 | 证明当前交互关联到持有会话秘密的主体 |

原创类比：信封是交给指定收件人的，寄件人携带信封并不必然知道封内全部内容；但类比不能代替密码学，因为票据复制和认证器重放都必须由协议状态处理。票据不是现实中的一次性纸票，光看文件存在无法判定可用性。

## 时间戳与重放缓存：为什么“时间还新”仍然不够

时间检查排除过旧或过新的认证信息，却不能仅凭时间戳排除允许时间窗口内的重复提交。RFC 4120 在没有其他适当重放防护的情况下要求服务维护重放缓存；认证通过之后仍须另做应用授权。[^v5-kerberos]

原创推演：允许时间窗口为某个正数，服务在相同窗口内两次收到同样的认证器。两次都满足“时间偏差不大”，所以新鲜度条件不能区分第一次与第二次。还要知道该认证器是否已被使用，或依靠协议明确提供的等价重放防护。这里不把时间窗口的示例值当成推荐配置，也不开展重放测试。

这与 [[计算机知识/Kali/03-Web与API安全/10-TLS证书与服务配置评估|TLS中的身份与重放边界]]、[[计算机知识/Kali/03-Web与API安全/12-现代API业务逻辑与并发边界|业务幂等]] 有共同结构，但三者保护的对象不同：认证消息、早期传输数据和业务副作用不能混为一层。

## SPN、DNS 名称与 IP 地址不能随意互换

服务主体名称（SPN）表达服务与实例的身份；连接地址解决网络到达。把域名直接替换成 IP，可能改变客户端构造的服务标识或认证路径。出现失败时先记录使用的名字、域、缓存和时钟，不先关闭签名或改弱认证。

实验中“有 TGT、能请求某服务票据、服务接受认证、某操作被授权”应保存为四个独立状态。`klist` 的存在性检查不证明下一次请求一定使用那个缓存，更不证明票据未过期；环境变量、用户上下文和程序实现都需要核对。

## NTLM、签名与通道绑定的概念位置

Windows 环境可能存在 NTLM 等认证路径；SMB/LDAP 的签名、加密与通道绑定针对不同完整性和绑定问题。它们的支持、默认和兼容性依具体系统版本与策略变化，必须查当前官方配置文档，不能从旧攻击教程推断今日默认值。

本页不提供票据盗取、凭据导出或认证中继操作。关注的是如何减少不必要协议、限制权限和核验正常业务仍然可用。

## 从组成员到权限图

Alice 属于某组，该组被赋予某对象权限，这是一条权限传播路径。嵌套组、继承、显式拒绝与具体操作语义会使结果复杂；不能仅看图上一条线就认为一定可执行。[[计算机知识/Kali/04-服务身份与主机评估/05-BloodHound权限图与修复验证|BloodHound]] 帮助组织关系，但每条边仍需解释前提。

自检：`ldapsearch` 返回用户列表，是否说明这些用户的口令可读取？不成立，目录属性读取与凭据获取是不同权限和数据类型。应记录实际请求的属性，避免夸大。

## 用四个互不替代的问题读工具输出

`klist` 展示选定凭据缓存中的条目；协议客户端回答能否按它的名字、缓存与配置完成交互；目录查询提供对象或成员信息；服务端授权日志说明具体动作的决定。将它们依次对应“材料存在、认证使用、权限依据、动作结果”。若某一步失败，就在该层保留错误和替代解释，而不是把所有失败统称密码错误。

## 从身份机制回到最小权限

组嵌套、对象 ACL 与委派可以增加间接授权；域信任不是任意主体自动获得另一域所有权限。把授权边写成“主体在什么条件下可对何对象做何动作”，再连接 [[计算机知识/Kali/04-服务身份与主机评估/05-BloodHound权限图与修复验证|权限图审阅]]，能避免把每一条关系都理解成同一种控制能力。
