# 任务委托写法

高质量委托不需要很长，但必须让 Agent 知道“完成是什么样、能碰什么、怎样证明完成”。可直接插入核心模板 [[Obsidian知识/90-资源/01-模板/核心模板/AI任务委托|AI任务委托]]。

## 六段式结构

1. **结果**：先写最终可见的交付物。
2. **上下文**：给入口文件、已有约定和真实问题。
3. **范围**：列出可读、可写与不得修改的路径或系统。
4. **约束**：格式、隐私、兼容性、工具和副作用边界；先说明任务是只读、可写 Markdown，还是只能输出方案。
5. **验收**：用可观察的检查项定义完成。
6. **证据**：要求列出改动、测试结果、未知与恢复方式。

## 可复制的短提示词

```text
目标：把【当前状态】改造成【期望结果】。
入口：【文件、链接或目录】。
可修改：【精确范围】；不要修改：【排除项】。
执行层：【只读 / 可修改指定 Markdown / 只输出方案】；外部动作需单独授权。
必须保持：【兼容性或内容不变量】。
验收：1) 【检查一】；2) 【检查二】；3) 【检查三】。
完成后报告：改动清单、验证证据、剩余风险和恢复方法。
遇到凭据、插件或账户授权、外部发布、破坏性操作或范围扩张时先停下询问。
```

## 让任务更容易并行

可以并行的子任务应读取不同资料或产生互不覆盖的交付物，例如“研究插件”“设计目录”“审计链接”。多个 Agent 同时改同一个配置文件通常不值得；先让它们提交发现，再由一个负责人统一落盘和验证。
