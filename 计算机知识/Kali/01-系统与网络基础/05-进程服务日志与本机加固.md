# 进程服务日志与本机加固

**先修关系：** [[计算机知识/Kali/01-系统与网络基础/04-Shell文件权限与文本处理|Shell文件权限与文本处理]]。

## 从端口追踪到进程和持久配置

`端口开放` 是网络观察，`某进程监听` 是本机观察，`某服务开机启动` 是持久配置。三者相关但不同。一个程序可以不经 systemd 手工启动；一个服务可以处于运行状态却不监听网络；一个启用的服务也可能启动失败。

```bash
ps -eo pid,ppid,user,etime,args --sort=pid
ss -lntup
systemctl --failed
systemctl status ssh --no-pager
```

`ss` 的进程信息可能因权限而缺失；不能把“没有显示程序名”写成“端口没有进程”。查询服务前先确认本机采用 systemd 且服务名存在。官方手册区分 `start`、`enable`、`is-active`、`is-enabled`，它们分别涉及当前运行与启动配置。[^s1]

## 有限授权与最小权限

普通账户完成阅读、离线分析和大多数 HTTP 请求；只有确实需要原始套接字、受限设备或系统配置修改时才考虑提升权限。每条 `sudo` 应回答“具体需要哪项权限”，不能把整套桌面应用都当管理员运行。

```bash
sudo -l
getcap /usr/bin/dumpcap 2>/dev/null
```

前者查看当前用户可使用的 sudo 规则，可能要求密码；后者依赖 `getcap` 已安装。输出可能暴露本机配置，分享前脱敏。capabilities 将部分传统 root 权限拆开，但组合能力仍可很强，不等于获得“安全的半个 root”。

## 日志是有条件的观察记录

```bash
journalctl -b --no-pager -p warning
journalctl -u ssh --since '30 minutes ago' --no-pager
date -u '+%Y-%m-%dT%H:%M:%SZ'
timedatectl status
```

分析日志前明确时区、采样时段、轮转与保留策略。查不到记录至少有几种解释：事件没有发生、应用没有记录、权限不足、日志不在这里、轮转/保留导致缺失、时钟偏差。不能直接从“无日志”推断“无人访问”。

跨系统关联优先使用 UTC 时间戳加原始时区说明。网络包时间、应用日志时间和文件系统时间不一定来自同一时钟。时间线方法见 [[计算机知识/Kali/06-取证逆向与检测/01-取证流程镜像与时间线|取证流程与时间线]]。

## 防火墙与服务加固

首先列出而不是改动：

```bash
sudo nft list ruleset
ss -lntup
```

这些查询也需要相应权限和工具存在。不要为了让实验通就执行清空规则、停止防火墙或关闭安全模块。应确认服务只监听实验接口，开放明确需要的单个端口，记录修改前后状态与回滚方案。远程改防火墙尤其可能把自己的管理通道切断。

本课程不直接给一份覆盖所有机器的防火墙脚本，因为网络管理器、Docker、VPN 和虚拟化平台可能已有规则。把不同规则管理器混用后，单看某个前端可能无法解释实际包路径。

## 常见资源故障

`df -h` 看已挂载文件系统容量，`df -i` 看 inode；磁盘有空间但 inode 耗尽仍可能无法创建文件。`free -h` 的缓存不能简单算作“被无用程序占满”；`top/htop` 用于观察资源，而不是看到高 CPU 就强杀所有进程。`lsof` 能关联打开文件与进程，但输出需要权限且会受系统状态变化影响。

停止进程先考虑正常退出与 `SIGTERM`；`SIGKILL` 无法让进程完成自己的清理逻辑，可能留下半写入输出。暂停、杀进程和停止服务是不同动作，应记录你做的是哪一个。

## 自检

“`systemctl enable app` 后，8000 端口仍不开，是 systemd 坏了。”检查点：enable 不等于立即启动；即使启动成功，监听地址、端口和应用配置也可能不同。用服务状态、日志与 `ss` 交叉验证，再回到 [[计算机知识/Kali/00-导航与方法/04-从观察到结论的安全方法|从观察到结论]] 的证据层次。

## 从 shell 能运行，到服务能运行，还缺哪些条件

交互 Shell 里成功不代表 systemd 服务里成功。服务有自己的运行用户、工作目录、环境变量和限制；相对路径可能指向不同目录，PATH 可能没有你的虚拟环境，服务用户可能无法遍历家目录。先比较这四项，而不是立即让服务改成 root。[^v2-systemdexec]

```bash
# 示例服务名是 ssh；不存在时保留“单元不存在”的结果。
systemctl show ssh -p User -p Group -p WorkingDirectory -p ExecStart
systemctl cat ssh
```

输出可能包含管理员写入的敏感参数，只在本机审阅，不整份复制进公开笔记。`systemctl cat` 展示主配置与覆盖片段，能解释“修改了一个文件但生效结果不一样”的情况。临时启动进程、启用单元、socket 激活及周期任务是不同触发方式；单独观察一个 PID 不能概括所有入口。

## 权限、资源限制和进程生命周期的交叉诊断

端口绑定失败可能是地址不存在、端口占用或权限不足；打开文件失败可能是路径权限、只读挂载或文件描述符耗尽。此时分别看 `ss`、具体错误信息、挂载状态和进程限制。不能把每个 `Permission denied` 都推成“需要 sudo”，也不能把每个超时都推成“需要加内存”。

向进程发送 SIGTERM 后，应确认进程实际退出、监听消失、输出文件写完；“kill 命令返回成功”只说明信号发送请求被接受，不自动证明应用完成清理。如果有父进程或服务管理器自动重启，PID 会改变，但服务仍存在。

防火墙更详细的包路径、连接跟踪和命名空间见 [[计算机知识/Kali/01-系统与网络基础/09-状态防火墙与网络命名空间|状态防火墙与命名空间]]。该专题解释为什么监听、可达和允许规则之间不是一条简单等号。
