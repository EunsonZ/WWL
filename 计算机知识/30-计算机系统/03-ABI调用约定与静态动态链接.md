# ABI、调用约定与静态/动态链接

## 本课目标

学完后，你应该能够：

- 区分源代码 API、指令集 ISA 与二进制 ABI；
- 解释一次函数调用为何需要约定参数、返回值、寄存器、栈和对齐；
- 画出源文件到目标文件、库和可执行文件的基本链接流程；
- 区分静态链接与动态链接的收益、成本和失败模式；
- 用 ABI 边界分析“编译通过但启动失败”或“插件能找到却不能安全调用”。

## 1. 三层契约：API、ISA、ABI

| 契约 | 主要参与者 | 典型问题 |
| --- | --- | --- |
| API | 源代码与源代码 | 函数名、参数类型、返回值和语义是什么？ |
| ISA | 机器指令与 CPU | CPU 能执行哪些指令、寄存器和寻址方式？ |
| ABI | 分别编译的二进制组件 | 参数放哪里、符号叫什么、对象怎样布局、库怎样加载？ |

同一个 API 可以在不同架构上有不同 ABI；同一 ISA 上也可能存在不同操作系统或工具链 ABI。ABI 不是单独一个文件，而是一组必须共同满足的二进制约定。

## 2. 调用约定：调用者和被调用者的交接单

设源代码概念上有 `add(a, b)`。编译后，双方至少要一致同意：

- 前几个参数放寄存器还是栈，超出后怎样传；
- 整数、浮点、向量和聚合对象分别怎样传；
- 返回值放哪个位置，过大的返回对象是否由调用者提供空间；
- 哪些寄存器由调用者负责保存，哪些由被调用者恢复；
- 栈在调用点必须满足什么对齐，调用结束后由谁平衡；
- 可变参数、异常展开、线程局部存储等怎样协作。

这份约定因体系结构和 ABI 而异。不能把某张 x86-64 寄存器表直接当成 AArch64、Windows 与 Unix-like 平台共同真理。

### 小例子：为什么双方必须一致

如果调用者把第一个整数参数放在寄存器 A，被调用者却按另一种约定从寄存器 B 读取，那么源代码里的类型声明完全正确也无济于事。ABI 错配会表现为错误值、崩溃、栈损坏，甚至只在优化构建中出现。

## 3. 栈帧是实现手段，不是固定模板

函数可能用栈保存局部对象、返回地址、溢出的参数和被要求保留的寄存器。调试图里常画出整齐的栈帧，但优化器可以：

- 把局部值只放在寄存器；
- 内联函数，使调用边界消失；
- 省略固定帧指针；
- 重排或消除没有可观察效果的操作；
- 对尾调用复用当前调用路径。

所以“源代码一行对应栈上一格”只是入门示意，不能作为调试优化程序的保证。

## 4. 从源文件到可执行文件

一个简化流程如下：

```text
源文件
  → 预处理/编译/汇编
  → 可重定位目标文件：机器码片段 + 符号 + 重定位信息
  → 链接器解析符号、安排区段、应用重定位
  → 可执行文件或共享库
  → 程序加载器建立映射并完成运行时装载工作
```

**符号**让一个目标文件引用另一个目标文件定义的函数或数据；**重定位**记录“这里的地址/偏移要等最终布局确定后再修正”。链接失败中的“未定义符号”通常表示声明可见但没有找到匹配定义；“重复定义”则表示多个输入提供了冲突的强定义。

## 5. 静态库与共享库不是“打包格式差异”

### 静态链接

链接器从静态库中选择需要的目标代码，复制进最终产物。常见特点：

- 部署时少依赖对应共享库文件；
- 每个产物可能带有自己的代码副本，体积和更新成本增加；
- 库漏洞修复后通常需要重新链接并重新发布使用它的产物；
- 并不意味着“完全没有运行时依赖”，操作系统接口、动态加载组件和许可证约束仍需单独检查。

### 动态链接

可执行文件保留对共享库和符号的依赖，加载器在启动或显式装载时解析它们。常见特点：

- 多个进程可能共享只读代码页；
- 可独立更新库，但更新必须保持所需 ABI；
- 部署需要正确找到版本和架构匹配的库；
- 搜索路径、环境、rpath/runpath 和加载器规则错误会导致启动失败或加载到意外版本。

环境变量和命令搜索属于 Linux 用户空间配置，见 [[计算机知识/20-操作系统/01-Linux/07-环境变量Shell启动与PATH|环境变量、Shell 启动与 PATH]]；动态加载器的库搜索并不等同于 shell 的 `PATH`。

## 6. 名称修饰、C ABI 与 C++ 边界

C++ 需要表达重载、命名空间和类型，因此编译器通常对符号做名称修饰。不同编译器版本、标准库、编译选项或 C++ ABI 可能生成不兼容的符号或对象布局。

`extern "C"` 可以要求使用 C 语言链接规则，常用于插件或跨语言入口，但它只解决一部分问题：

- 不会自动让 C++ 类、异常、模板或标准库容器变成稳定跨编译器 ABI；
- 不会统一整数宽度、结构体布局、内存分配器和所有权；
- 不会定义函数的业务语义、版本协商或线程安全。

稳健的插件边界常使用固定宽度标量、字节缓冲区、显式长度、版本号、错误码和清楚的“谁分配、谁释放”规则。

## 7. ABI 兼容为何服务于 llama.cpp 后端

当程序在运行时选择 CPU、Metal、CUDA 或其他后端时，它可能加载不同共享库或插件。要安全调用，双方不仅要“有同名函数”，还要一致理解：

- 目标架构和调用约定；
- 导出符号与版本；
- 张量描述结构的字段、对齐和大小；
- 缓冲区所在设备、生命周期和释放责任；
- 错误如何返回，异常是否允许跨边界。

ABI 稳定并不保证计算结果正确或性能良好；它只保证二进制交接有共同规则。数据表示边界回看 [[计算机知识/30-计算机系统/01-数据表示字节序与对齐|数据表示、字节序与对齐]]。

不要预设 llama.cpp 的所有后端都以同一种共享库形式存在：某个 revision/发行包可能静态编入、动态装载、按 feature 生成不同 target，或根本未启用。实际证据来自 CMake 配置摘要、target 依赖、最终链接命令、产物依赖表和运行时日志；代码阅读方法见 [[计算机知识/10-编程语言/02-C++/10-阅读大型C++仓库与llama-cpp调用链|阅读大型 C++ 仓库与 llama.cpp 调用链]]。

## 8. 常见失败的分层定位

| 现象 | 优先检查的层 |
| --- | --- |
| 编译期找不到声明 | 头文件、模块、API 可见性 |
| 链接期未定义符号 | 目标文件/库是否参与、符号名称、链接顺序与可见性 |
| 启动时找不到共享库 | 部署路径、加载器规则、架构与依赖链 |
| 找到库却找不到符号 | 库版本、导出规则、名称修饰、ABI 版本 |
| 调用后值错或崩溃 | 调用约定、结构布局、所有权、编译选项与运行库 ABI |
| 只在释放时崩溃 | 跨边界分配/释放、对象生命周期、运行库不匹配 |

## 练习

1. 画出 `main.cpp` 与 `math.cpp` 分别编译、再链接为程序的流程。标出声明、定义、符号和重定位各在哪一步参与。
2. 设计一个跨语言张量插件的最小入口：输入只允许固定宽度元素类型编号、维度数组、字节缓冲区与长度。写清版本、不支持类型、内存所有权和错误返回。
3. 对“程序启动时报共享库缺失”和“链接时报未定义符号”分别列出前三个证据来源，不要把两者都归因于 `PATH`。
4. 解释为什么两个使用同一 C++ 头文件编译成功的组件仍可能 ABI 不兼容。

## 成功标准

- 你能用一句话分别定义 API、ISA 和 ABI；
- 你能画出源文件 → 目标文件 → 链接 → 加载的路径；
- 你能区分静态库内容进入产物与共享库运行时解析这两种边界；
- 你设计跨组件接口时会显式写出版本、布局、所有权和错误规则。
