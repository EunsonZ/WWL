# 认证会话越权与API测试

**先修关系：** [[计算机知识/Kali/01-系统与网络基础/07-HTTP浏览器会话与信任边界|HTTP浏览器会话与信任边界]]；[[计算机知识/Kali/03-Web与API安全/01-Web测试模型与手工基线|Web测试模型与手工基线]]。

## 认证成功只是测试的起点

认证证明请求绑定到哪个主体；授权决定该主体能否执行特定操作。水平越权通常跨越同级用户的对象边界，垂直越权跨越角色/权限层级。OWASP 强调默认拒绝、每次请求都检查权限等原则。[^s1]

必须由服务端根据可信身份与对象关系作决定，不能相信客户端传来的 `owner=Alice` 或隐藏表单里的角色字段。本课程的名字只是教学标识，不是真实身份认证系统。

## 会话生命周期

登录、权限提升、退出、口令修改和超时都应有明确的会话语义。检查会话是否更新、旧会话是否失效、服务端是否真正终止授权，而不只看浏览器删除 Cookie。[^s2]

Cookie 属性、随机标识和传输保护分别解决不同风险。会话 ID 不应出现在 URL、访问日志或公开笔记中。记住登录状态的便利功能需要更长生命周期的威胁模型，不能只用一次短会话实验代表所有状态。

## JWT 与 OAuth 的常见混淆

JWT 是令牌格式，不是“天然安全的登录方案”。Base64url 解码只能读出载荷，不证明签名有效；验签还需要正确的算法策略、密钥、发行者、受众和时间声明等条件。应用是否允许撤销以及如何处理权限变化，还要单独设计。

OAuth 的授权委托与用户认证也不能直接等同；使用 OpenID Connect 时又增加身份层。具体规范与实现随场景而变，本页只建立工作概念，不提供令牌伪造或绕过流程；深入实现需另行核验对应标准和服务端配置。

## OAuth与OIDC：先分清谁接收哪种凭证

OAuth 的授权与 OIDC 增加的身份层不可直接混同。把资源所有者、客户端、授权服务器和资源服务器分别画出，才能解释令牌的受众。OIDC 的 ID Token 面向客户端表达身份认证结果；Access Token 用于访问对应资源；Refresh Token 用于向授权服务器申请新令牌；授权码是流程中的短期中间凭证，不是应用可以随处当作会话的通用密码。[^v5-oidc][^v5-oauth-bcp]

| 看到的对象 | 需要追问 | 容易误下的结论 |
| --- | --- | --- |
| ID Token | 谁签发、面向哪个客户端、关联哪次认证 | “已经登录，所以任意 API 都应接受它” |
| Access Token | 面向哪个资源、权限范围、有效状态与约束 | “能解析 JWT，所以一定可访问当前资源” |
| Refresh Token | 哪个客户端持有、如何绑定与撤销 | “过期时间长，只是另一个普通访问令牌” |
| 授权码 | 属于哪次流程、哪个客户端、是否已被使用 | “拿到字符串就等于已建立应用会话” |

Access Token 可以是结构化令牌，也可以是不透明引用；不能因工具无法本地解码便断言其损坏。OIDC 的主体标识也必须放在签发者上下文中解释，不能把不同签发者的相同 `sub` 自动合成一个人。

## OAuth 授权码流程的角色与绑定

资源所有者允许客户端访问受保护资源；授权服务器处理授权并签发相应令牌；资源服务器验收访问令牌。这几个角色可以由同一产品承担，但职责仍应区分。授权码不是访问令牌，访问令牌也不自动是客户端的登录身份证明。

在授权码流程中，PKCE 让一次授权请求与后续兑换动作绑定到同一随机 verifier；使用 `S256` 的 challenge 不把 verifier 本身暴露在授权请求中。仍需验证重定向 URI、发行者和事务关联，不能把“带 PKCE”当成全部 OAuth 安全性质。RFC 9700 对 PKCE 支持和防降级有具体要求。[^v2-oauth9700]

本包不提供真实令牌、不运行 OAuth 服务器，也不执行授权流程探测；这里用于阅读配置与理解故障。Web 与移动端都可沿此机制连接到 [[计算机知识/Kali/05-密码无线与专门领域/07-AndroidADBJadx与移动应用分析|移动应用身份边界]]。

## state、nonce与PKCE分别约束哪条关联

把流程看作三条需要保存的对应关系：浏览器发起的流程与返回响应对应；身份令牌与当前认证请求对应；授权码与实际发起该流程的客户端实例对应。`state` 常用于前一类关联与请求伪造防护，OIDC 的 `nonce` 将身份令牌与认证请求绑定，PKCE 将授权请求中的挑战与令牌交换时的验证材料绑定。具体流程对这些机制的要求与可替代条件应按规范审查，不能机械认为“加了任一个，另外两个永远可删”。[^v5-oidc][^v5-oauth-bcp]

原创比较：攻击者无法替换授权码，并不意味着应用就不会接受发给另一个受众的令牌；令牌受众正确，也不证明当前浏览器响应属于用户自己刚发起的登录。两者属于不同安全条件，必须分别验证。

## 从解码 JWT 到接受一个身份，中间还有哪些判断

把令牌分段并解码只得到未经信任的输入。验证器必须基于服务端固定策略选择可接受算法和密钥来源，验证签名及约定声明，再确定是否用于当前发行者、受众和令牌类型。`kid` 等字段可以是受控密钥索引的输入，但不应成为任意文件路径或网络地址。不要自己编写密码学验证来替代成熟库。[^v2-jwtbcp]

时间检查需要明确过期、尚未生效、时钟偏差容忍和缺失字段政策。验签通过的旧令牌也可能携带已经撤销的角色，因此业务仍需定义权限变更与撤销传播规则。只在登录时计算一次权限、后续永不复核，会把“凭据真实”错误等同为“现在仍被允许”。

## JWT验证应当由应用决定可接受的令牌类型

算法允许集合、密钥来源、签发者、受众、有效时间和必要声明必须由预期协议决定，不能由不可信令牌自行选择。不同用途的 JWT 应采用相互排斥的验证规则或其他可靠区分，防止把一种已正确签名的令牌误用为另一种。[^v5-jwt-bcp]

最后仍需对象授权：一个在密码学上有效、受众正确的访问令牌，可以合法地没有读取 Bob 报告的权限。因此令牌审查回到 [[#双账户矩阵比猜 ID 更有说服力|双账户矩阵]] 与 [[#把授权矩阵扩为五个维度|主体—对象—动作—租户—字段]]；签名有效不能跨越 [[计算机知识/Kali/03-Web与API安全/12-现代API业务逻辑与并发边界|字段授权、状态与并发边界]]。

## 双账户矩阵比猜 ID 更有说服力

在自建应用中创建 Alice 与 Bob 的测试数据，记录各自对象。用两个隔离会话分别正常读取自己的对象，再在固定会话下访问另一个测试对象。这样能独立知道期望所有者，避免把公开资源误当私人数据。

| 会话 | 对象 17（Alice） | 对象 18（Bob） |
| --- | --- | --- |
| Alice | 允许 | 拒绝 |
| Bob | 拒绝 | 允许 |
| 未认证 | 拒绝 | 拒绝 |

“拒绝”可以是 403，也可以按产品设计返回 404；关键是不返回受保护内容、不产生未授权状态改变。`200` 中包含拒绝页面也不能按状态码误判为允许。

## API：对象、字段、功能三层授权

对象级授权决定能否读报告 18；属性级授权决定能否看或改某个敏感字段；功能级授权决定能否调用管理员操作。REST、GraphQL 或 RPC 都需要这些判断。

接口批量更新可能发生“客户端提交了服务端本不允许修改的字段”。修复应采用明确允许字段映射与服务端角色判断，而不是只在前端隐藏输入框。GraphQL 还要考虑查询复杂度、深度与资源预算，schema 可见性本身不替代授权分析。

使用 curl/Burp 保存一组最小成对请求，敏感值脱敏；涉及批量导出、列表查询或删除时用极少教学对象并有回滚。不要通过读取真实用户数据来“证明影响”。

## 把授权矩阵扩为五个维度

在主体和对象之外增加动作、租户与字段：Alice 能读自己的报告，不必然能审批；同租户审核员可按合同读报告摘要，不必然能读私密备注；其他租户的管理员也不必然跨租户访问。角色名不是无限授权凭证。

新增 [[计算机知识/Kali/07-综合实验/12-实验I多租户字段与动作授权|实验 I]] 用有限纯函数测试允许、拒绝、字段投影和状态条件，**不执行持久状态改变**。实际事务写入、失败回滚与幂等重放由 [[计算机知识/Kali/07-综合实验/15-实验L事务幂等与并发控制|实验 L]] 单独验证。身份从可信测试夹具进入，不从请求中的 `role` 或 `tenant` 字段自报；因此它验证授权规则，仍不声称实现认证系统。

## 授权条件必须和被执行的动作绑定

假设 Alice 在红租户拥有报告 17，Bob 是同租户审核者，Carol 属于蓝租户。初始状态为 draft、版本 0。判断 Alice 可 submit 之后，如果执行端又接受来自请求的任意 owner、tenant 或目标 ID，那么先前的允许判断并没有覆盖后来真正执行的操作。授权结果不是一张可随意改目的地的通行证。

因此检查的输入至少绑定可信主体、实际对象、动作、必要字段和状态版本。请求者可以提出“我要改哪个对象”，但不能通过自报角色决定“我被允许改哪个对象”。对象是读取后被替换，还是更新时重新通过同样的条件选择，应在实现中可见。

### 三种拒绝不能混写成一个结果

Carol 请求红租户报告，属于权限范围拒绝；Bob 持旧版本审批，属于状态冲突；数据库被另一事务占用，属于运行条件失败。这三类都没有完成本次写入，却不能统一报告“访问控制正常”。尤其是最后一种，系统可能还没走到授权判断。新实验分别保留 `PermissionError`、`ConflictError` 与 SQLite 错误，帮助检查报告是否偷换了结论。

只读请求同样需要区分“看不到对象”“可以看摘要”“可以看全字段”。审批权不必然包括读取全部个人字段的权利，字段投影也不自动约束写字段。回到实验 I 的政策表逐项检查，而不是把一个全局 is_admin 开关扩散到所有判断。

重放旧结果时仍需重新确认主体与当前对象范围。幂等键本身不是身份凭据；即使知道另一个请求的键，也不应获得其响应。实验 L 的账本按租户与主体隔离，但它的主体注册表是固定教学夹具，**不包含实时角色撤销、会话认证或动态租户迁移**。这些缺口是迁移到真实系统前需要另行验证的条件，不是模型测试通过就自动解决的功能。

## 附带实验与自检

[[计算机知识/Kali/07-综合实验/04-实验CWeb请求与访问控制|实验 C]] 用纯函数演示 Alice/Bob 对象矩阵，并保留正常与拒绝路径。它验证授权逻辑，不宣称实现了安全登录、JWT 验证或完整 API 服务器。

自检：对象 ID 换成 UUID 后越权是否消失？不一定，难猜只降低某些发现概率，仍需服务端按主体、对象和动作进行授权。
