# 从文件系统到媒体流水线的数据路径

## 本课目标

学完后，你能：

1. 画出文件或网络字节如何成为容器 packet、解码 frame、过滤结果、编码 packet 与最终交付物；
2. 区分路径、VFS、页缓存、用户缓冲、packet、frame、编码器队列和 socket 缓冲；
3. 在每段指出“可能发生复制、缓存、排队或背压”的位置，而不是笼统说零拷贝；
4. 解释为何 `fsync()`、网络 `send()` 和播放器收到首帧不是同一个完成事件；
5. 用队列长度、时间戳与资源上限定位吞吐/延迟问题。

## 1. 一条主线，三种数据形态

```text
path/URL
  → VFS 路径解析 → open/read 或 socket receive
  → bytes（常经页缓存或网络缓冲）
  → demux → coded packets（payload + stream、PTS/DTS、duration、flags）
  → decode → raw frames / PCM samples
  → filter → transformed raw frames / samples
  → encode → coded packets
  → mux → container bytes
  → buffered write → filesystem / fsync
                       或 socket send → network buffers → peer
```

不要跳过箭头：**路径不是文件字节；packet 不是已解码画面；frame 不是一个“视频帧”这个自然语言概念；写入成功不是持久化；发送成功不是对端播放。** FFmpeg 的解复用 API 文档也说明 `av_read_frame()` 返回的是容器中存储的 packet，而不验证其中数据是否对解码器有效；packet 还携带时间戳语义。[FFmpeg Demuxing API](https://ffmpeg.org/doxygen/4.3/group__lavf__decoding.html)（核验：2026-09-03）

## 2. 从 path 到 read：VFS 和页缓存先参与

### 路径不是对象句柄

进程把 `/media/input.mov` 交给 `open` 时，内核的 VFS 按目录项（dentry）、挂载点、权限与 inode 等元数据逐段解析它，最后得到一个打开文件描述符。之后 `read(fd, ...)` 针对的是该已打开对象；同一文本路径在不同 mount namespace、符号链接变化或重命名后可能不再指向同一对象。文件系统、挂载和路径解析的基本模型见 [[计算机知识/20-操作系统/01-Linux/03-目录结构挂载与文件系统|目录结构、挂载与文件系统]]。

### 常见的缓冲读路径

```text
storage device / remote filesystem
       ⇅（块 I/O、DMA，具体实现依设备/驱动而变）
kernel page cache  ← readahead 可能预取后续页
       ⇅（通常复制到调用者用户缓冲）
application byte buffer → demuxer
```

**页缓存（page cache）**缓存文件内容页：命中时不必再次向设备读，未命中时读取可能阻塞或触发异步 I/O。顺序读常有 readahead；随机 seek 或多个并发扫描会改变命中率。页缓存并不代表“数据已永久落盘”，也不是每次 `read` 必经唯一副本：`mmap` 可把文件页映射到进程地址空间并按缺页加载，direct I/O 在满足对齐等条件时可绕过或减少普通页缓存路径，用户态库也会再做缓冲。不要在未测量系统调用、内核、文件系统和硬件的情况下承诺“零拷贝”。

虚拟内存、映射与页故障的前提见 [[计算机知识/30-计算机系统/02-进程虚拟地址空间与内存映射|进程、虚拟地址空间与内存映射]]；缓存为何改变延迟/带宽感知见 [[计算机知识/30-计算机系统/04-缓存局部性带宽与延迟|缓存局部性、带宽与延迟]]。

## 3. demux、packet、decode、frame：四个名字不能互换

| 阶段 | 输入 → 输出 | 它做什么 | 常被误解为 |
| --- | --- | --- | --- |
| demux（解复用） | 容器字节 → stream packet | 解释 MP4/MKV/TS 等索引、轨道和时间戳，分离各轨 coded payload | “把 H.264 解成像素” |
| packet | coded payload + stream index + PTS/DTS/duration/flags | payload 未必压缩；H.264/AAC/Opus 等特例通常是压缩数据 | “一 packet 永远等于一显示帧” |
| decode（解码） | packet → raw video frame / PCM samples | 按 codec 语法把 coded representation 还原为 decoded samples，且可能缓存/重排 | “输出一张立即可显示的 RGB 图” |
| frame | 平面缓冲 + 格式/尺寸/时间信息 | 视频可为 YUV/GBR/HDR 平面，音频是样本缓冲 | “已完成最终交付” |

这里的 **codec** 指 coded/encoded representation 与 decoded samples 之间的语法和处理；它可以有损、无损或不压缩。**packet** 则是一段 coded payload 加 stream/time/flag 元数据，并不自动意味着“压缩包”。H.264、AAC、Opus 等具体格式通常使用压缩表示；PCM 或 rawvideo 一类路径则可是不压缩表示。对 H.264 一类 codec，解码可能包含熵解码、预测重建和重排序；这不是所有 codec 的通用必经步骤。

视频存在 B-frame 重排序：解码顺序（DTS）和展示顺序（PTS）可以不同。音频 packet 的样本数也不必固定。解码器通常有内部延迟；输入结束后仍需 flush 才能取完已排队帧。因而只按“读了多少 packet”计进度会在结尾漏帧，也不能作为端到端延迟。

## 4. filter 与 encode：转换会改变格式、内存位置和时间

过滤器可能做缩放、裁切、颜色空间/transfer 转换、去隔行、叠加、混音、重采样或时间戳修正。每一步都应有明确的输入/输出格式与时间基契约：YUV 与 RGB、有限/全范围、8/10 bit、SDR/HDR、采样率/布局不同，都会诱发重排、重采样、CPU/GPU 上传下载或新缓冲分配。

```text
decoded frame (often decoder-owned/reference-counted)
  → format/scale/color conversion (often new buffer)
  → filter queue / possibly hardware transfer
  → encoder input frame (may be queued for lookahead/B-frames)
  → encoded packet
```

“过滤器不改变分辨率”不等于不复制；“GPU 解码”不等于后续滤镜/编码全在 GPU；“move/reference-counted packet”也不是跨进程、跨设备或跨格式免复制。要定位真实复制，记录每阶段的像素格式、内存域（CPU/GPU）、缓冲所有者、峰值内存与拷贝/传输事件；不要只看 CPU 利用率。

滤镜图与时间基如何形成可验证契约，见 [[计算机知识/60-数据编码与媒体系统/15-FFmpeg滤镜图时间基映射与硬件加速|FFmpeg 滤镜图、时间基、映射与硬件加速]]。若输入不可信，滤镜/字幕和协议本身也是安全边界，见 [[计算机知识/60-数据编码与媒体系统/17-媒体工程安全许可隐私与可复现性|媒体工程安全、许可、隐私与可复现性]]。

## 5. mux、write、fsync 与网络：完成语义逐层变弱

编码器产生的是 coded packet；是否有损、无损或不压缩由具体 codec/模式决定。**muxer** 根据容器规则写入头、轨道、时间戳、索引与交织后的字节。为了正确的 MP4 索引或流式启动，muxer/输出协议可能在结尾回写或延迟头部；因此“已经编码很多帧”不保证产物当前可播放。

| 事件 | 通常意味着 | 仍不保证 |
| --- | --- | --- |
| `write`/库写入返回 | 字节被接受到某层用户/内核缓冲，或部分写入已报告 | 文件数据已到稳定介质、容器已完整 |
| `close`/mux finalize 成功 | 输出端已完成容器收尾（具体协议仍有差异） | 所有设备已掉电安全持久化 |
| `fsync` 成功 | 本地文件系统已请求将该文件数据及必要元数据持久化 | 网络盘/RAID/磁盘固件在断电下的端到端物理保证；远端业务已处理 |
| `send` 返回 | 本地 socket 缓冲接受了部分/全部字节 | 对端已收、已写、已解码或已播放 |
| 对端 ACK/应用回执 | 取决于协议，可能证明传输/应用处理已到某层 | 用户已看到/听到预期内容 |

`fsync` 应在需要崩溃一致性时与同目录原子提交、错误处理和恢复设计一起讨论，不能每写一 packet 就盲调。网络端还要区分 DNS、连接、TLS、拥塞、重传、接收窗口与应用消费；“端口通”不等于媒体数据路径健康。相关排障方法见 [[计算机知识/20-操作系统/01-Linux/10-网络存储日志与故障排查|网络、存储、日志与故障排查]]。

## 6. 缓存、复制、队列与背压：数据为何会“卡住”

本节只把三层已有机制落实到 packet/frame 媒体流水线：队列的 FIFO/双端接口与不变量见 [[计算机知识/50-数据结构与算法/03-栈队列双端队列与单调结构|栈、队列、双端队列与单调结构]]；阻塞等待、条件变量与生产者—消费者协作见 [[计算机知识/30-计算机系统/09-进程线程调度同步与IPC|进程、线程、调度、同步与 IPC]]；socket 发送/接收队列与端到端背压见 [[计算机知识/30-计算机系统/14-网络栈Socket与端到端数据路径|网络栈、Socket 与端到端数据路径]]。本页不重复推导这些通用机制，而是追踪它们在 demux packet、decoded frame、encoder queue 与网络输出之间如何叠加成延迟和内存占用。

| 位置 | 可能的缓存/复制 | 队列涨满时的后果 | 可观察信号 |
| --- | --- | --- | --- |
| VFS/page cache | 文件页、readahead、用户 read buffer | 读线程阻塞或挤压内存 | page fault、cache miss、设备队列/读取吞吐 |
| demux → decode | packet 引用/复制、解码器重排序缓存 | packet 积压、时间戳延迟扩大 | packet queue 长度、DTS/PTS lag |
| decode → filter | raw frame、格式转换/硬件传输缓冲 | 大 frame 占用 RAM/VRAM，延迟递增 | frame queue、像素格式、VRAM/RSS |
| filter → encode | filter 内部帧、encoder lookahead | 上游暂停或开始丢帧（取决于策略） | encode queue、首 packet 时间、drop count |
| mux → write/network | 容器/stdio/socket 缓冲 | `write`/`send` 阻塞、输出不完整、端到端停滞 | 输出队列、partial write、RTT/重传/egress |

**背压（backpressure）**是慢消费者将“请放慢”传回上游的机制。若编码器比解码器慢，正确策略通常是有界队列满后阻塞/节流上游，或根据明确的实时策略丢弃可丢项目并记录。错误策略是让队列无界增长：吞吐看似暂时正常，内存、延迟和故障恢复却会一起失控。

一个有界实时流水线可按如下理解：

```text
read ──Q1──> demux/decode ──Q2──> filter ──Q3──> encode/mux ──Q4──> network
          ↑满则等待/按策略丢弃↑
```

队列容量是延迟预算的一部分。若 Q2 能堆 300 帧，30 fps 下仅这一处就可能容纳约 10 秒的排队时间；这不是“缓存更平滑”，而是需要由产品明确接受或限制的延迟。

## 7. 两种优化目标会给出相反的配置

| 目标 | 通常偏好 | 代价/验证 |
| --- | --- | --- |
| 离线批处理吞吐 | 更深队列、并行、lookahead、顺序 I/O、批量写入 | 首帧慢、内存高；验证总耗时与完整性 |
| 互动/直播低延迟 | 有界小队列、短 GOP/少重排序（按需求）、及时背压 | 压缩效率/画质/吞吐可能下降；验证玻璃到玻璃延迟 |
| 崩溃可恢复输出 | 临时文件、阶段 manifest、原子提交、必要 fsync | 额外 I/O 和实现复杂度；验证中断后旧产物仍可用 |
| 弱网交付 | 自适应码率、播放缓冲、分段重试、可观测回执 | 码率切换/延迟；验证不同网络切片而非平均带宽 |

因此不能只问“CPU 够不够”。一个 GPU encoder 可能空闲，是因为存储读慢、颜色转换把帧拉回 CPU、muxer 等待时间戳、socket 受拥塞限制，或下游消费者没有释放 buffer。硬件加速中的内存域、映射与实际路径见 [[计算机知识/60-数据编码与媒体系统/15-FFmpeg滤镜图时间基映射与硬件加速|FFmpeg 滤镜图、时间基、映射与硬件加速]]。

## 可观察练习：给一次卡顿找证据，而不是猜测

某 30 fps 预览服务“开始很快，10 分钟后越来越卡”，监控只显示平均 CPU 35%。请画出上面的 Q1–Q4，并为每个阶段写：

1. 输入/输出数据形态（字节、packet、frame 或容器字节）；
2. 队列上限和满时策略；
3. 一个时间戳或长度指标；
4. 一个可能的复制/缓存位置；
5. 一个能区分“磁盘慢、解码重排序、颜色转换、编码慢、网络慢、下游不消费”的观测。

然后给出两条不同假设的处置：一条针对网络背压，一条针对无界 frame 队列。不要仅建议“增加内存”。

### 成功标准

- [ ] 我能按顺序说出 path → VFS → page cache/read → demux → packet → decode → frame → filter → encode → packet → mux → write/fsync/network。
- [ ] 我能说明 packet 与 frame、PTS 与 DTS、mux 与 encode 各自的边界。
- [ ] 我至少标出了一个可能的用户态复制、一个页缓存、一个解码/编码内部队列和一个 socket 缓冲。
- [ ] 我能解释为什么 `send`、`fsync`、对端回执与用户播放不是同一个完成点。
- [ ] 我的解决方案先建立有界队列和观测证据，再决定限流、丢弃或扩容。
