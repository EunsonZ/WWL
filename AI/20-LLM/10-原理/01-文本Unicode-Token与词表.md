# 文本、Unicode、Token 与词表

<!-- deep-review-02 -->
> [!tip] 本轮深化：从当前概念继续追问
> token 是模型接口单位，而不是天然一致的语言尺度。不同分词器下每 token 困惑度不能直接排名；音频的帧、对齐路径和声学 token 也需要分别定义。 深化与验证：[[AI/20-LLM/10-原理/07-语言模型目标分词粒度与评测可比性|语言模型目标分词粒度与评测可比性]]；[[AI/40-语音与音频模型/03-CTC路径求和流式延迟与语音评测|CTC路径求和流式延迟与语音评测]]。


## 本课目标

把“屏幕上的文字”拆成四个不同层次：字符、编码后的字节、token 与 token ID。它们经常一一对应，但没有任何普遍保证；混淆它们会导致长度估计、截断、数据清洗和输出解析出错。

## 直觉：模型先看编号，不先看字

人读到 `café`，会把它当成四个字母，其中一个带重音；计算机首先处理编码后的字节；语言模型通常再将字节或字符片段合并成若干 token，并把每个 token 映射成词表中的整数 ID。模型前向计算拿到的是 ID 序列，例如 `[314, 8127]`，不是一个抽象的“法语咖啡概念”。

同一文本可以有不同的合法 tokenizer 切分。英文常见词可能作为一个 token，生僻词、代码、表情、中文片段或空格则可能被切成更多片段。因此“500 个字符”“500 个汉字”和“500 tokens”不是可互换的预算单位。

## 精确定义与边界

- **Unicode 码点**是标准为字符抽象分配的编号；它不等于屏幕上一个可见字形。一个可见符号可能由多个码点组合，字体也会影响外观。
- **编码**把码点序列表示成字节序列。UTF-8 是常用编码，且是变长编码；一个码点不固定占一个字节。
- **tokenizer（分词器）**是把文本转换为 token 序列、再可逆或近似可逆地转换回文本的特定算法和规则集合。它包含规范化、特殊 token 与字节处理等约定。
- **词表（vocabulary）**是 token 字符串/字节片段与 ID 的固定映射。`token ID = 42` 只在同一 tokenizer 与同一版本内有意义。

> [!note] 两个相邻但不可互换的先修
> 要查字节序列、UTF-8 合法性、码点、字素簇和规范化，请读 [[计算机知识/60-数据编码与媒体系统/02-字符编码Unicode-UTF-8与换行|字符编码、Unicode、UTF-8 与换行]]；要理解 KMP、前缀函数、多模式匹配与正则引擎的边界，请读 [[计算机知识/50-数据结构与算法/13-字符串匹配前缀函数与自动机|字符串匹配、前缀函数与自动机]]。tokenizer 可能在这些处理之上定义自己的步骤，但它不是通用 Unicode 解码器或字符串搜索算法。

> [!warning] 不要把 token 当作“词”
> token 可能是词、词的一部分、空白、标点、字节片段或控制标记。把“token 数”当作自然语言的词数，会在多语言和代码场景中系统性失真。

## tokenizer 不只是“按空格切开”

现代 tokenizer 通常还包含一条有顺序的管线：规范化（若有）→ pre-tokenization → 子词/字节模型 → 特殊 token 拼接 → ID 映射。常见模型思路包括：

- **BPE 类方法**从较小符号出发，按训练得到的合并规则反复合并常见相邻片段；
- **Unigram 类方法**从候选片段集合出发，为整段文本寻找概率较高的切分，并在训练中删减词表；
- **byte-level 或 byte fallback**保证陌生 Unicode 输入仍能落到有限字节符号上，但可能让一个可见字符对应多个 token。

它们都是 tokenizer 家族，不是可以只凭模型名字推定的精确配置。规范化形式、合并规则/子词模型、字节映射、特殊 token 与 post-processing 任一不同，都可能改变 ID 序列。

### 一个最小 BPE 思路例

假设初始符号是字符，训练语料中 `l o w` 和 `l o w e r` 很常见。若学到的前两条合并依次是 `l + o → lo`、`lo + w → low`，那么 `low` 可变成一个片段，而 `lower` 可能切成 `low + e + r`。若交换合并规则、限制词表或换语料，切分可能不同。

这个例子只解释“规则按顺序把片段合并”的直觉，不是任何真实 tokenizer 的完整训练算法。BPE/Unigram 的目标函数、词表训练语料和实现版本必须随具体 tokenizer 固定。

### 一个可观察的例子

假设某 tokenizer 的词表恰好包含 `"hello"`、`" "`、`"世"`、`"界"`，它可以把 `hello 世界` 切为四项：

```text
文本：hello 世界
token：["hello", " ", "世", "界"]
ID：  [  91,     3,   711,  712]
```

这不是任何真实模型的通用 ID 表，只展示层次：ID 是词表内索引；换 tokenizer 后，切分和数字都可能不同。一个真实 tokenizer 的特殊 token（如序列开始、结束、填充或聊天角色标记）还会影响实际长度与训练边界。

## 实务：何时必须固定 tokenizer

以下对象必须成组保存与核对：模型权重、tokenizer 文件、特殊 token 配置、聊天模板及它们各自的版本/修订号。只替换其中一个，可能造成 ID 含义错位，即使程序没有报错。实际训练数据怎样经过 tokenization 并进入预训练，见 [[AI/20-LLM/30-训练/01-数据Tokenization与预训练流程|数据、Tokenization 与预训练流程]]。

数据清洗也需要谨慎：Unicode 规范化、删除“看不见的字符”、改行尾或自动纠错都可能改变 token 序列。对安全规则、代码、密码、标识符和引文，先定义允许的变换并保留原文与可复现记录；不要仅凭肉眼判断两段字符串相同。

## 练习

1. 解释为何“模型上下文为 8,000 tokens”不能保证容纳 8,000 个中文字符或 8,000 个英文单词。
2. 某数据集把 `\r\n` 统一成 `\n`。列出它可能改变的两件事，以及为什么要在训练与评测中保持一致。
3. 有人给出 ID 序列 `[17, 93]`，却没有提供 tokenizer。说明你还能知道什么、不能知道什么。
4. 同一模型权重换用另一个“词表大小恰好相同”的 tokenizer，程序仍能前向。解释为什么输出语义仍可能完全错位。

<details>
<summary>核对要点</summary>

1. token 是 tokenizer 的可变长度切分，字符/单词/token 没有固定比例。
2. 文本字节与 token 化结果都可能改变；同一规则须用于可比的数据流程。
3. 只知道有两个词表索引，无法恢复其文字含义或模型输入语义。
4. 词表大小相同只保证索引范围可能合法，不保证每个 ID 指向同一片段、特殊 token 或聊天边界。

</details>

## 成功标准

你能为任意输入依次说出“字符/码点—编码字节—token—ID”的角色；能说明 BPE/Unigram/字节回退解决的是怎样把开放文本映到有限词表；在比较长度或载入模型时，主动追问规范化、模型文件、特殊 token、聊天模板和版本，而不把 ID 或 token 数当成跨模型通用事实。
