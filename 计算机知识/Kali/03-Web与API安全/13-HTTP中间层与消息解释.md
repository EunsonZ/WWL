# HTTP中间层与消息解释

本页解释同一次业务操作为什么在浏览器、代理、缓存和源站留下不同表示。它是协议与工具之间的桥梁，不提供请求走私载荷、缓存投毒步骤或真实站点探测流程。

## 从字节流到业务对象：每一层回答不同问题

把一条教学请求抽象成六次转换：网络包被重组为传输数据；HTTP 实现划定消息边界；首部和目标被解析；代理选择上游与协议；应用把路径和字段映射成对象；授权模块决定该身份能否执行动作。**前一层接受输入，不意味着后一层也接受；后一层返回错误，也不能倒推前一层没有收到。** HTTP/1.1 的消息长度规则解决的是“当前消息在哪里结束”，不是“这个用户能否读取账单”。[^v5-http11]

这可以写成原创的教学模型：$b\xrightarrow{P}m\xrightarrow{R}r\xrightarrow{A}s$。$b$ 是字节表示，$P$ 是协议解析，$m$ 是消息，$R$ 是资源解析，$r$ 是资源，$A$ 是带身份和状态的应用处理，$s$ 是结果。几个工具分别观察不同箭头。抓包不直接显示业务对象，HTTP 历史不自动包含源站内部调用，应用日志也未必保存原始字节。

当两个组件 $P_1$、$P_2$ 处理同一表示时，安全条件不是“都大概看懂了”，而是所有被允许继续传递的输入都具有兼容解释。不确定或冲突的长度、非法字段和无法安全转换的消息应按协议与实现合同处理，不能靠选择一个“看起来合理”的解释修补。这是理解解析差异的原理；本页不构造歧义消息。

## HTTP版本改变的是表示与复用方式，不是对象授权责任

| 层次 | 需要掌握的结构 | 工具画面中最容易误认的东西 |
| --- | --- | --- |
| HTTP/1.1 | 起始行、首部、消息体及长度规则；一条持久连接可承载多次交互 | 一个 TCP 分段不是一条完整 HTTP 请求 |
| HTTP/2 | 二进制帧、流标识、伪首部、首部压缩与流量控制 | 编辑器中的类 HTTP/1 文本可能只是工具重建的表示，不是线上字节 |
| HTTP/3 | 在 QUIC 上承载 HTTP，使用流和 QPACK；传输层不再是 TCP | 没有 TCP 流不能推出没有 HTTP；也不能将 HTTP/2 的重组方法原样套用 |

HTTP/2 和 HTTP/3 的多路复用减少某些交互间的阻塞，但“多流”不等于消除所有等待：连接级资源、应用处理、拥塞控制以及首部压缩依赖仍可带来等待。判断哪里阻塞，要区分传输数据缺失、解码依赖和应用尚未响应。[^v5-http2][^v5-http3]

一个代理可以对外讲 HTTP/2、对内讲 HTTP/1.1。此时应分别记录两跳协议、端点和消息表示，不能只写“系统使用 HTTP/2”。回到 [[计算机知识/Kali/02-信息收集与网络测量/05-WiresharkTcpdump与Tshark|抓包重组与显示]]，先确认自己观察的是哪一跳。

## 四个看起来像主机名的字段并不承担同一职责

DNS 名称参与地址解析；TLS 的 SNI 帮助服务端在握手时选择服务配置；证书中的服务标识用于验证所连接服务的身份；HTTP 的 Host 或 `:authority` 参与请求目标表达。ALPN 则协商应用协议，不是主机身份。HTTP/2 对 `:authority` 与 Host 的处理有明确约束，不能把两者当作可以随意冲突的独立标签。[^v5-http2][^v5-tls-name]

原创诊断例：客户端连接到某 IP，证书名字正确，但返回的是另一个应用的 404 页面。至少存在三种待区分解释：HTTP 目标字段不符合预期；代理路由正确但路径不存在；上游配置选错。证书正确只支持其中的 TLS 身份条件，不能排除后两类应用问题。比较证据时，应记录连接地址、TLS 身份、HTTP 目标和最终上游，而不是把“域名”写成一个无层次字段。

## 规范化不是把字符串越改越短

规范化试图给同一语义对象选择一致表示，但必须先知道“同一对象”的定义。URI 中保留字符可能充当分隔符；把其百分号编码形式无条件解码，可能改变结构。不能将“百分号解码”“大小写转换”“合并斜线”“查询参数排序”当作处处安全的通用清洗顺序。[^v5-uri]

用符号说明失配：授权层检查 $N_a(x)$，路由层访问 $N_r(x)$。目标是两者指向同一受保护对象，而不是要求两个字符串一定逐字相同。两个不同名称可以合法指向同一对象；相同文本在不同租户或工作目录下也可能指向不同对象。因此授权通常应落实在最终解析出来的资源及其上下文上。这个解释模型与 [[计算机知识/Kali/03-Web与API安全/09-SSRF路径上传与解析边界|文件路径、URL和检查使用时序]] 相通。

## 缓存键是对请求划分等价类

缓存把若干请求映射到同一键 $K(q)$。只有这些请求可以安全共享响应时，这种合并才正确。HTTP 缓存标准规定了存储、复用与 Vary 等条件；应用还要保证自己的身份相关表示没有被错误合并。缓存命中并不等于源站重新执行了一次权限判断。[^v5-http-cache]

原创的错误设计示例：租户 A 与 B 都访问“报告 17”，但其对象分别是 $(A,17)$ 与 $(B,17)$。若应用响应随租户变化，而共享层仅以路径形成键，两次请求可能被错误归为一类。问题不是“17 不够随机”，而是键遗漏了影响响应合法性的上下文。反过来，把完整凭据原文直接加入日志或可见缓存键也会产生泄露风险；正确设计依赖经审查的分区、缓存政策和授权机制，不是本例的一行替换建议。

判断响应属于谁，要同时看请求身份、缓存命中信息、响应对象与源站证据。先建立不共享缓存的可信对照，再讨论差异；一次清缓存后现象消失只提供线索，尚不能单独证明根因。

## 三个贯穿自检

代理历史显示 200、源站日志没有对应请求时，先列出缓存命中、日志覆盖缺失和请求关联错误三种解释，再写各需什么证据。HTTP/2 编辑器显示多行文字时，指出哪些是工具表示、哪些才可能对应协议字段。两个 URL 文本不同但最终对象相同，解释为什么访问控制不能只按原始字符串作结论。答案线索分别在本页缓存模型、版本表示和规范化三节，不需要构造攻击流量。
