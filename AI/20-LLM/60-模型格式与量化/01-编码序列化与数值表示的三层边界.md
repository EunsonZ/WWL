# 编码、序列化与数值表示的三层边界

<!-- deep-review-02 -->
> [!tip] 本轮深化：从当前概念继续追问
> token 编码、文件布局和低精度数值不属于同一层。格式能读不保证 tokenizer/模板匹配，也不保证量化后行为与原模型接近。 深化与验证：[[AI/20-LLM/60-模型格式与量化/08-量化误差传播校准目标与端到端评测|量化误差传播校准目标与端到端评测]]；[[AI/20-LLM/10-原理/07-语言模型目标分词粒度与评测可比性|语言模型目标分词粒度与评测可比性]]。


## 本课目标

- 把文本编码/tokenization、权重序列化/容器、数值精度/量化编码分成三层；
- 区分 PyTorch checkpoint、`state_dict` 与 safetensors 的逻辑/文件边界；
- 说清 `config`、tokenizer 和 weights 缺一时会破坏什么；
- 用一张清单快速识别“格式转换”是否意外改变了模型语义。

## 1. 第一层：文本到 token ID

一条文本输入可以经历下列步骤：

```text
字符序列 → Unicode 码点 → 字节编码与可选正规化
         → tokenizer 规则、词表和特殊 token → token ID 序列
```

- **UTF-8**规定字符如何映射到字节，不规定模型词表。
- **tokenizer**决定字符/字节片段怎样变成 token，及每个 token 的整数 ID。
- **chat template**把角色和消息包装成实际送给 tokenizer 的字符串，它会改变 token 序列。

因此，两个文件即使保存了完全相同的权重字节，如果 tokenizer 或特殊 token ID 不一致，模型看到的就不是同一串数。这是文本表示问题，不是 Q4/Q8 量化问题。详见 [[AI/20-LLM/10-原理/01-文本Unicode-Token与词表|文本、Unicode、token 与词表]]。

## 2. 第二层：从内存对象到磁盘容器

### 先加一个正交维度：模型契约

“三层”是为了分类错误，不是说一个模型只需三个文件。架构、张量身份与 tokenizer 还构成一份跨层契约：

| 对象 | 它是什么 | 它不是什么 |
| --- | --- | --- |
| `state_dict` | 张量名到 parameter/已注册 buffer 张量的逻辑映射 | 自足的模型架构，或一种唯一的磁盘格式 |
| `config`/模型类 | 说明层数、维度、attention/RoPE/MoE 等如何解释张量 | 权重字节本身 |
| checkpoint 容器 | 把 model/optimizer state、step、RNG 等按某个序列化契约保存 | 仅凭 `.pt`/`.pth` 后缀就能判定的内容 |
| tokenizer/chat template | 决定用户文本最终成为什么 token IDs | 权重量化参数 |

### `state_dict` 是逻辑映射，不是单一文件格式

在 PyTorch 中，模型 `state_dict` 通常是“名称 → 张量”的映射，例如 `model.layers.0.self_attn.q_proj.weight → Tensor`。它描述**需要恢复的状态**，却不单独定义：

- 张量在磁盘上用 pickle/ZIP checkpoint、safetensors 还是别的容器；
- 创建模型所需的 Python 类、架构和超参数；
- tokenizer、词表、聊天模板和生成配置。

`torch.save(...)` 生成的常见 checkpoint 使用 PyTorch 序列化机制，可以保存不只是张量的 Python 对象。训练 checkpoint 还可包含 optimizer state、scheduler、step、随机数状态与 loss-scaler；这些对继续训练很重要，对纯推理却可能是额外负担。当前 PyTorch 文档还区分 `torch.load(..., weights_only=True)` 的受限反序列化与 `Module.load_state_dict(...)` 的参数装载：后者接收的是已经解析出的映射，不是文件路径。

> [!danger] 不可信 checkpoint
> 传统 pickle 加载可在反序列化时触发代码路径。PyTorch 从 2.6 起在未显式传 `pickle_module` 时默认 `weights_only=True`，但这是版本化的受限 unpickler，不会把 checkpoint 变成 safetensors，也不消除 DoS、资源耗尽和库实现漏洞。对不可信 checkpoint，不要以“只想看一眼键名”为由在宿主环境直接加载。

### safetensors 与 GGUF 改变的是容器契约

- **safetensors**存储有类型、shape 和位置的张量以及受限元数据，不携带可任意执行的 pickle 对象图。
- **GGUF**为 ggml/`llama.cpp` 类运行时组织架构元数据、tokenizer 信息、张量目录与对齐的张量数据，并允许每个张量使用不同 ggml 数值类型。

容器可指明“张量在哪里、是什么 shape”，却不会自动证明这些张量对应正确的架构、没有后门或有合法来源。

## 3. 第三层：每个值怎样近似

数值表示层决定一个张量内的值用什么位模式和辅助参数保存：

- FP32、FP16、BF16 和具体 FP8 变体是浮点格式；
- INT8 可表示原生整数，也可代表“整数编码 + scale/可选 zero-point”的量化值；
- NF4、GPTQ、AWQ、`Q4_0`、K-quants 和 IQ 各有不同的分组、尺度、校准、代码表或误差优化规则。

“4 bit”仅说明了部分数据的位宽。真实比特/权重还包含分组 scale、zero-point/min、代码表、高精度保留张量、对齐和容器开销。完整数学定义见 [[数学/60-数值计算与量化/01-二进制浮点精度与数值稳定性|二进制浮点精度与数值稳定性]]与 [[数学/60-数值计算与量化/02-量化Scale-Zero-Point-Group与误差|量化 Scale、Zero-Point、Group 与误差]]。

## 4. `config`、tokenizer 和 weights 是三组必须相互对得上的事实

| 部件 | 典型内容 | 不一致时的常见结果 |
| --- | --- | --- |
| 架构/config | 层数、hidden size、attention heads/GQA、RoPE、词表大小、模型类型 | shape 不匹配、线性层被错读、上下文或 RoPE 错误 |
| tokenizer | 词表、merges/model、normalizer、special token ID、added tokens、chat template | 相同文本变成不同 ID，停止标记失效，聊天格式改变 |
| weights | 按张量名和 shape 排列的参数，可能分片、转置或量化 | 加载报错，或更危险地“能加载但语义错” |

GGUF 转换器需把上游的这三组事实映射到目标运行时认识的元数据键、tokenizer 字段和张量命名/布局。这是**架构感知的转换**，不是把 `.safetensors` 后缀改成 `.gguf`。

## 5. 一个可观察的分层例子

假设输入是“猫”，某 tokenizer 输出 token ID `[4312]`：

| 观察 | 属于哪层 | 改变后可能发生什么 |
| --- | --- | --- |
| UTF-8 字节是 `E7 8C AB` | 文本字节编码 | 换为错误字节会让 tokenizer 看到其他文本 |
| token ID 是 4312 | tokenizer/词表 | 换词表后 4312 可能对应另一个 token |
| embedding 张量位于 safetensors 的某个字节区间 | 序列化/容器 | 换容器可保持值不变，但须验证 shape、名称与字节 |
| embedding 分量由 BF16 近似为 Q4 block | 数值表示/量化 | token ID 不变，但向量的近似误差会传向后续层 |

这个例子也解释了为何么“量化后中文乱码”不能直接归因于 4-bit：先检查 tokenizer、chat template、special token 与字节处理，再通过配对评测判断数值误差。

### 把“文本一样”变成可复核记录

Unicode 文字 `é` 可以是单个码点 `U+00E9`，也可以是 `U+0065 U+0301`。它们视觉接近，UTF-8 字节却不同；某 tokenizer 是否先正规化，会决定 token IDs 是否相同。转换验收不应只保存屏幕上的字符串，而应保存如下结构：

```yaml
case_id: unicode-composed-vs-decomposed
raw_utf8_hex: <原始字节的十六进制>
normalization_declared: <none/NFC/NFKC/其他>
tokenizer_revision: <immutable revision>
chat_template_sha256: <hash>
rendered_utf8_hex: <模板渲染后字节>
token_ids: [<ids>]
```

这是文本/tokenizer 层的证据。量化前后对同一输入应先对比这些字段；若 token IDs 已不同，后续 logits 差异不能只归因于权重量化。

## 6. 快速诊断表

| 现象 | 首先检查 | 不要立即下结论 |
| --- | --- | --- |
| 输入 token 数与基线不同 | tokenizer revision、normalization、chat template、special tokens | “权重转换坏了” |
| 加载时 shape 不匹配 | config 架构、分片索引、张量名/转置映射 | “量化精度太低” |
| 能加载但输出异常 | 先对比 token IDs 和高精度 GGUF，再对比量化候选 | “文件后缀正确，所以模型正确” |
| 文件变小但 RAM 不按比例下降 | KV cache、compute buffer、mmap/page cache、工作线程和后端 offload | “一定是虚假量化” |

## 练习：审核一份虚拟模型清单

某目录只有：

```text
model-00001-of-00002.safetensors
model-00002-of-00002.safetensors
config.json
```

1. 写出不应盲目开始转换的至少四个理由。
2. 列出你会索取的信息：完整分片索引、tokenizer/聊天模板、模型卡与许可证、仓库 revision、每个文件的哈希。
3. 说明这些信息分别保护文本层、容器层、数值层还是法务/来源边界。

### 成功标准

- [ ] 我没有把 `state_dict` 与 `torch.save` 生成的某一种 checkpoint 文件等同。
- [ ] 我能画出“文本 → token ID → 架构与权重”的边界。
- [ ] 我能说明一个 GGUF 同时有容器结构和张量数值类型，两者不是同一概念。
- [ ] 我会在转换前固定 config、tokenizer、weights、模型卡和许可证的同一个 revision。

## 许可证、安全与恢复

- 不可信 PyTorch checkpoint 不在宿主环境直接反序列化；safetensors/GGUF 也先做长度、偏移、大小与哈希检查。
- 文件哈希只能证明当前字节与已知摘要一致；摘要必须来自可信的发布者/固定 revision。
- 转换不会重新授权权重；转换脚本许可与模型权重条款分别核对。
- 保留只读的上游清单、哈希和高精度基线；删除派生量化文件即可恢复，不覆盖原始分片。
