# 动态内存的核心不是 malloc，而是状态转移和失败恢复

> **学习位置**：[[计算机知识/00-开始/课程地图/01-C语言-课程地图|C语言课程地图]] · **适用边界**：ISO C17；C23 与 POSIX 扩展另行标识。

## 用不变量描述一个可增长数组

一个动态数组可以表示为 `data`、`length`、`capacity`。合理的不变量是：`length<=capacity`；可访问存储覆盖 `capacity` 个元素；前 `length` 个元素已经初始化；只有拥有者负责释放。零容量如何表示也要统一，例如 `data==NULL`、`length==capacity==0`。

这个模型把操作分成三段：先检查前提，再准备新资源，最后提交状态。失败时维持旧状态不变叫作失败原子性；它不是 CPU 的原子指令，而是接口保证。

## `realloc` 的两条结果路径

```c
int *next = realloc(v->data, bytes);
if (next == NULL) return false;
v->data = next;
v->capacity = new_capacity;
```

这里假定 `bytes>0`，且乘法已经检查。失败时旧分配仍由 `v->data` 持有；成功时必须使用返回的新指针，原分配相关的旧指针不再可作为有效对象引用继续使用，即使打印出来的地址值看起来未变。

`v->data=realloc(v->data,bytes)` 会在失败时覆盖唯一的旧指针，导致泄漏。更隐蔽的是数组内部指针缓存：调用者保存了 `&v->data[3]`，扩容后它可能失效。接口需要明确哪些操作使视图和迭代器失效。

## 增长策略为什么通常采用倍增

每次只加一个容量，会在插入第 $i$ 个元素时搬运近似 $i$ 个元素，总搬运量是二次级别。容量按 1、2、4、8 增长时，直到 $n$ 个元素的搬运量小于 $2n$，所以每次追加的**均摊**搬运成本是常数。

这并不意味着每次追加的最坏延迟是常数。实时场景可能需要预分配、分段存储或增量迁移。增长因子也影响内存峰值：旧块和新块在迁移阶段可能同时存在，不能只按最终容量估算峰值。

计算新容量时，要同时检查倍增是否溢出、最低所需容量是否可表示、`capacity*sizeof element` 是否溢出。不要用一个最后的 `malloc` 失败检查代替前面的整数安全。

## 谁拥有，谁借用，谁转移

最常见的三种接口应在名字或注释中显式约定：`create` 返回所有权；`view` 返回借用；`take` 或 `adopt` 接收所有权。C 类型系统通常不会替你证明这些规则，所以文档、测试和封装尤其重要。

若一个结构体拥有堆指针，直接 `b=a` 是浅复制。之后两个对象都释放该指针会双重释放。可选择禁止复制、提供深复制函数，或实现引用计数；但引用计数仍需解决循环引用和线程同步。

销毁函数宜接受合法空状态，并在释放后把对象恢复为空状态。例如释放 `data` 后将三个字段清零。这样方便同一所有者重复清理，但不会让别处的悬空别名自动变安全，也不能借此声称整个程序的 double-free 被根除。

## 多资源获取：集中清理不是落后风格

C 中用 `goto cleanup` 组织错误路径，可以避免每个失败分支复制一套释放逻辑：

```c
int status = -1;
FILE *in = NULL;
char *buffer = NULL;
/* 获取资源，每一步失败都跳到 cleanup。 */
/* 工作成功后令 status = 0。 */
cleanup:
free(buffer);
if (in != NULL) {
    if (fclose(in) != 0 && status == 0) status = -1;
}
return status;
```

这是结构示意，完整函数还需包含头文件、真实获取步骤和错误报告。释放顺序通常与获取顺序相反，因为后获取的资源可能依赖先获取的资源。关闭输出文件时的错误不能随意丢弃：缓存中的写入可能到关闭时才失败。

## 测试不应只跑成功路径

通过把分配器作为函数指针注入，可指定“第 k 次分配失败”，观察对象是否仍满足不变量、是否泄漏、原数据是否不变。系统化测试每个分配点，比等真实内存耗尽更可重复。

AddressSanitizer 可发现部分越界和释放后使用，UndefinedBehaviorSanitizer 可发现部分运行时未定义行为；它们不证明所有输入安全，也可能改变内存布局和时序。静态分析、模糊测试和故障注入各覆盖不同盲区。

## 练习与答案

若 `push` 扩容成功、写入新元素前又发生一次可能失败的深复制，该怎样保证失败原子性？一种方案是先构造新元素和新存储，全部成功才提交；另一种是扩容允许改变容量，但失败时保证长度和旧元素不变，并明确这属于怎样的异常/错误保证。重要的是接口承诺必须和实际状态变化一致。

若元素只是整数，`memcpy` 搬运通常足够；若元素拥有资源，仅复制字节可能复制所有权，必须定义元素的复制、移动和销毁协议。这直接连接 C++ 的构造/析构，也连接 Rust 的 `Drop` 与 move。
