# 从字节到对象：对齐、别名、字节序与可靠解析

## 看见四个字节，不代表那里有一个整数对象

设网络收到字节 `01 02 03 04`，协议规定它们是大端的 32 位无符号整数，预期值为 `0x01020304`，即 16909060。直接写 `*(uint32_t *)buf` 至少省略了四个问题：地址是否对齐；是否存在允许该类型访问的对象；长度是否足够；主机字节序是否与协议相同。

“我的机器打印正确”只证明这次运行的表象符合预期，不能补齐这些前提。尤其在编译优化、换架构或接收缓冲区带有一个字节头部时，隐藏问题才可能暴露。C 的有效类型规则及字符类型访问例外来自语言对象模型，不来自网卡或页表。[^c-object]

## 先构造值，再考虑优化

下面的函数把输入当字节序列，成功前不改变输出。教学基线明确要求八位字节，并且实现提供精确宽度类型 `uint32_t`。

```c
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <limits.h>

_Static_assert(CHAR_BIT == 8, "This protocol requires 8-bit bytes");

bool read_be32(const unsigned char *data, size_t size,
               size_t offset, uint32_t *out) {
    if (data == NULL || out == NULL) return false;
    if (offset > size || size - offset < 4) return false;
    uint32_t value = ((uint32_t)data[offset] << 24)
                   | ((uint32_t)data[offset + 1] << 16)
                   | ((uint32_t)data[offset + 2] << 8)
                   |  (uint32_t)data[offset + 3];
    *out = value;
    return true;
}
```

长度检查写成 `size - offset < 4`，并先确保 `offset <= size`，避免 `offset + 4` 发生无符号回绕。移位前把字节转换为 `uint32_t`，不让常见的整数提升先把它变成有符号 `int` 再左移到不可表示的结果。函数仍要求 `data` 实际指向至少 `size` 个可读字节，`out` 指向有效可写对象；C 函数不能从数字 `size` 自动证明实际分配容量。

逐步还原这个值：最高字节贡献 $1\times2^{24}$，其后是 $2\times2^{16}$、$3\times2^8$ 和 4，求和得到 16909060。无论主机如何排列自身整数对象的字节，计算结果都由协议定义。

把本页合同用于 [[计算机知识/10-编程语言/03-C语言/10-系统课程/12-测量流工具的完整工程#一个有限对象，两个输入适配器|测量流工程的二进制适配器]]：12 字节 `00 00 00 04 00 02 00 04 00 06 00 08` 先给出大端样本数 4，再给出四个大端 16 位码 `[2,4,6,8]`。前提仍是八位字节、实现具备所用精确宽度类型以及真实可读范围；若这 12 字节从缓冲区的奇地址开始，逐个 `unsigned char` 读取并构造值仍不要求该地址满足 `uint16_t` 对齐，也不借此创造一个 `uint16_t` 对象。返回工程时分别预测：累计前缀不足且尚无 EOF 是 `need_more`，EOF 后仍不足是 `truncated`；完整前缀也须等待 EOF，之后若出现尾随字节是 `invalid`，因为工具只接受一条记录。这里接口接收当前累计前缀，不自行记忆上次分片；`size=12` 只声明长度，不能证明调用者实际拥有 12 个可读字节。字节解析消除了强转读取的对齐与类型前提，没有取消存储有效性、码值范围或资源上限。

## memcpy 解决了什么，没有解决什么

若 `uint32_t value; memcpy(&value, data, sizeof value);` 的源范围和目标均合法且不重叠，复制本身无需源地址满足 `uint32_t` 对齐，因为它按对象表示复制。对于无填充的 `uint32_t`，所有位模式均表示相应无符号值；但得到的**数值**仍依赖主机字节序。`memcpy` 不自动做网络序转换。[^c-copy]

复制任意字节进 `float`、指针或其他类型，不应据此宣称目标一定具有可用值。目标表示、陷阱表示、实现格式和后续访问条件仍要检查。复制结构体也不能用 `memcmp` 代替成员语义相等：填充字节不代表业务数据，同样的成员值可能有不同对象表示。

反过来，使用字符类型观察合法对象的表示是一种受到支持的途径。这是“用字节查看对象”，不是“用任意类型解释任意字节”的双向许可证。`unsigned char` 明确表达原始字节意图，比依赖实现中 `uint8_t` 恰好是不是字符类型更直观。

## 重叠与 restrict 必须用访问轨迹判断

把 `abcdef` 的前五个字节向右移动一位，希望得到 `aabcde`。源和目标范围重叠，应使用 `memmove`；`memcpy` 在重叠下没有所需保证。即使某版库恰好向后复制，也不能把实现偶然行为写进可移植程序的合同。

对于数组计算，`restrict` 的问题不是两根指针的数值是否相同，而是本次执行中相关对象如何被读写。若两个受限输入只读同一对象，未发生需要排他关联的修改，就不能粗暴套用“地址相同必错”；若一个输出修改了该对象，却又经不允许的独立输入路径读取，则可能违约。用保守的“不重叠输入输出”API 合同可以降低审计难度，但应承认它比语言最低要求更严格。[^c-restrict]

## 解析器还需要状态与资源上限

读出长度字段后，先检查协议上限，再决定是否分配，不能只检查“长度 fits in size_t”。一个合法的十亿字节长度仍可能耗尽内存。解析应区分“当前数据不够，等待下一批”“格式永远无效”“声明长度超过政策限制”，否则网络分帧会把截断和恶意超大输入混成同一种错误。

例如约定消息是四字节长度加正文，长度不含头部，最大正文 1 MiB。收到 `00 00 00 05 68 65` 后应保留状态“长度 5，已有正文 2 字节”，而不是报文法错误或把第二次 `recv` 当成另一条消息。连接关闭时仍只收到两个正文字符，才确定为截断。此状态机连接到 [[计算机知识/20-操作系统/01-Linux/10-系统课程/09-FD共享epoll与非阻塞状态机|非阻塞 I/O]] 与 [[计算机知识/35-计算机网络/10-系统课程/10-TCP窗口RTO与拥塞控制手算|可靠字节流]]。

失败原子性也要明确：`read_be32` 失败时不写 `out`；较大的解析函数应先构造临时结果，全部验证后再提交，或者明确返回已消费字节数及部分结果。既悄悄推进游标又返回普通“失败”，会让重试从错误位置开始。

## 从代码层推导到优化层

别名限制为优化器提供“这个写操作不会影响那个读取”的依据。去掉一个加载、重排独立操作或向量化循环，需要成立的是所有合法执行上的语义保持，而不是某个机器码版本输出正确。[[计算机知识/70-编译原理/10-系统课程/10-活跃性不动点与抽象解释|抽象解释与优化]] 会进一步说明：分析结果必须是安全近似，遗漏实际别名比保守地多报别名危险。

数值解释同样跨层。把四字节当 binary32 浮点时，要按协议明确 IEEE 格式及特殊值政策；解析成功只意味着结构有效，不代表 NaN、无穷、负零在业务中都能接受。见 [[计算机知识/30-计算机系统/10-组成原理系统课程/09-浮点舍入消去与数值稳定性|浮点表示与数值合同]]。

## 验证题

将输入放在数组的第二个字节开始，保证它相对某些类型不对齐，再验证字节解析仍给出正确值；测试长度 0、3、4，偏移大于长度，以及 `offset` 接近 `SIZE_MAX`。失败时预先设置的输出值应保持不变。

答案不能只写“加一个强转”：强转不检查长度、不调整字节序，也不替调用者创造对象。实际回归只执行合法实现，不把运行未定义行为当作可靠的正反实验。
