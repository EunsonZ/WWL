# 13 · 字符串匹配、前缀函数与自动机

## 本课目标

学完后，你能先说明“匹配单位”是什么，再为单模式或多模式检索选择朴素扫描、KMP、Rabin–Karp、Trie 或有限自动机；能手工计算前缀函数，并能说清哈希碰撞、Unicode 边界与正则引擎的适用范围。

> [!tip] 首读核心闭环与按需选读
> **首读核心闭环**是：先写清匹配单位与相等规则（开头）→ 用朴素扫描建立正确性基线（第 1 节）→ 手算前缀函数并用 KMP 的回退不变量解释“不漏匹配”（第 2 节）。能完成一次含重叠匹配的追踪即可。
>
> **按需选读**：需要批量候选过滤时读 Rabin–Karp（第 3 节）；需要大量词条的前缀查找或多模式流式检测时读 Trie/自动机（第 4 节）；需要字符类、捕获或断言时再读正则引擎边界（第 5 节）。这些工具不能替代先定义匹配单位。

## 先问：这里的“字符”究竟是哪一层？

字符串匹配比较的是一串**单位**。单位选错，算法即使正确也可能回答错问题。常见层次如下：

| 层次 | 一个单位是什么 | `é` 与 `é` 的关系 | 适合的问题 |
| --- | --- | --- | --- |
| 字节（byte） | 编码后的 8-bit 值 | UTF-8 字节序列通常不同 | 协议、二进制格式、固定字节标记 |
| Unicode 码点（code point） | 如 `U+00E9` | 前者 1 个码点，后者常为 2 个 | 已解码文本的语言 API |
| 字素簇（grapheme cluster） | 用户通常看作一个字符的组合 | 两者各可显示为 1 个字素 | 编辑器光标、用户可见长度 |
| token | 某个 tokenizer 的片段和词表规则 | 没有固定关系 | LLM 上下文、模型输入 |

编码不是字符串算法的前置细节。UTF-8 下，按字节找一个 ASCII 分隔符通常没有问题；但任意截断或“第 `i` 个字符”的需求，必须先固定编码、解码错误策略和单位。码点序列相同也不必意味着屏幕字形相同；字素簇的切分应使用目标平台的 Unicode 分段实现，而不是假设“一个码点就是一个用户可见字符”。正则里的 `.`、`\\w` 和边界的单位还取决于具体引擎与标志，详见 [[编程知识/10-基础/01-正则表达式/07-Unicode与引擎差异|Unicode 与引擎差异]]。

LLM 的 token 更是另一层：tokenizer 可以把一个字素拆成多个 token，也可以把多个字符合成一个 token；它不能代替子串匹配的定义。见 [[AI/20-LLM/10-原理/01-文本Unicode-Token与词表|文本、Unicode、token 与词表]]。

> [!warning] 先定义相等，再谈搜索
> 若业务要把预组合 `é` 和 `e` 加组合重音视为相等，必须在**保留原文**的前提下，对两侧应用同一份、已测试的规范化规则；KMP、哈希和 Trie 都不会自动替你完成它。密码、标识符、签名数据和原始证据尤其不应擅自规范化。

## 1. 朴素匹配：最直接，也常是最佳基线

给定文本 `T`（长度 `n`）与模式 `P`（长度 `m`），朴素算法依次把 `P` 对齐到 `T` 的每个可能起点；遇到第一个不等的单位就停止这次比较。

本课统一把“匹配”定义为返回所有起始边界：空模式 `m=0` 匹配文本的全部 `n+1` 个边界（含开头和结尾）；`m>n` 返回空结果。这是 API 契约，不是 KMP、哈希或 Trie 自动替你决定的语义。

```text
朴素匹配(T, P):
    若 m = 0：返回 0, 1, ..., n
    若 m > n：返回空结果
    对 start 从 0 到 n - m：
        j ← 0
        当 j < m 且 T[start + j] = P[j]：
            j ← j + 1
        若 j = m：报告 start
```

例：在 `T = A B A B A C` 中找 `P = A B A C`。起点 0 会比较前三项后在 `B ≠ C` 失败；起点 1 第一项就失败；起点 2 完整成功。因此答案是 2。它不会漏解，因为枚举了每一个合法起点；它也不会误报，因为只有全部 `m` 项相等才报告。

最坏情况下要做 `O(nm)` 次单位比较，例如文本和模式都含有很长的相同前缀：`T = AAAAA...AB`、`P = AAAA...AB`。但当模式短、文本很小、调用次数少或实现的常数成本更重要时，朴素扫描通常最清晰可靠。不要只因出现“字符串”就上复杂预处理。

## 2. KMP：把已知的失败信息变成下一次起点

KMP 的关键不是神秘地“跳过字符”，而是对模式的每个位置预先回答：`P[0..i]` 的最长**真前缀**且同时是后缀有多长？记为 `π[i]`。真前缀不能等于整个串。

对 `P = A B A B A C A`：

| `i` | `P[0..i]` | 最长真前缀 = 后缀 | `π[i]` |
| ---: | --- | --- | ---: |
| 0 | `A` | 无 | 0 |
| 1 | `AB` | 无 | 0 |
| 2 | `ABA` | `A` | 1 |
| 3 | `ABAB` | `AB` | 2 |
| 4 | `ABABA` | `ABA` | 3 |
| 5 | `ABABAC` | 无 | 0 |
| 6 | `ABABACA` | `A` | 1 |

构造时，`j` 始终表示目前可复用的前缀长度；若候选后缀不能继续延长，就回退到更短、但已经证实的候选 `π[j-1]`，而不是重新比较文本。

```text
前缀函数(P):
    若 m = 0：返回空数组
    π[0] ← 0
    j ← 0
    对 i 从 1 到 m - 1：
        当 j > 0 且 P[i] ≠ P[j]：
            j ← π[j - 1]
        若 P[i] = P[j]：
            j ← j + 1
        π[i] ← j
    返回 π

KMP(T, P):
    若 m = 0：返回 0, 1, ..., n
    若 m > n：返回空结果
    π ← 前缀函数(P)
    j ← 0
    对 i 从 0 到 n - 1：
        当 j > 0 且 T[i] ≠ P[j]：
            j ← π[j - 1]
        若 T[i] = P[j]：
            j ← j + 1
        若 j = m：
            报告 i - m + 1
            j ← π[j - 1]       # 允许重叠匹配
```

### 为什么回退是正确的？

不变量是：处理完 `T[0..i]` 的某一步后，`j` 表示已处理文本的一个后缀，且它等于 `P` 的前缀 `P[0..j-1]`。当下一个单位失配时，任何仍可能作为已处理文本后缀的匹配前缀，必须也是这段 `P[0..j-1]` 的后缀；最长候选正是 `π[j-1]`。因此回退没有丢弃可能解，也不会把未比较的单位当作相等。

`j` 在构造和扫描中每次要么前进、要么按已计算的长度严格回退；总回退次数受总前进次数约束。因此预处理为 `O(m)`，一次扫描为 `O(n)`，额外空间 `O(m)`。这是对固定单位序列、确定相等比较的界；Unicode 规范化、I/O 和报告所有命中的输出成本不包含在这个简化模型里。

## 3. Rabin–Karp：先比较指纹，碰撞时必须再核验

Rabin–Karp 令每个长度 `m` 的窗口有一个滚动哈希。窗口右移一格时，可以移除最左单位的贡献、乘以基数、加入新单位，从而避免每次重新算完整哈希。它特别适合“一段文本对许多等长模式”或批量候选过滤。

```text
Rabin–Karp(T, P):
    若 m = 0：返回 0, 1, ..., n
    若 m > n：返回空结果
    选择基数 b、模数 q，并计算 P 与首窗口的哈希
    对每个长度 m 的窗口 W：
        若 hash(W) = hash(P)：
            逐单位比较 W 与 P；相等才报告
        用滚动公式更新到下一窗口的哈希
```

哈希相等只说明“指纹相等”，**不**推出窗口相等。模 `q` 之后不同序列必然可能映到同一个余数；攻击者若能控制输入，还可能刻意构造大量碰撞，使“只在相等时核验”的成本退化。随机选参和多重独立哈希可降低意外碰撞概率，但不把概率变成逻辑保证；安全或正确性关键的匹配仍须比较原单位序列，或使用具有相应安全证明的密码学方案。

因此应把复杂度写清：滚动更新通常为常数时间；在均匀散列等模型下，候选核验期望较少；最坏情况下大量哈希相等仍可达到 `O(nm)`。不要把“哈希”自动称作加密，也不要把一次未发生碰撞的测试当作不可能碰撞的证明。

## 4. 有限自动机：把共同前缀和失败信息编码为状态

很多词条的前缀索引、Trie 的空间代价和压缩路径，已在 [[计算机知识/50-数据结构与算法/06-平衡树B树Trie与索引结构|平衡树、B 树、Trie 与索引结构]] 中建立；这里不重复其插入/查词实现。多模式搜索的关键新增点是：把 Trie 的前缀节点再加上**失败边**，使读取一个不匹配单位后不必回扫文本。

### 单模式有限自动机：状态就是“已匹配了多少前缀”

对固定模式，状态 `q` 可表示“当前文本后缀与模式前缀相等的最大长度为 `q`”。读入一个单位，转移到仍成立的最大状态；状态 `m` 即一次命中。KMP 不显式存储完整转移表，而用 `π` 在失配时计算回退；若字母表小、模式固定且要反复扫描，预先建表能让每单位转移为一次查表。

多模式搜索可将 Trie 与失败边结合（经典 Aho–Corasick 思想）：状态共享模式前缀，失败边表示“当前后缀还能复用到哪个前缀”。当沿当前单位的边不存在时，反复走失败边，直到找到可走的边或回到根；状态还要保存本节点及失败链上结束的模式输出。它与 KMP 同属“把过去的比较结果编码为状态”的思路，但构造、输出处理和内存成本更高。

## 5. 它和正则引擎有什么关系？

只含字面量连接与有限选择的正则可以编译为有限自动机；这类问题与上面的状态转移直接相关。许多生产引擎使用 NFA/DFA 或其变体，通常可避免某些回溯灾难；另一些引擎采用回溯执行模型，支持反向引用、部分环视等更强或更复杂的功能，却可能在特定模式与输入上发生灾难性回溯。详细的性能与安全边界见 [[编程知识/10-基础/01-正则表达式/08-性能安全与可维护性|正则性能、安全与可维护性]]。

不能从“正则也匹配字符串”推出以下任何结论：

- KMP 能处理任意正则语法；
- 正则引擎必定线性时间；
- Trie 能直接表达捕获、替换或上下文断言；
- 对用户输入的正则都可以安全无限制执行。

选择时，固定字面模式优先考虑朴素/KMP；大量共享前缀词条可先看 [[计算机知识/50-数据结构与算法/06-平衡树B树Trie与索引结构|Trie 索引]]；多模式流式检测考虑带失败边的自动机；需要声明式字符类、锚点或捕获时才选择并审查目标正则引擎。

## 练习

1. 分别说明“在 UTF-8 文件中找字节序列 `0A`”“限制用户名为最多 12 个用户可见字符”“估算一段提示词的 LLM 上下文”应选择哪一层单位。给出一个不能混用的反例。
2. 手工计算模式 `A B A B A C A` 的前缀函数，再用 KMP 在 `A B A B A B A C A` 中追踪 `j` 的变化并写出命中起点。
3. 修改 KMP 的报告后状态：若不执行 `j ← π[j-1]`，为什么会漏掉模式 `A A` 在文本 `A A A` 中的重叠匹配？
4. 假设某滚动哈希模数很小，构造或搜索两个不同短序列却具有相同哈希的例子。说明为什么完整比较能阻止误报，却未必阻止性能退化。
5. 以模式 `he`、`she`、`his`、`hers` 为例，说明带失败边的多模式自动机在“当前边不存在”时为何不必把文本指针退回；Trie 的节点、压缩和空间分析回链到上一课。

### 练习核对锚点

第 2 题模式 `A B A B A C A` 的前缀函数是 `[0, 0, 1, 2, 3, 0, 1]`；它在文本 `A B A B A B A C A` 中的命中起点是 2（从 0 开始计数）。第 3 题若模式 `AA` 在文本 `AAA` 的第一次命中后把 `j` 直接清为 0，会遗漏起点 1 的重叠命中；回退到 `π[1]=1` 才保留那个候选后缀。
