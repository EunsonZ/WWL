# ZAP代理与被动扫描

**先修关系：** [[计算机知识/Kali/03-Web与API安全/01-Web测试模型与手工基线|Web测试模型与手工基线]]；[[计算机知识/Kali/03-Web与API安全/02-curlHTTPie与接口重放|curlHTTPie与接口重放]]。

## 同样是代理，不同的自动化边界

ZAP 可以作为拦截代理观察浏览器请求，并对已经经过的流量执行被动规则分析；它也包含会主动发送额外请求的爬取与扫描功能。**被动扫描**不主动生成攻击请求，但前提流量仍然是浏览器实际访问产生的；它不等于整个过程没有网络活动。[^s1]

本章先建立人工浏览、被动观察、人工复核的闭环。对本包静态服务不需要运行主动漏洞扫描。

## 专用 Context 与范围

启动前核对回环监听与端口，避免与 Burp 同时抢占 8080。使用专用浏览器，配置 Context/范围，把登录、退出、删除、邮件和外部跳转等需要特殊处理的路径分别标明。实际菜单位置依版本而异，本包未进行 ZAP GUI 验证。

ZAP 的模式（如 Safe、Protected 等）帮助约束某些操作，但不取代授权和网络隔离。不要因为选择了某个模式就忽略上下文、认证用户或自动加载的扩展行为。

## 认证爬取之前，先证明爬虫处于正确身份

Context 表示一组相关范围与配置，不等于身份已经配置成功。登录端点、会话机制、测试用户和“已登录/已退出”的可识别条件需要配合验证。不要只用一个到处出现的用户名字符串作成功标志；应选择仅在本账户成功访问时稳定出现、且不会在登录页面回显的业务特征。[^v2-zapauth]

先让测试用户访问一个仅登录后可见的教学对象，再主动退出、确认同一检查失败；这是一组正反对照。两者都成功说明识别条件太宽，两者都失败可能是会话配置错误，不是“安全性很高”。本包没有附登录服务器，这一 UI 流程属于明确标记的扩展练习。

## 从探索到告警

先手工打开 `/` 与 `/health`，确认 History 中的原始请求和响应。阅读被动告警的具体证据，例如某首部缺失、Cookie 属性或内容暴露。被动规则发现缺失安全首部，不等于已证明可造成业务影响。

把告警翻译成一个可检验问题：“这个页面会嵌入不可信内容吗？”“应用的认证 Cookie 是否在不安全上下文中使用？”“这份响应是后端生成还是缓存生成？”之后使用 [[计算机知识/Kali/03-Web与API安全/03-BurpSuite工作流|Repeater 式工作流]] 或 [[计算机知识/Kali/03-Web与API安全/02-curlHTTPie与接口重放|curl]] 做最小比较。

## 三种覆盖：可到达、已观察、已分析

把应用中相关交互记为集合 $U$，本次身份和探索方式可到达的集合为 $R$，实际经过观察点的为 $O$，完成指定规则分析的为 $A$。通常只能确认已知部分，并不能假定 $A=O=R=U$。这是一套原创的覆盖记账模型，不是 ZAP 内部状态变量。

传统 Spider 从种子 URL 提取链接并继续访问；AJAX Spider 借助浏览器探索动态交互，能处理另一部分客户端状态。二者不是“低级和高级扫描”关系：一个依赖链接提取，一个涉及浏览器执行与事件路径，仍都可能遗漏需要特殊角色、已有对象或特定业务顺序的入口。[^v5-zap-spider][^v5-zap-ajax]

被动扫描消费经过它的消息，不主动改写这些消息；分析有队列与完成状态。浏览器加载、Spider 抓取和主动扫描则可能发起请求。于是“只启用被动规则”并不能证明整个工具链没有产生主动访问；“探索已结束”也不自动证明分析队列已完成。[^v5-zap-passive]

## 爬虫与主动扫描的副作用

Spider/AJAX 的工作模型见 [[#三种覆盖：可到达、已观察、已分析|覆盖主解释]]；执行动态逻辑可能触发业务动作和外部请求。登录状态不正确时，爬虫可能只重复访问登录页，漂亮的“扫描完成”并不代表覆盖了认证后功能。

Active Scan 会生成测试输入，可能增加请求量、改变数据或触发限流。应使用自建可恢复应用，明确包含/排除规则、扫描策略、并发、时间与停止条件。对真实系统必须另有许可，不因“开源工具”就默认无风险。

自动化框架与容器化扫描适合流水线，但任务配置、目标、认证和输出仍需版本化；镜像标签与规则更新也会改变结果。不要未经评估把扫描器接到生产发布流水线。

## 一个没有告警但尚未覆盖的例子

教学应用含登录页、普通用户报告页和管理员审批页。匿名爬虫只访问登录页与公开帮助，零告警只能约束这批观测，不能评价管理员审批。以已登录用户重跑而未检查会话失效，又可能把统一登录跳转当成大量成功覆盖。

因此应分别说明种子、Context、身份、状态、实际 URL/方法、已完成规则和排除对象。ZAP 的告警计数适合做候选发现入口，不适合作为“已覆盖业务比例”的直接分母。与 [[计算机知识/Kali/02-信息收集与网络测量/07-漏洞扫描NucleiGreenbone与复核|扫描规则与结论层次]] 的区别只是输入对象不同，证据原则相同。

## 零告警需要同时报告覆盖范围

用 [[#三种覆盖：可到达、已观察、已分析|U/R/O/A 主模型]] 区分文档接口、实际请求和到达的业务请求；单页应用、一次性 token、角色与状态迁移仍可造成遗漏，重复一万次登录页不等于覆盖受保护页面。记录规则/附加组件版本、过滤、排除、认证、请求数和队列完成状态；删除告警只是视图操作，不是修复。

## 与 Burp 的选择关系

对人工逐请求研究，二者都能胜任，选择应围绕工作流、许可和团队已有证据格式。先把一条请求解释清楚，再比较工具的便捷功能。不要把“用了两个扫描器得到同样告警”当成独立验证：它们可能依赖相同规则和相同错误前提。

## 从交互式练习迁移到自动化

自动化计划应显式规定环境、用户、范围、先后顺序、时间上限和退出条件。最先加入的断言应是“身份正确且目标页面可达”，然后才是规则结果。否则自动化会稳定地重复一个配置错误，稳定本身没有证据价值。

本包不安装 ZAP 插件或运行自动扫描计划；只保留可审阅操作合同。对相同公开夹具的观察可与 [[计算机知识/Kali/03-Web与API安全/03-BurpSuite工作流|Burp 手工基线]] 比较，解释工具差异而不是争论哪个工具输出更多。

## 自检

ZAP 没有报对象越权，能否认为 Alice 无法读 Bob 的报告？不能，扫描器未必理解对象所有权与角色关系；必须按 [[计算机知识/Kali/03-Web与API安全/08-认证会话越权与API测试|授权矩阵]] 实施双账户对照。

结束时导出脱敏报告，关闭代理，保留原始请求定位。缺少 GUI 或授权靶场时把主动扫描标为未运行，不编造覆盖率。
