# 让异步任务有负责人：取消、异常组与有界流水线

**版本、模型与证据边界**：解释以 Python 3.13 文档为依据，实验运行于记录中的 Python 3.13.5；不是所有实现的内部布局承诺。

## 先列出任务所有权，再讨论 await

`await` 表达一个暂停点，不自动保证所有子任务都有负责人。一个函数创建后台任务后立即返回，外层即使已经退出，那个任务也可能继续修改文件或发送请求。结构化并发把这类生命周期约束成作用域：作用域结束前，要么所有子任务成功，要么取消并等待其收尾。Python 的 `TaskGroup` 自 3.11 提供这类机制；本课以 Python 3.13 的语义与标准库为基线。[^task]

不要把三种事件合并：请求取消、任务收到取消异常、任务真正结束。它们可能发生在不同时间，而且任务可以执行清理逻辑、错误地吞掉取消，或迟迟不进入可协作暂停的位置。

## 从时间线理解超时

设客户端发出数据库请求，服务器完成提交，回复在网络中丢失。客户端的 `asyncio.timeout` 到期，最多说明本地等待没有在期限内成功结束；它不能证明服务器没提交。这个区别与线程、Rust 和浏览器任务都有关，不是 Python 独有。详细业务后果见 [[计算机知识/85-综合贯通/02-超时重试幂等与事务发件箱|超时与幂等协议]]。

`Task.cancel()` 通常让任务在之后的协作机会收到 `CancelledError`，不是从 CPU 上强行剪掉任意一条指令。`CancelledError` 直接继承 `BaseException`，常规 `except Exception` 不会捕获它；清理用 `finally`，显式捕获取消后一般应继续抛出。`TaskGroup`、超时作用域等机制依赖取消传播，随意吞掉取消会破坏它们的假设。[^task]

```python
import asyncio

async def child(started: asyncio.Event, cleaned: list[str]) -> None:
    try:
        started.set()
        await asyncio.Event().wait()
    finally:
        cleaned.append("released")

async def demonstration() -> None:
    started = asyncio.Event()
    cleaned: list[str] = []
    async with asyncio.TaskGroup() as group:
        task = group.create_task(child(started, cleaned))
        await started.wait()
        task.cancel()
    assert task.cancelled()
    assert cleaned == ["released"]
```

这个例子等待了子任务完成，而不是发出 cancel 后就把它遗忘。实验中的 `finally` 不包含新的可中断 I/O；现实清理若再次 await，仍要设计再次取消、清理失败和总时限的策略。

## 异常组为什么不是“取第一个异常”

一个 TaskGroup 中某个子任务发生普通失败时，其他尚未结束的子任务会被取消，组会等待它们。多个失败可能形成 `ExceptionGroup`，需要按异常类别处理，例如用 `except* ValueError` 处理其中一类。它保留并发失败的结构，而不是宣称所有异常按某个全局时间顺序只会发生一次。`KeyboardInterrupt` 和 `SystemExit` 有特殊处理，不能套用普通失败的全部描述。[^task]

不要把 `gather()` 的默认行为当 TaskGroup：默认 `gather` 向等待者传播某个异常时，其他参与任务不因此自动全部取消。选机制要看“失败后兄弟任务还能不能继续产生效果”，而不只是看返回值是不是列表。

## shield 保护的是内层工作，不是调用者

`asyncio.shield(task)` 可以使外层等待被取消时，内层任务不因这条传播路径一起取消；外层调用者仍会收到取消。任务还可能被其他持有者显式取消，也可能自己失败。shield 不是“这段操作永不被中断”，更不是持久化事务。

`wait_for` 在超时后需要等待被取消对象完成取消，因而真实耗时可能超过传入的秒数。`to_thread` 可以避免某些阻塞调用卡住事件循环，但取消等待它的协程不能等同于停止已经运行的线程函数；外部函数应自行支持停止协议，或接受它会运行到返回的边界。[^task]

## 有界队列把压力向上传，而不是让内存无限接盘

设生产速率为每秒 120 项，单个消费者处理速率为每秒 100 项。忽略抖动时，无界队列每秒净增长 20 项。一小时不是“稍微忙一点”，而是积压 72,000 项。增加队列上限能限制某一段存储，但不能让服务率自动增加；生产者必须阻塞、拒绝、降级或把压力传给上游。

用 `asyncio.Queue(maxsize=k)`，`await put` 在队列满时暂停。若生产者已经先把一百万个任务都创建出来，再让任务各自等待 put，任务对象本身仍可能占满内存。背压需要覆盖整个生产路径，而不是只给中间盒子画一道线。队列指标与尾延迟见 [[计算机知识/85-综合贯通/03-从复杂度到尾延迟的性能证据链|性能证据链]]。

```python
async def consume(queue: asyncio.Queue[int | None], output: list[int]) -> None:
    while True:
        item = await queue.get()
        try:
            if item is None:
                return
            output.append(item * item)
        finally:
            queue.task_done()
```

每一次成功 get 对应一次 task_done，包含哨兵。多个消费者要设计足够的结束信号，或采用一致的关闭协议。`queue.join()` 等的是任务计数归零；它不知道追加结果是否已经落盘，也不知道业务是否成功。失败后仍在 finally 中 task_done，是完成记账，不是证明成功，应另行记录失败或让 TaskGroup 传播它。[^queue]

Python 3.13 增加队列 shutdown，较早版本不能直接调用。特别是立即关闭会改变未完成任务的等待语义，因此不能拿“join 返回”证明所有工作被处理。跨版本示例宜采用明确的哨兵或专门适配层。

### 返回批事务：join 已返回，库内为什么仍只有两行

去[[计算机知识/10-编程语言/01-Python/10-系统课程/14-性能观察与有界取消恢复#四条都记账，为什么仍只提交两条？|同一四行的取消与恢复实验]]把本节的计数用到SQLite。两行一批，消费者在get后立即task_done，并在批提交前观察空队列join返回：a/b第一批提交，c/d也完成记账，INSERT c后抛异常则第二批回滚。实际state为 `accounted=4`、`joined_before_commit=2`，而已提交身份仍只有a/b；TaskGroup取消仍在await的生产者并等待收尾，文件和连接随后关闭。

返回本节分别说清“消费记账”“当前批提交”“任务结束”“资源关闭”四个时点，再到[[计算机知识/10-编程语言/01-Python/10-系统课程/12-可恢复导入器与安装交付#两行一批：失败之后，哪些数据已经存在|重放恢复]]核对新增c/d、重复a/b。把批大小改4，同位置故障库内为空；改变队列容量只改变缓冲与调度，不能替代查询提交行。这个应用使用3.11+ API、不调用3.13的shutdown，本页原3.13实验身份保持原样；该同步SQLite批中没有await，所以事件循环不能在批中段注入协作取消。它兑现本地失败/兄弟收尾，仍不解决远端确认丢失或分布式exactly-once。
## 同步计算、阻塞 I/O 与异步 I/O 的边界

一个协程如果连续运行很久而不让出控制，其他协程就得不到执行机会。`async def` 不会把内部 CPU 循环自动切成可抢占片段。是否用线程、进程、原生扩展或真正异步接口，需要区分计算量、GIL/解释器构建方式、扩展是否释放锁，以及取消和资源上限。不能用一句“Python 线程都没用”代替测量。

本轮实验验证协作取消的 finally、TaskGroup 兄弟任务收尾，以及小容量队列对生产者的实际阻塞。它不证明任意第三方驱动遵守取消，也不模拟真实网络丢包。Rust 的 [[计算机知识/10-编程语言/04-Rust/10-系统课程/10-Pin投影任务所有权与取消协议|任务句柄所有权]] 和 Linux 的 [[计算机知识/20-操作系统/01-Linux/10-系统课程/09-FD共享epoll与非阻塞状态机|事件就绪语义]] 解释了相邻两层仍须满足的条件。

**自测**：消费者取到消息，业务写入失败，但调用了 task_done。join 最后返回能证明业务成功吗？不能。需要业务结果集合、事务确认或可重试记录，不能把队列内部计数当提交日志。
