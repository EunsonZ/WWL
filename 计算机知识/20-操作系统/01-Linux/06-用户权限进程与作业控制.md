# 用户、权限、进程与作业控制

Linux 把「谁在做事」和「哪个程序在做事」分开处理：身份决定可访问什么，进程决定当前正在运行什么。先用普通用户完成日常工作；只在一条明确、可复查的命令确实需要时，通过 `sudo` 暂时取得管理员能力。

本课的文件与目录前置知识见 [[计算机知识/20-操作系统/01-Linux/05-文件目录与文本处理命令|文件、目录与文本处理命令]]；环境继承和 PATH 见 [[计算机知识/20-操作系统/01-Linux/07-环境变量Shell启动与PATH|环境变量、Shell 启动与 PATH]]。

## 学完能做什么

- 读懂 UID/GID、账户数据库和 `rwx` 权限；不会把目录权限误解成文件权限；
- 用 `umask`、`chmod`、`chown`、`chgrp` 在最小权限原则下管理自己的文件；
- 区分普通权限位、ACL、setuid/setgid/sticky bit，知道后面三者的安全边界；
- 使用 PID、PPID、状态和信号观察、停止或优雅结束进程；
- 在终端中可靠地使用前台、后台、作业控制、`nohup` 与优先级；
- 理解 shell 后台作业和由 `systemd` 管理的系统服务不是同一件事。

## 1. 身份：UID、GID、root 与账户数据库

内核按数字识别身份：**UID**（user ID）是用户身份，**GID**（group ID）是主组身份；进程还可携带一组附加组。用户名只是方便人阅读的映射。`id` 可显示当前身份及其组；`getent passwd "$USER"` 和 `getent group` 可通过系统配置的名称服务查询公开的账户与组条目。

`root` 通常是 UID 0 的超级用户。它能绕过许多普通文件访问检查，因此「能运行」不是「应该运行」。日常编辑、下载、构建和运行开发服务器都不应以 root 身份进行；错误的通配符、错误路径或不可信脚本在 root 下造成的影响会被放大。

常见本地账户数据库路径如下。它们的**格式和用途**可以学习，但本课不要求、也不建议读取你机器上的真实内容：

| 路径 | 用途 | 安全边界 |
| --- | --- | --- |
| `/etc/passwd` | 用户名、UID、主 GID、主目录、登录 shell 等账户元数据 | 常须可被普通程序读取；不应含可用密码哈希 |
| `/etc/group` | 组名、GID 及显式成员 | 用于名称到组的映射；附加组还可能来自目录服务等来源 |
| `/etc/shadow` | 密码哈希、密码期限和锁定信息 | 高敏感文件，通常仅 root 或特权账户服务可读；不要复制、展示或提交它 |

发行版还可能使用 LDAP、SSSD、容器映射或其他名称服务来源，所以不要假设编辑三个文件就能正确管理账户。账户创建、删除、改组、改密码属于系统级变更，应使用发行版的受控管理工具，并在共享机器上先取得管理员授权。

### `sudo` 是窄门，不是常驻模式

`sudo command` 根据 `/etc/sudoers` 及其包含文件执行**那一条**获准命令；它不是「登录后就永久安全地成为 root」。使用它前应先确认完整命令、目标路径和参数，避免下列扩大边界的习惯：

> [!danger] 不要把未知内容交给 root
> 不要把网络下载内容直接管道给 `sudo sh`，也不要用 `sudo -i` 进入常驻 root shell。若管理员已经批准一项具体写入，应先检查本地文件、完整参数、目标路径和恢复方案，再只提升那一条必要命令。

```bash
# 较小边界：先检查本地脚本和参数，再仅提升必要的一步。
sudo install -m 0644 ./app.conf /etc/myapp/app.conf
```

即便使用 `sudo`，shell 在提升前仍会处理重定向：`sudo echo x > /etc/example` 中的 `>` 仍由普通 shell 执行，往往会失败。不要用此技巧绕过权限；对于管理员确实批准的单个文件写入，采用明确、可审查的安装工具或 `sudo tee`，并先准备好内容和备份策略。

## 2. `rwx`：文件与目录的含义不同

`ls -l` 常显示类似 `-rwxr-x---`：第一个字符是对象类型，后九位每三位分别表示**所有者 / 所属组 / 其他人**的读（`r`）、写（`w`）、执行（`x`）权限。内核先比较进程的有效 UID 与文件所有者，再比较其所有组，最后才使用 other；它不会把三组权限累加。

| 位 | 普通文件 | 目录 |
| --- | --- | --- |
| `r` | 可以读取文件内容 | 可以列出目录项名称 |
| `w` | 可以修改或截断文件内容 | 可以在目录中创建、删除、重命名目录项 |
| `x` | 可以把可执行格式的文件交给内核执行 | 可以穿过该目录、访问其中已知名称的对象 |

目录的 `w` 控制的是「目录项」，不是其中文件的内容。因此，即使你不能写某个文件，只要对其父目录有 `w` 与 `x`，也可能删除或改名该文件；反过来，只有目录 `r` 而没有 `x` 时可看到名字却通常无法查看其元数据或进入。实际访问还受挂载选项、ACL、SELinux/AppArmor、能力（capabilities）和网络文件系统策略影响，`rwx` 不是全部安全模型。

### 默认权限与 `umask`

创建程序先提出一个权限上限（常见为文件 `666`、目录 `777`），系统再按进程的 **umask** 清除相应权限。可用 `umask` 查看当前值；常见 `022` 使新文件通常为 `644`、新目录为 `755`，而 `077` 更适合私人材料，通常得到 `600` 与 `700`。新文件默认没有执行位；不要为了「能运行」而对不可信下载文件执行 `chmod +x`。

`umask` 是创建时的默认值，不会追溯修改已有对象，也不是访问控制替代品。共享项目应先决定所有者、组、目录继承和 ACL，而不是依赖每个人终端里碰巧相同的 umask。

## 3. 改权限与归属：最小、明确、可撤回

`chmod` 改权限位。符号形式可精确表达意图：

以下示例自包含地使用一个刚由 `mktemp -d` 创建、并在执行前已核对的临时目录；不要把 `$lab_dir` 替换成真实项目路径：

```bash
lab_dir="$(mktemp -d)" || exit 1
printf 'private note\n' > "$lab_dir/notes.txt"
mkdir "$lab_dir/project"

# 仅让所有者可读写；去掉组和其他人的全部权限。
chmod u=rw,go= "$lab_dir/notes.txt"

# 在目录上为所属组补充可穿过/列出权限；不改变其他类。
chmod g+rx "$lab_dir/project"

# 八进制依次对应 user、group、other：r=4、w=2、x=1。
chmod 640 "$lab_dir/notes.txt"
chmod 750 "$lab_dir/project"
ls -ld -- "$lab_dir/notes.txt" "$lab_dir/project"

rm -i -- "$lab_dir/notes.txt"
rmdir -- "$lab_dir/project" "$lab_dir"
unset lab_dir
```

八进制 `640` 是 `rw- r-- ---`，`750` 是 `rwx r-x ---`。优先选符号形式来做局部变更；用八进制时应写清三组含义，避免无意把 other 设成可写。递归 `chmod -R` 会触及每个子项，也会把文件和目录设成相同模式，通常过宽且难恢复；除非你已盘点对象类型与原权限，否则不要使用。

`chown owner[:group] path` 改所有者（也可同时改组），`chgrp group path` 只改组。普通用户通常只能把自己拥有的文件改到自己所属的组；把文件交给另一个用户或任意组常需管理员授权。不要对不确定的路径使用递归 `chown`，特别是 `sudo chown -R`：它会快速破坏系统或项目的所有权模型。

### 特殊权限位与 ACL：能力更强，审计也更重要

- **setuid（`u+s` / 八进制前缀 `4`）**：对可执行的二进制程序，执行时可采用文件所有者的有效 UID。传统上少量受审计工具需要它；若属主为 root，漏洞会变成提权路径。现代 Linux 通常忽略 shell 脚本上的 setuid。绝不为「省事」给自写或不可信程序设 setuid，也不要复制其权限模式。
- **setgid（`g+s` / 前缀 `2`）**：对可执行文件可采用文件所属组的有效 GID；对目录则常使新建对象继承该目录的组，适合经过设计的协作目录。它不等于对所有人开放写入；仍要配合目录的组写/执行权限与审核成员。
- **sticky bit（`+t` / 前缀 `1`）**：主要用于可写目录。目录中即使多人能创建文件，通常也只能删除/改名自己的条目（以及目录所有者/root 可管理的条目）。`/tmp` 是经典例子；它不阻止别人读取一个本就可读的文件。
- **ACL（access control list）**：可为指定用户或组添加比 owner/group/other 更细的权限，常通过 `getfacl` 查看、`setfacl` 修改。ACL 可能带有 mask，限制命名用户、命名组与所属组的有效权限；`ls -l` 权限后出现 `+` 往往表示有扩展 ACL。ACL 适合例外授权，但会提高排查成本：记录理由、最小化范围、定期复核，并在撤销时移除精确条目。

只有理解完整影响并在专用测试对象上时，才练习特殊位或 ACL；它们不是「解决 Permission denied 的万能开关」。遇到权限失败，先确认对象、所有者、父目录 `x`、当前身份、挂载和安全策略，而不是直接 `sudo chmod 777`。

## 4. 进程：PID、父子关系、状态与信号

程序启动后是一个**进程**。它有 PID；启动它的进程通常是 PPID（parent PID）。PID 1 通常是系统的第一个用户空间服务管理者；进程结束后，父进程需要回收退出状态，未回收的已退出子进程会短暂显示为 zombie（`Z`）。不要试图「杀掉 zombie」：它已经结束，应排查并修复未 `wait` 的父进程。

可用下列只读命令观察系统：

```bash
ps -o pid,ppid,stat,user,ni,etime,command -p "$$"  # 当前 shell
ps aux                                           # BSD 风格的较宽快照，注意输出会随系统变化
ps -ef                                           # POSIX/System V 风格的全表快照
pgrep -a -u "$USER" python                      # 按条件找出自己的匹配进程及命令行
top                                              # 交互式、持续刷新的观察器；按 q 退出
```

`STAT`/`S` 是调度状态的摘要，常见有：`R`（正在运行或可运行）、`S`（可中断睡眠）、`D`（不可中断等待，常与 I/O 有关）、`T`（已停止）、`Z`（僵尸）。不同 `ps` 实现还会附加前台组、会话首进程、多线程等标记；先查本机 `man ps`，不要把单个字母当成性能结论。

信号是发送给进程的异步通知，不是「必然立即强杀」的承诺。`SIGTERM`（15）可被程序处理，适合请求有序退出；`SIGINT`（2）通常由 `Ctrl-C` 发给前台进程组；`SIGSTOP` 无法被捕获或忽略，`SIGCONT` 继续已停止进程；`SIGKILL`（9）也无法被处理，因此不会给程序清理文件、保存数据或释放锁的机会。

```bash
# 仅对本课安全实验中自己启动、并刚刚复核过的作业发送优雅退出信号。
ps -p "$job_pid" -o pid,ppid,stat,etime,command
kill -TERM "$job_pid"
```

`kill` 的名称来自早期用途，但它主要是发信号工具。PID 可复用，因而不要把很久以前记录的 PID 直接交给 `kill`；执行前重新用 `ps` 检查 PID、所属用户和命令。`pkill` 的匹配范围更大，必须先预览；不要对系统服务、其他用户进程或不认识的命令随意发信号。无法处理的 `SIGKILL` 只应在确认进程无响应、接受未清理后果且遵循组织流程时作为最后手段，不在本课提供可复制命令。

## 5. 前台、后台与作业控制

**作业（job）**是交互式 shell 对一个或一组进程的管理概念；**进程**是内核概念。作业控制仅在支持它的交互式 shell 中有意义，`jobs` 输出里的 `%1` 是当前 shell 的作业编号，不能代替 PID。

```bash
long-task                 # 前台：终端等待它结束；Ctrl-C 通常发送 SIGINT
long-task &               # 后台启动；shell 立即返回提示符
jobs -l                   # 查看此 shell 的作业和对应 PID
fg %1                     # 将作业 1 放回前台

# 对前台任务按 Ctrl-Z 使其停止，再继续到后台。
# ^Z
bg %1
```

后台不等于「不输出」：它仍可能读写终端，和你的输入竞争。为长任务显式重定向输出，并确认日志文件的位置与权限。关闭终端或 SSH 会话时，shell 可能向它的作业发送 `SIGHUP`；`nohup command >run.log 2>&1 &` 会使程序忽略 SIGHUP 并保存输出，但它不是服务管理器：不提供依赖关系、重启策略、健康检查、标准日志整合或可靠生命周期管理。

`nice` / `renice` 调整的是 CPU 调度的友好程度：较高 nice 值通常意味着愿意在竞争时让出 CPU，降低优先级常可由普通用户完成；提高优先级（较低甚至负值）通常需要额外权限。它不保证速度，不直接限制内存或 I/O，也不替代资源隔离。例如：

```bash
nice -n 10 batch-import >batch-import.log 2>&1 &
```

## 6. 后台作业与系统服务的区别

由 shell 启动的后台作业仍依附于该 shell 的作业控制和会话语境；`nohup` 只能处理其中一部分断连情形。**系统服务**则由服务管理器（许多 Linux 发行版为 `systemd`）按声明式单元配置管理：它能定义运行用户/组、启动顺序与依赖、重启策略、日志、资源限制和安全沙箱，并可在开机时按策略启动。unit、依赖与 transaction 的系统模型见 [[计算机知识/20-操作系统/01-Linux/02-启动链Kernel与systemd|启动链、Kernel 与 systemd]]；实际故障证据的读取顺序见 [[计算机知识/20-操作系统/01-Linux/10-网络存储日志与故障排查|日志与分层排错]]。

服务不应仅因「想让命令常驻」就以 root 运行。设计或审查服务时，至少确认：专用低权限账户、只授予必要目录访问、明确的 `User=`/`Group=`、最小可写路径、受控环境变量、日志位置、更新和停止方式。安装、启停、启用开机自启或编辑系统单元都改变系统状态，必须遵循组织变更流程并获得管理员授权；不要把临时 `nohup` 命令伪装成生产服务。

### 容器不是第四种权限，也不是一台完整虚拟机

容器运行时通常用 **namespace** 改变进程看到的 PID、网络、挂载或用户视图，并用 **cgroup** 按层级组织进程和分配/限制 CPU、内存、I/O 等资源；它们仍使用宿主 Linux kernel。于是，容器里的 PID 1、文件系统根目录和进程列表都可能与宿主不同，而容器内安装的软件也不能证明宿主的启动链、内核模块或硬件驱动已经改变。

这不是自动成立的安全结论：是否启用 user namespace、是否授予 `--privileged`、host network/host PID、设备直通、挂载宿主目录和 runtime 的默认策略都会改变边界。不要因为提示符显示为 root 就假定获得宿主 root，也不要因为应用“在容器里”就把密钥、监听端口或可写宿主目录视为安全。容器、VM、服务和 AI/GPU 工作负载的选择与证据链见 [[计算机知识/20-操作系统/01-Linux/14-Linux开发容器与AI工作负载边界|Linux 开发、容器与 AI 工作负载边界]]。

## 安全实验：在临时目录观察权限与作业

本实验只使用当前普通用户、一个新建临时目录和短暂的 `sleep` 进程。**不要使用 `sudo`，不要读取 `/etc/shadow`，不要设置 setuid/setgid/sticky bit，也不要对现有目录递归改权限。**

```bash
lab_dir="$(mktemp -d)" || exit 1
printf 'private note\n' >"$lab_dir/note.txt"
mkdir "$lab_dir/private-dir"

umask
ls -ld "$lab_dir" "$lab_dir/note.txt" "$lab_dir/private-dir"
chmod u=rw,go= "$lab_dir/note.txt"
chmod u=rwx,go= "$lab_dir/private-dir"
ls -ld "$lab_dir/note.txt" "$lab_dir/private-dir"

sleep 120 &
job_pid=$!
jobs -l
ps -p "$job_pid" -o pid,ppid,stat,ni,etime,command
kill -TERM "$job_pid"
wait "$job_pid" 2>/dev/null || true

rm -i -- "$lab_dir/note.txt"
rmdir -- "$lab_dir/private-dir"
rmdir -- "$lab_dir"
unset lab_dir job_pid
```

观察 `note.txt` 和 `private-dir` 的权限差异：同样的 `rw`/`rwx` 字符对目录和文件的效果不同。`sleep` 退出后，`ps -p "$job_pid"` 应不再显示该进程。实验没有修改账户数据库、服务、现有文件权限或系统配置；最后两行就是恢复步骤。若在 `rm` 前想人工复查，先运行 `printf '%s\n' "$lab_dir"` 和 `ls -la -- "$lab_dir"`，确认它仍是本实验刚创建的临时目录。

## 练习

1. 用自己的话解释：为什么「能删除某文件」主要取决于父目录的权限，而不取决于该文件的 `w` 位？用上面的临时目录验证后写下观察结果。
2. 在临时目录创建一个文件和一个目录，分别在独立子 shell 的 `umask 022` 与 `umask 077` 下观察默认模式；使用 `( umask 022; ... )` 和 `( umask 077; ... )` 包住实验，关闭子 shell 后确认你的原终端 umask 没有被改动。
3. 启动 `sleep 300 &`，用 `jobs -l` 找到作业与 PID；先发 `SIGTERM`，再解释为何本练习不需要 `SIGKILL`。
4. 选一个你正在运行的普通用户进程，用 `ps -o pid,ppid,stat,user,ni,etime,command -p PID` 画出它与父进程的关系。不要向不认识的 PID 发信号。
5. 比较一个 `nohup` 命令与一个正式服务至少三项差异，并说明若正式服务需要写日志或读取配置，你会如何限制它的用户、目录与权限。

## 成功标准与恢复

- 你能不看资料解释 UID/GID、有效身份、主组/附加组与 root 的最小权限边界；
- 你能区分文件和目录上 `r`、`w`、`x` 的含义，且不会用 `chmod 777` 处理未知的权限错误；
- 你能先观察再以 `SIGTERM` 结束自己启动的单个进程，并知道 `SIGKILL` 的数据一致性代价；
- 你能用 `jobs`/`fg`/`bg` 管理当前终端的任务，不会把作业编号与 PID 混淆；
- 实验临时目录已经删除，`jobs` 中没有遗留实验 `sleep`；若终端中断，可重新打开终端后用 `pgrep -a -u "$USER" sleep` 核对，再仅结束你能确认是实验创建的 PID。
