# CPU 数据通路、流水线、分支预测与乱序执行

## 本课目标

学完后，你应该能够：

- 区分 ISA 规定的架构结果与微架构内部的执行过程；
- 用数据通路解释寄存器、执行单元、缓存和控制逻辑怎样协作；
- 识别结构、数据与控制三类流水线 hazard，并说明停顿、旁路和预测各解决什么；
- 解释寄存器重命名、动态调度、乱序执行、结果完成与按序提交之间的关系；
- 说明重排序缓冲区如何帮助提供精确异常，但不把某一种实现结构当成 ISA 要求；
- 理解推测执行的性能目的，以及 Spectre 类问题提示的安全边界。

前置知识：[[计算机知识/30-计算机系统/06-指令系统汇编与程序执行|指令系统、汇编与程序执行]]已经建立“取指—译码—执行”和架构状态。本页向 CPU 内部走一层，但始终把具体实现与软件契约分开。

## 1. 直觉：像厨房流水线，更像带撤销日志的并行厨房

最简单的执行器可以等一条指令完全结束，再开始下一条。这样容易理解，却会让取指、译码、算术和访存等硬件轮流闲置。

流水线让多条指令处在不同阶段：当指令 1 执行时，指令 2 可以译码，指令 3 可以取指。高性能乱序核心更进一步：只要依赖和资源允许，后来的独立指令可以先执行；但对软件可见的结果仍要像遵守程序顺序一样提交。

```text
程序顺序： I1 → I2 → I3 → I4

内部时间：
I1  取指  译码  执行  访存  完成  提交
I2        取指  译码  等待  执行  完成  提交
I3              取指  译码  执行  完成  等待  提交
I4                    取指  译码  ……
```

I3 可以比 I2 先完成，却通常不能越过更老、尚未确认的 I2 随意改变架构可见状态。这就是“执行顺序”和“提交顺序”必须分开。

## 2. ISA 与微架构的边界

**架构状态**是软件按 ISA 能观察和依赖的寄存器、内存、PC、异常等状态。**微架构状态**包括流水线队列、物理寄存器、预测器历史、缓存内容和内部标记等实现细节。

| ISA/架构层常规定 | 微架构可自由选择 |
| --- | --- |
| 指令的逻辑结果 | 分成多少内部操作 |
| 架构寄存器与地址宽度 | 使用多少物理寄存器 |
| 分支成功后应到哪里 | 用什么预测器提前猜路径 |
| 异常的架构语义 | 用何种队列发现并按序报告 |
| 内存顺序模型与同步指令 | 缓存层级、load/store 队列和推测细节 |

x86-64 与 AArch64 都有大量不同微架构实现。同一 ISA 世代内也可能有顺序核、乱序核、不同宽度和不同缓存；不能根据 ISA 名称推出某颗 CPU 的流水级数、执行端口数或预测器算法。

## 3. 数据通路：值真正经过哪些部件

一个教学化的 CPU 数据通路包含：

```text
        ┌──────────────── 前端 ────────────────┐
PC → 取指/指令缓存 → 译码 →（可选：微操作与重命名）
        └──────────────────┬───────────────────┘
                           ↓
                   调度队列/操作数就绪判断
                    ↙          ↓          ↘
                 整数单元    向量单元    地址生成单元
                                            ↓
                                load/store 队列 → 数据缓存
                    ↘          ↓          ↙
                       结果转发/物理寄存器
                                  ↓
                            按序提交/退休
```

真实核心可能把复杂指令拆成多个内部操作，也可能融合相邻操作；这些内部操作通常不等同于 ISA 指令。x86 高性能实现常把复杂编码译为内部微操作；AArch64 实现也可以做自己的融合、拆分与调度。不能把某厂商的“µop 数量”写成 ISA 固有属性。

## 4. 流水线提高吞吐，不自动降低单条延迟

假设取指、译码、执行、访存、写回各需要一个教学周期。非流水方式处理 4 条无关指令可能占用约 `4 × 5` 个阶段时间；理想流水在填满后可以接近每个阶段时间完成一条。

这里改善的是**吞吐**：单位时间完成更多指令。第一条指令从进入到离开仍要经过全部阶段，甚至因为阶段寄存器和控制开销而有额外成本。现实吞吐还受依赖、执行宽度、缓存未命中、分支和资源冲突影响。

## 5. 三类 hazard：为什么流水线不能永远满速

### 5.1 结构 hazard：多个操作争同一资源

两条指令同一时刻都需要唯一的执行单元、缓存端口或队列条目，就会发生资源冲突。处理器可以增加资源、分时使用或让部分指令停顿。

结构 hazard 取决于具体微架构。某颗 CPU 只有一个特定除法单元，不代表 ISA 要求所有实现都只有一个。

### 5.2 数据 hazard：值还没准备好

看程序顺序：

```asm
load r1, [r_base]
add  r2, r1, r3
mul  r4, r5, r6
```

`add` 对 `load` 有真实数据依赖（read after write，RAW）；必须等 `r1` 可用。独立的 `mul` 不依赖前两条，在乱序核心上可能先执行。

简单流水线可用**旁路/转发**把刚产生的结果直接送到下一个执行阶段，不必等它先写回再读出；若结果仍未准备好，例如缓存未命中的 load，则依赖指令仍要等待。

名称依赖还包括：

- **WAR（write after read）**：后指令要写一个名字，但老指令还要读旧值；
- **WAW（write after write）**：两条指令都写同一名字，最终顺序不能颠倒。

寄存器重命名可把同一个架构名字映射到不同物理寄存器，消除 WAR/WAW 这类假依赖；RAW 是真正的数据流，不能靠改名消失。

### 5.3 控制 hazard：下一条地址还不确定

条件分支是否跳转，要等条件计算完成。若前端一直等待答案，深流水线会空出很多位置。分支预测器因此根据历史和当前上下文猜测方向及目标，让前端沿预测路径继续取指。

预测正确时节省等待；预测错误时，错误路径上的年轻工作要被丢弃，前端从正确地址重新开始。代价取决于具体核心、当时队列占用和指令位置，不应背成固定周期数。

## 6. 可观察例子：同样三条指令，两种执行时间线

```asm
I1: load r1, [r_base]   ; 假设这次等待较久
I2: add  r2, r1, r3     ; 依赖 I1
I3: mul  r4, r5, r6     ; 与 I1/I2 独立
```

### 顺序流水核心的概念路径

1. I1 等待数据；
2. I2 位于其后，又需要 I1 的结果；
3. I3 即使独立，也可能被前方停顿挡住；
4. 数据回来后依次推进。

### 乱序核心的概念路径

1. I1 发出 load，等待缓存/内存；
2. I2 被记录为等待 I1 的物理结果；
3. I3 操作数已就绪且执行单元可用，先执行并完成；
4. I1 返回，唤醒 I2；
5. I2 执行并完成；
6. I1、I2、I3 最终仍按程序顺序退休。

这解释了为什么独立工作能隐藏部分延迟，也解释了为什么一条长依赖链难以靠乱序变快。若任务本身每一步都依赖前一步，核心找不到可提前执行的工作。

## 7. 乱序执行的逐步机制

一种常见但不是唯一的教学模型如下：

1. **取指与预测**：前端预测控制流并取得一批指令；
2. **译码**：把架构指令变成核心能调度的内部操作；
3. **重命名**：为架构目标寄存器分配新的物理寄存器，记录新旧映射；
4. **分派**：为操作分配调度队列、重排序记录和 load/store 相关资源；
5. **等待/发射**：当输入就绪且执行资源可用时发射，不要求严格按程序顺序；
6. **执行与完成**：执行单元产生结果，转发给依赖者，并记录异常或预测结果；
7. **提交/退休**：从最老指令开始确认其架构效果；遇到错误预测或异常时，撤销更年轻的推测状态。

**重排序缓冲区（ROB）**是许多乱序设计用来跟踪程序顺序、完成状态和异常的结构，但不是 ISA 强制所有处理器采用这一名字或这一组织。这里的关键不在背结构名，而在理解两种顺序：

```text
操作数就绪顺序 → 可以乱序执行和完成
程序定义顺序   → 通常按序提交架构结果
```

## 8. load/store 为什么更难

寄存器依赖可通过重命名和标签明确追踪；内存依赖的地址可能要执行到较晚才知道：

```asm
store [r_a], r_value
load  r_x, [r_b]
```

只有算出 `r_a` 与 `r_b` 对应的地址和范围，才能知道 load 是否与更老 store 重叠。核心可用 load/store 队列、地址比较、store-to-load forwarding 和依赖预测提高并行度；猜错时必须重放或回滚。

这仍不替代并发程序的同步。单核内部推测、ISA 内存顺序、缓存一致性和 C++ 内存模型是不同层次。没有合适原子与 happens-before 关系的数据竞争，不能靠“这颗 x86 看起来顺序更强”修复。并发边界见 [[计算机知识/30-计算机系统/05-并发并行SIMD与加速器|并发、并行、SIMD 与加速器]]。

## 9. 分支预测：猜路径，而不是改变程序答案

预测器可概念化为：

- 方向预测：这个条件分支跳还是不跳？
- 目标预测：若跳，下一地址是什么？
- 返回预测：函数返回可能回到哪里？

实际算法、表项大小和历史组合属于具体微架构，也会随代际变化。程序员通常看到的架构结果只有“正确路径执行了什么”；错误路径上的寄存器结果不会被正常提交。

### 分支与条件选择的权衡

把分支改成无分支表达并不必然更快：

- 可预测分支可能非常便宜；
- 条件选择可能必须计算两侧或增加数据依赖；
- 分支高度不可预测、两侧工作很小时，无分支形式可能更合适；
- 编译器和目标 ISA 可能已经选择条件移动、掩码或向量化。

结论必须来自代表性数据、优化构建与目标 CPU 的测量，而不是“分支总是慢”的口号。

## 10. 按序提交与精确异常

假设程序顺序为：

```asm
I1: add  r1, r2, r3
I2: load r4, [bad_address]   ; 产生同步异常
I3: mul  r5, r6, r7          ; 可能已经内部执行
```

若处理器承诺**精确异常**，异常交给软件时应呈现一个清楚的架构边界：

- I2 之前应当完成的老指令效果已经可见；
- I2 本身报告与其对应的异常状态；
- I2 之后的年轻指令即使内部执行过，也不应作为已退休架构结果出现。

按序提交队列可以在 I2 到达队首时报告异常，并丢弃 I3 等年轻推测状态。恢复后，操作系统可终止进程、传递信号，或处理可恢复事件后重试相关指令。

“精确”是架构观察边界，不表示异常在物理上发生的那个周期立即打断所有部件，也不表示所有 ISA 的每类事件都必须用完全相同的保存规则。异常、中断与系统调用的入口路径见 [[计算机知识/30-计算机系统/08-异常中断系统调用与特权级|异常、中断、系统调用与特权级]]。

## 11. 推测执行的安全边界：Spectre 只作边界提示

推测路径的寄存器结果可以被撤销，但推测期间可能改变缓存、预测器等微架构状态。Spectre 类攻击利用“架构结果被撤销，微架构痕迹仍可能被侧信道观察”的差距，诱导受害者在推测路径上处理越权数据并泄露相关信息。

本课只建立三条边界：

1. **边界检查存在于源代码，不自动证明推测路径不可泄露。**
2. **普通功能测试看不到微架构侧信道是否安全。**
3. **缓解依赖威胁模型、编译器、操作系统和具体 CPU。** 不应自创“通用屏障序列”，也不应为了性能随意关闭系统缓解。

Spectre 不等于所有推测执行都错误，也不等于程序可以在架构层读到错误路径结果；它提醒我们：缓存与预测器等非架构状态也可能承载信息。

## 12. x86-64 与 AArch64：差异应落在哪一层

| 主题 | x86-64 与 AArch64 的共同原则 | 必须按目标核查的差异 |
| --- | --- | --- |
| 流水与乱序 | 两种 ISA 都可由高性能乱序核心实现，也都有实现选择空间 | 具体核是否乱序、流水深度、发射宽度、执行端口、缓存和预测器 |
| 内部操作 | 实现可拆分、融合并动态调度工作 | 内部操作数量与融合规则是微架构特征，不是汇编助记符的固定属性 |
| 分支 | 错误预测需恢复正确控制流 | 条件编码、分支形式、目标预测细节与误预测代价 |
| 内存顺序 | 正确并发都必须遵守语言与 ISA 同步契约 | x86-64 与 AArch64 的架构内存模型及屏障/acquire-release 指令不同 |
| 异常 | 都需要定义架构状态和返回/处理语义 | 异常类别、状态寄存器和入口细节不同 |

不要把“ARM 是顺序执行、x86 是乱序执行”当成结论。ISA 与微架构是正交层次：AArch64 和 x86-64 都有不同复杂度的具体核心。

## 13. 常见误解

| 误解 | 更准确的说法 |
| --- | --- |
| 流水线让每条指令延迟都变短 | 流水线主要提高吞吐，单条延迟不一定降低 |
| 后面的指令先执行就破坏程序顺序 | 内部执行可乱序，架构结果通常按序提交并满足 ISA 契约 |
| 寄存器重命名能消除所有依赖 | 它消除名字造成的 WAR/WAW；真实 RAW 数据依赖仍存在 |
| 分支预测错了会把错误答案写进程序 | 错路径架构结果会被恢复，但会浪费工作并可能留下微架构痕迹 |
| ROB 是所有 CPU/ISA 必备结构 | ROB 是常见实现方式；ISA 规定结果，不要求同一种内部结构 |
| CPU 乱序执行等同于编译器重排或多线程数据竞争 | 三者处在不同层，正确性分别受语言、ISA 和同步规则约束 |
| ISA 名称能告诉我预测器和端口数量 | 这些是具体微架构与处理器型号属性 |

## 练习

1. 对 `load → dependent add → independent mul` 画顺序执行与乱序执行时间线，标出哪些依赖不能消除。
2. 为 RAW、WAR、WAW 各写一个只含三条说明性指令的例子，判断寄存器重命名能消除哪两类。
3. 假设条件分支要到第 8 个阶段才解析。解释“等待”“预测正确”“预测错误”三条路径各自发生什么，不填写固定周期惩罚。
4. 对 I1/I2/I3 的精确异常例子，写出异常被报告时哪些指令允许退休、哪些年轻结果必须撤销。
5. 解释为什么一次缓存未命中可能被独立计算隐藏，却无法被依赖该 load 的指令隐藏。
6. 用两句话区分 Spectre 的“架构状态恢复”和“微架构痕迹仍可观察”，并说明为什么缓解不能凭一段通用汇编解决。

## 成功标准

- 你能把架构状态与预测器、物理寄存器、队列等微架构状态分开；
- 你能识别结构、数据、控制 hazard，并分别给出至少一种应对机制；
- 你能解释乱序执行为何需要重命名、就绪调度、结果跟踪和按序提交；
- 你能用“老指令已提交、故障指令被识别、年轻结果未退休”解释精确异常；
- 你不会从 x86-64/AArch64 的 ISA 名称推断固定流水线、预测器或性能。
