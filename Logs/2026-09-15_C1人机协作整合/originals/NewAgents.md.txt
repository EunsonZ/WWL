# NewAgents.md — WorkWithLLM Agent 实践与知识编写指南

> [!important] 本文件的地位
> 根目录 [[AGENTS.md|AGENTS.md — WorkWithLLM Agent 操作规范]] 是本 Vault 唯一的仓库级权威规范。本文件是它的执行性补充：把规则展开为新人可以照做的决策流程、写作方法、学科差异、检查清单和失败恢复方式。若两者与系统指令、开发者指令或用户当前请求发生冲突，优先顺序为：当前高优先级指令与用户授权 → `AGENTS.md` → 本文件。

> [!summary] 一句话原则
> 先确认现场，再确定知识归属；用最低且足够的能力做最小修改；让每个结论、链接、代码和“已验证”声明都能追溯到证据。

## 1. 怎样使用这份指南

Agent 开始较大任务时，建议按以下顺序阅读：

1. 当前用户请求与适用的系统、开发者指令；
2. 根目录 [[AGENTS.md|AGENTS.md]]，确认不可违反的仓库边界；
3. 本文件，选择合适的操作、写作、链接和审校流程；
4. 目标知识域的首页、MOC、相邻课程和最近相关变更日志；
5. `git status --short --branch` 与目标路径的当前 diff。

本文件解决五类问题：

- Agent 怎样和 Obsidian 文件、索引、CLI、Bases、Canvas 及插件边界打交道；
- 新知识应该进入哪个目录，以及稳定课程、实践、资源和原始材料怎样隔离；
- 所有学科共同遵守什么写作和证据规范；
- 数学、AI、计算机、编程、哲学文化和 Obsidian 教学各自还需要哪些特别规则；
- 怎样建立有意义的链接、完成审校、报告证据并留下可恢复的交接。

它不代替目标领域的专业判断，也不把某次现场快照写成永久事实。版本、工具、硬件、法律、价格、政策和外部资料等可能变化的内容，仍要在执行时现场核验。

## 2. 每次任务的标准闭环

### 2.1 先确认现场

在计划写什么之前，先确认“正在改哪个 Vault、当前有哪些变更、谁拥有这些变更”：

```bash
git status --short --branch
git diff -- "目标路径"
rg --files "目标知识域"
rg -n "关键术语" "目标知识域"
```

必须遵守：

- 现有修改、删除和未跟踪文件默认属于用户或其他协作者；不要因为它们看起来不完整就恢复、删除、暂存或重写。
- 先读目标文件当前内容和当前 diff，不能依赖旧会话里的记忆覆盖现场。
- 先找首页和 MOC，再找具体课程；不要从一个孤立文件推断整个知识域的结构。
- 如果任务包含移动、删除、同步、发布、远端操作、凭据或系统设置，先解析精确目标和副作用，再判断现有授权是否足够。

### 2.2 写出任务合同

即使不单独创建计划文件，Agent 也应在内部明确：

| 项目 | 要回答的问题 |
| --- | --- |
| 结果 | 用户最终应该看到什么可见成果？ |
| 范围 | 哪些文件可读、可改；哪些明确不能碰？ |
| 权威位置 | 这个概念应该在哪一篇笔记维护？ |
| 入口 | 用户怎样从首页或 MOC 找到它？ |
| 证据 | 需要静态检查、运行测试、真实工具还是人工观察？ |
| 副作用 | 是否会写磁盘、改配置、联网、占用 GPU 或影响外部系统？ |
| 恢复 | 失败时怎样回到最后一个已验证状态？ |
| 交付边界 | 是否得到 commit、push、发布或同步的明确授权？ |

### 2.3 选择最低且足够的能力层

普通任务不需要从最高权限工具开始。默认按以下顺序选择：

1. 用 `rg --files`、`rg -n`、`sed` 和 Git diff 做只读定位；
2. 用 `apply_patch` 做普通 Markdown 或小型配置的最小修改；
3. 用原生 Obsidian CLI 完成移动、重命名和需要真实索引语义的查询；
4. 只有文件和 CLI 不能证明结果时，才进行必要的 GUI 人工检查；
5. Local REST API、社区插件、MCP、连接器、插件 skill 或 app 只有在当前请求明确点名且确有必要时才能使用。

### 2.4 修改、读回、验证、交接

一个完整闭环不是“文件已经写入”，而是：

```text
读取现场 → 确定归属与接口 → 最小写入 → 读回 → 精确 diff
         → 内容/链接/代码验证 → warning 分类 → 日志与交接
```

如果中间任何一步出现路径不确定、并发冲突、索引不一致、测试失败或权限超出，应停止扩大写入范围，保留现场证据后重新决策。

## 3. Agent 怎样与 Obsidian 沟通

本节展开 `AGENTS.md` 的工具路由和权限规则，只解释何时、怎样操作以及失败后怎样处理；它不扩大 `AGENTS.md` 授予的能力或授权范围。

### 3.1 先理解 Obsidian 的两层状态

这个 Vault 同时有两层现实：

- **文件层**：Markdown、附件、`.base`、`.canvas`、JSON 配置和代码实际存在于磁盘；
- **应用语义层**：Obsidian 对 Wikilink、Backlink、Properties、Tags、Tasks、Templates、Daily Notes、Bases 和 Canvas file node 建立索引并赋予语义。

文件存在不代表 Obsidian 已正确解析；CLI 查询成功也不代表 GUI、插件、同步或外部服务已经真实可用。Agent 必须根据声明的强度选择证据层。

### 3.2 工具路由

| 任务 | 默认通道 | 验证重点 |
| --- | --- | --- |
| 找文件、关键词、旧路径 | `rg --files`、`rg -n` | 输出范围是否足够窄，是否遗漏同义词 |
| 读取少量已知文件 | `sed` 或直接读取 | 是否读到完整相关段落和 frontmatter |
| 新增或修订 Markdown | `apply_patch` | 最小 diff、UTF-8、末尾换行、既有内容未丢失 |
| 移动或重命名笔记 | `obsidian move` | Wikilink、Backlink、Unresolved、配置路径 |
| 查链接、属性、标签、任务 | Obsidian CLI | 应用实际索引，而不是正则猜测 |
| 查 Templates、Daily Notes、Bases | Obsidian CLI | 配置路径和真实查询是否可用 |
| 检查 Canvas | JSON 检查 + Obsidian/人工抽查 | JSON 合法、file node 目标存在、布局可读 |
| 并发局部 PATCH | 明确授权后的 Local REST API | 完整 heading chain、`ifMatch`、HTTP 412 处理 |
| 插件业务命令 | 明确点名后的精确插件命令 | 插件 ID、版本、权限、副作用、写后验证 |
| Git 提交、远端或同步 | 另行明确授权 | 精确暂存范围、凭据、可见性、冲突与恢复 |

工具方便不等于获得授权。插件已经安装、MCP 已经连接、REST 服务能够访问，都不自动允许 Agent 使用它。

### 3.3 精确路径是操作接口的一部分

原生 CLI 操作必须显式使用从 Vault 根目录起算的路径：

```bash
obsidian vault info=name
obsidian read path="AGENTS.md"
obsidian outline path="AI/20-LLM/00-LLM-MOC.md" format=json
obsidian backlinks path="计算机知识/70-编译原理/00-编译原理-MOC.md" format=json
obsidian move path="Obsidian知识/某目录/旧名.md" to="Obsidian知识/某目录/新名.md"
```

规则如下：

- `path=` 是默认选择；`file=` 像 Wikilink 一样按名称解析，只有确认名称唯一时才使用。
- 不依赖 active file；用户可能正在 Obsidian 中查看另一篇笔记。
- 中文、空格和特殊字符路径使用 shell 引号。
- 不把长篇正文塞进 CLI 的 `content=`；长篇内容使用 `apply_patch`，保持 diff 可审阅。
- CLI 失败时先检查 Vault、路径、应用状态和索引，不得直接降级为无保护的整文件覆盖。

### 3.4 查询应低输出、机器可读

```bash
obsidian files total
obsidian search query="关键词" path="Obsidian知识" limit=20 format=json
obsidian unresolved format=json
obsidian templates total
obsidian daily:path
obsidian base:query path="Obsidian知识/40-视图/02-Bases/课程进度.base" limit=1 format=json
```

- 使用 `total`、`limit=`、`path=` 和 `format=json`；不要无缘故打印整个 Vault 或全部插件 bundle。
- 文件名、字面文本可以由 `rg` 检查；Backlinks、Properties、Tags、Tasks、Bases 等解析结果以 Obsidian 语义检查为准。
- 语义命令不可用时，应明确报告该证据层未验证，不能把静态检查描述成 Obsidian 运行时验收。

### 3.5 直接文件写入的安全流程

1. 读取目标段落、frontmatter 和相关 diff；
2. 用 `apply_patch` 修改最小范围；
3. 立即读回修改区；
4. 查看 `git diff -- "精确路径"`；
5. 若影响链接、属性、Bases 或 Canvas，再做 Obsidian 语义检查；
6. 若需要补救，只修复自己能确定归属的部分。

禁止用 `cat > file`、shell 重定向、临时脚本整篇覆盖，或用 `git reset --hard`、`git checkout --`、`git clean` 清理混合工作树。

### 3.6 Local REST API 与插件能力

Local REST API 只适合经过明确授权的 heading、block 或 frontmatter 并发局部编辑：

```bash
scripts/obsidian-rest status
scripts/obsidian-rest map 'AGENTS.md'
scripts/obsidian-rest read 'AGENTS.md'
```

使用时必须先取得版本，使用完整 heading chain 和 `ifMatch`。HTTP `412` 表示现场已经变化，必须重新读取、重新判断；不得移除并发保护后盲写。REST 只允许 loopback HTTPS，不得暴露到局域网或公网。

社区插件、MCP、连接器和插件能力遵守明确 opt-in：当前请求没有点名，就不用。插件的 `data.json` 可能同时包含设置和凭据，只能检查必要的非敏感字段、忽略状态和权限，不能读取或报告 secret。

### 3.7 不直接编辑的状态

- `.obsidian/workspace*.json` 是设备与窗口状态，应用会重写；不要修改它来迁就旧标签页或旧搜索状态。
- 不读取、输出或提交 Local REST API token、TLS 私钥、OAuth token、密码、API key 和个人数据。
- 不直接修改社区插件的 minified `main.js`。
- 不因 bundle 存在就启用插件；安装、启用、升级、卸载和 restricted-mode 切换都需要明确授权与独立审计。

## 4. Vault 目录结构与内容归属

### 4.1 根目录

```text
WorkWithLLM/
├── 00-工作台/             # 真实收件箱、运行记录入口及复核视图
├── AI/                    # 机器学习、LLM 与多模态路线
├── 数学/                  # 按传统学科归档的数学权威课程
├── 计算机知识/            # 语言、操作系统、系统、算法、媒体、编译与异构计算
├── 编程知识/              # 可迁移的编程主题
├── 哲学与文化/            # 哲学、文化、制度和组织研究
├── Obsidian知识/          # Obsidian 与知识管理教学
├── Clippings/             # 未完成整理的外部原始材料
├── Logs/                  # 变更、迁移、验证和交接记录
├── .obsidian/             # 经审阅的稳定设置与本机状态边界
├── config/                # Vault contract
├── scripts/               # 只读检查和受控辅助脚本
├── AGENTS.md              # 唯一权威 Agent 规范
├── NewAgents.md           # 本执行与知识编写指南
├── README.md              # 面向读者的仓库入口
└── CONTRIBUTING.md        # 面向维护者的贡献入口
```

根目录不堆放普通课程，也不为“统一”再增加一个包住所有知识域的中间目录。未来新增物理、历史、经济、法学等知识域时，应先证明它有独立的对象、方法、证据标准和持续内容，再与现有知识域并列。

### 4.2 常用编号语义

不同知识域可以有不同细节，但通常遵循：

| 编号 | 常见职责 |
| --- | --- |
| `00` | 首页、MOC、开始入口 |
| `01–69` | 稳定课程、按主题或学习顺序编号 |
| `70–79` | 跨学科专题或该域明确约定的扩展区 |
| `80–89` | 实验、计算练习或实践区 |
| `90–99` | 资源、速查、来源、维护资料 |

编号是稳定定位符，不是必须连续的章节序号。阅读顺序以 MOC 为准；为了插入一篇桥接课程，不要批量重命名所有后续文件。

数学有更严格的两级编号规范：根目录 `00–09` 只放全域入口，`10、20、30……` 表示传统学科；学科内 `00` 为 MOC、`01–69` 为课程、`70–79` 为跨学科专题、`80–89` 为实验、`90–99` 为参考。

### 4.3 稳定知识、实践、资源和原始材料必须隔离

| 内容性质 | 归属 |
| --- | --- |
| 已审校、可长期引用的解释和推导 | 对应知识域的稳定课程目录 |
| 可修改代码、命令、合成数据和实验输出 | 对应 `80-实践/` 或指定实验区 |
| 速查、术语表、选择矩阵、模板与来源索引 | 对应 `90-资源/` |
| 尚未核验、尚未拆解的外部材料 | `Clippings/` |
| 仓库变更、验证、风险与交接证据 | `Logs/` |

不要把运行输出、构建目录、模型权重、媒体产物或临时缓存放进稳定课程目录。不要把 `Clippings/` 当成第七个知识域；材料形成稳定知识后，应进入对应域，并保留必要的来源追溯。

### 4.4 怎样判断内容归属

按以下顺序提问：

1. 这篇笔记回答的核心问题是什么，而不是示例使用了什么工具？
2. 它依赖哪种学科方法判断正确性？
3. 哪个知识域应该成为该概念的唯一权威来源？
4. 其他域需要完整内容，还是只需要应用解释与链接？
5. 内容是稳定知识、可修改实践、参考资源，还是待核验材料？

例如：

- 矩阵分解的完整定义与推导进入数学；LoRA 页面只解释它怎样使用低秩结构并链接数学权威页。
- VFS、inode、页缓存和崩溃一致性进入计算机系统；FFmpeg 页面链接复用这些机制，只讲媒体流水线怎样经过它们。
- 正则表达式作为可迁移编程主题进入 `编程知识/`；某种语言特有的字符串 API 和包管理进入 `计算机知识/10-编程语言/`。
- GGML 是具体 LLM 执行引擎案例；通用图 lowering、内存规划和代码生成语义进入编译原理。

### 4.5 新目录的成立条件

只有满足以下多数条件才新建子目录：

- 已有或确定会有多篇相互关联的稳定内容；
- 能定义一个清楚的 MOC 和学习边界；
- 有与其他目录不同的对象、方法或实践区；
- 不会制造只有一篇笔记的空壳层级；
- 能说明未来扩展位置，而不是把所有未知内容塞进“杂项”。

不创建只有标题、TODO 或空 frontmatter 的占位页面。规划主题可以使用一篇内容完整、标明 `status: planned` 的 MOC，说明问题、先修、课程路线和未来实验。

## 5. 多学科共同遵守的知识编写规范

### 5.1 先设计知识单元，再写正文

一篇稳定笔记应围绕一个**可完整回答的问题群**，而不是围绕一个偶然出现的词。合适粒度通常满足：

- 读者能够说清“读完解决了什么问题”；
- 核心概念、必要推理和一个有效例子可以在同页完成；
- 拆开会切断同一个论证、算法或机制；
- 合并又不会同时承担多个完全不同的学习目标。

不要“一公式一页”“一术语一页”，也不要把整门课塞进一篇无法导航的长文。最小化拆分不是目标，保持概念、证据和应用之间的完整关系才是目标。

### 5.2 教学页的推荐结构

稳定教学页通常包含：

1. 与文件名语义一致的一级标题；
2. 为什么需要本课、适用场景和不解决什么；
3. 明确先修和本课目标；
4. 直觉模型或可观察现象；
5. 精确定义、机制、推导或实现；
6. 一个足以暴露关键差异的实际例子；
7. 常见误解、反例、失败条件或边界；
8. 练习与可验证成功标准；
9. 上一站、下一站、相关概念和返回 MOC；
10. 快速变化内容的来源、版本、核验日期和环境。

不是每页都必须使用完全相同的小标题，但这些教学功能不能悄悄缺失。

### 5.3 从直觉到精确，再回到应用

推荐使用四层展开：

```text
直觉：它想解决什么、可以怎样想象
精确：术语、变量、前提、不变量和边界是什么
推演：公式、算法、论证或数据流怎样一步步工作
应用：在真实工具、系统、历史案例或实验中怎样观察
```

只给比喻会让读者无法迁移；只给公式或术语会让初学者无法建立模型。比喻必须注明在哪里失效，公式必须说明量纲、shape、假设和可观察后果。

### 5.4 一概念一权威位置

- 每个核心概念选择一个权威页面保存完整定义、推导、假设和练习。
- 其他页面可以复述当前应用所需的最小公式或上下文，但必须链接权威页，不复制一套会独立过时的完整课程。
- 同名不一定同义；同义也可能在不同学科使用不同抽象层。链接时要说明关系是“先修、应用、类比、对比、实现”中的哪一种。
- 发现重复内容时，先比较两页的问题和证据方法；不要仅因关键词相同就强行合并。

### 5.5 证据与不确定性

写作时区分：

- **定义**：由课程或标准明确规定；
- **可复现事实**：能由来源、代码、测试或观察支持；
- **推论**：从事实和假设推出，应写出推理链；
- **解释模型**：帮助理解，但不是对象本身；
- **经验法则**：依赖环境和分布，不能伪装成定理；
- **规范判断**：表达价值取向，应与描述性事实分开；
- **计划**：尚未交付或验证，使用 `status: planned` 等明确状态。

来源优先使用标准、官方文档、原始论文、原始数据或可追溯史料。二手资料可以帮助解释，但不能在高风险结论中替代一手证据。引用外部网页时记录页面名称、链接和核验日期；会快速变化的内容还要记录版本、commit、操作系统、镜像或硬件。

### 5.6 术语、符号和命名

- 第一次出现时给出中文、常用英文和必要缩写；后续保持同一写法。
- 不把 encoding、serialization、compression、container、codec 等相关但不同的概念翻译成同一个模糊词。
- 数学符号说明类型、维度、索引范围和约定；代码变量尽量和正文一致。
- 文件名描述问题或概念簇，避免 `笔记1`、`Overview`、`Untitled` 等重名和无信息名称。
- 一级标题应与文件名对应；MOC 通常使用 `00-主题-MOC.md`。

### 5.7 元数据

推荐使用稳定且可查询的 Properties：

```yaml
---
type: lesson
stage: 1
status: ready
difficulty: 入门
estimated_minutes: 30
topics:
  - example-topic
domain: computer-science
tags:
  - computer-science/example
---
```

当前知识域使用以下稳定命名空间：

| 知识域 | `domain` | 标签前缀 |
| --- | --- | --- |
| `AI/` | `artificial-intelligence` | `ai/` |
| `数学/` | `mathematics` | `mathematics/` |
| `计算机知识/` | `computer-science` | `computer-science/` |
| `编程知识/` | `programming` | `programming/` |
| `哲学与文化/` | `philosophy-culture` | `philosophy-culture/` |
| `Obsidian知识/` | 沿用现有页面约定，不强制新增 `domain` | `playground/` 等现有前缀 |

根目录系统文档、配置和日志不冒充某个知识域，也不为了表面统一强行添加 `domain`。

规则：

- `type` 表示页面职责，例如 `lesson`、`moc`、`reference`、`practice`、`changelog`；
- `status` 至少区分 `ready`、`planned` 和需要核验的研究状态；
- `stage` 表示课程阶段，不要把它当成精确难度排名；
- `topics` 保存稳定概念，`tags` 使用知识域前缀；
- 不自动加入每次编辑都会变化的 `modified` 时间；
- 新增属性类型前检查 `.obsidian/types.json`，不能为了单篇笔记制造新的近义字段。

### 5.8 例子、练习和成功标准

一个例子应能观察到本课的关键机制，而不是只证明代码没有语法错误。练习要明确：

- 输入、操作范围和允许修改的位置；
- 预期现象或不变量；
- 怎样判断成功；
- 常见失败意味着什么；
- 怎样清理产物或恢复原状。

不要把“命令退出码为 0”自动等同于功能正确。文件可解析、代码可编译、程序可运行、结果语义正确、性能满足目标和真实用户验收是不同证据层。

### 5.9 可运行代码与 code-sync

可运行示例同时存在于 Markdown fenced code block 和同一课程目录的源文件：

````markdown
<!-- code-sync: ./example.py -->
```python
print("hello")
```
````

- 源文件是规范来源，标记后的代码块必须逐字一致；
- 输出、伪代码、交互记录不使用 `code-sync`；
- 多文件实验的 README、代码、测试、构建配置放在同一实践目录；
- 构建产物、缓存、模型、数据集和媒体输出不进入 Git；
- 测试报告区分语法检查、toy、CPU、GPU、真实模型或真实媒体输入，不能相互替代。

### 5.10 安全、隐私与可恢复性

涉及命令或系统写操作时，正文必须说明：

- 是否需要 root、网络、设备、GPU、登录或第三方账号；
- 会修改哪些精确路径、进程、服务或配置；
- 怎样先在合成数据、临时目录、容器或虚拟机中练习；
- 成功和失败怎样观察；
- 怎样回滚、删除产物或恢复原配置；
- 哪些命令只允许阅读，哪些会产生副作用。

示例不得包含真实 token、密码、个人路径数据、私有提示、私人媒体或可识别个人信息。

## 6. 特别学科指南

### 6.1 Obsidian 与知识管理

- 每个功能至少包含一个真实 Vault 文件或可观察操作，以及明确恢复方式。
- 链接、Properties、Tags、Bases、Canvas、Templates 和 Daily Notes 不能只靠文字描述；有条件时用原生 CLI 或真实文件语义验证。
- 社区插件实验使用无个人数据的隔离区域；高风险功能默认关闭，secret 字段保持为空。
- 说明禁用插件后内容是否仍是可读 Markdown，避免把知识锁进不可迁移的私有格式。

### 6.2 编程知识

- 覆盖正常路径、空输入、边界值、错误输入、Unicode、性能和安全风险。
- API 用法与底层原理分开；不要从单一库的行为推导所有实现。

### 6.3 计算机知识总则

适用目录：`计算机知识/`。

所有计算机课程都应明确：抽象层、接口、状态、不变量、成本模型、平台差异和可观察证据。不能用一个命令的输出代替对整个系统的解释，也不能把 toy 实现描述成生产实现。

#### 6.3.1 编程语言、环境和依赖管理

- 分开语言语法、运行时、标准库、第三方包、构建系统、包管理器和虚拟环境。
- 涉及 Python 环境或依赖管理时，写清本页相关工具管理什么，并链接环境选择课程；专门的环境课程再完整比较 `venv`、pip、uv、Conda、Miniconda、Anaconda，以及解释器、包、环境和锁文件的边界。
- C++ 课程区分预处理、编译、汇编、链接、装载和运行；说明语言标准、编译器、目标 ABI、CMake 与依赖版本。
- 命令同时给出环境检查、成功标准和清理方式；跨平台差异不能藏在脚注里。

#### 6.3.2 Linux 与操作系统

- 从用户空间、系统调用、内核、驱动、设备和硬件的边界解释命令行为。
- 区分发行版工具：`pacman`、`apt`、`dnf`、`yum` 不是可互换语法；涉及 Arch Linux 时记录内核、headers、DKMS、驱动和引导环境。
- 每个需要 root 的命令明确标记，并优先提供只读检查、虚拟机或容器实验路线。
- systemd 内容同时说明 unit、依赖、启动状态、journal 日志和恢复；环境变量内容区分当前 shell、子进程、服务与持久配置。
- 分区、格式化、挂载、用户权限、网络、防火墙和驱动操作必须列出精确目标、失败风险和恢复路径。

#### 6.3.3 数据结构与算法

- 每个结构先给抽象接口，再给表示方法与表示不变量。
- 每个算法说明输入前提、终止性、正确性依据和复杂度模型；复杂度必须说明最坏/平均/摊还、RAM/I/O 模型及输入分布。
- 同时检查常数、局部性、分配成本、并发、磁盘 I/O 和概率误差，不能只比较大 O。
- 至少包含一个会击穿错误实现的反例或性质测试。
- 概率数据结构明确假阳性/假阴性、失败概率、哈希假设和误差预算；ANN 明确 recall、延迟、内存和基准数据。
- toy 实现用于暴露机制，生产选择还要考虑成熟库、并发、持久化和故障恢复。

入口：[[计算机知识/50-数据结构与算法/00-数据结构与算法-MOC|数据结构与算法 MOC]]。

#### 6.3.4 计算机系统与文件系统

- 按数据路径讲清 ISA、CPU、缓存、内存、MMU、内核、VFS、块层、设备和持久化，而不是堆术语。
- 明确地址、权限、所有权、生命周期、并发顺序、一致性和故障边界。
- 区分逻辑地址/物理地址、page cache/设备缓存、write/flush/durable、进程隔离/虚拟机隔离。
- 性能实验记录输入规模、预热、重复次数、时钟类型、硬件、系统负载与测量噪声。
- 不用静态图声称硬件行为已经验证；Linux-only、NUMA、IOMMU、GPU 和设备路径在不可用环境中应报告跳过。

入口：[[计算机知识/30-计算机系统/00-计算机系统-MOC|计算机系统 MOC]]。

#### 6.3.5 编译原理

- 分开源语言语义、AST/IR 结构、变换合法性、目标 ISA/ABI 和真实工具链行为。
- 每一种 IR 写出不变量；每个 pass 写出前置条件、保持的语义和可能使后续 pass 失效的信息。
- parser 要说明文法、优先级、结合性、错误恢复和源位置；类型检查要说明作用域、约束和诊断。
- SSA verifier、IR 可打印、代码可生成、目标文件可链接、程序可执行和结果正确是不同证据层。
- 优化至少用差分测试、性质测试、解释器对照或正式论证中的一种证明语义保持。
- 对可复现实验、命令输出或工具链行为结论，记录 LLVM/MLIR/编译器版本、target triple、命令和输入哈希；纯理论页只记录影响结论的必要版本边界。AI 编译章节区分框架图、编译 IR、runtime graph 与具体后端实现。

入口：[[计算机知识/70-编译原理/00-编译原理-MOC|编译原理 MOC]]。

#### 6.3.6 数据编码、媒体系统与 FFmpeg

- 必须分开字符/数值编码、序列化、压缩、文件格式、container、codec、传输协议和 DRM。
- 图像课程说明尺寸、通道、色彩空间、transfer function、采样和 bit depth；音频说明采样率、量化、声道、PCM 和响度；视频说明帧率、扫描、色度采样、GOP 和时间基。
- FFmpeg 命令明确输入、输出、stream mapping、stream copy 或转码、codec、container 和覆盖行为。
- 诊断优先使用 `ffprobe` 建立流、时间戳和 codec 证据，再决定转码；“能打开”不等于音画同步、质量、兼容或交付正确。
- 实验使用合成媒体和独立输出目录，说明清理命令；真实媒体还要考虑隐私、版权、专利和许可证。
- 文件系统、页缓存、DMA 和媒体缓冲的完整原理链接计算机系统权威页，不在媒体域复制。

入口：[[计算机知识/60-数据编码与媒体系统/00-数据编码与媒体系统-MOC|数据编码与媒体系统 MOC]]。

#### 6.3.7 CUDA、并行与异构计算

- 分开宿主 Linux 内核与驱动、CUDA Runtime、CUDA Toolkit、容器运行时和上层框架。
- 明确 host/device、kernel/grid/block/thread/warp 和各类 memory 的作用域与生命周期。
- 性能结论同时检查 coalescing、bank conflict、分支发散、occupancy、同步、带宽和算力；单一指标不能证明瓶颈。
- FP16、BF16、FP8、量化存储和累加精度分开说明，记录误差与硬件支持。
- CPU 编译通过不能证明 CUDA 路径；有 Toolkit 才报告编译证据，有 GPU 才报告真实执行，无硬件时明确 `SKIP`。
- PyTorch extension、Triton、原生 CUDA、llama.cpp backend 等页面说明它们所在抽象层和互相替代不了的证据。

入口：[[计算机知识/40-并行与异构计算/01-CUDA/00-CUDA-MOC|CUDA MOC]]。

### 6.7 未来新增学科的扩展规范

新增学科首先遵守通用规范，再根据证据方法补充特殊规则：

| 学科类型 | 必须额外记录 |
| --- | --- |
| 物理、化学、工程 | 单位、量纲、测量条件、模型适用域、实验装置、误差和可复现性 |
| 生物与医学 | 样本、群体、实验设计、效应量、不确定性、伦理与临床/实验室证据边界 |
| 经济学与社会科学 | 指标定义、数据时期与地域、识别策略、相关/因果、制度背景和外推边界 |
| 历史学 | 时间线、来源批判、作者立场、史料间冲突、缺失证据和后见之明风险 |
| 法学与政策 | 法域、生效日期、规范层级、原文、解释争议和事实分析/法律建议边界 |
| 语言学 | 语料、语言变体、描述/规范、分析层次和跨语言可比性 |

如果一个新知识域没有明确的对象、方法、入口、MOC、来源标准和持续内容，应先作为现有域中的专题，而不是立即增加根目录。

## 7. 链接管理：构建知识关系，而不是 Graph 装饰

### 7.1 链接必须表达关系

常见有效关系包括：

| 关系 | 链接要回答什么 |
| --- | --- |
| 归属 | 这篇课属于哪个 MOC 或学习路线？ |
| 先修 | 不理解哪个概念就无法继续？ |
| 应用 | 这个抽象概念在什么实际系统中落地？ |
| 实现 | 理论怎样变成代码、命令或实验？ |
| 对比 | 两个相近概念在哪些维度不同？ |
| 证据 | 这个结论由哪份来源、实验或日志支持？ |
| 返回 | 读者怎样回到当前主线？ |

只因两个页面出现同一个词就加链接，会制造语义噪声。同一个词也可能是同名异义；链接前先判断对象和抽象层是否一致。

### 7.2 Wikilink 书写

- Vault 内部优先 Wikilink；根 `README.md` 面向 GitHub，使用标准 Markdown link。
- 跨目录、跨知识域或可能重名时使用完整 Vault 相对路径和清晰 alias。
- 同目录短链接也要先确认文件名唯一；多个 `README.md` 只能用完整路径。
- heading link 只指向相对稳定的小节；重命名标题后必须检查锚点。
- block link 用于确实需要稳定引用的结论，不为每段自动生成 block ID。
- embed 适合复用同一权威内容或附件；嵌入前判断上下文是否仍然完整，不要用嵌入隐藏必要解释。
- 教学假链接放入代码示例并按 contract 精确管理；真实断链不能靠宽泛 allowlist 隐藏。

示例：

- [[数学/50-信息论/02-指数对数Softmax与LogSumExp|Softmax 与 LogSumExp]]；
- [[AI/20-LLM/20-架构/02-注意力MHA-MQA与GQA|Attention 架构]]；
- [[计算机知识/40-并行与异构计算/01-CUDA/08-Reduction-Softmax与GEMM|CUDA 中的 Softmax 与 GEMM]]。

这三页不是同一内容的三份副本，而是数学定义、模型结构和并行实现三个不同抽象层。

### 7.3 关键页面的最小连接

每个稳定关键页面至少应有：

- 一个来自首页、学习路线或 MOC 的进入路径；
- 一个返回本域 MOC 的路径；
- 一个真正相关的概念链接；
- 有先修时，一个明确先修链接；
- 有跨域应用时，一个应用链接或目标页上的反向应用入口。

“双向连接”不意味着把每个链接机械复制到目标页。目标页只在该关系对读者导航有价值时增加反向说明；Obsidian Backlinks 已经提供机械反向索引。

### 7.4 第一次使用跨域概念

第一次依赖其他学科概念时，使用简短 callout 说明：

```obsidian
> [!note] 数学先修
> 本节需要矩阵乘法、Softmax 和数值稳定性：
> - [[数学/20-线性代数与几何/02-矩阵乘法线性映射与Einsum]]
> - [[数学/50-信息论/02-指数对数Softmax与LogSumExp]]
```

正文只重复当前推理必需的最小内容；完整定义、证明和练习留在权威页。目标数学或系统页可以在“应用去向”中链接回来，形成有意义的双向路线。

### 7.5 MOC 的职责

MOC 不是文件列表。它至少要提供：

- 领域解决的问题和不覆盖的边界；
- 先修诊断与推荐路线；
- 课程分组以及每组的学习目的；
- 跳读路线和实践路线；
- 权威页与相邻知识域的连接；
- planned、ready、实验和参考之间的状态区分；
- 返回知识域首页和下一步。

确保新增课程从一个稳定入口可发现；如果所属 MOC 是该系列的既定入口，就更新该 MOC。不要为了形式要求把普通补充页链接进多个无关 MOC；只有文件存在却没有任何进入路径，仍属于不可发现内容。

### 7.6 链接审计流程

1. 用 `rg` 检查旧路径、目标文件名、heading 和同名候选；
2. 用 `scripts/check-vault` 检查基础目标和 contract；
3. Obsidian 运行时用 `scripts/check-vault --semantic` 与 `obsidian unresolved format=json`；
4. 抽查关键页面 backlinks，确认入口、返回和跨域关系；
5. 人工判断链接是否解释关系，而不是只统计数量；
6. 检查代码 fence 中的示例不会污染真实 unresolved links。

## 8. 目录创建、移动、重命名与删除

本节是 `AGENTS.md` 目录迁移、安全和恢复要求的执行清单。是否获准移动、删除或扩张范围，仍由当前用户授权与 `AGENTS.md` 决定。

### 8.1 新建页面

新建前检查：

- 是否已有同义或权威页面；
- 目标目录是否属于正确知识域和内容层；
- 文件名是否清楚、唯一、可扩展；
- 哪个 MOC 提供入口；
- 是否需要伴随源文件、实践目录或资源页；
- 是否会引入新的 property 类型或 contract 必需路径。

写入后先更新最小必要入口。不要把一篇普通课程同时链接进所有首页和 MOC。

### 8.2 单文件移动或重命名

使用 Obsidian 感知的精确移动：

```bash
obsidian move path="Obsidian知识/某目录/旧名.md" to="Obsidian知识/某目录/新名.md"
obsidian backlinks path="Obsidian知识/某目录/新名.md" format=json
obsidian unresolved format=json
```

普通 `mv` 不会可靠维护 Wikilink 和索引语义。命令返回成功之后仍要检查目标文件、链接、配置和 Git diff。

### 8.3 批量迁移

批量迁移必须经过：

1. 记录源目录、目标目录、文件数与类型数；
2. 写出逐文件旧路径 → 新路径 manifest；
3. 标记首页、MOC、书签、模板、Daily Notes、Bases、Canvas 和用户内容；
4. 建立目标目录，按清单逐文件执行 `obsidian move`；
5. shell 循环与可能读取 stdin 的子命令使用不同输入通道；
6. 中文路径用已验证的 UTF-8 工具，小批试跑；
7. 多个路径互相包含时按最长、最具体的路径优先；
8. 每批扫描旧路径、双重前缀、混合路径、mojibake、孤立页和重名；
9. 单独检查无法由 Wikilink 自动更新覆盖的配置面；
10. 写迁移日志、验证恢复路径，再决定是否建立版本快照。

必须额外检查：

- `.obsidian/app.json`、`templates.json`、`daily-notes.json`、`graph.json`、`bookmarks.json`、`types.json`；
- 经审计且不含 secret 的插件路径字段；
- 所有 `.base` 中的路径筛选和公式；
- 所有 `.canvas` 的 file node；
- `README.md`、`CONTRIBUTING.md`、`AGENTS.md`、本文件、检查脚本和 Vault contract。

### 8.4 删除、归档与恢复

- 删除前用只读检查解析精确目标、引用和所有者；范围不清楚就停止。
- 原始材料可能承担证据追溯，不因已经拆成课程就自动删除。
- 能归档或移入可恢复位置时，不做永久删除。
- 删除生成物只针对已确认的构建、缓存或实验输出，不能用宽泛 glob 指向知识域或仓库根。
- 完成物质性删除后说明删除了什么、是否可恢复、恢复方法是什么。
- Git index 与工作树不是同一集合；未提交迁移时旧路径仍可能出现在 `git ls-files`，不能据此判断新文件丢失。

## 9. 多 Agent 协作

只有用户或适用的更高优先级规则明确要求或允许多 Agent 协作时，才采用本节的拆分建议；本节本身不构成自行委派的授权。

### 9.1 适合并行的任务

- 不同知识域或不重叠目录的课程撰写；
- 不同来源的只读研究与事实核验；
- 技术正确性、教学可读性、链接格式和安全边界的独立审校；
- 代码测试、元数据扫描、路径审计和生成物检查；
- 作者与审校者使用不同视角进行复核。

### 9.2 不适合并行写入的任务

- 同一 MOC、首页或核心规范；
- 同一个 JSON、Base、Canvas 或 contract；
- 同一批路径迁移；
- Git 暂存区、commit 或 push；
- 彼此依赖但接口尚未确定的多文件实现。

主 Agent 应独占根 MOC、contract、基础设施和 Git 集成；子 Agent 得到精确文件所有权，并被告知仓库中还有其他协作者，不得回退他人的修改。

### 9.3 模型和 effort 的经济分配

| 工作 | 建议分配 |
| --- | --- |
| 文件盘点、计数、格式、frontmatter、字面链接扫描 | 轻量模型，low/medium |
| 常规课程草稿、例子、初学者可读性和 MOC 结构 | 平衡模型，medium/high |
| 数学推导、并发、编译器、CUDA、量化、安全和迁移设计 | 强推理模型，high/xhigh |
| 最终跨域一致性和高风险结论 | 与作者不同的强推理审校者 |

并发槽位不是完成度指标。只在边界互不重叠时并行；当前 AI/LLM 相关建设的团队总并发上限为 20，包含主 Agent。小任务不要为了占满槽位而复制上下文和消耗 token。

### 9.4 子 Agent 的交付格式

子 Agent 应报告：

- 读取了什么、修改了什么精确路径；
- 哪些事实得到验证，哪些是推断或未验证；
- 测试、命令和结果摘要；
- 与其他 Agent 接口或冲突；
- 风险、恢复方式和下一步；
- 没有执行的 commit、push、发布或外部动作。

子 Agent 的“完成”只是主 Agent 的输入。主 Agent仍需检查实际文件、diff、链接和测试，才能对用户声明完成。

## 10. 验证协议与证据等级

本节用于选择和陈述验证证据；最终完成条件仍以 `AGENTS.md` 的验证协议、Definition of Done 和当前用户约定为准。

### 10.1 普通内容修改

```bash
scripts/check-vault
git diff --check
git status --short
git diff -- "相关路径"
```

### 10.2 链接、Properties、Bases 或 Canvas

Obsidian 正在运行时增加：

```bash
scripts/check-vault --semantic
obsidian unresolved format=json
```

然后抽查：

- 首页、学习路线和 MOC 能进入新页面；
- Backlinks、heading link、embed 和 bookmarks 指向正确目标；
- 新建笔记、附件、Daily Notes 和 Templates 仍指向正确目录；
- 受影响 Base 至少执行一次查询；
- Canvas 是合法 JSON，file node 目标存在；
- Graph 和非敏感插件路径没有保留迁移前地址。

### 10.3 代码和实验

按风险逐层验证：

| 证据层 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| 静态解析/格式 | 文件可读取、语法或结构基本合法 | 程序行为正确 |
| 单元测试/toy | 局部合同和受控样例成立 | 真实规模、真实平台或生产性能 |
| CPU 实际运行 | 当前 CPU 环境的执行路径成立 | GPU、设备或分布式路径 |
| GPU/设备运行 | 当前硬件与驱动组合能执行 | 其他显卡、驱动、数据和负载 |
| 真实模型/媒体/数据 | 当前工件上的端到端行为 | 普遍质量、无污染或无回归 |
| 人工产品验收 | 指定场景可用且体验符合目标 | 所有边界和未来版本 |

报告中只能声明实际取得的那一层。缺工具或硬件时写 `SKIP` 及原因，不把跳过写成通过。

### 10.4 warning、error 和已知基线

当前 v2 检查器按 critical/error/review/style 分级，旧 warning 的解释仍可参考下文，但不能据此把 style 当作确认错误。默认 share profile 不要求本机插件启用清单；local_restore 保留该完整性检查。YAML 使用现有 PyYAML 或 Ruby Psych，缺依赖时报错；候选扫描和实际 UI 验收是独立层次。

- 完整 Vault 或要求全库验收的交付必须满足相关检查 `0 error`。若存在本轮无权处理的既有全库 error，必须逐项说明来源、本轮影响和“未新增”的证据；不得据此声明全 Vault 已通过。窄范围任务能否完成，仍以 `AGENTS.md` 的完成条件和用户约定为准。
- warning 可以保留，但必须按教学 hard break、示例链接、未启用插件 bundle、原始材料等类型解释。
- 真正故意的 unresolved link 只能在 `config/vault-contract.json` 中以目标、来源和理由精确声明。
- 不通过通配 allowlist、忽略整个目录或修改检查器来掩盖新增错误。
- 检查器通过只是证据之一，不取代内容正确性、运行测试或人工语义审阅。

### 10.5 Definition of Done

只有同时满足以下条件才可以声明完成：

- 用户要求的文件和内容真实落盘；
- 目标读者能从明确入口找到并理解；
- 内容满足通用规范和目标学科特殊规范；
- 权威位置清楚，没有复制出互相漂移的课程；
- 链接表达真实关系，入口、返回和先修有效；
- 可运行代码、已有伴随文件与正文一致；多文件、易回归或有明确算法/系统合同的示例具备相应测试，短小示例至少有实际运行或可观察成功标准；
- 风险、权限、版本、环境和证据等级诚实；
- Vault 检查、语义检查和相关测试按范围完成；
- warning、skip 和受保护问题得到分类；
- Git diff 已审阅，没有覆盖用户或协作者工作；
- 大变更有 `Logs/` 记录和恢复方法；
- 没有执行未获授权的 commit、push、同步、发布或外部动作。

## 11. 常见任务的简明操作手册

### 11.1 新增一篇课程

1. 读 `AGENTS.md`、本文件、知识域首页和对应 MOC；
2. 搜索同义概念，确定权威位置与粒度；
3. 建立 frontmatter、目标、直觉、精确内容、例子、边界、练习和成功标准；
4. 补入站、返回、先修与应用链接；
5. 有代码则建立同目录源文件，保持 `code-sync`；按风险决定是否建立测试，并记录实际运行或其他验证；
6. 确保课程从稳定入口可发现；所属 MOC 是既定入口时更新该 MOC，不扩散到无关首页；
7. 运行检查、读回和精确 diff。

### 11.2 新增一个课程系列或知识域

1. 定义对象、方法、读者、边界和与现有域的区别；
2. 先设计首页/MOC、稳定课程、实践和资源的职责；
3. 只有真实内容足以支撑时才建目录，不生成空占位页；
4. 选择编号余量和稳定命名；
5. 设计与相邻域的网关链接和唯一权威页；
6. 接入 README、目标域首页、contract 和日志；
7. 做结构、链接、内容、代码与安全独立审校。

### 11.3 从 Clippings 整理材料

1. 保存原始出处、作者、时间和获取状态；
2. 区分原文主张、事实、解释、推论和规范判断；
3. 为关键事实寻找更接近一手的来源；
4. 按问题群组织稳定知识，不按原文段落机械切片；
5. 记录反例、冲突来源、置信度和待核验项；
6. 将稳定知识放入对应域，建立回到来源索引的链接；
7. 是否保留或归档原件根据追溯价值决定，不自动删除。

### 11.4 更新快速变化的工具页

1. 现场核验官方来源和当前版本/commit；
2. 记录操作系统、容器镜像、硬件和命令；
3. 将稳定原理与版本特定操作分开；
4. 检查旧命令、弃用项和兼容矩阵；
5. 只报告实际验证层，未运行路径明确标记；
6. 更新来源核验记录和相关选择矩阵。

### 11.5 移动一个目录

1. 先生成逐文件 manifest 和迁移前计数；
2. 标记所有入口、配置、Base、Canvas、书签和用户内容；
3. 小批使用精确 `obsidian move`；
4. 每批检查乱码、旧路径、双重前缀、断链和文件数；
5. 更新非 Markdown 配置与 contract；
6. 运行静态和语义验证；
7. 写日志和恢复映射，得到授权后才做 Git 交付。

## 12. 常见反模式

| 反模式 | 问题 | 正确做法 |
| --- | --- | --- |
| 未读现场就按旧记忆整篇重写 | 覆盖用户或协作者修改 | 先读文件与精确 diff，再做局部 patch |
| 因插件已安装就直接调用 | 安装不等于启用、审计或授权 | 当前请求明确点名后才使用 |
| 依赖 active file | 可能改错目标 | 所有自动化传精确 Vault 相对路径 |
| 用普通 `mv` 移动笔记 | 链接和索引可能失效 | 使用逐文件 `obsidian move` 并审计 |
| 全库盲目正则替换中文路径 | 可能产生乱码、重复或混合前缀 | UTF-8、小批、最长路径优先、逐批验证 |
| 为 Graph 连线给每个关键词加链接 | 产生语义噪声 | 只链接先修、应用、对比、实现和证据 |
| 在多个域复制完整课程 | 内容会漂移且权威不明 | 一个权威页，其他域保留应用解释与链接 |
| 一公式或一术语一页 | 打断推理和学习上下文 | 按可完整回答的问题群组织 |
| 命令成功就宣布系统正确 | 混淆解析、运行和语义证据 | 按证据等级逐层验收 |
| toy/CPU 通过就宣称 GPU/真实模型通过 | 证据越级 | 明确通过层和 `SKIP` 层 |
| 用宽泛 allowlist 消除断链 | 隐藏未来真实错误 | contract 只登记精确教学例外 |
| 自动 commit、push 或同步 | 扩大可见性并可能制造冲突 | 获得明确授权后做精确暂存与交付 |
| 用 reset/clean 解决混合工作树 | 可能永久丢失他人修改 | 停止扩大写入，审阅精确路径并交接 |
