# 数据表示、字节序与对齐

## 本课目标

学完后，你应该能够：

- 区分“位模式”与“这个位模式代表的值”；
- 解释无符号整数、常见二进制补码有符号整数和浮点数的边界；
- 根据给定的字节序还原多字节整数；
- 说明对齐、填充和结构体布局为什么属于 ABI/格式约定，而不是数学必然；
- 判断何时可以读取原生内存，何时必须逐字段编码和解码。

适用场景：读取模型文件、网络协议或二进制日志，理解 C++ 对象布局、SIMD 对齐，以及量化张量为什么需要额外的 scale、zero-point 或分组元数据。

## 1. 位只有 0 和 1，意义来自解释规则

本课面向的现代 macOS/Linux 通用平台通常都是 `CHAR_BIT == 8`，因此下文的 byte 示例统一按 8 bit 讲解。但 C 与 C++ 里的 byte 是“最小可寻址单元”，标准不保证它在每个平台都恰好有 8 bit；需要写这种跨平台代码时，用 `<climits>` 中的 `CHAR_BIT` 核对。协议规范中的 **octet** 则明确指 8 bit。

在上述 8-bit byte 前提下，位模式 `11111111` 本身没有写着“255”或“-1”：

| 解释规则 | 结果 |
| --- | ---: |
| 8 位无符号整数 | 255 |
| 常见的 8 位二进制补码有符号整数 | -1 |
| 八个开关 | 全部打开 |
| 某种文件格式中的字段 | 由格式规范决定 |

因此，复制字节只复制表示，不会自动复制类型、形状、单位或所有权。模型文件中的 32 个字节究竟是 8 个 `float32`、32 个 `int8`，还是压缩后的 4-bit 权重加元数据，必须由文件格式和张量描述共同决定。

## 2. 整数：位宽先决定范围

对一个 `n` 位无符号整数，范围是 `0` 到 `2^n - 1`。8 位无符号整数因此能表示 0 到 255。

现代通用计算机通常用**二进制补码**表示有符号整数。`n` 位补码的常见范围是 `-2^(n-1)` 到 `2^(n-1)-1`；负数比正数多一个，是因为 0 只需要一种表示。

> [!important] 溢出的边界取决于语言和操作
> 固定位宽无符号算术通常可理解为模 `2^n` 环绕，但不能据此假设所有语言的有符号溢出也会安静环绕。C++ 中某些有符号整数溢出会产生未定义行为；文件解析还必须先验证输入范围，不能依靠溢出来“自动截断”。

### 小例子：8 位加法

无符号 `250 + 10` 的数学结果是 260；若运算明确按 8 位无符号模 256 保存，结果为 4。这里变化的不是数学，而是存储宽度和运算规则。

## 3. 浮点数：有限位宽近似实数

常见二进制浮点表示把有限位分给符号、指数和有效数字。它能覆盖很大的数量级，却不能精确表示所有十进制小数。例如 `0.1` 通常只能存为附近的二进制值。

需要同时记住三件事：

- 位宽影响可表示范围和相邻可表示数之间的间距；
- `float16`、`bfloat16` 和 `float32` 即使都是浮点数，指数与有效数字的分配也不同；
- 降低位宽不只“少占空间”，还可能引入舍入、溢出、下溢和累积误差。

完整的误差与稳定性分析见 [[数学/60-数值计算与量化/01-二进制浮点精度与数值稳定性|二进制浮点精度与数值稳定性]]。

## 4. 字节序：多字节值先放哪一端

设一个 32 位整数写成十六进制 `0x12345678`。它由四个字节 `12`、`34`、`56`、`78` 组成：

| 地址从低到高 | 第 0 字节 | 第 1 字节 | 第 2 字节 | 第 3 字节 |
| --- | --- | --- | --- | --- |
| 大端序 | `12` | `34` | `56` | `78` |
| 小端序 | `78` | `56` | `34` | `12` |

大端序把最高有效字节放在最低地址，小端序把最低有效字节放在最低地址。这里讨论的是**字节在内存中的顺序**，不要未经协议说明继续推断单个字节内部的位发送顺序。

CPU 的原生字节序只描述本机怎样解释多字节值。网络协议和文件格式可以规定固定字节序；正确的读写器应遵守格式，而不是把本机内存原样倒进文件后祈祷另一台机器刚好相同。

## 5. 对齐与填充：地址也有“整齐的起点”

许多体系结构和 ABI 希望某类数据从特定倍数的地址开始。例如，一个 4 字节整数常被安排到 4 的倍数地址。这样便于 CPU 用自然宽度访问；某些指令对未对齐访问有额外代价，某些架构或指令甚至要求特定对齐。

考虑字段顺序：1 字节标志、4 字节计数、2 字节版本。在一种常见但**并非跨平台保证**的布局中：

| 偏移 | 内容 |
| ---: | --- |
| 0 | 1 字节标志 |
| 1–3 | 编译器插入的填充 |
| 4–7 | 4 字节计数 |
| 8–9 | 2 字节版本 |
| 10–11 | 末尾填充，使数组中的下一个对象继续满足对齐 |

字段有效数据只有 7 字节，对象大小却可能是 12 字节。改变字段顺序可能减少填充，但真正结果还取决于字段类型、目标平台、编译器选项和 ABI。

> [!warning] 对象布局不是通用文件格式
> 直接保存结构体的整段内存会把字节序、填充、类型宽度甚至未初始化填充字节一起写出。跨编译器、跨平台或长期保存时，应定义字段宽度、字节序、版本和校验规则，并逐字段编码。

## 6. 对齐不等于“越大越快”

对齐有多层含义：

- **类型对齐**让单个标量或对象满足 ABI 要求；
- **缓存行对齐**有时用于减少两个线程写入同一缓存行的伪共享；
- **SIMD 对齐**取决于指令集和编译器生成的加载方式；现代指令常能处理未对齐加载，但跨边界访问仍可能更贵；
- **GPU 合并访问**关注一组线程访问的地址能否组合成少量内存事务，不等同于给每个对象盲目增加填充。

增加对齐会增大对象和工作集，反而可能降低缓存利用率。要以目标 ABI、访问模式和测量结果为依据。

## 7. 量化是“表示协议”，不只是缩短整数

把浮点权重映射到低位宽整数，通常还需要约定：

- scale 如何把整数步长映射回实数范围；
- 是否使用 zero-point 表示非对称零点；
- 每个张量、通道或 group 分别使用哪些参数；
- 累加使用什么更宽的类型；
- 元数据怎样排列、对齐和版本化。

因此“4-bit 模型”不必然精确占用 FP16 的四分之一；打包边界、scale、zero-point、索引和文件头也占空间。数学定义与误差实验见 [[数学/60-数值计算与量化/02-量化Scale-Zero-Point-Group与误差|量化的 Scale、Zero-Point、Group 与误差]]。

GGUF 把这些约定固化为有版本的文件结构与张量元数据；解析器应先验证 magic/version、字段类型、维度乘积、偏移对齐和文件边界，再创建 view。不要把当前编译器的 `struct` 直接映射成文件头。具体格式实验见 [[AI/20-LLM/60-模型格式与量化/03-GGUF结构转换与验证|GGUF 结构、转换与验证]]。

## 练习

1. 写出 `0x0A0B0C0D` 在大端和小端内存中从低地址到高地址的四个字节。
2. 对“1 字节类型、8 字节长度、1 字节标志”三个字段，分别画出 `类型→长度→标志` 与 `长度→类型→标志` 的可能布局。不要猜固定答案：先写明你假设的对齐规则。
3. 设计一个跨平台二进制记录，包含版本号、张量元素类型、元素个数和载荷长度。写明每个字段的固定位宽、字节序、非法范围和版本不兼容时的处理。
4. 解释为什么仅知道“每个权重 4 bit”仍不足以还原量化张量。

## 成功标准

- 你能从字节序表还原整数，不把字节序与单字节内的位序混为一谈；
- 你知道本课假设 8-bit byte，也能说明 C/C++ `CHAR_BIT` 与协议 octet 的边界；
- 你能说明结构体大小为何可能大于字段大小之和；
- 你不会把 C++ 对象原生布局直接当作稳定文件或网络格式；
- 你能列出量化表示至少需要的位宽、scale、分组和累加类型信息。
