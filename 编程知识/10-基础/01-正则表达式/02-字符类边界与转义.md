# 02 · 字符类、边界与转义

## 本课目标

用字符类描述“当前位置允许什么字符”，用锚点和单词边界描述“匹配必须发生在哪里”，并减少常见转义错误。

## 字符类一次消费一个字符

方括号定义字符集合：

```regex
[abc]
```

它匹配一个 `a`、`b` 或 `c`，不是字符串 `abc`。常见写法：

| 模式 | 含义 |
| --- | --- |
| `[0-9]` | 一个 ASCII 数字 |
| `[A-Za-z]` | 一个 ASCII 英文字母 |
| `[A-Za-z0-9_]` | 一个 ASCII 单词式字符 |
| `[^,]` | 一个不是逗号的字符 |
| `[-./]` | 一个连字符、点号或斜杠 |

字符类开头的 `^` 表示否定；放在类外通常是行或字符串起点。连字符在字符类中可能表示范围，放在开头、结尾或转义后更不容易产生歧义。

> [!warning] 范围不是自然语言类别
> `[A-z]` 会把 ASCII 中位于 `Z` 与 `a` 之间的符号也包含进来。需要英文字母时写 `[A-Za-z]`。

> [!warning] 严格 ASCII 不要再无意扩大大小写折叠
> `[A-Z]` 与 `[A-Za-z]` 在**不使用扩大 Unicode 大小写折叠的标志**时表示 ASCII 范围。Python 的 `re.IGNORECASE`、JavaScript 的 `/iu` 等组合可能让少量非 ASCII 字符进入匹配。协议白名单若已经写出 `[A-Za-z]`，通常不要再加 `i`；Python 确需忽略大小写时还应核对 `re.ASCII`。

## 预定义字符类

```text
\d  数字字符
\D  非数字字符
\w  单词字符
\W  非单词字符
\s  空白字符
\S  非空白字符
```

这些类别是否只限 ASCII，取决于引擎与 Unicode 模式。若规则必须严格限定协议或文件格式中的 ASCII 数字，`[0-9]` 往往比 `\d` 更明确。Unicode 细节见 [[编程知识/10-基础/01-正则表达式/07-Unicode与引擎差异]]。

## 锚点约束位置

锚点不消费字符，只要求当前位置满足条件：

| 模式 | 常见含义 |
| --- | --- |
| `^` | 字符串开头；多行模式下也可能是每行开头 |
| `$` | 字符串结尾；某些引擎中也可能匹配末尾换行之前 |
| `\A` | 绝对字符串开头；Python/PCRE 支持，不能直接作为 JavaScript 通用语法 |
| `\Z` 或 `\z` | 绝对结尾；拼写、语义与可用版本依引擎而异 |

校验一个仅含 6 位 ASCII 数字的输入：

```regex
^[0-9]{6}$
```

如果 API 提供 `fullmatch` 一类完整匹配方法，优先使用 API 语义，通常比自行猜测 `$` 的换行行为更清晰。

跨语言课程不把 `\A`、`\Z`、`\z` 当成可移植基础语法。2026-09-06 核验时，JavaScript 的 [RegExp Buffer Boundaries 提案](https://tc39.es/proposal-regexp-buffer-boundaries/) 仍标为 Stage 3（页面草案日期 2026-07-10），不能据此宣称所有 JavaScript 运行时已支持。在本次实际运行的 Node 22.16.0 中，`new RegExp("\\A", "u")` 抛 `SyntaxError`；非 Unicode 模式中的 `\A` 还可能被当成字面 `A` 的 identity escape，而不是开头锚点。部署时核对标准、引擎和标志三者，严格校验优先使用明确的完整匹配协议与反例测试。

## 单词边界不是空格

`\b` 表示 `\w` 与 `\W` 之间，或字符串边缘的一个位置：

```regex
\bcat\b
```

它能避免在 `concatenate` 中命中 `cat`。但 `\w` 的定义会随引擎变化，中文、连字符、撇号与 emoji 不一定符合自然语言里的“单词”。处理自然语言分词时，不要把 `\b` 当成通用语言学边界。

## 转义要看所在上下文

正则本体中，常见元字符需要反斜杠才能按字面匹配：

```regex
\. \+ \? \( \) \[ \] \{ \} \\
```

但在字符类中，许多元字符失去特殊含义。例如点号在 `[.]` 中本来就是字面点号。更可靠的做法不是“见符号就加反斜杠”，而是知道当前位于：

1. 正则普通上下文；
2. 字符类内部；
3. 宿主语言字符串；
4. Shell、JSON 或 URL 等更外层编码中。

## 可观察例子：日期形状

```regex
^[0-9]{4}-[0-9]{2}-[0-9]{2}$
```

| 输入 | 匹配？ | 说明 |
| --- | --- | --- |
| `2026-08-31` | 是 | 形状符合 |
| `26-08-31` | 否 | 年份不是 4 位 |
| `2026/08/31` | 否 | 分隔符不同 |
| `2026-99-99` | 是 | 正则只检查形状，不验证真实日期 |

这正是“词法形状”与“业务语义”的边界。真实日期应交给日期库解析并验证。

## 练习

为以下标识符写一个**完整匹配**表达式：

- 必须以 ASCII 字母开头；
- 后面允许 ASCII 字母、数字或下划线；
- 总长度为 3 到 12 个字符；
- `dev_01` 应成功；`1dev`、`ab`、`dev-name` 应失败。

把表达式和四个测试结果写到 [[编程知识/30-实践/01-正则表达式实验区/02-练习场#练习 2 · 标识符|练习场]]。

## 成功标准

- 我能解释字符类为何一次只消费一个字符。
- 我能区分字符类外与字符类内的 `^`。
- 我能说明 `\b` 为什么不等于“左右有空格”。
- 我知道 `[0-9]` 与 `\d`、`[A-Za-z0-9_]` 与 `\w` 可能因 Unicode 模式而不同。
