# 采样、停止条件与生成控制

<!-- deep-review-02 -->
> [!tip] 本轮深化：从当前概念继续追问
> 温度和截断先定义实际采样分布。投机接受率必须使用真正提议与目标分布的概率；对未经同样变换的 logits 做校正会破坏分布结论。 深化与验证：[[AI/20-LLM/40-推理/08-投机解码接受拒绝与分布不变性|投机解码接受拒绝与分布不变性]]；[[AI/20-LLM/10-原理/07-语言模型目标分词粒度与评测可比性|语言模型目标分词粒度与评测可比性]]。


## 本课目标

- 区分 greedy、beam search 与随机采样；
- 解释 temperature、Top-k、Top-p 改变的是哪个分布；
- 理解 repetition penalty、logit bias 和处理顺序的实现边界；
- 设计 EOS、stop string、长度和时间等停止条件；
- 记录足够参数，使生成实验可以复核。

## 从 logits 到一个 token

模型对词表中每个候选输出一个 logit。生成控制通常经历四类操作：

```text
原始 logits
  ├─> 约束/偏置/重复惩罚
  ├─> 温度缩放与候选过滤
  ├─> 选择：argmax、采样或搜索
  └─> 停止检查：EOS、stop、长度、时间、外部取消
```

这只是概念顺序。实际引擎可能改变处理器顺序、组合方式和默认值；同名参数也未必语义完全相同。要复现结果，必须记录引擎和版本。

> [!prerequisite] 第一次使用采样与 Softmax 数学前
> Softmax 的指数、对数与数值稳定性见 [[数学/50-信息论/02-指数对数Softmax与LogSumExp|指数、对数、Softmax 与 LogSumExp]]；温度、Top-k、Top-p 的严格定义与手算见 [[数学/30-概率与统计/04-温度Top-k与Top-p采样|温度、Top-k 与 Top-p 采样]]。本页只解释这些变换在生成系统中的位置。

## Greedy：每步选当前最大项

greedy decoding 在每一步选择最大 logit（等价于最大概率）的 token：

$$
y_t=\operatorname*{arg\,max}_{i} z_i.
$$

它通常确定、简单、开销小，适合格式严格或需要低随机性的基线。但“每一步局部最大”不保证整段序列的联合概率最大，也不保证答案正确。若实现、硬件、精度或并列处理不同，即使 greedy 也未必跨环境逐 token 完全一致。

## Beam Search：保留多条候选序列

beam search 不是“把温度调低”，也不是普通随机采样。它在每一步保留若干条累计得分较高的部分序列，再分别扩展：

1. 从当前 $K$ 条候选各取下一 token 候选；
2. 计算扩展后序列的累计对数概率；
3. 按长度惩罚、约束等规则打分；
4. 只保留新的前 $K$ 条，直到结束。

beam width 增大通常会增加计算、KV cache 和管理开销。它在翻译、受约束序列等任务中可能有用，但开放式对话中可能产生趋同、重复或“高概率但平淡”的文本。**搜索更彻底不等于事实更可靠。**

## Temperature：改变相对尖锐程度

温度 $T>0$ 对 logits 做缩放后再 Softmax：

$$
p_i(T)=\frac{e^{z_i/T}}{\sum_j e^{z_j/T}}.
$$

- $T<1$：分布更尖，偏向高 logit；
- $T=1$：保持原 Softmax；
- $T>1$：分布更平，增加低 logit 候选机会；
- 软件中的 `temperature=0` 常被约定为 greedy，不是把 0 代入公式。

温度只改变候选概率，不会增加模型知道的事实，也不会把不安全输出变安全。

## Top-k 与 Top-p：截断候选集合

- **Top-k**：只保留概率最高的 $k$ 个 token，再归一化；候选数固定，保留概率质量不固定。
- **Top-p**：从高到低累加，保留达到阈值 $p$ 的最小前缀，再归一化；保留质量近似固定，候选数随上下文变化。

温度、Top-k、Top-p 可以组合，但先后顺序会影响结果。比如先降温让分布更尖，Top-p 可能只需保留更少候选。不同库对“最少保留几个 token”、并列、浮点误差和过滤顺序可能有不同约定。

一个小例子：候选概率是 `[0.50, 0.25, 0.15, 0.06, 0.04]`。`top_k=3` 固定保留前 3 个；`top_p=0.80` 保留“累计概率达到或越过 0.80”的最小前缀，因此是前 3 个，不是只保留前 2 个的 0.75。并列和阈值边界仍应以引擎实现为准。

## Repetition Penalty：改变已经出现过的候选

重复惩罚的共同目标是降低某些已出现 token 再次出现的倾向，但并没有一个跨引擎唯一公式。实现可能：

- 对最近窗口或整个已生成序列生效；
- 分别使用 presence penalty 和 frequency penalty；
- 按 token 是否出现或出现次数修改 logits；
- 对正负 logits 采用不同乘除规则；
- 在 temperature 或 Top-k/Top-p 之前执行。

惩罚过强会破坏代码变量名、引用、固定短语和必要的语法重复。token 也不等于人眼看到的“单词”，一个词可能拆成多个 token，因此不能按文字直觉预测惩罚效果。

## Logit Bias 与硬约束

logit bias 通常给指定 token 的 logit 加一个值：

$$
z'_i=z_i+b_i.
$$

正值提高相对机会，负值降低；极端负值有时被用作近似禁止。但要注意：

- 字符串可能有多个 tokenization，包括前导空格、大小写和 Unicode 变体；
- “禁止一个 token”不等于禁止同义表达；
- 极端数值可能被实现裁剪，或与其他处理器交互；
- 真正的 JSON/schema/语法约束通常需要按允许 token 集合做受约束解码，而不是只给少数 token 加 bias。

## 停止条件：模型何时算“说完了”

常见停止条件可同时存在：

| 条件 | 检查对象 | 主要边界 |
| --- | --- | --- |
| EOS token | 新生成 token ID | 模型和 tokenizer 必须匹配；聊天模板可能定义多个终止 token |
| `max_new_tokens` | 新生成 token 数 | 不含或区别于输入长度，具体 API 要核对 |
| 最大总长度 | 输入 + 输出 token | 长提示会挤占输出空间 |
| stop token 序列 | token ID 序列 | 比字符串更接近模型层，但 API 未必暴露 |
| stop string | 解码后的文本片段 | 可能跨 token 边界；返回值是否包含 stop 串依实现而异 |
| 时间上限 | 墙钟时间 | 通常只能在安全检查点取消，未必精确到毫秒 |
| 外部取消 | 客户端断开或用户取消 | 服务端是否及时释放 KV cache 必须验证 |

EOS 是模型学会输出的特殊 token，但不能保证每次及时出现，所以生产系统仍需长度、超时和取消上限。反过来，过短的 stop 字符串可能在正常内容中误触发。

### 流式解码不能把 token piece 直接当字符串

tokenizer 返回的 piece 可能是一段字节，单个 token 不一定构成完整 UTF-8 字符。流式层需要缓冲未完整字节，stop string 检查也要允许目标跨 token/piece 边界。同时记录两个量：“模型已选 token”与“客户端已可见文本”；它们在 Unicode 缓冲、网络 backpressure 或 stop 修剪时可能不同步。

## 一张可复现参数卡

```yaml
model_id: 发布者/完整模型名
revision: 固定提交或版本
engine_and_version: 工具与版本
prompt_or_prompt_hash: 提示或可审计摘要
chat_template: 模板来源与版本
seed: 随机种子
decoding: greedy | beam | sampling
temperature: ...
top_k: ...
top_p: ...
repetition_controls: ...
logit_bias: ...
max_new_tokens: ...
eos_and_stop: ...
processor_order: 引擎实际顺序
hardware_and_precision: ...
```

随机种子只控制伪随机流的一部分；并行归约、浮点精度、kernel、batch 组成和软件版本变化都可能破坏逐 token 复现。

## 常见误区

- greedy 是确定性选择规则，不等于“答案确定正确”。
- beam search 优化的是实现定义的序列分数，不是人类偏好或事实性。
- Top-p 0.9 不是“每个 token 至少 90% 概率”，也不是保留词表的 90%。
- repetition penalty 不是语义去重器；它作用于 token/logit 层。
- stop string 不是模型安全边界；应同时有 token、时间、资源和输出验证边界。
- 相同参数名在不同引擎中可能默认值、范围和处理顺序不同。

## 练习

1. 对 logits $(2,1,0)$，写出 greedy 的选择；说明温度升高后 argmax 是否改变，以及采样概率是否改变。
2. 为什么 beam width 为 4 不等于一次生成 4 个独立答案？
3. 设计一个代码生成配置：哪些重复必须允许，哪些停止条件应保留？
4. 某 stop string 是 `END`。列出 token 边界、正常文本误触发和返回内容三个需要验证的问题。
5. 比较两组采样参数时，除参数外还应固定哪些信息？

## 成功标准

- 能把 greedy、beam 和 sampling 放在同一生成流程中比较；
- 能解释 temperature、Top-k、Top-p 分别怎样改变分布；
- 能说明 repetition penalty 与 logit bias 的 token 级边界；
- 能设计至少三层停止保护，并记录引擎版本和处理顺序。
