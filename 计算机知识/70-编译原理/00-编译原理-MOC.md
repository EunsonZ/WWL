# 编译原理 MOC

<!-- ROUND3 NAV START -->
> [!info] 深化课程入口
> [[计算机知识/00-开始/课程地图/12-编译原理-课程地图|编译原理课程]]。原专题与实验在下方继续保留。
<!-- ROUND3 NAV END -->


编译原理研究的不只是“怎样把 C++ 变成机器码”，而是一个更一般的问题：**怎样把一种有明确语义的程序表示，转换成另一种表示，同时保留应当保留的行为，并给出可定位、可验证的失败证据？**

这门课从一个很小的语言开始，贯穿词法、语法、名称与类型、中间表示、控制流、数据流、优化、运行时、代码生成、链接、虚拟机和现代 AI 编译栈。它的目标不是让你背编译器术语，而是让你能回答四类问题：

1. 这一阶段接收什么对象，又产生什么对象？
2. 哪些不变量必须成立，谁负责验证？
3. 一项变换为什么合法；合法又为什么不一定值得做？
4. 当前证据只说明 toy 实现、某个工具版本，还是能说明语言语义本身？

> [!abstract] 学完后的能力
> 你将能从源文本追踪到 token、AST、语义模型、IR、目标文件或字节码；能画出 CFG、检查 SSA、运行一个有限格上的工作列表分析；能区分优化合法性与收益；能解释 ABI、运行时、链接器、VM 和 JIT 的协作；还能把 LLVM、MLIR、`torch.compile` 与 Triton 放进同一张分层地图，而不会把某个框架的当前 API 当成永恒原理。

## 一条端到端机制链

```text
源文件与编译选项
  → 字符/字节流
  → token 流                         lexer
  → CST / AST                        parser
  → 名称绑定、类型与语义模型           semantic analysis
  → 高层/中层/低层 IR                 lowering
  → CFG、SSA 与分析事实                analysis
  → 合法且有收益的 IR 变换             optimization
  → 目标指令、寄存器与对象布局          code generation + runtime contract
  → section、symbol、relocation        object file
  → 可执行文件或共享库                 linker
  → 进程映射与动态绑定                 loader
  → 执行结果、异常、GC 或去优化          runtime / VM / JIT
```

箭头不是“每个编译器都必须落盘这些文件”。有的实现直接在内存中从 AST 解释执行；有的集成汇编器直接产生目标代码；有的运行时在热路径上重新编译；张量编译器还可能保留多层方言并逐步 lowering。课程关心每一层的**语义职责**，不把一种实现布局写成普遍定律。

## 八组必须分开的概念

| 容易混淆的对象 | 正确边界 |
| --- | --- |
| compiler token / parser node / LLM token | lexer token 服务语言语法；AST 节点表达结构；模型 token 是词表中的模型输入单位 |
| grammar / AST / parser algorithm | 文法描述语言；AST 是表示；递归下降、Pratt、LL、LR 是识别并构造表示的方法 |
| name resolution / type checking / runtime lookup | 名称解析确定引用哪个声明；类型检查判断静态是否合法；动态查找发生在执行时 |
| AST / HIR / SSA / machine instruction | 它们服务不同分析与执行层；“都是图”不代表能互换 |
| CFG 合法 / 程序语义正确 | 每块有终结指令、边一致，只说明结构可分析，不说明程序做对了事 |
| optimization legality / profitability | 合法表示行为可保持；收益还取决于目标、输入、布局、硬件和成本模型 |
| compile / link / load / execute | 四个阶段有不同输入、失败位置与证据，退出 0 不能替后续阶段验收 |
| graph capture / graph optimization / kernel lowering / GPU execution | 捕获到图不等于成功融合；生成 kernel 不等于真实 GPU 路径已运行或更快 |

## 配套实践：受控语义与一条 MiniLang 端到端切片

实践 01–08 共享一组受控语义、相同的诊断/不变量语言和彼此相关的教学切片；它们不是一个承诺接口可直接串接的单体实现。各实验为了隔离词法、类型、CFG、字节码、重定位或工具链问题，可以各自使用最小数据结构、输入子集和测试夹具。共同的概念核心是：以 `i32` 模运算与 `bool` 为主，围绕 `let`、赋值、条件、循环、函数、返回与输出讨论；不覆盖指针、并发、文件/网络 I/O、生产级 GC 或真实原生 JIT。

## 安全、版本与恢复边界

- 所有基础实践使用 Python 标准库和合成输入，不下载依赖、不运行不可信源码、不写用户项目。
- LLVM/MLIR 探针只使用机器上已存在的工具；缺失就是可接受的 `SKIP`，不得自动安装或修改系统工具链。
- 构建或临时产物只能进入实践自身的唯一临时目录；运行前核对路径，运行后按 README 的精确步骤清理。
- 17、18 的具体工具行为必须记录核验日期、实际版本、平台和命令；框架默认值和内部 IR 可能变化。
- 不用含未定义行为的程序输出证明语言语义；不把 sanitizer 未报告错误解释为“程序没有 UB”。
- 不为展示 JIT 而生成并执行任意可写可执行内存；本课程用专用化与去优化模拟器解释合同。

- **IR 到进程：**13–15 连接[[计算机知识/30-计算机系统/03-ABI调用约定与静态动态链接|ABI 与链接]]、[[计算机知识/30-计算机系统/06-指令系统汇编与程序执行|ISA 与执行]]和[[计算机知识/30-计算机系统/02-进程虚拟地址空间与内存映射|进程映射]]。
- **编译器到 GPU：**18 连接[[计算机知识/40-并行与异构计算/01-CUDA/10-PyTorch扩展-Triton与llama.cpp后端|PyTorch 扩展、Triton 与 llama.cpp 后端]]；图被捕获或生成 kernel 都不能代替真实 GPU 路径验证。
- **编译器到 LLM 实现：**[[AI/20-LLM/50-实现/06-GGML张量计算图分配器与Backend|GGML 张量、计算图、分配器与 Backend]]展示模型执行图；它与通用编译器 IR 有相似工程问题，但不能混为相同语义对象。

## 结课成功标准

- [ ] 我能为一个错误指出最早可检测阶段，并区分编译、链接、加载与运行失败。
- [ ] 我能解释 compiler token、AST node、IR value 和 LLM token 的不同合同。
- [ ] 我能写出一个小文法，处理优先级/结合性，并解释 parser 的进展与恢复不变量。
- [ ] 我能为名字使用标注 symbol identity，并从约束来源解释一个类型错误。
- [ ] 我能构造基本块与 CFG，检查 predecessor/successor、terminator、dominance 和 SSA 定义使用关系。
- [ ] 我能说明一个数据流分析为何收敛、为何保守，以及它可能在哪些地方不精确。
- [ ] 我会把优化合法性、收益和证据分开，不用一次更快证明普遍性能。
- [ ] 我能区分对象布局、ABI、寄存器、section、symbol、relocation 与进程映射。
- [ ] 我能解释 JIT guard 失败后为什么必须去优化或回退。
- [ ] 我能在记录版本和环境后阅读 LLVM/MLIR/AI 编译栈证据，并诚实标注 `passed`、`skipped` 与未验证层。
