# 实验 L：事务、幂等与并发控制

**从上一实验接过的问题：** [[计算机知识/Kali/07-综合实验/12-实验I多租户字段与动作授权|实验 I]] 只判断一个动作是否允许，不修改数据库。这里把同一初始身份与报告场景放进真实 SQLite 文件，检查“获准后究竟写了什么”和“中间失败时有没有半更新”。

## 模型与输入合同

本实验需要 Python 3.11+ 及标准库 sqlite3，以明确读取 SQLite 错误代码；实际运行版本见验收记录。它比原实验 A–J 的最低 Python 要求更严格，不自动升级解释器。

唯一实现是 [[计算机知识/Kali/07-综合实验/代码/transaction_lab.py|transaction_lab.py]]，模型版本 `transactions-v3.1`；回归用例在 [[计算机知识/Kali/07-综合实验/代码/test_transaction_lab.py|test_transaction_lab.py]]。需要 Python 3.11+ 及标准库 sqlite3，无第三方包、无数据库服务器、无网络监听。CLI 仅使用临时目录，关闭连接后清理临时数据库。

可信主体为 Alice/red/author、Bob/red/reviewer、Carol/blue/reviewer。身份来自固定教学表，**不是 HTTP 认证系统**。报告 17 属于红租户 Alice，初态 draft/0；18 已 submitted/0；19 属于蓝租户；20 是红租户 Bob 自己的报告；21 已 approved/0。原实验 I 数据按字节保留，L 在自己的数据库中初始化独立副本，不把两者拼成一份历史记录。

支持的动作只有 submit 与 approve。提交须为本人对象；审批须为同租户、非对象拥有者的 reviewer。状态合法性和版本相符是另外两个条件。输入 ID 与版本是有界整数，布尔值不按 0/1 接受；幂等键为 1–64 个限定 ASCII 字符。故意排除无限输入与所有业务动作，使边界能被独立检查。

数据库路径由可信调用者提供，`connect` 不是恶意路径沙盒。初始化只面向空白教学数据库，遇到已有表报错，不自动覆盖；初始化本身也不是任意现有库的迁移工具。

## 先画一条成功路径

Alice 对 17 执行 submit，期望版本 0，键 `submit-17`；结果为 submitted/1。Bob 再执行 approve，期望版本 1，键 `approve-17`；结果为 approved/2。每个首次成功动作写一条 events 和一条 requests 记录，所以这条路径最终是两条事件，不是每个客户端尝试都增加一条。

requests 表以 `(tenant, actor, request_key)` 唯一标识一次请求，并绑定对象、动作和期望版本。该键不是访问令牌。重放仍先确认主体及对象范围；原结果是历史请求的返回值，不必等于对象现在的最新状态。

```bash
cd "$HOME/kali-lab/code"
python3 -B transaction_lab.py
```

JSON 中检查 `model`、`sqlite_version`、`operations`、`negative_cases`、`event_count` 与 `final_report_17`。本轮实测最终报告为 approved/2，事件数为 2。其他系统版本应自己运行，不能把本段预期当作你已验证的输出。

## 沿源码看一次事务边界

`connect` 使用 `isolation_level=None`，使例子采用显式 SQL 事务。`transition` 先拒绝已经有调用者事务的连接，避免替调用者提交或回滚无关工作；再校验参数、执行 `BEGIN IMMEDIATE`，读取实际对象、校验授权与状态，然后条件更新并写事件/幂等记录，最后 COMMIT。内部任何一步异常都会 ROLLBACK。[^sqlite][^python]

实验没有把更新函数藏在布尔判断后面。检查点是条件 UPDATE 的 rowcount 为 1；不满足则抛冲突，不补写“成功事件”。写事务开始时发生的 SQLITE_BUSY 也不被改称权限拒绝。

### 先提交，再丢失响应，会发生什么

把 Alice 的首次 submit 想成已经提交，但客户端没收到响应。原样重试同一键时，返回 submitted/1 并标记 replayed，不增加事件。Bob 随后批准后，Alice 再重试原键仍返回首次结果；数据库本身保持 approved/2。用新键重做已经完成的 submit，则因状态不符而拒绝，不把新键当成重新开放状态机的权利。

这段行为支持“在当前数据库与固定权限模型内，相同请求不重复施加该状态转换”，不支持跨服务 exactly-once、无限期去重或动态角色撤销保证。键过期、账本清理、外部副作用和响应包含敏感数据等均未实现。

## 用失败注入检查原子性

```bash
cd "$HOME/kali-lab/code"
python3 -B -m unittest -v test_transaction_lab
```

重点读两个测试名：`test_event_failure_rolls_back_state_and_replay_record` 在写事件前注入 SQLite 临时触发器错误；`test_ledger_failure_also_rolls_back_event` 在写幂等记录时注入错误。测试不是只检查“抛了异常”，还分别读取报告状态、事件数、账本数，确认恢复为 draft/0、0、0。

两个触发器都只作用于测试自己的临时数据库；不连接真实系统。异常触发点不同，能区分“更新还没开始”与“更新已经执行但随后整体回滚”。移除临时故障后再重试，应能正常提交，证明修复没有把功能永久锁死。

## 用两个连接理解并发，不靠碰运气

一个连接执行 `BEGIN IMMEDIATE` 后保持未提交，另一个连接尝试写事务。本实验 `timeout=0`，使冲突立即作为 SQLite 运行错误被观察，不在测试里无限等待或重试。第一连接回滚后，锁条件解除。SQLite 同时只能有一个写入事务的边界与快照/事务模式见官方说明。[^isolation]

这是一种**确定性的交错测试**，不是多线程压力测试。它验证此安排下第二个写入者不能悄悄绕过锁，不证明所有生产调度都无竞态。不要把 SQLite 行为无条件搬成 PostgreSQL 的行锁或隔离级别结论。

## 独立检验与解释错误

演示器只把实际 `SQLITE_BUSY` 归入预期的锁冲突；其他 `OperationalError` 不得改名后作为负例通过。本轮用独立注入的 `SQLITE_IOERR` 复现了旧演示器的宽松归因，随后修正并保留失败输出。未识别的 SQL 错误会使演示失败，而不是伪称拒绝逻辑正常。

测试覆盖同租户成功、跨租户拒绝、自审批拒绝、字段类型、旧版本、错误状态、同键换内容、同字符串不同主体、重连后的幂等记录，以及调用者已有事务不被破坏。SQLITE_BUSY、输入错误、权限拒绝、业务冲突四类分别保留。

某次拒绝并不等于所有表一定没变化，所以每个写入性质都需检查持久状态。反过来，事件数不变也不证明查询权限正确。将这组证据和 [[计算机知识/Kali/03-Web与API安全/08-认证会话越权与API测试|授权矩阵]] 组合，才能覆盖“谁可读什么”与“谁可改变什么”两条主线。

## 自检与迁移

为什么 Alice 重试后拿到 submitted/1，而数据库已 approved/2？响应属于首次请求，当前资源属于后续状态。为什么不同主体使用同一键可以不冲突？唯一键作用域包含主体，但每个动作仍要授权。为什么数据库忙不能算越权测试阴性？它可能在权限判断之前阻断流程。

最后把 submit 换成真实业务动作前，列出模型未覆盖的东西：认证、角色撤销、数据量、外部交付、日志保留、访问审计保护和所选数据库的隔离语义。课堂上的真实事务不等于生产服务已具备这些条件。
