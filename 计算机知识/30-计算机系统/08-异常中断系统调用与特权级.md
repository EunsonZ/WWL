# 异常、中断、系统调用与特权级

## 本课目标

学完后，你应该能够：

- 区分同步异常、外部中断、软件请求进入内核和用户空间信号；
- 解释 trap、fault、abort 等术语为什么必须先看 ISA 或操作系统上下文；
- 从用户态指令开始，逐步画出系统调用入口、参数检查、内核服务与安全返回；
- 说明特权级是 CPU 执行状态，不是 root/普通用户的同义词；
- 区分“进入内核”“保存最小异常上下文”“完整线程上下文切换”；
- 用精确异常解释内核如何决定重试、跳过、终止或向用户空间报告事件；
- 识别 x86-64 与 AArch64 在入口指令、异常级和保存状态上的层次差异。

## 1. 直觉：正常执行流有三种“转向内核”的来源

普通用户程序大部分时间在用户态执行。控制流进入内核通常来自三大类事件：

1. **当前指令自身引发的同步异常**：例如非法指令、权限错误、地址翻译失败或某些算术事件；
2. **与当前指令不同步的外部中断**：例如定时器或设备通过中断控制器通知 CPU；
3. **程序主动请求的系统调用**：经 ISA 的受控入口机制进入内核，并按操作系统的系统调用 ABI 请求受保护操作。

```text
用户态正常执行
  ├─ 当前指令出现问题/需要 OS 协助 ─→ 同步异常
  ├─ 外部设备或定时器到达          ─→ 中断
  └─ 程序主动执行受控入口          ─→ 系统调用
                                      ↓
                        CPU 建立受保护的内核入口状态
                                      ↓
                      内核识别原因、保存上下文并处理
                                      ↓
                  返回原执行流 / 调度别的线程 / 终止或报告
```

三者都可能让 CPU 开始执行内核代码，但原因、可重启位置、优先级和返回语义并不相同。

## 2. 精确定义：异常、中断、trap 与系统调用

### 同步异常（exception）

由当前指令或与其执行直接相关的条件同步产生。给定相同架构状态再次执行，通常能定位到同一指令或明确的后继边界。例如：

- 指令编码无效或当前状态不允许执行；
- load/store 地址未映射或权限不符；
- 某些体系结构定义的除零、断点或对齐事件；
- 在把主动特权入口定义为同步异常或 trap 的 ISA 上，系统调用入口也可属于此类，例如 AArch64 `svc` 与 RISC-V `ecall`。

并非所有“异常”都是程序错误。按需分页的缺页可以是正常机制：内核准备页面后重试指令。系统调用统一使用受控特权入口；有些 ISA 把该入口定义为同步异常或 trap，另一些 ISA 提供专用系统调用控制转移，不能把前一种分类无条件套给所有平台。

### 外部中断（interrupt）

通常由处理器外部或核外异步来源提出，例如定时器、网卡、存储控制器或核间通知。它不由当前正在执行的那条用户指令语义直接要求；硬件会在架构允许的边界接受并保存返回所需状态。

设备完成也不保证“一次操作对应一次中断”。轮询、中断合并、DMA、消息信号中断和控制器策略都会改变通知方式。驱动层主链见 [[计算机知识/20-操作系统/01-Linux/09-设备驱动内核模块与udev|设备驱动、内核模块与 udev]]。

### trap、fault、abort：术语有上下文

教材常把异常进一步分成：

- **fault**：处理后可能从故障指令重试，例如可恢复缺页；
- **trap**：常在指令完成后报告，例如调试断点或某些主动入口；
- **abort**：难以可靠恢复或无法精确定位的严重事件。

这是有用分类，却不能覆盖所有 ISA/操作系统命名。x86 文档有自己的 fault/trap/abort 分类；RISC-V 常把同步事件称 exception、异步事件称 interrupt，并把总称写作 trap；操作系统与语言运行时又可能用 trap 表示别的层次。遇到术语时先确认“谁的文档、哪一层、返回地址指向哪里”。

### 系统调用（system call）

系统调用首先是**操作系统语义类别**：用户空间请求内核服务的受控接口。操作系统的系统调用 ABI 定义系统调用编号、参数放置、返回值与错误规则；它不是任意库函数，也不是“直接调用一个普通内核函数”。

不要把这一 OS 契约与 ISA 入口机制混为一层：ISA 规定某条入口指令怎样造成特权控制转移、记录返回状态并抵达入口；OS syscall ABI 才规定“哪个编号表示哪项服务、参数怎样传、错误怎样编码”。在常见实现中，AArch64 的 `svc` 和 RISC-V 的 `ecall` 从用户态执行时会经**同步异常/trap**路径进入相应向量；x86-64 的 `syscall` 是专用的系统调用控制转移指令。它们都可承载 OS 系统调用，却不自行规定 `write`、文件描述符或参数寄存器协议。一个 OS 也可为不同兼容 ABI 选用不同的封装、编号与入口细节。

## 3. 特权级：限制哪些代码能做哪些事

CPU 提供至少两类执行权限状态：受限的应用状态与可执行特权操作的内核状态。现代操作系统用它们保护：

- 页表和地址空间控制；
- 中断与异常控制状态；
- 设备寄存器或特权系统寄存器；
- 内核代码和内核数据；
- 调度与跨进程资源管理。

在简化 Linux 模型中：

| 概念 | 含义 | 不等于 |
| --- | --- | --- |
| 用户态/用户模式 | CPU 正在受限特权状态下执行应用或用户空间服务 | 普通账号 |
| 内核态/内核模式 | CPU 正在更高特权状态下执行内核代码 | root 账号本身 |
| root/effective UID/capability | 内核用于授权系统调用请求的进程凭据 | CPU 当前特权级 |

root 启动的编辑器仍主要在用户态运行；它请求文件操作时经系统调用进入内核，内核再依据凭据、文件权限、命名空间、安全模块和当前状态作决定。普通账号的进程同样能进入内核处理允许的系统调用，进入内核不代表请求必然获准。

## 4. x86-64 与 AArch64 的特权模型应怎样表述

| 层次 | x86-64 常见 Linux 描述 | AArch64 常见 Linux 描述 |
| --- | --- | --- |
| 用户应用 | 通常在 ring 3 | 通常在 EL0 |
| 操作系统内核 | 通常在 ring 0 | 通常在 EL1 |
| 更高层能力 | x86 还有其他环与虚拟化/系统管理机制，Linux 通常不把普通进程放在 ring 1/2 | EL2 常用于 hypervisor，EL3 属于安全监控等更高层固件语境 |
| 系统调用入口示例 | 64-bit Linux 常用 `syscall` 指令 | AArch64 Linux 常用 `svc` 触发同步异常入口 |
| 返回与状态保存 | 由 ISA 入口机制与内核汇编共同完成 | 由异常级寄存器、向量入口与内核汇编共同完成 |

这些是常见 Linux 映射，不是所有操作系统、虚拟化配置或固件的唯一用法。尤其不要写成“x86 有四个环，所以 Linux 每个服务依次经过四环”，也不要写成“AArch64 EL 数字越高就是普通用户权限越大”。

> [!note] 入口机制与参数协议是两份契约
> 对 AArch64 `svc`、RISC-V `ecall`，ISA 说明它们产生同步异常/trap；对 x86-64 `syscall`，ISA 说明其专用控制转移与状态规则。无论哪一种，**OS syscall ABI** 才指定服务号、参数和返回/错误值的位置。故而不能从“用了 `svc`/`ecall`/`syscall`”直接推出某个寄存器就是第几个参数；也不能把某个 Linux ABI 的寄存器表当作 ISA 通则。

## 5. 一次系统调用的逐步数据路径

用“请求从一个用户缓冲区写出若干字节”作为概念例子。这里不绑定具体寄存器编号：

```text
伪源代码：
result = write(handle, buffer, length)

用户空间封装：
  按当前 OS syscall ABI 放置系统调用编号
  按同一 ABI 放置 handle、buffer、length
  执行当前 ISA/OS 组合所采用的入口机制
```

完整路径：

1. **用户代码准备请求**：语言运行时或 C 库封装把编号和参数放到 ABI 指定位置；封装还可能先做缓冲，因而一次库调用不一定对应一次系统调用。
2. **执行入口指令**：CPU 依据 ISA 配置切换到内核入口，改变特权状态，并保存/提供返回 PC 和必要状态；具体哪些字段由硬件自动保存、哪些由入口汇编保存，依架构而异。
3. **进入受信任入口**：CPU 不能直接采用用户提供的任意内核跳转地址；它从内核配置的入口或向量开始执行。
4. **保存必要上下文**：入口代码保存可能被处理过程改写、但返回用户态仍需恢复的寄存器和状态，建立内核可安全使用的栈/线程上下文。
5. **识别系统调用**：内核读取编号，验证它是否存在，并按 ABI 解释参数。
6. **复制与验证用户数据**：指针只是用户虚拟地址。内核必须检查长度、溢出和访问有效性，并用安全的用户内存访问机制；不能把用户指针当可信内核指针长期保留。
7. **权限和状态检查**：依据进程凭据、对象权限、文件描述符、命名空间、安全策略与对象当前状态决定是否允许。
8. **执行服务**：内核可能完成操作，也可能阻塞当前线程等待 I/O、锁或事件；阻塞时调度器可运行其他线程。
9. **形成结果**：设置返回值或平台约定的错误表示；库封装还可能把原始错误转换为语言/库层形式。
10. **返回检查与恢复**：处理待决信号、调度和架构安全检查，恢复用户上下文，通过特权返回指令回到用户态后继位置。

```text
用户寄存器/用户虚拟地址
          ↓ 系统调用 ABI
受控入口指令 ─→ 内核入口 ─→ 保存上下文
                               ↓
                     编号分派与参数/权限检查
                               ↓
                    VFS / 网络 / 内存 / 进程等子系统
                               ↓
                       驱动与硬件（若需要）
                               ↓
                    返回值、信号、调度决定
                               ↓
                       恢复并返回用户态
```

## 6. 可观察例子：缺页为何可能“出错后继续”

假设用户程序执行：

```asm
load r_value, [r_address]
```

而 `r_address` 位于合法文件映射中，但对应页面尚未驻留：

1. 地址翻译发现当前没有可用页表映射，产生同步缺页异常；
2. CPU 转到内核异常入口，保留可重启该 load 的架构位置与原因；
3. 内核查询进程的虚拟地址区间，确认访问类型与权限合法；
4. 内核取得文件页或分配物理页，必要时等待存储 I/O；
5. 内核更新映射与页表相关状态；
6. 返回用户态并重新执行/继续该 load；
7. 这次地址翻译成功，load 得到数据。

若地址根本不在合法映射中，或用户试图写只读页，内核可能无法修复：它可向进程报告信号或终止执行。具体信号和错误细节属于操作系统 ABI，不由“缺页”两个字单独决定。

这个例子说明：异常是控制转移机制，缺页是异常原因之一；“发生 exception”不等于语言抛出 C++ exception，也不等于机器必然崩溃。

## 7. 中断的逐步路径

以设备完成一次 DMA 后通知 CPU 为概念例子：

1. 设备把数据传到预先安排的内存，并向中断控制器发出事件；
2. 中断控制器按路由、优先级和屏蔽状态把中断呈现给某个 CPU；
3. CPU 在 ISA 允许的架构边界接受中断，保存返回所需状态并进入相应向量；
4. 内核低层入口保存额外上下文，确定中断来源；
5. 处理程序确认/清除设备或控制器状态，记录完成信息，并尽量限制必须立即做的工作；
6. 较重工作可延后到其他内核执行上下文；被唤醒的线程之后继续处理结果；
7. 内核决定返回被中断执行流，或因调度需要运行另一线程。

中断发生时 CPU 可能正在执行用户代码，也可能已经在内核中。具体嵌套、屏蔽、优先级和延后机制属于 ISA 与操作系统实现，不应从一张简图推断“所有中断都立即抢占一切”。

## 8. 上下文保存：三个层次不要混成一次“保存全部”

### 层次 A：硬件异常入口状态

CPU 必须提供足以识别事件并在允许时返回的信息，例如返回 PC、先前特权状态和原因。x86-64 与 AArch64 自动记录的位置和字段不同。

### 层次 B：内核入口保存

入口汇编根据内核约定保存更多通用寄存器、切换或选择安全栈、建立统一 trap frame/寄存器帧。哪些寄存器已由硬件保存、哪些必须软件保存依架构而变。

### 层次 C：调度上下文切换

若当前线程阻塞、时间片处理导致调度，或更高优先级线程就绪，内核还需保存足以以后恢复该线程的调度上下文，并装入另一个线程的上下文、地址空间相关状态等。

```text
进入内核 ≠ 必然切换进程
保存异常返回状态 ≠ 立刻保存机器上所有寄存器和缓存
上下文切换 ≠ 清空全部缓存和内存
```

一个很快完成的系统调用可以在同一线程中进入内核再返回，不发生线程切换。一次定时器中断也可能处理后返回原线程；只有调度器决定换人时，才发生调度上下文切换。

## 9. 精确异常、返回位置与恢复策略

对于精确的同步异常，内核需要知道：

- 哪条指令或哪一个明确边界引发事件；
- 老指令的架构效果是否已经提交；
- 故障指令能否在修复条件后重试；
- 年轻的推测工作是否已从架构状态撤销。

典型策略包括：

| 事件 | 可能处理 | 返回语义 |
| --- | --- | --- |
| 合法按需缺页 | 准备页面、更新映射 | 重试故障访问 |
| 调试断点 | 交给调试机制检查状态 | 从 ISA 定义的位置继续或由调试器决定 |
| 系统调用 | 执行内核服务、设置返回值 | 返回入口指令后的用户位置 |
| 非法指令/权限错误 | 向进程报告、终止或由受控虚拟化机制处理 | 不一定返回原程序 |
| 外部中断 | 服务设备/计时并进行调度判断 | 通常恢复到可继续的被中断边界，或切换线程 |

表中的“可能”非常重要。异常能否恢复由 ISA 语义、内核策略、进程映射和事件原因共同决定。

## 10. 系统调用、库函数、信号与语言异常不是同一物

| 名称 | 所在层次 | 典型含义 |
| --- | --- | --- |
| 库函数 | 用户空间 API | 可能纯计算、缓冲请求，或封装一个/多个系统调用 |
| 系统调用 | 用户—内核 ABI | 受控请求内核服务 |
| 硬件异常 | ISA/CPU 边界 | 当前指令产生同步控制转移 |
| 硬件中断 | ISA/设备边界 | 异步事件通知 CPU |
| POSIX signal | 操作系统进程抽象 | 内核向用户进程报告异步/同步事件的一种机制 |
| C++ exception | 语言与运行时机制 | `throw`/栈展开/`catch`，通常不等同于 CPU 异常 |

例如一次非法用户内存访问可先产生硬件异常，内核判断无法修复，再通过信号把事件报告给进程；C++ 运行时不会因此自动得到一个可 `catch` 的标准 C++ 异常。

## 11. 参数验证与用户指针：特权入口不是信任入口

内核在更高特权状态执行，因此任何来自用户空间的内容都必须视为不可信：

- 系统调用编号可能无效；
- 长度计算可能溢出；
- 指针可能未映射、跨页、权限不符，或在并发中发生变化；
- 文件描述符可能关闭、复用或指向意外对象；
- 权限检查必须绑定实际对象与当前凭据，不能只看调用者声称什么。

“先检查指针再普通解引用”也未必足够，因为检查后状态可能变化。内核使用架构与操作系统提供的受控用户内存访问、复制和异常恢复机制，并避免把用户地址直接当作持久内核所有权。

这也是为何自定义驱动 `ioctl`、内核模块和系统调用接口需要严格审计：入口参数解析错误发生在高权限域，影响远大于普通进程崩溃。

## 12. 虚拟化再加一层，但不推翻基本模型

在虚拟机中，客体用户态进入客体内核仍可遵循用户/内核特权转换；hypervisor 使用更高或独立的虚拟化机制控制第二阶段地址翻译、虚拟中断和敏感操作。某些事件由客体处理，某些会导致 VM exit 交给 hypervisor。

因此“执行了一条特权指令”不一定直接触碰物理硬件，“进入内核态”也不等于进入宿主机内核。分析时要标明当前讨论的是应用、客体内核、hypervisor 还是宿主内核。

## 13. 常见误解

| 误解 | 更准确的说法 |
| --- | --- |
| exception 就是程序崩溃 | 异常是同步控制转移；缺页和系统调用入口也可走受控异常机制 |
| interrupt 与 exception 完全同义 | 中断通常异步来自外部；异常通常与当前指令同步，术语仍需按 ISA 文档确认 |
| trap 永远只指一种事件 | trap 的范围在教材、x86、RISC-V、OS 与调试器语境中不同 |
| root 程序一直运行在内核态 | root 是进程凭据；普通 root 应用仍主要运行在用户态 |
| 调用 C 库函数就一定进入一次内核 | 库函数可能不调用、调用多次或缓冲后再调用系统调用 |
| 每次系统调用都会切换进程 | 会切换特权状态；只有调度器选择另一线程时才发生调度上下文切换 |
| 进入异常就自动保存所有 CPU 状态 | 硬件保存架构规定的入口状态，内核再按需要保存更多上下文 |
| 用户指针检查一次后就可信 | 用户地址和并发状态仍可能变化，必须使用内核的受控访问机制 |

## 练习

1. 把“未驻留但合法的文件页”“未映射地址”“网卡完成 DMA”“程序请求写文件”分别归类为同步异常、外部中断或系统调用，并说明可能的后续动作。
2. 画出系统调用十步路径，在每一步标出谁提供规则：语言库、系统调用 ABI、ISA、内核或设备。
3. 对合法缺页例子，解释为什么返回地址必须允许重试；再对系统调用说明为什么通常返回入口指令之后。
4. 比较“进入内核”和“线程上下文切换”：列出一个进入内核但不换线程的场景，以及一个系统调用阻塞后换线程的场景。
5. 将 x86-64 的 ring 3/ring 0 与 AArch64 的 EL0/EL1 对齐到共同的“用户态/内核态”概念，并写出至少两项不能跨架构照搬的细节。
6. 解释硬件异常、POSIX signal 与 C++ exception 可能形成怎样的处理链，又为什么它们不是同一个机制。

## 成功标准

- 你能按“同步/异步/主动请求”区分异常、中断和系统调用；
- 你能说明 trap/fault/abort 的定义必须绑定具体 ISA 或操作系统文档；
- 你能完整画出用户代码 → 受控入口 → 参数与权限检查 → 内核服务 → 安全返回；
- 你能区分硬件入口保存、内核寄存器帧和调度上下文切换；
- 你不会把 root 与内核态、信号与中断、C++ 异常与硬件异常混为一谈；
- 你能说明 x86-64 与 AArch64 共享特权隔离原则，但入口指令、状态寄存器与异常级命名不同。
