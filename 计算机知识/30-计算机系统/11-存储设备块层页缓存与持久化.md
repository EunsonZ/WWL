# 存储设备、块层、页缓存与持久化

## 本课目标

学完后，你应该能够：

- 用介质与控制器的差异解释 HDD、NAND SSD 和 NVMe 设备的延迟/并行性；
- 画出从 POSIX 文件 I/O、Linux VFS/文件系统、页缓存、块层队列到设备的数据路径；
- 区分 buffered I/O、memory mapping 与 direct I/O 的缓存、对齐、一致性与性能边界；
- 解释 dirty page、writeback、flush/FUA、`fsync` 与目录持久化在链条中的不同职责；
- 设计一个不过度承诺的 crash-consistency 协议，并正确处理 `fsync`/关闭时返回的错误。

适用场景：理解大模型文件加载、数据库 WAL/checkpoint、视频录制与转码输出、日志系统，以及排查“`write` 已成功但断电后数据不在”。

## 1. 一张边界表先防止跨层误解

| 层次 | 它约定/实现什么 | 不能单独保证什么 |
| --- | --- | --- |
| POSIX 文件抽象 | `open`/`read`/`write`、文件偏移、同步 I/O 相关接口的应用可见语义 | 不规定 Linux 页缓存、blk-mq 或 NVMe queue；一次成功 `write` 不自动意味断电持久 |
| Linux 实现 | VFS、具体文件系统、page cache、writeback、block layer/multi-queue、设备驱动 | 确切路径受文件系统、mount 选项、内核版本、device mapper/虚拟化影响 |
| 存储硬件/协议 | 介质读写单元、设备缓存、队列、flush/FUA 命令和断电行为 | 设备若错报完成、忽略 flush、缺少电力保护或经过未知虚拟层，上层同步协议会被削弱 |

“文件已写”至少可能指：应用已复制到库缓冲、内核已接受 dirty page、块层已提交请求、设备已接收到 volatile cache，或介质已达到某个持久域。每个句子的证据和断电后果都不同。

## 2. HDD、SSD 与 NVMe 不在同一个分类维度

### HDD：机械定位使随机 I/O 昂贵

HDD 把数据存在旋转盘片磁性介质上。一次访问通常要经过磁头寻道、等目标扇区转到合适位置，再传输数据。因此：

- 大块连续 I/O 可以更好地摊薄定位成本；
- 大量小块随机 I/O 容易被 seek/rotation latency 主导；
- 调度器合并或重排邻近请求可能有明显收益，但还要保留公平性和时限。

### NAND SSD：没有寻道，但有 page/program 与 erase block

NAND flash 通常以 page 为读/编程单位，以更大的 erase block 为擦除单位，不能像 RAM 一样原地随意覆盖。控制器的 Flash Translation Layer（FTL）把逻辑块地址映射到介质上，并处理：

- wear leveling：分散擦写，避免少数块过度磨损；
- garbage collection：整理有效页并回收 erase block；
- over-provisioning：保留额外空间支持替换和整理；
- error correction 与 bad-block management；
- TRIM/discard 线索：上层可告知某些逻辑范围已无有效数据，但这不是立即物理擦除或安全销毁的承诺。

所以 SSD 随机访问通常远快于 HDD，但写放大、garbage collection、SLC cache 耗尽、温控降频与介质老化都能使延迟出现长尾。

### NVMe：主要是一套为非易失存储设计的协议/队列模型

NVMe 常通过 PCIe 连接高速 SSD，使用内存中的 submission/completion queues，支持多队列和深队列。但分类时要注意：

- HDD/SSD 主要描述介质或设备类型；
- SATA/NVMe 主要描述接口/协议和队列模型；
- “NVMe”不自动等于某个 NAND 类型、固定耐久性、固定队列深度，也不保证应用必然比 SATA SSD 快。

小块同步 I/O 可能被应用串行依赖限制，无法用满 NVMe 并行度；大块顺序 I/O 则可能先撞上链路或介质带宽。测量时必须记录 request size、queue depth、read/write mix、是否命中 cache 与尾延迟。

## 3. Linux 存储路径：文件不是直接设备扇区

```text
应用的文件语义
  → POSIX/Linux I/O 接口
  → VFS + 具体文件系统（名字、inode、权限、块映射、一致性协议）
  → page cache / dirty pages / writeback（buffered path）
  → block layer：bio/request、合并/拆分、队列与调度
  → device-mapper/RAID/虚拟层（若存在）
  → 设备驱动：submission/completion queue、DMA、中断/poll
  → controller cache/FTL/media
```

Linux 块层将上层块 I/O 转换为设备可接受的请求，可按设备限制拆分/合并、调度并交给多队列驱动。不同调度器在 HDD 的定位、SSD 并行性、公平性和延迟上取舍不同。不能把某个发行版/设备的默认 scheduler 当作永久 Linux 事实。

路径中还可能有 LVM、加密、RAID、网络块设备、虚拟机和主机缓存。每加一层，就要重新核对 flush、错误传播、对齐与持久域，不能只确认客户机里 `fsync` 返回成功。

## 4. 页缓存：同一文件页的共享内核视图

> [!note] CPU cache 与 page cache 不是一层套一层的同一种 cache
> **page cache** 是内核按文件页管理、驻留在主存中的文件数据视图；**CPU cache** 是硬件按 cache line 暂存主存数据的 L1/L2/L3 等层级。当 CPU 访问某个 page-cache 页时，该页的部分 cache line 可以暂时进入 CPU cache，但不能据此说“page cache 在 CPU cache 里面”或反过来。前者回答“哪个文件页在 RAM、是否 dirty、能否复用”，后者回答“某个 CPU 核如何更快访问近期内存”。

这一区分也给出四条边界：

- **coherence：**在硬件支持一致性的普通主存上，CPU cache coherence 让多个 CPU 核对同一内存位置的读写遵守平台规则；它不把 dirty 文件页写到设备，更不等于断电耐久。对非一致 DMA 或特定设备访问，驱动必须按内核 DMA API 在 CPU 与设备交接缓冲区前后执行所需同步，不能把 CPU 的普通内存屏障当成通用替代品。
- **writeback：**文件系统的 writeback 是把 page cache 中 dirty 文件页沿文件系统、块层、驱动提交到设备；它不是把 CPU L1/L2/L3 “刷到磁盘”的同义词。CPU cache 的正常可见性、内核锁与 DMA 映射同步属于另一套机制。
- **`fsync`：**成功的 `fsync` 请求文件数据和相关元数据跨越 page-cache/writeback 与设备持久化边界，取得该文件抽象的同步结果；它不是让应用直接控制各级 CPU cache，也仍受文件系统、驱动、设备 cache 与供电契约约束。
- **direct I/O 与 DMA：**direct I/O 主要改变文件数据是否经常规 page cache；应用缓冲仍在主存、仍可能被 CPU cache 访问，设备通常仍借 DMA 和 IOMMU 映射读写它。DMA 是否与 CPU cache 硬件一致、是否需要显式同步，由平台与驱动 API 决定；direct 不等于没有缓存、没有复制或已经持久。

### Buffered read

当读取范围已在 page cache 中，内核可从缓存页交付数据；未命中时才发起下层 I/O，等页就绪。顺序访问时，readahead 可预先取后续页；随机访问或工作集过大时，预读可能浪费 I/O 与内存。

### Buffered write

普通 buffered `write` 常将用户字节复制到 page cache 并标为 dirty，便可返回成功。后续 writeback 线路把 dirty page 交给文件系统与块层。好处是：

- 小写可被合并，顺序化更容易；
- 应用可与设备 I/O 重叠；
- 读写与 `mmap` 可复用同一文件页缓存视图。

代价是应用看到“写成功”时，数据可能仍是 dirty memory；dirty 过多时，后续写者可被节流或在不显眼的地方承担 writeback 延迟。“异步写”没有消除成本，只是改变谁在什么时候等。

> [!note] “buffer cache”的语境
> 历史资料常把块设备缓冲称为 buffer cache。现代 Linux 普通文件数据主要统一在 page cache 中，但文件系统元数据和某些 block-buffer 结构仍可出现。阅读旧文章时要确认它说的年代和数据类型。

## 5. `mmap` 不绕过文件系统与页缓存

文件映射建立虚拟地址区间与文件偏移的关系。首次触碰未驻留页时，缺页处理会查 page cache，必要时发 I/O。所以：

- `mmap` 可省去显式循环 `read` 和一些用户缓冲管理，但不意味整个文件立即进 RAM；
- 缺页延迟会在第一次访问的指令位置暴露，随机模式可形成大量故障处理；
- shared mapping 的可见性与回写仍要按 API/文件系统同步规则设计；
- 底层是文件页，不是设备寄存器或物理磁盘扇区的直接指针。

大型模型映射与 RSS/工作集边界回看 [[计算机知识/30-计算机系统/02-进程虚拟地址空间与内存映射|进程虚拟地址空间与内存映射]]。

## 6. Direct I/O：减少 page-cache 参与，不是自动直达介质

Linux 的 direct I/O 通常让文件数据路径绕过或减少 page cache 的常规缓存，使用应用管理的缓冲对接底层 I/O。典型适用场景是数据库自有 cache、大块流式 I/O 或避免对 page cache 的二次污染。但必须保留下列边界：

- 文件 offset、I/O length 和用户缓冲地址常有对齐要求，具体限制受内核、文件系统和设备影响；
- 仍要经过文件系统块映射、块层、驱动、DMA 和设备缓存，“direct”不是 CPU 直接访问 NAND/platter；
- buffered/mmap 与 direct I/O 同时触碰重叠区域时存在一致性、序列化或性能风险，必须依目标文件系统规则设计；
- direct I/O 也不自动表示 synchronous/durable I/O；提交返回、设备完成和稳定介质仍是不同里程碑；
- 小 I/O、重复读或应用 cache 设计不好时，direct I/O 可能更慢。

所以 buffered 与 direct 不是“慢与快”两档，而是由谁管理 cache、谁做合并/预读、内存预算和一致性协议怎样分工。

## 7. Writeback：延后提交，不是已经持久

一个简化的 buffered write 时间线：

| 时刻 | 应用可见状态 | Linux 内核 | 设备/介质 |
| --- | --- | --- | --- |
| t0 | 调用 `write` | 准备文件页和权限/空间检查 | 可完全未参与 |
| t1 | `write` 返回成功 | 页缓存中已有 dirty 数据 | 仍可完全未参与 |
| t2 | 应用继续工作 | writeback 构造块 I/O 并排队 | 可正在执行 |
| t3 | 应用若未同步，不一定知道错误 | 收到 completion 或记录延后 writeback error | 数据可在 volatile cache 或持久域 |

空间不足、介质故障或远程错误可能延后到 writeback/`fsync` 才暴露。应用若只检查初始 `write` 而忽略 `fsync` 和 `close` 可能报告的错误，就会在用户面前虚构成功。

## 8. `fsync`、flush 与 FUA 处在不同层

### 应用层：`fsync` / `fdatasync`

`fsync(fd)` 请求将该文件的 dirty data 以及为恢复它所需的相关元数据推进到同步完成点；`fdatasync` 通常可少同步与数据恢复无关的部分元数据。精确 POSIX/Linux 语义和文件系统支持是设计依据，不应只从函数名猜。

Linux 中还有两个容易遗漏的点：

- 新建、删除或 rename 改变的是目录项；若协议要求崩溃后新名字必须保留，通常还需对相关目录 FD 成功 `fsync`；
- `fsync` 返回错误是协议失败，不能继续对外宣告耐久性。处理方式应保留旧版本、进入降级/停写状态或请求人工处理，取决于业务协议。

### 块/设备层：flush 与 FUA

- **cache flush** 概念上要求设备把先前已确认但仍在 volatile write cache 的数据推到持久域；
- **FUA（Force Unit Access）** 通常表达某次写要求在报告完成时已达指定稳定域，具体能力与实现依协议/设备而定；
- **ordering/barrier** 要求 A 的持久化不能被 B 无意越过，但应用仍要用文件系统提供的正确上层协议，不直接发裸设备命令。

文件系统/块层负责把高层同步语义翻译成适合底层设备的命令与顺序。这条链若途经 RAID controller、USB bridge、虚拟磁盘、网络文件系统或云存储，必须核对每层是否正确传播语义。

> [!warning] `fsync` 不是宇宙级绝对保证
> 在内核、文件系统、驱动、设备和供电链都履行契约时，成功 `fsync` 是应用获得文件持久化语义的关键接口。它不会修复撒谎的设备 firmware、缺少电力保护的 volatile cache、未传播 flush 的虚拟/远程层、内核/硬件缺陷，也不对未同步的其他文件、业务事务或异地备份做承诺。

## 9. 可恢复替换协议：原子可见不等于断电持久

本节只保留理解单文件里程碑所需的最小协议。完整的耐久替换、错误分支、恢复状态与故障注入权威课程在 [[计算机知识/30-计算机系统/13-文件系统布局日志CoW与一致性|文件系统布局、日志、CoW 与一致性]]；不要因本节的简化伪代码而跳过那里的平台与事务边界。

要用新内容替换一个同一文件系统中的配置/小型状态文件，可以从以下伪代码理解协议：

```text
pseudocode: durable-replace attempt

temp = create_new_file_in_same_directory(exclusive = true)
write_all(temp, versioned_payload_with_checksum)
if sync_file(temp) fails:
    keep_old_target_and_report_failure()
rename(temp, target)  # 同文件系统上通常提供命名空间原子替换语义
if sync_directory(parent_of_target) fails:
    report_durability_unknown_or_failed()
```

这条协议的意图是：

1. 永远不在旧文件上就地覆盖半份新内容；
2. 先让新文件内容通过自身的 sync 边界；
3. 再原子改变目录中的可见名字；
4. 最后同步目录项变化。

但它不是可不加条件的通用保证：必须核对目标 POSIX/Linux 平台、文件系统与 mount 语义，不能跨文件系统 rename；还要处理权限、旧临时文件、空间耗尽、并发写者、所有 sync/close 错误和恢复时校验。

多文件事务不能只靠多做几次 rename 获得原子性。通常需要 WAL/journal、版本指针、checksum 和启动恢复程序，并通过断电/崩溃 fault injection 验证每个切断点只出现允许状态。

## 10. 一条常见故障链：过早对外确认

```text
应用将新记录 write 进 page cache
  → write 返回成功，业务就向客户端回答“已持久”
  → dirty page 尚未 writeback，或只到设备 volatile cache
  → 突然掉电/主机崩溃
  → 重启后该记录缺失，或数据与元数据只完成了一部分
  → 客户端已基于假确认执行下游动作，单机数据恢复也无法重建外部世界
```

若应用补了 `fsync` 却忽略其返回值，故障链仍然成立。若替换了文件却没同步目录，数据块可能已持久，但重启后的名字关系仍不是应用协议所期待的状态。

正确做法是先定义确认级别：“已进程内接受”、“已本机同步”、“已冗余副本确认”是不同服务契约。不要用一个含混的“saved”覆盖它们。

## 11. 数据与元数据的一致性

文件系统日志、copy-on-write 或 checksum 可以改善特定失效模式，但名称不等于应用事务保证：

- metadata journaling 可让文件系统结构在崩溃后可回放，却不必然让未同步的最新文件数据存在；
- copy-on-write 可避免直接覆盖原块，仍需根指针/元数据的正确更新顺序和持久化；
- block checksum 能发现部分损坏，不自动拥有可修复的良好副本；
- snapshot 保留某个本机状态，不是隔离故障域的异地备份。

文件系统、mount、inode 与目录项的基础见 [[计算机知识/20-操作系统/01-Linux/03-目录结构挂载与文件系统|目录结构、挂载与文件系统]]，设备到块节点的观察路径见 [[计算机知识/20-操作系统/01-Linux/09-设备驱动内核模块与udev|设备驱动、内核模块与 udev]]。

## 12. 性能分析的最小证据集

说“存储慢”前至少记录：

1. 读/写、顺序/随机、请求尺寸和实际并发/queue depth；
2. buffered、`mmap` 还是 direct I/O，是冷 cache 还是热 cache；
3. 测的是单请求延迟、IOPS、有效带宽、尾延迟还是 durability latency；
4. 路径经过哪个文件系统、mount、device mapper/RAID/虚拟/网络层；
5. CPU、内存带宽、页错误、锁、writeback throttling 或设备是谁先饱和；
6. 测试是否误用 page cache 带宽代替存储带宽，或用异步提交时间代替真实 completion/durability 时间。

存储也是内存层级的更远端，延迟、带宽、工作集和预取的统一分析见 [[计算机知识/30-计算机系统/04-缓存局部性带宽与延迟|缓存、局部性、带宽与延迟]]。

## 练习

1. 对 HDD 和 NAND SSD 分别解释为何“4 KiB 随机读”与“1 MiB 顺序读”的比值可完全不同；不使用任何未测量的固定倍数。
2. 画出 buffered `write` 从用户缓冲到 page cache、writeback、block queue、device cache 和介质的链路，在每个点写下突然掉电的可能结果。
3. 比较 buffered I/O、`mmap` 和 direct I/O 读取一份 40 GiB 模型：记录 page cache、拷贝、缺页、对齐、重复读和内存压力方面各需什么证据。
4. 为一个单文件配置替换写伪代码，明确 temp file sync、same-filesystem rename、directory sync 和每一个错误分支；再说明它为何不是多文件事务。
5. 对“成功 `fsync` 后就绝对不可能丢数据”做分层审查：列出文件系统、块层、驱动、设备 cache、供电、虚拟/远程层和异地故障域的前提。
6. 设计一次 crash fault-injection 表：在“写 temp 后、sync temp 后、rename 后、sync directory 后”切断，为每个点列出允许的重启状态与校验方法。

## 成功标准

- 你能区分介质类型和存储协议，不再把 SSD、SATA 与 NVMe 当作同一类名词；
- 你能画出 POSIX 文件抽象、Linux VFS/文件系统/page cache/块层和实际设备的边界；
- 你能用 cache ownership、alignment、reuse 和 consistency 比较 buffered/direct I/O，而不宣称 direct 必然更快；
- 你能区分 `write` 接受、writeback 提交、设备 completion 和断电持久；
- 你的持久化协议会检查 file sync、rename、directory sync 以及它们的错误，并明确声明底层契约和故障域假设。
