# 01 · 编译器流水线、诊断与可复现构建

## 本课目标

学完后，你能把“程序跑不了”定位到恰当的一层：构建描述、预处理、编译、汇编、链接、装载或运行时；能区分 compiler、assembler、linker、loader、interpreter、VM 与 JIT；还能写出一次构建能被他人复查的最小证据，而不是只说“我这里能过”。

## 直觉：源文件到运行进程不是一次魔法转换

把 `hello.cpp` 交给一个命令，表面上像“一次编译”。实际常是一串输入输出明确的变换：源文件和头文件先组成翻译单元，翻译单元被检查并变成目标代码，多个目标文件和库再组成可执行文件，操作系统最后才把它映射为进程。每个箭头都可能失败；把所有失败叫作“编译错误”会让排查走错路。

```text
源文件 + 头文件 + 构建配置
        │
        ├─ 预处理：展开 include、条件编译、宏
        ├─ 编译：词法/语法/语义检查，生成汇编或中间表示
        ├─ 汇编：汇编文本 → 目标文件（.o/.obj）
        ├─ 链接：目标文件 + 库 → 可执行文件或共享库
        ├─ 装载：OS 建立进程地址空间，装入依赖、重定位、开始执行
        └─ 运行：程序、运行时、解释器或 VM 的实际行为
```

这个图是诊断地图，不要求每种语言或工具链恰好分成这些独立进程。某些编译器驱动会在一次调用中协调前几步；LTO 会把部分优化推到链接阶段；解释型语言也可能先生成字节码。但“输入是什么、谁消费它、产物是什么、在何时失败”仍是可靠问题。

## 1. 名称相近的组件，职责不同

| 组件 | 主要输入 → 输出 | 它负责什么 | 它通常不负责什么 |
| --- | --- | --- | --- |
| 编译器（compiler） | 源/翻译单元 → 汇编、IR 或目标文件 | 把语言规则落实为目标表示，优化与生成代码 | 把所有库的符号拼成最终程序 |
| 汇编器（assembler） | 汇编 → 目标文件 | 编码指令、生成节、符号与重定位记录 | 理解 C++ 类型或跨库依赖图 |
| 链接器（linker） | 目标文件、静态库、共享库信息 → 产物 | 解析符号、选择库成员、布置节、处理重定位 | 在用户机器上创建进程 |
| 装载器（loader） | 可执行文件/共享库 → 进程映像 | 映射段、加载动态依赖、最终重定位并转入入口点 | 修复未定义的编译期符号 |
| 解释器（interpreter） | 源码或字节码 → 执行效果 | 在运行时读取/执行语言表示 | 必须提前生成原生机器码 |
| 虚拟机（VM） | 字节码或 IR → 执行效果 | 定义并实现抽象指令集、内存与运行时契约 | 自动等同于解释执行 |
| 即时编译（JIT） | 热路径的字节码/IR → 本机码 | 在运行时利用实际类型、分支或热点数据生成本机码 | 让语言没有解释器/VM 语义 |

解释器、VM 和 JIT 不是互斥的标签。例如一个 VM 可先解释字节码、收集热点信息，再由 JIT 编译热点；AOT（ahead-of-time）编译则在交付前生成本机代码。重要的是交付物和失败时机：同一段源程序可能在 AOT 构建时被拒绝，也可能在动态语言执行到某条路径时才报错。

关于 C++ 的翻译单元、CMake target 与配置/编译/链接的基本闭环，先复用 [[计算机知识/10-编程语言/02-C++/01-编译链接与CMake|编译、链接与 CMake]]；关于 ABI、静态/动态链接与调用约定，复用 [[计算机知识/30-计算机系统/03-ABI调用约定与静态动态链接|ABI、调用约定与静态/动态链接]]。本课不复制平台专有命令，而建立跨工具链的诊断方式。

## 2. 一次可追踪的最小构建

设项目有两个源文件：`main` 调用 `add`，而 `add` 的定义位于另一个翻译单元。抽象过程如下：

```text
main.cpp + api.hpp  ──compiler──> main.o    （main.o 引用 add）
math.cpp + api.hpp  ──compiler──> math.o    （math.o 定义 add）
main.o + math.o     ──linker────> app
app                 ──loader────> 进程，再从入口点开始运行
```

这里的“声明”和“定义”分处两个输入。编译 `main.cpp` 时，编译器只需要知道 `add` 的声明足以检查调用形式；它不必已经看见定义。链接时才要求在参与链接的对象或库中找到兼容定义。因此下列三种现象不是同一种故障：

| 改动/现象 | 首先可能失败的阶段 | 应先看的证据 |
| --- | --- | --- |
| 头文件不存在，或条件编译选择了错误分支 | 预处理 | include 搜索路径、宏定义、预处理后文本 |
| 把两个参数的调用写成一个参数 | 编译 | 源位置、诊断中的期望类型/重载集合 |
| 只给链接器 `main.o`，漏掉 `math.o` | 链接 | 未定义符号名、target 的源/库列表 |
| 运行时找不到共享库 | 装载或运行初始阶段 | 动态依赖清单、运行环境与产物打包方式 |
| 程序已启动但除零、越界或业务断言失败 | 运行 | 输入、栈、日志、测试与调试信息 |

> [!warning] “成功产出二进制”不等于“程序正确”
> 链接成功只能说明链接器在其规则下完成了符号与重定位工作；它不能证明输入、算法、并发、权限、动态库版本或业务结果正确。反过来，某些动态语言把语法、名称或类型错误留到执行路径被触及时才显现，也不表示没有语言处理阶段。

## 3. 失败分层：从最早的确定性证据开始

排查时先记录**第一个未被后续错误淹没的失败**。一种可复现的顺序是：

```text
1. 固定要构建的 target、源码修订、工作目录与输入。
2. 记录构建系统实际调用的编译/链接命令，而非手写猜测命令。
3. 读取首个错误的阶段、文件、行列、命令与退出码。
4. 最小化地修正同一层的输入或声明；重新运行同一 target。
5. 构建通过后，才进入装载和运行时测试。
```

这不是“永远只看第一行”的教条：预处理错误可能引起大量后续语法错误；一个缺失库会引起许多未定义符号。它的价值在于避免看到一长串输出后同时修改头文件、链接选项和程序逻辑，导致因果关系消失。

### 错误信息也有来源位置

编译器诊断的行和列应指向**源文本的 span**；宏展开、生成文件和 `#line` 指令会使“显示位置”和物理文件位置不同。后续的 [[计算机知识/70-编译原理/02-词法分析正则自动机Unicode与源位置|词法分析、正则自动机、Unicode 与源位置]] 会解释 token、字节偏移、码点/显示列如何影响诊断。不要在看到列号后假设它一定等于 UTF-8 字节数或用户看到的第几个字符。

## 4. 可复现构建：把“环境恰好可用”变成可检查输入

可复现不只指“我能再次按下构建按钮”。最低层的可复查构建至少应写清：

- 源码版本及其未提交差异是否参与构建；
- 构建 target、配置（例如 Debug/Release）和生成器；
- 编译器、链接器、标准库及关键依赖的版本；
- 实际编译/链接参数、目标三元组、包含目录和库搜索路径；
- 影响结果的环境变量、特性开关、代码生成输入和时间/随机源；
- 产物的路径、校验值，以及运行/测试的命令、输入与预期输出。

一个实用的层次是：**可重跑**表示同一台机器可按记录再次运行；**可复查**表示他人能看到实际命令和版本；**字节可复现**表示受控环境下两次构建的产物逐字节相同。最后一层还要处理时间戳、绝对路径、随机种子、压缩元数据、链接顺序和依赖解析；不能由“测试通过”推得。

构建系统是声明依赖图和生成实际命令的协调器，不是编译器的同义词。CMake 的 target 思维、`compile_commands.json` 的证据价值及单/多配置差异已有说明，见 [[计算机知识/10-编程语言/02-C++/01-编译链接与CMake|编译、链接与 CMake]]。机器码、指令、入口和执行上下文则与 [[计算机知识/30-计算机系统/06-指令系统汇编与程序执行|指令系统、汇编与程序执行]] 相连。

## 错误边界与反例

1. **“链接错误就是编译器坏了”**：未定义符号常由漏链接对象、错误库顺序或 ABI 不兼容造成；重写调用处通常不会补出缺失定义。
2. **“动态库存在就一定能运行”**：装载器还要找到名称匹配、架构兼容且依赖闭包完整的库；加载后初始化代码仍可能失败。
3. **“VM 就是解释器”**：VM 是执行抽象机的环境；它可以解释、JIT 或 AOT 辅助。相反，解释器也可以直接解释源表示而没有公开字节码 VM。
4. **“同一源码 + 同一版本号 = 同一二进制”**：绝对路径、时间、环境、依赖解析和生成工具都可能进入产物。版本号不足以描述构建输入。

## 练习

1. 为上面的 `main.o`/`math.o` 例子画出依赖图，并分别说明“缺头文件”“参数类型不匹配”“漏传 `math.o`”“运行时找不到共享库”在哪一层首次可观察。
2. 选择一个你熟悉项目中的 target，写一份不含秘密的构建记录：源码状态、实际命令、工具版本、产物路径和一条测试命令。区分事实与自己尚未验证的假设。
3. 某程序在开发机能运行，到干净机器报“缺共享库”。列出你要收集的三条装载阶段证据；解释为何再次编译业务代码不一定相关。

## 成功标准

- [ ] 我能给出 compiler、assembler、linker、loader、interpreter、VM 与 JIT 各自的输入、输出和边界。
- [ ] 我能把一个具体失败归到最早可观察阶段，并指出下一条应检查的证据。
- [ ] 我能说明构建系统与编译器不同，并用实际命令而不是印象描述 target 的构建。
- [ ] 我能列出一次可复查构建的关键输入，且不会把“本机通过”误说成字节可复现。
