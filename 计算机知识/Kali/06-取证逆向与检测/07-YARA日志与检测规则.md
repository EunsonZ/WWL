# YARA日志与检测规则

**先修关系：** [[计算机知识/Kali/06-取证逆向与检测/04-文件元数据Binwalk与ExifTool|文件元数据Binwalk与ExifTool]]；[[计算机知识/Kali/00-导航与方法/04-从观察到结论的安全方法|从观察到结论的安全方法]]。

## 规则命中是条件满足，不是意图鉴定

YARA 通过字符串、字节模式和布尔条件描述文件特征。规则匹配回答“输入是否满足本规则”，而不是自动回答“这个文件是不是恶意”。条件太宽容易误报，太窄容易漏报；命名叫 `Malware` 也不会增加证据强度。[^s1]

本包附带 `toy_markers.yar` 和两个无害文本，专门避免使用真实恶意样本。规则要求文件小于 4096 字节且同时出现 `KALI_LAB_MARKER_A`、`KALI_LAB_MARKER_B`。完整规则真源在实验代码目录；此处只解释逻辑，不维护第二份完整副本。

## 一条规则的完整含义包含扫描对象

YARA 命令行可以把目标解释为文件、目录或进程，递归、超时、大小限制和结果选项还会改变实际检查的对象集。因而规则文本只是条件的一部分；完整实验单位还包括对象表示、遍历范围、引擎版本、模块/外部变量及执行是否完成。[^v5-yara-cli]

原创例子：明文文件含教学标记 M，将它压缩成归档后，归档原始字节未必含同样的 M。对归档原始字节未命中，与对解压后成员命中，可以同时正确。它们不是同一输入上的矛盾结果。若只保存文件名，解压前后还可能同名，因此必须按 [[计算机知识/Kali/06-取证逆向与检测/04-文件元数据Binwalk与ExifTool|派生对象身份]] 关联。

“原始字节规则、格式模块条件、日志字段条件”的检查对象也不同：原始字节偏移不能直接当成解压对象偏移；某字符串在文件中存在，不能自动证明其在执行时被使用；日志字段存在则还依赖上游解析与记录政策。不要在看见条件为真后跳过这些表示层。

## 一次正例和一次反例

```bash
yara --version
yara "$HOME/kali-lab/code/toy_markers.yar" \
  "$HOME/kali-lab/fixtures/files/positive.txt"
yara "$HOME/kali-lab/code/toy_markers.yar" \
  "$HOME/kali-lab/fixtures/files/negative.txt"
```

预期正例命中，反例缺少第二个标记而不命中。这里“预期”来自我们设计的条件；本包构建时是否实际调用 YARA 以 [[计算机知识/Kali/90-来源与维护/05-v3深度审阅与变更记录|v3 验收]] 为准，Python 检查文本条件并不等于 YARA 引擎编译通过。再制作一个超 4096 字节但含两个标记的副本，应不命中，因为长度也是成立条件。

不要从正例命中就删掉长度条件，或为让测试全绿把负例改成正例。规则变更应先提出目的，再更新独立的回归集合。外部规则的 `include`、模块和递归扫描范围应先审阅，避免无限扫整个主目录或泄露私密路径。

## 补强：一个规则至少要有边界样本，而不只有正负各一份

本包原规则要求两段标记同时存在且 `filesize < 4096`。应分别验证：只有标记 A、只有标记 B、两个都没有、两个都有但大小恰为 4096、两个都有且大小为 4095。比较运算是严格小于，边界 4096 应不命中。新增 `nocase`、`wide` 或改动逻辑连接词都会改变接受集合，必须回归相应样本；不能只保留原先那一个阳性文件。[^v2-yara]

规则评审还要区分“字符串特征稳定”“目标类别定义稳定”“采集覆盖稳定”。文件命中只能定位该文件满足规则条件；它未必被执行，更不必然造成入侵。日志规则也要检查字段来源、大小写、时区、缺失值和多行事件重组。同名字段在两种采集器中可能不是同一语义，规则迁移需要输入映射与正反例，不能仅把语法转换成功当成检测能力迁移成功。

## 规则条件不满足，与文件根本没扫到是两种阴性

`filesize < 4096` 是本包规则接受集合的一部分；扫描器设置的文件大小上限、超时和输入清单则决定有没有完整执行这次检查。一个 5000 字节文件被规则拒绝，与扫描器在打开它之前跳过，不能记录为同一种证据。YARA 的目录扫描 `--skip-larger`、递归和超时选项应按本机版本核对。[^v3-yaracli]

假设有 100 个获准输入，实际读取并完成规则检查 80 个，另外 15 个因大小跳过、5 个读取失败。零命中只说明那 80 个已完成对象没有满足所用规则，覆盖率是 80%，不是“100 个都安全”。这是原创计数例子，未借用任何产品性能数据。

把每个输入归入完成且命中、完成未命中、跳过、读取失败或超时，并保留规则摘要和扫描设置。某些工具输出不能直接提供完整清单时，应承认未知，不把缺失项塞进未命中。这个合同与 [[计算机知识/Kali/07-综合实验/11-实验H扫描XML差异与不确定性|扫描 XML 的 not_observed]] 完全相连。

### 偏移能帮助定位，但不能单独鉴定意图

命中字符串的偏移、长度、编码修饰符和出现次数有助于解释条件。用 `--print-strings` 等选项时可能输出样本正文，真实数据必须限制分享范围。递归扫描还需审阅符号链接行为与目录边界，不把整个用户主目录作为默认目标。[^v3-yaracli]

不要仅为匹配一份已知样本反复增加特定字节，直到正例通过且负例只剩原来那一份。新增规则应保留无关但相似文件、条件边界和未覆盖类型。测试集中的标签需要独立来源，不能反过来用规则命中给样本定真值再计算“准确率”。本轮未运行 YARA 引擎，原玩具条件的 Python 检查也不升级为引擎验收。

## 指标中的分母决定含义

设 TP 为真正例且被命中，FP 为真负例却被命中，FN 为真正例但未命中，TN 为真负例且未命中。则

$$\mathrm{Precision}=\frac{TP}{TP+FP},\qquad
\mathrm{Recall}=\frac{TP}{TP+FN},\qquad
\mathrm{FPR}=\frac{FP}{FP+TN}.$$

分母为零时应标为未定义，不自动填 0 或 1。我们的两个玩具样本不能估计实际环境性能，只能验证若干条件分支。真实部署中基率很低，即使 FPR 看起来不高，也可能产生大量无关告警；还需评估每日告警数与人工复核成本。

## 补强：为什么“检出率 90%”仍可能让多数告警是误报

以下数字是教学假设，不是任何产品的性能。假设一百万个样本中有 1000 个真阳性，检出率为 90%，对其余 999000 个真阴性样本的误报率为 1%。则真正检出 900 个，误报 9990 个，总告警 10890 个，告警中的真阳性比例为

$$
\mathrm{Precision}=\frac{900}{900+9990}\approx 0.08264.
$$

也就是约 8.26%。这里“真阳性样本”指评估前已有可靠标签的正类样本；不能拿待验证告警当成真实标签。一般地，正类基率为 $\pi$、检出率为 $t$、误报率为 $f$ 时，假设它们适用于同一总体且分母非零，则

$$
P(\text{正类}\mid\text{告警})=\frac{t\pi}{t\pi+f(1-\pi)}.
$$

推导只需把总体分成正类和负类，再分别乘以触发告警的比例。换一个基率，结论就会改变；因此在刻意平衡的测试集得到的精确率，不可直接搬到真实生产流量。对于标签未知的告警，应保留“待判定”，不能算入真阴性来降低误报率。[[计算机知识/Kali/07-综合实验/13-实验J时间线与检测基率|实验 J]] 对分母为零返回缺失值，而非凭空填 0 或 100%。

这张百万样本表还能反向检验概率迁移：先沿[[数学/30-概率与统计/01-概率分布条件概率与贝叶斯关系#贝叶斯公式的推导|Bayes 的分解]]带入 $\pi,t,f$，再去[[AI/10-机器学习与深度学习基础/17-概率校准保形预测与分布偏移#同一检测器的告警与未告警两端|告警与未告警两档后验]]。那里把平衡源总体的 $90/91$ 修正成这里的 $10/121$，也算未告警端；回到本页时回答“固定规则的排名没有变，为何人工队列中误报所占比例变了”。如果扫描对象、规则或类条件误报率变了，先核失效条件，不能仅用新基率修旧分数。

## 检测覆盖率与分类指标应联合报告

沿用本页的混淆矩阵，增加一个独立维度：哪些输入实际完成了检查。原创例子：待查 100 个对象，其中 80 个完成检查；在这 80 个里发现 8 个真实阳性、2 个假阳性。如果其余 20 个因错误跳过，当前可以计算已完成集合中的部分指标，却不能把未完成者全部作为真阴性抬高准确率。

进一步说，若没有独立确定 80 个对象中的真实阴性与漏检数量，就连完整混淆矩阵也尚未得到。告警人工复核能估计这些已复核告警中的精确率，不会自动给出对所有对象的召回率。与 [[计算机知识/Kali/02-信息收集与网络测量/07-漏洞扫描NucleiGreenbone与复核|漏洞扫描候选与风险]] 的关系在这里：工具输出是一组按某条件生成的候选，需要独立标签与范围说明，不能拿输出自身证明自己的检出能力。

## 日志规则与文件规则怎样互补

Sigma 表达日志检测逻辑，具体字段与后端翻译会影响语义；YARA 侧重内容，Suricata 侧重网络规则，Zeek 提供协议分析日志。它们不是简单互换的语法。对同一事件，应把文件摘要、规则版本、主机上下文和网络连接连接起来，而不是堆叠多个“可疑”标签。参见 [[计算机知识/Kali/06-取证逆向与检测/08-SuricataZeek与网络检测|网络检测]]。
