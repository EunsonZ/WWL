# Arch Linux 安装前规划

> [!abstract] 本课目标
> 学完后，你能判断一台机器是否适合安装 Arch Linux，区分 UEFI 与 BIOS 启动，解释 ESP、根、`/home` 和 swap 的角色，选择 ext4 或 Btrfs，写出包含备份、恢复点与双系统边界的安装计划，并在不改写磁盘的前提下核对 Live 环境。

> [!danger] 本课不执行安装，也不改写磁盘
> 分区、格式化、创建加密容器、安装或重写引导程序都会导致数据丢失或系统无法启动。本课**不提供可以直接抹盘的命令**，也不假定你的目标盘叫 `/dev/sda`、`/dev/nvme0n1` 或任何其他名字。真正的写盘操作全部推迟到下一课，并且只有在“目标设备、备份、启动模式和恢复介质”四项都再次核对后才能进行。

## 1. 先判断 Arch 是否适合你

Arch Linux 不是一套“装完就不用管”的固定版本系统。它采用 **rolling release（滚动发布）**：软件包持续更新，通常不需要隔几年重装一个大版本，但使用者必须持续维护同一套系统。

这意味着：

- 定期做完整系统升级，而不是长期只升级某一个包；
- 升级前查看 [Arch Linux News](https://archlinux.org/news/)，留意需要人工干预的公告；
- 理解包管理器、systemd、日志、引导与网络的基本排错方法；
- 保留可启动的安装介质和经过验证的备份；
- 遇到配置文件变化时，由使用者判断如何合并，而不是期待发行版替你决定一切。

Arch 的 DIY 边界也要说清楚：官方安装镜像提供一个 Live 环境和构建系统所需的工具，但不会替你自动决定磁盘布局、文件系统、加密结构、桌面环境、网络管理器和长期维护策略。安装成功只表示“系统能够启动”，不等于无线网、休眠、显卡、备份、声音或安全策略已经配置完整。

如果你需要一台随时可工作的主力机，又无法接受停机排错，先选择更集成化的发行版可能更合适。选择 Arch 应当是因为你愿意理解并维护组成系统的各层，而不是只因为它“看起来更高级”。

### 先在 VM 或备用盘完成一次闭环

第一次安装必须优先在虚拟机或没有重要数据的备用盘练习：

1. 从 ISO 启动；
2. 识别启动模式、网络和目标盘；
3. 完成安装并启动新系统；
4. 模拟一次配置错误；
5. 从安装介质进入救援环境并恢复；
6. 确认自己能解释每个分区和挂载点的作用。

虚拟机可以降低误删真实数据的风险，但不能完全模拟实体机的 Wi-Fi、GPU、指纹、休眠、Secure Boot 和多系统引导。VM 练习通过后，仍应先在备用盘验证真实硬件，再考虑主力盘。

## 2. 硬件与启动方式：安装前必须确认的事实

### 2.1 CPU 架构是 x86_64

官方 Arch Linux 当前支持 **x86_64**。`amd64`、Intel 64 和 x86_64 在这个语境中通常指同一类 64 位 PC 架构；ARM 设备、Apple Silicon 和老旧的 32 位 x86 机器不能直接使用官方 x86_64 安装镜像。

在现有 Linux 系统中可只读检查：

```bash
uname -m
```

预期结果是 `x86_64`。在 Windows 或 macOS 上，应先从系统信息中确认处理器架构，而不是仅凭品牌推断。

### 2.2 UEFI 与传统 BIOS 不是可以混用的标签

固件、启动加载器、kernel、initramfs 与 PID 1 的先后关系见 [[计算机知识/20-操作系统/01-Linux/02-启动链Kernel与systemd|启动链、Kernel 与 systemd]]；本节只负责把其中会改变安装布局和引导方案的选择变成执行前门禁。

| 项目 | UEFI | 传统 BIOS / Legacy / CSM |
| --- | --- | --- |
| 常见分区表 | GPT | MBR 常见；也存在 BIOS + GPT |
| 引导关键结构 | EFI System Partition（ESP） | MBR 引导区或 BIOS boot partition，取决于方案 |
| Live 环境应以何种方式启动 | UEFI 启动项 | Legacy / CSM 启动项 |
| 多系统原则 | 各系统的启动模式应保持一致 | 不要让一个系统用 UEFI、另一个用 BIOS |

在 Arch Live 环境中可以只读检查 UEFI 位数：

```bash
cat /sys/firmware/efi/fw_platform_size
```

- 输出 `64`：以 64 位 UEFI 启动；
- 输出 `32`：以 32 位 UEFI 启动，能选用的引导程序会受限；
- 路径不存在：通常表示当前以 BIOS / CSM 模式启动，但仍要结合固件设置核对。

同一个 U 盘可能在固件菜单中同时出现 UEFI 和 Legacy 两个入口。**Live 环境的启动方式应与计划安装的系统一致。** 如果启动错了，返回固件菜单重新选择，而不是在错误模式下勉强继续。

> [!warning] Secure Boot 是单独的一层
> Arch 官方安装镜像当前不能直接在启用 Secure Boot 的常规配置下启动，安装时通常需要在固件中临时关闭它；安装完成后可以另行规划自己的 Secure Boot 方案。固件选项和官方支持可能变化，执行当天必须重新阅读 Installation guide 的 “Boot the live environment”。关闭 Secure Boot 还可能触发 Windows BitLocker 恢复，因此双系统用户要先保存恢复密钥。

### 2.3 网络是安装依赖，不只是“装完再说”

官方安装流程需要从远程仓库获取软件包，因此 Live 环境必须有可用网络。安装前记录：

- 优先使用有线网络，还是必须使用 Wi-Fi；
- Wi-Fi 芯片是否能被 Live 环境识别；
- 网络是否有网页认证、企业 802.1X、静态地址或代理要求；
- 是否有另一台设备能在安装过程中打开 ArchWiki；
- 是否准备了手机热点或 USB 网卡作为备用路径。

Live 环境中可进行只读或无持久副作用的检查：

```bash
ip link
ping -c 3 ping.archlinux.org
timedatectl
```

`ip link` 用于观察接口；`ping` 用于验证连接和名称解析；`timedatectl` 用于确认时间同步。准确时间对 TLS 与软件包签名验证很重要。

> [!important] Live 能联网，不等于新系统会自动联网
> 安装镜像预先启用了网络相关服务；新安装的系统不会自动继承这套临时配置。你的计划必须写明要安装和启用哪一种网络管理方案，并在重启前验证它已进入新系统。

## 3. 先识别磁盘，再谈分区

Linux 中的块设备名称由硬件类型和发现顺序决定。SATA/SCSI 盘可能显示为 `/dev/sd…`，NVMe 盘可能显示为 `/dev/nvme…`，eMMC 还会是另一种形式。设备名可能在重启、插拔或虚拟机配置变化后改变，因此**绝不能从教程复制设备名**。如果“块设备 → 分区 → 文件系统 → 挂载点 → 路径”的关系还不能口述，先回到 [[计算机知识/20-操作系统/01-Linux/03-目录结构挂载与文件系统|目录结构、挂载与文件系统]]，不要进入写盘步骤。

Live 环境中可以先做只读盘点：

```bash
lsblk -o NAME,PATH,SIZE,TYPE,FSTYPE,FSVER,LABEL,UUID,MOUNTPOINTS,MODEL,SERIAL
```

对每一块候选盘，至少用以下信息交叉确认：

- 容量是否吻合；
- 型号和序列号是否吻合；
- 当前文件系统、卷标和挂载点是什么；
- 是否包含 Windows、macOS、恢复分区或厂商诊断分区；
- 安装 U 盘本身是哪一个设备；
- 目标是整块备用盘，还是现有磁盘中的未分配空间。

把识别结果抄进计划，采用“容量 + 型号 + 序列号 + 当前分区用途”描述目标。`/dev/…` 名称只能作为执行当天再次核对的临时事实。

> [!danger] 在进入下一课之前禁止执行
> 不要在本课运行分区表写入、删除分区、格式化文件系统、初始化 swap、创建 LUKS 容器或安装引导程序的命令。这些动作的共同特点是会改变磁盘元数据或内容，很多无法靠“撤销”恢复。下一课也必须先截取并人工核对 `lsblk` 结果，再把占位符替换成当时确认的精确目标。

## 4. 分区方案：从职责出发，而不是照抄容量

官方安装指南要求至少有一个根文件系统；UEFI 启动还需要 ESP。`/home`、swap 和更复杂的层次是根据需求选择的设计，不是越多越专业。

### 4.1 各区域的角色

| 区域 | 是否必需 | 作用 | 规划重点 |
| --- | --- | --- | --- |
| ESP | UEFI 必需 | 保存 UEFI 可读取的引导文件，通常为 FAT32 | 双系统通常复用已有 ESP；记录挂载点和剩余空间，**不可误格式化** |
| `/` 根 | 必需 | 系统、软件包、日志以及未单独挂载的数据 | 给更新、包缓存、容器和日志留余量 |
| `/home` | 可选独立 | 用户文件与配置 | 独立分区便于某些重装场景，但会固定容量边界；它仍需要备份 |
| swap | 条件选择 | 内存压力缓冲；休眠时还需容纳休眠映像 | 可以是分区、swapfile 或安装后配置 zram；休眠需求会改变设计 |

### 4.2 三种适合写进计划的基线

#### 简单单系统

- UEFI：复用或创建一个 ESP；
- 其余主要空间作为 `/`；
- 先不独立划分 `/home`；
- 根据内存和休眠需求选择 swapfile、swap 分区或 zram。

优点是结构简单、空间不容易在 `/` 与 `/home` 之间失衡，适合第一次 VM 或备用盘练习。

#### 根与 home 分开

- ESP；
- 固定容量的 `/`；
- 其余空间作为 `/home`；
- 另行决定 swap。

它能把用户数据与根文件系统分开，但不会自动提供备份，也不会保护误删。容量估算错误后，重新分配空间可能很麻烦。

#### Btrfs 单文件系统 + 子卷

- ESP；
- 一个 Btrfs 文件系统；
- 用子卷组织根、home、快照等逻辑区域；
- 按 Btrfs 的限制单独规划 swapfile，或使用 swap 分区 / zram。

子卷共享文件系统的可用空间，避免固定分区边界，也便于快照；代价是挂载、快照、恢复和 swap 规则更复杂。

### 4.3 容量不要机械照抄

官方示例只提供最低限度和示意布局，不了解你的软件、游戏、容器、虚拟机、数据集和休眠需求。计划时估算：

```text
根空间 = 基础系统 + 桌面/开发工具 + 包缓存 + 日志 + 容器/VM + 至少一段增长余量
用户空间 = 当前个人数据 + 预计增长 + 本地工作副本
恢复空间 = 快照/临时文件所需余量（快照并不是零成本）
```

如果现有磁盘已经有 ESP，官方指南明确建议复用，而不是再创建一个；但是否扩容、挂载到 `/boot` 还是 `/efi`，还要与所选引导程序和内核文件位置一起决定。

## 5. ext4 与 Btrfs：选择可维护的复杂度

| 维度 | ext4 | Btrfs |
| --- | --- | --- |
| 心智负担 | 传统且相对简单 | 需要理解子卷、写时复制、快照和空间统计 |
| 快照 | 文件系统本身不提供 Btrfs 式快照 | 支持子卷快照，但需要自己设计与清理 |
| 压缩 | 不提供透明压缩 | 支持透明压缩 |
| 数据完整性能力 | 成熟的日志文件系统 | 数据与元数据校验；仍不能替代备份 |
| swapfile | 常规配置较直观 | 有额外限制，必须按 Btrfs 官方页面规划 |
| 典型适用 | 第一次安装、追求简单恢复路径 | 愿意学习快照/子卷并确实会使用其能力 |

第一次练习若没有明确需要，ext4 是很合理的基线。选择 Btrfs 的理由应当是“我会使用并测试快照、压缩或子卷”，而不是“功能更多”。

> [!warning] 快照不是备份
> 同一块盘上的 Btrfs 快照无法应对磁盘损坏、设备丢失、控制器故障或整盘误操作；某些误删和勒索软件也可能同时影响在线快照。真正的备份应有独立副本，重要数据至少保留一份不与安装目标同盘的副本，并实际做过恢复测试。

## 6. 加密：先画层次，再选步骤

Arch 常见的全盘或根分区加密方案以 dm-crypt/LUKS 为基础。概念上的层次可能是：

```text
物理磁盘
└── 分区表
    ├── ESP（通常必须让固件直接读取，因此一般不放进根 LUKS 容器）
    └── LUKS 加密容器
        └── ext4 / Btrfs，或先经过 LVM 再放文件系统
```

加密会改变以下安装环节：

- 解锁口令与密钥如何保管；
- initramfs 中需要哪些 hook；
- 内核命令行如何定位并解锁根；
- 引导程序能读取哪些区域；
- swap 是否也加密，以及休眠如何恢复；
- 忘记口令、头部损坏或设备故障时的恢复能力。

加密保护的是设备关机后数据被直接读取的风险，不会阻止已解锁系统中的恶意软件，也不会替代备份。第一次真实安装若选择加密，应先在 VM 完整演练“正常启动、从 Live 解锁、进入 chroot、更新 initramfs、恢复引导”这条路径，并安全保存恢复信息。

## 7. 双系统：风险集中在共享磁盘与固件状态

双系统不是“在空白处再装一个系统”那么简单。安装前至少处理以下风险：

1. **备份现有系统。** 不只备份文档，还要保存恢复密钥、恢复介质和当前分区布局。
2. **在原系统内缩容。** 例如 Windows 分区优先使用 Windows 自己的磁盘管理工具缩小，得到明确的未分配空间；不要在不理解文件系统状态时从 Live 环境强行缩容。
3. **一致的启动模式。** 现有系统与 Arch 都使用 UEFI，或都使用 BIOS；现代机器通常应保持 UEFI。
4. **识别并保护已有 ESP。** 复用不等于格式化；误格式化会删除其他系统的引导文件。
5. **处理 BitLocker 与设备加密。** 先保存恢复密钥；修改 Secure Boot、固件或分区可能触发恢复验证。
6. **关闭 Windows Fast Startup / 休眠后再共享 NTFS。** 休眠状态的文件系统不应由另一个系统写入。
7. **准备恢复引导。** 固件更新或系统升级可能改变默认启动项；应知道如何从两个系统各自的恢复介质修复。

最安全的初学路径是：Arch 使用独立备用盘，安装时在条件允许的情况下物理断开其他数据盘。笔记本无法断盘时，更应反复用容量、型号与序列号核对目标。

## 8. 备份与恢复点：在写盘之前证明能回来

“我已经复制过文件”不是完整的恢复计划。安装前应有四层准备：

- **数据备份**：个人文件、项目、照片、密钥材料和应用导出；
- **系统恢复材料**：原系统恢复盘、安装介质、许可证或登录恢复方式；
- **启动恢复材料**：Arch ISO、另一台可查文档的设备、固件入口方式；
- **事实记录**：当前分区布局、文件系统、UUID、ESP 内容、加密状态和启动项的截图或文本记录。

备份必须位于安装目标之外。至少抽取几个文件恢复到临时位置并打开，确认副本不是空的、损坏的或仍依赖原盘。对于全盘加密系统，还要确认恢复密钥确实可用，而不是只记得“应该存过”。

建议设置三个明确的停止点：

1. **写盘前**：备份恢复测试通过，目标盘已用四个属性确认；
2. **格式化前**：再次核对分区表，确认只处理新建或明确允许重建的分区；
3. **首次重启前**：网络、用户、sudo、fstab、initramfs 和引导程序都已检查，并保留 Live 环境的救援路径。

任何一项不确定都应停止，而不是“先运行看看”。

## 9. 获取 ISO 并验证来源与完整性

只从 [Arch Linux 官方下载页](https://archlinux.org/download/) 进入镜像与校验信息。下载时保留：

- 与计划日期对应的 x86_64 ISO；
- 该 ISO 的独立 PGP 签名文件；
- 官方页面公布的校验和信息；
- 官方验证说明和签名者密钥指纹的核对路径。

### 校验和与签名回答不同问题

- **校验和匹配**：说明本地文件的字节与公布值一致，能发现传输损坏；
- **PGP 签名有效且签名密钥可信**：进一步验证镜像确由受信任的 Arch 发布者签署；
- 如果镜像、校验和与签名都来自同一个不可信镜像站，攻击者可能一起替换它们，因此签名和密钥信任信息应从官方通道核对。

官方页面会给出随当前版本变化的文件名、签名者和命令。下面只表示验证关系，不应原样复制：

```text
下载得到：<archlinux-日期-x86_64.iso>
官方签名：<同名.iso.sig>
验证目标：用已核对指纹的 Arch 发布密钥验证“签名文件”与“ISO 文件”这一对
成功条件：工具报告签名有效，并且签名密钥指纹与官方发布者信息一致
```

> [!important] 不要把“Good signature”四个字当作全部验证
> 签名工具可能同时警告密钥尚未建立信任。你仍需从独立的 Arch 官方页面核对完整指纹、签名者与当前发布信息。不要从随机教程复制旧版本文件名、短 key ID 或某位过往签名者的邮箱。

本 VM 课程不覆盖制作 USB 安装介质。若要在实体机上安装，执行当天必须从 ArchWiki 官方的 [Prepare an installation medium](https://wiki.archlinux.org/title/Installation_guide#Prepare_an_installation_medium) 入口选择与当前操作系统匹配的方法；写入前独立核对三次：第一次核对目标介质的容量、型号、序列号和可丢失内容，第二次核对将要传给写盘工具的完整设备路径，第三次在确认前再对照“安装介质”与“将要安装 Arch 的目标磁盘”，防止把两者混淆。

## 10. Live 环境只读检查单

从 ISO 启动后，先完成下面的观察，不进行分区和格式化：

```bash
# 1. 架构
uname -m

# 2. 启动模式
cat /sys/firmware/efi/fw_platform_size

# 3. 网络接口、外网与时钟
ip link
ping -c 3 ping.archlinux.org
timedatectl

# 4. 磁盘身份、文件系统和当前挂载
lsblk -o NAME,PATH,SIZE,TYPE,FSTYPE,FSVER,LABEL,UUID,MOUNTPOINTS,MODEL,SERIAL
```

逐项记录结果：

- [ ] `uname -m` 为 `x86_64`；
- [ ] Live 以计划中的 UEFI 或 BIOS 模式启动；
- [ ] 网络可用，系统时间正确；
- [ ] 安装 U 盘与目标盘能够明确区分；
- [ ] 目标盘由容量、型号、序列号和现有内容共同确认；
- [ ] 已识别已有 ESP、恢复分区、加密卷和其他系统；
- [ ] 任何设备名都标注为“仅本次启动观察值”；
- [ ] 没有运行任何会写入磁盘的命令。

如果硬盘没有出现，先检查固件中的存储控制器模式、RAID/VMD 设置和硬件支持文档；不要因为“教程里应该有”就对另一个相似容量的设备动手。

## 12. 成功标准

完成本课时，你应能做到：

- [ ] 用自己的话解释 rolling release 带来的持续维护责任；
- [ ] 说明 Arch 的 DIY 边界，并已在 VM 或备用盘安排完整练习；
- [ ] 确认目标机器是 x86_64，并能区分 UEFI 与 BIOS 启动；
- [ ] 证明 Live 环境网络与时间可用，且知道其配置不会自动进入新系统；
- [ ] 不依赖固定 `/dev/…` 名称，用容量、型号、序列号和现有内容识别目标盘；
- [ ] 为 ESP、根、home 与 swap 作出有理由的选择；
- [ ] 能解释 ext4 与 Btrfs 的主要取舍，并知道快照不是备份；
- [ ] 能画出加密层次，说明解锁、initramfs、swap 与恢复会受到影响；
- [ ] 双系统计划明确保护已有 ESP、恢复分区和加密恢复密钥；
- [ ] 已完成异盘备份并实际抽样恢复；
- [ ] 已从官方渠道获取 ISO、核对校验和并验证签名与完整指纹；
- [ ] 计划中没有把示例设备名当成真实目标，也没有提前运行破坏性命令。
