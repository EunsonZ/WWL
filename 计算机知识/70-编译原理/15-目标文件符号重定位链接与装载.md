# 目标文件、符号、重定位、链接与装载

## 本课目标

学完后，你应该能够：

- 严格区分 section、segment、symbol、relocation、archive 与 shared library；
- 用 `S`（symbol address）、`A`（addend）、`P`（patch place）手工完成一个 toy relocation；
- 解释 PIC、GOT、PLT、TLS 和 debug info 各解决什么问题，以及哪些名字不是跨格式通用语法；
- 区分 link-time symbol resolution、load-time dependency resolution / binding 与运行后的普通函数调用；
- 用同一组抽象比较 ELF、Mach-O 与 PE/COFF，而不把任何一种格式的字段当作“目标文件必然定义”；
- 依据失败发生的阶段，区分编译、链接、加载和运行时故障。

> [!important] 三层抽象
> 下文先建立与格式无关的概念，再用 ELF、Mach-O、PE/COFF 作映射。ELF 的 program header、Mach-O 的 load command、PE 的 import address table 都是真实格式机制，但都不是“所有目标文件必须长这样”的普遍定义。

## 1. 直觉：编译器不能为尚未布局的地址提前猜答案

文件 `caller` 调用另一个文件中定义的 `helper`：

```text
function caller(x):
    return helper(x) + 1
```

编译 `caller` 时，编译器可能知道：

- 这里需要某种 call 指令；
- `helper` 的符号名和 ABI 类型；
- call 编码中的某个字段最终要表示目标地址或相对距离。

它通常还不知道：

- `helper` 最终来自哪个 object 或 library；
- linker 会把双方放到什么地址；
- 目标距离是否能直接编码；
- 动态链接时是否需要间接跳转槽；
- ASLR 后进程中的实际地址。

因此 object file 不只是“未链接的机器码”。它还携带命名、布局候选、未决引用、重定位公式、可见性、调试与异常展开等元数据，让后续阶段能完成工作。

## 2. 七个对象必须分开

| 对象 | 格式无关的精确定义 | 典型消费者 | 它不等于什么 |
| --- | --- | --- | --- |
| section | object/link 阶段按用途、属性和布局规则组织的一段内容与元数据 | assembler、linker、debugger | 进程中必然独立映射的一页或 segment |
| segment / loadable region | loader 按权限、文件偏移、虚拟地址、内存大小等建立映射的区域 | loader、内核 | 一个源文件或一个 symbol |
| symbol | 对定义或引用赋予名字/身份，并附带位置、范围、binding、visibility、type 等属性的记录 | linker、loader、debugger | 地址本身；undefined symbol 尚无最终地址 |
| relocation | 告诉后续工具在何处、按何种公式，用哪个 symbol/section 与 addend 修补或验证字段 | linker、dynamic loader | symbol resolution 本身 |
| archive | 多个成员 object 加索引等元数据组成的静态集合，linker 通常按未满足引用选择成员 | static linker | 一个已经装入进程的 shared library |
| shared library | 可由多个映像复用、带动态依赖/导入导出与运行期重定位信息的链接产物 | dynamic loader、runtime linker | archive 的另一种压缩形式 |
| executable image | 具有入口、可加载区域和依赖信息的最终映像 | loader | 已经运行的进程 |

### section 与 segment 不是一一对应

链接器可能把多个只读 sections 合并进一个只读可执行 segment，把可写数据 sections 合并进另一个可写 segment；零初始化数据可能只记录内存大小而不占同等文件字节。某些不可分配 section（例如部分 symbol/debug 信息）仅供工具读取，运行时不映射。

```text
link-time sections                 load-time regions
------------------                -----------------
code section A  ----\
code section B  -----+----------> read + execute region
read-only constants -/

initialized data ---\
zero-fill data -------+----------> read + write region

debug information ----------------> usually not mapped for execution
```

这是概念图。实际合并、页对齐、权限和命名由格式、linker script/flags 与平台规则决定。

## 3. Section：内容类别与布局输入

常见逻辑类别包括：

- 可执行代码；
- 只读常量；
- 已初始化可写数据；
- 零初始化数据；
- TLS 模板数据；
- relocation、symbol/string tables；
- unwind、exception、constructor 列表；
- debug information；
- target/toolchain 自定义 metadata。

section 通常带有对齐、大小、是否占文件空间、是否需要分配到内存、读写执行属性以及合并/丢弃规则。函数级 section 或 COMDAT-like group 可帮助 dead stripping / identical code folding，但具体机制和选择规则依格式而异。

> [!warning] section 名不是语义本身
> `.text`、`.data` 等名字在很多工具链中常见，却不能替代格式字段和平台约定。自定义名字不自动拥有可执行/可写属性；同名 section 在不同格式中的处理也可能不同。

## 4. Symbol：名字、定义、引用和可见性

一个抽象 symbol record：

```text
symbol = {
    name,
    defined_or_undefined,
    defining_section_or_special_location,
    offset_and_size_if_known,
    kind,
    binding,
    visibility,
    version_or_namespace_information_if_supported
}
```

必须区分：

- **local symbol**：只在当前 object/link unit 内使用；
- **externally visible definition**：可以满足其他输入的引用，但是否导出到动态边界另有规则；
- **undefined reference**：当前 object 使用该名字，期待 linker 或 loader 找到定义；
- **weak / coalescable / tentative 等特殊类别**：冲突和选择规则依 object format、语言 ABI 和 linker 选项，不能只凭“弱符号优先级低”概括所有平台。

源语言的 overload、namespace、泛型实例和内部链接可经 name mangling 或额外 metadata 变成链接层名字。符号名相同也不证明源级类型相容；若两个翻译单元以不兼容声明调用同一 symbol，linker 可能成功，运行仍因 ABI 不匹配而出错。

## 5. Relocation：把“未知地址”变成可审计的补丁公式

一个抽象 relocation record：

```text
relocation = {
    section_containing_patch,
    patch_offset,
    relocation_kind,
    referenced_symbol_or_section,
    addend_explicit_or_encoded_elsewhere,
    field_width_and_overflow_rule_implied_by_kind
}
```

常用记号：

- `S`：最终 symbol address；
- `A`：addend；
- `P`：要修补位置的地址，或 relocation kind 明确定义的基准位置；
- `B`：映像加载基址，某些基址重定位使用；
- `GOT(symbol)`：若该格式/ABI 使用 GOT-like 结构，表示对应槽地址。

不同 relocation kind 可能计算：

```text
absolute:       S + A
pc_relative:    S + A - P
base_relative:  S + A - B
table_relative: GOT(symbol) + A - P
```

公式只是核心，还必须知道写入位宽、右移/缩放、符号扩展、对齐、指令位域拆分、允许范围以及 overflow 时是报错、生成跳板还是放宽指令。

### resolution 与 relocation 的区别

**Symbol resolution** 决定“这个 undefined reference 由哪个定义满足”。**Relocation** 决定“知道所选定义与布局后，怎样修补使用位置”。先选定义，再计算许多对应 relocation；二者不是同义词。

## 6. 手算：两个 toy object 的布局与重定位

输入 `A.object`：

```text
section code_A:
    size = 12 bytes
    alignment = 4

symbol caller:
    defined in code_A at offset 0

symbol helper:
    undefined

relocation call_helper:
    patch is in code_A at offset 4
    kind = PCREL_NEXT32
    target = helper
    addend = 0
    formula = S + A - P_next
```

输入 `B.object`：

```text
section code_B:
    size = 8 bytes
    alignment = 4

symbol helper:
    defined in code_B at offset 0
```

linker 决定布局：

```text
code_A starts at 0x1000
code_B starts at 0x100C
therefore S(helper) = 0x100C

patch field starts at 0x1004
toy relocation explicitly defines P_next = 0x1008
```

于是：

```text
relocated_value
= S + A - P_next
= 0x100C + 0 - 0x1008
= 4
```

检查清单：

1. `helper` 是否恰有一个按当前规则可选择的定义；
2. section 起点是否满足对齐；
3. relocation 的 `P` 定义究竟是字段地址、下一条指令地址，还是别的基准；
4. 结果 `4` 是否满足 32 位有符号范围和该指令编码约束；
5. 写入采用何种字节序与位域布局；
6. 若超范围，target/linker 是否允许 thunk/veneer/long branch，还是必须报错。

这里故意定义了 toy kind `PCREL_NEXT32`，避免暗示 ELF、Mach-O 或 PE 中某个真实 relocation type 都使用同一 `P_next` 规则。分析真实文件必须查对应 target ABI 和 relocation 规范。

## 7. 静态 archive：成员选择不是“把所有文件拼起来”

一个 archive 可抽象为：

```text
archive:
    member_1.object
    member_2.object
    member_3.object
    symbol_to_member_index
```

传统静态链接器通常根据当前未满足引用，从 archive 索引中抽取能提供定义的成员；未被需要的成员不一定进入输出。链接器的扫描顺序、group/rescan 选项和 whole-archive-like 模式会影响选择。

例子：

```text
main.object references parse
archive index says parse is in parser.object
linker extracts parser.object
parser.object newly references report_error
linker may then extract diagnostics.object if rules permit another lookup
```

这解释了为什么 archive 顺序在某些链接模型中会影响 undefined reference，而把同样的 object 全部直接列出又可能成功。archive 本身不是运行时加载单位，也不提供跨进程共享页面。

## 8. Shared library 与动态依赖

shared library 通常是已经完成大部分内部布局的可加载映像，同时保留动态 loader 需要的：

- 依赖库标识与查找信息；
- 导出/导入 symbol 或等价结构；
- 运行时仍需处理的 relocations；
- 初始化/终止入口；
- TLS、unwind、版本与平台 metadata。

静态链接把选中 object 的代码/数据复制或合并进最终映像；动态链接让 executable 记录对 shared library 和 symbol 的依赖，在 load time 或首次使用等时机建立地址绑定。实际“何时绑定”受格式、平台、安全策略和选项影响，不能把 lazy binding 当作所有系统默认。

### Link-time resolution 与 load-time binding

```text
link time:
    read input objects and libraries
    choose definitions visible at this link
    lay out output sections/regions
    apply resolvable relocations
    record remaining dynamic dependencies and relocations

load time:
    map executable and required shared libraries
    locate dependencies according to platform policy
    choose allowed dynamic definitions
    apply required runtime relocations or initialize indirection slots
    prepare TLS, unwind/runtime metadata and initial control transfer
```

链接成功只说明链接器在其规则和输入下形成了输出，不保证部署机器能找到兼容 shared library；加载成功又不保证第一次 lazy-bound 调用、插件加载或实际函数执行必然成功。

## 9. PIC：不要把绝对运行地址写死

**Position-independent code（PIC）**允许代码被装到不同虚拟地址而无需修改大量只读指令字节。常见策略包括：

- 使用 PC-relative 访问可达的本地代码/数据；
- 通过地址表间接访问可能被重定位或 interpose 的全局对象；
- 通过调用 stub/indirection slot 访问外部函数；
- 把少量必须修改的 runtime relocations 放在可写数据区。

PIC 不意味着“没有 relocation”。它通常意味着：编译时采用与位置无关的寻址，使 loader 只处理有限的动态 relocation 或间接表，而不是对每个代码地址做 text relocation。

## 10. GOT 与 PLT：两个常见的 ELF/ABI 名字，不是宇宙通用术语

在许多 ELF ABI 中：

- **GOT（Global Offset Table）**提供地址槽，PIC 可通过相对可达的表项取得最终 global address；
- **PLT（Procedure Linkage Table）**提供外部函数调用 stub，配合动态 symbol binding 和 GOT-like slot；
- binding 可按平台/选项选择 eager 或 lazy，安全加固也可能改变表项何时可写。

概念路径：

```text
data access:
    PC-relative address of GOT slot
    -> load resolved object address from slot
    -> access object

external call:
    call linkage stub
    -> read target function address from indirection slot
    -> if unresolved and lazy binding is enabled, invoke resolver
    -> jump to resolved function
```

Mach-O 与 PE/COFF 有相似目的的 stubs、symbol pointers、import tables / IAT 等机制，但名称、记录、可见性与绑定协议不同。教学时可以比较“间接槽解决地址晚绑定”，不能说它们都是 ELF GOT/PLT。

## 11. TLS：同一个 symbol，每个线程看到不同实例

Thread-local storage 的变量具有每线程实例：

```text
thread 1: tls_counter -> instance_1
thread 2: tls_counter -> instance_2
```

object/shared image 通常携带 TLS 初始化模板与 metadata；loader/runtime 为线程建立 TLS block，并使生成代码能由线程指针、模块标识、offset 或 resolver 找到实例。常见 TLS access model 会依据：

- 变量是否在当前映像内且不可被外部替换；
- 是否可能来自动态加载模块；
- 地址何时可知；
- target ABI 提供何种 thread-pointer 与 relocation。

编译器选择过于乐观的模型，会在 shared library、动态加载或 symbol interposition 场景失效；过于保守则可能增加间接访问和 resolver 成本。具体模型名称和 relaxation 规则依平台，不应跨格式硬套。

## 12. Debug info：描述源级映射，不参与普通 symbol resolution

debug info 可记录：

- 机器地址范围对应的源文件、行列和内联调用链；
- 变量、类型、作用域和位置表达式；
- 编译单元、宏、语言与 producer 信息；
- unwind / call frame 相关信息（它与语言异常、采样和栈回溯的边界依平台而异）。

它可以位于 object/executable 内、被压缩、拆分到 companion file，或发布时 stripped。删除 debug info 通常不应改变普通执行语义，但可能显著降低调试、符号化和崩溃分析能力。

普通 linker symbol 与 debug symbol 也不能混为一谈：动态绑定所需导出若被错误隐藏，不能靠保留调试信息补回；反过来，运行所需最小 symbol records 也不足以还原优化后的局部变量与源级类型。

## 13. Loader：从文件区域建立初始进程状态

一个概念化 loader 流程：

```text
validate executable format, architecture, ABI and integrity policy
choose load addresses subject to platform rules and ASLR
map loadable file regions with required permissions
create zero-filled memory ranges where memory_size > file_size
locate and map required shared libraries
perform required dynamic relocations and symbol binding
initialize TLS and runtime metadata
prepare stack, arguments, environment and auxiliary platform data
run platform-defined initialization sequence
transfer control to entry point/runtime startup
```

segment/region 权限应遵循最小权限原则：可写数据通常不应同时可执行。实际内核与动态 loader 的责任划分、签名/entitlement、代码签名、hardened runtime 与 library search policy 都依操作系统。

ASLR 改变运行地址，因此 crash report 中的地址常需结合映像 load address、build identity 和 debug info 做 symbolication；不能直接把一次运行的绝对地址当成下次运行的固定位置。

## 14. ELF、Mach-O 与 PE/COFF 的概念映射

| 通用问题 | ELF 家族常见机制 | Mach-O 常见机制 | PE/COFF 常见机制 |
| --- | --- | --- | --- |
| object/link-time 内容分组 | section headers / sections | segment 中的 sections，以及相应 load commands | COFF sections 与相关 tables |
| load-time 映射说明 | program headers 描述 loadable segments | load commands 描述 segments、依赖等 | PE headers 与 section table 描述映像布局 |
| 静态 symbol / relocation | symbol tables 与 relocation sections/entries | symbol table、relocation 与 dyld metadata，具体随产物而异 | COFF symbol/relocation；最终 PE 另有 import/export/base relocation structures |
| 动态外部调用/数据 | dynamic symbols、GOT/PLT 等，依 ABI | stubs、lazy/non-lazy symbol pointers、dyld binding metadata 等 | import directory、IAT、export table 等 |
| 基址变化 | PIC 与 dynamic relocations | position-independent code、rebasing/binding/fixups | image base、base relocation table、IAT 等 |
| shared library | shared object | dynamic library | DLL |
| debug info | 常见 DWARF，可内嵌或分离 | 常见 DWARF + dSYM 工作流 | 常见 CodeView/PDB 工作流 |

这张表是导航，不是字段等价表：

- ELF section 与 Mach-O section 的 header 结构不相同；
- Mach-O segment 同时是格式术语，不能凭名字假设其 loader 语义与某个 ELF program segment 完全一致；
- PE 的 RVA、image base 与 file offset 有自己的换算规则；
- COFF object 与最终 PE image 的可用表也不同；
- 同一格式在不同 architecture / OS ABI 上也可定义不同 relocation kinds 和调用惯例。

## 15. 从错误文本判断失败阶段

| 现象 | 最早典型阶段 | 应检查的证据 | 不能直接推出 |
| --- | --- | --- | --- |
| 机器指令操作数组合非法 | assembly / emission | target、指令、立即数、寄存器约束 | 一定是 linker 问题 |
| undefined symbol during final link | link time | 输入 objects、archive 顺序、名称修饰、visibility | 运行机器缺库 |
| duplicate definition | link time | symbol binding、ODR/语言规则、重复输入 | 任意删除一个定义就安全 |
| relocation overflow | link/layout time | kind、S/A/P、距离、代码模型、thunk 支持 | symbol 不存在 |
| dependent shared library not found | load time | 依赖标识、搜索策略、架构、签名/权限 | 源码未编译 |
| symbol not found in loaded library | load/bind time | 实际加载版本、导出/visibility、symbol version | 调用参数 ABI 正确 |
| 第一次调用外部函数时失败 | lazy bind 或运行时 | binding mode、映像版本、错误发生地址 | executable 启动成功就证明所有符号已绑定 |
| 进入函数后崩溃或栈损坏 | runtime / ABI | 调用签名、寄存器保存、栈对齐、unwind | linker 应该能发现类型不匹配 |

阶段判断是排障起点。错误字符串和工具行为依平台变化，应记录 target、格式、linker/loader、完整构建输入与实际加载映像。

## 16. 安全与供应链边界

- loader 搜索路径是代码执行边界；不可信可写目录、当前目录优先和环境变量注入可能加载错误 library；
- symbol interposition、preload-like 机制和插件系统可用于调试，也可改变进程信任边界；
- debug info 可能包含源路径、类型名和构建环境，不应默认公开发布；
- archive/shared library 的名字或版本号不证明其来源与完整性，应结合签名、哈希、构建 provenance 和发布策略；
- writable + executable 映射、text relocation 和永久可写的函数地址槽会扩大攻击面，具体防护依平台；
- stripping 可以减少信息暴露，却不能修复 ABI 不兼容、恶意依赖或内存安全漏洞。

## 17. 常见误解与失败边界

- **“section 就是 segment。”** 前者主要服务 object/link 组织，后者描述 load-time region；可多对一，也有不加载 section。
- **“symbol 就是函数地址。”** symbol 还可能未定义、代表数据/section/TLS，最终地址也可能经间接槽取得。
- **“relocation 就是查找符号。”** resolution 选定义，relocation 按选定定义和布局修补位置。
- **“静态库会整体复制进程序。”** archive 成员常按未满足引用抽取，除非选项要求整体纳入。
- **“动态库只是磁盘更小的 archive。”** 它是可加载映像，涉及导入导出、运行时映射、relocation 和绑定。
- **“PIC 没有 relocation。”** PIC 减少位置依赖与 text relocation，仍可包含 link-time / dynamic relocations。
- **“所有平台都有 GOT/PLT。”** 这是特定 ABI 中的常见命名；其他格式用不同结构实现相似目的。
- **“链接成功说明 ABI 正确。”** linker 通常不能验证跨 object 的全部源级类型与调用合同。
- **“加载成功说明所有调用都已绑定。”** lazy binding、插件和延迟加载可把失败推迟到首次使用。
- **“debug symbol 越多，动态链接越可靠。”** 调试信息和运行期导出是不同数据与策略。

## 练习

### 练习 1：给对象分类

将以下记录归入 section、segment/loadable region、symbol、relocation、archive、shared library metadata 或 debug info，并说明消费者：

```text
read-only bytes holding constants
an undefined name helper
a patch at code offset 12 using S + A - P
a mapping request with read+execute permissions
a source line table
an index from symbol names to member objects
a runtime dependency on another image
```

### 练习 2：手算 absolute 与 PC-relative relocation

给定：

```text
S = 0x2400
A = 8
P = 0x2000
```

分别计算 `S + A` 与 `S + A - P`。若目标字段只有 8 位有符号数，判断第二个结果能否容纳；不能容纳时，只能写“报告 overflow 或使用该 target 允许的放宽/跳板”，不要自行截断。

### 练习 3：archive 成员抽取

设计三个 member objects：`alpha` 定义 `a` 并引用 `b`，`beta` 定义 `b`，`unused` 定义 `u`。主程序只引用 `a`。列出 linker 按需抽取的顺序，并解释为何 `unused` 不进入输出；再比较 whole-archive-like 模式。

### 练习 4：链接时与加载时

为下面四个故障各写一条最小诊断树：

1. final link 报 undefined symbol；
2. 应用启动时找不到 shared library；
3. 应用启动成功，第一次调用插件函数时报 symbol missing；
4. 函数被调用后返回地址附近崩溃。

每棵树必须写出“当前证据能证明什么”和“还不能证明什么”。

### 练习 5：格式映射而非强行等同

选择 ELF、Mach-O、PE/COFF 中任意两种，按以下通用问题做表：

```text
How are link-time content groups described?
How are loadable regions described?
How are external functions imported?
How is base-address movement repaired or avoided?
Where can debug information live?
```

成功条件不是字段名完全对应，而是每行都注明“相似目的”和“不可直接等同的格式细节”。

## 成功标准

- 我能不看提示说清 section、segment、symbol、relocation、archive、shared library 的职责；
- 我能先完成 symbol resolution，再依据明确的 relocation kind 手算 `S/A/P`，并检查位宽与 overflow；
- 我能解释 PIC 仍可有 relocation，GOT/PLT 也不是所有格式的统一名称；
- 我能区分 link-time resolution、load-time binding、lazy first-use binding 与普通运行时调用；
- 我能把同一组抽象映射到 ELF、Mach-O、PE/COFF，同时指出字段、命名和 ABI 不可直接互换；
- 我能从一条错误先判断发生阶段，再选择对应证据，不用“能启动”替代全部动态依赖与 ABI 验证。
