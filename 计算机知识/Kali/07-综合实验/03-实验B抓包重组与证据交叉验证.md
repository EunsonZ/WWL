# 实验B抓包重组与证据交叉验证

**先修关系：** [[计算机知识/Kali/07-综合实验/01-离线实验准备与夹具说明|离线实验准备与夹具说明]]；[[计算机知识/Kali/02-信息收集与网络测量/05-WiresharkTcpdump与Tshark|WiresharkTcpdump与Tshark]]；[[计算机知识/Kali/01-系统与网络基础/06-TCPIP路由DNS与TLS|TCPIP路由DNS与TLS]]。

## 从十帧还原一次请求

使用合成 `http-lab.pcap`。客户端为 `192.0.2.10:40000`，服务器为 `192.0.2.20:8000`；这些是文档用途地址，**不是本次扫描目标**。PCAP 可离线读取，不需发包或管理员权限。先检查摘要，再在已安装 Wireshark/Tshark 的实验机打开。[^s1]

```bash
cd "$HOME/kali-lab/fixtures"
capinfos http-lab.pcap
tshark -r http-lab.pcap -Y 'http.request' \
  -T fields -e frame.number -e http.request.method -e http.request.uri
tshark -r http-lab.pcap -Y 'http.response' \
  -T fields -e frame.number -e http.response.code
```

若端口 8000 未被该版解析器识别为 HTTP，先核对流量字节，再通过 Decode As 或适用的 `-d tcp.port==8000,http` 显式指定解析。这改变解释器选择，不改变原始字节。

## 建立序号账本

十帧依次为：SYN、SYN/ACK、ACK、请求、请求确认、响应、响应确认、服务器 FIN/ACK、客户端 FIN/ACK、最终 ACK。客户端初始序号为 1000，服务器为 5000。SYN 各消耗一个序号，因此请求从 1001 开始。设请求长度为 $q$，响应长度为 $r$，则响应确认客户端序号到 $1001+q$，客户端确认服务器到 $5001+r$；FIN 同样消耗一个序号。[^s2]

`q` 和 `r` 的实际值在 expected.json 中，也能由 TCP payload 的字节长度独立计算。Wireshark 常显示**相对序号**，不要把界面上的 1 当成 PCAP 原始绝对序号1001的矛盾。关闭相对序号显示或读取原始字段后再比较。

在 Follow TCP Stream 中观察请求和响应，不把按帧分段误认为应用消息边界。服务器 HTTP 的 `Content-Length` 只数响应体字节，不包含头部，也不是字符数通用替代。这里响应体是 ASCII JSON，字符与 UTF-8 字节碰巧相同；换成中文就不能等同。

## 三路交叉验证

第一路是十六进制与包头字段；第二路是 Tshark/Wireshark 解析；第三路是 [[计算机知识/Kali/07-综合实验/09-实验代码合同与复现|Python 单元测试]] 的独立长度、校验和与序号检查。附带测试实际通过不代表第二路已经运行：本次构建没有这些 Kali 网络解析器。你完成工具复核后，在自己的 [[计算机知识/Kali/08-模板与速查/02-实验记录模板|实验记录]] 写版本和输出，而不是改写本包历史验收。

再按 [[计算机知识/Kali/06-取证逆向与检测/08-SuricataZeek与网络检测|Zeek]] 生成结构化连接记录，解释为什么十帧只对应一条连接。别把请求数、日志行数和告警数混在一个计数器里。

## 反例与结束条件

复制 PCAP 到 output 并截断副本，测试解析错误应被记录，不能写为“没有流量”。Python 的截断拒绝测试只覆盖本夹具格式，不是通用 PCAP 验证器。完整 PCAP 没有重传、乱序、分片或 TLS，这些都不在本实验观测范围内，不能据此推断真实网络总如此简单。

最终应能用序号解释完整会话、从原字节定位 GET 与状态码、区分解析失败与阴性结果。后续的 [[计算机知识/Kali/07-综合实验/07-实验F从发现到报告复测|报告]] 应引用同一个原始输入摘要。
