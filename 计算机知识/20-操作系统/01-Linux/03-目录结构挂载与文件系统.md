# 03 · 目录结构、挂载与文件系统

## 本课目标

学完本课，你应该能够：

- 从 `/` 出发说清常见 Linux 目录各自的角色，并区分 FHS 规范、发行版约定和本机实际布局；
- 解释“块设备、分区、文件系统、挂载点”是四个不同层次，而不是把它们都叫作“磁盘”；
- 读懂绝对路径与相对路径，并建立 `inode`、`dentry` 和路径解析的初步心智模型；
- 用只读命令查看挂载、文件系统类型、交换空间、容量与 inode 使用量；
- 知道 `/etc/fstab`、UUID、软链接、硬链接和 mount namespace 分别解决什么问题，以及哪些操作暂时不要做。

本课只观察本机状态：**不执行** `mount`、`umount`、`mkfs`、`fdisk`、`parted`、`mkswap`，也不编辑 `/etc/fstab`。这些命令可能让数据暂时不可见、破坏分区或导致下一次启动失败。

## 1. 一棵目录树，不等于一块磁盘

Linux 向程序呈现一棵从 `/` 开始的目录树。`/` 读作“根目录（root directory）”，并不是管理员账户的家目录；管理员账户 `root` 的家目录通常是 `/root`。一条路径会在这棵树中逐段被解析，挂载则可以把另一个文件系统的根接到树中某个已有目录上。

```text
物理/虚拟存储
  └─ 块设备（例如 /dev/nvme0n1）
       └─ 分区（例如 /dev/nvme0n1p2；也可能没有分区）
            └─ 文件系统（例如 ext4、btrfs、xfs、vfat）
                 └─ 挂载到一个既有目录（挂载点，例如 /、/home、/mnt/data）
                      └─ 从 / 可达的一棵路径树
```

这条链不是唯一模型：`tmpfs`、`procfs`、`sysfs` 没有普通磁盘分区；一个文件系统也可能跨多个设备，或同一文件系统出现在多个挂载点。因此先问“我在看的是设备、分区、文件系统，还是挂载点？”比先背命令更重要。

目录挂载的目标通常是一个已存在的目录；Linux bind mount 也支持把一个普通文件挂到另一个普通文件位置，例如本页后面的容器 `/etc/hosts` 单文件观察。见 [mount(8) 的 bind 操作](https://man7.org/linux/man-pages/man8/mount.8.html)。挂载成功后，原来放在该目录里的内容会在该挂载**可见期间被遮住**，并没有自动删除；卸载后才会再次出现。这是排查“文件不见了”的常见线索，也是为什么不能在不理解目标的情况下随意挂载或卸载。

## 2. FHS：目录用途的共同语言

[Filesystem Hierarchy Standard（FHS）3.0](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/index.html) 描述了 Linux/类 Unix 发行版共同遵守或参考的目录用途。它不是“每台机器必有且绝不变”的清单：容器、最小系统、只读系统、Nix 等布局都可能不同；目录还可能是符号链接或独立挂载点。下表用于建立方向感，真实状态以本机的挂载和发行版文档为准。

| 路径 | 主要用途 | 初学者应记住的边界 |
| --- | --- | --- |
| `/` | 整棵文件层级的起点 | 不是 `/root`；一个进程也可能处在不同的根目录或 mount namespace 中。 |
| `/boot` | 启动加载器使用的静态文件；内核和 initramfs 常在此处 | 可能是独立分区，也可能只是根文件系统中的目录。 |
| `/efi` | 常见的 EFI System Partition（ESP）挂载位置 | **不是 FHS 指定的顶层目录。** 有些系统用 `/boot/efi` 或 `/boot`，有些不挂载 ESP。 |
| `/etc` | 仅属于这台主机的系统配置 | 配置不等于可随意编辑；先查发行版文档和相关服务的说明。 |
| `/home` | 普通用户的家目录 | 可以是独立文件系统、网络文件系统，或在某些系统中并不存在。 |
| `/root` | `root` 用户的家目录 | 与根目录 `/` 是两回事。 |
| `/usr` | 大部分用户态程序、库、共享数据等 | 名称不是“用户自己的文件”；软件包通常主要安装在这里。 |
| `/var` | 会随运行而变化、且通常需要跨重启保留的数据，例如日志、缓存、状态、队列 | `/var/cache` 通常可再生成；`/var/lib` 往往是重要应用状态，不能凭名字就删除。 |
| `/tmp` | 临时文件 | 清理时机由系统策略决定，不能把唯一重要数据放在这里。 |
| `/run` | 自本次启动以来的运行时数据，如 PID 文件、套接字、状态 | 通常是内存中的 `tmpfs`，重启后会消失；不要把它当持久配置目录。 |
| `/dev` | 设备节点和特殊文件 | `/dev/sda`、`/dev/nvme0n1` 是访问内核设备的入口，不是“普通文件内容”。 |
| `/proc` | 内核与进程状态的虚拟文件系统（procfs） | 读它像读文件，实则由内核即时提供；内容会随进程和系统状态变化。 |
| `/sys` | 内核设备与驱动模型的虚拟文件系统（sysfs） | 主要用于观察和控制内核对象；很多节点可写，初学阶段只读。 |
| `/mnt` | 临时手工挂载的通用位置 | 适合临时观察或救援环境；不是固定的数据盘目录约定。 |
| `/media` | 可移动介质的挂载位置 | 桌面环境可能自动在其下或其他位置挂载 U 盘。 |
| `/opt` | 附加的、自包含式应用软件包 | 不是所有第三方程序都会放这里；仍须看软件包自己的安装约定。 |
| `/srv` | 本机对外提供服务的数据 | 例如网站、文件服务的数据；具体子目录布局由管理员或发行版决定。 |

### Arch 的 usr merge 例外不是错误

FHS 仍描述 `/bin`、`/sbin`、`/lib` 等历史目录，但不要据此推断每个发行版都把它们作为独立实体。Arch 已完成 usr merge：`/bin`、`/sbin`、`/usr/sbin` 指向 `/usr/bin`，`/lib`、`/lib64` 指向 `/usr/lib`。这是兼容路径，不表示程序有两份。

可只读验证本机是否如此：

```bash
readlink -f /bin /sbin /lib /lib64
ls -ld /bin /sbin /lib /lib64
```

其他发行版、容器镜像和救援环境可能采用不同布局；写脚本时应优先依赖 `PATH`、发行版打包约定或明确的文档，而不是假设 usr merge 必然存在。[ArchWiki 的说明](https://wiki.archlinux.org/title/Frequently_asked_questions)和[Arch 官方迁移公告](https://archlinux.org/news/binaries-move-to-usrbin-requiring-update-intervention/)可供核对。

## 3. 路径如何找到文件：绝对、相对、inode 与 dentry

### 绝对路径与相对路径

以 `/` 开头的是**绝对路径**，从调用进程看到的根目录开始：`/etc/hosts`。不以 `/` 开头的是**相对路径**，从当前工作目录开始：如果当前目录是 `/home/lin/project`，那么 `notes/todo.md` 指向 `/home/lin/project/notes/todo.md`。

```text
.        当前目录
..       父目录
./run.sh 当前目录中的 run.sh
../data  父目录中的 data
/usr/bin/env  从根目录开始，不受当前目录影响
```

路径解析会逐段查找：`/usr/bin/env` 先从该进程所见的 `/` 开始，再依次解析 `usr`、`bin`、`env`。中间任一目录缺少“搜索（目录的执行）”权限就会得到 `Permission denied`；某一段不是目录会得到 `Not a directory`。[`path_resolution(7)`](https://man7.org/linux/man-pages/man7/path_resolution.7.html) 说明了这一规则，也说明了绝对路径和相对路径的起点。

### inode、dentry 与 path：三层名字解析模型

可以把普通文件想成至少有三种不同的“身份”：

- **inode**：文件系统中的对象记录，通常保存类型、权限、所有者、大小、时间戳、链接数以及数据块位置等元数据；inode 本身不保存文件名。
- **目录项（directory entry）**：目录把“一个名字”映射到 inode。Linux 内核会把常用的目录项缓存为 **dentry**（directory entry cache）；dentry 是内核路径查找实现中的缓存对象，不等于磁盘上永远固定的一份文件。
- **path**：对程序而言，一个可解析的路径还要结合目录层级和挂载关系。相同的底层文件系统可以在不同挂载点出现，所以“文件名”和“从哪个挂载点走过去”都重要。

这解释了两件常见现象：改名主要改变目录中的名字映射，不一定移动数据；硬链接可以让多个名字指向同一 inode。可用下面的只读命令把 inode 号和链接数看出来：

```bash
ls -li /etc/hosts
stat -c 'inode=%i links=%h type=%F path=%n' /etc/hosts
```

在容器或某些桌面系统中，`/etc/hosts` 可能被单独挂载，甚至不是通常意义上的磁盘文件；这正是“从观察结果解释，而非死背预期”的例子。

## 4. 文件系统、交换空间与链接

### 常见文件系统概览

| 类型 | 适合先建立的印象 | 注意边界 |
| --- | --- | --- |
| `ext4` | 成熟、通用、带日志（journaling）的 Linux 文件系统；许多系统以它作为默认选择 | 不是“不会损坏”；仍需备份，功能与修复流程要看 `ext4(5)` 和发行版文档。 |
| `btrfs` | 写时复制（CoW）、子卷、快照、校验和等能力常被用于需要灵活布局的系统 | 快照不是异地备份；RAID、压缩、子卷、维护策略有独立的学习曲线。 |
| `xfs` | 面向大容量与并发 I/O 的成熟 Linux 文件系统，常见于服务器场景 | 选择和扩容/维护能力有关；不要把其他文件系统的缩容或修复习惯套过来。 |
| FAT 家族（Linux 常见 `vfat`；另有 exFAT） | 为跨设备、固件或其他操作系统交换数据而常见；EFI System Partition 通常使用 FAT | 不提供完整的 Unix 所有者、权限和硬链接语义；Linux 会用挂载选项呈现部分权限行为。 |

不要只凭“文件系统名”决定方案。是否加密、是否需要快照、断电风险、跨系统兼容、备份/恢复演练和可用工具，往往更决定实际选择。

### swap 不是“另一个可浏览的目录”

**交换空间（swap）** 是内核在内存压力下可使用的页后备空间，常由磁盘专用分区或 swap 文件承载，也可用压缩 RAM 块设备 zram。`/dev/zram0` 用作 swap 时，页主要以压缩形式留在 RAM，以 CPU 压缩/解压开销换较小内存占用；压缩率、元数据与工作负载决定收益，不能承诺无条件扩容。zram 可选 writeback 另需后备设备配置，不能把它与纯 RAM zram 或普通磁盘 swap 混同。见 [内核 zram 文档](https://docs.kernel.org/admin-guide/blockdev/zram.html)。它不作为普通文件系统挂载到目录树，因此不会有一个“进去看看文件”的挂载点。它也不是额外 RAM：访问磁盘通常远慢于内存。

只读查看已启用的交换空间：

```bash
swapon --show
free -h
```

交换空间、休眠、加密和内存压力处理彼此相关；改变它们需要针对当前发行版和启动方案制定计划，本课不配置。

### 硬链接和符号链接

- **硬链接**是同一文件系统内的另一个目录项，指向同一个 inode；删除其中一个名字不会删除对象，直到链接数降为零且没有进程继续打开它。目录通常不允许普通用户创建硬链接，以免破坏目录树结构。
- **符号链接（symlink）**自身是一个很小的特殊文件，内容是另一条路径；它可以跨文件系统，目标不存在时会成为悬空链接。路径解析通常会继续跟随它，而 `lstat` 这类接口可以查看链接本身。

只读观察已有链接而不创建新链接：

```bash
ls -ld /bin /sbin
readlink /bin
stat -c 'inode=%i links=%h type=%F path=%n' /bin /usr/bin
```

## 5. 挂载与 mount namespace：谁看到哪棵树

普通桌面或服务器上，进程通常共享同一份挂载视图；但 Linux 的 **mount namespace** 允许一组进程看到自己的一份挂载列表，因此可以形成不同的单目录树视图。这是容器隔离文件系统视图的基础之一：容器内的 `/`、`/proc`、`/tmp` 看起来可能与宿主不同。

它不是完整安全隔离的同义词：挂载传播、bind mount、设备权限、用户 namespace、内核漏洞和宿主授予的目录都会影响边界。新的 namespace 从已有挂载列表复制开始，之后的挂载变更通常彼此不影响，但带有 shared subtree 的挂载可以传播变化。详见 [`mount_namespaces(7)`](https://man7.org/linux/man-pages/man7/mount_namespaces.7.html)。

只读检查当前 shell 所在的 mount namespace 和挂载视图：

```bash
readlink /proc/self/ns/mnt
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS
findmnt -T /etc/hosts
```

`findmnt -T /etc/hosts` 询问“包含这个路径的挂载是什么”，比凭目录名字猜它属于哪个磁盘更可靠。输出中的 `overlay`、`tmpfs`、`proc`、`sysfs` 也提醒我们：挂载源不一定是块设备。

## 6. 容量、inode 和 UUID：先观察，再做配置

### 容量满与 inode 用尽是两种不同故障

一个传统文件系统既可能因为数据块没有空间而“满”，也可能因为可分配 inode 耗尽而无法创建新文件。后者常发生在产生了海量小文件时：`df -h` 仍显示有空间，创建文件却失败。不同文件系统的 inode 实现与统计方式不同，尤其不能把 ext4 的预分配心智模型机械套给 btrfs；排查时仍应同时看字节容量和 inode 统计。

```bash
df -hT /
df -i /
findmnt -T / -o TARGET,SOURCE,FSTYPE,OPTIONS
```

`df -hT` 观察字节容量和类型，`df -i` 观察 inode；它们只报告已挂载文件系统。若输出看起来与预期不同，先确认路径实际落在哪个挂载点，而不是贸然清理文件。

### `/etc/fstab` 与 UUID

`/etc/fstab` 是由挂载工具读取的静态文件系统描述；它不是自动生成后就可不审阅的配置。典型一行有六列：

```text
# <来源>          <挂载点> <类型> <选项>    <dump> <fsck 顺序>
UUID=<示例 UUID>   /data    ext4   defaults  0      2
```

第一列可写设备路径、`LABEL=`、`UUID=`、`PARTUUID=` 等；第二列是预先存在的挂载点；第三列是类型；第四列是逗号分隔的挂载选项；最后两列分别供 `dump` 和开机时的 `fsck` 顺序使用。实际 systemd 系统修改 fstab 后还可能需要重新加载其生成的挂载单元，具体流程要看本机文档。

相较 `/dev/sdX` 这类可能随硬件探测顺序改变的名字，UUID 通常更稳定，因此常用于 fstab；但**重新格式化会产生新的文件系统 UUID**，克隆磁盘也可能复制 UUID。对 GPT 分区还可使用 `PARTUUID=`，它与文件系统 UUID 不是一回事。[`fstab(5)`](https://man7.org/linux/man-pages/man5/fstab.5.html) 和 [ArchWiki：Persistent block device naming](https://wiki.archlinux.org/title/Persistent_block_device_naming) 都强调了这些差别。

只读检查，不输出或修改完整配置：

```bash
lsblk -o NAME,FSTYPE,LABEL,UUID,MOUNTPOINTS
findmnt --fstab --evaluate -o SOURCE,TARGET,FSTYPE,OPTIONS
findmnt --verify
```

第二、三条会读取 fstab 并检查其可解析性，**不会挂载任何东西**；仍可能显示本机 UUID、卷标和挂载布局，录屏或粘贴到公开位置前应先去除这些环境标识。

## 7. 只读观察清单

以下命令都只读取或显示信息；没有 `sudo`、没有写入、没有挂载动作。个别最小化系统可能未安装其中某个工具，跳过后查相应 `man` 页即可。

```bash
# 当前目录、目录的类型/权限，以及 usr merge 的实际形态
pwd
ls -ld / /boot /efi /etc /home /root /usr /var /tmp /run /dev /proc /sys /mnt /media /opt /srv
readlink -f /bin /sbin /lib /lib64

# 这棵树在哪里接入了哪些文件系统
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS
findmnt -T / -o TARGET,SOURCE,FSTYPE,OPTIONS
findmnt -T /run -o TARGET,SOURCE,FSTYPE,OPTIONS

# 块设备、文件系统、挂载点、交换空间与两种容量指标
lsblk -o NAME,TYPE,FSTYPE,LABEL,UUID,MOUNTPOINTS
swapon --show
df -hT /
df -i /

# 路径与 inode：按你的系统实际存在的普通文件替换 /etc/hosts
stat -c 'inode=%i links=%h type=%F path=%n' /etc/hosts
readlink /proc/self/ns/mnt
```

如果 `/efi`、`/media`、`/opt`、`/srv` 或 `swap` 不存在/为空，通常不代表异常，只表示该机器当前没有采用那个布局或功能。`/root` 可能因权限无法列出内容；这里使用 `ls -ld` 只查看目录本身的元数据。

## 练习：画出你当前系统的一条存储路径

选择根目录 `/` 或你确定存在的 `/home`，只做下列观察并把答案写在自己的学习笔记中：

1. 运行 `findmnt -T /`，记录 `SOURCE`、`FSTYPE`、`TARGET` 和挂载选项。它的源是块设备、`overlay`、`tmpfs` 还是其他类型？
2. 运行 `lsblk -o NAME,TYPE,FSTYPE,UUID,MOUNTPOINTS`。若第一步的源是块设备，找出它对应的分区和文件系统；若不是，说明为什么“目录一定在某块磁盘上”不成立。
3. 对比 `df -hT /` 和 `df -i /`：分别记录可用空间与 inode 使用率，并用一句话说明二者为何都值得检查。
4. 运行 `readlink -f /bin`。如果输出是 `/usr/bin`，用自己的话解释 Arch 的 usr merge；如果不是，也记录真实布局，不要把示例当结论。
5. 任选 `./example`、`../example`、`/usr/bin/env` 三条路径，在纸上标出它们的起点。说明哪一条会受当前工作目录影响。

### 成功标准

完成后，你能够在不修改系统的前提下：

- 正确说出 `/`、`/root`、`/home`、`/run`、`/tmp`、`/var` 的区别；
- 用“设备 →（可选）分区 → 文件系统 → 挂载点”解释至少一条实际路径，或说明它为何是虚拟/叠加文件系统；
- 指出 `df -h` 与 `df -i` 各自回答的问题；
- 说明 UUID 与 `/dev/sdX` 的稳定性差异；
- 说清硬链接共享 inode、符号链接保存目标路径，以及 mount namespace 只隔离挂载视图而非自动提供完整安全隔离。

## 安全、恢复与下一步

本课没有产生任何持久修改；关闭终端或结束命令即可，不需要恢复操作。若观察时只看到意外的目录、挂载或权限错误，不要用 `sudo` 或“试试 `mount -a`”来修复：先保存命令和错误信息，确认当前是在宿主机、容器、WSL、救援环境还是 chroot。

以后真的需要修改分区、文件系统、swap 或 fstab 时，先备份可恢复数据，记录当前 `findmnt`/`lsblk` 输出，确认设备的稳定标识，准备可启动的救援介质，并在变更前获得针对该系统的明确方案。即使只是挂载，错误的目标也会遮住目录内容；而 `mkfs`、分区工具和不当的 fstab 修改则可能带来数据丢失或无法启动的后果。

权限与目录“执行”位只在本课预告：文件的 `x` 通常表示可执行，目录的 `x` 表示可搜索/可穿越；它与读取目录列表的 `r`、在目录内创建/删除条目的 `w` 共同决定访问。下一阶段学习 Shell 和命令时会在更具体的用户、组与权限课程中继续展开。

如果你已经能用 `findmnt`、`lsblk`、`stat` 和 `df` 描述当前状态，下一步不要在本页继续堆命令：转到 [[计算机知识/30-计算机系统/12-VFS文件描述符Inode目录与路径解析|VFS、文件描述符、inode、目录与路径解析]]，理解路径查找、打开文件描述与进程 FD；再读 [[计算机知识/30-计算机系统/13-文件系统布局日志CoW与一致性|文件系统布局、日志、CoW 与一致性]]，区分“写入已返回”“其他进程可见”“元数据一致”和“断电后可恢复”。可写练习只在 [[计算机知识/80-实践/06-计算机系统/05-文件系统原子替换与fsync/README|文件系统原子替换与 fsync 实验]] 的受控临时目录进行。
