# 08 · 性能、安全与可维护性

## 本课目标

识别容易产生灾难性回溯的形状，理解正则拒绝服务（ReDoS）的风险，并把正则当成需要测试、评审和限制输入的生产代码。

正则拒绝服务（Regular Expression Denial of Service，ReDoS）是指：攻击者构造输入，让某个高回溯模式花费异常长的时间，从而持续占用 CPU 或服务线程。

## 一个典型危险形状

```regex
^(a+)+$
```

对于完全由 `a` 组成的短输入，它可能很快成功。但对于“很多个 `a`，最后跟一个 `!`”的近似匹配失败输入，回溯型引擎可能尝试大量不同的分组方式。

这个表达式实际只需要：

```regex
^a+$
```

危险不来自字符 `a`，而来自**嵌套量词对同一字符范围存在许多等价切分**。

> [!danger] 不要在共享环境里随意压测危险表达式
> 极长恶意输入可能让编辑器、服务线程或进程长时间占用 CPU。使用受控短样本、超时和隔离环境；课程不要求生成攻击负载。

## 高风险信号

看到以下结构时需要额外审查：

- 嵌套的宽泛量词，例如 `(.*)+`、`(.+)*`；
- 多个相邻量词都能消费同样字符，例如 `a*a*`；
- 交替分支共享大量前缀或可以用多种方式匹配同一文本，例如 `(a|aa)+`；
- 宽泛量词后跟一个很晚才失败的结尾条件；
- 模式未锚定，导致引擎从许多起点重复尝试；
- 反向引用、复杂环视与无限量词叠加；
- 表达式作用于不可信、无长度上限的输入。

这些是审查信号，不表示每次都必然指数爆炸；实际行为取决于引擎和优化。

## 降低风险的优先顺序

1. **换工具。** 结构化格式使用解析器，固定边界使用字符串 API。
2. **限制输入。** 在进入正则前限制长度、行数或字段大小。
3. **写具体边界。** 用 `[^,]{0,100}` 代替无限的 `.*`，前提是业务规则确实如此。
4. **消除重叠。** 让分支起始字符或范围尽量可区分。
5. **锚定已知结构。** 校验时明确开头和结尾，或使用完整匹配 API。
6. **选择可预测引擎。** 面对不可信输入时，可考虑 RE2 类线性时间引擎并接受语法限制。
7. **使用超时/取消。** 如果库支持，为运行设置时间预算；超时不是修复模式本身，但能形成防线。
8. **基准测试近似失败输入。** 成功样本快，不代表最坏情况安全。

原子组或占有量词可以阻止部分回溯，但语法和支持度依引擎而异。它们是局部工具，不应代替清晰结构与输入限制。

## 校验正确性与业务安全是两层

正则可以检查“字符串长得像什么”，但通常不能独立完成：

- 日期是否真实存在；
- 路径规范化后是否逃出允许目录；
- URL 最终指向哪里；
- 邮箱、电话、账号是否真实可达；
- 用户名是否违反保留词、混淆字符或业务唯一性；
- 输入是否需要 Unicode 规范化。

安全校验常见顺序是：长度限制 → 规范化 → 结构解析/匹配 → 业务规则 → 必要的外部验证。

### 命令行文本工具也有自己的方言与安全边界

在 Linux 终端里，`grep -E`、`sed`、`awk`、`rg` 与 Python/JavaScript 并不共享一套完整正则语法或默认 Unicode 行为。特别是：

- 固定文本优先用 `grep -F` 或 `rg -F`，不要把动态字面文本误作正则；
- 需要扩展正则时显式选择 `grep -E` 或工具文档指定的模式；不要假设 lookaround、反向引用或命名组在命令行工具中可用；
- 模式或文件名来自不可信输入时，使用 `--` 结束选项，正确引用 shell 参数；正则匹配成功也不能证明路径安全；
- `sed` 的原地修改、重定向和管道会改变文件或丢失错误流，批量替换前先在复制样本上预览并保留恢复路径。

这些不是“再背几条正则”的问题。命令参数、引用、管道和退出状态见 [[计算机知识/20-操作系统/01-Linux/04-Shell命令行与帮助系统|Shell、命令行与帮助系统]]；可恢复地组合 `grep`、`rg`、`sed`、`awk` 与文本流水线见 [[计算机知识/20-操作系统/01-Linux/05-文件目录与文本处理命令|文件、目录与文本处理命令]]。

## 数据不是模式

“开发者控制模式，用户只提供待匹配文本”与“用户还能提供模式”是两种不同的风险模型。不要把动态字面文本直接拼进正则：

```text
目标：按字面查找 a+b
错误拼接后的模式：a+b
意外含义：一个或多个 a，随后是 b
```

- Python 使用 `re.escape(dynamic_text)` 把动态文本按字面处理；
- 支持该能力的现代 JavaScript 可使用 `RegExp.escape(dynamicText)`，旧运行时应使用经过测试的兼容实现并核对版本；
- 如果只是查找固定字面文本，`includes`、`indexOf` 等字符串 API 通常更直接；
- 默认不要接受不可信方提供任意正则。业务确需此能力时，应单独限制引擎、模式长度、可用特性、输入长度、运行时间与隔离边界。

## 让表达式可维护

把正则当成代码，至少提供：

- 需求说明，而不是只留一行神秘字符；
- 目标引擎、版本和标志；
- 正例、反例、边界例和近似失败例；
- 捕获组的名字与含义；
- 输入长度或规模上限；
- 替换前后的预览；
- 失败时采用什么替代路径。

Python 可用 `re.VERBOSE` 把复杂模式分行并加注释；标志必须实际传给编译或匹配 API：

```python
import re

pattern = re.compile(
    r"""
    ^
    (?P<prefix>PO|SO)
    -(?P<year>[0-9]{4})
    -(?P<serial>[0-9]{4})
    $
    """,
    re.VERBOSE,
)

match = pattern.fullmatch("PO-2026-0042")
assert match is not None
assert match.groupdict() == {"prefix": "PO", "year": "2026", "serial": "0042"}
```

现代 JavaScript 没有完全等价的内建 `x` 标志；可以把清晰的小片段组合成字符串，并通过单元测试保护最终模式。组合时仍要审查括号、转义和意外空白。

## 代码评审清单

### 从本库链接检查器看“匹配到字符”与“解析出语义”

同一串链接字符出现在正文、行内代码、长围栏中的短围栏示例、HTML 注释或 YAML 属性时，含义不同。只用一个全库正则找方括号，会把教学文本报成断链；即使找到了目标文件，仍需检查标题或块 ID。显式写成 `Wrong/Target` 时也不能偷偷用其他目录的同名文件救回它。

本轮回归在 `scripts/test_check_wikilinks.py` 和 `scripts/test_markdown_links.py` 保留正反夹具；它们是解析器行为的证据，不是完整 Markdown 标准认证。自检：为正文假链接、围栏同样字符、正确文件错误标题各预测一个诊断，再解释为什么合法脚注定义不应被当成文件路径。检查点是分开词法上下文、语法结构、目标解析与语义校验，而不是继续加一个更宽的正则。上述测试在仓库根目录以 `python3 -B -m unittest discover -s scripts -p 'test_*links.py'` 运行，不会执行笔记中的命令。

- [ ] 是否有更简单的字符串 API 或解析器？
- [ ] 输入是否来自不可信来源？长度是否有上限？
- [ ] 引擎是否为回溯型？是否有超时或取消机制？
- [ ] 是否存在嵌套量词、重叠分支或宽泛点号？
- [ ] 正例、反例、边界例、近似失败例是否都测试？
- [ ] 表达式、标志与替换字符串是否在同一处说明？
- [ ] 命名组和非捕获组是否表达了意图？
- [ ] 维护者能否在一分钟内解释每一段？

## 练习

审查下面三个模式，不要用超长输入运行它们：

```regex
^(a+)+$
^([A-Za-z]+\s?)+$
^.*\.log$
```

对每个模式回答：

1. 它试图完成什么需求？
2. 哪些输入会形成“接近成功但最终失败”？
3. 能否通过更具体的字符类、有限量词、锚点或字符串 API 改写？
4. 还需要什么输入上限或超时策略？

## 成功标准

- 我能指出嵌套量词与重叠选择为什么危险。
- 我知道最快的成功样本不能代表最坏情况。
- 我会把输入长度、引擎选择与超时纳入设计。
- 我的复杂正则带有引擎、标志、样本和字段说明。
- 我不会把 Python/JavaScript 的正则特性直接复制给 `grep`、`sed` 或 `awk`，并会在真正写入前用复制样本预览命令行替换结果。
