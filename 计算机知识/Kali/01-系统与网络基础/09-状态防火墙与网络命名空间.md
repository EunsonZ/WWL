# 状态防火墙与网络命名空间

## 本页解决的不是“怎样关掉防火墙”

当同一个 TCP 8000 从本机能访问、从另一台实验机不能访问时，服务状态只是解释的一部分。还要知道包经过哪条路径、哪套规则、哪个网络命名空间。读完应能画出一次请求的逻辑路径，区分监听、过滤、转发和 NAT，不需要先执行任何规则修改。

先修是 [[计算机知识/Kali/01-系统与网络基础/06-TCPIP路由DNS与TLS|地址与路由]]。贯穿场景仍是自建 `127.0.0.1:8000` 静态服务；这里不提供可直接替换系统防火墙的配置。

## 五个钩子对应五种观察位置

钩子是内核包处理路径中调用规则的阶段。常见 IP 路径可抽象为：入站包先经过 prerouting，再做路由决策；目的为本机时进入 input，目的需转发时进入 forward；本机产生的包进入 output；离开路径还涉及 postrouting。桥接、容器和其他钩子会增加复杂性，因此这是主干模型，不是所有网络路径的完整实现图。[^v2-nftmanual]

端口 8000 的本机输入规则不会自动等价于转发到容器的规则。本机 `ss` 看到的监听，也只属于相应网络空间的 socket 视角。诊断时要同时问“谁生成包”“谁是目的”“是否发生了地址改写”。

## 表、链和规则怎样一起决定结果

nftables 的 table 是组织容器，chain 是规则序列；base chain 连接内核钩子，普通链通过其他规则跳转进入。地址族 `ip` 处理 IPv4，`ip6` 处理 IPv6，`inet` 可用于两者；写了 `inet` 仍不表示每条具体地址匹配都自动支持双栈。[^v2-nftmanual]

同一钩子可以存在多个基础链。较早链的 accept 不一定免除后续链的检查；drop 会终止该包相应处理。不要只找到一条允许 8000 的规则，就宣布其余规则不重要。优先级、默认策略和跳转都要一起解释。

```bash
# 只读；需要相应本机授权及能力，不修改规则。
nft --version
sudo nft -a -n list ruleset
ip rule show
ip route show table all
```

规则 handle 便于定位当前规则，但不是跨重载永久稳定的业务 ID。公开笔记只保留合成规则，避免泄露真实网络布局。

## 状态连接跟踪和 TCP 状态不是同一个词典

连接跟踪为流量保存原始方向、回复方向、状态和超时等元数据；`new`、`established`、`related` 是防火墙用于匹配的类别，不是应用登录状态。UDP 虽没有 TCP 握手，也能被连接跟踪以超时流的形式关联。[^v2-conntrack]

因此“允许 established”不等于“只允许已认证用户”；“出现 related”不等于“任何关联端口都安全”；“记录失效”也不能独自证明应用正常关闭。已经存在的连接与新建连接可能受到不同规则，所以修改规则后应分别设计新的连接复测和已有会话复测，不能只刷新一次页面。

NAT 与过滤同样分工不同。NAT 改变地址或端口映射，不替代用户认证、对象授权或明确的过滤策略。多个观察点上的五元组可以不同，详见 [[计算机知识/Kali/02-信息收集与网络测量/05-WiresharkTcpdump与Tshark|抓包观察位置]]。

## conntrack 的状态不是应用的状态

连接跟踪（conntrack）为经过内核的数据流维护状态与方向信息；`ct state` 是对这些记录的匹配，不是读取应用是否登录。`new`、`established`、`related`、`invalid` 等标签不能机械对应到“新用户”“可信用户”“已授权用户”和“攻击者”。NAT 语句与过滤判定也属于不同职责。[^v5-nftables]

尤其是 UDP：协议本身没有 TCP 三次握手，连接跟踪仍可根据流量方向和超时维护记录。因此观察到某 UDP 流具有回复方向的状态，不是发现了一个隐藏的 UDP 握手。反过来，状态表中有旧记录，也不证明远端服务此刻仍在线。

设一个教学防火墙允许既有连接的返回数据。它解决的是“这份回复与已观察的通信关系是否相符”，不是“回复内容是否符合业务授权”。对端通过已经允许的连接返回错误对象，状态规则不会因此自动阻止。关联 [[计算机知识/Kali/03-Web与API安全/08-认证会话越权与API测试|应用授权]]：网络许可与对象许可是不同检查点。

## 一个容器中的 localhost 是谁

网络命名空间可隔离设备、协议栈、路由与端口等资源。两个命名空间都出现 `127.0.0.1:8000`，不代表同一个 socket，也不必发生端口冲突。容器暴露端口后还要经过宿主机的映射或代理路径。[^v2-netns]

```bash
# 只查看当前进程所在的网络命名空间标识。
readlink /proc/self/ns/net
ip -br address
ss -lnt
```

`ip netns list` 主要列出以相应方式命名的空间，不能保证列出机器上所有容器使用的匿名空间。没有充分授权时，不进入其他进程的命名空间，不用诊断当借口扩大访问。

## 网络命名空间隔离什么，又留下什么

Linux 网络命名空间隔离网络设备视图、协议栈、路由表、相关防火墙规则和端口等资源。两个空间都可以有自己的回环与相同端口号，因为“端口冲突”首先发生在相应网络上下文内。[^v5-netns] 但网络命名空间不是完整虚拟机：它不单独提供全部文件系统、进程、用户身份和内核隔离。

可以把网络排错写成四个坐标：**进程所在空间、源接口、目的地址、规则观察点**。只在宿主机查看监听列表，却要解释容器内的回环服务，可能根本看错了坐标系。将本机端口映射到容器还会引入转发与转换关系；是否隔离取决于实际连接方式，而非是否出现了 namespace 这个名字。

NAT 只说明某些地址或端口被转换；加密说明通信表示受到密码保护；过滤说明某些报文被允许或拒绝。三者可以一起出现，也可以单独存在。把 NAT 当作防火墙、把 VPN 当作完整匿名、把命名空间当作无条件沙盒，都是用一个机制替代另一份安全合同。进一步的权限条件见 [[计算机知识/Kali/05-密码无线与专门领域/06-容器Kubernetes与IaC审计|容器隔离的多个维度]]。

## 用最小证据区分四个假说

假说 A：服务只绑定回环。预期本机回环能访问、跨机不能；检查服务配置和 `ss`。假说 B：请求在入站过滤阶段丢弃。预期发送侧有包但应用无请求，需要合适采集点和规则计数佐证。假说 C：去程到达但回程路由错误。预期服务端观察到请求，客户端不见相应回应。假说 D：请求进了另一个容器或代理。预期返回应用特征、日志位置或五元组与假设不同。

这些是假说而非自动判决。规则计数器增长表示某规则匹配了流量，不表示它匹配的就是你那次操作。应使用限定时间窗口、专用测试端口和多点关联，不靠清空规则获得一个无法解释的“成功”。

> [!question] 自检
> 关掉宿主机防火墙后恢复访问，能否立即断言所有问题都在 input 链？不能。操作可能改变多条链、转发和连接状态。应缩小到具体规则与包路径，再恢复最小必要配置。
