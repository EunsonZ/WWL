# SSRF路径上传与解析边界

**先修关系：** [[计算机知识/Kali/03-Web与API安全/01-Web测试模型与手工基线|Web测试模型与手工基线]]；[[计算机知识/Kali/01-系统与网络基础/04-Shell文件权限与文本处理|Shell文件权限与文本处理]]。

## 共同根因：把外部输入交给了更有权限的解释器

服务端请求伪造（SSRF）让外部输入影响服务器向哪里发请求；路径穿越让输入影响文件系统的访问位置；上传问题可能让文件跨越存储、解析和执行边界。它们不是同一种漏洞，但都需要追踪“谁提供数据、谁解释、以谁的权限访问什么”。[^s1][^s2]

## 同一性问题：检查的对象必须是实际使用的对象

先分清三个问题：字符串是否符合允许格式；解析得到的对象是否允许访问；真正使用时是否仍是这个对象。它们分别对应语法、策略和时序，任一层正确都不能替其他层作保证。URI 的保留字符和编码规则约束第一层解释；SSRF 防护还需考虑解析地址、重定向和网络出口等后续条件。[^v5-uri][^v5-ssrf]

原创推演：检查时对象为 $r(t_0)$，连接或打开时对象为 $r(t_1)$。若两者之间允许改变，则“检查通过”只直接支持 $r(t_0)$。解决思路是缩小或消除检查—使用之间的身份漂移，让使用操作受同一受控对象、解析结果或强制访问边界约束；不是在字符串上多加一次替换。具体系统实现需要额外评审，本节不提供声称可通用防御所有场景的函数。

这与文件系统中的符号链接、容器挂载和命名空间具有相似结构：名称不是对象本身。但相似结构不表示防御 API 可以直接互换。DNS 地址固定与安全文件句柄解决的是不同底层对象，必须回到各自系统语义。

## SSRF 的两层限制

允许用户输入 URL 的预览、导入或 Webhook 功能，应控制协议、目的主机、端口、重定向和实际连接地址。单纯判断字符串是否包含某个域名不足够，因为 URL 解析、用户信息字段、大小写、编码和重定向可能改变实际目的地。

应用层允许列表与网络层出站限制互补。域名校验后解析到的地址可能变化；检查时与连接时不是同一动作，需要防止只验证第一次解析或仅第一跳。[^s1] 本课程不提供云元数据、内部管理地址探测列表，也不把内部网络读取当作默认验证目标。

安全实验可使用两个均由你控制的教学服务：一个实现允许列表，另一个只记录是否收到无敏感内容的测试请求。还需记录没有收到请求的替代解释，例如 DNS、出站策略、异步队列或观察窗口不足。

## 为 URL 导入功能画一条可审阅的解析链

设产品仅允许从组织控制的图片源导入头像。先解析 URL 为结构化字段，允许明确 scheme/host/port；再检查所有将使用的 IPv4/IPv6 解析结果；连接时确保实际目的地仍符合策略；每次重定向重复同样判断，或按合同直接禁用跳转。还需限制响应体大小、读取时间和可接受媒体类型。[^v2-ssrf]

这条链的难点不是罗列更多字符串，而是验证与实际使用是否采用一致的解释器、地址和时刻。DNS 结果变化、重定向以及代理再次解析名字都可能改变最终连接。应用检查与独立出站策略应共同设计；一次 `urlparse` 或 `is_private` 判断不能独自构成完整 SSRF 防护。

对照实验只比较已登记的允许教学源和另一个自有、明确不在允许列表的教学源，不读取内部业务数据。未观察到请求时保留 DNS、队列、超时和网络丢弃等替代解释。

## 路径处理不只是删掉 ../

路径可能经过 URL 解码、应用拼接、文件系统规范化和符号链接解析。仅删除字面量 `../` 不能保证最终访问在允许目录内。反过来，调用一次 `resolve()` 也不能自动解决符号链接竞态、权限变化和检查后使用的问题。

应用设计优先让客户端提交逻辑对象标识，由服务端映射到已登记文件，而不是直接接受任意路径。需要处理路径时，明确允许根目录、符号链接政策、读取/写入权限以及原子打开方式。

教学检查只使用你创建的 `public-demo.txt` 和受限教学文件，证明边界即可；不要读取真实系统凭据、私钥或个人文件。即使是本地实验，也要把无意越界与预期反例分开记录。

## 规范化检查与打开操作之间仍有竞争窗口

先计算一个路径在允许根目录内、再用普通字符串路径打开，期间目录或符号链接可能变化。将检查结果当作永久权限事实属于检查到使用之间的竞态（TOCTOU）。有高要求时应依赖平台提供的受约束目录句柄、相对打开与一致的符号链接政策，并分别审阅读和创建的语义。

本包的归档验收也采用路径白名单、符号链接排除和最终归档检查，但它处理的是受控构建目录，不宣称能安全打开任意敌对并发文件系统。防护保证必须匹配实际威胁模型。

## 上传文件跨越多次解释

扩展名、Content-Type、文件魔数分别提供有限线索，不是单独的安全证明。上传后还可能被图片库、解压器、预览器或脚本引擎解析。应限制大小、数量、允许类型、存储位置与访问权限，按需求重编码或净化，并避免让上传目录具备执行能力。[^s2]

把用户文件名直接用于服务器路径会带来覆盖、路径和日志问题；最好生成服务端标识并单独保存显示名。压缩包还涉及解压路径穿越、巨大展开比例与递归资源消耗，不能“先解压再检查”。

## 上传的生命周期决定检查放在哪里

按“接收 → 临时存储 → 类型/大小检查 → 必要转码 → 正式存储 → 授权下载 → 到期删除”逐段标注权限。临时目录也要有容量与权限限制，拒绝文件应清理；正式存储名由服务端生成，显示名作为数据保存；访问时重新应用对象授权。[^v2-upload]

例如一张合成小图片既要满足声明类型，也要能被允许的图片解析器正确读取；解析后重新编码得到的输出仍需检查大小。不要在分享包附带可执行上传演示或宣称所有多格式文件都恶意。文件签名、扩展名和解码成功分别提供不同证据。

## 其他解析边界：XXE、模板与反序列化

XML 外部实体、不受信任模板执行与不安全反序列化都涉及解释器能力超出数据需求。修复应收紧解析器功能、只接受明确数据结构并限制资源；把异常吞掉或禁用错误输出并不会消除根因。

本页只提供机制与审阅框架，不附对象执行链、系统命令 payload 或文件读取链。评估时优先设计无破坏的可观察标记与源码对照，而不是追求最大的后果展示。

## 工具证据应按解析阶段摆放

代理和 curl 主要帮助观察请求与响应；DNS 工具帮助核对名称解析；抓包帮助核对实际连接；文件元数据和类型工具帮助分析上传对象；运行时日志帮助核对最终处理器。这些观察互补，但任何一个都不能单独证明整个生命周期安全。将“没有回连”直接解释为不存在 SSRF，就忽略了名字解析失败、出口阻断、超时和观察点缺失等替代解释。

完整 HTTP 多组件模型在 [[计算机知识/Kali/03-Web与API安全/13-HTTP中间层与消息解释#规范化不是把字符串越改越短|规范化与资源同一性]]；取证场景下同样需要区分原始表示和解释产物，见 [[计算机知识/Kali/06-取证逆向与检测/04-文件元数据Binwalk与ExifTool|文件格式与元数据]]。

## 自检

一个上传图片经过改扩展名后仍能被浏览器显示，是否证明任意代码执行？不能，显示路径、服务器端执行路径与后续解析器是不同边界。必须先说清要检验的机制，再选择最小证据。

连接到 [[计算机知识/Kali/06-取证逆向与检测/04-文件元数据Binwalk与ExifTool|文件格式分析]] 可理解为什么魔数只是线索；连接到 [[计算机知识/Kali/01-系统与网络基础/08-BashPython与可复核自动化|脚本输入合同]] 可把这些原则迁移到自己的分析工具。
