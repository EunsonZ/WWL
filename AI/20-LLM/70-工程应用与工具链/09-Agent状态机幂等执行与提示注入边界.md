# Agent状态机、幂等执行与提示注入边界

**先修与定位：** 先读原有最小Agent循环，再引入状态、副作用和信任边界。

## 模型提出行动，不代表它拥有执行授权

Agent 可以观察环境、提出工具调用、读取结果并继续决策。关键变化不是聊天循环更长，而是输出可能影响外部状态。模型生成的参数必须经过确定性的类型检查、权限检查、范围校验与风险策略，才能交给工具执行。OWASP 的 Agent 指南将工具权限、数据外泄和注入列为重要设计问题。[^S55]

一个可审计的状态机可以是：接收任务，生成候选行动，验证参数与授权，等待必要确认，执行，记录结果，再决定继续或结束。明确状态转换比让一段自由文本承担规划、批准和执行三种角色更可靠。

## 超时最容易暴露“看起来成功”的假象

工具请求超时可能表示未执行，也可能已经执行但响应丢失。对于发信、付款、提交订单等有副作用操作，盲目重试会造成重复结果。系统应使用工具支持的幂等键、查询操作状态或人工核对；幂等键的作用域、过期规则与参数绑定需由外部服务真实保证。

在分布式环境中，简单重试通常更接近“至少一次”，而不是天然“恰好一次”。本地给 action 标记完成也不能撤销远端已发生的副作用。事务、补偿动作和审计日志应根据具体工具能力设计，不能用提示词替代。

## 结构化输出只保证一部分语法

JSON Schema 可以约束字段名、类型、枚举和部分数值范围，但合法 JSON 仍可能请求错误对象、过大范围或未经授权的接收人。路径必须规范化并限制工作目录，URL 与域名需按网络策略检查，工具名采用白名单；自由字符串不要直接拼接到 shell 或 SQL 中。

模型自报“已经完成”不是执行证据。成功状态必须来自工具结果及必要的读后验证。对文件交付，应检查文件真实存在、可打开、内容符合要求，而不是只生成一个看起来像下载路径的字符串。

## 间接提示注入为什么不靠一句提醒消失

检索网页、仓库文件、邮件或工具响应可能包含企图改变任务目标的文字。应把这些内容视为低信任数据，不允许它们授权新操作、索取凭证或覆盖用户目标。分隔符和来源标签有帮助，但不构成不可绕过的安全边界。[^S54]

更强的控制来自工具层：最小权限、按操作授权、限制外网、秘密信息不进入不必要上下文、敏感写入确认和完整审计。把读取与写入工具分离，可减少模型误解后的后果。对多 Agent 系统，一个 Agent 的结论也不是天然可信的系统指令。

## 记忆、预算和停止条件也是安全设计

短期状态要记录已尝试行动、结果版本和失败原因，避免循环。长期记忆必须标注来源、时间和用户授权，不把网页内容自动升级为稳定事实。设置最大工具调用数、token/资源预算、超时和失败转交条件。

用户任务可能在中途改变，因此继续执行前要确认当前授权仍覆盖行动。执行过的不可逆步骤需要保留记录，而不是因新计划而抹去。日志只保存必要信息，并对秘密与个人资料做最小化处理。

## 监督能力也是系统容量，不能只写“人工兜底”

人工监督需要时间、领域判断和能够恢复上下文的证据。若每个 Agent 产物都需要人工读完，增加并发只会把工作从生成阶段移动到审查队列；若审查者来不及处理积压，超时、错误升级和未经确认的副作用都会增加。因此设计时应把人工复核视为有限资源，记录每类任务的复核触发条件、平均复核时长、队列等待、可自动验证比例和必须人工决定的例外。

这不是“一个人能监督多少 Agent”的普适公式。复核需求会随任务风险、输出结构、验证器质量和失败可逆性改变；可靠的解析／测试可减少部分人工检查，却不能替用户判断目标、权限和价值取舍。原始讨论及其对简单可靠性模型的自我修正位于 [[Clippings/WorkWithLLM/对话原稿/分析大模型算力极限 2|《分析大模型算力极限 2》“人类监督带宽是一个可以计算的硬约束”“我之前的 p^n 可靠性模型过度悲观”]]；本页将其保留为容量设计问题，而非经验比例或劳动市场结论。

## 如何测试一个Agent，而不是只看演示录像

离线模拟工具成功、超时、重复响应、恶意内容、权限拒绝和部分失败。对写入操作检查未授权调用数、重复副作用、恢复后状态一致性和审计完整性；对读任务检查来源忠实与完成覆盖。工具模拟验证的是控制逻辑，不等于外部服务真实集成已通过。

自测：模型在工具参数中填写了有效用户ID，是否可跳过权限检查？不可。存在性和授权是不同谓词。与[[AI/20-LLM/70-工程应用与工具链/08-混合检索重排RAG误差分解与证据|证据来源]]和[[AI/12-PyTorch/07-完整训练状态恢复与可复现实验|状态恢复]]合读，可以看到 AI 工作流仍受普通软件工程的不变量约束。
