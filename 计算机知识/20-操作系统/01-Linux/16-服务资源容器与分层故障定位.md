# Linux 深化：服务、资源、容器与分层排障

> 阅读定位：只读观察优先；发行版、内核、工具版本不能混为一谈。返回 [[计算机知识/00-开始/课程地图/13-Linux-课程地图|Linux · 课程地图]]；全域入口 [[计算机知识/00-开始/全局导航/00-总学习地图|计算机知识库 · 总学习地图]]。

## 先观察，再改变系统

高 CPU、慢响应、内存增长和磁盘繁忙可能互为因果，也可能只是同时发生。先记录时间、版本、影响范围和基线，读取进程、线程、文件描述符、日志、资源限制和 I/O 等信息。不要在没有证据时重启服务、清缓存、修改内核参数，让原始现场消失。

常见只读入口包括 `ps`、`top`、`free`、`df`、`du`、`ss`、`ip` 和 journalctl；具体选项依发行版与版本不同。`df` 看文件系统空间，`du` 统计可遍历文件的使用，两者不一致可能涉及已删除仍打开的文件、稀疏文件、权限与快照等。page cache 不是自动等于泄漏，RSS 也不等于全部申请过的内存。

## 服务管理的依赖与顺序

systemd unit 描述进程管理及依赖等合同。启动顺序关系与依赖拉起关系不同，`After=` 本身不保证另一服务被启动，也不保证业务已经可用。服务“进程存在”、端口监听、健康检查和依赖就绪是不同层证据。重启策略应防止配置错误造成无限快速重启。

资源问题先确认预算：cgroup v2 的 cpu.max 可限制带宽配额，memory.max 等限制相应内存使用，命名空间决定看到的对象集合。容器内逻辑 CPU 数与可持续 CPU 配额不同；同一应用移入容器后变慢可能是限额、存储、网络、NUMA 或依赖变化，而不只是“容器有开销”。

## 一次分层诊断示例

现象：HTTP p99 增大而平均 CPU 不高。先区分客户端排队与服务端处理；再看线程是否等锁、数据库连接池是否耗尽、网络是否重传、存储是否存在长尾。若容器 CPU 被周期性节流，平均利用率可能掩盖预算耗尽后的等待。每一步需对应具体可观察证据和能够推翻假设的结果。

`strace` 可观察系统调用但可能改变时序，perf 和 eBPF 等工具涉及权限、开销与内核能力，不能无条件在生产运行。日志、指标和跟踪互补，采样位置、丢失与时钟一致性影响解释。

## 完整运维地图

账户、组、权限、ACL、capabilities、SELinux/AppArmor、SSH、包管理、内核模块、udev、启动链、网络配置、存储、LVM/RAID、备份恢复、日志轮转、时间同步、容器和虚拟机均有位置。发行版包管理、Python 虚拟环境和应用依赖锁定不是同一层“装包”。

练习为一个本地示例服务记录 PID、监听、资源边界和应用健康，模拟可控的错误配置，再按证据定位。分区、格式化、引导修复、权限递归修改和驱动切换都放在隔离环境，不能复制课程设备名到正在使用的主机。
