# TCPIP路由DNS与TLS

**先修关系：** [[计算机知识/Kali/01-系统与网络基础/02-虚拟机快照与网络隔离|虚拟机快照与网络隔离]]；[[计算机知识/Kali/01-系统与网络基础/04-Shell文件权限与文本处理|Shell文件权限与文本处理]]。

## 一次连接经过哪些不同边界

输入网址之后，客户端通常需要解析名字、选择目标地址、查询路由、到达下一跳、建立传输层通信，再运行应用协议。如果是 HTTPS，还要完成 TLS。每一层回答不同问题，因此“网站打不开”不是一个足够精确的诊断。

把课程场景缩小到 `127.0.0.1:8000`：它不需要跨局域网的 ARP，也不依赖公网 DNS；但仍会涉及监听地址、TCP 和 HTTP。之后把服务移到实验虚拟机，才新增路由、防火墙和虚拟交换机因素。这样的递进能控制变量。

## 从字节到业务动作：每层确认的对象不同

TCP 的累计 ACK 表示接收 TCP 端点对序号空间的确认；它不等于应用已解析这些字节，更不等于数据库事务提交。应用可能在 TCP 接收后崩溃，也可能已经提交而响应在途中丢失。[^v5-tcp] 因而“TCP 可靠”与“业务只发生一次”是两种保证。前者讨论字节流，后者需要应用协议、状态与重试规则，连接 [[计算机知识/Kali/03-Web与API安全/12-现代API业务逻辑与并发边界|幂等和并发边界]]。

同样要区分链路帧、IP 包、TCP 段、TLS 记录和 HTTP 消息。封装并不要求它们一一对应：一个 HTTP 消息可以跨多个 TLS 记录与 TCP 段；一个 TCP 段中也可能包含多个上层记录的片段。看到抓包里“一行”并不意味着应用完成“一件事”。本页先建立层次关系，具体重组条件由 [[计算机知识/Kali/02-信息收集与网络测量/05-WiresharkTcpdump与Tshark|抓包的捕获、重组与解析]] 统一解释。

## 地址、前缀与路由

IPv4 地址有 32 位。`/24` 表示前 24 位是网络前缀，留下 8 位；地址总数为 $2^{32-24}=256$。在常见多访问子网中通常排除网络与广播地址，但 `/31` 点到点和 `/32` 主机路由不能套用“减二”口诀。IPv6 为 128 位，不使用 IPv4 的广播机制。

```bash
ip -br address
ip route
ip route get 192.168.56.20
ip neigh
```

`ip route get` 展示内核对一个目的地址的路由选择，不等价于探测对方是否存活。通常先匹配最具体的前缀，再综合路由规则等条件。网关是下一跳，不一定是最终目标。`ip neigh` 反映邻居缓存，不是“本网段全部在线设备清单”。[^s1]

同网段的以太网通信常需把 IP 映射到链路地址，IPv4 使用 ARP，IPv6 使用邻居发现。ARP 缓存缺失可能表示尚未通信；有缓存也不代表设备此刻仍在线。

## 具体算一次子网和最长前缀匹配

地址 `192.168.56.37/27` 的掩码末字节是 `11100000₂`，即 224；37 的二进制末字节是 `00100101₂`。逐位与得到 32，因此网络为 `192.168.56.32/27`，32 个地址覆盖 32 到 63，常见多访问网络中主机地址为 33 到 62。这里的“32 个”是地址数量，不是系统实际存在 32 台机器。

设教学路由表包含 `/0` 默认路由、`192.168.56.0/24` 经接口 A、`192.168.56.32/27` 经接口 B。目的 37 同时匹配三条，通常的单表查找选择更具体的 `/27`。即使默认路由 metric 更小，也不能让它抢走更具体前缀。只有在相应查表语境与相同前缀等条件下，再比较优先级；策略路由、多个表和等价多路径需单独处理。[^v2-iproute]

本包的 [[计算机知识/Kali/07-综合实验/10-实验G路由与扫描状态推理|实验 G]] 将此模型做成离线推演，并明确不模拟 Linux 全部路由策略。理论模型的边界不能用一句“与内核一样”抹平。

## 往返路径、NAT 和五元组

一个 TCP/UDP 流常用源地址、源端口、目的地址、目的端口和协议组成五元组。NAT 可能改写地址或端口，因此同一业务连接在不同观察点呈现不同五元组。记录抓包位置，才能把宿主机、来宾机和目标日志连接起来。

请求能到达目标，只证明去程某部分成立；回应可能经另一条路返回，受不同策略影响。非对称路由、状态防火墙和错误源地址选择，都可能造成“服务端收到请求，客户端却超时”。先比较双方时间与包方向，再决定在哪一层修复。

## 双栈排错：一个名字可能对应两条不同的连接路径

IPv4 成功不能证明 IPv6 成功，反之亦然。`127.0.0.1` 是 IPv4 回环，`::1` 是 IPv6 回环；服务仅绑定其中一个时，另一个路径可以失败而不构成矛盾。IPv6 的 `::` 通配监听是否接收 IPv4 映射地址，还取决于套接字选项和系统配置，不能看到一行 `:::8000` 就断言两种地址族均已验证。[^v3-ipv6]

先检查本机而不发探测：

```bash
ip -6 address show
ip -6 route show
ip -6 route get ::1
ss -4 -lnt
ss -6 -lnt
```

读 `ss` 时区分本地绑定地址、端口和监听状态；读 `ip -6 route get` 时，只能得到这次路由查找的结果，仍不证明目的服务可用。若一个域名有 A 与 AAAA，后续客户端选择的实际 peer 应随请求记录，否则两次看似相同的 URL 可能实际走了不同服务器或不同过滤路径。[^v3-ss]

链路本地地址通常形如 `fe80::...`，它的意义依赖接口范围。两张虚拟网卡各有自己的链路，“相同地址字符串”不总能唯一指定目标；使用带范围标识的地址时，应记录接口，例如 `fe80::1%eth0` 只是语法示例，不是本包目标。链路本地地址不能像公网地址那样任意跨路由转发。IPv6 的邻居发现依赖 ICMPv6，不宜把“阻断全部 ICMP”当成无副作用的加固。[^v3-ipv6]

### 用一个失败现象串起地址、监听和过滤

假设教学服务仅显示 `127.0.0.1:8000` 监听。请求该地址成功，请求 `[::1]:8000` 被拒绝，首先解释为绑定范围不同，不先改防火墙。若本机双栈都能连接、另一台获批虚拟机只有 IPv6 失败，才继续检查 IPv6 地址作用域、返回路由和对应规则。IPv4 NAT 的存在不自动说明 IPv6 也经过同样转换或隔离。

最后检查范围合同：授权某 IPv4 网段不自动授权同一主机的全部 IPv6 地址；扫描完整 IPv4 端口也不覆盖 IPv6。把地址族、来源接口、实际连接地址加入 [[计算机知识/Kali/08-模板与速查/02-实验记录模板|实验记录]]，才能正确解释 [[计算机知识/Kali/02-信息收集与网络测量/03-Nmap主机发现与端口状态|Nmap 的观察点差异]]。

## TCP：字节流而不是消息列表

TCP 为应用提供有序的字节流。连接通常通过 SYN、SYN-ACK、ACK 建立：双方交换初始序号，并确认对方的序号空间。数据中的序号按字节推进；SYN 和 FIN 也各占一个序号位置。抓包中一个应用请求可能被分成多个段，一个段也可能包含多个应用记录。[^s2]

> [!important] 观察单位
> **TCP 包数量、TCP 连接数量、HTTP 请求数量和用户操作数量不是同一个量。** ^observation-unit

设客户端初始序号为 1000，服务端为 5000。握手后客户端首个数据字节序号为 1001。若发送 80 字节，接收方可确认到 1081，表示期望下一个字节的序号。这里只是简化教学，不处理乱序、重传和序号回绕。

重传通常反映某种丢失或确认问题，不能独自定位是服务器故障、链路拥塞还是采集点漏包。RST 表示连接被复位，但发出者、网络中间设备和应用状态需要结合上下文判断。

## TCP 的流量控制和拥塞控制不是一个旋钮

流量控制关注接收端还能接受多少数据，拥塞控制关注路径能承载多少在途数据。吞吐下降可能来自接收窗口、往返时延、丢包、应用处理或磁盘，而非单纯“带宽不足”。抓包里的零窗口提示接收侧压力，重传则需要更多路径证据；不把二者混成一个“网络卡”。

此处使用 TCP 的抽象解释，不给真实网络未经测量的吞吐承诺。下一步在 [[计算机知识/Kali/02-信息收集与网络测量/05-WiresharkTcpdump与Tshark|抓包工作流]] 中分别检查序号、确认号、窗口和时间。

## 把窗口、时延与吞吐放进同一张量纲表

**往返时延 RTT** 是一次往返的时间；**带宽时延积 BDP** 是在理想稳态下填满路径所需的在途数据量。设路径目标速率为 $R$ bit/s，RTT 为 $T$ s，则 $RT$ 的单位是 bit，换成 byte 要除以 8。下例为手算模型，不是对任何虚拟机的测速。

假设 $R=100\times10^6$ bit/s、$T=0.040$ s，带宽时延积为 4,000,000 bit，即 500,000 byte，约 488.3 KiB。若可维持的在途数据上限只有 128 KiB，即 131,072 byte，即使没有额外损耗，窗口与 RTT 给出的速率上界也只有 $8\times131072/0.040\approx26.2$ Mbit/s。不是网卡标称速率写着 100 Mbit/s，单条连接就必然达到该值。

这里至少有接收窗口和拥塞窗口两类约束：前者与接收缓冲能力有关，后者反映发送方对路径的控制；应用供数速度、接收消费速度、协议开销、启动阶段与丢包还会进一步限制实测速率。TCP 窗口的序号与通告机制可查 RFC 9293，但上面的稳态上界只是原创简化推导，不能拿来反推出某台主机必然配置错误。[^v5-tcp]

一个有用的反例是“连接慢，但接收窗口始终很大”。这只削弱了接收窗口不足的解释，不能排除拥塞、CPU、磁盘或应用等待。另一个反例是“ping RTT 很低但应用首字节很慢”：测量对象不同，应用可能需要认证、数据库或后端调用。把时间起点、终点和单位写清楚，才能与 [[计算机知识/Kali/03-Web与API安全/02-curlHTTPie与接口重放|curl 的阶段时间]] 对照。

## MTU、MSS 与小包成功大包失败

MTU 是某条链路或接口所允许的网络层包大小上限；TCP MSS 是 TCP 负载大小相关的协商参数。以无选项 IPv4 首部 20 字节、TCP 首部 20 字节和 MTU 1500 为纯教学假设，可得最大 TCP 负载 1460 字节。IPv6、扩展首部、TCP 选项、VPN 封装会改变计算，不能把 1460 当成普适常数。

路径 MTU 取决于整条路径的约束。IPv6 路由器不会按 IPv4 式方式替发送方分片，发现过大包时依赖相应控制消息帮助端点调整；随意屏蔽必要的 ICMPv6 消息，可能产生小请求成功、大传输停滞的现象。[^v2-pmtu] 本地离线计算只能解释假设，不能代替实际路径测量。

## UDP 与 ICMP：没有回复并不等于没有服务

UDP 不建立 TCP 式连接，应用必须自行处理需要的可靠性。一个开放的 UDP 服务可能只对正确格式请求响应；防火墙、限速与丢包也可能导致沉默。因此 `open|filtered` 是证据不足的联合状态，不是“半个开放端口”。详见 [[计算机知识/Kali/02-信息收集与网络测量/03-Nmap主机发现与端口状态|Nmap 的状态模型]]。

ICMP 不只用于 ping，还传递部分网络差错与诊断信息。禁用 ICMP 并不会自动让主机“不可见”，还可能破坏某些正常路径发现过程。

## DNS、端口和服务名字

DNS 的 A/AAAA 记录给出地址，CNAME 是别名关系，MX/SRV 指向特定服务信息，TXT 用于多种元数据。DNS 结果可以受递归解析器、缓存、地理调度、内外网视图与时间影响。一次解析记录应该包含查询类型、解析器、时间与响应状态。

TCP/UDP 端口号各自处于自己的协议空间；“53 端口”必须说明 TCP 还是 UDP。端口常见用途只是先验线索，不能仅凭 `443` 就断定所有流量是正常 HTTPS，也不能凭服务 banner 保证真实版本。

## TLS 在哪里增加信任

TLS 保护通信的机密性与完整性，并通过证书等机制支持对等方认证。TLS 1.3 中握手协商参数并导出通信密钥；它不负责修复服务器端越权，也不能阻止合法登录用户读到应用错误授权的数据。[^s3]

验证 HTTPS 时至少区分：链路能否连接、协议握手能否完成、证书链是否被信任、证书名字是否与目标匹配、有效期是否正确。SNI 是 TLS 握手中的服务器名字信息，HTTP 的 Host 字段属于应用层；多租户场景两者都可能影响路由。

## 连贯的排错顺序

先看本机接口与路由，再用小范围连接确认端口，然后检查 TLS，最后解释 HTTP。不要把加大 Nmap 强度当成解决 DNS 或认证问题的方法。多层证据的操作版见 [[计算机知识/Kali/07-综合实验/02-实验A从路由到HTTP与Nmap|实验 A]] 与 [[计算机知识/Kali/07-综合实验/03-实验B抓包重组与证据交叉验证|实验 B]]。

自检：`ping` 不通但 `curl` 得到 HTTP 403，能否说目标离线？不能，HTTP 响应已经证明某条路径上有应用响应；403 的生成者还需通过代理和服务日志确认。
