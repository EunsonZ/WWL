# 构建、签名与更新迁移：新APK装上去，旧预约还由谁负责

有限后台预算以后，D仍可用原id显式恢复accepted；resources.db不因此抹掉已经记下的后台尝试。此时开发者发布v2，给资源账本加一个last_http列。最省事的实现是“打开失败就删库重建”：错误消失，原预算、未知意图和草稿也一起消失。升级测试如果只看App能启动，会把数据丢失评为一次漂亮修复。

本页让同一合成包依次经历v1、失败v2、修复v2、异签更新、降级和同签release v3。先区分**谁能被系统接受为更新**，再核**接受更新以后数据能否继续解释**。源和实际操作接 [[计算机知识/64-移动平台开发/android-intent-demo/资源与更新实践|同一个实践入口]]；上一页的原id/fp、accepted和新queued不因换APK变成一套新样本。

## 五个版本，各自回答哪一层问题

| 量 | 本例锁定/变化 | 不能混同的对象 |
| --- | --- | --- |
| compileSdk/targetSdk/minSdk | 35/35/26 | 可编译API、行为兼容目标、安装下限；不是数据schema |
| APK versionCode/versionName | code1→2→3，name为展示文字 | 平台比较的更新顺序；name不是可靠数值版本 |
| 签名证书/可接受签名历史 | 教学同一签名；另造异签负例 | 系统对更新来源的校验，不是TLS服务器身份 |
| resources.db布局 | PRAGMA user_version1→2 | 资源账本列与迁移规则；client.db仍其原布局 |
| 协议/政策/决策epoch | v2/1、policy2、epoch2沿SE82 | 服务可解释的请求和原结果，不由APK code自动改变 |

构建仍是Kotlin2.1.21、AGP8.7.2、Gradle8.9、JDK17；新增r变体用Gradle属性固定courseVersion、courseDbVersion和显式故障开关。release是另一构建类型，不是“code更大的debug”。签名、debuggable和版本号是相关但独立的检查对象。

## 签名如何连接安装与后续更新

Android安装包带有签名。最初安装还没有此包的旧签名可比；以后同applicationId更新时，系统按其支持的签名/历史与版本政策检查来源。本文不实现签名轮换lineage，有限实验使用**同一签名证书**，异签副本应拒绝覆盖；versionCode降低也应拒绝正常更新。[官方签名说明](https://developer.android.com/studio/publish/app-signing)与[版本说明](https://developer.android.com/studio/publish/versioning)分别给出机制。不要把此基本模型夸成“所有Android升级永远只能同一张证书”，生产轮换有额外平台合同。

本轮在隔离环境使用本地教学签名输入，不交付私钥或keystore。debug APK由既有隔离debug key签名；release v3用apksigner对齐签入相同教学key，以便在**相同包**上实际更新。它证明这组APK签名/更新机制，不是生产密钥管理、商店审核或上架回执。[apksigner](https://developer.android.com/tools/apksigner)的verify/print-certs用于核实际APK，而不是看源码文件里写了一个signingConfig就说签名正确。

这里有两类证书：APK签名证书用于安装/更新来源；HTTPS证书及信任锚用于连接目标。把APK签名搞对，不会让App自动信任任意服务器；把TLS教学CA加进debug包，也不允许另一个开发者用异签APK覆盖已安装App。

### release不继承debug教学信任

生成器在库外新目录生成TLS材料；debug只打包生成的CA公证书，私钥不进入发布树或APK。release资源仍只信系统CA，**不含debug教学CA**。因此release v3可以同签安装并保留原accepted，却不能据此推出它能继续连接本机教学CA服务；这个连接应在默认校验下拒绝，不为跑通实验改成trust-all。

真实发布需配置实际目标和有效服务证书/受众、保护签名key、制定轮换/撤销与更新渠道。Play App Signing另区分上传key与实际App签名key；本轮没有商店账号/付费云，不把它们设成理解基本安装更新机制的先修，也没有冒报这些流程已经执行。

## 升级成功以后，旧字节还要有解释

客户端业务表与资源表属于不同数据库。本例只迁移resources.db；ClientStore的原业务规范与原布局保持，不能为了新资源字段重建意图表。资源v1保存`actor,intent_id,fp,attempts`，v2新增`last_http TEXT NOT NULL DEFAULT 'none'`。旧行的none表示旧布局没有这个后台结果字段，不代表从未尝试、没有HTTP或业务没有提交；旧events与ClientStore原结果仍分别解释。

| 输入库与APK | 打开动作 | 应保留的结果 |
| --- | --- | --- |
| v1库→v1 APK | 按原布局读 | 原id/fp与attempts |
| v1库→故障v2 APK | ALTER后显式抛异常 | 迁移事务回滚；user_version仍1，last_http列不存在，原行仍在 |
| 上述原v1库→修复v2 APK | ALTER成功并记迁移事件 | user_version2；原id/fp/attempts不变，新增列为none |
| v2库→v1布局程序 | 本例onDowngrade拒绝 | 不清库，不伪造旧程序已兼容新布局 |

[SQLiteOpenHelper的onUpgrade](https://developer.android.com/reference/android/database/sqlite/SQLiteOpenHelper#onUpgrade(android.database.sqlite.SQLiteDatabase,int,int))在事务中执行，抛异常会回滚。失败开关专门放在ALTER之后，让测试不能只证明“什么都没做所以没丢数据”。失败发生时界面显示“迁移/存储失败，原数据库保留，请安装修复版本”，不发送依赖失败账本的后台工作；它不把旧预约改成rejected。

**必须从真实v1库升级。** 空装故障v2走onCreate，不走onUpgrade，因而不会触发本例故障；拿空装成功截图证明迁移可靠，像测试桥梁时绕河而行，鞋子干净，承重仍未知。

还要区分“迁移抛异常全部回滚”和“错误迁移曾经成功提交”：前者可以在保留v1库上安装修复v2后重做；后者不能简单改写已经发布的1→2步骤，已完成迁移的设备不会自动重跑。生产应增加新的纠错迁移，处理实际可达旧版本集合。本单元实际验证前一种，后一种给出明确设计边界。

## 同一数据穿过安装链的判据

前一页的原意图是`resources-D-original-1`690–720；随后`resources-D-next-1`810–840只queued。升级测试至少核：

- 原accepted完整JSON与booking/event身份没有变，不只是预约总数相同；新queued仍未被发出，草稿仍与它相符。
- 资源原行的actor/id/fp/attempts和schema版本/列，坏迁移后仍是v1；好迁移后仅出现预期新列/迁移事件。
- 异签或降级安装实际失败，已装版本与数据保留；不能卸载重装后冒充更新成功。
- release v3的实际APK签名证书与debuggable标志；同一applicationId和数据继续存在。release不能run-as是另一个调试边界，不等于“无法验证任何状态”：本教学包提供用户显式“导出合成实验状态”，只对固定合成数据输出，不给真实App引入隐秘导出后门。

平台受理安装与SQLite成功迁移不是一条跨层原子事务。可能“新APK已装上，但打开数据库失败”，此时需要保全文件和发布修复，而非删库维持启动率。备份、数据损坏、卸载/清数据与设备迁移也各有合同，本轮不由一次更新外推。

## 一个可评估的兼容矩阵

| 改变的条件 | 当前可迁移的设计 | 应重新验证的接口 |
| --- | --- | --- |
| 无相机或权限撤回 | 可选能力降级，业务身份不变 | 目标设备实际枚举/权限提示/用户恢复 |
| 后台配额更紧 | 持久原意图、受约束重试、保守预算 | 目标API/OEM的任务时机、停止原因与用户等待反馈 |
| 服务接口/epoch升级 | 同键原结果不能随APK更新抹掉 | 新旧协议、fence发现与保留期；回SE82版本演进主解释 |
| DB2新增字段 | 显式迁移，旧行有定义默认值 | 所有实际可达旧schema、成功/失败切面与纠错迁移 |
| 签名key轮换 | 不偷偷卸载或换applicationId伪成升级 | 平台支持的签名历史、分发渠道与恢复策略 |
| min26目标真机 | 状态归属、授权与协议分层可复用 | API分支/安装/硬件/后台行为；本轮API35不是API26实测 |

跨平台共同问题是能力授权、异步执行、持久身份、更新后解释旧数据；Android特有的危险权限流程、JobService生命周期、APK签名/版本与本地数据API必须依平台文档实现。把Linux有进程或Web有fetch当成这些细节已经验证，会跳过恰好最容易丢状态的部分。

## 迁移题与完整答案

1. **把versionName从1.9改2.0，但versionCode仍1。**  
   答：展示名不替代平台更新顺序；正式版本用明确递增code。是否能覆盖相同code还取决于安装通道/操作，不能以实验工具-r的行为当商店版本政策。
2. **异签APK安装失败，先卸载旧包再装就成功了。算升级兼容吗？**  
   答：不算。卸载改变签名比较与数据保留前提。应保留拒绝事实，解决合法签名/历史与发布合同，不把删应用写成无损迁移。
3. **故障v2在空设备能打开。能宣布旧用户升级通过吗？**  
   答：不能，空库走onCreate。要保留v1原行，实际运行onUpgrade，在ALTER之后失败，再核user_version1、无新增列与原行不变。
4. **迁移已经成功写成错误值，更新同一个1→2函数能自动修旧用户吗？**  
   答：不能假设重跑。已在schema2的库通常不再调用该步，应设计2→3等纠错路径，并覆盖实际旧状态。本文失败v2是事务回滚，不能混同这两种历史。
5. **release同签更新成功，但教学HTTPS拒绝。应该复制debug CA进生产吗？**  
   答：不为过实验扩大信任。APK来源校验与TLS目标信任是两条链；release默认不信教学CA是预期边界，生产应配置真实目标/证书与安全政策，保留原业务记录和明确错误。
6. **把budget字段迁移时全部置0，新后台最多再试三次。**  
   答：破坏跨更新预算合同。需要保留原attempts；若政策有明确用户同意的额度更新，应版本化并解释成本，不能用schema升级暗中清账。
7. **API35模拟器同签三版通过，是否还必须买全品牌手机才能交本课？**  
   答：不需要把全部生产部署添成课程关闭条件。但必须清楚证据只覆盖该环境，给设备/API/OEM/签名渠道/数据迁移的具体复核接口，不冒称真机、商店或真人已验。
