# 软件与构建环境：区分安装成功、兼容和可重现

> **学习位置**：[[计算机知识/00-开始/课程地图/13-Linux-课程地图|Linux课程地图]] · **适用边界**：GNU/Linux；Bash 与 systemd 示例单独标明，命令先审计后执行。

## 包管理器管理的是一组契约

发行版包管理器维护版本、依赖、文件归属、配置和签名等信息。apt/dpkg 与 dnf/rpm 不是同一命令体系，发行版版本和仓库策略也不同。安装前先识别系统、架构、仓库来源与权限需求，不把一条网上命令当跨平台通用解决方案。

直接下载脚本并以管理员权限执行，会把远程内容、传输路径和脚本逻辑放进高信任边界。应先取得、审查、验证来源和完整性，再决定执行；哈希只能验证与某个预期值相符，预期值本身也要可信。

## 从源代码到产物的依赖图

预处理、编译、汇编和链接产生不同中间产物。构建系统需要知道目标依赖哪些输入，增量构建只重做受影响部分。漏记头文件或代码生成器依赖会导致“修改后不生效”，过度声明则浪费时间。

Make 的时间戳模型、Ninja 的执行图和 CMake 的配置生成角色不同。交叉编译需要区分 build/host/target 的语境，以及 sysroot、工具链和目标依赖；在本机成功链接不证明能在目标系统加载。

## 环境隔离的不同层

Python venv 隔离部分解释器包环境，不虚拟化内核；容器封装用户空间与隔离设置，不天然固定宿主内核；虚拟机提供另一层硬件与内核边界。动态库搜索路径、环境变量、locale、时区和工作目录都可能影响程序行为。

可重现构建要求相同定义的输入得到相同产物，通常需要控制依赖版本、工具链、时间戳、路径和随机性。版本锁定不等于二进制重现，二进制重现也不等于软件安全或科学结果正确。

## 调试与二进制检查

file 判断文件类型，readelf/objdump 查看目标格式与符号/指令，ldd 类工具检查动态依赖时要注意对不可信文件的风险及工具实现。编译时保留调试信息，必要时选择更易调试的优化等级；不能因为优化后的变量“消失”就直接判断内存损坏。

gdb 的断点、调用栈、寄存器与内存查看应围绕假设使用。core dump 可能含密钥和私人数据，收集与共享前必须审查。AddressSanitizer、UndefinedBehaviorSanitizer 和线程检测工具覆盖不同错误，测试没有报告不证明不存在所有错误。

## 依赖更新与供应链

锁文件要包含实际解析出的传递依赖，哈希清单要覆盖允许安装的产物；只锁一个顶层包仍可能让下层版本变化。更新应在独立分支或环境中运行测试，记录变更与回滚方案。SBOM 帮助列出组成，不直接证明每个组件没有漏洞。

**练习**：两台机器安装了同名同版本包，结果就必然一致吗？还可能有不同架构构建、编译选项、动态库、locale、CPU 指令能力和外部数据。先定义需要重现的是依赖集合、字节产物、功能结果还是性能指标，再控制对应输入。
