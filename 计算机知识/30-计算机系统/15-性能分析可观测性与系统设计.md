# 性能分析、可观测性与系统设计

## 本课目标

学完后，你应该能够：

- 把“系统要更快”改写成带工作负载、指标、边界和正确性约束的需求；
- 区分 wall time、CPU time、延迟分位数、吞吐、利用率、队列长度与服务时间；
- 沿“需求 → 指标 → 测量 → 归因 → 最小改动 → 复测”建立证据链；
- 用 Amdahl 定律约束端到端收益，用 Roofline 判断计算 kernel 更接近计算还是数据移动上限；
- 正确选择 metrics、profiling、tracing 与 logging，并识别观察扰动、基准幻觉和错误因果。

## 1. 性能不是一个数字，而是一份契约

“把 API 优化一下”缺少至少五项信息：

1. **工作负载：**输入大小/分布、请求到达模式、并发、读写比例、冷/热状态；
2. **边界：**只测一个函数、一个进程、一个 GPU kernel，还是用户端到端体验；
3. **指标：**p95 latency、request/s、token/s、CPU/GPU/内存、能耗还是成本；
4. **正确性与可靠性：**输出容差、错误率、超时、拒绝、数据一致性和安全边界；
5. **约束：**硬件、预算、功耗、版本、部署拓扑和维护复杂度。

一条更可测的教学需求可以写成：

```text
在固定模型 revision、输入/输出长度分布与 8 个并发客户端下，
稳态 15 分钟窗口内：
- 成功请求的 TTFT（time to first token，首 token 时间）p95（95% 样本不超过的分位数）≤ 800 ms；
- ITL（inter-token latency，相邻 token 间隔）p95 ≤ 80 ms；
- 超时 + 5xx ≤ 0.5%；
- 机器总内存不超过预算且不得以截断答案换取达标；
- 另外单独报告冷启动，不把它混入或藏在稳态结论中。
```

这里的数值只是练习输入，不是通用生产标准。真正阈值来自用户体验、容量与风险，而不是从某次 benchmark 反推。

## 2. 从需求到归因的闭环

```text
需求与正确性约束
      ↓
选择端到端与分层指标
      ↓
固定工作负载、环境、版本与测量边界
      ↓
建立可重复基线和分布
      ↓
metrics 发现“何时/多大范围异常”
      ↓
trace 定位“请求在哪个阶段等待”
      ↓
profile 定位“CPU/GPU 时间花在哪段代码”
      ↓
logs 解释离散事件、错误与状态变化
      ↓
形成一个可证伪假设，只改一个主要因素
      ↓
验证正确性，复测端到端与资源/尾延迟
```

这不是必须调用所有工具的仪式。小型本地程序可能只需正确性测试、monotonic timer 和采样 profiler；分布式在线服务则需要 trace 关联网络、队列、存储与计算。工具应由问题决定。

## 3. Wall time 与 CPU time 回答不同问题

**Wall time（elapsed time）**是从开始到结束实际经过的 duration，接近用户等待或批任务完成时间。测量同一进程中的 duration/deadline 应优先使用 monotonic clock，避免 NTP/人工校时等让 realtime/civil clock 倒退或跳变。日历时间戳另有用途：它适合回答“事件在什么时刻发生”并与外部记录对齐，但不应直接作为本地 timeout 倒计的唯一时钟。

**CPU time**是进程或线程实际获得 CPU 执行的累计 user + system time。它排除的是线程真正阻塞、睡眠等待网络/磁盘/锁或被调度出去的那段时间；**自旋、忙轮询、反复检查队列等即使逻辑上“在等”，只要线程仍在 CPU 上执行，就会计入 CPU time。** 多线程并行时，各线程 CPU time 相加可以大于 wall time：

```text
4 个线程各忙 1 秒并大致并行
wall time ≈ 1 秒
累计 CPU time ≈ 4 秒
```

反过来，一个请求 wall time 10 秒但 CPU time 20 毫秒，更像在等待 I/O、锁、队列、定时器或其他进程，并不能据此断言“机器 CPU 性能差”。GPU 工作通常异步提交；CPU timer 可能只测到 launch/enqueue，必须在结果真正可消费的边界同步，或用对应 device timeline。

CPU monotonic clock、GPU event clock、NIC/PTP clock 与另一台主机的 realtime clock 可能属于不同 **clock domain**。其中各自的 duration 可在本域中有意义，但要把起止时间戳直接拼成一条跨 CPU/GPU/主机 timeline，必须说明校准方法、同步误差与不确定性。只看未校准的绝对时间戳，不能证明两个跨域事件的微小先后。

**反例：**优化后 CPU time 下降 30%，就宣称用户延迟下降 30%。若用户主要等网络或队列，wall time 可能几乎不变；若引入并行，CPU time 甚至可能上升而 wall time 下降。

## 4. 延迟必须看分布和条件

平均值会把少量极慢请求稀释。在线系统常报告 p50、p95、p99：p95 表示样本中约 95% 不超过该值，而不是“95% 的请求都恰好这么慢”。报告分位数时要一起给出：

- 样本量和时间窗口；
- 成功、失败、超时、取消与拒绝如何计入；
- 请求类别、输入大小和租户是否混合；
- 从客户端、入口、服务内部还是某个 span 计时；
- 冷启动与稳态是否分开。

分位数通常**不能相加**。检索 p99 + 推理 p99 不等于端到端 p99，因为两个阶段的慢样本不一定是同一请求。要从同一批 trace 直接计算端到端分布，再用 span 做归因。

### 避免 coordinated omission

若负载发生器“等上一个请求完成后才发下一个”，系统变慢时它也自动降低到达率，恰好漏掉真实用户仍持续到达时的排队。这个偏差称为 coordinated omission。应明确采用：

- closed-loop：每个客户端完成后再发，适合模拟有限并发用户；
- open-loop：按独立到达计划发请求，适合验证给定到达率下的容量；

两者回答不同问题。过载时必须保留计划发送时间、实际发送时间、排队、超时和拒绝，不能只统计幸存成功请求。

## 5. 吞吐、利用率与排队不是同义词

**吞吐**是单位时间完成的工作，例如 request/s、output token/s、GB/s。必须写清分子：完成请求、输入 token、输出 token 或字节不能混为一个“速度”。

**利用率**描述资源在时间窗口内的忙碌比例，但“忙”由计数器语义决定：CPU 可能算 user/system/iowait 不同类别；GPU utilization 常表示采样窗口内是否有 kernel 活动，不等于 Tensor Core、显存带宽或每个 SM 都达到峰值。100% 利用率不是目标函数，也不能指出是哪种上限。

**排队**连接到达与服务能力。用稳定系统的 Little 定律建立直觉：

$$
L = \lambda W
$$

其中 $L$ 是系统内平均工作数，$\lambda$ 是平均完成/到达率，$W$ 是平均逗留时间；使用它要保证同一边界、相对稳定和单位一致。它不直接给出 p99，也不保证任意瞬时窗口成立。

当到达率逼近可持续服务率时，微小波动就可能造成长队，尾延迟通常非线性上升。因此：

- 吞吐仍在上升，不代表延迟健康；
- 资源未达 100%，也可能被锁、串行阶段、单队列或外部配额限制；
- 更大 batch 可能提高总吞吐，同时恶化单请求等待和 token 间隔；
- 更大 buffer 可能减少即时拒绝，却把过载藏成更长排队。

LLM 服务的 TTFT、TPOT/ITL、端到端 latency 与输出 token throughput 的准确边界见 [[AI/20-LLM/40-推理/03-批处理调度延迟吞吐与投机解码|批处理、调度、延迟、吞吐与投机解码]]。

## 6. Amdahl 与 Roofline：一个看端到端，一个看计算上限

### Amdahl：局部优化能影响总时间多少

若原总时间中比例 $p$ 的部分被加速 $S$ 倍，理想总加速为：

$$
Speedup_{total}=\frac{1}{(1-p)+p/S}
$$

例：某 kernel 占端到端时间 20%，即使它无限快，理想总加速也不超过 $1/(1-0.2)=1.25$ 倍。Amdahl 要求 $p$ 来自同一基线边界；优化后其他比例会变化，还可能新增复制、同步和排队，不能永远沿用旧占比。

### Roofline：kernel 更接近搬运还是计算上限

$$
Arithmetic\ Intensity=\frac{Useful\ Operations}{Bytes\ Transferred}
$$

$$
Attainable\ Performance \le \min(Peak\ Compute,\ Bandwidth \times Arithmetic\ Intensity)
$$

低算术强度工作更可能受数据移动限制，可尝试减少 bytes、提高复用或融合；接近计算平顶时才更关注指令吞吐、专用单元与算法。必须说明 bytes 是 DRAM、L2 还是其他层，operations 如何计算。Roofline 是上界分类，不自动涵盖锁、网络、排队、kernel launch、分支和负载不均衡。

两者组合使用：

```text
端到端 trace / timeline 找到占比 p
  → Amdahl 判断“值得投入的最大收益”
  → 对关键 CPU/GPU kernel 用 Roofline 判断优化方向
  → 优化后回到端到端重测，不把 kernel 加速当服务加速
```

CUDA 上的设备 timeline、kernel counters、hierarchical Roofline 与 occupancy 边界见 [[计算机知识/40-并行与异构计算/01-CUDA/09-Roofline与Nsight性能方法|Roofline 与 Nsight 性能方法]]。

## 7. Metrics、Profiling、Tracing 与 Logging 各自回答什么

| 信号 | 适合回答 | 典型单位/结构 | 主要盲区与风险 |
| --- | --- | --- | --- |
| Metrics | 何时、哪些实例、异常多大？ | counter、gauge、histogram | 聚合会丢掉单请求因果；高基数标签可拖垮系统 |
| Profiling | CPU/GPU 时间、分配或硬件事件集中在哪段代码？ | sampled stacks、timeline、counters | 采样遗漏短事件；插桩/replay 会扰动；无法单独解释跨服务等待 |
| Tracing | 某请求跨网络/服务/队列在哪些 span 等待？ | trace ID、span、parent、时间与状态 | 采样可能漏掉稀有尾部；clock domain/同步误差、上下文传播和 span 边界会出错 |
| Logging | 哪个离散事件、错误、配置版本或状态转换发生？ | 结构化事件 + 时间 + severity | 原文泄密、同步 I/O、日志风暴；全文搜索不能替代指标 |

四者应通过版本、实例、request/trace ID 和时间窗口关联，但不要把用户正文、凭据、完整 prompt 或高敏感标识写入关联字段。LLM 的字段 allowlist、token 用量、质量回归和日志边界见 [[AI/20-LLM/70-工程应用与工具链/04-评测回归与可观测性|评测、回归与可观测性]]。

### 先问一个具体问题再开工具

- “CPU 时间集中在哪些函数？”→ 采样 CPU profiler；
- “请求卡在本进程、下游 RPC 还是队列？”→ 分布式 trace；
- “过去一小时从哪次部署开始恶化？”→ 按版本分组的 metrics + 部署事件；
- “为何某次请求被拒绝？”→ 有限、结构化、去敏日志；
- “GPU kernel 是 memory-bound 吗？”→ 设备 counters / Roofline，而不是只看 GPU utilization。

## 8. 从性能证据回到系统设计

性能调查不应止于“找到一个热点”。热点只是当前 workload 与拓扑下的结果；系统设计要让容量、等待和失败在边界上可控。

| 设计问题 | 可观察的契约 | 常见失败方式 |
| --- | --- | --- |
| 容量与余量 | 给定到达/长度分布下的可持续吞吐、尾延迟与资源余量 | 按实验室峰值满配，上线后任何波动都排队 |
| 入站控制 | 并发、队列容量、deadline、租户配额与拒绝原因 | 无限队列把过载藏成超时或 OOM |
| 隔离 | 长短任务、在线/离线、租户或故障域的资源边界 | 一个大任务、热点租户或下游故障拖慢所有请求 |
| 超时与取消 | 端到端 deadline 怎样分配并向下游传播 | 上游已超时，下游仍继续消耗 CPU/GPU |
| 重试 | 哪些错误可重试、幂等键、退避、抖动与总尝试预算 | 故障时同步重试放大负载，形成 retry storm |
| 降级与拒绝 | 过载时保留什么、减少什么、谁有决定权 | 静默降低质量、截断输出或丢请求来美化 latency |
| 缓存 | key、命中、失效、一致性、容量与隐私边界 | 命中率提高却返回过期/越权数据，或挤压真实工作集 |
| 异步化 | “已接收”和“已完成”的协议状态、队列持久性与查询方式 | 提前返回成功，却无法追踪、取消或恢复任务 |

端到端 latency budget 可以帮助每层发现异常，但不要把各层 p99 机械相加成总 p99；预算是设计约束，真实端到端分布仍要从同一批请求测量。资源也要保留故障和流量波动所需的 headroom，不能用“平均利用率尚未 100%”代替容量实验。

所有队列都应回答：容量按什么单位计算、满时谁等待/拒绝/丢弃、工作是否有 deadline、取消能否传播、队列驻留时间如何观察。网络 socket buffer、线程池、数据库连接池、GPU 调度队列和 LLM KV 预算虽然实现不同，却都不能靠无限扩容消除到达率长期超过服务率的问题。网络侧的压力传播见 [[计算机知识/30-计算机系统/14-网络栈Socket与端到端数据路径|网络栈、Socket 与端到端数据路径]]。

最后，把可观测性作为接口的一部分：版本和 request/trace ID 能跨边界传播；拒绝、超时、取消和降级都有有限类别；队列公开深度与驻留时间；指标标签受控；日志默认去敏；恢复操作能被同一组端到端指标验证。没有这些设计，事故后再“加日志”通常只会得到大量无法关联的文本。

## 9. 观察会改变被观察系统

可观测性不是免费的：

- 每次函数插桩会增加调用、时间戳与 buffer 开销；高频短函数尤其敏感；
- sampling 降低开销，但频率太低会漏掉稀有路径，太高会抢 CPU；
- `strace` 一类 syscall tracing 可能显著改变 syscall 密集程序的调度与时序；
- 同步日志会持锁、格式化、分配并写 I/O；异步日志也有队列、丢弃与内存成本；
- 高基数 metrics 标签会扩大内存、网络和存储成本；
- GPU profiler 可能 replay kernel、串行化活动或采集多轮 counters；profiled runtime 不能直接当生产延迟；
- 全量分布式 tracing 会增加 header、序列化和导出流量，采样策略又可能漏掉尾部。

因此应记录“工具、配置、采样率、是否附加到运行中进程、持续时间”，并比较 instrumentation off/on 的关键指标。若观察开销与目标改变量同量级，结论不可信。先在副作用可控的代表负载中缩小问题，再对生产使用最低必要观测。

## 10. 基准幻觉：数字很精确，问题却测错了

### 常见来源

1. **首次运行混入或被隐藏：**JIT、动态链接、page fault、模型加载、autotune、连接建立与 cache warm-up；冷启动和稳态应分别报告。
2. **边界偷换：**只测 kernel，不计 H2D/D2H、tokenization、排队或同步，却用结果声称端到端变快。
3. **工作被优化掉：**微基准结果未被消费，编译器删掉计算；必须验证输出且避免 UB。
4. **单次最快值：**调度、温度、频率、后台负载和 allocator 抖动被挑选性忽略；应多轮报告分布与环境。
5. **输入失真：**全是相同长度、全零、可压缩或 cache-fit 数据，不代表真实长度与访问分布。
6. **并发模型失真：**只测 concurrency=1，却承诺在线容量；或固定最大并发，把排队失败从统计中删除。
7. **正确性退化换速度：**少算 token、降低精度、跳过校验或丢请求，却不报告质量、错误和拒绝。
8. **把相关当因果：**CPU 90% 与延迟尖峰同时发生，不证明 CPU 是根因；二者可能都由同一流量峰值造成。
9. **跨机器比较未归一：**版本、编译选项、NUMA、功耗、容器配额和后台共享不同，却把结果归因给一行代码。
10. **时钟域混用：**用 realtime clock 做 timeout，或把未校准的 host/GPU/跨主机时间戳当成精确因果顺序。
11. **只看均值和成功者：**超时、OOM 与被拒请求从样本消失，剩余平均值反而“改善”。

### 反例：三个漂亮但无效的结论

- “GPU utilization 从 60% 到 95%，优化成功。”如果 p95 TTFT 更差、功耗更高或只是 batch 变大，这不是已证明的目标改善。
- “热点函数快 2 倍，所以 API 快 2 倍。”若它只占 10%，Amdahl 的无开销理想上限约为 $1/(0.9+0.1/2)\approx1.053$ 倍。
- “新版本平均延迟下降。”若 p99 翻倍且超时被排除，用户体验可能更差。

## 11. 逐步案例：归因一个 LLM 服务的 p95 TTFT 回归

这是推理方法示例，数字均为教学假设，不是实测结果。

### 步骤 1：重述需求与变化

部署后 p50 TTFT 变化小，p95 从 700 ms 升到 1.6 s；吞吐上升 10%，错误率未变。先保留模型 revision、硬件、请求长度分布、到达率和部署版本，不能只写“模型变慢”。

### 步骤 2：验证样本可比

按 prompt 长度、租户、冷/热、并发分层；把超时/拒绝纳入；确认客户端计时含相同网络边界。若新窗口恰好有更多长 prompt，应先调整比较或明确 workload shift。

### 步骤 3：用 trace 分解同一批慢请求

为每个请求关联：入口 → 等待队列 → tokenization → prefill → decode 首步 → 首字节发送。假设慢请求的 queue span 增长，而 prefill service time 基本不变，这将问题从“GPU kernel 变慢”缩到“调度/容量造成排队”。

### 步骤 4：用 metrics 检查队列机制

对齐 active sequences、scheduled prompt/decode tokens、KV 使用、队列深度/驻留时间与到达率。若 continuous batching 把更多请求留在设备侧，总吞吐可能上升，同时新请求等待首 token 更久；这正是吞吐—尾延迟折中，不是矛盾。

### 步骤 5：仅在证据指向代码时 profile

若 trace 显示 prefill 本身变慢，再用 CPU/GPU timeline 判断 host preparation、H2D、kernel、同步和空隙；确认关键 kernel 占比后才进入 Roofline/counters。不要因为 GPU 图最醒目就跳过队列证据。

### 步骤 6：提出一个最小、可证伪的改动

例如降低每轮 prefill token 预算并与 decode 交错，预测是“长 prompt TTFT 可能略增，但已有请求 ITL 与总体 p95 TTFT 改善；吞吐可能下降”。固定相同到达序列复测，并检查饥饿、KV、错误、吞吐与质量，不能只挑获益指标。

### 步骤 7：恢复与决策

若 SLO、正确性或容量预算未改善，恢复原调度配置；保留版本、输入、原始分布摘要和假设结果。性能实验失败仍是有效证据，不应通过改名指标来宣布成功。

## 12. 只读观察清单与平台差异

下面命令只查询现有系统状态，不修改配置、不启动 profiler 记录文件，也不主动产生网络请求。连续采样仍消耗少量 CPU，并可能看到用户名、路径、进程和设备信息；限定 PID、轮数与分享范围。

### Linux

```bash
# 将 PID 换成已确认且有权限观察的进程号。
ps -o pid,ppid,etime,time,%cpu,%mem,rss,vsz,stat,comm -p PID

# 有限次数的系统、磁盘和目标进程观察；命令可能来自不同软件包。
vmstat 1 5
iostat -xz 1 5
pidstat -dur -p PID 1 5

# NVIDIA 驱动提供时，有限窗口查看利用率、功耗、显存等采样。
nvidia-smi dmon -s pucm -c 5
```

`ps` 的 `time` 是累计 CPU time，不是 wall time；`%CPU` 的多核表示随工具而异。`iostat` 通常来自 sysstat，`pidstat` 也常来自 sysstat，极简系统可能没有；首次 `vmstat` / `iostat` 行可能是自启动以来平均值，须读本机手册。`nvidia-smi` 的 utilization 是采样指标，不是 Roofline 结论，也不适用于 AMD/Intel/Apple GPU。

### macOS

```bash
ps -o pid,ppid,etime,time,%cpu,%mem,rss,state,comm -p PID
top -l 1 -pid PID -stats pid,command,cpu,time,mem,state
vm_stat
iostat -w 1 -c 5
```

macOS 的 BSD `ps` / `top` / `iostat` 字段和参数与 GNU/Linux 不同；`vm_stat` 的 page size 应以输出为准，不能把 page 计数直接当字节。Apple GPU 也不能用 `nvidia-smi`。

### Windows PowerShell

```powershell
Get-Process -Id PID | Select-Object Id,ProcessName,CPU,WorkingSet64,PrivateMemorySize64,StartTime
Get-Counter '\Processor(_Total)\% Processor Time' -SampleInterval 1 -MaxSamples 5
Get-Counter '\PhysicalDisk(_Total)\Disk Transfers/sec' -SampleInterval 1 -MaxSamples 5
```

`Get-Process.CPU` 是累计 CPU 秒数，不是瞬时百分比；performance counter 名称可能因系统语言、本机实例和版本而不同。容器内看到的 CPU、内存和 PID 还受 namespace/cgroup 或 Windows 容器边界影响，不能自动代表宿主整机。

> [!warning] Profiler 命令为何不放进“无副作用观察”练习
> attach profiler 会占用权限和资源，record 通常创建报告文件；某些 GPU profiler 会 replay 被测 kernel，某些程序本身会写文件、发请求或修改数据。应先在副作用受控的 benchmark 中阅读本机工具手册，明确输出路径、采样率、持续时间与目标程序，再使用 `perf`、eBPF 工具、`py-spy`、Nsight、Instruments、ETW/WPR 等平台工具。它们不能被当作一条可无脑复制的跨平台命令。

## 13. 练习：写一份可证伪的性能调查卡

选择一个无生产副作用的现象，例如“本地测试程序在输入增大后变慢”或纸面上的“LLM 服务 p95 TTFT 回归”。填写：

```text
需求与用户后果：
正确性/错误率约束：
工作负载与到达模型：
硬件、软件版本与资源配额：
测量边界：
端到端主指标（含分位数/样本量/窗口）：
分层辅助指标：
wall time 与 CPU time 各回答什么：
队列边界、容量单位、到达率与服务率：
当前证据支持的一个假设：
能证伪它的下一项测量：
观察工具可能造成的扰动：
最小改动、预测、正确性复核与恢复：
```

再完成三个计算/判断：

1. 一个阶段占原端到端时间 30%，被加速 3 倍。用 Amdahl 计算无额外开销的理想总加速：$1/(0.7+0.3/3)=1.25$ 倍。
2. 平均到达率 40 request/s，平均系统逗留 0.25 s。在稳定、边界一致的教学假设下，用 Little 定律估计平均系统内有 $40\times0.25=10$ 个请求；解释这不能推出 p99。
3. 为“本进程 500 ms 后超时”与“日志记录当地日历时刻”分别选 monotonic/realtime clock，解释为何不应反过来；再列出把 GPU event 与 host span 合并时需要的校准证据。
4. 某 GPU kernel 的 arithmetic intensity 很低且已接近 DRAM bandwidth ceiling。说明为何“提高理论 FLOPS”通常不是第一方向，并列出减少 bytes、提高复用或融合的一个候选假设。

### 成功标准

- 能把性能目标写成包含 workload、边界、分布、正确性与资源约束的可测需求；
- 能用不同例子区分 wall time、CPU time、latency、throughput、utilization 与 queueing；
- 能为 duration/deadline 与 civil timestamp 选对时钟，并识别未校准的跨 CPU/GPU/主机 clock-domain 推断；
- 能说明分位数为何不可直接相加，超时/拒绝为何不能从样本删除；
- 能用 Amdahl 约束局部优化的端到端收益，并用 Roofline 选择 kernel 优化方向；
- 能根据问题选择 metrics、profile、trace 或 logs，并记录观察扰动；
- 能识别至少五种基准幻觉，且复测同时覆盖正确性、端到端、尾延迟与资源成本。
