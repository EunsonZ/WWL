# 音频编码：变换、心理声学、码率与延迟

## 本课目标

学完后，你应该能够：

- 区分 codec、bitstream、container、文件扩展名和 metadata；
- 解释 frame、window、overlap、transform、quantization 与 entropy coding 的责任；
- 用听觉遮蔽理解有损 codec 如何分配误差，而不是笼统说“删掉人耳听不到的声音”；
- 区分 CBR、VBR 和受约束 VBR/ABR，并按网络与存储目标选择；
- 说明 MP3、AAC、Opus 和 FLAC 的定位与不能由格式名推出的结论；
- 把 algorithmic delay、packetization、jitter buffer、pre-skip、end trim 和 gapless playback 分开；
- 解释为什么有损转码会累积损失，而转为 FLAC 不会恢复原始 PCM。

学习前先完成 [[计算机知识/60-数据编码与媒体系统/06-数字音频采样量化PCM与响度|数字音频：采样、量化、PCM 与响度]]；窗口、DFT、STFT 的数学权威页是 [[数学/70-信号处理与多模态数学/02-采样定理波形STFT与Mel频谱|采样定理、波形、STFT 与 Mel 频谱]]，编码长度与熵的数学入口是 [[数学/50-信息论/00-信息论-MOC|信息论 MOC]]。

## 1. 先拆开五个经常混用的名词

| 层 | 例子 | 决定什么 |
| --- | --- | --- |
| 原始表示 | PCM sample frames | 采样率、声道、样本格式与时长 |
| codec | MP3、AAC、Opus、FLAC | PCM 与压缩位流之间怎样编码/解码 |
| bitstream | Opus packet、FLAC frame 等 | codec 语法和压缩载荷 |
| container/encapsulation | Ogg、MP4/M4A、Matroska、ADTS 等 | 轨道、时间戳、索引、metadata，以及如何装载位流 |
| 文件扩展名/MIME | `.m4a`、`.ogg`、`audio/ogg` | 给软件的线索，不足以唯一确定 codec/profile |

例如 `.m4a` 常是 ISO Base Media File Format 家族容器的使用约定，不等于“AAC 算法本身”；Ogg 可以封装 Opus 或其他 codec。只改扩展名既不转码也不改变位流。

> [!failure] 反例：播放器能打开 `.ogg`，所以它支持所有 Ogg 音频
> 错。容器解析和内部 codec 解码是两项能力。还需验证具体 mapping、声道、采样率、metadata 和 seek 行为。

## 2. 为什么要分帧与加窗

真实音频很长且随时间变化，编码器通常把它切成短帧处理。帧长度形成权衡：

- 长帧对稳定音调的频率表示更集中，头部开销相对小，但突发变化定位差、延迟高；
- 短帧能更快响应瞬态、降低部分缓冲延迟，但频率分辨率和压缩机会减少，头部比例增加。

直接截断一帧会在边界制造突变。变换 codec 通常给重叠片段加窗，再以 lapped transform 让相邻帧共同重建。编码中的 **frame**、网络 **packet** 和容器 **sample** 不一定一一对应：一个 packet 可装多个 codec frame，容器也可按自己的时间单位索引。

### 可观察例子：20 ms 不是端到端 20 ms

48 kHz 下 20 ms 是 960 个 sample frame。但实时发送还可能等待：

```text
采集缓冲 + codec look-ahead/重叠 + frame 聚合
+ 网络传输 + jitter buffer + 解码 + 播放设备缓冲
```

因此“codec 使用 20 ms frame”不能推出通话端到端延迟为 20 ms。

## 3. 变换、量化与熵编码

一种典型感知音频编码流程可以抽象为：

```text
PCM → 分帧/加窗 → 时频变换（常见 MDCT 类）
    → 频带能量与心理声学分析 → bit allocation
    → 系数量化 → entropy coding → frame/packet/container
```

解码器反向执行熵解码、反量化近似、逆变换和 overlap-add。

### 3.1 MDCT 为什么常见

MDCT 是重叠的实数 lapped transform，能把相邻帧共同表示，减少简单独立分块的边界不连续。稳态声音可用较长窗口提高频率选择性；遇到瞬态时，许多 codec 会切到较短块/窗口以控制 **pre-echo**——量化噪声在时间上扩散到瞬态之前的现象。

变换本身可以构成可重建分析/合成对；主要有损点通常是量化、丢弃/合并信息、带宽限制和某些参数化工具。熵编码根据符号概率减少冗余，本身不需要再牺牲解码后的系数。

### 3.2 预测与变换可以组合

不是所有音频 codec 都只有 MDCT。语音在短时内可被线性预测有效描述；Opus 因而包含基于线性预测的 SILK 层和基于 MDCT 的 CELT 层，并可按模式组合或切换。FLAC 则使用无损预测，把样本与预测值之差作为 residual，再无损编码 residual。

## 4. 心理声学：管理可听误差，不是绝对删除清单

有损编码器在给定码率下不可避免地产生误差。心理声学模型估计误差放在哪里更不容易被听见，例如：

- 强音附近可能掩蔽相近频率的弱音（同时掩蔽）；
- 强瞬态前后存在时间掩蔽，但前掩蔽窗口短，处理不当会出现 pre-echo；
- 人耳在不同频率的敏感度不同；
- 左右声道相关时可用 joint stereo 等工具减少冗余，但要控制空间感损伤。

编码器据此给不同频带/声道分配 bit、选择量化步长和编码工具。真实阈值依内容、声压、设备和听者而变，所以“人耳绝对听不到”通常是过度陈述。低码率、级联转码、训练数据异常、纯音、打击乐和空间音频都可能暴露伪影。

## 5. CBR、VBR、ABR 与瞬时码率

| 模式 | 约束重点 | 优势 | 风险/误区 |
| --- | --- | --- | --- |
| CBR | 每个时间单位接近固定 bit 预算 | 网络/缓冲预算简单、随机访问可预测 | 简单段可能浪费，复杂段可能质量不足；容器开销后文件仍不必逐字节恒定 |
| VBR | 按内容复杂度改变 bit 数 | 固定主观质量目标下通常更有效 | 峰值码率和文件大小较难预先严格保证 |
| ABR/受约束 VBR | 一段时间平均或峰值受约束 | 在质量弹性和带宽边界间折中 | “平均达到目标”不表示每帧恒定，也不保证网络瞬时不堵塞 |

名义码率不是质量单位。不同 codec、profile、encoder 版本、声道、采样率、内容和延迟设置下，同一个 `128 kbit/s` 不能直接视为同质。网络应用还要看 packet overhead、FEC/冗余、重传策略、DTX 和 packet loss concealment。

### 文件大小估算

若平均 payload bitrate 为 $R$ bit/s，时长为 $T$ 秒：

$$
\text{payload bytes}\approx\frac{RT}{8}.
$$

3 分钟、128 kbit/s 约为 $128\,000\times180/8=2\,880\,000$ byte。容器、索引、标签、封面和 padding 会额外增加；VBR 的实际平均码率需从完成文件测量。

## 6. 四种 codec 的定位

下表的规范/项目入口于 **2026-09-03** 核验。它是工程定位，不是没有固定测试条件的音质排行榜。

| Codec | 核心性质 | 常见定位 | 关键边界 |
| --- | --- | --- | --- |
| MP3（MPEG-1/2 Audio Layer III） | 有损感知编码，filterbank/MDCT、量化与熵编码 | 历史兼容、音乐/播客分发存量 | 老格式生态广；gapless 信息、标签和精确时长依容器/约定/播放器，不能只靠裸帧假设 |
| AAC 家族 | MPEG 感知音频工具家族，AAC-LC 等 profile 及后续扩展 | MP4/M4A、广播、移动/流媒体生态 | “AAC”不是单一 profile；LC、HE-AAC、xHE-AAC、ELD 等能力/延迟不同，必须写清 profile、transport 和 decoder |
| Opus | IETF 交互式语音与音频 codec，结合 LP 与 MDCT 路线 | VoIP、会议、游戏语音、WebRTC，也可做音乐/文件 | frame、码率、带宽、VBR/CBR、FEC/DTX 可调；容器映射、pre-skip、packet loss 策略和端到端缓冲需单测 |
| FLAC | 无损预测编码，分块、预测、residual/Rice 类熵编码 | 归档、制作交换、无损音乐库 | 恢复的是送入编码器的 PCM；不会恢复更上游丢失的频率、位深、metadata 或有损编码前的 PCM |

### 6.1 选择不是“越新越好”

- 要在未知老设备播放，MP3 的实际兼容性可能比更高效的新格式重要。
- 已固定在 MP4/Apple/广播生态时，要按明确 AAC profile 和 transport 验证。
- 交互语音需要低延迟、丢包恢复和网络自适应时，Opus 的设计目标匹配，但仍要测整条链。
- 保存可重复编辑的 master 时，PCM/FLAC 类无损链路通常比任何感知有损分发副本更合适。

这些是候选方向，不是授权、专利/许可或目标平台支持结论；产品交付需按目标地区、实现和分发条款单独核验。

## 7. 延迟账本

端到端单向延迟可按责任拆成：

$$
L_{total}=L_{capture}+L_{frame}+L_{lookahead}+L_{encode}
+L_{packetize}+L_{network}+L_{jitter}+L_{decode}+L_{render}.
$$

其中：

- `frame`：等够一个或多个帧；
- `lookahead`：编码算法为判断未来样本而等待；
- `packetize`：把多个帧聚合进包，节省头部却增加等待；
- `jitter buffer`：为吸收网络时延波动而缓存；
- `render`：操作系统、设备和硬件播放缓冲。

“编码速度快于实时”只说明吞吐，不说明首帧延迟或交互延迟。离线文件压缩可以容忍较长 lookahead 来换质量；实时会话则需把质量、丢包韧性和 latency 一起测。

## 8. Pre-skip、end trimming 与 gapless

变换窗口、预测状态和 resampler 会使解码输出包含 codec delay 或启动样本。若容器/映射不告诉播放器哪些样本应丢弃，文件开头会多出静音/过渡，连续曲目边界也会错位。

### 8.1 Ogg Opus 的明确时间边界

RFC 7845 定义 Ogg Opus mapping 的 `pre-skip`：播放器从初始解码输出中丢弃指定数量的 48 kHz 样本，以补偿 codec delay 或完成精确剪辑；granule position 还用于确定页面结束位置和尾部裁剪。pre-skip 是封装层的播放时间语义，不应误认为 Opus 位流“没有延迟”。

### 8.2 Gapless 需要编码器、封装和播放器协作

连续专辑或循环素材要无缝播放，必须知道：

- 原始 PCM 的精确起止 sample frame；
- encoder delay/pre-skip；
- 末尾为补齐 frame 加入的 padding/end trim；
- 播放器是否理解并连续调度这些信息。

MP3 生态常借助 encoder/container metadata 记录 delay 和 padding，但不同工具/播放器解释可能不同。把两个解码后的文件按“各自文件长度”拼接，不一定等于原始连续 PCM。

> [!failure] 反例：剪到整秒就天然 gapless
> 错。整秒不一定落在 codec frame 边界，codec delay 与 padding 也不会因时间标签好看而消失。验收应比较解码后 sample count、边界波形和实际连续播放。

## 9. 转码损失与“无损外壳”

有损 encoder 接收 PCM 并选择保留/量化信息：

```text
原 PCM ─有损 A→ 位流 A ─解码→ PCM_A
      PCM_A ─有损 B→ 位流 B ─解码→ PCM_B
```

第二个编码器面对的是已经带有 A 的误差和伪影的 `PCM_A`，其心理声学判断和变换边界通常又不同，所以损失可能累积；即便 A、B 使用同 codec、同码率也不是“重新整理比特”。避免代际损失的原则是始终从最早的无损 master 生成分发版本。

把 MP3 解码后存为 FLAC，会无损保存 `PCM_A`，但不会找回原 PCM。之后文件更大，只是停止继续增加编码损失。相反，remux 在不解码/重编码的情况下搬运兼容位流，通常不改变音频载荷，但可能改变 timestamps、metadata 或 gapless 信息，仍需审计。

### 可观察的转码实验设计（不依赖特定软件）

1. 保存同一份许可明确的无损 master 和精确 sample count。
2. 从 master 分别编码 A 与 B；另做 `master → A → decode → B`。
3. 全部解码为相同 PCM 格式，对齐 pre-skip/end trim。
4. 比较 sample count、边界、差分、频谱和盲听；记录编码器版本/参数。
5. 不把波形差异自动等同可听差异，也不把一次听不出自动等同数学无损。

## 10. 元数据、完整性与安全边界

音频文件可带标题、作者、歌词、封面、时间戳、设备、位置、loudness/replay gain、chapter 和 application-specific data。Codec 无损只约束音频样本的重建，不保证：

- tag、封面或 chapter 被转码器原样保留；
- gapless、channel layout 或 loudness metadata 被播放器采用；
- 嵌入图片、歌词和私有字段适合公开；
- 文件解析器面对异常长度、巨大封面或损坏 frame 时安全。

FLAC 的 STREAMINFO 可包含解码 PCM 的 MD5，用于检测流重建是否匹配该流记录的样本；它不是来源真实性、作者身份或恶意内容安全证明。对不可信媒体应限制文件大小、时长、channel count、metadata 长度和解码资源，并使用受维护的解析库。

## 11. 选择与验收模板

```text
用途：归档 / 下载分发 / 自适应流 / 实时交互
输入：sample rate、sample format、channel layout、时长、来源许可
codec：名称 + profile/mode + encoder version
container/mapping：名称 + timestamps/timebase
码率：CBR/VBR/ABR、目标与峰值约束
延迟：frame、look-ahead、packetization、jitter、设备缓冲
时间边界：pre-skip、end trim、解码 sample count、gapless
质量：代表性样本、盲听/客观指标、失败例
metadata：保留/删除清单，封面和隐私审计
兼容性：目标编码器、解码器、系统和硬件实测
恢复：保留无损 master；分发副本可重新生成
```

## 练习

1. 3 分钟音频以 96 kbit/s 和 160 kbit/s 编码，分别估算纯载荷大小。为什么最终文件不会精确等于该值？
2. 为“会议实时通话”“长期音乐 master”“兼容十年前车机”“现代 Web 音乐预览”各列两个候选 codec/容器组合，并写出决定选择的实测项。
3. 一条链路使用 20 ms frame、额外 5 ms look-ahead、40 ms packet 聚合、60 ms jitter buffer。仅这些已知项的下界是多少？为何仍不是端到端延迟？
4. 解释 `MP3 → FLAC` 与 `MP3 → AAC` 的不同损失边界。
5. 设计一个 10 秒无缝循环验收：你会记录哪些 sample count、pre-skip/end trim 和边界证据？

## 成功标准

- [ ] 能把 codec、container、mapping、metadata 和扩展名分别指出。
- [ ] 能说明分帧/加窗、变换、心理声学、量化、熵编码各自的责任。
- [ ] 得到 3 分钟 96 kbit/s 约 2,160,000 byte、160 kbit/s 约 3,600,000 byte，并说明容器与 VBR 偏差。
- [ ] 对延迟例得出已知项下界 125 ms，且继续列出采集、计算、网络、解码和播放缓冲。
- [ ] 能比较 MP3、AAC、Opus、FLAC 的设计定位，不把名义码率当统一质量尺度。
- [ ] 能解释 pre-skip、end trim 和 gapless 协作，并以解码 sample count 验收。
- [ ] 能说明有损级联为何累积误差、FLAC 为何不能恢复有损来源。

## 官方来源与核验边界
