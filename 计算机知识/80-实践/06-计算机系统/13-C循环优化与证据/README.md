# C 循环优化与证据：同一个模二结果，哪些改变仍然合法？

> 本单元对应 CS:APP 3e 第 5 章的“程序优化”主题，采用原创程序和当前机器上的有限测量；它不复制教材，也不把测量当作特定微架构的证明。先读 [[计算机知识/30-计算机系统/04-缓存局部性带宽与延迟#10. 性能分析的最小证据链|性能分析的最小证据链]]，带着问题回来：**一次较短的运行，到底足以支持什么主张？**

同一块连续、row-major 的 `uint32_t` 二维数组，四个函数都必须返回：

$$
S=\left(\sum_{r=0}^{R-1}\sum_{c=0}^{C-1}A[rC+c]\right)\bmod 2^{32}.
$$

这是本实验的**结果合同**，但只适用于能表示为一个实际连续对象的形状：`rows*columns` 与 `count*sizeof(uint32_t)` 均不溢出 `size_t`，且非空形状给出非空数组。任一维度为零时结果为零，允许 NULL，因为函数在任何指针算术前返回。程序在形成这两个乘积、分配内存和进入比较前检查它们。

`uint32_t` 是精确 32 位的**保存对象类型**；C 表达式先受整数提升规则约束，再把结果存回对象。为避免把两层混成一句口号，本程序以编译期断言拒绝 `UINT_MAX != UINT32_MAX` 或 `INT_MAX >= UINT32_MAX` 的实现：在接受的平台上，参与加法的 `uint32_t` 值不会先提升成有符号 `int`，每次无符号加法按 $2^{32}$ 取模。这里特意不借助有符号溢出。先证明/测试合同，再讨论哪条依赖链、哪种地址访问和哪段机器代码被测到了。

![[计算机知识/80-实践/06-计算机系统/13-C循环优化与证据/数据依赖与访问顺序.svg]]

图中蓝色实线是数值依赖；橙色虚线是同一存储布局上候选的地址访问顺序。两者不能互相替代，更不是因果箭头。四累加器能缩短一条 `total` 的循环携带依赖链；它没有保证某台机器更快。按列访问改变地址顺序；它没有直接计数任何 cache/TLB miss。

## 从基础补桥入口开始：先算，再停

固定 `R=2,C=3`，数组为：

```text
A = [0xffffffff, 1, 7,
     9,          11,13]
```

逐行相加时前两项为 `0xffffffff + 1 = 0 (mod 2^32)`，所以结果为 `40`。逐列访问的顺序变成 `A[0,0], A[1,0], A[0,1], …`，顺序不同，但在这个明确的模二合同中结果仍为 `40`。四个累加器暂存部分和，最后相加；模二加法满足结合律和交换律，故结果也相同。

先写下预测，再运行程序：

1. `row_base` 相比 `baseline` 改变了哪一个源代码表达式，却没有改变访问顺序？
2. `four_accumulators` 哪几条数据依赖链变短了？最后的合并为什么仍在合同内？
3. `column_visit` 改变了什么，没改变什么？

**停点。** 还不能从纸算推出“编译器会保留这些写法”“四累加器更快”“按列必然 cache miss 更多”。这些需要分别查看编译产物或收集对应的硬件/系统证据。

## 本科基础快进入口：先固定等价条件

对于满足上述对象长度和编译期平台前提的有限数组，参与表达式的加法是在有限阿贝尔群 $(\mathbb Z/2^{32}\mathbb Z,+)$ 中计算。因此只要每个元素恰好被取一次，重排与分组保留 `S`。这解释了本例的三种变换：

| 版本 | 保持的对象 | 改变的对象 | 不能由此推出 |
| --- | --- | --- | --- |
| `baseline` | 合同、row-major 遍历 | 无 | 基准就是最优 |
| `row_base` | 合同、访问顺序 | C 源层的地址表达式 | 编译器没有早已做同样化简 |
| `four_accumulators` | 合同、总访问集合 | 中间依赖图与加法分组 | 延迟、吞吐或 SIMD 的具体数值 |
| `column_visit` | 合同、总访问集合 | 地址访问顺序 | cache miss、TLB miss 的数量或因果 |

这个证明有边界：`float`/`double` 加法通常不满足结合律。比如有限精度下 `(1e20f + -1e20f) + 3.14f` 可能得到 `3.14f`，而 `1e20f + (-1e20f + 3.14f)` 可能得到 `0`。所以把四累加器直接移到浮点归约，必须把“数值容差、舍入模式、NaN/无穷值处理、可否重结合”写入新合同；不能从本例偷渡过去。

同样，`restrict` 不是“性能开关”。它是调用者给出的不别名承诺。若一个函数可从两个指针读写同一对象，再擅自将其声明为 `restrict`，程序已经违背前提，不能用这次实验的结果替它背书。此处只有一个只读 `matrix` 指针，刻意不演示或执行未定义行为。

## 运行：先验证结果，再收集有限样本

源程序是真源。以下命令把编译产物放在一个新建的系统临时目录，退出后由 Python 清理；每个子进程都有超时：

```bash
cd "计算机知识/80-实践/06-计算机系统/13-C循环优化与证据"
python3 -B -m unittest -v test_loop_optimization.py
```

它会优先使用环境变量 `CC`；若未设置而 `/opt/homebrew/opt/llvm/bin/clang` 已存在，则使用该 clang，否则回退 `cc`，并以 `-std=c17 -O2 -Wall -Wextra -Wpedantic` 编译，先让平台断言检查整数合同，再运行 `--self-test`，最后运行两份 benchmark 样本。自测试还覆盖零维度、四项尾部、不可表示的元素/字节数和非空形状的空指针拒绝。macOS 上，若已安装 Command Line Tools，测试只给本次编译子进程设置 `DEVELOPER_DIR=/Library/Developer/CommandLineTools`，避开未接受的完整 Xcode 许可；它不接受许可、不安装工具、也不改变系统选择。若编译器确实不可用，测试明确 `SKIP`。若只想手动做一次可查看的汇编与七样本运行：

```bash
cd "计算机知识/80-实践/06-计算机系统/13-C循环优化与证据"
(
  output_dir="$(mktemp -d /private/tmp/wwl-loop-opt.XXXXXX)" || exit 1
  trap 'rm -rf "$output_dir"' EXIT
  compiler="${CC:-/opt/homebrew/opt/llvm/bin/clang}"
  DEVELOPER_DIR=/Library/Developer/CommandLineTools "$compiler" -std=c17 -O2 -Wall -Wextra -Wpedantic -S loop_optimization.c -o "$output_dir/loop_optimization.s"
  DEVELOPER_DIR=/Library/Developer/CommandLineTools "$compiler" -std=c17 -O2 -Wall -Wextra -Wpedantic loop_optimization.c -o "$output_dir/loop_optimization"
  "$output_dir/loop_optimization" --self-test
  "$output_dir/loop_optimization" --benchmark 7
  sed -n '1,220p' "$output_dir/loop_optimization.s"
)
```

手动命令中的 `rm -rf` 只清理由刚刚 `mktemp` 返回、并绑定在 `output_dir` 的单一目录；运行前后不修改 Vault，也不启动服务。汇编是**这次编译器、目标架构、选项和源版本**的证据：在当前 arm64 Mach-O 环境看到的符号、指令和优化不等于 CS:APP 常用的 x86-64/Linux 输出。

程序每个样本轮换四个版本的测量先后顺序，打印全部样本、编译器名字、`NDEBUG` 状态、形状、重复次数与 guard。结果测试只断言合同，不含“某版本必须更快”的阈值。

## 如何读输出，及输出不能说明什么

单个 `*_ns` 是“同一进程中，某个版本连续做 64 次、由此时钟测得的总墙钟间隔”。它可帮助发现一个候选差异，也会受到频率调整、热状态、调度、预热、预取、内存页、别的进程、编译器向量化和计时分辨率影响。

建议把原始 stdout 与下列信息一同保存到自己的学习记录：操作系统/版本、CPU、编译器完整版本、命令与优化选项、是否插电/省电、样本数、输入形状以及源哈希。比较时报告全样本，而非只取最快的一次。

| 问题 | 适当证据 | 这个实验单独不能回答 |
| --- | --- | --- |
| 四个版本结果是否相同？ | 自测试、更多测试输入 | 所有 C 改写都合法 |
| 本次构建生成了什么？ | 保存 `.s` 或反汇编、完整编译命令 | 另一编译器或平台会生成什么 |
| 本次端到端耗时有何差异？ | 交错、重复的全样本计时 | 差异由 cache miss 单独造成 |
| 是否受 cache/TLB/分支/SIMD 限制？ | 匹配事件定义的硬件计数器、向量化报告、受控实验 | 从 wall time 直接归因 |

`CPE = cycles / processed element` 是把已测的周期数除以元素数的描述量，不是跨平台的语言语义，也不是单条指令延迟。依赖链限制的是一条链上“下一个值何时可用”的延迟；多条独立链和足够工作可提升可并行的吞吐。最终程序时间仍取决于访存、前端、向量化、端口、分支和其它资源，不能把“依赖少”偷换为“每元素周期必然低”。

## 迁移：同时改变条件，重建判断

现在把问题改为：数组元素改成 `float`，视图具有 `stride=2`，并且调用点声称两个输入指针不别名。请自行选择可接受的改写，并回答：

1. 新的结果合同怎样规定舍入、容差、NaN 与无穷值？是否允许重结合？
2. 逻辑坐标 `(r,c)` 到地址的关系是什么？`stride=2` 时，“按行连续”这句话还剩多少含义？
3. `restrict` 是谁的承诺？若无法证明不别名，哪些优化假设必须撤回？
4. 要支持“优化改善了目标指标”，需测什么输入、保存什么构建证据，如何避免把一个指标误叫成另一个？

可接受的答案不止一种：例如选择顺序浮点累计并以逐位一致作为严格合同；或声明允许固定的误差界与树形归约，但必须说明此时结果不再等于原有顺序。对于 stride，任何正确回答都应使用实际地址公式并区分逻辑访问与物理连续性。对于 alias，任何不宣称 `restrict` 且保留保守路径的方案都可接受；不能以实际“碰巧没出错”代替前提。
