训练回答“参数怎样学出来”，推理回答“固定参数怎样把提示逐步变成输出”。本模块从一次请求内部的逐 token 循环出发，再扩大到多请求调度、显存预算和服务引擎选择。读完后，你应当能把“回答慢”“显存爆了”“并发上不去”拆成可测量的问题，而不是只换一个工具碰运气。

> [!important] 先建立一张资源地图
> 一次推理至少同时占用模型权重、KV cache、临时激活与运行时工作区。模型参数量决定权重的主要规模；上下文长度、batch、KV 精度和注意力结构决定 KV cache；引擎、算子、并行策略和硬件又决定额外开销。任何单一“某显卡能跑某模型”的表格都不能替代现场测量。

## 两条学习路线

### 单机理解路线

1. 先学逐 token、prefill/decode 与 KV cache；
2. 再学 greedy、sampling、beam search 与停止条件；
3. 用显存页为自己的 8GB、16GB 或 24GB 设备做**保守候选路线**；
4. 最后从 Transformers、llama.cpp 或 Ollama 选一个易观察的本地入口。

### 服务工程路线

1. 先统一 TTFT、TPOT、吞吐和端到端延迟口径；
2. 理解静态 batching、continuous batching、队列和抢占；
3. 再评估 vLLM 或 SGLang 等服务引擎；
4. 用固定模型、提示长度、输出长度、并发和硬件做现场压测。

## 贯穿模块的因果链

```text
模型参数量 × 权重精度 ───────────────> 权重内存
层数 × KV 头宽 × 上下文 × batch × KV 精度 ─> KV cache
提示长度 ──> prefill 工作量 ──> TTFT
输出长度 ──> decode 次数 ─────> 生成时间
请求到达方式 + 调度策略 ───────> 排队、公平性与吞吐
硬件带宽/算力 + 引擎实现 ──────> 实际速度与额外开销
```

把它再压缩成一条请求时间线：

```text
到达 → 排队 → tokenize/模板 → prefill → 首 token → decode × N → stop/回收
       │                         │                     │
       └─ 调度与公平性          └─ TTFT              └─ TPOT/ITL、吞吐与尾延迟
```

学习时每遇到一个“优化”，都先标注它改变了哪一段、用了哪块内存、可能伤害哪个指标。例如 prefix cache 主要少做可复用的 prefill，continuous batching 主要重组多请求执行，投机解码主要减少 target 模型的串行 decode 轮数。它们不是同一类开关。

## 三个不要混淆

- **能装下**不等于**速度可接受**：CPU 内存足够也可能每 token 很慢。
- **单请求快**不等于**服务吞吐高**：为一个人优化和为几十个并发优化的目标可能冲突。
- **低比特权重**不等于**所有内存都同比降低**：KV cache、临时激活、工作区和运行时仍然存在。

## 快速变化事实的证据边界

工具的模型支持、量化格式、硬件后端、命令参数和性能会快速变化。本模块的工具定位以 [[AI/90-资源/05-官方资料与版本核验记录|官方资料与版本核验记录]] 为入口；账本核验日期为 **2026-09-01**。它只证明当日可以定位官方维护入口，不证明本机已安装、某模型必定兼容或某性能数字可以复现。实施前仍须固定模型 revision、工具版本、驱动/后端、硬件和测试日期。

## 模块验收挑战

任选一个候选模型，不必下载，完成一页纸推理方案：

1. 写出参数量、权重格式与权重精度；
2. 假设上下文、输出长度和并发，估算权重与 KV cache；
3. 说明首 token 慢或后续 token 慢时分别检查什么；
4. 选择一个引擎，并写出为什么没有选另外四个；
5. 列出至少四项现场验证指标和失败后的回退方案。

## 成功标准

- 能描述一次请求从 tokenization 到停止的完整路径；
- 能解释参数、KV cache、batch、context 与 precision 对内存的不同影响；
- 能区分单请求延迟、TTFT、TPOT 与系统吞吐；
- 能把 8GB、16GB、24GB 只当作课程起步路线，而不是兼容保证；
- 能从官方来源、固定版本和本机测量形成可复现结论。
