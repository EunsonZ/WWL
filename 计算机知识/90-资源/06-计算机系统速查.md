# 计算机系统速查

这张表用于定位“慢、打不开、连不上、内存涨、句柄耗尽”等现象所在层。每个工具只证明局部事实；沿诊断链逐层取证，不要把 CPU 高误判成 CPU 算力不足。

## CPU、内存与执行

| 对象/指标 | 定义/看什么 | 常用证据 | 常见陷阱 |
| --- | --- | --- | --- |
| CPU 利用率 | 时间窗口内线程占用逻辑 CPU 的比例 | `top`/`htop`、`pidstat -u`、`perf stat` | 100% 可能只是单核满；I/O wait、steal、频率变化要分开看。 |
| load average | 可运行或不可中断等待任务的队列趋势 | `uptime`、`/proc/loadavg` | 不是 CPU 百分比；I/O 堵塞也能抬高 load。 |
| 上下文切换 | 线程从一个执行上下文切换到另一个 | `vmstat`、`pidstat -w`、`perf stat` | 多线程更多不必然更快；锁竞争和调度开销可能主导。 |
| 虚拟地址/映射 | 进程看到的地址到物理页/文件的映射 | `/proc/$PID/maps`、`pmap`、`smaps` | `VSZ` 不等于驻留 RAM；共享映射不能简单相加。 |
| RSS/PSS | 驻留页；PSS 按共享比例计入 | `/proc/$PID/status`、`smaps_rollup` | RSS、cache、swap、匿名页含义不同；容器还受 cgroup 限制。 |
| page fault | 地址访问触发页表建立或从后备存储取页 | `perf stat -e page-faults`、`vmstat` | minor fault 不等于磁盘 I/O；不能只看 fault 数断言换页。 |

## I/O、FD、VFS 与文件系统

| 层 | 心智模型 | 观察/诊断 | 常见陷阱 |
| --- | --- | --- | --- |
| I/O 路径 | 应用 → syscall → VFS → 文件系统 → block layer → 设备 | `iostat -xz`、`iotop`、`strace -e trace=%file,%network` | 吞吐高不等于延迟低；page cache 会让“写完”与持久化不同。 |
| FD | 进程内整数句柄，指向 open file description、pipe、socket 等 | `ls /proc/$PID/fd`、`lsof -p $PID`、`ulimit -n` | FD 不是 inode/路径；unlink 后仍可被已打开 FD 占用空间。 |
| VFS | 给不同文件系统统一 open/read/write/stat/mount 语义的内核层 | `findmnt`、`stat`、`/proc/mounts` | VFS 统一接口不代表所有语义、锁和性能相同。 |
| inode/目录项 | inode 保存元数据，目录项把名称映射到 inode | `stat`、`df -i` | 磁盘有空间但 inode 用尽仍无法创建文件；硬链接共享 inode。 |
| 文件系统 | 定义命名、权限、日志/写回和空间布局 | `findmnt -T PATH`、`df -h`、`df -i` | `df` 看文件系统；`du` 看可遍历目录，两者差异可能是删除但仍打开的文件。 |
| mount namespace | 进程可见的挂载树视图 | `findmnt -N PID`（版本支持时）、`/proc/$PID/mountinfo` | 容器里看到的路径不一定是宿主同一挂载；不要凭设备名做破坏性操作。 |

## 网络与服务

| 层次 | 要回答的问题 | 工具/证据 |
| --- | --- | --- |
| 名称 | 域名解析成了什么？ | `getent hosts NAME`、`resolvectl query NAME` |
| 路由 | 本机准备从哪里发包？ | `ip route get ADDRESS`、`ip addr` |
| 传输 | TCP/UDP 端口是否可达、谁在监听？ | `ss -lntup`、`nc -vz HOST PORT`、`curl -v` |
| TLS/协议 | 握手、证书、SNI 或应用响应是否成功？ | `openssl s_client`、`curl -v --fail-with-body` |
| 服务/进程 | 服务是否存活、日志是否解释失败？ | `systemctl status UNIT`、`journalctl -u UNIT -b`、`ps` |

## 性能诊断链

```text
复现并计时 → 明确请求/输入规模 → CPU/内存/IO/网络四类资源分流
→ 进程/线程与 syscall 证据 → 锁、缓存、页错误、队列或设备延迟
→ 只改一个假设 → 再以同一工作负载验证吞吐、p95、错误率和资源账本
```

安全边界：`strace`、`perf`、`lsof` 等可能需要权限且会增加开销；先在测试进程和短时间窗口使用。任何 `kill`、卸载、清缓存、调整 sysctl 或格式化操作都必须先确认精确目标、影响和恢复路径。
