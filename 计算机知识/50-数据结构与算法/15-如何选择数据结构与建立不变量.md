# 15 · 如何选择数据结构与建立不变量

## 本课目标

学完后，你能从问题、操作、规模、内存与局部性、并发、持久化逐层选择数据结构；能把核心正确性写成不变量，并用边界测试、性质测试和参考实现交叉验证，而不是只背复杂度表。

## 1. 选择不是“哪个结构最快”，而是固定一份工作负载

在比较 `array/vector`、链表、哈希表、平衡树、堆、Trie 或数据库索引前，先写出下列事实。没有这些事实的 `O(1)`、`O(log n)` 只是脱离上下文的标签。

```text
问题：对象、唯一性、顺序、查询语义和允许的近似是什么？
操作：读、按键查、范围查、插入、删除、取极值、迭代各占多大比例？
规模：现在与峰值 n、键长度、值大小、延迟/吞吐目标是什么？
资源：内存上限、分配频率、访问局部性、缓存/带宽瓶颈是什么？
并发：谁读写、需要线性化/快照/最终一致中的哪种语义？
持久化：进程崩溃后要保留什么，索引如何恢复，日志和版本怎样处理？
```

数学上可把数据结构看作一个抽象状态集合 `S` 与操作的映射；实现状态还要满足表示不变量。集合、映射和量词的精确定义见 [[数学/10-数学语言与基础/03-集合映射命题与合法推理|集合、映射、命题与合法推理]]。这解释了为什么“看起来存了一样的数据”不够：两个实现若操作结果、错误行为、迭代顺序或并发可见性不同，就未必实现同一抽象数据类型。

## 2. 一张由问题到结构的决策框架

| 主要需求 | 常见候选 | 先确认的代价与边界 |
| --- | --- | --- |
| 连续遍历、按位置读、批量数值计算 | 连续数组、`vector`、紧凑列式布局 | 中间插删可能搬移；扩容与迭代器/指针失效；元素布局是否连续 |
| 通过唯一键查、去重、计数 | 哈希表 / `dict` / `set` | 平均查找通常快；哈希质量、装载因子、扩容、最坏碰撞和键相等语义 |
| 有序键、范围查询、前驱/后继 | 平衡搜索树、排序数组、B-tree 类索引 | 写入频率、比较成本、页/缓存局部性；排序数组的插入搬移 |
| 反复取当前最小/最大，但不需任意排序 | 堆 / 优先队列 | 只保证堆顶关系；按任意值查找或删除通常不等于 `O(1)` |
| 许多词的共享前缀、前缀补全 | Trie、压缩 Trie、有限自动机 | 字符单位、稀疏分支的内存、节点分配与 Unicode 规范化 |
| 先进先出工作流 | 队列、环形缓冲区、双端队列 | 容量满/空的约定、背压、单/多生产者消费者语义 |
| 最近使用淘汰 | 哈希表 + 双向链表，或库缓存 | 读是否改变顺序、淘汰回调、容量和并发锁的边界 |

表中“常见候选”不是唯一正确答案。例如小规模且读多写少的有序数组可能比指针很多的树更省内存且更快；大规模磁盘索引常关心页访问而非单个指针比较。字符串索引的单位与算法选择见 [[计算机知识/50-数据结构与算法/13-字符串匹配前缀函数与自动机|字符串匹配、前缀函数与自动机]]。

## 3. 完整例子：为事件去重与时间范围查询设计两层结构

需求：每个事件有不可变 `id`、时间 `t` 与载荷；重复 `id` 只保留第一次；需要按 `id` 快速查找，也要按时间区间顺序列出；单进程、先以中等规模为目标。

一种明确的设计是：

- `by_id`：从 `id` 到事件记录的位置的哈希映射，用于去重与点查；
- `by_time`：按 `(t, id)` 排序的记录位置序列，用于范围二分与顺序扫描；
- `records`：记录的稳定存储；删除策略先不支持，或改为 tombstone 并明确压实过程。

```text
插入(event):
    若 event.id 在 by_id 中：返回 duplicate
    验证 event，并在 by_time 中找到 (event.t, event.id) 的插入位置 k
    预留 records 与 by_time 增长所需资源；任一步失败则尚未改变公开状态
    开始不向读者暴露中间状态的 commit 区间：
        pos ← append records(event)
        在 k 插入 pos 到 by_time
        by_id[event.id] ← pos
    若 commit 区间仍可失败：按 by_id → by_time → records 的逆序回滚
    返回 inserted

时间范围(lo, hi):
    a ← by_time 中第一个 t ≥ lo 的位置
    b ← by_time 中第一个 t > hi 的位置
    对 by_time[a..b) 的每个 pos：产出 records[pos]
```

对事件 `(A, 10)`、`(B, 7)`、`(C, 10)` 依次插入后，可以得到：

```text
records: [A@10, B@7, C@10]
by_id:   {A: 0, B: 1, C: 2}
by_time: [1, 0, 2]     # 依 (t, id)：B@7, A@10, C@10
```

查 `id = C` 走 `by_id[C] → 2 → records[2]`；查 `[8, 10]` 在 `by_time` 二分后产出 A、C。取舍也可见：哈希索引增加内存；按时间插入数组需要移动后缀，写入很多时可换平衡树、分段/批量合并或持久化索引。这个例子不声称某语言内建容器的精确复杂度；要检查 Python 容器的语义见 [[计算机知识/10-编程语言/01-Python/04-容器迭代器生成器与推导式|容器、迭代器、生成器与推导式]]，C++ 中 `vector` 的连续布局与扩容失效规则见 [[计算机知识/10-编程语言/02-C++/05-struct类模板与STL|struct、类、模板与 STL]]。

## 4. 把正确性写成不变量

**不变量**是在每次公开操作开始和成功结束时都应成立的断言；中间步骤可以暂时破坏它，但异常、返回和并发可见点不能暴露破坏后的状态。它比“代码看着合理”更具体，也给测试提供了 oracle。

上例可写成：

1. `by_id` 的每个键都唯一，且映射到合法 `records` 位置；该记录的 `id` 等于该键。
2. 每个被接受的记录恰好由 `by_id` 引用一次，且在 `by_time` 中恰好出现一次。
3. `by_time` 按 `(records[pos].t, records[pos].id)` 非降序排列。
4. 若范围查询返回事件 `e`，则 `lo ≤ e.t ≤ hi`；所有已存记录中满足该条件的事件都被返回一次。

操作的证明轮廓是：初始化时四条都真；插入先检查重复与全部可拒绝输入，再计算位置并预留资源；只在不向并发读者暴露中间状态的 commit 区间更新三处；完成前检查位置、顺序和引用计数。“预留后不会失败”必须由实际语言与容器契约支持；若不能保证，就要记录哪些步骤已生效并按逆序回滚，或先在新快照中构造完整状态再一次替换。失败返回与异常逃逸点都必须恢复四条不变量，不得留下“只写了一半索引”的状态。删除、更新和压实也必须逐一重做这份证明，不能因为插入正确就自动正确。

链表可有“双向链接互相一致、头尾边界为空”；堆可有“每个父节点不大于子节点”；哈希表可有“每个已占槽按探测规则可从其初始桶到达”。不变量需要可判定、与接口语义相关，避免空泛地写“数据始终正确”。

## 5. 从不变量导出测试，而非只测几个顺利案例

| 测试层 | 例子 | 能证明/不能证明什么 |
| --- | --- | --- |
| 例例测试 | 插 A、B、C，查 `[8,10]` 返回 A、C | 固定场景的可观察结果；不是全部输入证明 |
| 边界测试 | 空结构、首尾时间、相同时间、重复 ID、容量边界 | 常暴露 `≤`/`<`、空/满、偏移问题 |
| 不变量检查 | 每次随机操作后验证四条不变量 | 能定位首次破坏状态的操作 |
| 性质测试 | 插入后查询到同一 ID；重复插入大小不变 | 覆盖许多生成输入，仍依赖生成器与 oracle |
| 差分测试 | 小输入与简单列表/集合参考实现逐操作比对 | 参考实现也可能有 bug；适合缩小反例 |
| 压力/并发测试 | 多线程读写、崩溃恢复、长时运行 | 能发现某些竞态；一次通过不证明无竞态 |

可把操作随机序列记录为可重放的种子和日志。一旦失败，先最小化序列，再检查“第一条被破坏的不变量”，通常比只盯最终错误更有效。有限测试无法证明“任意输入均正确”；若需要更强保证，要结合审查、形式规格或证明，并明确适用的模型。

## 6. 内存、局部性与测量：大 O 不替代机器成本

两个同为平均 `O(1)` 的查找，可能因指针追逐、分配器、缓存未命中、键比较或哈希开销差异很大；两个同为 `O(n)` 的扫描，也可能因连续访问、SIMD 和预取而差异明显。连续数组常有良好空间局部性，链式节点通常多一次间接访问；但若数组频繁在中间插入，移动成本和峰值内存又是现实代价。

测量前应固定：数据规模与分布、键长度、读写比例、线程数、预热、内存上限与指标（p50/p99 延迟、吞吐、分配数或峰值内存）。一次只改一个结构因素，同时验证输出和不变量不变。缓存行、带宽、工作集与伪共享的完整分析见 [[计算机知识/30-计算机系统/04-缓存局部性带宽与延迟|缓存、局部性、带宽与延迟]]。

## 7. 并发：先选择语义，后选择锁或无锁结构

“线程安全”不是一个足够精确的需求。至少要声明：

- 一个操作在何时对其他线程可见，是否要求线性化（看起来像某一瞬间原子发生）；
- 范围查询要单一快照、允许变化中的视图，还是必须加锁到结束；
- 读会不会改变结构（如 LRU 更新最近使用顺序）；
- 内存何时可回收，读者会不会持有失效的指针/迭代器；
- 发生冲突时是阻塞、重试、丢弃、合并还是报错。

对上例，一个简单正确的起点可用同一把互斥锁保护 `records`、`by_id` 和 `by_time` 的复合更新；这样插入不会向读者暴露半更新状态。随后再根据测量考虑读写锁、分片、不可变快照或专用并发容器。把三个容器各自“线程安全”并不能自动保证跨容器不变量。锁、原子、内存顺序与数据竞争边界见 [[计算机知识/10-编程语言/02-C++/08-线程锁与原子|线程、锁与原子]]。

## 8. 持久化：内存索引不是崩溃恢复方案

若重启或断电后数据仍须存在，要另外定义：权威数据在哪、写入何时算成功、如何恢复、如何处理部分写入和格式升级。常见可靠顺序是先追加可校验日志，再更新内存索引；启动时从快照加日志重建并核验。具体保证依赖文件系统、数据库、同步调用、校验、原子重命名和失败模型，不能只因调用了“保存”就声称断电安全。

持久化会反过来改变选择：磁盘/SSD 往往偏好页或块友好的布局，B-tree 类结构和批量写入可能比大量随机小节点更合适；数据版本、迁移和压实也要成为不变量与恢复测试的一部分。先分清延迟、带宽和工作集，避免把内存结构的微基准外推到存储系统。

## 练习

1. 为“聊天室最近 10,000 条消息：按时间显示、按消息 ID 去重、偶尔按作者过滤”填写六层问题清单。分别给出一个小规模原型和一个需要持久化时的演进方案，并说明哪些假设改变了。
2. 对事件索引例子，补充删除 `id` 的伪代码设计。写出删除后必须保持的四条不变量，并说明若删除时先删 `by_id`、后更新 `by_time`，在中途失败会怎样。
3. 写一个最小参考模型：用普通列表保存事件，每次查询都线性筛选和排序。设计至少 20 次随机操作，逐步与优化结构的结果及不变量比较。
4. 把范围查询改成“返回一个一致快照”。选择粗粒度锁、复制快照或版本号重试之一，写清读者可见的语义、写者成本和一个仍须测试的失败场景。
5. 选一个你熟悉的 `O(1)` 数据结构，列出至少五个使真实延迟变差的因素；其中至少两个必须与键/输入分布有关，而非只说“机器慢”。

## 成功标准

- [ ] 我能从操作和数据规模出发选择候选结构，且能说出每个候选被排除或保留的理由。
- [ ] 我能为一个复合索引写出能在代码中检查的不变量，并在每种修改操作后检验它。
- [ ] 我会用边界、性质和差分测试互补，而不把一次成功基准当成通用正确性或性能证明。
- [ ] 我能把并发可见性、崩溃恢复和数据布局作为设计输入，而不是等问题出现后才补丁修复。
