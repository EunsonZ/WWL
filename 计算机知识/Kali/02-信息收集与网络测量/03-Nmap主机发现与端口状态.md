# Nmap主机发现与端口状态

**先修关系：** [[计算机知识/Kali/01-系统与网络基础/06-TCPIP路由DNS与TLS|TCPIP路由DNS与TLS]]；[[计算机知识/Kali/00-导航与方法/02-授权范围与风险分级|授权范围与风险分级]]。

## 扫描回答的是“从这里看见什么”

Nmap 的主机发现尝试判断目标是否响应某类探测，端口扫描判断特定传输端口对探测的反应。一次结果受扫描方式、权限、采集位置、目标状态与网络设备影响。没有回复，不足以单独证明主机离线。[^s1]

第一步不是 `-A`，而是固定目标。对含 IP 的范围文件，可先进行不发探测、也不做 DNS 的列表审阅：

```bash
# scope.txt 只含本次批准的目标；-n 避免反向 DNS 查询
nmap -sL -n -iL scope.txt
```

只有目标集合与书面范围一致，才选择下一步。域名可能动态解析成多个地址，范围批准的是域名还是具体地址需要事先说明。

## 端口状态是观察结果

| 状态 | 可以支持的结论 | 不能直接支持的结论 |
| --- | --- | --- |
| open | 有应用接受该类连接/数据报的证据 | 应用一定脆弱、一定是端口常见服务 |
| closed | 目标可响应，但此端口当前未见监听 | 整台主机没有其他服务 |
| filtered | 过滤或网络行为妨碍区分开放/关闭 | 一定由哪台防火墙丢弃 |
| unfiltered | 探测可到达，但这种方式无法判定开放性 | 与 open 同义 |
| open\|filtered | 无法区分开放与过滤 | 已确认开放 |
| closed\|filtered | 无法区分关闭与过滤 | 已确认关闭 |

这是 Nmap 的状态语言，不是目标永恒属性。[^s1] 给出报告时保留 `--reason` 的原因信息，避免只导出一个“开放/关闭”的二值列。 ^port-state

## 从包或系统调用反应推到状态

以简化 SYN 扫描为例：探测 SYN 得到 SYN-ACK，支持有监听的 open 判断；得到 RST，支持 closed；没有回答或某些不可达响应，可能落入 filtered。connect 扫描则以操作系统连接接口的结果为主要依据，不能把其所有失败都当成收到了远端 RST。ACK 扫描得到 RST 通常说明相应探测可达，但不区分端口是否监听，因此使用 unfiltered 等状态。[^v2-nmaptech]

| 改变的条件 | 预期可能变化 | 不应得到的结论 |
| --- | --- | --- |
| SYN 改为 ACK 探测 | 状态词典与判断目标变化 | 状态不同就说明工具坏了 |
| TCP 改为 UDP | 无回应的歧义明显增加 | 两个同号端口必然同开同关 |
| 探测位置改变 | 路由与过滤路径改变 | 原报告一定错误 |
| 重试预算减少 | 未观测到响应的机会增加 | 更快等于更准确 |

一个教学概率例子：假设端口确实会回复，每次回应被独立丢失的概率为 0.1，则三次都漏掉的概率是 $0.1^3=0.001$。真实丢包可能相关，防火墙可能确定性丢弃，限速也依赖先前请求，所以不能把这个数字当成 Nmap 漏报率。它只解释“增加重复观察在某些假设下为何有帮助”。

## 主机发现与二层探测

`-sn` 只做主机发现，不做通常的端口扫描，但它仍发送探测。在本地以太网，ARP 等二层方式可能参与发现；跨路由器不能照搬相同行为。`arp-scan` 直接面向二层邻居，不会把 ARP 广播穿越普通路由边界。[^s3]

只对明确批准的小集合使用发现操作，先检查网卡名与虚拟交换机。不要把 `--localnet` 或整个 `/16` 当成教学默认值。`netdiscover` 也是同类范围敏感工具，模式可能主动发包，使用前读帮助。

## 把主机发现与端口集合分别写清

`-sn` 不做常规端口扫描，但仍做发现探测；`-Pn` 跳过通常的主机发现，却不等于关闭所有二层解析，例如本地以太网仍可能需要 ARP 或邻居发现。`-p 8000,8001` 只选两个端口，`-A` 不替代端口集合。[^v2-nmapdiscovery]

原课程中 `nmap -sL -n -iL scope.txt` 的无 DNS、无目标探测说法，**严格限定输入是数字 IP 或数字 CIDR**。若文件含主机名，工具为了枚举目标仍可能需要正向解析；`-n` 不能把域名变成无需解析的地址。范围文件先做类型审阅，不用名字解析结果悄悄扩大范围。

## 范围覆盖的分母要先于扫描结论

假设目标合同是 4 个教学 IP、每个 TCP 端口集合 20 项，则计划端点数是 80。若 2 个目标因发现阶段未回应而未进入端口扫描，实际完成的端点不能仍写 80。若对某目标超时，也不能把剩余端口补成 `closed`。这是集合与执行状态的统计问题，不是扫描器的性能测试。

覆盖度还可以按地址族、来源位置、协议和时窗分层；“端口全扫”通常只描述其中一个维度。与 [[计算机知识/Kali/07-综合实验/11-实验H扫描XML差异与不确定性|扫描差异实验 H]] 连接时，保留未覆盖、未完成和已完成的阴性，才能解释一个开放端口为什么在下一份报告里消失。

## TCP connect 与 SYN 扫描

`-sT` 通过操作系统的连接接口尝试建立 TCP 连接，适合无原始包权限的起点。`-sS` 使用 SYN 探测，需要相应原始包权限；它不是“不可检测扫描”，服务端和网络监控仍可能记录相关流量。[^s2]

本包的首个在线练习仅针对**自己显式启动**的回环服务：

```bash
mkdir -p "$HOME/kali-lab/output"
nmap -sT -n -Pn -p 8000,8001 --reason --max-rate 10 \
  -oA "$HOME/kali-lab/output/loopback-ports" 127.0.0.1
```

前提见 [[计算机知识/Kali/07-综合实验/02-实验A从路由到HTTP与Nmap|实验 A]]。`-p` 精确限定两个端口；`-Pn` 跳过常规主机发现、按目标在线继续扫描，不是让目标“变在线”；`-n` 不做名字解析；`-oA` 保存多种输出。此处扫描回环，不需要管理员权限。

`--max-rate` 约束扫描探测速率，但不能当作整个 Nmap 所有阶段、所有 NSE 请求的严格总 HTTP 请求上限。`--max-retries` 限制重试会减少流量，也可能增加漏报。参数变化必须和结果一起保存。

## 按问题读扫描方式，而不是按“强度”排序

下面列的是功能与解释边界，不是建议把所有方式对同一目标执行一次。Nmap 的结果依赖探测类型、目标栈、路径和回应；某种模式的标签不能直接套用到另一种模式。[^v5-nmap-tech]

| 方式或控制项 | 实际问题 | 最容易过度解释的地方 |
| --- | --- | --- |
| 主机发现 `-sn` | 所选发现探测是否得到可解释回应 | 未回应不等于机器不存在；它不执行通常的端口扫描阶段 |
| 跳过发现 `-Pn` | 不用发现阶段筛掉给定目标，继续既定扫描 | “按在线处理”不等于已经证明在线 |
| TCP SYN `-sS` | 特定 TCP 探测引发何种回应 | 半开探测不等于不留日志或无副作用 |
| TCP connect `-sT` | 操作系统连接接口能否建立连接 | 与原始报文模式的权限、握手与日志效果不同 |
| UDP `-sU` | 特定 UDP 输入是否有协议回应或差错 | 沉默仍可能是开放服务不理解输入 |
| ACK `-sA` | ACK 探测路径是否表现为可达或过滤 | `unfiltered` 不判断监听服务是否开放 |
| FIN/NULL/Xmas | 特定 TCP 栈对相应标志组合如何回应 | 依赖栈行为；不能当作跨平台的通用真值 |
| IP protocol `-sO` | IP 协议号层面的响应特征 | 扫的是协议号空间，不是 TCP/UDP 端口空间 |

`-Pn` 与 `-sn` 的具体发现行为承接前文的范围解释；上表的扫描机制以官方扫描技术章节为依据。即使使用相同数字 53，TCP/53、UDP/53 与 IP 协议号 53 也不是同一个对象。先写出“地址族、地址、传输/网络协议、端口是否适用”，再填写状态。

## 两种模式得出不同标签，为什么不一定互相矛盾

原创纸面例子：同一来源对教学端点作 ACK 探测收到 RST，被分类为 `unfiltered`；另一份 SYN 探测也收到 RST，被分类为 `closed`。前者只排除了该 ACK 探测受到某种过滤的解释，后者给出了相应 SYN 观察下没有监听者的证据。它们回答不同问题，所以不能用“一个开放一个关闭”来概括。[^v5-nmap-tech]

再改变一个前提：把来源移到另一条网络路径，原来 `open` 现在 `filtered`。这不必然表示服务停止；访问控制和返回路径都可能随来源变化。报告应把状态写成带条件的关系，而不是目标端口的永久属性。

## UDP 与时间预算

`-sU` 检查 UDP；某些服务需要正确协议内容才会回答，ICMP 限速又会影响判定。可以对自建 DNS 的单个 UDP 端口做限界验证，但本包不默认启动 DNS。UDP 扫描的沉默必须结合应用层请求与抓包解释，不用“再扫快一点”替代证据。

Masscan 擅长高吞吐异步探测，但高速度会放大错误范围、网络负载和漏包问题。[^s4] 它不代替细致服务确认。本课程把它放在选型层，不提供大范围或高发包速率的预设命令。

## 速率、并发、超时和停止条件

速率是单位时间的探测数量，并发是在途任务数量，重试是失败后增加的尝试，超时是等待预算。它们相互影响但不等价。`--max-rate` 主要用于端口扫描和发现，不为版本识别、所有脚本请求或整个系统建立总带宽保证；极短 `--host-timeout` 可能导致目标结果无法完整输出。[^v2-nmaptiming]

报告应保留“本次只扫描 TCP 8000/8001，从某观察点未确认 8001 监听”，而不是“目标没有其他开放端口”。完整端口范围也不等于完整服务覆盖，UDP、IPv6、应用虚拟主机和认证后功能仍是另外的维度。

## 一次合格复测应同时有正例与反例

关闭教学 8000 服务后，预期该端口不再接受连接；另一个已批准的正常教学服务或本机监听证据可作为测量链仍工作的检查。若所有目标同时消失，优先排除网卡、路由或扫描器故障。进入 [[计算机知识/Kali/07-综合实验/10-实验G路由与扫描状态推理|实验 G]] 做纸面状态推理，再用真实靶场验证，不反过来从一次输出发明理论。

## 反例与自检

同一端口从宿主机看是 filtered，从目标本机看是 open，矛盾吗？不矛盾，观察路径不同。应确认目标监听、路径防火墙与采集时间，而不是擅自删掉“难看”的结果。

自检：为什么 `-Pn` 可能使大范围扫描更慢？它让工具对那些实际上不在线、或无法到达的目标也继续尝试端口探测。下一步的 [[计算机知识/Kali/02-信息收集与网络测量/04-Nmap服务识别NSE与结果管理|服务识别与结果管理]] 只应作用于已确认范围。
