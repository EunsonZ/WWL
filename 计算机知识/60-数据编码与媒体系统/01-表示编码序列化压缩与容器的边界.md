# 表示、编码、序列化、压缩与容器的边界

## 本课目标

学完后，你能够把一个“文件打不开”或“内容乱码/失真”的问题放到正确层次：值的表示、文本编码、对象序列化、压缩、加密、容器，或媒体 codec；并能说明每层还缺少哪些契约，不能只凭文件扩展名猜测。

## 直觉：同一段字节可以经过多道彼此独立的变换

把一段录音发给朋友，可能发生这样的链条：采样值被量化为整数 → 音频 codec 以有损或无损方式编码 → 结果被放进带时间轴和标签的容器 → 整个文件被压缩、加密，或装进归档包。最后收到的是字节序列，但“怎样还原”取决于每一层的约定。

不要把下面这些词当成同义词。它们回答的是不同问题：

| 层 | 它回答什么 | 例子 | 它不保证什么 |
| --- | --- | --- | --- |
| **表示（representation）** | 一个值以哪些位表达？ | `int32`、IEEE 754 浮点、RGB 像素 | 字节怎样组织成文件 |
| **文本编码（text encoding）** | 文字怎样变成字节？ | UTF-8、UTF-16 | 模型 token 或自然语言分词 |
| **序列化（serialization）** | 内存中的结构怎样成为可传输字节？ | JSON、TLV、Protobuf、二进制记录 | 一定更小，或一定保密 |
| **压缩（compression）** | 怎样利用冗余减少平均字节数？ | DEFLATE、LZ、JPEG 的熵编码部分 | 保密或一定逐字节相同 |
| **加密（encryption）** | 没有密钥的人怎样不能读出明文？ | 加密密文；AEAD 是带认证的具体类别 | 普通加密不自动防篡改；只有正确使用并验证标签的 AEAD/MAC 等认证方案才提供该性质 |
| **容器（container）** | 多条数据流、元数据与索引怎样装在一起？ | ZIP、MP4、WAV、GGUF | 每条流用什么 codec |
| **codec** | 某类媒体怎样编码/解码？ | H.264、AV1、AAC、FLAC | 文件有无封面、时间轴或附件 |

`codec` 是 *coder/decoder* 的缩写；它可指压缩算法，也可带有采样、预测、变换和量化等媒体语义。媒体场景中，**容器像文件夹与目录，codec 像每件内容的编码规则**。同为 `.mp4` 的两个文件可能分别装 H.264/AAC 与 AV1/Opus；播放器必须同时认识容器和各条流的 codec。

## 1. 从值到字节：先固定解释规则

十六进制 `FF` 只是一个字节。它可以表示无符号 255、补码 -1、像素的最大通道强度、压缩数据的一部分，或加密密文。位模式本身没有“类型标签”。多字节数还需要宽度、符号、浮点格式、字节序和对齐约定，详见 [[计算机知识/30-计算机系统/01-数据表示字节序与对齐|数据表示、字节序与对齐]]。

因此“把内存写到文件”不是稳定序列化方案。原生对象可能含有平台相关的指针、填充、大小端、未初始化字节或临时地址；可交换的格式应逐字段声明长度、编码、字节序、版本与非法值处理。

## 2. 文本编码不是 tokenizer，也不是序列化格式

UTF-8 把 Unicode 码点序列编码为字节。它解决“`中`、`é` 这些文本如何表示成字节”，不规定一个业务对象有哪些字段，也不规定 LLM 怎样切 token。

一个最小例子：

```text
字符：A 中
Unicode 码点：U+0041 U+0020 U+4E2D
UTF-8 字节：41 20 E4 B8 AD
```

这五个字节可以作为 JSON 字符串的内容、Protobuf 的一个 string 字段，或 ZIP 内某个文本文件的载荷；这些是更外层的协议。LLM tokenizer 则可能把同一文本切为不同数目的 token，再映射到模型专属 ID。相关边界见 [[AI/20-LLM/10-原理/01-文本Unicode-Token与词表|文本、Unicode、Token 与词表]]；字符、正规化与换行在下一课展开。

## 3. 序列化：为“结构”建立可复现契约

序列化将有结构的数据写成字节，反序列化按**同一格式契约**重建它。可读性与二进制紧凑性是常见取舍，而非安全或性能的单调排序。

| 形式 | 直觉 | 常见优势 | 必须继续明确的事 |
| --- | --- | --- | --- |
| JSON / YAML | 以文本键和值表达对象 | 易阅读、调试方便 | 字符编码、数字精度、重复键、schema、大小限制 |
| TLV | Type–Length–Value 连续记录 | 可跳过未知字段，利于演进 | type 的含义、length 宽度与上限、嵌套边界 |
| Protobuf / MessagePack 等 | schema 或类型规则驱动的二进制数据 | 较紧凑、字段化 | schema/版本、未知字段策略、反序列化资源限制 |
| 原生对象内存 | 某次运行的实际布局 | 本机临时调试可能省事 | 几乎所有跨平台、长期与安全边界 |

以 TLV 为例，假设约定 `01` 是用户名、长度为一字节、文本为 UTF-8：

```text
01 03 4C 69 6E
│  │  └────── UTF-8: "Lin"
│  └──────── length = 3
└─────────── type = 1（由格式规范解释）
```

读取器必须先确认剩余字节至少有 type 和 length，再确认 `length <= 剩余载荷` 且不超出业务上限；不是“读到哪里算哪里”。

> [!warning] 反序列化是输入边界
> 格式合法不等于对象可信。除了避免会执行任意对象构造的格式，还要限制递归深度、数组数量、字符串长度、解压后的总大小和计算时间；把不可信输入交给宽容解析器，仍可能造成内存、CPU 或磁盘耗尽。

## 4. 压缩减少冗余；加密隐藏内容；顺序很重要

压缩利用来源中的统计规律，把常见模式以较短表示写出；它不能从任意数据中无损地稳定“变小”。加密的目标是让没有密钥的观察者看不出明文结构；好的密文近似随机，通常没有可压缩冗余。

所以常见的安全管线是：

```text
明文 → 序列化/媒体编码 → 压缩 → 带认证的加密 → 密文
```

先加密再压缩通常几乎没有收益。更重要的是，不要让攻击者同时控制“被压缩的秘密邻居内容”和观察到的密文长度：长度侧信道可能泄露秘密是否与猜测相同。含秘密的 Web/协议设计需结合具体威胁模型，不能用“已经压缩”代替安全设计。

加密也不等于完整性，除非所选方案提供认证并且接收端**验证认证结果后**才使用明文。哈希/校验和主要用于偶发损坏检测；它们不是对抗篡改者的密钥认证。第 03 课会区分这些校验用途。

## 5. 容器与 codec：文件后缀不是充分信息

一个容器通常定义文件头、轨道或条目、时间戳、索引、元数据和可选附件。codec 定义某条音频、视频或图像流的 coded/encoded representation 与 decoded samples 之间的语法和处理；它可以有损、无损，也可以是不压缩表示。归档容器也常把多个文件、目录名、权限与压缩条目组合起来。

```text
容器文件
├── 文件头：版本、全局标志
├── 视频流：codec = 某视频编码规则
├── 音频流：codec = 某音频编码规则
├── 元数据：标题、时长、语言（可选）
└── 索引：时间 → 数据位置
```

因此排障时不要只问“这是不是 MP4/ZIP”。还应记录：magic bytes 识别到了什么、容器版本、每条流的 codec profile、是否加密、索引是否存在、文件是否截断，以及播放器/解析器支持的能力集。

## 练习

1. 把“把 UTF-8 文本放进 JSON，再 gzip 压缩后用带认证加密发送”按层写出；对每层说明输入、输出和它**不**解决的问题。
2. 某人说“这个文件已经 Base64 编码，所以更安全”。指出 Base64 实际做什么，以及它不提供的至少两种性质。
3. 设计一个照片分享格式的诊断清单：哪些问题属于容器、图像 codec、元数据、压缩或加密？
4. 对上面的 TLV 记录，若长度字节为 `FF` 但文件只剩 8 个字节，写出解析器必须拒绝它的原因。

## 成功标准

- 我能解释 UTF-8、tokenizer、JSON、gzip、AEAD 各自处于什么层，不把它们统称为“编码”。
- 我知道 codec 与 container 可独立替换，扩展名不是可靠格式证明。
- 我知道加密后的数据通常不可有效压缩，且校验和不能代替认证。
- 我能为任何不可信序列化输入列出长度、深度、数量、解压大小和计算时间的限制。
