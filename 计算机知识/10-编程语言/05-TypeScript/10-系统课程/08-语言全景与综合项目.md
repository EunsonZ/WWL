# TypeScript 语言全景与综合项目：从类型技巧回到系统质量

> **学习位置**：[[计算机知识/00-开始/课程地图/05-TypeScript-课程地图|TypeScript课程地图]] · **适用边界**：strict 模式；ES2022 运行语义；Node 与浏览器环境区分。

## 语言知识的完整检查面

基础层要掌握原始值、数组、元组、对象、函数、类、模块、枚举以及 null/undefined；类型关系层要掌握结构化兼容、联合与交叉、字面量类型、控制流分析、重载、泛型与方差；类型计算层要认识 `keyof`、索引访问、条件类型、`infer`、映射类型、模板字面量类型和常用工具类型。

工程层要认识声明文件、声明合并、模块扩充、项目引用、构建增量、源码映射和 JS 迁移。装饰器存在不同提案历史与编译配置，不能把旧 experimental decorators、标准装饰器和反射元数据生态当成一种机制。JSX 是语法与类型检查入口，不等于某个框架的全部运行机制。`enum`、`const enum`、命名空间与现代 ESM 的取舍应结合输出、库发布和工具链兼容，避免仅按个人风格决定。

## 不必把所有问题变成类型谜题

如果验证某个路径字符串的条件类型比业务实现长十倍、编译耗时显著上升且报错无法理解，应考虑改用简单类型与运行时验证。类型层擅长表达稳定结构和局部关系，不适合承诺任意业务事实，例如“余额一定够”“网络永远成功”。公开 API 的可理解性也是质量指标。

配置与推导是设计的一部分。读懂报错应从最外层不匹配的关系开始，找具体字段或函数参数，而不是立即插入 `as unknown as T`。双重断言应有明确、可审计的理由和边界测试，不能成为日常胶水。

## 综合项目：有界并发的数据收集器

构建一个命令行工具，读取本地 JSON 任务清单，每项包含唯一 id 和一个受控测试地址。输入先经运行时验证；固定数量工作者执行请求；每项有总超时预算；支持协作取消；记录成功、失败与取消三类结果。示例默认使用本地回环服务，不访问用户未授权的站点。

输出稳定排序的结果文件，并采用临时文件写入后替换的方式减少半成品暴露。注意原子重命名不自动等同于掉电持久性；需要持久性时再讨论文件和目录同步。日志记录请求 id、阶段与耗时，不记录凭据。

## 验收要能抓住具体错误

类型侧：错误任务字段、遗漏状态分支和错误回调参数应被拒绝。运行侧：null 输入、超大任务清单、重复 id、畸形响应、超时、取消与写文件失败都有测试。并发侧：实际同时工作数量从未超过配置上限；失败策略与文档一致；退出后没有遗留任务或监听器。发布侧：从打包制品启动，而不是依赖编辑器路径别名。

进阶分支包括 Web Workers、共享内存和 Atomics、WebAssembly、跨 realm 对象、流式协议、SSR/水合、服务端渲染安全、可访问性与国际化。这里只给出它们与核心课程的连接：工作者涉及内存与通信，Wasm 涉及 ABI，流式传输涉及背压，SSR 涉及不同宿主与不可信输出。选择项目中真正遇到的边界继续深挖，而不是把所有框架名称塞进主干。

## 自检问题

为什么 TypeScript 无法证明网络响应符合接口？因为接口通常在输出中擦除，外部世界不受本地检查器约束。为什么所有测试通过仍可能存在故障？因为测试只覆盖有限输入和环境。为什么还要使用类型与测试？因为它们在不同阶段排除不同错误，配合清晰合同、日志与隔离，可以显著缩小剩余不确定性。
