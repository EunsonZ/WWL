# 外设接口与物理边界

## 两个入口

基础入口：从下面的引脚、导线和参考地开始，再看一个字节需要多少物理时间。快进入口：检查“吞吐预算”和“故障出口”，尤其 UART 帧、I2C 上拉和 CAN 重试。两路共享同一个问题：本组每秒 1000 个 12 bit 码，如何完整带状态传送，何时根本不能保证及时？

## 同名接口不等于同一物理条件

GPIO 表示一组输入/输出引脚能力；推挽输出驱动高低，开漏输出只能下拉而依靠上拉恢复高。引脚容限、VIH/VIL、驱动电流、边沿速率、参考地和电源来自具体器件。软件把某引脚复用成 UART TX，也不能据此将它直接连到 RS-232 电压接口。这里逻辑侧统一假设 3.3 V，并非所有接收器兼容。

UART 通过发送与接收双方约定的波特率和起止帧异步传字节；3.3 V TX/RX 是本例电气连接，RS-232/RS-485 是需要相应收发器的其他物理接口。SPI 由 SCLK、数据和片选组织同步传输，CPOL/CPHA、位序与片选保持必须匹配设备；没有一种普适的 SPI 最大频率。I2C 的 SDA/SCL 采用开漏上拉总线，地址、ACK、起止和仲裁是协议条件，RC 上升和电平是物理条件。读 [TI SLAA734A Rev A §3、§4.1–4.2](https://www.ti.com/lit/an/slaa734a/slaa734a.pdf) 对照实际 UART 与 SPI 配置，不能把一个厂商的相位位名称直接套到另一个厂商。

CAN 控制器通过额外收发器连接 CANH/CANL；标准 11 bit 数据帧与扩展帧分开讨论，CAN FD 又有不同数据阶段。经典 CAN 同时竞争时，发送 recessive 位却观察到 dominant 的节点退出仲裁，较小标准标识符先行；本例不混用标准和扩展标识符的整体优先级。读 [TI SLOA101B Rev B §4.1、§5](https://www.ti.com/lit/an/sloa101b/sloa101b.pdf)，对应仲裁过程和控制器/收发器分层。Bosch [M_CAN 产品说明](https://www.bosch-semiconductors.com/products/ip-modules/can-ip-modules/m-can/) 也明确其协议控制 IP 仍需物理收发器。

USB 中主机、设备、端点、传输类型、PHY 与软件 pipe 是不同对象。IN 表示向主机，OUT 表示离开主机；默认端点 0 用于控制。bulk 数据可以重试且不因此获得固定期限。[Microsoft USB endpoints and pipes，2025-05-09](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/usb-endpoints-and-their-pipes) 支持这些主机驱动对象的定义。USB 2.0 high-speed 的 480 Mbit/s 是物理速率，USB 3.2 控制器也可能另有 USB 2.0 PHY；参见 [AMD AM026 v1.4 的 USB controller 小节](https://docs.amd.com/r/en-US/am026-versal-ai-edge-prime-gen2-trm/USB-3.2-DRD-Controller)。本页没有把 USB 标称速率当程序可持续吞吐。

## 上拉同时面对低电平电流与上升时间

I2C 释放后，一阶近似 v(t)=VDD(1−e⁻ᵗ/ᴿᶜ)。从 0.3VDD 到 0.7VDD 的上升时间为

\[
t_r=RC[\ln(1/0.3)-\ln(1/0.7)]=0.84729786RC.
\]

取 Cbus=100 pF、Rpull=2.2 kΩ，tr=186.4 ns。按本例 Fast-mode tr≤300 ns，Rmax=300ns/(0.8473×100pF)=3.541 kΩ。若低电平端在 VOL≤0.4 V 时允许下拉 3 mA，Rmin=(3.3−0.4)/0.003=966.7 Ω，因此 2.2 kΩ 同时位于两界内。不是越小越好：过小电阻提高下拉电流。两个引脚、接插件与布线的电容都要计入 Cbus；200 pF 时同一电阻得到 372.8 ns，不能以原频率预算宣称通过。

这些阈值和 Fast-mode 的本页条件来自 [NXP UM10204 Rev7.0，§3.1、Table10、§7.1](https://cache.nxp.com/docs/en/user-guide/UM10204.pdf?fsrch=1&pageNum=1&sr=3)。数值 RC 推导由本页完成。真实波形可能包含传播、反射和噪声；一阶 RC 不等于完整信号完整性验证。

## 从帧推吞吐预算

本组每个 ADC 样本用 2 byte，再每四样本增加 8 byte 头：有效流量 2000+250×8=4000 byte/s。UART 8N1 每 byte 含 1 start+8 data+1 stop=10 bit，因此至少 40000 bit/s；115200 baud 占用约 34.72%，留出的时间还要覆盖协议间隔、其他流量和重试。每块 16 byte 用 1.3889 ms。帧格式变 8E1 就是 11 bit/byte，不能沿用这个占用率。

SPI 假设每个块 8 bit command+16 byte payload，并且不插额外空周期：136 clock/block，在 1 MHz 下 136 μs。设备片选间隔、转换就绪时间与总线共享是额外项。I2C 假设一次写入 7 bit 地址的 1 byte 地址字段、1 byte 寄存器索引、16 byte 数据，每 byte 连 ACK 共 9 clocks，因此 18×9=162 clocks；400 kHz 时约 405 μs，另加起止及总线空闲。时钟延展和重试未被这个名义数约束，没有额外上界就不能承诺 deadline。

经典标准 CAN 若用 8 byte 数据，SOF1+arbitration12+control6+data64+CRC15+delimiter1+ACK2+EOF7+intermission3=111 bit。可填充段从 SOF 到 CRC sequence 长 98 bit；用 floor((98−1)/4)=24 作为保守填充上界（插入反相位后后续连续计数可能提前达到五位），最多 135 bit，不含错误帧、重传和仲裁等待。500 kbit/s 的单帧名义预算≤270 μs。若每块 16 byte 拆两帧，至少还需应用层序号组装：一帧到达不能证明块完整。无限高优先级流量可让低优先级长期等不到总线。Bosch [M_CAN v3.3.1 §3.1.7](https://www.bosch-semiconductors.com/media/ip_modules/pdf_2/m_can/mcan_users_manual_v331.pdf) 的自动重传说明支持这一故障出口；此处 135 bit 是本页保守推算，不是手册给出的所有帧长度定理。

## 故障必须返回给数据链

UART framing/parity/overrun，SPI 片选或相位错，I2C NACK/延展超时，CAN bus-off/组包超时，USB disconnect/短传输都会破坏完整性。CPU 应返回状态、序号和缺测区间；重复帧须按序号去重，不能无标记补进采样序列。物理失配可能表现为偶发软件错误，但“重试后看似可用”不是电气容限通过。

读 [[电子电路/34-时序状态与协议/02-建立保持时钟偏斜与路径#固定同沿关系再算deadline]]，把其数据到达与采样窗口用于理解 SPI 的接收时序；返回选择极性相位和留出裕量。那个同步数字路径模型没有包括长导线反射，不能代替本页 RC 或 CAN 收发器分析。

## 四题与理由

1. 4000 byte/s 用 38400 baud 的 8N1 UART 是否够？答：不够，仅有效数据就需要 40000 bit/s，尚未计额外间隔。
2. I2C 100 pF 改成 200 pF，是否只需降低软件处理时间？答：不是；tr 变为 372.8 ns，违反本例 300 ns 条件，应调整上拉、总线电容或速率并实际检查电流/波形。
3. CAN 仲裁输了是否等于数据帧 CRC 失败？答：不是。仲裁无损退出，随后等待重发；CRC 是已传输帧的数据完整性检查，等待时间仍影响截止期限。
4. USB 480 Mbit/s 能否证明每 1 ms 更新一个控制量？答：不能。端点传输类型、主机调度、驱动与设备时序共同决定延迟；标称位率只给物理尺度。
