## 给数据命名不等于验证数据

`JSON.parse(text) as Order` 是告诉编译器采用某个视角，不是检查 JSON 的字段、金额范围或用户权限。跨进程和网络边界应先视作 unknown，完成结构检查、领域约束与必要的授权，才构造业务对象。三者分别回答“长什么样”“值是否有意义”“这个主体能不能这么做”。[^narrowing]

## 一个明确失败位置的解析器

以下例子只接受普通 JSON 风格的数据。函数本身不声称能安全读取任意带副作用 getter 或 Proxy 的敌意同进程对象；这也是输入合同的一部分。

```typescript
type Order = { id: string; cents: number };
type Result<T> = { ok: true; value: T } | { ok: false; error: string };

function parseOrder(value: unknown): Result<Order> {
  if (typeof value !== "object" || value === null || Array.isArray(value)) {
    return { ok: false, error: "expected object" };
  }
  if (!("id" in value) || !("cents" in value)) {
    return { ok: false, error: "missing field" };
  }
  const id = value.id;
  const cents = value.cents;
  if (typeof id !== "string" || !/^[A-Za-z0-9_-]{1,40}$/.test(id)) {
    return { ok: false, error: "invalid id" };
  }
  if (typeof cents !== "number" || !Number.isSafeInteger(cents) || cents < 0) {
    return { ok: false, error: "invalid cents" };
  }
  return { ok: true, value: { id, cents } };
}
```

通过 `typeof` 与 in 检查后再读取，将结果复制为新对象，而不是返回未经控制的原始对象。`Number.isInteger` 不足以证明整数精度未丢失，金额还需要 safe integer、币种、上下限和单位合同。这里仅演示非负安全整数分，未定义税率、货币转换或数据库存储精度。

是否拒绝额外字段、是否接受空白、是否规范化大小写，应由协议明示。上例忽略额外字段。若需要拒绝，必须枚举允许键，而不是误以为 TypeScript 结构类型自动做了这件事。数据结构正确以后，仍必须根据认证主体验证订单访问权。

## 判别联合让非法状态更难表示

```typescript
type LoadState =
  | { kind: "idle" }
  | { kind: "loading"; requestId: number }
  | { kind: "ready"; requestId: number; order: Order }
  | { kind: "failed"; requestId: number; message: string };

function unreachable(value: never): never {
  throw new Error(`unexpected state: ${String(value)}`);
}
```

相比 `{loading:boolean,error?:string,data?:Order}`，判别联合不能同时轻易表示“成功数据和失败消息都存在，但 loading 也为 true”的矛盾组合。switch 根据 kind 收窄，默认分支交给 unreachable 可帮助发现新状态没有处理。[^narrowing]

不过任意函数仍可以构造从 ready 直接回到 loading 的值，类型并未自动证明整个状态迁移协议。迁移应集中在 reducer 或受控方法中，测试允许边、拒绝旧请求返回值，并区分领域状态和界面显示状态。

## 取消请求还需要防止旧结果覆盖新结果

用户先查询 A，马上改成 B。B 很快返回并展示，A 随后返回。如果只按返回顺序设置状态，页面最终显示旧 A。AbortController 能请求支持该信号的操作中止，但仍需考虑响应已经到达、某段转换不响应取消、以及取消和提交结果之间的竞态。[^abort]

一个稳健的本地策略是递增 requestId。开始 B 时更新当前代号；在将结果提交到状态前，再检查返回结果的代号是否仍为当前值。取消用于节约资源，代号用于拒绝过期提交，二者不是同一个保证。结果一旦被服务器提交，本地 abort 也不能撤销该业务效果，见 [[计算机知识/85-综合贯通/02-超时重试幂等与事务发件箱|超时重试]]。

```typescript
let current = 0;
let state: LoadState = { kind: "idle" };

async function load(get: () => Promise<unknown>): Promise<void> {
  const id = ++current;
  state = { kind: "loading", requestId: id };
  try {
    const parsed = parseOrder(await get());
    if (id !== current) return;
    state = parsed.ok
      ? { kind: "ready", requestId: id, order: parsed.value }
      : { kind: "failed", requestId: id, message: parsed.error };
  } catch (error: unknown) {
    if (id !== current) return;
    state = { kind: "failed", requestId: id, message: "request failed" };
  }
}
```

这个例子仅解决单个状态所有者中的过期结果，不解决全局缓存一致性、组件销毁后的资源回收或 requestId 超出安全整数范围的长期运行策略。生产代码可以改用唯一令牌对象，并为错误信息设计可审计、不过度泄露细节的映射。

## Promise 的完成与资源的结束也要分开

`Promise.all` 中一个输入拒绝会使组合结果拒绝，但 Promise 协议本身不因此取消其余输入对应的外部操作。每个操作要有显式取消合同，外层还要处理之后的完成和清理。这与 [[计算机知识/10-编程语言/01-Python/10-系统课程/10-异步取消异常组与有界流水线|TaskGroup 和 gather 的差别]]、[[计算机知识/10-编程语言/04-Rust/10-系统课程/10-Pin投影任务所有权与取消协议|Future 与任务句柄的差别]] 是同一个所有权问题在不同语言中的表现。[^promise]

不要把浏览器 CORS 当认证机制，也不要把 TLS 当业务权限系统。编译器、浏览器来源策略、传输加密和服务端授权各控制不同边界。贯通关系在 [[计算机知识/35-计算机网络/10-系统课程/11-TLS身份验证重放与信任边界|TLS 与信任边界]] 和 [[计算机知识/85-综合贯通/04-跨层保证与反例矩阵|跨层保证矩阵]] 中展开。

## 验证点

本轮实验会拒绝 null、数组、NaN、Infinity、超出安全整数的金额和非法标识符；验证正常解析创建新的业务对象；并人为颠倒两个 Promise 的完成顺序，确认旧结果不覆盖新结果。类型测试还验证分支收窄和非法状态构造被拒绝。

这些测试不包含真实认证服务或网络攻击测试。parseOrder 的输出值得被业务逻辑采用，是因为明确的检查与复制，不是因为函数的返回类型看起来郑重。

[^abort]: WHATWG [DOM Standard，Aborting ongoing activities](https://dom.spec.whatwg.org/#aborting-ongoing-activities)，AbortSignal 是协作式操作合同。
[^promise]: ECMAScript 2022 [Promise.all](https://tc39.es/ecma262/2022/multipage/control-abstraction-objects.html#sec-promise.all)，组合 Promise 的兑现和拒绝算法，不提供通用外部任务取消。
