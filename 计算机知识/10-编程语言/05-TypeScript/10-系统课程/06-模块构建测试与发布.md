# 模块、构建、测试与发布：开发环境成功不是部署成功

> **学习位置**：[[计算机知识/00-开始/课程地图/05-TypeScript-课程地图|TypeScript课程地图]] · **适用边界**：strict 模式；ES2022 运行语义；Node 与浏览器环境区分。

## 建立一个可解释的构建闭环

最小项目应区分源码、测试、输出、配置与依赖锁定文件。固定目标运行环境，并在 CI 中从干净目录安装、检查、构建和测试。源码能够被编辑器识别不等于发布包包含所有运行文件；本地路径别名能被检查器解析，也不等于运行时会自动重写该路径。

建议把 `strict` 作为基础，再按项目启用 `noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`、`noImplicitOverride` 等独立约束。用于浏览器打包的配置不应直接照搬成 Node 库配置。源码映射有助于定位错误，也可能包含源码或路径信息，发布策略需要考虑调试需求与信息暴露。

## 模块接口包含运行时和类型两部分

包的 `exports`、主入口和类型入口需要相互一致。只导出类型名却没有相应运行值是合法的设计，但调用方必须使用正确导入方式。双 ESM/CommonJS 发布可能导致同一逻辑模块被加载成两份实例，单例状态、身份比较和缓存因此出现差异；不要在没有需求时增加两套发布路径。

树摇依赖静态分析与副作用信息，不意味着所有未显式调用的代码都能删除。模块顶层注册、全局修改、样式导入等可能具有副作用。把包标为无副作用前应验证实际导出和构建产物。

## 分开测试三个层次

类型测试检查非法调用被拒绝；单元测试检查纯逻辑和边界解析；集成测试检查真实模块加载、文件和网络适配器。把全部业务逻辑放在浏览器点击测试中，会让失败难定位；把所有外部边界 mock 掉，又无法发现导出配置和请求协议错误。

对异步测试，必须返回或等待 Promise，否则测试框架可能在断言执行前就判定通过。测试拒绝路径时确认真的发生了拒绝，不能只在 catch 中写断言却没有“未抛错则失败”。固定随机种子与可控时钟有助于重现，但不要掩盖真实并发契约。

## 依赖与发布的可追溯性

锁定文件记录解析结果，不证明依赖安全。审阅安装脚本、维护者变更、传递依赖和许可证；生产凭据不能放在源码、前端构建常量或公开源码映射中。发布前在独立临时项目中安装打包制品，而不是直接引用仓库源码，才能发现漏包和路径问题。

公共 API 变更要考虑调用方类型推导、可选字段语义和运行时行为。一个看起来“只是更精确的类型”也可能让旧代码无法编译，因此版本管理不只关注 JavaScript 输出是否变化。

## 练习与答案

建立一个只导出 `parseReading` 的小包，分别做源码测试与安装制品测试。故意把输出文件从打包列表移除：源码测试可能仍通过，制品测试应失败。再为一个错误参数添加 `@ts-expect-error`，确认它与运行时解析测试互补，而不是二选一。交付记录应包含实际 TypeScript、Node 版本及完整命令，不能只写“本地通过”。
