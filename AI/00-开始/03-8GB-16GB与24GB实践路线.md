# 8GB、16GB 与 24GB 实践路线

<!-- deep-review-02 -->
> [!tip] 使用本页前
> 资源容量不是性能保证。用[[AI/20-LLM/40-推理/09-KV缓存分页滑窗与前缀复用|KV 账本]]区分上下文成本，用[[AI/12-PyTorch/09-性能剖析编译动态形状与内存账本|性能剖析]]控制计时条件；所有 GPU 路线仍需在实际硬件核验。


显存数字是规划线索，不是能力承诺。能否完成某项工作同时受模型结构、参数规模、权重精度、上下文长度、batch、图像/音频尺寸、KV cache、优化器状态、驱动、框架版本、系统内存、磁盘和实现方式影响。不要根据“某模型有人跑过”就假定自己的机器也一定能运行。

## 先把任务分开

| 活动 | 主要资源 | 与“显存大小”的关系 |
| --- | --- | --- |
| 阅读、数据检查、传统基线、CPU 小实验 | CPU、内存、磁盘 | 没有 GPU 也能完成大量基础工作 |
| 小模型推理 | 权重、激活、KV cache、输入长度 | 长上下文或多并发会显著改变需求 |
| 小规模微调 | 额外的梯度、优化器状态、激活 | 通常比同一模型推理更占显存 |
| 从头训练或高分辨率生成 | 批量、激活、检查点、数据吞吐 | 单看参数量或显存都不足以规划 |
| 部署服务 | 并发、隔离、网络、日志、可用性 | 不是“本地能跑”就自动具备上线条件 |

## 三档路线：从最小闭环开始

| 可用 GPU 显存 | 优先做什么 | 避免把什么当成保证 | 建议的完成证据 |
| --- | --- | --- | --- |
| 约 8GB | CPU/小 GPU 数据管线、小模型分类或嵌入、低批量/短输入推理、读日志与测量 | 大上下文、多个并发、完整训练或高分辨率生成一定能完成 | 记录输入形状、精度、峰值显存、耗时和失败信息 |
| 约 16GB | 更完整的小模型实验、受限推理、较小批次微调探索；优先比较设置而非追求规模 | 某一量化格式或省显存技巧可普遍复现 | 同一任务下对比至少两个可解释设置，并说明质量/速度取舍 |
| 约 24GB | 较宽的推理与小规模训练探索空间，可研究显存、吞吐和上下文的权衡 | 可以无边界服务、训练任意模型或跳过数据与许可审查 | 给出资源预算、停止条件和从失败中恢复的步骤 |

> [!warning] “约”不是规格表
> 上表只用于决定从哪里开始。运行前必须现场读取实际 GPU、驱动、可用显存和框架兼容性；同时确认系统内存、磁盘余量、模型许可证和下载来源。显存碎片、其他进程或图形桌面也会使可用空间小于标称值。

## 资源预算的心智模型

推理至少要考虑四部分：权重、当前输入产生的激活、随上下文增长的 KV cache、框架/运行时开销。训练还会增加梯度和优化器状态；不同精度和算法的占用方式不同。因此下面的式子只用于提问，不用于精确估算：

```text
总需求 = 权重 + 激活 + KV cache + 运行时开销 +（训练时的梯度与优化器状态）
```

真正可靠的做法是：从小输入、小 batch、短上下文开始，记录峰值；每次只改一个变量；出现 OOM 时先缩小任务并保存报错，而不是同时改模型、精度、batch 和环境。

### 不同模态先缩小什么

| 路线 | 首先记录/缩小的输入变量 | 为什么不能只看参数量 | 当前课程状态 |
| --- | --- | --- | --- |
| LLM | context、并发序列数、KV cache dtype、batch | KV cache 和调度会随输入长度与并发改变 | 已交付；进入 [[AI/20-LLM/00-LLM-MOC\|LLM MOC]] |
| VLM | 分辨率、图片数、Patch/视觉 token、batch | 图像预处理和视觉 token 会同时影响时间与显存 | 已有核心正文；可用 [[AI/30-VLM/00-VLM-MOC\|课程地图]] 设计问题 |
| 语音/音频 | 采样率、时长、声道、流式窗口、batch | 特征帧数、缓存和解码延迟随时长累积 | 已有核心正文；可用 [[AI/40-语音与音频模型/00-语音与音频模型-MOC\|课程地图]] 设计问题 |
| 扩散 | 分辨率、latent 尺寸、采样步数、batch、VAE | 激活、attention、VAE 与多步采样的成本并不只由权重决定 | 已有核心正文；可用 [[AI/50-扩散模型/00-扩散模型-MOC\|课程地图]] 设计问题 |

这张表只说明预算变量的因果方向，不说明任一模型、运行时或 GPU 的兼容性。具体账本字段见 [[AI/90-资源/03-GPU显存与资源预算表|GPU 显存与资源预算表]]。

## 一条容器优先的实验路径

容器的价值是固定依赖与运行入口，不是“自动安全”。推荐把每次实验组织为：

```text
公开代码与配置样板
        +
受控挂载的输入数据目录（默认只读）
        +
独立输出目录（可清理、可备份）
        +
固定镜像与依赖版本
        =
可说明、可复现的实验边界
```

默认不要把宿主家目录、Docker socket、私钥目录或整个数据盘挂进容器；不要为了方便使用特权容器；不要在不需要时发布端口。详细的网络、许可证和资产边界见 [[AI/00-开始/04-环境安全许可证与资源边界|环境、安全、许可证与资源边界]]。

### Ubuntu 与 Arch 原生环境的区别

| 维度 | 容器中的用户空间 | Ubuntu 原生环境 | Arch 原生环境 |
| --- | --- | --- | --- |
| 依赖固定 | 镜像标签/摘要、项目锁文件更易一起记录 | 由 APT 与发行版版本维护 | 由 pacman 的滚动发布维护，尤其需要整体更新策略 |
| 内核与 GPU 驱动 | 仍使用宿主内核与宿主驱动 | 驱动、内核和 DKMS/发行版策略需匹配 | 内核、驱动和用户空间更新节奏更紧密，避免 partial upgrade |
| 适用性 | 有成熟镜像、希望隔离项目依赖时优先 | 希望稳定的开发/部署基线时常见 | 想学习系统、愿意维护滚动发行版时适合，不是“更快的容器” |
| 共同边界 | 容器不能替代宿主驱动兼容性、许可证审查、数据权限或网络门禁 | 同左 | 同左 |

容器镜像可以是 Ubuntu 用户空间，即使宿主是 Arch；但它不会带来另一个内核，也不会绕过 GPU 驱动 ABI。遇到安装或兼容性问题，回到 [[计算机知识/20-操作系统/01-Linux/00-Linux基础-MOC|Linux 基础]]理解包、进程、驱动和日志，再查所用框架与硬件的当前官方文档。

## OOM 或很慢时的安全排查顺序

1. 保存完整报错、输入形状、版本、可用/峰值资源和当前设置；
2. 确认不是其他进程占用 GPU，且不要杀掉不属于自己的任务；
3. 一次只缩小一个变量：batch、上下文、分辨率、模型或精度；
4. 若要使用量化、offload、checkpointing 或 flash attention，先说明它改变的是哪一部分资源与哪种质量/速度风险；
5. 复跑一个最小基线，比较结果而不是只报告“终于跑通”。

## 练习：写一页资源计划

为一个你准备做的小实验写下：任务、输入上限、模型/方法、精度、batch、数据位置、输出位置、可用资源、停止条件和回滚方式。若有任何一项未知，就把它列为“开始前必须核验”，而不是用猜测填满。

**成功标准：** 你能解释为什么选择从小实验开始；即使 OOM 或下载失败，也能保留证据并回到一个安全、可复现的基线。
