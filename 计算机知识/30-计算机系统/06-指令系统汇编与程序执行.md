# 指令系统、汇编与程序执行

## 本课目标

学完后，你应该能够：

- 从源代码一路追到编译、汇编、链接、装载和机器指令；
- 区分高级语言语义、汇编表示、机器码、ISA、ABI 与微架构；
- 用程序计数器、通用寄存器、状态寄存器和内存描述一条指令可见的状态变化；
- 逐步解释取指、译码、读操作数、执行、访存与写回；
- 阅读一小段 x86-64 或 AArch64 汇编时，先识别数据流和控制流，不把助记符背诵当成理解；
- 说明优化、反汇编和调试观察为什么都必须绑定具体 target、编译选项与 ABI。

适用场景：理解 C++ 编译产物、调试崩溃、阅读性能热点、判断 SIMD/CPU feature dispatch，以及为后续流水线、异常和系统调用课程建立共同语言。

> [!important] 本页的安全与适用边界
> 本页只使用伪代码和说明性汇编片段，不提供可直接改写系统状态的程序。汇编语法、寄存器名、指令编码和调用约定依赖 ISA、汇编器、操作系统与 ABI；下文的 x86-64/AArch64 片段用于对照概念，不是可跨平台复制的固定模板。

## 1. 直觉：CPU 看见的不是变量名，而是受契约约束的状态变化

高级语言可以写出“把两个元素相加并根据结果选择下一步”。CPU 最终执行的却是一串编码后的指令。每条指令从某个机器状态出发，读取寄存器或内存，产生新值，并决定下一条指令的位置。

```text
源代码中的值、表达式和控制流
  ↓ frontend：解析、类型检查与语言语义
中间表示/内部程序形式
  ↓ optimizer + target code generation：依规则优化并选择目标 ISA
  ├─ 可选输出人可读的汇编文本 → 独立汇编器
  └─ 或由集成 assembler/code emitter 直接生成机器码
  ↓
目标文件：机器码 + 符号 + 重定位 + 调试等元数据
  ↓ 链接器布局并解析跨文件引用
可执行文件/共享库
  ↓ 加载器建立代码、数据、栈和库映射
进程中的指令字节与数据
  ↓ CPU 取指、译码并执行
架构可见状态发生变化
```

“源代码→汇编文本→目标文件”是一条很有用的可观察路线，却不是所有工具链都会在磁盘上生成 `.s` 文件的强制流水线。编译驱动程序可把内部表示直接交给集成汇编器或代码发射器；LTO 还可把部分优化推迟到链接阶段。因此调查时应记录工具链、target、优化/LTO 选项和实际产物，不要从一张六阶段示意图推出必然的临时文件。

“源代码的一行”与“机器指令的一条”通常不是一一对应。编译器可以内联函数、消除无用计算、把循环向量化、把值只保存在寄存器中，或让多行代码共用同一段指令。调试信息只是帮助工具把优化后的机器状态映射回源代码，不会恢复已被优化掉的一切。

## 2. 六层对象必须分开

| 层 | 精确定义 | 主要回答的问题 |
| --- | --- | --- |
| 高级语言 | 由语言标准和实现定义的类型、表达式、对象生命周期与可观察行为 | 程序“应该做什么”？ |
| 汇编语言 | 某 ISA 机器指令及伪指令的人类可读表示 | 这些字节如何写成助记符？ |
| 机器码 | CPU 可取指和译码的编码字节/指令字 | 内存中的具体编码是什么？ |
| ISA | 软件可见的指令、寄存器、地址与异常等架构契约 | 合法程序可以要求处理器做什么？ |
| ABI | 分开编译的二进制组件如何交接参数、栈、符号、布局等 | 两个二进制怎样合作？ |
| 微架构 | 某个处理器实现 ISA 的内部组织 | 这颗 CPU 怎样更快或更省电地实现契约？ |

**ISA（Instruction Set Architecture）**是软硬件之间的架构契约。它通常规定指令编码与语义、架构寄存器、地址计算、控制转移、异常模型和内存访问相关规则。**微架构**则是实现方法：流水线深度、执行端口、缓存大小、分支预测器、乱序窗口都可在不同 CPU 中变化，只要对软件呈现符合 ISA 的结果。

因此，两颗处理器可以都运行同一份 ISA 机器码，却有不同吞吐、延迟和功耗；同一算法编译到 x86-64 与 AArch64，又会得到不同机器码。ABI 还会继续区分同一 ISA 上的操作系统和工具链约定。相关二进制边界回看 [[计算机知识/30-计算机系统/03-ABI调用约定与静态动态链接|ABI、调用约定与静态/动态链接]]。

## 3. 从伪源代码到数据流

先看一段不绑定具体语言的伪代码：

```text
x = memory[base + index * element_size]
y = x + bias
if y == 0:
    result = fallback
else:
    result = y
```

它至少包含三类工作：

1. **地址计算与加载**：计算元素地址，再把内存值读入 CPU 可直接使用的位置；
2. **算术与比较**：生成 `y`，再判断它是否为零；
3. **控制转移或条件选择**：依据条件选择 `fallback` 或 `y`。

一种概念化的类 RISC 汇编可以写成：

```asm
shift   r_offset, r_index, log2(element_size)
add     r_addr, r_base, r_offset
load    r_x, [r_addr]
add     r_y, r_x, r_bias
compare r_y, 0
branch_equal use_fallback
move    r_result, r_y
branch  done
use_fallback:
move    r_result, r_fallback
done:
```

这不是任何具体 ISA 的可汇编程序，而是把隐藏在表达式里的数据依赖显出来：地址依赖 `base/index`，加法依赖加载结果，分支依赖比较结果。

真实优化器可能把乘法折成移位、把比较并入设置条件的指令、用条件选择消除分支、重排无依赖指令，或在证明结果不被观察时删除整段工作。汇编是某次构建的证据，不是源代码的永恒翻译。

## 4. 架构可见状态：程序在概念上改变什么

为了讨论一条指令，可以把架构状态简化为：

```text
S = {
  PC,                  下一条架构指令的位置
  general_registers,   整数地址与普通整数数据
  vector_registers,    SIMD/浮点数据（若 ISA 提供）
  status/control,      条件状态、控制位与当前执行状态
  memory,              经当前地址空间可访问的字节
  privilege_state      当前特权执行状态
}
```

指令可抽象为 `S_next = instruction(S)`。这不是说硬件内部真的只做一次整体函数调用，而是说明 ISA 给软件的承诺：执行后哪些架构可见状态应改变，哪些不应改变。

### 程序计数器

程序计数器（PC）或指令指针指向当前/下一条架构指令的位置，具体定义依 ISA 而异。普通顺序执行会前进到后继指令；分支、调用、返回、异常和中断会选择别的位置。

### 通用寄存器

通用寄存器保存当前计算需要的整数、位模式或地址。名字里的“通用”不保证每个寄存器完全没有特殊角色：某些 ISA/ABI 会赋予栈指针、链接寄存器、参数寄存器等特殊语义或约定。

### 状态与条件

有的 ISA 让算术指令更新一组条件标志，随后条件分支读取这些标志；有的指令选择显式产生布尔结果；实际设计还可混合两者。不要把“每次比较都写一个统一 flags 寄存器”当成所有 ISA 的共同模型。

### 内存

加载读取内存，存储写入内存；大多数算术先在寄存器或内部执行资源中完成。程序提供的通常是虚拟地址，地址翻译、权限检查与缓存访问共同决定请求怎样到达数据。完整映射语义见 [[计算机知识/30-计算机系统/02-进程虚拟地址空间与内存映射|进程虚拟地址空间与内存映射]]。

## 5. 一条指令的逐步数据路径

为先说明一条指令的**架构语义**，教学上常把它拆成六步；这里采用“一条指令完成后，再观察下一条”的简化顺序模型：

1. **取指（fetch）**：用 PC 指定的虚拟地址请求指令字节，经过地址翻译和指令缓存取得编码；
2. **译码（decode）**：识别操作、操作数位置、立即数和控制需求；
3. **读操作数（operand read）**：取得架构寄存器值，或准备内存地址所需输入；
4. **执行（execute）**：ALU、移位器、向量单元或地址生成单元完成运算；
5. **访存（memory access）**：若为 load/store，访问数据缓存与更远内存层级，同时进行地址翻译和权限检查；
6. **写回（write-back）**：把本模型中的结果写入其架构目标（寄存器或内存）；控制转移则按顺序后继、分支目标、调用/返回目标或异常入口选择后继 PC。

```text
PC
 ↓
地址翻译 → 指令缓存 → 指令字节 → 译码
                              ↓
                    寄存器/立即数
                              ↓
                   执行单元/地址生成
                         ↓          ↓
                    算术结果    数据缓存/内存
                         └────┬─────┘
                              ↓
                      架构结果与下一 PC
```

这是**功能分解**，不是所有 CPU 都严格用六个时钟完成一条指令。更不能把本模型里的“写回”混成以下不同层次：

| 层次 | 它表示什么 | 它不自动表示什么 |
| --- | --- | --- |
| 结果产生 | 执行单元算出算术结果，或 load 从内存层级取得数据 | 结果已经写入架构寄存器或对其他线程可见 |
| 转发（forwarding/bypass） | 把尚未写回的内部结果送给依赖它的后续内部操作 | 指令已完成，更不表示已经提交 |
| 内部完成（completion） | 该指令所需的内部执行已结束，结果可被保留等待 | 架构状态已按程序顺序改变 |
| 退役/提交（retire/commit） | 许多乱序核心按程序顺序让已完成指令的结果成为架构可见状态，以支持精确异常 | 跨线程已观察到该结果，或数据已经持久化 |
| 跨线程可见 | 其他执行流能否观察到某次内存写，受语言/ISA 内存模型、缓存一致性与同步协议约束 | 写已落到持久介质 |
| 持久化 | 数据经所需的写回、屏障、设备/文件系统协议等步骤后能在相应故障模型下保留 | 仅凭 store、completion 或 retire 就能保证 |

简单微控制器可能顺序复用硬件；现代高性能核心则会让许多指令流水、并行、推测和乱序地处理。第 07 课会展开结果转发、内部 completion 与按序 retire/commit 怎样共同提供架构语义和精确异常：[[计算机知识/30-计算机系统/07-CPU数据通路流水线分支预测与乱序执行|CPU 数据通路、流水线、分支预测与乱序执行]]。跨线程发布/获取则见 [[计算机知识/30-计算机系统/09-进程线程调度同步与IPC#6. 原子性、顺序与可见性是三个问题|第 09 课]]。

## 6. 可观察例子：追踪一次 load-add-store

假设开始时：

```text
r_base = 0x1000
r_bias = 3
memory[0x1000 .. 0x1003] 按当前目标规则表示整数 7
```

说明性汇编：

```asm
load  r_value, [r_base]
add   r_value, r_value, r_bias
store [r_base], r_value
```

逐步观察：

| 步骤 | 读入 | 架构可见结果 |
| --- | --- | --- |
| load | 地址寄存器 `r_base`，地址翻译后的内存字节 | `r_value = 7` |
| add | `r_value = 7`，`r_bias = 3` | `r_value = 10` |
| store | 地址 `0x1000`，值 10 | 对应内存位置表示 10 |

这张表仍省略了字节序、访问宽度、对齐、缓存、并发可见性和异常。若 load 指定的地址未映射，处理器不会凭空得到 7，而会产生相应的同步异常；若其他核心同时访问该位置，还要遵守语言内存模型、ISA 内存顺序与缓存一致性规则。数据字节边界见 [[计算机知识/30-计算机系统/01-数据表示字节序与对齐|数据表示、字节序与对齐]]，缓存路径见 [[计算机知识/30-计算机系统/04-缓存局部性带宽与延迟|缓存、局部性、带宽与延迟]]。

## 7. 分支、调用和返回都在选择下一条指令

### 分支

条件分支读取比较结果或条件状态，在“顺序后继”和“目标地址”之间选择。循环本质上也依靠比较与向后控制转移反复执行一段指令。

### 函数调用

调用需要保存返回位置，并把控制流转到函数入口。返回再恢复该位置。具体机制并不统一：

- 某些 ISA 有显式链接寄存器；
- 某些调用指令把返回信息放入栈或另一个约定位置；
- 编译器还可能内联或采用尾调用，使通常的调用/返回序列消失。

“参数放哪些寄存器、哪些寄存器由谁保存、栈怎样对齐”是 ABI 调用约定，不应从 ISA 名称单独推出。

## 8. x86-64 与 AArch64：同一概念，不同表达

下面只比较层次，不把某个操作系统 ABI 混进 ISA：

| 维度 | x86-64 常见特征 | AArch64 常见特征 | 不能推出的结论 |
| --- | --- | --- | --- |
| 指令编码 | 长度可变，编码形式很多 | 基础 A64 指令通常固定 32 bit | 固定长度不等于每条都一个周期；可变长度也不等于必然慢 |
| 普通算术 | 存在二操作数和三操作数等多种形式，部分指令可带内存操作数 | 常见 load/store 与寄存器算术分开，算术常见三寄存器形式 | 源代码操作数数量不能直接预测指令数量 |
| 条件状态 | 常使用 RFLAGS 中的条件标志 | 常使用 NZCV 条件标志，也有条件选择等形式 | flags 的具体更新必须看指令语义 |
| 返回信息 | 具体调用序列与 ABI 共同决定 | ISA 提供链接寄存器概念，ABI 常约定其用途 | 有链接寄存器不代表永不使用栈 |
| 内存模型 | 架构内存顺序相对较强，但仍需语言原子/同步规则 | 允许更多硬件重排，提供相应屏障与 acquire/release 指令 | 单线程反汇编不能证明多线程程序正确 |

一个“把两个寄存器相加”的说明性对照可能长这样：

```asm
; x86-64 Intel 风格示意：目的寄存器也常是一个输入
add rax, rbx        ; rax := rax + rbx

// AArch64 风格示意：显式写出两个输入与一个目的
add x0, x1, x2      // x0 := x1 + x2
```

这里没有声明这些寄存器一定是函数参数，因为参数位置属于具体 ABI。x86 还存在 Intel/AT&T 等汇编语法差异，操作数顺序和记法可能不同；看到助记符前先确认反汇编器采用的语法。

## 9. 怎样阅读一小段反汇编

按以下顺序比背寄存器表更可靠：

1. 记录目标三元组/平台、ISA 扩展、编译器、优化级别和二进制来源；
2. 找函数或基本块边界，但允许内联、尾调用和符号缺失；
3. 标出每条指令的读集合与写集合；
4. 沿寄存器定义追踪数据从哪里来、到哪里去；
5. 标出 load/store 的基址、偏移、宽度和可能对象；
6. 画出条件分支、无条件分支、调用与返回形成的控制流；
7. 再结合 ABI 判断参数、返回值、callee-saved/caller-saved 寄存器；
8. 最后回到源代码与调试信息提出假设，而不是强行逐行对齐。

对性能问题还要查看热点、计数器和当前微架构资料。只看到某条“高级指令”不等于它在所有处理器上延迟更低；只看到较短汇编也不等于端到端更快。

## 10. 常见误解

| 误解 | 更准确的说法 |
| --- | --- |
| 编译一定会先生成汇编文本 | 汇编文本是可选的观察/交换形式；工具链也可用集成 assembler/code emitter 直接产生目标代码 |
| 汇编就是机器码 | 汇编是机器指令的人可读表示；汇编器还会处理标签、伪指令和重定位 |
| 一行源代码对应一条指令 | 对应关系受优化、内联、向量化和语言语义影响，可能一对多、多对一或被消除 |
| ISA 就是 CPU 内部电路图 | ISA 是软件可见契约；流水线、缓存和执行单元属于微架构 |
| 寄存器就是特别快的一小块普通内存 | 寄存器属于架构状态与执行数据路径，寻址和用途不同于普通内存 |
| load 直接读取物理 RAM | 程序通常给出虚拟地址，请求可能命中缓存，也可能触发地址翻译、缺页或权限异常 |
| x86-64/AArch64 决定完整调用约定 | ISA 只提供能力；具体 OS/工具链 ABI 决定二进制交接规则 |
| Debug 汇编最接近“真实程序” | Debug 更容易映射源代码，但 Release 优化构建才更接近实际部署性能行为 |

## 练习

1. 把本页伪代码拆成“加载、算术、比较、控制转移”四类操作，画出每一步的输入和输出依赖。
2. 对 load-add-store 例子，分别加入“地址未映射”“数据已在 L1”“数据需从更远层级取得”三个条件。哪些改变架构结果，哪些只改变等待时间？
3. 解释为何 `add x0, x1, x2` 与 `add rax, rbx` 的操作数形式不同，却都能表达加法。不要把寄存器名解释成跨平台 ABI 参数表。
4. 画一张从 `main.cpp` 到运行中指令的链，标出 frontend/优化/代码生成、可选汇编文本、汇编器或代码发射器、链接器、加载器、ISA 与 ABI 各自出现的位置。
5. 给一段未知反汇编设计最小记录表：至少包含 target、汇编语法、构建模式、指令地址、读/写寄存器、访存宽度和控制流目标。

## 成功标准

- 你能用一句话分别定义机器码、汇编、ISA、ABI 和微架构；
- 你能画出“源代码 → 目标文件 → 可执行文件 → 虚拟映射 → 取指执行”的完整路径；
- 你知道汇编文本是可选的观察/交换形式，不会把磁盘上的 `.s` 文件当成所有编译流水线的必经产物；
- 你能逐条追踪 load-add-store 对寄存器和内存的架构可见影响；
- 你不会把 x86-64 或 AArch64 的寄存器表、汇编语法、调用约定推广到所有平台；
- 你能解释为什么功能相同的程序会因编译选项和 CPU 实现不同而产生不同指令与性能。
