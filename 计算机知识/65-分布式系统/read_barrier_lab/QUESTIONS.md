# 先预测，再解除提示

本题纸不含答案。成员A/B/C固定，单键寄存器初始0，节点遵守协议、非Byzantine；不同身份严格多数为2。稳定term/vote/log先于相应确认保存；共识前缀/领导者完备性作为读协议的下层合同。

1. term1主A与B/C隔离，B在term2通过B/C提交并回答put7。其后A收到get。A的role仍leader、自己的log/commit/applied均未变化，能直接返回0并称线性一致吗？写出历史的强制顺序。
2. A在隔离前收过B的一次term1心跳确认。现在get后把这张旧票和自己相加，是否足够？若给该读一个新nonce，只重复B的旧确认十次又怎样？
3. 新主B的日志包含前任已提交的put7，但B自己的commit/applied还停在0。B得到新鲜多数心跳后能否返回0？本任期空操作提交解决哪一层信息问题，哪些事仍须另等？
4. 某次读捕获readIndex=4，同任期新鲜多数确认已齐，但applied=3、状态仍旧。此时应返回什么状态？让apply推进到4，与提高任期或扩大超时有什么不同？
5. 读在term2捕获索引后跨过term3/term4重选，再拿term4的新鲜多数给这份旧索引盖章，会怎样？状态上下文至少绑定哪些身份；服务进程重启后旧读确认能否续用？
6. A发读屏障后，B才投term3、C随后提交新写；A延迟收到先前已产生的term2屏障确认。A若未看到更高任期，是否必然不能完成这次读？用调用/返回区间说明‘新主已出现’与‘历史仍可线性化’的区别。超时/无法取到多数算业务值0吗？
