# 继承、组合、variant 与异常：怎样让非法状态更难表达

> **学习位置**：[[计算机知识/00-开始/课程地图/02-C++-课程地图|C++课程地图]] · **适用边界**：C++20；ABI、容器实现与后续标准不混同。

## 继承首先是替换关系，不是复用语法

若把派生对象交给只理解基类的代码，仍应保持基类承诺的前置条件、后置条件和不变量。只因为两个类型有相同字段就建立继承，容易让修改彼此耦合。组合把“拥有某能力”和“本质上是一种某对象”分开，通常更容易控制依赖。

动态多态通过虚函数接口表达运行时可替换行为。通过基类指针删除派生对象时，公共基类析构通常需要是虚函数；另一种设计是受保护的非虚析构，禁止这种删除路径。`override` 让编译器检查覆盖意图，避免因为 const、参数或限定符差异而意外隐藏函数。

## 对象切片与构造期调用

`Base b = derived;` 只保存基类子对象，不会把派生状态与动态行为完整搬进去。需要运行时多态时一般通过引用、指针或明确的类型擦除包装访问。构造和析构期间的虚调用也不能假定派生部分已经构造或仍然存在；对象阶段决定可用行为。

多重继承、虚继承和菱形结构有合理用途，但会增加布局和转换复杂性。虚表是常见实现策略，不是可以跨 ABI 序列化的标准内存格式。RTTI、`dynamic_cast` 和 `typeid` 提供运行时类型能力，代价与可用性还受构建配置约束。

## 封闭状态集合用代数数据类型表达

```cpp
struct Loading {};
struct Ready { std::string data; };
struct Failed { std::string message; };
using State = std::variant<Loading, Ready, Failed>;
```

它避免 `bool done; bool failed; string data; string error;` 产生“既没完成又有成功数据”等组合。访问时通过 `std::visit` 覆盖状态；新增状态会推动访问逻辑重新接受检查。类型系统不能自动验证 message 不为空等业务规则，构造边界仍要校验。

`optional<T>` 表达缺失，不说明缺失原因；`variant<T,E>` 可以携带失败原因；C++23 的 `expected` 是后续标准能力，C++20 主线不把它当作已经可用的标准库组件。选择时看错误是否普通分支、需要携带什么上下文、是否跨接口传递。

## 异常和错误码都需要协议

异常适合把非局部失败向有恢复能力的边界传播，并与 RAII 配合。错误码适合需要显式检查、跨 C ABI 或禁用异常的环境。两者都可能被误用：异常被吞掉会隐藏失败，错误码被忽略也一样危险。

抛出的异常通常按 `const&` 捕获，避免切片和不必要复制；重新抛出用 `throw;` 保留当前异常，而不是随意构造一个丢失上下文的新对象。析构函数不应在异常展开期间再让异常逸出；可恢复的提交、刷盘或关闭应提供显式操作。

## lambda 捕获就是一种对象布局

捕获值意味着闭包中保存状态，捕获引用意味着保存借用关系。异步回调使用 `[&]` 很容易把已结束的栈对象带到未来。`[this]` 捕获的是指向当前对象的指针，不延长对象寿命；把某个成员值复制进去与保存 `this` 具有不同生命周期。

需要把所有权移入回调，可以使用初始化捕获：`[p=std::move(owner)]`。这会让闭包自身可能不可复制，进而影响能否放入要求可复制目标的包装器。`std::function` 的类型擦除便利与分配/复制要求，必须和具体回调语义一起考虑。

## 练习：设计一个下载任务状态

至少区分未开始、进行中、完成、取消和失败。完成状态携带完整数据，失败状态携带错误，进行中状态携带可验证进度。不要让 `optional<data>` 和 `optional<error>` 各自随意组合，否则仍可能同时出现成功和失败。

答案关键不在选择 `variant` 这个名称，而在定义允许转移：取消后回调是否仍可能到达？失败后能否重试？重试是否复用同一任务身份？这些问题把 C++ 类型建模连接到操作系统状态机和网络超时协议。
