# 05 · 贪婪、惰性与回溯

## 本课目标

解释为什么量词会匹配过多或尝试多条路径，知道惰性量词的真实含义，并能用更具体的边界代替宽泛通配。

## 贪婪量词先尽可能多地消费

这里的“消费”是指：字符被包含进本次匹配结果。锚点和环视只检查位置，通常不消费字符。

输入：

```text
<item>first</item><item>second</item>
```

模式：

```regex
<item>.*</item>
```

`.*` 默认贪婪，通常会先走到文本末尾，再回退到最后一个能让 `</item>` 成功的位置。因此一次匹配可能覆盖两个元素。

> [!warning] 这里只演示边界行为
> 不要用这种正则解析任意 HTML。真实 HTML 允许嵌套、属性、注释、脚本与不规则空白，应使用 HTML 解析器。

## 惰性量词先尝试尽可能少

在常见回溯型引擎中，量词后加 `?` 会变成惰性版本：

```regex
<item>.*?</item>
```

它从较短候选开始扩展，因而上例第一次通常只匹配 `<item>first</item>`。

常见对应关系：

| 贪婪 | 惰性 |
| --- | --- |
| `*` | `*?` |
| `+` | `+?` |
| `?` | `??` |
| `{m,n}` | `{m,n}?` |

“惰性”不等于“更快”或“更安全”；它仍可能反复尝试候选。最好的边界往往是明确说明哪些字符可以出现。

## 排除式字符类通常更具体

提取双引号中的简单字段：

```regex
"[^"]*"
```

它表达“一个双引号，随后是零个或多个非双引号字符，再到下一个双引号”。这通常比 `".*?"` 更直接。

但若字段允许转义引号，例如 `"a \"quoted\" value"`，简单字符类又不够，需要根据格式定义转义规则，或交给 JSON / CSV 等正式解析器。

## 回溯型引擎如何寻找路径

“回溯”可以先理解为：引擎选择一条路径，后来失败时退回最近的选择点，再换一种长度或分支尝试。

以模式为准，可以把常见回溯引擎想象为：

1. 从某个起点选择一条可能路径；
2. 量词或分支作出选择；
3. 后续失败时，退回最近的选择点；
4. 换一个长度或分支继续尝试；
5. 成功或穷尽所有路径。

这种机制让反向引用、环视等能力很灵活，但含糊且嵌套的量词可能产生大量组合。RE2 等非回溯引擎使用不同策略，以限制某些高级语法为代价换取可预测的线性时间。

## 先限定范围，再决定贪婪性

需求：提取一行中 `message=` 后到行尾的内容。

如果输入保证一条记录一行，可以写：

```regex
message=([^\r\n]*)
```

这里直接排除了换行，不依赖点号是否启用了 DOTALL，也不需要纠结 `.*` 或 `.*?`。

需求：提取逗号前的字段，可以写：

```regex
[^,]*
```

如果格式是 CSV 且允许引号、转义、字段内换行，请使用 CSV 解析器。

## 可观察例子：最后一个扩展名

输入：

```text
archive.2026.08.tar.gz
```

模式：

```regex
\.([A-Za-z0-9]+)$
```

通过结尾锚点直接约束最后一段，得到 `gz`。与其先写 `.*` 再尝试修补，不如从“结果与字符串结尾的关系”开始设计。

## 练习

从下面文本中分别提取两个简单的双引号字段：

```text
name="alpha" status="ready"
```

要求：

1. 先用贪婪点号观察过度匹配；
2. 再用惰性点号得到更小、较接近目标的局部结果；
3. 最后用排除式字符类完成；
4. 写出该方案不支持转义引号的限制。

把三个表达式和匹配结果写到 [[编程知识/30-实践/01-正则表达式实验区/02-练习场#练习 5 · 引号字段|练习场]]。

## 成功标准

- 我能描述贪婪与惰性的尝试顺序。
- 我知道惰性量词不自动带来更高性能。
- 当终止符明确时，我会优先考虑排除式字符类或锚点。
- 我能指出简单正则与正式格式解析器之间的边界。
