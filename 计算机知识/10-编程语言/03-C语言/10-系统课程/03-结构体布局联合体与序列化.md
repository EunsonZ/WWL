# 结构体不是文件格式：布局、别名和二进制协议

> **学习位置**：[[计算机知识/00-开始/课程地图/01-C语言-课程地图|C语言课程地图]] · **适用边界**：ISO C17；C23 与 POSIX 扩展另行标识。

## 为什么成员大小之和不等于结构体大小

设常见 ABI 中 `char` 占 1 字节、`int` 占 4 字节且按 4 字节对齐：

```c
struct Record { char tag; int value; char valid; };
```

一种常见布局是 `tag` 在偏移 0，`value` 在偏移 4，`valid` 在偏移 8，结构体总大小 12。中间和末尾的填充帮助后续成员及数组中的下一对象满足对齐。这里的数值是**指定 ABI 下的示例**，不是 ISO C 保证；实际检查用 `sizeof`、`_Alignof` 和 `offsetof`。

把成员重新排列可能减少空间，但会改变 ABI。公开结构体一旦被其他模块直接使用，字段顺序和大小就是兼容性的一部分。高性能布局也不只追求最小大小：频繁由不同线程写入的相邻字段可能造成伪共享，数组结构 AoS 和结构数组 SoA 的选择还取决于访问模式。

## 不要通过 `memcmp` 推导结构体值相等

两个记录的语义字段可以相等，填充字节却不同。`memcmp(&a,&b,sizeof a)` 比较对象表示，不是逐字段语义比较。浮点 NaN、有符号零、指针表示也让“相同字节”“相等的值”“相同业务对象”成为三个不同问题。

正确的相等函数应逐项比较需要比较的字段。需要稳定哈希时，同样应按明确编码后的语义字段计算，不能把未规定的填充字节混入哈希或发到网络上。

## 联合体与带标签数据

联合体共享一块足够容纳最大成员的存储。它适合表达互斥的表示，但不能独自告诉使用者当前哪一成员具有有效业务意义。常用做法是把枚举标签和联合体放进同一结构：

```c
enum ValueKind { VALUE_INT, VALUE_TEXT };
struct Value {
    enum ValueKind kind;
    union { long integer; const char *text; } as;
};
```

每个分支必须先检查 `kind`，再访问约定成员；还要决定字符串是借用还是拥有。语言允许或限制的表示重解释规则，与“标签和数据一致”这个程序不变量不是一回事。

C 与 C++ 的联合体活动成员、对象生命周期规则不应互抄。即使某种 type-punning 在当前 C 实现上有定义或文档保证，它仍可能受到陷阱表示、字节序和实现特性的限制。可移植的对象表示复制优先考虑 `memcpy`，并验证目标位模式确实有效。

## 为什么强制把网络包转成结构体指针很危险

```c
/* 不推荐作为通用解包策略： */
/* const struct Header *h = (const struct Header *)packet; */
```

这忽略了四个独立问题：包是否足够长；起始地址是否满足对齐；字段是否包含编译器填充；多字节整数使用什么字节序。此外还存在有效类型和别名规则。打包属性只处理其中一部分，且通常是编译器扩展，不会自动完成边界与端序验证。

更清楚的网络序读取方式是逐字节组合：

```c
#include <limits.h>
#include <stdint.h>

_Static_assert(CHAR_BIT == 8, "This protocol requires 8-bit bytes");

uint32_t read_be32(const unsigned char p[4]) {
    return ((uint32_t)p[0] << 24) | ((uint32_t)p[1] << 16)
         | ((uint32_t)p[2] << 8)  | (uint32_t)p[3];
}
```

此例前提是实现提供 `uint32_t` 且一个 C 字节恰为八位；静态断言会拒绝不满足后一个前提的平台。协议以八位字节定义，调用方已经验证可读至少四字节。每一项在移位前转成无符号目标类型，避免先在有符号 `int` 中产生问题。真正解析器还应携带剩余长度，读取成功后再推进游标。

## 柔性数组、位域与枚举的适用范围

柔性数组成员允许把变长负载放在结构体末尾，例如 `struct Packet { size_t n; unsigned char data[]; };`。分配需要检查 `sizeof(struct Packet)+n` 是否溢出；柔性数组不包含在 `sizeof` 的负载部分中，结构体复制也不自动复制变长数据。

位域可用于某些受控 ABI 的寄存器或紧凑状态表示，但布局顺序、跨存储单元行为等具有实现相关性，不能天然充当网络格式。硬件寄存器还要求遵守设备文档的访问宽度、读写副作用和内存屏障协议。

枚举提高状态可读性，却不是跨语言序列化时的固定宽度承诺。对文件格式，写下字段位宽、允许取值、保留位、版本号和遇到未知值的处理策略；对内存 API，使用显式验证守住状态集合。

## 推演：设计一个可扩展的记录格式

需要保存“类型、一段字节负载、校验值”。可靠格式可以先写固定魔数与版本，再写明确端序的类型和长度，最后负载及校验。解码时先验证最小头长度，再验证 `length <= remaining`，再决定是否支持该类型，最后验证校验。不能先信任长度并分配巨大缓冲区。

练习：结构体字段完全一样的两个程序，为什么仍可能读不懂对方写出的 `fwrite(&r,sizeof r,1,f)`？答案包括 ABI、字节序、整数宽度、填充、浮点表示、版本变化，以及指针字段只对原进程地址空间有意义。序列化是在定义协议，而不是搬运内存。
