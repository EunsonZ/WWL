# 数据库：WAL、恢复、复制与分布式一致性

> 阅读定位：关系理论通用；实现示例区分 SQLite 与 PostgreSQL 17。返回 [[计算机知识/00-开始/课程地图/10-数据库-课程地图|数据库 · 课程地图]]；全域入口 [[计算机知识/00-开始/全局导航/00-总学习地图|计算机知识库 · 总学习地图]]。

## 提交先保证什么能恢复

WAL 的核心顺序是相关日志先满足持久化要求，再允许对应数据页按协议写回。这样崩溃后可依据日志恢复已承诺状态，不必每次提交都立即把所有脏数据页随机写盘。具体系统的 redo/undo、页版本和提交记录规则不同，不能认为所有 WAL 都是同一个实现。

checkpoint 限制恢复需要回溯的范围，但通常不等于“所有事务结束、以后不需要日志”。备份、日志归档与时点恢复要一起设计。文件拷贝成功不证明备份一致，恢复演练才检验它是否真的可用。

## 崩溃时间线

修改缓冲页；生成日志；提交所需日志达到相应持久化边界；回复成功；稍后刷数据页。若在回复之后、数据页刷盘之前崩溃，正确的恢复路径应能利用日志重建承诺结果。若在提交确认之前客户端断线，客户端可能不知道事务是否已经提交，不能直接当失败重做。

## 复制与分片回答不同问题

复制在多个节点维护副本以改善可用性和读取等目标，分片把数据分布到不同节点以扩大容量与吞吐。异步复制可能有读取滞后和故障切换数据损失窗口；同步复制要明确等到哪个副本的哪种确认，代价通常包含额外等待。多副本不等于多地同时无条件可写且强一致。

线性一致性把操作与真实时间顺序联系起来，可串行化要求事务等价于某串行次序，二者不是同一属性。CAP 讨论网络分区情况下某些一致性与可用性目标的冲突，不是“分布式系统随便三选二”的采购表。

共识用于在相应故障模型下对日志或状态达成一致；两阶段提交协调跨参与者原子提交，不能简单等同于共识，且有阻塞与恢复问题。分布式事务、saga 和 outbox 的失败语义各不同。复制、分片、事务和共识必须沿不同坐标理解。

## 应用幂等的实现思路

为每个业务请求分配幂等键，数据库内以唯一约束识别重复，在同一正确事务边界保存执行结果和业务变更。只有“请求 ID 写进日志”却没与实际效果绑定，仍可能重复。跨系统 exactly-once 不能靠一次 ACK 宣布成立，应说明重复检测、结果保存、保留期限与失败模型。

练习：画出“提交成功但响应丢失”的时间线，设计客户端查询与重试协议。然后说明主库确认后副本尚未同步时切换会产生什么风险，哪些配置改变承诺，哪些只是改善常见情况。
