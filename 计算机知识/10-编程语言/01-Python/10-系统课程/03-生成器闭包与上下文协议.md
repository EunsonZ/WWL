# 生成器、闭包与上下文协议：控制权和资源如何流动

> **学习位置**：[[计算机知识/00-开始/课程地图/04-Python-课程地图|Python课程地图]] · **适用边界**：Python 3.11+；CPython 实现细节明确注明。

## 闭包保存绑定，不是自动拍照

```python
funcs = [lambda: i for i in range(3)]
assert [f() for f in funcs] == [2, 2, 2]
fixed = [lambda i=i: i for i in range(3)]
assert [f() for f in fixed] == [0, 1, 2]
```

第一组函数共享循环变量对应的闭包单元，调用时读取最终值；第二组在每次创建函数时计算默认参数，保存当时引用的对象。默认参数同样不是深复制：若保存的是可变对象，后续修改仍可见。定义时求值也解释了可变默认参数为何在多次调用间共享。可用 `None` 哨兵创建每次调用独立的新对象；但如果 `None` 本身是合法业务值，就应使用独有哨兵对象。

## 迭代器是一次性状态机

可迭代对象能提供迭代器；迭代器实现 `__next__` 并在结束时抛 `StopIteration`。列表可以反复产生独立迭代器，生成器对象通常只有一条消费进度。`iter(g) is g` 不意味着它可以重新开始。

函数中出现 `yield` 会使调用先返回生成器，函数体随后在推进时执行。局部变量和暂停位置保存在状态中。惰性节省的是未物化的中间结果，不保证总内存小：生成器仍可能持有整个输入列表，缓存或 `itertools.tee` 也可能积压大量元素。一次消费之后再求和得到零，不是数据消失，而是游标已经到末尾。

```python
def running_total(values):
    total = 0
    for value in values:
        total += value
        yield total

assert list(running_total([2, -1, 4])) == [2, 1, 5]
```

这里每次暂停保留 `total`；把 `yield` 换成 `return` 将在第一次循环退出。`yield from` 不只是循环转发值，还转发生成器协议中的部分控制操作，并接收子生成器的返回值。不要在生成器内部用裸 `raise StopIteration` 表示普通终止，应当 `return`。

## 上下文管理器为异常路径负责

`with resource as x` 调用 `__enter__`，把其返回值绑定给 `x`；退出时调用 `__exit__`。`__exit__` 返回真值会抑制异常，这应该是明确设计而非随手 `return True`。若 `__enter__` 自身失败，本次上下文尚未成功进入，其清理责任仍由 `__enter__` 的实现承担。

```python
from contextlib import contextmanager

@contextmanager
def acquired(lock):
    lock.acquire()
    try:
        yield
    finally:
        lock.release()
```

生成器式上下文管理器必须恰好让出一次。`yield` 处是调用者代码插入的位置；调用者抛出的异常会被重新送回这里。动态数量的资源应使用 `ExitStack`，它按后进先出关闭已经成功获得的资源。异步资源对应 `async with` 与 `AsyncExitStack`，但退出过程也可能需要等待、超时及处理取消。

## 流式处理的边界契约

设计 CSV 或日志管线时，每层明确输入单位是字节、文本行还是已验证记录；编码错误、超长行、末尾无换行和坏记录必须有策略。不要让“跳过所有异常”悄悄改变统计分母。流式算法仍应输出处理数量、拒绝数量和拒绝原因，让结果可复核。若消费者提前退出，要确保上游文件被显式关闭，而不是期待垃圾回收马上执行。

## 练习与答案

写一个只读取前十条记录的消费者，证明它在遇到第六条解析异常时仍关闭输入。答案的关键不是 `for` 会结束，而是输入资源由外层 `with` 持有。再比较 `sum(g); sum(g)` 与两次 `sum(make_generator())`：前者第二次为零，后者重新构造状态机。最后观察闭包的 `__closure__`，并解释为什么这只适合诊断，不能成为业务接口。
