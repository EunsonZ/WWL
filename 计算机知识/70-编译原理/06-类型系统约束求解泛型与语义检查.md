# 类型系统、约束求解、泛型与语义检查

## 本课目标

学完后，你应该能：

- 读写 typing judgment，区分表达式类型、环境、约束与效果；
- 从 AST 生成等式约束，并手工执行 substitution 与 unification；
- 解释 occurs check 为什么阻止无限类型，而不是把它当作实现细节；
- 区分 nominal/structural typing、类型相等/子类型、泛型实例化/重载选择；
- 用函数参数逆变、返回值协变检查子类型推理方向；
- 说明 effect、可变状态和错误节点为什么影响泛化与诊断边界；
- 把类型检查放在完整语义检查流水线中，而不是做语言特性百科。

本课只使用**推导规则、约束表和伪代码**。真实语言可能采用不同的泛化、重载、子类型和 effect 规则；实现前必须先固定该语言的规范。

## 直觉：类型检查是在 AST 上构造一份可核验的证明

类型检查不只是给节点贴字符串标签。它要在环境与语言规则下证明：“若这些前提成立，该表达式具有这个类型，并可能产生这些效果。”当信息暂时未知时，先产生约束；求解器找到 substitution 后，再把未知量替换成具体类型。若约束矛盾，诊断应指出最小、最相关的来源。

## 1. Typing judgment：把前提写在结论左边

基本判断写作：

$$
\Gamma \vdash e : \tau
$$

读作：“在类型环境 $\Gamma$ 下，表达式 $e$ 具有类型 $\tau$。”其中 $\Gamma$ 通常从已解析的 SymbolId 映射到类型 scheme；它不是从名字字符串重新查找声明。若还跟踪 effect，可写：

$$
\Gamma \vdash e : \tau \; ! \; \varepsilon
$$

表示求值产生值类型 $\tau$，并可能产生效果集合/效果行 $\varepsilon$。这里 effect 的具体代数由语言定义，本课只要求不要把“返回值类型正确”等同于“可在纯上下文中执行”。

### 三条最小规则

变量规则：

$$
\frac{x : \tau \in \Gamma}{\Gamma \vdash x : \tau}
$$

整数字面量规则：

$$
\frac{}{\Gamma \vdash n : Int}
$$

函数应用规则：

$$
\frac{\Gamma \vdash f : \tau_1 \to \tau_2 \qquad \Gamma \vdash a : \tau_1}
     {\Gamma \vdash f(a) : \tau_2}
$$

这条应用规则是一个规格；实现时若 `f` 与 `a` 的类型尚未确定，可以创建新类型变量并生成约束。

## 2. 从 AST 生成约束

设 `fresh()` 产生新的类型变量。对简化表达式，可写：

```text
infer(expr, environment):
    if expr is IntegerLiteral:
        return (Int, no_constraints, Pure)

    if expr is ResolvedName(symbol_id):
        scheme = environment[symbol_id]
        return (instantiate(scheme), no_constraints, Pure)

    if expr is Call(function, argument):
        (tf, cf, ef) = infer(function, environment)
        (ta, ca, ea) = infer(argument, environment)
        tr = fresh_type_variable()
        latent = fresh_effect_variable()
        constraint = tf = Function(ta, tr, latent)
        return (tr, cf + ca + constraint, combine(ef, ea, latent))

    if expr is ErrorExpr or refers to ErrorSymbol:
        return (ErrorType(origin), no_new_diagnostic, UnknownEffect)
```

第1节的基础箭头只规定参数和返回类型；此处带 effect 的进阶模型把 `Function(ta,tr,latent)` 写作 `ta -> tr ! latent`。latent 表达式先随类型约束统一，再求解/代入效果并集，不能把未解变量默认成 Pure。求值函数表达式 ef、实参 ea、执行函数体 latent 是三种来源；取函数名字本身 Pure 不代表调用 Pure。

此处等号表示必须统一的**类型相等约束**，不是赋值，也不是子类型关系。每条约束还应带源位置与生成原因，例如“实参类型必须等于形参类型”；否则求解失败时只能输出晦涩的内部类型。

## 3. Unification：寻找使等式同时成立的 substitution

substitution $S$ 把类型变量映射到类型，例如 $S=[\alpha \mapsto Int]$。unification 要寻找使两边相等的最一般 unifier（若存在），避免过早固定无关变量。

```text
unify(left, right):
    left = apply_current_substitution(left)
    right = apply_current_substitution(right)

    if left and right are identical:
        succeed
    else if left is type variable α:
        bind_variable(α, right)
    else if right is type variable α:
        bind_variable(α, left)
    else if both are Function types:
        unify(left.parameter, right.parameter)
        unify(left.result, right.result)
    else if both have same constructor and arity:
        unify each corresponding argument
    else:
        fail with both constraint origins
```

绑定变量前必须做 occurs check：若 $\alpha$ 出现在候选类型 $\tau$ 中，则拒绝 $\alpha=\tau$，除非语言明确支持并表示递归类型。

### 手算一：`choose(flag, 1, x)`

假设：

```text
choose : Bool -> α -> α -> α
flag   : Bool
x      : β
```

应用依次产生：

| 来源 | 约束 |
| --- | --- |
| 第一个实参 `flag` | `Bool = Bool` |
| 第二个实参 `1` | `α = Int` |
| 第三个实参 `x` | `α = β` |

先得 substitution `[α ↦ Int]`，应用到第三条得到 `Int = β`，再得 `[β ↦ Int]`。最终调用类型为 `Int`。如果已知 `x : String`，第三条变为 `Int = String`，应报告分支值类型不一致，并同时引用 `1` 与 `x` 的位置。

### 手算二：occurs check

推断自应用 `x(x)`，设 $x:\alpha$、调用结果为 $\beta$。应用规则要求：

$$
\alpha = \alpha \to \beta
$$

若绑定 $\alpha \mapsto \alpha\to\beta$，替换后右侧仍含 $\alpha$，继续展开会得到无限类型。occurs check 发现 $\alpha \in FV(\alpha\to\beta)$，拒绝该绑定。省略它可能造成无限递归、无限结构或求解器崩溃。

## 4. 泛型：generalize 与 instantiate 是两个方向

类型 scheme 可写作 $\forall \alpha.\tau$。在适当的 `let` 边界，推断出的、且不被环境自由引用的类型变量可被 generalize；每次使用时 instantiate 为新的变量。

```text
let id = function(x) => x
pair(id(1), id(true))
```

`id` 的主体得到 $\alpha\to\alpha$，generalize 为 $\forall\alpha.\alpha\to\alpha$。两次使用分别实例化：

```text
first use:  α₁ -> α₁, with α₁ = Int
second use: α₂ -> α₂, with α₂ = Bool
result: Pair(Int, Bool)
```

若两次使用共享同一个未重新实例化的变量，第一次会固定为 `Int`，第二次错误地要求 `Bool = Int`。反之，若对环境中受可变状态约束的任意变量都无条件 generalize，可能允许以不同类型读写同一存储位置，破坏类型安全。

### effect 与 value restriction 边界

一些语言只对语法值或纯表达式做 `let` 泛化，另一些用 effect 系统判断能否安全泛化。核心问题不是记住“value restriction”这个词，而是验证：

- 这个绑定是否创建/捕获可变状态？
- 多次实例化是否会把同一运行时位置当成不同类型？
- effect 是否会在看似多态的使用之间共享？

因此泛型推断、可变状态与 effect 不能完全独立设计。

## 5. Nominal 与 structural：相等依据来自哪里

**Nominal typing** 以声明身份和显式关系为主：两个记录字段完全相同，但由不同类型声明创建，仍可不同。**Structural typing** 以形状/成员契约为主：只要所需结构满足，就可能兼容。

```text
type UserId = record { value: Int }
type OrderId = record { value: Int }
```

- nominal 规则可让 `UserId` 与 `OrderId` 不同，从而阻止误传；
- structural 规则可能认为两者结构相同，除非另有品牌字段或不透明边界。

没有哪一个自动“更安全”：nominal identity 便于表达领域区别，structural compatibility 便于组合与渐进接口。语言必须定义别名、新类型、不透明类型、接口/trait 的具体关系；实现不能看到字段一样就擅自合并。

## 6. 子类型不是 unification：方向决定安全性

若 $S <: T$，表示需要 $T$ 的位置可接受 $S$。这是一种有方向的可替换关系；unification 的 $S=T$ 是对称等式。把子类型约束塞进无方向等式求解，会拒绝合法程序或接受错误程序。

对只读记录，宽度子类型的简化直觉是“字段更多者可用于只要求较少字段的位置”：

```text
{name: String, age: Int} <: {name: String}
```

一旦字段可写，还要考虑写入安全，不能无条件套用只读协变。

### 函数参数逆变、结果协变

若 $S_1 <: T_1$ 且 $T_2 <: S_2$，则在常见安全规则下：

$$
(T_1 \to T_2) <: (S_1 \to S_2)
$$

即函数在参数上逆变、返回值上协变。用 `Animal` 与 `Cat <: Animal` 手算：

- 需要 `Cat -> Animal` 的位置，可以接收 `Animal -> Cat`：它能处理任何 Cat，并返回更具体的 Cat；
- 不能用 `Cat -> Animal` 替代 `Animal -> Cat`：调用者可能传 Dog，或期待返回 Cat，两边都可能失败。

**反例：参数协变。** 若误以为 `Cat <: Animal` 推出 `(Cat->Unit) <: (Animal->Unit)`，调用者会把 Dog 传给只会处理 Cat 的函数。

子类型还会引入约束传播、上下界、join/meet 与可能的推断不唯一；若语言同时支持复杂子类型和全局类型推断，必须明确可判定性、性能与需要注解的边界。

## 7. 重载：先收集候选，再基于完整约束选择

名称解析可能为 `add` 返回重载集合：

```text
add(Int, Int) -> Int
add(Float, Float) -> Float
add(String, String) -> String
```

对 `add(1, x)`：

1. arity 过滤仍留下三个候选；
2. 第一个实参 `1` 排除 String，可能保留 Int 与允许数值提升的 Float；
3. `x` 的已知类型和语言转换规则继续约束；
4. 若一个候选按明确的“更具体”规则唯一胜出，才选择；
5. 无候选时报告关键不匹配；多个同等最佳候选时报告歧义。

不要按声明顺序选第一个，也不要在只看一个实参后过早承诺。隐式转换、默认参数、泛型候选与子类型会让排序更复杂，必须有终止且确定的规范。overload resolution 的结果应记录选择的 SymbolId 与采用的转换，供后续代码生成和诊断复核。

## 8. Effect 是类型之外的语义轴

两个函数都可写作 `Unit -> Int`，但一个纯计算，另一个读取文件、抛异常或阻塞。如果调用环境要求纯表达式，仅返回类型相同不够：

```text
read_config : Unit -> Int ! {IO, Throws}
constant    : Unit -> Int ! {}
```

在本文集合模型中 Pure=∅：`read_config(())` 的函数名字求值 ef=∅，Unit 实参 ea=∅，箭头携带 latent={IO,Throws}，故调用效果为 ∅∪∅∪{IO,Throws}={IO,Throws}。`constant(())` 的三项均空，仍为 Pure。若函数表达式 ef={IO}、实参 ea={Throws}、函数体 latent={State}，结果为 {IO,Throws,State}，三项不能遗漏。此为伪推断规则，MiniLang 实验没有实现 effect 语言。

effect 检查可以采用集合、行多态、能力或显式上下文；无论表示如何，至少要回答：

- 哪些表达式引入 effect？
- 组合表达式如何合并 effect？
- handler、`try`、异步边界或事务如何消除/转换 effect？
- effect 是否进入函数类型、接口哈希与重载选择？

本课不展开某一套 effect 语言，但强调边界：类型正确不自动意味着纯、不会抛错、不会阻塞或线程安全。

## 9. 类型检查只是语义检查的一部分

一个常见顺序是：

```text
parsed AST with error nodes
    -> declaration collection and name resolution
    -> control-flow/context checks
    -> constraint generation and type/effect solving
    -> post-type checks and lowering preconditions
```

除类型外，语义检查还可能包括：

- `break` 是否位于循环，`return` 是否位于函数；
- 所有要求返回值的路径是否返回；
- 变量是否在读取前确定初始化；
- 模式匹配是否穷尽、分支是否不可达；
- 常量表达式是否满足编译期限制；
- 借用、移动、可变性、effect 或能力规则是否满足；
- API 可见性是否泄漏私有类型。

有些检查依赖 CFG，有些依赖类型，有些应更早执行以改善诊断。不要把它们全部塞进 `infer(expr)` 的巨型分支；为每类检查记录输入契约、输出事实和诊断所有权。

## 10. 错误类型、毒化与级联抑制

解析产生 `ErrorExpr`，名称阶段可能产生 `ErrorSymbol`，类型阶段应将其转换为带 origin 的 `ErrorType`：

```text
check_add(left, right):
    tl = check(left)
    tr = check(right)
    if tl is ErrorType or tr is ErrorType:
        return ErrorType(propagated_origin)
    if no valid add rule applies:
        report one mismatch at operator with notes to operand types
        return ErrorType(this_diagnostic)
    return selected_result_type
```

ErrorType 可以在多数约束中“吸收”冲突，但不能被当作正常 top/bottom 类型写进公共接口或送到代码生成。进入 lowering 前必须有闸门：存在未恢复的 error node、ErrorSymbol 或 ErrorType 就禁止生成可执行产物。

为改善诊断，还应保存约束 provenance：AST 源区间、规则名称、两侧类型最初从哪里来。union-find 可加速等式类合并，但若丢掉 provenance，性能提升会换来无法解释的错误。

## 11. 一次完整手算：从名称到泛型调用

伪程序：

```text
let id = function(x) => x
let n = id(1)
let b = id(true)
if b then n + 2 else 0
```

1. 名称解析给 `id`、`n`、`b` 各自 SymbolId，每个 use 指向对应声明；
2. `function(x)=>x` 生成 $\alpha\to\alpha$，在纯 `let` 边界 generalize 为 $\forall\alpha.\alpha\to\alpha$；
3. `id(1)` instantiate 为 $\alpha_1\to\alpha_1$，约束 $\alpha_1=Int$，所以 `n:Int`；
4. `id(true)` instantiate 为 $\alpha_2\to\alpha_2$，约束 $\alpha_2=Bool$，所以 `b:Bool`；
5. `if` 条件要求 `b:Bool`，满足；
6. `n + 2` 的整数加法要求两侧 `Int`，结果 `Int`；
7. `then` 与 `else` 结果统一为 `Int`；整个表达式为 `Int`，effect 为各子表达式 effect 的组合，此例为纯。

把最后的 `0` 换成字符串会产生 `Int = String` 冲突；诊断应落在两个分支的合并处，并指出各分支类型来源，而不是把错误归咎于 `if` 关键字。

## 常见反例

1. **AST 节点有 type 字段就等于类型系统。** 仍需环境、规则、约束、求解、来源和错误边界。
2. **unification 可以顺便处理所有子类型。** 相等是对称的，子类型有方向并可能需要上下界。
3. **省略 occurs check 只是接受更多程序。** 它可能构造无限类型并使求解不终止。
4. **泛型就是每次把 `T` 换成用户写的类型。** 推断式多态还涉及 generalize、instantiate 与环境自由变量。
5. **字段相同必然是同一类型。** nominal 系统以声明 identity 区分；structural 系统也可能有可变性与不透明边界。
6. **参数类型应与子类型同向变化。** 函数参数通常逆变，错误协变会允许不安全调用。
7. **存在最佳重载就取第一个看起来能用的。** 必须用完整候选排序规则证明唯一最佳，否则报告歧义。
8. **ErrorType 什么都能通过。** 它只用于抑制级联，最终必须阻止 lowering/代码生成。

## 练习

1. 为 `f(x)` 写出 typing judgment 与约束生成步骤，假设 `f: α`、`x: β`、结果为 `γ`；指出哪条约束决定 `f` 必须是函数。
2. 手工 unify `Pair(α, Int) = Pair(Bool, β)`，给出 substitution；再尝试 `α = List(α)`，指出 occurs check 的失败位置。
3. 为多态 `const = function(x) => function(y) => x` 推导类型 scheme；分别实例化到两个不同调用，不共享新鲜变量。
4. 用 `Animal`、`Cat`、`Dog` 构造函数参数协变的不安全反例，并解释正确的逆变/协变方向。
5. 对 `UserId` 与 `OrderId` 的同形记录，分别给出 nominal 与 structural 规则下的判断；说明产品需求可能为何偏好其中一种。
6. 设计三个 `convert` 重载，让某个调用无候选、某个调用唯一、某个调用歧义；为三者写诊断要点。
7. 构造一个返回类型为 `Int` 但带 `IO` effect 的表达式，说明纯上下文为何拒绝它。
8. 从一个未解析名称开始，画出 ErrorSymbol → ErrorType → lowering gate 的传播路径，规定哪一层拥有主诊断。

## 成功标准

- 我能读写 $\Gamma \vdash e:\tau$，并说明环境中的键应是解析后的 SymbolId；
- 我能从函数应用生成约束，执行 substitution/unification，并解释 occurs check；
- 我能正确区分 nominal/structural、相等/子类型、generalize/instantiate、泛型/重载；
- 我能用具体调用证明函数参数逆变、结果协变，而不是背口诀；
- 我知道 effect、可变状态与泛化互相影响，类型正确不等于纯或无副作用；
- 我能把 ErrorType 用作级联抑制，同时在 lowering 前拒绝含语义错误的程序；
- 我能列出类型之外的语义检查，并为各阶段划定输入、输出和诊断所有权。
