# 二进制文件格式：魔数、字节序、对齐与校验

## 本课目标

学完后，你能读懂一个小型二进制格式的“目录”：magic、版本、字段、offset、长度、对齐、校验和；并能写出安全解析的验证顺序。重点不是记住某一种格式，而是不会把本机结构体布局、扩展名或一个成功读取的样本误当作格式规范。

## 直觉：二进制文件不是一坨“按顺序读”的字节

一个可靠的二进制文件像带目录的仓库：门牌（magic）帮助初步识别；版本告诉读者采用哪套规则；目录给出每个区域的位置与大小；对齐让某些区域从约定边界开始；校验帮助发现传输或存储损坏。任何一个数字都来自不可信输入，必须先验证才可以用于寻址、分配或循环。

## 1. 一个教学格式：先写规范，再看十六进制

下面是虚构的 `TINY` 文件。它只用于学习边界检查：

| 偏移 | 字段 | 宽度与规则 |
| ---: | --- | --- |
| `0x00` | magic | 4 字节 ASCII：`54 49 4E 59`（`TINY`） |
| `0x04` | version | `u16` 小端；当前只接受 1 |
| `0x06` | flags | `u16` 小端；未定义位必须为 0 |
| `0x08` | payload_offset | `u32` 小端，必须是 8 的倍数 |
| `0x0C` | payload_length | `u32` 小端，最大 16 MiB |
| `0x10` | payload_checksum | `u32` 小端，载荷的 CRC-32/ISO-HDLC |
| `0x14..` | padding / payload | `payload_offset` 前为填充，随后为载荷 |

一个载荷为 `68 69`（ASCII `hi`）的例子可以写为：

```text
54 49 4E 59  01 00 00 00  18 00 00 00  02 00 00 00
AC 2A 93 D8  00 00 00 00  68 69
└─ magic ─┘  └v─┘└flags┘  └offset=24┘ └length=2 ┘
                              └ CRC 字段（小端存储 0xD8932AAC）┘
```

`TINY` v1 的 checksum 契约是完整且可执行的：对区间 `[payload_offset, payload_offset + payload_length)` 中的**载荷字节本身**计算 CRC-32/ISO-HDLC（width 32、poly `0x04C11DB7`、init `0xFFFFFFFF`、refin/refout 均为 true、xorout `0xFFFFFFFF`）；不覆盖固定头、checksum 字段或 padding。把结果作为无符号 `u32` 以小端写入 `payload_checksum`。该变体对 ASCII `123456789` 的 check 值为 `0xCBF43926`；本例的 `68 69` 得到 `0xD8932AAC`，所以字段字节为 `AC 2A 93 D8`。这仍只是偶发损坏检测，不是防篡改认证。

## 2. magic、扩展名与内容识别

magic number 是格式在固定位置的标识字节，常在开头；它方便快速拒绝明显不匹配的输入。扩展名来自文件名，可能被改写；MIME 类型、magic 和完整结构验证也各自只是证据的一部分。

magic **不是安全授权**：攻击者能复制任何公开 magic。解析器还须检查版本、字段关系、所有 offset/length、压缩/加密声明、完整性与资源上限；消费不可信文件时，还要隔离高风险解码器并及时修补依赖。

## 3. 数字字段必须说明字节序和宽度

`01 00` 到底是 1 还是 256，取决于格式约定。`TINY` 明确写“小端 `u16`”；若没有这个约定，读者无法正确解释。主机 CPU 的字节序不能替代格式规范。整数位宽、补码、浮点和对齐的系统背景见 [[计算机知识/30-计算机系统/01-数据表示字节序与对齐|数据表示、字节序与对齐]]。

同样，`length` 是字节数、元素数还是字符数也必须写清。若是元素数，还需要元素宽度与安全乘法；`count × element_size` 溢出后再比较边界是危险的。

## 4. offset、length 与对齐：把每一次寻址变成可证明的范围

对于文件大小 `N`、offset `O`、length `L`，载荷区间应满足：

```text
0 ≤ O ≤ N
0 ≤ L ≤ N - O
```

写成 `O + L ≤ N` 容易在有限位整数中先溢出；采用“先确认 `O ≤ N`，再确认 `L ≤ N - O`”更直接。还应检查 `O` 是否落在头后、与其他区域是否允许重叠、是否满足对齐，以及其声明是否与版本/flags 一致。

对齐是格式作者规定的**文件布局**，不是 CPU 必然要求。例如 `O mod 8 = 0` 可让大块数据从 8 字节边界开始，便于某些内存映射或 SIMD 后端；但读取器仍不能把文件字节强制转换为本机 `struct`。本机 ABI 的填充、字段排列和字节序依旧可能不同。

### 解析顺序（伪代码）

```text
require file_size >= fixed_header_size
read fixed-width fields by specified byte order
require magic == expected_magic
require version is supported and reserved flag bits are zero
require payload_offset >= fixed_header_size
require payload_offset is aligned to 8
require payload_offset <= file_size
require payload_length <= MAX_PAYLOAD
require payload_length <= file_size - payload_offset
create a bounded view [payload_offset, payload_offset + payload_length)
verify CRC-32/ISO-HDLC of that view; compare it to the little-endian u32 field
only then decode payload with its own size/depth/count limits
```

读取固定头也应避免无检查的未对齐加载；以逐字节组合或成熟的边界检查库读取，并确保每一步都不会越过文件尾。

## 5. 校验和、哈希与认证各能证明什么

| 机制 | 主要用途 | 面对偶发损坏 | 面对主动篡改者 |
| --- | --- | --- | --- |
| checksum / CRC | 快速发现传输、磁盘或内存误码 | 通常有效 | 不安全；攻击者可重算 |
| 无密钥哈希（如 SHA-256） | 内容标识、与可信外部摘要比对 | 有效 | 摘要来自可信渠道时可发现替换 |
| MAC / AEAD 认证标签 | 持有密钥的双方验证消息完整性与来源 | 有效 | 能抵抗不知道密钥的篡改者 |
| 数字签名 | 由私钥持有者签发、他人用公钥验证 | 有效 | 在密钥与验证链可信时可验证签发者 |

哈希值写在同一个可被改写的文件内，不能独自给出来源证明；攻击者可同时替换文件与哈希。校验成功也不证明载荷语义正确、没有恶意内容或来自可信发布者。

## 6. 版本演进：让新旧读者安全地不同意

格式会演进，但“版本号存在”不足以保证兼容。规范应回答：

- 读者遇到未知版本，是拒绝、降级还是走兼容分支？
- 新增字段是可跳过的 TLV，还是会改变固定头后的所有 offset？
- 未知 flags、保留位、枚举值和 codec ID 应怎样处理？
- 可选字段缺失的默认值是否与历史版本一致？
- 写入器如何避免旧读者把新数据误读为旧语义？

对安全敏感字段，未知通常应拒绝（fail closed）；对明确可扩展的非关键元数据，规范可允许跳过。两种策略都要写在格式中，并以旧样本、新样本、截断样本、未知 flag 和超大 length 作为回归测试集。

## 练习

1. `TINY` 文件大小为 25，`payload_offset=24`、`payload_length=2`。用 `L ≤ N - O` 判断为何必须拒绝。
2. 将 `payload_offset` 写成 `17` 时，即使文件足够长，为什么本格式仍应拒绝？说明“格式对齐”与“CPU 能否读取”不同。
3. 给一个支持新 codec 的版本 2 设计兼容策略：旧读者、新读者遇到未知 codec 分别怎么做？
4. 某下载文件的内置 CRC 正确，但你没有来自发布者的签名或哈希。列出这能证明和不能证明的事情。

## 成功标准

- 我可以从完整格式表说明每一字段的宽度、字节序、范围、含义和未知值策略。
- 我会在分配、循环、seek、解压或解码之前验证由输入控制的长度、数量和 offset。
- 我知道 magic 与扩展名只能帮助识别，不能把不可信内容变可信。
- 我能区分 CRC、哈希、MAC/AEAD 标签与签名的威胁模型，不把“校验通过”说成“安全”。
