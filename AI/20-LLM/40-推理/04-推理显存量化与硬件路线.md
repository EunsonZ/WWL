# 推理显存、量化与硬件路线

<!-- deep-review-02 -->
> [!tip] 本轮深化：从当前概念继续追问

## 本课目标

- 把推理内存拆成权重、KV cache、临时激活/工作区和运行时开销；
- 显式解释参数、batch、context 和 precision 各自怎样影响显存；
- 区分权重量化、KV 精度和计算精度；
- 比较 CPU、GPU 与 mixed offload；
- 把 8GB、16GB、24GB 变成保守试验路线，而不是“能跑保证”。

## 先问“哪一块内存”

推理容量不能只看模型文件大小。一个实用的一阶预算是：

$$
M_{runtime}\approx M_{weights}+M_{KV}+M_{activation/workspace}+M_{engine}+M_{other}.
$$

- **权重**：模型加载后主要常驻，与参数量和权重表示直接相关；
- **KV cache**：随层数、KV 头宽、驻留序列数、上下文和 KV 精度增长；
- **激活/工作区**：prefill、batch、kernel、量化解码、图捕获和并行策略会改变；
- **引擎开销**：分配器预留、页表、通信 buffer、采样状态等；
- **其他**：tokenizer、操作系统、桌面显示占用、draft 模型、适配器或多模态编码器。

## 权重内存：参数量 × 平均位宽只是起点

若模型有 $P$ 个参数，平均每参数 $q$ bit，权重主项为：

$$
M_{weights,raw}\approx P\times\frac{q}{8}\ \text{bytes}.
$$

例如 7B 参数的理想原始主项：

| 表示 | 理想权重主项 |
| --- | ---: |
| FP32，4 byte/参数 | 约 28 GB |
| FP16/BF16，2 byte/参数 | 约 14 GB |
| 8-bit，1 byte/参数 | 约 7 GB |
| 4-bit，0.5 byte/参数 | 约 3.5 GB |

这些是十进制 GB 的粗略主项，不是实际峰值。量化还可能保存 scale、zero-point、group metadata、未量化层和对齐填充，因此“4-bit”通常不是精确 0.5 byte/参数。文件也可能被压缩、分片或带额外 tokenizer/metadata，文件大小不能直接等同运行峰值。

对于 MoE 模型，还要区分**总参数**与**每 token 激活参数**：稀疏激活能降低每 token 计算，不会自动让所有专家权重消失；若专家都常驻，内存仍接近总权重。

## KV Cache：context 与 batch 的乘法项

常见 decoder-only 模型中，令 $n_{kv\_heads}$ 为每层 KV head 数、$d_{head}$ 为每个 KV head 的宽度，并定义每层每 token 的 KV 总宽度

$$
H_{KV}=n_{kv\_heads}\times d_{head}.
$$

若每个 KV 元素占 $b_{KV}$ 字节，则 KV 主项为：

$$
M_{KV}\approx B\times L\times S\times2\times H_{KV}\times b_{KV}.
$$

因此：

- 参数量 $P$ 增大，通常主要推高权重；
- context $S$ 翻倍，KV 主项近似翻倍；
- 驻留 batch $B$ 翻倍，KV 主项近似翻倍；
- KV 从 2 byte 降到 1 byte，KV 主项近似减半，但质量和支持必须验证；
- 在 $d_{head}$ 不变时，MQA/GQA 减少 $n_{kv\_heads}$，因而减少总宽度 $H_{KV}$，可显著缩小 KV；不能只从总参数量推断。

更完整解释和例题见 [[AI/20-LLM/40-推理/01-生成循环Prefill-Decode与KV-Cache|生成循环、Prefill、Decode 与 KV Cache]]。

## Precision 不是一个总开关

一次“4-bit 推理”可能同时包含：

- 4-bit 权重存储；
- FP16/BF16/FP32 的 scale 或部分敏感层；
- FP16/BF16 计算或累加；
- FP16/BF16 KV cache；
- FP16/FP32 临时激活；
- 特定 kernel 内部的解量化与打包格式。

所以要分别记录 `weight dtype/quant scheme`、`compute dtype`、`KV dtype` 和关键未量化模块。仅写“INT4”不足以复现内存、速度或质量。

## 量化的四组权衡

| 目标 | 可能收益 | 可能代价 | 必须测量 |
| --- | --- | --- | --- |
| 降低权重位宽 | 更小权重、可能提高带宽利用 | 量化误差、metadata、解量化开销 | 任务质量、权重占用、速度 |
| 降低 KV 精度 | 长上下文/并发更省内存 | 注意力误差、引擎/模型支持有限 | 长上下文质量、TPOT、峰值内存 |
| 更小 group | 通常更细致地适配数值范围 | scale/metadata 比例更高 | 文件/运行占用与质量 |
| 混合精度保留敏感层 | 可能改善质量 | 占用比纯低比特高 | 层级配置与任务回归 |

质量损失不是只看平均困惑度。代码、数学、长上下文、少数语言、工具调用和结构化输出可能有不同敏感度；需要与目标任务匹配的回归集。

## CPU、GPU 与 Mixed Offload

### CPU 路线

权重和 KV 主要放系统内存，由 CPU 执行。优势是容量通常更容易扩展、无需独显、适合量化小模型和离线实验；代价是内存带宽与向量指令决定速度，长输出可能明显慢。NUMA、内存通道和线程配置也会影响结果。

### GPU 路线

权重、KV 和计算尽量放显存，利用 GPU 并行和高带宽。通常低延迟和吞吐更好，但容量边界严格，桌面显示占用、驱动上下文和工作区会吃掉可用显存。多 GPU 还要考虑互联、切分和通信。

### Mixed Offload 路线

把一部分层/张量放 GPU，其余放 CPU，或把 KV、专家、权重按引擎支持分布。它可以让更大模型“装下”，但每个 token 可能跨总线搬运数据；PCIe/统一内存带宽和调度会成为瓶颈。

offload 的关键不是“卸载比例”一个数字，而是：哪些层在哪里、每 token 搬多少数据、KV 在哪里、是否重复迁移、总线与内存是否足够。**能加载成功是容量证据，不是速度合格证据。**

用一张 placement 账本代替“offload 了 60%”：

| 对象 | 保存在哪 | 在哪计算 | 每轮可能搬运 | 结束时如何回收 |
| --- | --- | --- | --- | --- |
| 权重/量化 block | CPU RAM / GPU VRAM / 统一内存 | 对应 layer/op backend | 理想情况下加载后不每 token 往返 | model 生命周期 |
| KV cache | host / device / 分层存储 | attention 所在 backend | 若与 attention 异地可能高频迁移 | sequence/context 生命周期 |
| activation/workspace | 执行 backend 的临时 buffer | 当前 op | graph split 边界可能复制 | graph/allocator 复用 |
| logits/采样输入 | device 或 host output buffer | 采样通常在应用层，以引擎为准 | 可能需 D2H 输出 | 每轮覆盖/释放 |

离散显卡上主要查 PCIe/NVLink 传输；统一内存平台也并非“无搬运”，页迁移、竞争和可用带宽仍可以制造延迟。因此需同时测内存驻留、传输字节、同步等待、prefill 和 decode，不能从平台名称推断成本为零。

## 8GB、16GB、24GB：保守课程路线

下表只用于缩小第一次实验范围，不是模型兼容保证，也不是购买建议。模型架构、量化格式、上下文、batch、引擎、显示占用和平台内存共享方式都会改变结果。

| 可用加速器内存 | 保守起步 | 可在严密预算后尝试 | 先避免 |
| --- | --- | --- | --- |
| 约 8GB | 1B–3B 级量化模型、短上下文、batch 1；或更小模型全精度 | 7B–8B 级低比特权重配短上下文/部分 offload | 直接承诺 7B–8B 全 GPU、长上下文或高并发 |
| 约 16GB | 7B–8B 级量化模型、batch 1、逐步增加 context | 13B–14B 级更低比特或 mixed offload | 把“权重刚好装下”当作服务可用 |
| 约 24GB | 7B–14B 级量化模型留出运行余量 | 更大低比特模型、长上下文或并发三者择一后逐步试 | 同时拉满模型、context、batch 与高精度 |

这里的“级”只指粗略参数规模，不能替代模型配置。统一内存机器也不能把标称内存全部给模型：系统和其他应用仍需空间，GPU 可用带宽与离散显卡不同。

## 一套不靠猜的容量流程

1. 固定完整模型 ID、revision、架构和 tokenizer；
2. 读取参数量、层数、KV 头数、head dim、上下文限制；
3. 固定权重量化、计算 dtype、KV dtype；
4. 先算权重与 KV 主项，再预留引擎/工作区/显示/系统余量；
5. 从 batch 1、短 context、短输出做最小加载和生成；
6. 逐项只增加一个变量：context、batch 或输出长度；
7. 记录空闲、加载后、prefill 峰值、稳定 decode 与结束后内存；
8. 同时测 TTFT、TPOT、错误和任务质量；
9. OOM 时先回退最近单项变化，不要同时改五个参数。

快速变化的格式与工具支持以 [[AI/90-资源/05-官方资料与版本核验记录|官方资料与版本核验记录]] 为入口。核验日期 **2026-09-01**；本页未下载模型、未运行硬件测试，也不把任何引擎的公开性能数字当作本机结果。

## 常见误区

- “模型是 4-bit，所以全部运行内存就是参数量 × 0.5 byte。”
- “batch 只影响速度，不影响 KV 和临时内存。”
- “context 上限写 128k，所以 128k 一定装得下且质量稳定。”
- “量化一定更快。”没有合适 kernel 时，解量化或回退路径可能更慢。
- “系统内存 + 显存可以无代价相加。”跨总线搬运有带宽与延迟成本。
- “24GB 能运行一次，就能承载多人服务。”并发、峰值和尾延迟尚未验证。

## 练习

1. 估算 13B 模型在 16-bit、8-bit、4-bit 下的理想权重主项，并说明实际为何更大。
2. 某模型权重占 9 GiB，KV 预算 4 GiB，工作区峰值 2 GiB，引擎和显示预留 2 GiB。16 GiB 显卡是否应尝试直接加载？为什么？
3. 只改变参数、context、batch、precision 中一个变量，分别说明最直接影响哪一项内存。
4. 为 8GB 设备写一个从安全配置逐步上调的三轮实验，每轮只改一个变量。

1. 理想主项约 26GB、13GB、6.5GB，尚未计 metadata、未量化层、对齐和运行开销。2. 预算总和约 17 GiB，已超过 16 GiB，且无安全余量，不应直接承诺；应降低权重/KV、缩短 context、offload 或换容量。3. 参数最直接影响权重；context/batch 线性影响 KV 主项；precision 需说明是权重、KV 还是计算精度。4. 例如固定小模型与 batch 1，先短 context；第二轮只加 context；第三轮恢复 context 后只换更大模型或提高 batch，不应同时改变。

## 成功标准

- 能写出总内存分解与权重、KV 两个主项公式；
- 能说明参数、context、batch 和各类 precision 的独立影响；
- 能解释 CPU/GPU/mixed offload 的容量—带宽—延迟取舍；
- 能把显存分档转化为带余量、逐变量的验证路线；
- 不再把“文件能下载”“权重能装下”“服务能稳定运行”混为一谈。
