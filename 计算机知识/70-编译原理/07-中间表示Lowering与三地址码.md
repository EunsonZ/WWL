# 中间表示、Lowering 与三地址码

## 本课目标

学完后，你应该能够：

- 区分 tree IR、linear IR 与 graph IR，说明同一编译器为什么会同时需要多种表示；
- 准确定义 instruction、operand、temporary、basic block 与 terminator；
- 把复杂表达式、短路逻辑、条件和循环手工降成三地址码与基本块；
- 解释 lowering 怎样逐层显式化类型、控制流、存储、调用约定等隐含语义；
- 在多对多变换后保留 source location、内联链和“合成指令”来源；
- 用结构 verifier 和语义检查区分“IR 形状合法”与“lowering 保持了源程序含义”。

适用场景：设计 toy compiler、阅读 LLVM/MLIR 一类多层 IR、定位某次优化前后的错误、理解后续 CFG、SSA、数据流分析和代码生成课程。

> [!important] 本课边界
> 本页使用伪 IR，不绑定某个 LLVM、MLIR 或商业编译器版本。CFG 的支配关系与 SSA 构造留到下一课，数据流方程留到第 09 课，目标指令选择与 ABI lowering 留到后端课程。IR verifier 只能证明结构契约成立，不能单独证明转换与源程序语义等价。

## 1. 直觉：IR 是编译阶段之间可检查的合同

源代码适合人表达意图，机器指令适合特定处理器执行；二者之间隔着类型检查、控制流展开、优化、对象布局、调用约定和目标限制。若每个阶段都直接读 AST、直接吐机器码，所有隐含语义会在一处纠缠，错误也难以定位。

中间表示（Intermediate Representation，IR）把编译过程拆成一组边界清楚的合同：

```text
源代码
  ↓ 词法、解析、名称解析、类型检查
带符号与类型的 AST / HIR
  ↓ 显式化求值顺序、控制流、临时值
三地址码 / CFG 形式的 MIR
  ↓ 显式化地址、布局、调用和目标限制
LIR / machine IR
  ↓ 指令选择、寄存器分配、编码
目标代码
```

一份 IR 的价值不在“长得像汇编”，而在它明确回答：

1. 哪些程序状态和操作在这一层可表达？
2. 哪些不变量必须始终成立？
3. 哪些细节已经显式，哪些仍由更低层决定？
4. 如何检查一次转换的输入和输出？

所以 IR 既是数据结构，也是阶段接口和证明边界。

## 2. 三类 IR：按主要结构区分，而不是互相排斥

同一函数可以同时拥有树、线性序列和图三种视图。分类描述的是**主要组织方式**，不是三个互斥产品名。

| 形式 | 主要结构 | 擅长表达 | 典型优势 | 典型代价 |
| --- | --- | --- | --- | --- |
| tree IR | 父子节点构成的树或近似树 | 嵌套语法、表达式层次、类型与源结构 | 接近源语言，局部递归处理自然 | 共享子表达式、跨语句数据流和跳转不够显式 |
| linear IR | 指令或语句的有序序列 | 明确求值顺序、临时值、顺序扫描 | 易打印、序列化和做局部 peephole | 分支目标与跨块关系仍需标签/索引补充 |
| graph IR | 节点与边构成的图 | 控制流、数据依赖、use-def、区域嵌套 | 合流、循环和依赖关系可直接查询 | 维护边、一致性与遍历顺序更复杂 |

例如源表达式 `(a + b) * (c - 2)` 的 AST 以乘法为根，两个子树分别是加法和减法；三地址码把它线性化为三个临时值；若再把基本块作为节点、跳转作为边，就得到控制流图。SSA 还会让“定义到使用”的数据依赖形成图。

图的顶点、边、遍历和环的基础见 [[计算机知识/50-数据结构与算法/07-图的表示BFS-DFS与拓扑排序|图的表示、BFS、DFS 与拓扑排序]]。不要因为 IR 被打印成文本就断言它是“纯线性”表示：文本可能只是图结构的稳定序列化。

## 3. IR 的最小词典

### 3.1 Instruction 与 operand

**instruction（指令）**是在当前 IR 层执行一个定义明确操作的节点，例如整数加法、比较、加载、调用或分支。它可以产生零个、一个或多个结果。

**operand（操作数）**是指令读取的输入。操作数可能是常量、临时值、符号引用、基本块标签、类型或属性；具体类别由 IR 契约决定。

```text
%t3 = mul.i32 %t1, %t2
```

这里 `mul.i32` 是带 32 位整数语义的操作，`%t1` 和 `%t2` 是两个操作数，`%t3` 是结果。`i32` 到底按模运算、可陷阱溢出还是携带“不会溢出”的前置条件，必须由该 IR 的语义明说，不能从名字猜。

### 3.2 Temporary

**temporary（临时值）**是编译器生成、用于命名中间结果的值标识。它不是源语言变量，也不自动对应机器寄存器：

- 一个源变量可能在不同程序点对应多个临时值；
- 一个临时值可能最终放在寄存器、栈槽、常量中，甚至被优化掉；
- 临时值的生命周期由 IR 中的定义和使用决定，不等于源对象生命周期。

### 3.3 Basic block

**basic block（基本块）**是一个最大化的单入口、顺序执行指令序列：控制只能从块首进入；在执行到末尾前不会跳出；块末的控制转移决定后继。

“单入口”是控制流结构的性质，不表示块首只能有一条入边。多个前驱可以都跳到同一块首。把指令从块中间作为跳转目标，会破坏基本块划分，必须先在那里切块。

### 3.4 Terminator

**terminator（终结指令）**是基本块的最后一条指令，完整说明控制流怎样离开该块，例如：

- `goto B`：唯一后继；
- `branch %cond, B_true, B_false`：两个候选后继；
- `return %value`：返回调用者，在函数内没有后继；
- `throw`、`unreachable`：按本 IR 的异常或不可达语义结束块。

一个结构良好的基本块通常要求**恰好一个 terminator，且 terminator 后没有普通指令**。异常边是否由普通调用隐式产生，还是由专门的 `invoke` 一类 terminator 显式表示，取决于 IR；分析算法必须服从实际契约。

## 4. 三地址码：一次只显式完成一个小步骤

三地址码（Three-Address Code，TAC）常把一条指令限制为“一个结果、一个操作符、至多两个普通数据输入”，例如：

```text
%t1 = add a, b
%t2 = sub c, 2
%t3 = mul %t1, %t2
out = copy %t3
```

这不是说所有 IR 都必须有严格三个文本字段。函数调用可有多个参数，load/store 还涉及内存，分支使用标签。它的核心是：把嵌套求值拆成可命名、可重排、可分析的小步骤。

### 手算例 1：表达式拆分

源表达式：

```text
out = (a + b) * (c - 2)
```

在假定左、右子表达式都无副作用，并已确定整数语义后，可得到：

| 顺序 | 新指令 | 定义 | 使用 |
| ---: | --- | --- | --- |
| 1 | `%t1 = add.i32 a, b` | `%t1` | `a, b` |
| 2 | `%t2 = sub.i32 c, 2` | `%t2` | `c` |
| 3 | `%t3 = mul.i32 %t1, %t2` | `%t3` | `%t1, %t2` |
| 4 | `out = copy %t3` | `out` 的新状态 | `%t3` |

核心不变量是：使用某个临时值前，它已沿当前顺序被定义；每条算术指令的操作数类型满足操作契约。若源语言规定表达式求值顺序、副作用或异常可观察，就不能任意交换第 1、2 步。

### 为什么拆分有用

- 常量传播可以单独处理 `%t2`；
- 公共子表达式消除可以比较操作与输入；
- 活跃性分析可以看到每个临时值最后一次使用；
- 指令选择能把小操作匹配到目标指令模式。

但“看起来更细”不等于天然正确。若源语言的有符号溢出、浮点舍入、异常顺序或 volatile/atomic 访问可观察，TAC 必须保留相关顺序与属性。

## 5. 手算例 2：短路逻辑必须变成控制流

考虑：

```text
if a != 0 && 10 / a > 1:
    y = f(a)
else:
    y = 0
return y
```

`&&` 的短路语义要求：只有 `a != 0` 为真时才能计算 `10 / a`。不能先算除法再对两个布尔值做普通 `and`。一种非 SSA 的三地址码是：

```text
B0_entry:
    %t0 = ne.i32 a, 0
    branch %t0, B1_rhs, B3_else

B1_rhs:
    %t1 = div.i32 10, a
    %t2 = gt.i32 %t1, 1
    branch %t2, B2_then, B3_else

B2_then:
    %t3 = call f(a)
    y = copy %t3
    goto B4_exit

B3_else:
    y = copy 0
    goto B4_exit

B4_exit:
    return y
```

逐块检查：

| 块 | 普通指令 | terminator | 后继 |
| --- | --- | --- | --- |
| `B0_entry` | 比较 `a != 0` | 条件分支 | `B1_rhs, B3_else` |
| `B1_rhs` | 除法、比较 | 条件分支 | `B2_then, B3_else` |
| `B2_then` | 调用、赋值 | 无条件跳转 | `B4_exit` |
| `B3_else` | 赋值 | 无条件跳转 | `B4_exit` |
| `B4_exit` | 无 | 返回 | 无 |

这里已经显式化了源语言原本藏在 `&&` 中的控制依赖。`B4_exit` 有两个前驱，而可变名字 `y` 有两个定义；下一课会把它转换为 SSA 的 `phi` 合流。

> [!warning] 除零反例
> 若 lowering 生成 `%t1 = div 10, a` 后才判断 `%t0 && %t2`，那么输入 `a = 0` 时会执行源程序本应跳过的除法。即使大多数输入结果相同，这仍是语义错误。

## 6. 多层 lowering：逐步显式化，不是一次改格式

**Lowering** 是把较高层操作转换为较低层、更受约束的操作，同时保持该层承诺的可观察语义。它通常分多步完成：

| 层次 | 仍然保留 | 逐步显式化 |
| --- | --- | --- |
| AST / HIR | 源变量、结构化 `if/while`、高层类型、源范围 | 名称绑定、隐式转换、重载选择 |
| MIR | 临时值、基本块、调用、抽象内存操作 | 求值顺序、短路控制流、循环回边、异常边 |
| LIR | 接近机器的值类别、地址计算、调用序列 | 对象布局、字段偏移、整数宽度、目标约束 |
| machine IR | 目标指令候选、虚拟/物理寄存器、栈槽 | ABI 参数位置、指令限制、寄存器与调度约束 |

例如一个高层数组读取 `a[i]` 可能依次变成：

```text
HIR: array_get(a, i)                  // 保留数组与边界语义
MIR: bounds_check(i, length(a))       // 显式检查与失败控制流
     %addr = element_address(a, i)    // 仍是目标无关地址操作
     %v = load_element %addr
LIR: %off = mul i, element_size       // 显式大小和偏移
     %ptr = add base_address(a), %off
     %v = load.i32 %ptr, align 4
```

每一步都有独立前提：元素大小来自已确定布局；边界检查不可在未证明安全时删除；地址计算的溢出与越界规则必须与语言/IR 契约一致。地址、对齐和字节表示的系统基础见 [[计算机知识/30-计算机系统/01-数据表示字节序与对齐|数据表示、字节序与对齐]]，机器指令视角见 [[计算机知识/30-计算机系统/06-指令系统汇编与程序执行|指令系统、汇编与程序执行]]。

### Lowering 与优化不是同一件事

- lowering 的首要目标是把一种合法表示变成更低层合法表示；
- 优化的目标是在给定语义和成本模型下改进某个指标；
- 一次 pass 可以同时做两者，但评审时仍要分别检查“是否覆盖所有高层操作”和“是否保持语义/真的改善成本”。

若 lowering 后高层操作仍意外残留，后端可能无法处理；若为了简化而丢掉异常、溢出或求值顺序，即使输出 IR 能被打印和执行，也可能已经编错。

## 7. Source location：让低层结果还能解释来自哪里

源位置（source location）至少应能表示文件、起止偏移或行列范围；更完整的 provenance 还包括宏展开链、内联调用链、模板/泛型实例化来源和 pass 生成原因。

Lowering 的映射通常不是一对一：

- 一条源语句会生成多条比较、分支、load/store；
- 多条源语句可能合并为一个低层操作；
- 边界检查、清理块、phi 等指令可能没有唯一对应的源 token；
- 内联后，当前机器位置同时属于调用点和被调函数位置。

推荐的不变量是：

1. 可直接追溯的指令继承最具体、真实的源范围；
2. 合成指令明确标记 synthetic，并记录生成它的高层操作或 pass；
3. 合并位置时保留内联/展开链，不伪造一个看似精确的单行；
4. 源文件身份、版本和字符偏移约定稳定，Unicode 行列含义明确；
5. 删除或合并代码后，调试映射允许“不完全可观察”，但不能悄悄指向无关源句。

source location 既服务错误诊断，也服务调试、覆盖率、性能 profile 回映和 crash symbolication。它不是普通注释：丢失后通常无法从低层指令唯一恢复。

## 8. 结构 verifier 与 lowering 不变量

每次建立或重写 IR 后，先检查局部结构合同：

```text
VERIFY_BLOCK(block):
    require block has exactly one terminator
    require terminator is the final instruction
    for each instruction in block:
        require opcode exists in this IR level
        require operand count and types match opcode contract
        require every referenced value and block exists
    require terminator successors match its opcode
```

函数级检查还应验证块标签唯一、入口存在、引用关系一致，以及当前层不允许的高层操作已经清零。这个过程近似与 IR 节点和边数线性相关，前提是值/块查询使用哈希表或紧凑 ID 的近似常数时间索引。

Lowering 的正确性则需要更强的不变量：

- **覆盖性**：每种合法输入操作都有转换规则，或能给出明确“不支持”诊断；
- **类型保持/精化**：结果类型满足更低层契约，隐式转换已被正确显式化；
- **控制效果保持**：正常返回、分支、短路、异常和不可达行为不被混淆；
- **内存效果保持**：读写顺序、别名、volatile/atomic 和生命周期约束没有丢失；
- **来源可追溯**：诊断和调试所需的 source provenance 仍可查询。

结构 verifier 通过只能说明“输出属于 IR 的合法集合”。要证明语义保持，还需等价性论证、差分测试或更强的转换验证。合法推理的边界可回看 [[数学/10-数学语言与基础/03-集合映射命题与合法推理|集合、映射、命题与合法推理]]。

## 9. 复杂度与实现前提

设函数有 `N` 个 IR 指令、`B` 个基本块、`E` 条 CFG 边：

- 一次直接的 AST/TAC 遍历通常为 `O(N)`，前提是每个节点只处理常数次；
- 构造 CFG 的块和边为 `O(N + E)`，前提是标签解析和块查询为均摊 `O(1)`；
- verifier 通常为 `O(N + E)`，但全局支配、类型推导或别名检查不属于本页的“简单结构验证”；
- 临时值和显式指令会增加常数因子与峰值内存，打印文本也可能比紧凑内存表示大很多；
- 若对每次插入都线性扫描全部值、反复复制大列表，实际实现可能退化到二次复杂度。

大 O 不替代内存布局与局部性判断。IR 若由大量散落对象和指针构成，遍历成本可能被缓存未命中主导；相关系统直觉见 [[计算机知识/30-计算机系统/04-缓存局部性带宽与延迟|缓存、局部性、带宽与延迟]]。

## 10. 失败边界与常见误解

| 误解或失败 | 为什么错 | 应怎样处理 |
| --- | --- | --- |
| “IR 越低级越好” | 太早丢失高层类型、结构和来源，会阻碍诊断与高层优化 | 为不同阶段保留多层 IR |
| “TAC 临时值就是寄存器” | 寄存器数量、类别和调用约定尚未决定 | 把 temporary 当逻辑值，后端再分配位置 |
| “块尾没有跳转也能猜下一个块” | 文本排列不一定等于控制流 | 要求显式 terminator 或明确定义 fallthrough |
| “结构 verifier 通过就等价” | verifier 不知道源程序应有的全部行为 | 独立验证转换语义和失败路径 |
| “整数运算都可自由重排” | 溢出、异常、原子/volatile、副作用和语言顺序可能可观察 | 在 IR 中携带语义属性并证明前置条件 |
| “一个源行对应一条低层指令” | lowering、内联和优化通常多对多 | 保留范围和 provenance 链，不伪造一对一 |
| “不可达块一定可直接删除” | 反射、异常、地址可取标签或错误 CFG 可能改变判断 | 先依据当前 IR 的可达性和副作用契约证明 |

还要区分 IR 层级：高层 `add` 可能是任意精度整数、带溢出检查的机器整数、浮点加法或用户重载调用。若 pass 把它们当成同一种运算，表示再漂亮也不正确。

## 练习

1. 把 `r = (x + 1) * (x + 1)` 写成最直接的 TAC，再写一个复用公共子表达式的版本。分别列出临时值的定义和使用；不要把“复用更快”当作已证明事实。
2. 将 `while i < n: sum = sum + a[i]; i = i + 1` 降成 `entry/header/body/exit` 四类基本块，给每块补恰好一个 terminator，并标出数组边界检查应发生的位置。
3. 把本页短路例中的 `&&` 改成 `||`，重新画控制流。用 `a = 0` 与 `a = 2` 手算哪些块被执行。
4. 为 `array_get(a, i)` 写出 HIR → MIR → LIR 三层转换清单：每层新增了什么显式事实，仍把什么留给后续阶段？
5. 故意构造三份非法 IR：terminator 后还有指令、引用不存在的块、操作数类型不匹配。写出 verifier 应在哪条规则拒绝。
6. 设计 source location 表，表示“一条源表达式生成四条 IR 指令”以及“内联函数中的一条指令同时属于被调函数和调用点”。

## 成功标准

- 你能用同一个例子分别说明 tree、linear、graph IR 的结构，而不把文本打印形式误当成唯一内部结构；
- 你能逐项指出 instruction、operand、temporary、basic block 和 terminator，并验证每块只有一个末尾 terminator；
- 你能正确 lowering 短路逻辑，不提前执行本应跳过的除法或调用；
- 你能解释至少三层 lowering 各自显式化了什么，并区分 lowering 与优化；
- 你能说明 source location 为什么是多对多映射，并给合成指令保留来源；
- 你能明确说出：结构合法、编译成功和语义等价是三个不同命题。
