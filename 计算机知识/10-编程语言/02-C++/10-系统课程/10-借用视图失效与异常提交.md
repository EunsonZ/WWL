# 值还在不等于引用有效：视图、容器与异常提交

> **本页要解决**：vector 没扩容时，erase 为什么仍会使某些引用失效？

## 先分开四个容易被合并的问题

一个引用能否使用，至少要问：对象是否仍在生命周期内；引用是否仍指向那个对象；当前操作是否按容器规则使它失效；访问是否遵守线程同步。底层地址还可读，不能自动回答后三个问题。

`std::string_view` 是字符序列的非拥有视图；`std::span` 是连续元素的非拥有视图。它们保存可访问信息，却不承担底层存储的释放责任。将它们保存到异步任务、缓存或返回值中，会把寿命要求带到更远的地方。[^cpp-view]

## 从最小悬垂反例理解拥有关系

```cpp
#include <string>
#include <string_view>

std::string make_text() { return "a message with owned storage"; }

// 错误设计，不用于运行测试：
// std::string_view bad() { return make_text(); }

std::string good() { return make_text(); }
```

临时 `std::string` 在相应完整表达式结束时析构；视图不接管它的字符缓冲区。返回值优化可能消除拥有对象的中间移动，却不能让上面的错误视图自动拥有数据。即使短字符串优化让结果偶尔“看起来还在”，生命周期错误也没消失。

另一个例子是保存 `vector` 元素引用后再 `push_back`。若扩容重分配，旧元素位置改变，指针、引用和迭代器失效。提前 `reserve` 可以在一定容量内避免重分配，但不是所有修改下的引用稳定承诺。[^cpp-vector]

## 没扩容也可能失效

设向量元素为 `[A,B,C,D]`，保存指向 C 的迭代器，再删除 B。后面的元素要向前移动；`erase` 使删除位置及其后的迭代器和引用失效。容量完全可能不变，因此“比较 capacity 前后相等”不足以证明旧引用有效。

插入也要区分重分配和不重分配：发生重分配时全面失效；未重分配时，插入点及其后的元素相关引用仍需要按规则处理。尾后迭代器也不代表一个普通长期稳定元素。准确策略是把“哪些操作会发生”写入借用期间的合同，而不是只挑一种常见失效原因。[^cpp-vector]

对 `unordered_map`，rehash 对迭代器与对元素引用的影响又不同。不能把一种容器的表格机械复制给另一种。稳定 ID、索引、节点句柄、间接拥有对象等方案有各自成本；索引虽然避免直接指针悬垂，删除和重排后也可能指向另一条业务记录。

## 返回借用还是返回拥有值

读取已有文档中的短期字段，返回视图可以省复制；把结果放入长期任务，返回拥有字符串往往更清晰。也可让结果对象共享拥有整份不可变缓冲区，再保存合法区间。这与 [[计算机知识/10-编程语言/04-Rust/10-系统课程/09-借用检查中的量词方差与重借用|Arc 与范围表示]] 相近，但 C++ 需要自行保证区间不越界、缓冲区不被破坏性修改。

“零复制”应说明省掉哪次复制，是否增加引用计数、间接访问和保留整块大缓冲区的成本。为了保留十个字节而让一百兆字节缓冲区长期存活，局部零复制未必降低整体内存。

### 返回测量应用：先给结果找拥有者

从[[计算机知识/10-编程语言/02-C++/10-系统课程/12-值类型泛型算法与数值应用#阶段 1：哪些不变量应该属于类型|测量Batch的值与借用合同]]带回同一份`[2,4,6,8]`和三个对象：拥有原码vector的Batch、只读借用`codes()`的span，以及按值返回的Calibration。回来回答“数组为什么借用、两个int的标定为什么按值返回”：`codes() const&`拒绝临时拥有者，却仍要求借用期间Batch不析构、赋值、移动、swap或replace；`calibration()`返回独立值，从临时Batch取得也不借用已销毁的成员。这个接口拒绝少数危险表达式，不使C++自动具备Rust的完整借用检查。

继续[[计算机知识/10-编程语言/02-C++/10-系统课程/13-可交付组件与并发测量工程#结果、资源与视图放在同一张图上|ReportSession的资源与借用]]，带回旧windows span/text string_view和一份候选Snapshot。返回时分别预测失败、成功：replace失败保留旧Snapshot，所以旧借用仍可读；成功提交销毁旧Snapshot，旧借用结束，应重新取得。结果PMR资源活计数与每个注入失败点支持的是指定资源/输入路径；不回滚已读流位置，也不认证文件输出事务或所有普通allocator失败。

若要延后执行，进入[[计算机知识/10-编程语言/02-C++/10-系统课程/14-有界任务关闭取消与性能证据#取消不销毁已经运行的对象|拥有任务与全部等待]]，携带“调用何时真正结束”的问题。ReportTask拥有输入string/settings，worker拥有本地Session，TaskOutcome复制拥有文本，全部join后返回；没有把text()的string_view送出Session寿命。返回本节时，给出任务前后谁拥有数据、谁负责等待的答案。取消可丢弃未开始任务，已开始可完成，不能凭stop请求推断借用已经结束。

## 强异常保证是一种提交协议

假设配置对象要同时更新路径和查找表，任一步都可能分配失败。直接修改原对象，失败后可能留下“新路径配旧表”。更容易证明的方式是先在临时对象中完成校验与构造，再通过满足所需不抛保证的提交步骤替换原状态。

```cpp
#include <string>
#include <utility>
#include <vector>

struct Config {
    std::string name;
    std::vector<int> values;
    void swap(Config& other) noexcept {
        name.swap(other.name);
        values.swap(other.values);
    }
};

void replace_config(Config& live, const Config& input) {
    Config candidate = input;   // 可能抛异常；live 尚未改变
    live.swap(candidate);       // 此处使用默认 allocator 的成员类型
}
```

这里使用的具体成员与默认 allocator 支持所需交换保证；不能把这段 `noexcept` 原样复制到任意自定义 allocator 或带抛异常交换的成员上。失败前原状态保持不变，成功后旧状态由临时对象负责析构。把析构和清理设计为不抛异常也很重要，尤其在栈展开已经处理另一个异常时。

强异常保证只承诺当前操作可观察状态在异常时保持原样，并不自动撤销已经发送的网络请求、写出的日志或另一个线程看到的外部副作用。内存内的 copy-and-swap 与 [[计算机知识/20-操作系统/02-操作系统原理/10-系统课程/11-崩溃一致性与恢复状态机|磁盘原子替换]] 有结构相似性，但故障模型不同。

## 证明与测试分别做到哪一步

测试用一个可控抛异常的元素类型：复制第 k 个元素时抛出，检查原配置仍保持旧值；对每个可能失败点分别注入，再检查资源计数回到预期。测试应包含自赋值、空对象和大对象。

视图失效的负例不应靠反复运行 UB 来断言“会崩溃”。可用编译器警告、审计规则和安全的所有权模型说明拒绝原因；正向例子则在明确寿命下验证内容。Sanitizer 没报错不是容器引用有效性的证明。

**练习**：异步发送函数接受 `string_view` 并只排队、立即返回，调用方可否传一个临时字符串？若任务真正发送时临时对象已销毁，就不可以。修复可以改为接收并拥有 `std::string`，或者要求调用者持有缓冲区直至完成并用类型/句柄明确表达。它不是再加一个 `const` 就能解决的问题。
