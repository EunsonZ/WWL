# BashPython与可复核自动化

**先修关系：** [[计算机知识/Kali/01-系统与网络基础/04-Shell文件权限与文本处理|Shell文件权限与文本处理]]。

## 什么时候值得写脚本

先能手工解释一条命令，再自动化重复步骤。脚本的价值是保持输入、参数、输出和失败政策一致，而不是把一堆未经理解的命令拼成“全自动渗透”。网络范围、并发、超时、数据去向和停止条件必须成为显式输入合同。

本包的 [[计算机知识/Kali/07-综合实验/09-实验代码合同与复现|实验代码]] 只做标准库离线任务：生成合成夹具、演示 SQL 参数化与对象授权、汇总教学日志。导入模块不运行实验，不下载数据，不读取凭据，不打开监听端口。

## Bash 适合编排，Python 适合结构化逻辑

Bash 擅长连接已有程序，但字符串、文件名和退出状态容易产生隐含行为。下面是只读文件的编排片段，不是完整脚本：

```bash
# Bash 语义；目标必须是你明确指定的普通文件
input=${1:?请提供一个输入路径}
if [ ! -f "$input" ]; then
  printf '不是普通文件：%s\n' "$input" >&2
  exit 2
fi
sha256sum -- "$input"
```

`--` 阻止以连字符开头的文件名被解释成选项；引号避免拆词。检查文件后到真正打开之间仍存在竞态，不能把这个片段宣传为处理敌对文件系统的完整沙盒。[^s1]

Python 处理 JSON、CSV、XML 时优先使用对应解析器。调用外部程序通常用参数列表而不是 `shell=True` 拼字符串；文件来源不可信时，还要考虑文件大小、编码、符号链接与解析器资源消耗。

## 输入合同必须写出失败行为

以“从 JSONL 日志统计 HTTP 状态码”为例：每行需要是 JSON 对象，`status` 必须是合法整数状态码，空行是否允许应明确。错误行不能静默丢掉，因为丢弃比例可能改变结论。

好的输出可以说“读到 6 行，其中 0 行格式错误”，或者直接在第 3 行失败并定位错误；坏的输出是“成功率 100%”，却从未说明它悄悄跳过了一半行。布尔值在 Python 中是整数的子类，因此验证纯整数时还应防止把 `True` 当成状态码 1。

## 结构化证据，不保存秘密

每次运行至少关联：输入文件内容摘要、脚本版本/摘要、明确参数、时间基准、退出状态与输出位置。凭据不应出现在命令行参数、调试输出、Shell 历史或分享报告中。环境变量也并非完美秘密容器，需评估继承、诊断与进程可见性。

把原始证据与派生结果分开：`raw/` 尽量只读，`derived/` 可重建，`report/` 保存解释。派生 CSV 不应成为唯一数据源，尤其当它丢失了时间精度或过滤掉异常行。

## 测试分层

单元测试验证一个函数的已声明行为；性质测试验证如“同一夹具生成参数应产生同一字节串”这样的不变量；端到端测试验证从输入到产物的完整路径。一个纯函数测试通过，不代表 Kali 的驱动、工具或 GUI 已通过。

本包保留三个具体反例：SQL 拼接与参数化的行为差异；Alice 请求 Bob 对象时拒绝；无效日志状态应明确报错。它们不仅检查“能跑”，还检查错误路径是否保留了安全边界。

## 可复现不等于普适

固定随机种子只能控制特定伪随机过程；输出一致不保证实验设计正确。工具升级、协议实现、靶机补丁和采集位置仍可能改变结论。应记录“在哪些条件下复现”，而不是给代码贴永久“已验证”标签。

自检：脚本忽略所有超时目标后报告“开放端口率下降”，这说明防护更好吗？不一定，可能只是难以测量的对象被选择性排除。应同时报告超时数、有效样本分母和未决状态。见 [[计算机知识/Kali/00-导航与方法/04-从观察到结论的安全方法|测量偏差与证据分层]]。

## 自动化应先定义结果状态，而不是先写循环

批处理至少区分 `success`、`negative`、`invalid_input`、`timeout` 和 `not_run`。把这五种都压成 True/False，会把“工具根本没运行”混进“没有发现问题”。每条记录应含任务标识、输入标识、工具版本、退出码和适用的结果字段；失败时保留错误类别，不把秘密正文写入日志。

结构化输出还要定义合并规则。地址与端口的键应包含传输协议；时间戳应含时区；同一资产重复记录不能未经判断就去重。对象 17 和字符串 "17" 在 HTTP 解析前后可能等价，但边界转换必须显式发生，不让各下游函数各自猜测。

## 子进程：参数列表能解决什么，不能解决什么

Python 调用本地工具时优先用参数列表与 `shell=False`，避免让不受信任文本再次作为 Shell 语法解释。需要超时、返回码和标准错误时分别记录。[^v2-subprocess]

```python
# 说明性小片段：只读取本地程序版本，不访问网络。
import subprocess
result = subprocess.run(
    ["python3", "--version"],
    shell=False, capture_output=True, text=True, timeout=5, check=False,
)
print({"returncode": result.returncode, "stdout": result.stdout.strip()})
```

参数列表不能阻止**目标程序自己的选项解释**。用户输入若被当成选项、模板路径或可执行配置，仍可能改变行为；应先做枚举或路径合同检查，在目标支持时用 `--` 结束选项。`timeout` 也不自动限制目标的所有后代进程或内存；大型生产调度需另外设计进程组、资源限制和清理策略，本包不将此片段包装成沙盒。

## 失败样本是代码合同的一部分

新增解析器先准备正常对象、空集合、重复键、错误类型、越界值、未完成任务和恶意声明等反例。独立对照应该从合同和可手算结果出发，不调用同一个有缺陷核心生成“期望值”。原实验保持在 [[计算机知识/Kali/07-综合实验/09-实验代码合同与复现|代码合同]]；新增离线推理和 XML 差异实验分别验证未观测端口、时间线与授权矩阵，而不假装执行了真实扫描。

## 原始产物与成功产物不要用同一个文件名冒充

考虑一个扫描进程先写出半份 JSON，然后超时退出。文件存在、甚至前半段包含一条告警，都不能说明任务完成。可靠的编排应同时保存三条线：进程状态及 stderr、原始产物、通过结构与覆盖检查后认可的结果。原始失败产物不能删除，但也不能被下游当成完整报告。

一次本地工作流可以是：先在本次独有目录写临时输出，等待进程结束，检查退出状态和格式，再验证目标数、结束标记与覆盖范围；满足合同后发布一份明确标为有效的派生结果。临时文件到最终文件的原子替换只解决部分可见性问题，不自动保证跨文件一致性、磁盘持久化、并发隔离或权限安全。不要拿一个 `rename` 当事务系统。

下游至少区分四类状态：`completed` 表示完成了声明的范围，`partial` 表示有可用观察但范围不完整，`failed` 表示本次任务不能提供约定结果，`not_run` 表示根本未运行。零发现只是结果数量，不能替代上述状态。若工具不提供所需信息，保留 unknown，而不是为了整齐填 completed。

### 用顺序反例验证你的验收器

[[计算机知识/Kali/01-系统与网络基础/04-Shell文件权限与文本处理|jq 多输入例子]] 表明，好的最后一条记录可能掩盖前面的坏记录。验收器应测试空输入、坏记录在开头/中间/末尾、结构合法但字段错误、截断输出、预期拒绝和真正运行失败。输入排列不该改变“所有记录合格”这个命题的真值。

对于具备写入行为的流程，再加入中间步骤失败后是否留下半更新的检查。[[计算机知识/Kali/07-综合实验/15-实验L事务幂等与并发控制|实验 L]] 会让审计写入故意失败，检查业务状态、事件和幂等记录一起回滚；它补充的是原实验 I 没有实现的原子状态变更，不把纯函数返回 True 当成数据库已完成提交。
