## 本课目标

完成本课后，你能先分清工具的职责，再为一个具体项目选择 `pip + venv`、`uv` 或 Conda；能把“能在我电脑跑”变成团队可复现的依赖记录；也能在不破坏系统 Python、原环境或生产服务的前提下迁移项目。

这里会随版本变化的工具能力与命令已于 **2026-09-01** 核对。它们表达的是当时的常见工作流、不是永久承诺；执行前应分别以 [PyPA 官方指南](https://packaging.python.org/en/latest/)、[Conda 官方文档](https://docs.conda.io/projects/conda/en/stable/) 和 [uv 官方文档](https://docs.astral.sh/uv/) 为准。

## 1. 先拆开五种职责

“我用 uv/Conda/Poetry，所以它管理了一切”是常见但危险的简化。一个工具可能覆盖多项职责，职责本身仍然不同：

| 职责 | 要解决的问题 | 典型产物或动作 | 代表工具 |
| --- | --- | --- | --- |
| 包管理 | 安装哪个 Python 分发包及其依赖？ | `requests`、版本约束、wheel | `pip`、`uv`、Conda |
| 环境管理 | 哪些已安装包彼此隔离？ | `.venv/`、Conda environment | `venv`、`uv venv`、`conda create` |
| 项目管理 | 项目的名称、依赖组、构建、发布和锁定如何声明？ | `pyproject.toml`、lockfile | `uv`、Poetry，或手工的 PyPA 标准文件 |
| 解释器管理 | 用哪个 Python 版本，以及它从何而来？ | Python 3.x 安装、项目版本要求 | 系统/官方 Python、`uv python`、Conda |
| 应用工具安装 | 如何全局可用而不污染项目？ | `ruff`、`black`、`httpie` 等命令行工具 | `pipx`、`uv tool` |

例如，`venv` 是标准库中的**环境管理**工具，不会解依赖或写 lockfile；`pip` 是 PyPA 的参考**包安装器**，也不是完整的项目工作流。`uv` 覆盖更多职责；Conda 同时管理环境与 Python/非 Python 包，但是否有可靠锁定和发布约定仍取决于团队选择的具体流程。

相关横链：[pip 文档](https://pip.pypa.io/en/stable/)、[venv 文档](https://docs.python.org/3/library/venv.html)、[Conda 文档](https://docs.conda.io/projects/conda/en/latest/)、[uv 文档](https://docs.astral.sh/uv/)。

## 2. 先选“环境边界”，再选命令

无论选择哪个方案，优先把第三方依赖放进项目专属环境。不要把项目依赖装进系统 Python、操作系统包管理器拥有的 Python，或已有的通用科研环境。

```bash
# 在项目根目录；显式把 pip 绑定到当前解释器
python -m venv .venv
source .venv/bin/activate       # Windows PowerShell: .venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install requests
python -c "import sys, requests; print(sys.executable, requests.__version__)"
```

`.venv/` 是可再生的构建产物：加入 `.gitignore`，不提交。提交的是依赖声明、锁定文件和必要的安装说明。用 `python -m pip` 而不是裸 `pip`，可以避免 shell 中的 `pip` 恰好属于另一套 Python。

操作系统标记为“外部管理”的 Python 旨在保护系统工具。不要为图方便使用破坏该边界的选项；新建 `.venv`，或按操作系统的包管理方式处理系统软件。

## 3. 三条主路线怎么选

| 路线 | Python 依赖与环境 | 非 Python 二进制/库 | 锁定与可复现 | 速度与日常体验 | 团队与 CI | 数据科学 | 系统 Python 边界 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `pip + venv` | `venv` 隔离，`pip` 安装 PyPI 包 | 主要依赖系统已提供的编译器、库或 wheel | 可用精确 `requirements`、constraints 和哈希；需要团队自己约定生成/审查流程 | 足够直接，生态基线最稳 | 几乎所有 Python 工具和 CI 都理解它 | 小型/纯 Python 分析可用；复杂原生依赖时配置成本可能上升 | **最适合**保留系统 Python 不受项目影响 |
| `uv` | 可管理项目、环境、Python 解释器和工具；兼容常见 `pyproject.toml`/pip 工作流 | 核心仍面向 Python 包；系统级依赖不自动消失 | 项目可生成并同步 `uv.lock` | 解析、缓存与安装通常很快；命令统一 | 适合新项目和愿意统一工具链的团队 | 适合常规数据分析；含复杂系统库时仍要评估平台与包来源 | 用项目 `.venv`；不要把“管理 Python”理解成可随意替换系统 Python |
| Conda（可通过 Miniconda 或 Anaconda Distribution 安装） | Conda environment 同时装 Python 和包 | **强项**：可一并分发许多原生库、运行时和命令行依赖 | `environment.yml` 表达可重新求解的意图；Conda 26.5+ 可原生生成/消费多平台 `conda-lock.yaml`；渠道、平台与重建测试仍需团队规范 | 首次求解可能较重；科学计算的二进制安装常更省心 | 适合已有 Conda 规范的科研/数据团队；务必固定渠道与锁定/导出方式 | **适合**NumPy/SciPy 等受原生依赖影响的工作和多语言栈 | 不在 base 环境做项目；每个项目单独 `conda create -n ...` |

### Conda、Miniconda 与 Anaconda 不是三种求解器

- **Conda** 是包与环境管理器，也是其包格式和仓库生态的名称。
- **Miniconda** 是较小的 Conda 发行版起点：先得到 Conda、Python 与少量基础内容，再按需创建环境、安装包。
- **Anaconda Distribution** 是面向数据科学的更完整发行版/套件，预装或易获取更多组件；它不等于“Conda 的增强模式”。组织使用前还要按[官方发行版说明](https://www.anaconda.com/docs/getting-started/anaconda/)核对当前许可、渠道和支持条款。

这三者可共享 Conda 的命令与环境概念；选择它们时，真正要问的是“团队需要的预装内容、支持和许可是什么”，不是“哪一个能创建虚拟环境”。

### Poetry 与 pipx 的边界

- **Poetry** 是项目工作流工具：声明依赖、建立环境、锁定和发布都可以涵盖。若仓库已经以 `pyproject.toml`、`poetry.lock` 和 Poetry 命令作为约定，就跟随该约定；不要为了“统一”在同一个项目再引入第二个 lockfile。
- **pipx** 用于把面向人的 Python 命令行应用安装到各自隔离的环境，例如格式化器或项目脚手架。它不是项目依赖管理器；项目运行仍应使用项目的 `.venv`。PyPA 的[独立命令行工具安装指南](https://packaging.python.org/en/latest/guides/installing-stand-alone-command-line-tools/)说明了这条边界。`uv tool` 也服务于相似的“工具而非项目依赖”场景。

## 4. 一个可操作的选择树

```text
起点：这是一个要长期维护、可能交给别人运行的项目吗？
  ├─ 否，只是一次性学习脚本
  │   └─ 仍创建 .venv；pip + venv 最少认知负担
  └─ 是
      ├─ 需要随项目安装大量非 Python 原生库、CUDA/系统运行时，
      │  或团队已有明确 Conda 环境与渠道规范吗？
      │   ├─ 是 → 为项目建独立 Conda environment；记录 Python、渠道和导出方式
      │   └─ 否
      │       ├─ 团队要一个统一的项目、锁定、解释器和工具入口，且愿意采用 uv 吗？
      │       │   ├─ 是 → uv project + uv.lock
      │       │   └─ 否 → pyproject.toml/requirements + pip + venv；另立锁定生成约定
      │       └─ 现有仓库已使用 Poetry 吗？
      │           └─ 是 → 沿用 Poetry；不要在无迁移计划时混用多个项目管理器
```

这不是“性能排行榜”。例如，一个纯 API 服务用 `pip + venv` 可读、可移植；一个有大量科学计算二进制与跨语言运行时的研究项目用 Conda 可能更可控；新团队想减少不同工具之间的衔接时，`uv` 的统一入口很有价值。团队的既有 lockfile、CI 和发布流程，通常比个人偏好更重要。

## 5. 声明、解析与锁定：不要混为一谈

以 `requests>=2,<3` 为例，它是**意图**，不是环境快照。安装器会把它和所有传递依赖解析成某一组实际版本。可复现需要至少三层信息：

1. **声明**：直接依赖与允许的版本范围，例如 `pyproject.toml` 或面向 pip 的依赖输入文件；它便于维护。
2. **锁定**：某次已解析的直接与传递依赖版本，最好再带分发文件哈希；它让 CI、同事和部署使用同一集合。
3. **同步/安装**：按锁定的结果创建一个新环境，然后运行测试。旧环境“正好能跑”不证明锁定有效。

### pip + venv 的可复现基线

`requirements.txt` 可以写精确版本，`pip install -r requirements.txt` 可以重建它；`pip freeze` 能记录当前环境，但它会混入临时安装、编辑安装或平台差异，不能替代对“直接依赖”和“锁定产物”的审查。对供应链敏感的部署，使用精确版本并考虑 `--require-hashes`，让 pip 校验被允许的分发文件哈希。详见 pip 的[可重复安装](https://pip.pypa.io/en/stable/topics/repeatable-installs/)与[安全安装](https://pip.pypa.io/en/stable/topics/secure-installs/)文档。

```bash
# 只在空的项目 .venv 中执行；requirements.lock 由团队既定流程生成并审查
python -m pip install --require-hashes -r requirements.lock
python -m pip check
python -m pytest
```

`pip check` 能发现已安装包的版本要求是否相互冲突，但不会证明代码兼容、wheel 没问题或运行时系统库存在。因此测试仍是锁定流程的一部分。

### uv 的可复现基线

`uv` 项目把声明放在 `pyproject.toml`，将解析结果写进 `uv.lock`。常见工作流是改声明后更新锁文件，提交两者，在干净环境或 CI 中按锁文件同步并测试：

```bash
uv init
uv add httpx
uv lock
uv sync --locked
uv run --locked pytest
```

不要手写 `uv.lock`，也不要只提交 `pyproject.toml` 而不审查锁文件变化。阅读 uv 的[项目锁定与同步说明](https://docs.astral.sh/uv/concepts/projects/sync/)以核对当前命令语义。

### Conda 的可复现基线

Conda 环境不能只记录顶层“我装过 pandas”。团队至少应记录 Python 版本、直接依赖、使用的渠道及其优先级，以及面向目标平台的导出/重建命令。导出文件是可复现的起点，不是跨操作系统必然逐字相同的承诺：原生库、平台标记和渠道中的构建会影响求解结果。

```bash
conda create -n sample-python python=3.12
conda activate sample-python
conda install numpy pandas
conda env export --from-history > environment.yml
conda env create -f environment.yml
```

上面的 `--from-history` 导出更接近“顶层依赖意图”，创建时仍会重新求解，不是精确锁文件。**Conda 26.5 及以上**可原生生成和使用多平台 `conda-lock.yaml`，不需要额外插件：

```bash
# 只列出项目真正需要支持的目标平台
conda export --name sample-python --file conda-lock.yaml \
  --platform linux-64 --platform osx-arm64 --platform win-64
conda create --name sample-python-locked --file conda-lock.yaml
```

锁文件记录精确版本、build、channel 和平台；从它创建时 Conda 跳过求解。不要为了“看起来支持更多”而盲目锁定未实际测试的平台；旧版 Conda 应使用团队已审核的传统导出或独立 `conda-lock` 流程。

在真实项目中，在第二台机器或 CI 中实际重建、运行测试；若项目同时使用 Conda 包和 PyPI 包，明确两者的边界和安装顺序，避免一个工具在另一个工具管理的环境中静默替换二进制依赖。参见 Conda 的[环境管理与锁文件文档](https://docs.conda.io/projects/conda/en/stable/user-guide/tasks/manage-environments.html)。

## 6. 安全迁移流程：平行创建，验证后切换

迁移不是把旧环境原地“升级”成新工具。原环境可能正被 notebook、服务或编辑器使用；原地修改难以比较，也难以回退。采用下面的可逆流程：

1. **界定对象与冻结变更。** 记录项目目录、目标平台、当前解释器、直接依赖、lockfile/环境文件、CI 命令、私有索引配置的“存在与来源”（不记录 token）。不要把 `.venv/`、`env/`、Conda `base` 当成迁移对象。
2. **先做可恢复快照。** 确认依赖声明、锁定文件、脚本和测试都已在版本控制中；复制必要的非机密配置说明。不要把凭据写进 `requirements`、`environment.yml` 或提交记录。
3. **在平行位置创建目标环境。** 例如新建 `.venv-migrate`、一个新的 Conda 环境名，或一个新的 uv 项目环境；绝不覆盖旧 `.venv` 或正在服务中的环境。
4. **从声明重新解析，并生成目标工具的锁定产物。** 不要从旧环境随手 `freeze` 后直接当作永久规范；先移除偶然安装项，确认直接依赖和 Python 版本的意图。
5. **验证三层事实。** 检查解释器路径与版本；运行依赖一致性检查；在干净目标环境运行测试、最小启动命令和必要的安全/许可检查。数据科学项目还要打开一个最小 notebook 或执行一段关键计算。
6. **双轨观察后切换。** CI 先使用新环境；生产服务先在可控的测试/预发布环境验证，再按现有发布流程切换。保留旧环境、旧 lockfile 和旧启动方式，直到恢复窗口结束。
7. **明确回退与清理。** 失败时把 CI/服务指回原锁定文件和原环境，不要试图临场修补新环境。确认不再需要后，再按团队保留策略删除旧的可再生环境目录或 Conda environment；不要删除系统 Python、Conda `base` 或全局工具。

### 迁移前后最小核验

```bash
# 在目标项目环境中
python -c "import sys; print(sys.executable); print(sys.version)"
python -m pip check                 # pip 路线适用
python -m pytest                     # 用项目实际测试命令替换
python -c "import your_package"     # 用项目真实入口替换
```

“安装命令退出码为 0”只说明求解器完成了一次安装；不等于环境中的原生依赖、数据库驱动、GPU、证书、私有源权限或业务行为都正确。

## 7. 练习：为一个 API 小项目做选择并锁定

假设你要维护一个带测试的 JSON API 小项目：它使用 `httpx`、没有 CUDA/Fortran/系统运行时依赖，团队希望在本地和 CI 使用同一命令。

1. 写下你的选择：`pip + venv` 或 `uv`，并用本课的选择树说明理由。
2. 建立一个全新项目环境；不要复用系统 Python 的 site-packages。
3. 加入一个直接依赖和一个测试工具，写出声明与锁定产物应放在哪里。
4. 在删除并重建环境后，运行依赖检查和测试；记录解释器路径。
5. 写下回退动作：若新锁定失败，CI 应使用哪个已验证的文件/命令。

### 成功标准

- 你能指出包管理、环境管理、项目管理、解释器管理和工具安装分别由什么负责；
- 项目依赖没有安装进系统 Python 或全局 Conda `base`；
- 仓库提交了可审查的声明与锁定产物，但没有提交 `.venv/`；
- 从空环境重建后，解释器路径、依赖检查和测试都符合预期；
- 迁移计划包含平行环境、验证点与明确的回退路径。
