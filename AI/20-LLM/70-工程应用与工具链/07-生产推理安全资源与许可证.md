# 生产推理：安全、资源与许可证

<!-- deep-review-02 -->
> [!tip] 本轮深化：从当前概念继续追问
> 系统安全由权限、隔离、资源限制与审计共同构成，模型拒答只是一层。许可、数据使用和威胁模型要按实际部署单独核验。 深化与验证：[[AI/20-LLM/70-工程应用与工具链/09-Agent状态机幂等执行与提示注入边界|Agent状态机幂等执行与提示注入边界]]；[[AI/20-LLM/80-研究拓展/04-隐私记忆成员推断与机器遗忘|隐私记忆成员推断与机器遗忘]]。


## 目标与边界

“生产”不等于“公网”。一个只供本机或受控 LAN 客户端访问的私有推理服务，只要承担真实工作负载，就需要预算、过载保护、契约、可观测性、数据保留、供应链和许可证边界。本页不提供公网暴露路线，也不将任何框架的官方性能图当成本机证据。

## 先定义服务契约

一次请求至少应有以下受控字段：

```text
request_id: 由服务端或可信网关生成的关联 ID
model_id: 精确模型和可复现 revision，不接受模糊别名
input: 符合大小、类型和内容策略的输入
max_input_tokens: 服务端上限
max_output_tokens: 服务端上限
deadline: 端到端截止时间
output_schema: 允许的结构和版本
```

客户端给出的上限只能比服务端策略更严，不能放大服务端上限。Schema 能约束形状，却不保证事实正确、来源充足或内容可以被业务执行；详见 [[AI/20-LLM/70-工程应用与工具链/03-结构化输出Schema与错误恢复|结构化输出、Schema 与错误恢复]]。

## 资源预算不是一个“显存数字”

推理的粗略显存组成可写成：

$$
M_{\text{VRAM}} \approx M_{\text{weights}} + M_{\text{KV}} + M_{\text{workspace}} + M_{\text{runtime overhead}}
$$

其中权重受参数量与数值格式影响；KV cache 随并发序列、已处理 token 和精度增长；workspace 受引擎、算子、batching 和图捕获等影响。这只是预算结构，不是对某模型的实测值。

| 资源 | 上限与观测 | 耗尽时的行为 |
| --- | --- | --- |
| GPU 显存 | 权重、KV、workspace；峰值与 OOM 数 | 拒绝新请求或降低已批准的并发，不无限重试 |
| 系统内存 | tokenizer、页锁定缓冲、offload、服务进程 | 保护宿主，避免 swap 抖动与系统级 OOM |
| CPU | tokenization、调度、反序列化、非 GPU 算子 | 排队或快速失败，不让健康检查饿饿 |
| 磁盘 | 权重、缓存、日志、会话/批处理输出 | 停止产生新输出，不覆盖唯一可恢复产物 |
| 网络 | 请求/响应字节、连接数；默认只 loopback | 按身份限流和断开超时连接 |
| 时间/成本 | 排队、prefill、首 token、decode、总时间 | 超过 deadline 停止生成，不在后台无限继续 |

在真实硬件上调整前，先读 [[AI/20-LLM/40-推理/00-LLM推理-MOC|LLM 推理 MOC]] 理解 prefill、decode、KV cache 和调度，再用 [[AI/20-LLM/40-推理/05-推理引擎与服务选择|推理引擎与服务选择]] 区分引擎职责与部署取舍；不把官方文档的示例性能当成本机证据。

## 有界队列、限流与超时

无界队列会把过载从“快速拒绝”变成“长时间占用内存，最后集体超时”。一个最小策略应包含：

1. **入口验证**：在进队前限制 body、输入 token、输出 token、模型和 schema。
2. **入场控制**：估算该请求的 KV/时间成本，只在预算容许时接受。
3. **有界队列**：限制等待项数与等待时间；保存必要身份和截止时间，不保存不必要原文。
4. **分层限流**：按身份、模型、并发、token/时间窗口和长任务份额限制，避免单个客户端占满服务。
5. **端到端 deadline**：队列等待、prefill 和 decode 共享同一截止时间；不要每层重新起算。
6. **过载拒绝**：返回结构化、可分类的“稍后重试/超出配额”，不让客户端立即风暴式重试。

超时发生后，应取消排队或生成工作，释放 KV 和关联资源，记录阶段化错误，而不是只断开客户端连接。

## Schema、输出校验与工具边界

生产推理的服务端响应应有版本化 schema，并区分：

- 语法可解析；
- schema 验证通过；
- 业务约束通过；
- 来源/事实可验证；
- 允许执行外部动作。

前四项都不自动提供第五项授权。若响应可进入 Agent 工具，必须经过 [[AI/20-LLM/70-工程应用与工具链/06-Agent工具调用状态与最小循环|Agent 工具调用、状态与最小循环]] 中的独立输入验证、权限和终止门禁。

## 可观测性：观察行为，不默认录入内容

建议保留的低敏感信号：

- 请求/追踪 ID、模型 revision、服务版本和 schema 版本；
- 排队时间、prefill 时间、首 token 时间、decode 时间和总时间；
- 输入/输出 token 数、结束原因、限流、超时、取消与 OOM 分类；
- 队列深度、活跃序列、资源高水位和健康状态；
- 认证结果与授权类别，但不记凭据本身。

默认不记录完整提示词、生成文、检索文档原文、Authorization 头、cookie、凭据或本机全路径。调试采样需要独立授权、脱敏、最短保留期和到期删除验证。如何将这些信号变成回归见 [[AI/20-LLM/70-工程应用与工具链/04-评测回归与可观测性|评测、回归与可观测性]]。

## 数据保留与资产隔离

| 资产 | 保存理由 | 隔离与删除要求 |
| --- | --- | --- |
| 原始权重 | 可复现推理 | 只读；按模型许可控制访问；不进镜像和 Git |
| 量化/转换权重 | 实际部署产物 | 与原始权重分开，记录转换链、哈希与派生权重许可 |
| 下载/编译缓存 | 加速重建 | 独立、定容、可全删；不与唯一权重副本混放 |
| 请求与生成输出 | 只在业务确有需要时 | 按用户/项目隔离，最短保留，可定向删除 |
| 评测产物 | 发布门禁和回归 | 与生产输出分开，标记数据版本和许可 |
| 凭据/证书私钥 | 认证和 TLS | 只经密钥机制注入，可轮换；不进输出、日志、缓存或镜像 |

数据“默认不保留”也需要证据：队列、错误追踪、备份、崩溃转储和临时目录都可能留下副本。

## 供应链边界

生产不应直接依赖漂移的 `latest` 或模型主分支。最小账本包含：

| 对象 | 固定与核验 | 还不能推出 |
| --- | --- | --- |
| 模型/权重 | 官方发布者、精确仓库、revision、文件哈希、模型卡、tokenizer/模板 | 无后门、适合任务、许可所有用途 |
| 服务代码 | 发行版/提交、锁文件、审查配置 | 无漏洞或安全默认不会改变 |
| 容器镜像 | 发布者、不可变摘要、基础镜像、组件清单与更新责任 | 容器隔离了宿主驱动、挂载、网络和凭据 |
| 依赖/二进制 | 固定版本、来源与哈希/签名；定期漏洞复核 | 与 GPU 驱动、Toolkit、内核必然兼容 |
| 远程代码/自定义模型实现 | 先在无凭据、无个人数据的隔离环境审查 | 只因为来自模型 Hub 就可安全执行 |

实施前应刷新 [[AI/90-资源/05-官方资料与版本核验记录|官方资料与版本核验记录]]；该账本已核验至 2026-09-01，但工具支持矩阵、镜像、默认监听、驱动组合和许可可能继续变化。

## 许可证是三份记录，不是一个“开源”复选框

| 记录 | 至少包含 | 典型独立问题 |
| --- | --- | --- |
| 模型/权重许可 | 精确模型及 revision、许可文本版本、可接受使用策略、商用/再分发/派生条件 | 转换、量化或编辑后的派生权重能否分发？ |
| 数据许可与权利 | 数据来源、许可/同意、用途、个人数据、删除与再分发 | 训练、RAG、评测、调试日志是否都被允许？ |
| 工具/代码许可 | 服务器、框架、容器、依赖的许可及通知/源码/网络服务义务 | 内部修改、分发或网络提供服务时触发什么义务？ |

一份许可不会传染给其他对象。例如 Heretic 工具代码的许可，不会自动授予输入基座权重、修改后权重或评测数据的再分发权。这类模型编辑还会改变安全性质，须单独审计，见 [[AI/20-LLM/30-训练/07-模型对齐拒答方向与Heretic|模型对齐、拒答方向与 Heretic]]。本页不是法律意见。

## 容器、Ubuntu native 与 Arch native

容器优先用于固定服务用户空间和构建物：使用不可变镜像摘要、非 root 进程、只读根文件系统（若应用支持）、精确挂载和明确资源上限。不挂载容器管理 socket、整个家目录或不相关凭据，默认不发布端口。

- Ubuntu native：系统层使用 APT 和明确支持周期，适合需要较稳定系统组合的主机；不要为了项目依赖随意替换系统 Python 或驱动。
- Arch native：内核、驱动、CUDA 相关用户空间和包管理处在滚动更新边界；升级前要有快照/回退点和兼容性冒烟，不做 partial upgrade。

两种 native 都必须理解宿主职责：[[计算机知识/20-操作系统/01-Linux/02-启动链Kernel与systemd|Kernel/systemd]]、[[计算机知识/20-操作系统/01-Linux/09-设备驱动内核模块与udev|驱动/内核模块]]、[[计算机知识/20-操作系统/01-Linux/07-环境变量Shell启动与PATH|环境变量/PATH]]以及 [[计算机知识/20-操作系统/01-Linux/10-网络存储日志与故障排查|网络/存储/日志]]。GPU 容器仍使用宿主驱动能力，兼容边界见 [[计算机知识/40-并行与异构计算/01-CUDA/00-CUDA-MOC|CUDA MOC]]。

## 发布前 Go / No-Go 门禁

| 门禁 | Go 证据 | No-Go 条件 |
| --- | --- | --- |
| 正确性 | 固定模型/schema 的正常、边界、敌对和回归用例通过 | 只有一次成功请求 |
| 容量 | 在有限并发下测得延迟、显存、队列与拒绝行为 | 照抄官方基准图 |
| 过载 | 队列有界，限流/超时/取消会释放资源 | 请求可无限排队或生成 |
| 隐私 | 日志字段清单、保留期、删除验证和访问主体已审阅 | 默认记录提示词或凭据 |
| 供应链 | 权重、代码、镜像、依赖和驱动组合均可追溯 | 依赖 `latest`/未固定主分支 |
| 许可 | 模型、数据、工具三份记录都符合当前用途 | 用“开源”两字代替条款 |
| 网络 | 默认 loopback；若经审批的 LAN，完整通过认证/TLS/防火墙/日志/停止门禁 | 无认证、空凭据、模糊监听或无恢复方案 |

网络门禁详见 [[AI/20-LLM/70-工程应用与工具链/05-私有部署认证TLS与边界|私有部署、认证、TLS 与边界]]。任何 No-Go 项存在时，保持未启动或仅在无敏感数据的 loopback 隔离环境内继续评测。

## 练习：做一次纸面容量与许可评审

不启动模型、不下载权重、不打开端口。为“一个已获许可的本地模型，最多两个本机客户端”写一页发布卡：

1. 写出 GPU/内存/磁盘/CPU/时间预算中需要实测的量，不填猜测数字。
2. 设计有界队列、每身份并发、输入/输出 token、端到端 deadline 和过载拒绝行为。
3. 列出响应 schema 及两个“形状正确但业务错误”的反例。
4. 列出允许的低敏感指标，明确禁止记录的原文与凭据。
5. 分开填写模型许可、数据许可/权利和工具许可，均记录核验日期。
6. 按 Go / No-Go 表得出“仍不可发布”或“可进入 loopback 冒烟”，不得推导到公网部署。

## 成功标准

- 能解释权重、KV cache、workspace 和运行时开销为什么都要进入显存预算。
- 能设计有界队列、入场控制、限流、端到端超时和可分类过载拒绝。
- 能区分 schema 正确、业务正确、事实正确和外部动作授权。
- 能证明权重、缓存、输出、日志和凭据分离，并说明保留与删除证据。
- 能分别展示模型、数据、工具的许可记录和可追溯供应链。

## 恢复方法

本页练习不会启动服务。真实服务若出现队列无界、OOM、超时后仍运算、原文日志或许可不明，将发布状态立即降为 No-Go，停止入场，让在途请求在截止时间内结束或取消，回到上一个已固定的镜像与模型 revision。如疑似凭据或数据进入日志，停止日志扩散，轮换凭据，按保留图定向删除副本并保留不含敏感原文的审计证据。
