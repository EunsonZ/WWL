# 07 · Unicode 与引擎差异

## 本课目标

理解“字符”在不同引擎中可能指代码单元、码点或更复杂的用户可见字素，并能系统检查字符类、标志、换行和高级语法的兼容性。

## 先观察，再给概念命名

请先预测下面的模式分别能否完整匹配每个输入，再到 [[编程知识/30-实践/01-正则表达式实验区/04-5分钟运行与测试模板|自己的运行环境]] 实测：

```regex
^.$
^..$
```

| 输入 | 肉眼看到 | 需要观察的问题 |
| --- | ---: | --- |
| `中` | 1 个字符 | 一个中文码点是否被点号消费一次？ |
| `🙂` | 1 个 emoji | JavaScript 有无 `u` / `v` 时结果是否相同？ |
| `é` | 1 个字符 | 这是预组合码点还是别的底层表示？ |
| `é` | 1 个字素 | `e` 与组合附加符号是否需要两个点号？ |

看到差异后，再用下面三层术语解释。正则里的“一个点号”不自动等于“用户看到的一个字符”。

## 用户看到的一个字符，底层不一定是一个单位

Unicode 文本至少涉及三个层次：

1. **代码单元**：某种编码实现中的存储单位，例如 UTF-16 的 16 位单元；
2. **码点**：Unicode 分配的编号，例如 `U+4E2D`；
3. **字素簇**：用户感知的一个字符，可能由多个码点组合而成，例如字母加组合附加符号，或由多个码点组成的 emoji。

正则中的点号、长度量词和字符类究竟跨过哪一层，取决于引擎及其 Unicode 模式。不要用 `^.$` 断言“正好一个用户可见字符”，除非已经验证目标引擎和目标文本集合。

### 文本编码、正则与 tokenization 是连续但不同的层

一次文本处理常经过这条链：**字节 → 按某种编码解码为字符串 → Unicode 规范化（可选）→ 正则或字符串 API 处理 → tokenizer 编成 token ID**。正则通常面对的是已经解码后的字符串；它不会替你判断原始字节是 UTF-8、GBK 还是损坏数据，也不会把字符串切成模型的 token。字节、代码单元、码点、字素簇与换行的权威入口是 [[计算机知识/60-数据编码与媒体系统/02-字符编码Unicode-UTF-8与换行|字符编码、Unicode、UTF-8 与换行]]；字符串匹配算法与正则引擎的责任边界见 [[计算机知识/50-数据结构与算法/13-字符串匹配前缀函数与自动机|字符串匹配、前缀函数与自动机]]。

例如，“一个 emoji”可能由多个 Unicode 码点组成，而 LLM tokenizer 可能把它编码成一个、多个或未知 token；反过来，一个 token 也不保证对应一个自然语言单词。完整的 token、词表、字节回退和特殊 token 语义见 [[AI/20-LLM/10-原理/01-文本Unicode-Token与词表|文本、Unicode、token 与词表]]。因此：

- 用正则检查日志或协议的**文本形状**时，先确认 I/O 解码和错误处理；Python 的文件 I/O 语义见 [[计算机知识/10-编程语言/01-Python/05-异常文件IO与上下文管理|异常、文件 I/O 与上下文管理]]；
- 用正则做自然语言切词时，不要把 `\\b` 当作分词器，更不要把匹配结果当作 LLM token 序列；
- 是否进行 NFC/NFKC 等规范化是业务决策：它可能帮助比较等价文本，也可能改变密码、标识符或原始证据的语义；先保留原文、记录规则并测试。

## `\d`、`\w` 与 `\b` 不是全球统一定义

- Python 3 的 `re` 在普通 Unicode 字符串中，`\d`、`\w` 等通常采用 Unicode 感知语义；使用 `re.ASCII` 会缩小到 ASCII；
- JavaScript 的 `\d` 仍主要表示 ASCII 数字，`\w` 也不是通用的“所有语言文字”；
- PCRE2、Java、.NET、编辑器与命令行工具各有默认值和标志；
- `\b` 依赖引擎对 `\w` 的定义，因此对中文自然语言分词通常并不可靠。

若协议明确要求 ASCII，应直接写 `[0-9]`、`[A-Za-z]`，并避免无意叠加会扩大 Unicode 大小写折叠的 `i` / `IGNORECASE` 标志。若需求是真正的 Unicode 字母类别，则应查目标引擎是否支持 Unicode 属性。

## Unicode 属性转义

支持相应能力的 JavaScript 环境可以在 `u` 模式中使用：

```regex
\p{Letter}+
```

JavaScript 字面量示意：

```javascript
const words = text.match(/\p{Letter}+/gu);
```

PCRE2、Java、.NET 等引擎也常支持 `\p{...}`，但属性名和启用方式可能不同。Python 标准库 `re` 不支持通用的 `\p{...}` 写法；不要因为在某个在线测试器里成功，就假设复制到 Python 仍能工作。

## 标志（flags）的名称与传递方式

| 意图 | Python `re` | JavaScript | 需要确认的边界 |
| --- | --- | --- | --- |
| 忽略大小写 | `re.IGNORECASE` | `i` | Unicode 大小写折叠并非所有语言都直观 |
| 多行锚点 | `re.MULTILINE` | `m` | 改变 `^`、`$`，不改变点号 |
| 点号匹配换行 | `re.DOTALL` | `s` | 改变 `.`，不等于多行锚点 |
| 全部查找 | `findall` / `finditer` | `g` | Python 通过 API，JavaScript 常通过标志 |
| Unicode 相关语义 | Python 3 `str` 默认使用 Unicode；可用 `re.ASCII` 收窄部分字符类 | `u` 影响码点与 Unicode 转义，`v` 进一步扩展 Unicode 集合能力 | 具体行为仍依引擎与版本 |
| 扩展/注释模式 | `re.VERBOSE` | 无直接同等内建标志 | 常需拆分字符串或使用辅助库 |

`m` 与 `s` 经常被混淆：前者改变锚点，后者改变点号。

## 换行并不只有 `\n`

文本可能使用：

- LF：`\n`；
- CRLF：`\r\n`；
- 旧式 CR：`\r`；
- 其他 Unicode 行分隔符。

若处理跨平台纯文本，显式使用 `\r?\n` 可以覆盖常见 LF/CRLF；若使用语言提供的逐行 API，往往比正则自行拆分更稳妥。

下面的模式在多行模式下匹配以 `ERROR` 开头的行：

```regex
^ERROR\b.*$
```

但点号是否包含 `\r`、`$` 是否停在换行前、返回内容是否带行尾，仍需要用真实 CRLF 与 LF 样本测试。

## 常见引擎能力对照

| 能力 | Python `re` | 现代 JavaScript | RE2 类引擎 |
| --- | --- | --- | --- |
| 捕获组、非捕获组 | 支持 | 支持 | 支持 |
| 命名组 | `(?P<name>...)` | `(?<name>...)` | 依绑定与版本 |
| 反向引用 | 支持 | 支持 | 通常不支持 |
| 先行断言 | 支持 | 支持 | 通常不支持 |
| 后行断言 | 支持，常要求固定长度 | 现代环境支持 | 通常不支持 |
| 原子组 | 新版 Python 支持，需核对版本 | 通常无直接语法 | 不需要同类回溯控制 |
| Unicode 属性 | 标准 `re` 不支持 `\p{...}` | Unicode 感知模式中支持，具体用 `u` 或 `v` 需核对语法 | 依实现 |

这张表用于提醒“必须现场核对”，不是永久版本承诺。

## 可移植策略

1. 先确定运行环境与版本；
2. 尽量使用字面字符、字符类、有限量词、非捕获组和锚点等共同子集；
3. 把命名组、替换模板、Unicode 属性、环视单独列为方言层；
4. 为每个实际目标引擎运行同一组正例和反例；
5. 不把在线测试器的默认引擎当成生产环境。

## 运行两条可复现的差异断言

课程中的表格是趋势说明；真正的兼容性结论必须由目标运行时给出。实验区提供了两份零依赖脚本：

- [[编程知识/30-实践/01-正则表达式实验区/05-Python差异断言.py|Python 差异断言]]：验证 Python `re` 对 Unicode `\\w`、`\\d`、点号、命名组、替换与 NFC 的当前行为；
- [[编程知识/30-实践/01-正则表达式实验区/06-JavaScript差异断言.js|JavaScript 差异断言]]：验证 Node.js 中 ASCII 风格 `\\w`、`\\d`、`u` 标志、命名组、替换与 `g` 的 `lastIndex` 状态。

两者通过各自的断言只能证明“当前解释器的这组样本符合预期”；不能证明其他浏览器、编辑器、grep 方言或线上服务完全相同。

## 练习

### 实验 1 · 字符类

用目标环境分别测试下面六个输入：

```text
hello_42
中文
１２３
café
🙂
é
```

对比这三个模式的结果：

```regex
^\w+$
^[A-Za-z0-9_]+$
^\d+$
```

### 实验 2 · 点号、码点与字素

对 `中`、`🙂`、预组合的 `é` 和由 `e` + 组合附加符号构成的 `é` 测试 `^.$` 与 `^..$`。JavaScript 分别记录无 Unicode 标志与 `u` 或 `v` 的结果；Python 记录默认 `str` 结果。

再使用语言自带的 NFC 规范化功能，把 `é` 与 `é` 规范化后比较。规范化是独立的数据处理步骤，不是正则语法；不要在未了解业务语义时擅自改写用户文本。需要按“用户可见字素”切分时，应使用目标平台的 Unicode / 字素 API。

> [!example] 本例的已测参考答案
> 下表记录 Python `3.14.7` 和 Node.js `26.8.1` 的独立实测结果，只覆盖本节的四个输入与两个模式，不构成其他版本、浏览器、编辑器或 Unicode 字素 API 的永久保证。`T / F` 表示模式 `^.$` / `^..$` 是否完整匹配。

| 比较项 | 预组合 `é` | 分解 `é` |
| --- | --- | --- |
| 码点序列 | `U+00E9` | `U+0065 U+0301` |
| UTF-8 字节数 | 2 | 3 |
| 码点数 | 1 | 2 |
| UTF-16 码元数 | 1 | 2 |
| 通常呈现的字素数 | 1 | 1 |

将两种表示规范化为 NFC 后，结果都是 `U+00E9`；规范化为 NFD 后，结果都是 `U+0065 U+0301`。两者通常都显示为一个字素，但点号不保证按字素消费。

| 输入 | Python `re` | JS 无 `u` | JS `u` / `v` |
| --- | --- | --- | --- |
| `中` | T / F | T / F | T / F |
| `🙂` | T / F | F / T | T / F |
| NFC `é` | T / F | T / F | T / F |
| NFD `é` | F / T | F / T | F / T |

这组结果说明两件不同的事：无 `u` 的 JavaScript 会将 `🙂` 按两个 UTF-16 码元处理；而分解的 `é` 即使在 Python 和带 `u` / `v` 的 JavaScript 中也有两个码点，因此需要两个点号。NFC/NFD 是否应在实际数据处理中统一，仍取决于业务语义。

记录语言、运行时版本、标志、匹配结果和规范化前后差异。不要先猜，用实际输出完成 [[编程知识/30-实践/01-正则表达式实验区/02-练习场#练习 7 · Unicode 对照|练习场]]。

## 成功标准

- 我能区分代码单元、码点和用户可见字素。
- 我不会把 `\w` 直接解释成“所有语言中的单词字符”。
- 我能解释 `m` 与 `s` 分别改变什么。
- 复制高级语法前，我会核对目标引擎、版本、标志与替换语法。
- 我能运行至少一份差异断言，并把实际解释器版本与输出记入练习；需要跨 Python 与 JavaScript 部署时，我会分别运行两份。
