# 数字视频：帧率、扫描、色彩采样与时间基

视频不是“每秒固定张数的图片文件夹”。它至少同时包含空间采样、色彩表示和时间轴；任一层的元数据被忽略，都可能出现比例错误、颜色错误、梳齿或不同步。

> [!info] 事实核验边界
> 本页的规范与工具事实按 FFmpeg、ISO、ITU 等一手资料核对至 **2026-09-03**。标准版本、播放器兼容性、硬件能力和命令输出字段会变化；涉及交付时，应以目标设备、实际文件和当前官方文档现场复核。

## 本课目标

学完后，你应能：

1. 区分帧、场、帧率、扫描方式、编码分辨率和显示比例；
2. 用 `DAR = 宽 / 高 × SAR` 解释“像素数量正确但画面被拉伸”；
3. 区分 RGB/YCbCr、位深、范围、色度采样与色彩元数据；
4. 把 time base、PTS、DTS、duration 换算为时间，并解释解码顺序为何可能不同于显示顺序；
5. 用分层证据诊断快慢播放、梳齿、偏色和时间戳异常。

> [!tip] 首读 20 分钟
> 先读帧/场、帧率、编码尺寸与 SAR/DAR，再掌握 `显示时间 = PTS × time_base`。能识别“帧号不是时间”后，二读再学隔行/field order、primaries/transfer/matrix/range、chroma location 与 PTS/DTS 重排。

## 1. 四层对象不要混在一起

```text
现实中的连续光与运动
  ↓ 相机的空间/时间采样
帧或场中的像素样本
  ↓ 色彩表示、位深与色度采样
Y/Cb/Cr 或 R/G/B 数值平面
  ↓ 编码、封装与时间戳
按时间轴播放的媒体样本
```

- **帧（frame）**：一个显示时刻的完整空间图像表示。
- **场（field）**：隔行扫描中只含奇数行或偶数行的一次时间采样。
- **编码图片（coded picture）**：编码语法中的图像单位；它与应用 API 返回的 frame 通常相关，但不能假设所有编码都一一对应。
- **codec**：规定 coded/encoded representation 与 decoded samples 之间的语法和处理；具体格式可以有损、无损，也可以是不压缩表示，不能仅凭 “codec” 一词推出“有损压缩”。
- **容器样本或 packet**：承载一段 coded payload，并附带 stream 归属、时间戳、duration、flags 等元数据；payload 未必经过压缩。它不等于已解码像素，也不必等于 IP 网络包。

“第 100 帧”只有在你同时知道从哪里计数、是否有丢帧/重复帧、是否为可变帧率时才有稳定含义。跨工具定位时优先使用时间戳，而不是裸帧号。

## 2. 帧率是时间采样，不是播放速度的唯一真相

帧率常写成有理数：

$$
f=\frac{N}{D}\ \text{frames/s}.
$$

例如 `24000/1001 ≈ 23.976`。保留分数可以避免把长时节目中的累计误差写进时间轴。理想恒定帧率（CFR）下，第 $i$ 帧的显示时刻可近似写为：

$$
t_i=t_0+\frac{i}{f}.
$$

但真实文件可能是可变帧率（VFR）：相邻帧间隔来自各自 PTS，不能用“总帧数 ÷ 标称 fps”还原每一帧时刻。

### 三个容易混淆的量

| 名称 | 回答的问题 | 不能单独证明什么 |
| --- | --- | --- |
| 捕获帧率 | 相机多久采一次运动？ | 文件最后如何定时播放 |
| 编码/流的平均帧率 | 一段时间平均有多少帧？ | 每个相邻 PTS 都相等 |
| 时间基与逐帧 PTS | 每个整数 timestamp 代表多久、帧何时显示？ | 像素内容是否真的来自那个捕获时刻 |

如果把 60 个不同捕获时刻的帧改为每秒 30 帧播放，而不丢帧，时长会翻倍并形成慢动作；若转成 30 fps 时丢掉一半帧，时长可以不变。两者都可被口语描述成“60 转 30”，结果却完全不同。

## 3. 逐行与隔行：一帧和一场不是同一时间单位

**逐行扫描（progressive）**的一个帧通常表示同一显示时刻的完整图像。**隔行扫描（interlaced）**把不同时间采到的两组交错行组合为一帧：

```text
场 A：第 0、2、4、… 行，采样于 t
场 B：第 1、3、5、… 行，采样于 t + Δt
```

运动物体在两场之间移动时，把两场当成同一时刻的逐行帧直接显示，会出现横向“梳齿”。字段还需说明哪一场先显示，例如 top-field-first 或 bottom-field-first；字段顺序写错会造成来回抖动。

去隔行不是简单删除一半行。它需要在空间分辨率、时间分辨率、插值和运动估计之间取舍：

- weave 合并两场，静止区域细节多，运动区域可能梳齿；
- bob 把每场扩展成一帧，保留场时间率，但需要补行；
- 运动自适应方法按区域选择，效果取决于检测与插值质量。

> [!warning] 数字值相同不代表语义相同
> `29.97 fps progressive`、`29.97 frames/s interlaced` 和 `59.94 fields/s` 可能被不同工具以不同字段呈现。诊断时同时记录帧率、场率、field order 和原始来源，不要只抄一个 `fps`。

## 4. 分辨率、SAR 与 DAR

“1920×1080”通常描述存储的亮度像素网格，不自动等于屏幕上的物理比例。

- **编码/存储分辨率**：像素样本网格的宽和高。
- **SAR（Sample Aspect Ratio）**：单个样本显示时的宽高比；有些工具沿用 Pixel Aspect Ratio 一词。
- **DAR（Display Aspect Ratio）**：整幅图像期望显示的宽高比。

在没有额外裁剪/旋转语义时：

$$
\mathrm{DAR}=\frac{W}{H}\times\mathrm{SAR}.
$$

### 可观察例子

存储分辨率为 `720×576`，若 SAR 为 `16:15`：

$$
\mathrm{DAR}=\frac{720}{576}\times\frac{16}{15}=\frac{4}{3}.
$$

若播放器错误地假设 SAR 为 `1:1`，它会按 $720/576=5/4$ 显示，人物就会变形。修正 SAR/DAR 元数据与真正重采样像素不是一回事：前者改变显示解释，后者会计算新的像素网格。

还要区分 coded size、裁剪后的可见区域、clean aperture、旋转矩阵和显示窗口。看到 `width`/`height` 时先问它来自解码器、容器还是渲染输出。

## 5. RGB、YCbCr 与“4:2:0”分别描述什么

RGB 直接表示红、绿、蓝分量。视频处理中常用 YCbCr：

- Y′ 是经非线性传递后的亮度相关分量，通常称 luma；
- Cb/Cr 是蓝差和红差色度分量；
- 从 R′G′B′ 到 Y′CbCr 的矩阵由色彩矩阵/系数约定决定。

这不是“把绿色通道改名为亮度”。从光到数字值还涉及 primaries、transfer、matrix 和 range；少一个环节，数值就不能唯一解释为显示颜色。

### 色度采样

`4:4:4`、`4:2:2`、`4:2:0` 描述亮度与两个色度平面的相对空间采样密度，而不是压缩算法名称：

| 采样 | 直觉 | 常见代价 |
| --- | --- | --- |
| 4:4:4 | 每个亮度位置都有对应色度采样 | 数据量最大，保留精细色边缘 |
| 4:2:2 | 水平方向色度采样减半 | 彩色细线的水平细节减少 |
| 4:2:0 | 水平和垂直方向的色度密度都降低 | 文本/UI/色键边缘更易出现色彩模糊 |

`4:2:0` 仍有多种 **chroma sample location**：色度样本相对于亮度网格在左侧、中心或其他位置。位置解释错误会让色边缘发生半像素级偏移。具体位置与扫描方式、编码规范和容器信令有关，不能仅靠字符串 `yuv420p` 推断全部语义。

### 位深不是色域

8-bit、10-bit 描述每个分量可编码的离散层级或格式宽度；更高位深可以减轻量化带状伪影并支持更精细的信号，但不自动表示更宽色域或 HDR。反过来，标记为 BT.2020 也不保证源内容真的使用了宽色域。

## 6. 颜色需要一组元数据共同解释

常见字段至少包括：

| 元数据 | 它定义什么 | 写错时的典型现象 |
| --- | --- | --- |
| color primaries | R/G/B 基色与白点 | 饱和色相与色域映射不对 |
| transfer characteristic | 线性光与编码信号值的关系 | 整体亮暗、对比度或 HDR 映射异常 |
| matrix coefficients / colorspace | R′G′B′ 与 Y′CbCr 的矩阵关系 | 肤色、饱和度和色相偏移 |
| color range | limited/tv 与 full/pc 等数值范围解释 | 黑位抬高、黑白截断或灰雾 |
| chroma location | 色度样本相对亮度网格的位置 | 彩色边缘错位 |

“BT.709 视频”在口语里常把多项字段压成一个词。严谨检查应逐项读取；缺失时播放器可能猜测，且不同播放器的猜测并不保证相同。

> [!warning] 标记和转换是两件事
> 只改元数据标签不会重算像素；真正把一种色彩表示转换到另一种，需要按源解释解码，再做矩阵/传递函数/色域/范围处理。若源标签本来错误，必须先用来源证据确认其真实含义，不能盲目“统一成 BT.709”。

## 7. time base、PTS、DTS 与 duration

媒体时间戳通常保存为整数，time base 决定一个 tick 多久：

$$
t=\mathrm{timestamp}\times\frac{num}{den}.
$$

若 time base 为 `1/90000`，PTS 为 `180000`，则显示时刻是 2 秒。使用整数加有理数能避免长期累积浮点误差。

- **PTS（Presentation Timestamp）**：解码后的样本何时呈现。
- **DTS（Decoding Timestamp）**：coded sample 按何顺序/时间送入解码过程。
- **duration**：该样本在相同或明确指定的时间基上持续多久；缺失时可能需从相邻时间戳或其他信令推断。
- **start time**：流或容器时间轴的起点，未必是 0，也未必所有轨道相同。

无帧重排时 PTS 和 DTS 常相同。存在引用未来画面的编码结构时，解码器必须先获得参考画面，再显示依赖它的画面，于是 DTS 顺序和 PTS 顺序可能不同：

```text
显示顺序（PTS）：I0  B1  B2  P3
一种解码顺序：  I0  P3  B1  B2
```

这个图只是说明“显示顺序可不同于解码顺序”，不是某个具体 codec 的完整语法。真实重排规则由编码格式和 bitstream 决定。

### time base 不等于 frame rate

time base `1/90000` 表示时间戳精度单位；若每帧 PTS 增量为 3003，则帧间隔为 `3003/90000 ≈ 0.03337 s`，约 29.97 fps。time base 可以比帧间隔细很多，也能同时表示 VFR 间隔。

## 8. 与视频 VLM 输入的边界

视频 VLM 常先按时间选帧，再把解码后的像素变成视觉 token。若预处理只按“每隔第 $n$ 帧”抽样，就可能在 VFR、丢帧或时间戳断点附近得到不均匀的真实时间间隔；忽略 SAR 会改变物体形状，忽略 range/primaries/transfer/matrix 会改变模型实际看到的数值分布，错误去隔行则会制造并不存在的梳齿纹理。

因此，可复现的视频模型输入至少要记录：源文件哈希、所选 track、目标 PTS 或时间区间、seek/RAP 策略、解码器与像素格式、缩放/裁剪/SAR 处理、颜色转换和最终张量 shape。解码帧只是经过采样、编码和预处理后的证据，不等于完整现实事件；模型也不能从缺失帧或已丢失色度中可靠恢复原始事实。多模态接口的数据流见 [[AI/20-LLM/20-架构/07-编码器解码器与多模态接口|编码器、解码器与多模态接口]]，任务与评测边界见 [[AI/30-VLM/00-VLM-MOC|VLM 第二阶段课程地图]]。

## 9. 用证据定位四类故障

下面的 FFmpeg/ffprobe 字段名按 2026-09-03 官方文档核验，但不同构建、容器和 codec 可能缺失字段。先复制样本到实验目录；下面只展示只读查询思路，不修改源文件。

```text
ffprobe -v error -show_entries \
  stream=index,codec_type,width,height,sample_aspect_ratio,display_aspect_ratio,avg_frame_rate,r_frame_rate,time_base,color_range,color_space,color_transfer,color_primaries,chroma_location,field_order \
  -of json INPUT

ffprobe -v error -select_streams v:0 -show_frames \
  -show_entries frame=pts,pts_time,pkt_dts,pkt_dts_time,duration_time,pict_type,interlaced_frame,top_field_first \
  -read_intervals "%+3" -of json INPUT
```

| 现象 | 先核对 | 不要立刻做 |
| --- | --- | --- |
| 人物被拉宽/压窄 | width/height、SAR、DAR、旋转/裁剪 | 直接重编码缩放，掩盖错误元数据 |
| 运动边缘有梳齿 | field order、逐行/隔行标志、逐帧内容 | 假设所有旧视频都是 top-field-first |
| 整体灰雾或黑白截断 | range、primaries、transfer、matrix 与来源 | 只改一个 `colorspace` 标签 |
| 快慢播放或卡顿 | time base、逐帧 PTS/duration、是否单调、VFR | 只看 `avg_frame_rate` 就重写时间戳 |

诊断时保存“原始字段 + 来源 + 播放器行为 + 预期”的最小证据包。播放器看起来正常，可能只是它做了兼容性猜测，并不能证明元数据正确。

## 练习

1. `1440×1080` 的视频标记 SAR=`4:3`。计算 DAR；若按方形像素显示会怎样？
2. time base=`1/90000`，连续三帧 PTS 为 `0, 3003, 6006`。计算前两段帧间隔和近似帧率。
3. 解释为何 `yuv420p10le` 只能告诉你一部分事实，不能单独证明视频是 HDR 或 BT.2020。
4. 一个文件显示顺序为 `I0 B1 B2 P3`，为什么解码器可能先处理 `P3`？PTS 和 DTS 分别服务哪条顺序？
5. 为“画面偏灰且人物被拉宽”写一份分层检查清单，要求在任何转换前至少收集五个字段。

## 成功标准

- [ ] 得到 DAR=`16:9`，并能说明忽略 SAR 会错误显示为 `4:3`。
- [ ] 得到帧间隔 `3003/90000 ≈ 33.37 ms`、帧率约 `29.97 fps`。
- [ ] 能把位深、色度采样、primaries、transfer、matrix 和 range 分开说明。
- [ ] 能解释 PTS 控制呈现顺序，DTS 支持解码顺序，且二者不必相等。
- [ ] 排错方案先读取元数据和逐帧时间戳，不把重编码当作第一步。
