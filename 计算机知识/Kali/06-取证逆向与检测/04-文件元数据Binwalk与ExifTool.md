# 文件元数据Binwalk与ExifTool

**先修关系：** [[计算机知识/Kali/06-取证逆向与检测/01-取证流程镜像与时间线|取证流程镜像与时间线]]；[[计算机知识/Kali/01-系统与网络基础/04-Shell文件权限与文本处理|Shell文件权限与文本处理]]。

## 文件名、魔数和真实结构是三层证据

文件后缀只是名称；魔数是格式开头或其他位置的标识；完整解析才检查结构关系。`file` 给类型判断，`xxd` 显示原始字节，`strings` 提取可打印片段，ExifTool 解析多种元数据，Binwalk 寻找嵌入内容特征。一个工具的标签不是最终事实，尤其对故意构造或损坏的数据。[^s1][^s2]

使用本包的无害合成文件，先固定工作目录和输入摘要：

```bash
cd "$HOME/kali-lab/fixtures/files"
sha256sum positive.txt negative.txt
file positive.txt
xxd -g 1 -l 128 positive.txt
strings -a -n 4 positive.txt
exiftool positive.txt
```

文本文件没有相机 EXIF 数据很正常；ExifTool 仍可能显示文件层元数据，不能把未输出某字段解释为“从未有过”。输出中的文件修改时间与文件内部记录的拍摄时间也不是同一个对象。`strings` 命中一个域名，仅证明存在可打印片段，不证明文件曾联系它。

## Binwalk：签名候选不是解包成功保证

```bash
binwalk --version
binwalk --help
# own-firmware.bin 为你自有并获准分析的固件副本；未随包提供。
binwalk own-firmware.bin
```

Kali 当前文档与许多旧教程的 Python 版并非同一接口；不得照搬旧的提取参数。本页仅示范默认签名分析。自动提取可能调用外部程序、递归展开大量文件或遇到路径穿越与压缩炸弹，不能以“只是查看固件”为由在日常系统中开启全部提取功能。[^s1]

文件熵高可能来自压缩、加密或本来就接近随机的数据；它不是“恶意加密”的单一证据。熵低也不保证没有隐藏内容。若发现嵌入文件候选，记录偏移、类型、工具版本，并用对应格式解析器复核，不把签名命中率当作恢复成功率。

## 嵌套内容、候选偏移与实际解包分别意味着什么

Binwalk 上游把识别嵌入数据、提取和熵分析列为不同能力；应将其理解为不同分析阶段，而不是一次“扫描成功”同时证明三件事。签名命中回答某个位置与已知模式是否相容；结构解析回答长度、校验和或成员关系能否成立；提取回答工具能否产出派生对象。具体可用签名、提取器和依赖受版本影响，不能把 v2/v3 的选项和后端默认视为完全兼容。[^v5-binwalk]

原创例子：外层镜像在偏移 4096 出现压缩格式候选，解压后得到一个内层文件。内层文件的偏移 128 是**解压后对象的相对位置**，不可以直接用 $4096+128$ 宣称它在外层文件的位置。只有已知该层是无变换的直接切片时，加法才可能成立；压缩、加密和重排通常要求另一种映射，有时不存在单一逐字节映射。

这与 [[计算机知识/Kali/06-取证逆向与检测/02-SleuthKitAutopsy与文件恢复|逻辑文件恢复]] 的逻辑偏移/物理位置区别相同。证据记录应给每个派生对象独立身份，写清父对象、转换类型与失败边界，而不是只保存一个最终文件名。

## 补强：熵的数值是什么，为什么不等于加密识别器

把某一窗口中第 $b$ 个字节值的出现比例记为 $p_b$，常用的经验字节熵为

$$
\widehat H=-\sum_{b:p_b>0}p_b\log_2p_b.
$$

对数底为 2，单位是每个字节符号的 bit，范围为 0 到 8。全为同一字节的非空窗口得到 0；恰好包含 0 到 255 各一次的窗口得到 8。后者是完全可预测的人造序列，已经构成“高字节熵 ⇒ 不可预测或已加密”的反例。这里估计的是单字节频率分布，不是压缩器可利用的全部序列结构，更不是攻击者知识条件下的密码学不确定性。

窗口太短时，估计值受样本限制；不同窗口长度的曲线不能直接按同一阈值比较。压缩、编码、加密及混合格式可能产生相似的局部形态。高熵区间应成为进一步检查格式、边界和上下文的位置，而不是独立的恶意性判据。[[计算机知识/Kali/07-综合实验/13-实验J时间线与检测基率|实验 J]] 包含 0 与 8 的可手算边界以及空输入政策。

## 元数据修改与隐私

ExifTool 既能读取也能写入。调查工作中避免对原件执行赋值或删除元数据的参数。对外分享时可以在另建副本上做必要脱敏，但应记录加工关系，不把脱敏后的文件冒充原始证据。镜像、内存、照片、日志和压缩包可能藏有路径、设备标识、用户名和地理位置，归档前按白名单审查。[^s2]

## 元数据不等于独立于内容的可信旁证

把某字段解释为“软件写入的拍摄时间”，与把它解释为“事件真实发生时间”是不同命题。字段存在、格式合法、与其他字段一致，可以提高内部一致性，但都不能单独鉴别谁写入了它。同一文件中的三个字段可能由同一个程序复制，因此不能按三条独立证据重复加权。

这是一条证据独立性原则，适用于 ExifTool 展示的字段，也适用于多个安全工具引用同一漏洞数据库。遇到不一致，先区分字段语义、时区、有无再编码、父子对象和写入来源，再寻找真正外部的约束。工具能列出更多字段，不等于获得更多独立事实。自检：外层文件的修改时间与内层图片的 EXIF 时间不同，为什么不能仅凭不同就认定篡改？答案定位到本页的派生对象关系和 [[计算机知识/Kali/06-取证逆向与检测/01-取证流程镜像与时间线|时间模型]]。

## 补强：解析一个文件也是在运行解析器

“不执行样本”不等于“不执行任何接触样本的代码”。`file`、ExifTool、解压器、图像查看器都在解析受控输入之外的数据。处理陌生样本时，要控制解析器版本、资源预算、输出目录和网络能力，而不只是禁止双击样本。

格式审查先比较实际长度与声明长度，再检查嵌套、偏移、整数范围和输出规模。例如一个两字节头声明有 32 字节载荷，但文件总长只有 10 字节，缺少的是 24 字节，不应通过静默补零让解析“成功”。相反，总长超过头部加声明长度时，需要明确允许尾随数据还是拒绝。本包的 [[计算机知识/Kali/06-取证逆向与检测/09-模糊测试Sanitizer与崩溃归因|有界解析与模糊测试专题]] 采用拒绝策略，并保留合法零长度载荷这个反例，避免把“空载荷”与“空文件”混为一谈。

## 从观察到下一步

类型与文件名不一致时，先检查文件是否被误命名或局部截断；只有证据支持时才考虑伪装。可疑可执行内容先走 [[计算机知识/Kali/06-取证逆向与检测/05-GhidraRadare2与静态逆向|静态逆向]]，不要双击验证。规则化重复检测见 [[计算机知识/Kali/06-取证逆向与检测/07-YARA日志与检测规则|YARA]]；从已授权镜像恢复的片段再回到 [[计算机知识/Kali/06-取证逆向与检测/02-SleuthKitAutopsy与文件恢复|文件系统上下文]] 查来源。

> [!question] 自检
> 对同一文件连续运行 `file` 和 `strings` 都“正常”，能保证安全运行吗？不能。两个工具都不是对全部执行行为的证明；解析可疑输入本身也存在软件漏洞风险，应使用更新且隔离的分析环境。
