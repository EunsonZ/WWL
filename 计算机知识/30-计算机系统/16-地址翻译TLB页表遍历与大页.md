# 地址翻译、TLB、页表遍历与大页

## 本课目标

学完后，你应该能够：

- 沿一次 CPU load/store 解释虚拟地址怎样经过 TLB 与多级页表得到物理地址；
- 严格区分 **TLB miss、page-table walk 与 page fault**，不再把三者都叫“缺页”；
- 说明普通页与大页在 TLB reach、内存浪费、分配难度和观测上的权衡；
- 区分 CPU 进程页表、GPU 地址翻译与 IOMMU 的 I/O 地址域；
- 知道计时、fault 计数和页表统计分别能证明什么，不能把性能现象直接写成硬件事件。

> [!prerequisite] 前置知识
> 先完成 [[计算机知识/30-计算机系统/02-进程虚拟地址空间与内存映射|进程虚拟地址空间与内存映射]]。本页把“虚拟页映射到物理页”继续展开到硬件快路径、异常慢路径与设备地址域。

## 1. 一次访存先问“地址属于哪个翻译域”

CPU 指令中的地址通常是当前进程的虚拟地址。概念路径如下：

```text
CPU 虚拟地址 = 虚拟页号 + 页内偏移
        │
        ├─ TLB hit：得到缓存的翻译与权限信息 ─┐
        │
        └─ TLB miss：硬件或软件执行页表遍历
                      ├─ 找到有效叶子项 → 填充 TLB ─┤
                      └─ 映射无效或未就绪 → page fault 异常 → 内核处理
                                                   │
                    两条成功翻译路径都要检查本次访问权限
                      ├─ 权限允许 → 物理地址 = 物理页号 + 原页内偏移
                      └─ 权限不允许 → protection fault 异常 → 内核处理
```

这是一张通用图，不是任何 ISA 的固定微架构。页表层数、TLB 级数、页大小、权限位、硬件 page walker、walk cache 和异常编码都随 ISA、CPU 与操作系统变化。术语也有平台差异：文档可能把 translation fault、protection fault、minor/major fault 分成不同类别。

## 2. 三个事件必须分开

| 事件 | 发生在哪里 | 意味着什么 | 常见后续 |
| --- | --- | --- | --- |
| TLB miss | MMU 的地址翻译快取 | 当前 TLB 没有可用翻译；**不等于页面不在 RAM** | 查询页表或更专用的翻译缓存 |
| Page-table walk | 硬件/软件遍历页表层级 | 正在读取页表项以寻找翻译；**不必陷入内核** | 找到有效项后填充 TLB |
| Page fault / protection fault | CPU 产生同步异常并进入内核 | 映射尚未建立为可访问状态，或已有翻译但本次访问违反权限 | 分配/调入/CoW/更新映射，或向进程报告错误 |

### TLB miss 可以完全正常结束

若对应叶子页表项有效且物理页已驻留，page walker 读取页表项，TLB 被填充，指令重试。这里有额外延迟，却没有 page fault。遍历需要访问页表内存，但现代实现可能有多级 TLB、page-walk cache 或缓存中的页表项；不能用“页表有四层”就武断写成“每次 TLB miss 必然访问 DRAM 四次”。

### Page fault 也不等于磁盘 I/O

内核可能因为这些原因处理 fault：

- 匿名映射首次触碰，需要建立零页或新的私有页；
- 文件页已在页缓存，只需把它映射进当前进程；
- 写时复制需要为写者建立私有页；
- 页面确实要从文件或交换空间调入；
- 访问地址没有合法映射或违反读/写/执行权限。

Linux `ru_minflt` / `ru_majflt` 常分别称 minor/major faults，但具体计数口径应读本机文档。major 通常表示处理过程中需要 I/O 的一类 fault；它不是“更严重的程序错误”。反过来，权限错误或非法地址即使没有存储 I/O，也可能终止进程。

## 3. 多级页表怎样缩小稀疏地址空间的元数据

把虚拟页号分成若干索引段，就可以让高层页表只为实际使用的地址范围指向下层表：

```text
虚拟地址
┌────────┬────────┬────────┬────────┬──────────┐
│ L4索引 │ L3索引 │ L2索引 │ L1索引 │ 页内偏移 │
└────────┴────────┴────────┴────────┴──────────┘
     │        │        │        │
     ▼        ▼        ▼        ▼
  根表项 → 下级表 → 下级表 → 叶子 PTE → 物理页框
```

“四层”和这些位宽只是示意。x86-64 可有不同虚拟地址宽度与页表层数，Arm 的 granule 与层级选择也不同。应从目标 ISA、内核页大小和实际配置出发，不能把教学图当文件格式。

页表项除了物理页号，还通常参与读/写/执行、用户/特权、访问/脏状态、缓存属性等判断。操作系统维护虚拟内存区域和后备对象等更高层语义；硬件 PTE 不是完整的文件映射数据库。

## 4. TLB reach 与大页

若一个 TLB 能容纳 $N$ 个给定页大小的翻译，那么粗略的覆盖范围是：

```text
TLB reach ≈ TLB entries × page size
```

同样数量的条目，用更大的页可覆盖更大的连续区域，因此大工作集可能减少某些 TLB miss 与 page walk。但这只是潜在收益：TLB 往往按页大小分组或共享集合，层级、替换、访问模式和并发地址空间都会影响真实结果。

大页的成本也不能省略：

- **内部碎片：**只使用大页的一小部分，仍可能占据整个物理页粒度；
- **物理连续性与分配：**显式大页池、透明大页或启动期预留的策略不同，内存压力下可能分配失败或退回普通页；
- **首次触碰和清零：**建立更大物理页可能带来更集中的延迟；
- **CoW 与回收粒度：**更大粒度可能放大复制、拆分或回收成本；
- **观测歧义：**“申请了大页”不等于“本次映射实际由大页支撑”。

Linux Transparent Huge Pages、显式 hugetlb、macOS/Windows 的大页接口与权限模型都不同。课程不会要求修改 sysctl、huge-page pool 或系统安全策略。性能优化必须先确认实际页粒度与映射，再用可重复工作负载验证。

## 5. TLB shootdown：页表变化还要让其他执行单元忘掉旧翻译

多个逻辑 CPU 可能缓存同一地址空间的翻译。当内核撤销映射、收紧权限或复用物理页时，不能只改内存中的 PTE；还要使可能持有旧翻译的 TLB 条目失效。跨核心协调常称 TLB shootdown。

这说明频繁映射/取消映射、权限切换或大范围回收可能包含跨核心成本。但不能从一次延迟尖峰直接断言“发生了 shootdown”：需要内核 trace、计数器或更专门的系统证据，并核对事件语义与采样权限。

## 6. 进程切换、地址空间标识与虚拟化

进程切换会切换页表根或地址空间上下文。部分 ISA 支持 ASID/PCID 一类标识，使 TLB 能区分多个地址空间而不必每次全部清空；条目保留策略仍依实现和内核。

虚拟机还可能出现两阶段翻译：guest virtual → guest physical，再由宿主的二阶段页表翻译为 host physical。一次 guest TLB miss 的遍历成本可能涉及嵌套翻译与相应缓存。容器通常共享宿主内核，不等于硬件虚拟机的二阶段翻译，但 cgroup/cpuset 会改变进程可用资源与观测视角。

## 7. CPU、GPU 与 IOMMU 不是一张页表

```text
CPU load/store：进程虚拟地址 ──CPU MMU──> 主存物理地址

GPU 指令：GPU 虚拟地址 ──GPU MMU/驱动管理的页表──> 设备内存或可访问的系统内存

设备 DMA：IOVA/设备地址 ──IOMMU──> 主存物理地址
```

- **CPU 进程页表**隔离进程并实现主机虚拟内存；
- **GPU 地址翻译**属于设备/驱动上下文，可能涉及设备显存、共享虚拟内存、迁移与 page fault/replay；具体语义依 GPU 和运行时；
- **IOMMU**把设备可发出的 I/O 虚拟地址限制并翻译到允许的主存页，支持 DMA 隔离、虚拟机设备直通等；它不会把 CPU 指针自动变成任意设备都能访问的地址。

CUDA Unified Virtual Addressing、managed memory 或共享虚拟内存提供更统一的编程表面，也不代表只有一个硬件 TLB、一个页表或没有迁移成本。观察 `/sys/kernel/iommu_groups` 只证明 Linux 暴露了某些分组目录；它不能证明某次 DMA 实际怎样命中 IOTLB，更不能证明 GPU 页表状态。

## 8. 如何选择证据

| 想回答的问题 | 较接近的证据 | 仍不能推出 |
| --- | --- | --- |
| 进程发生了多少类 fault | OS 的进程累计 fault 计数/trace | 其中每次都由你的目标循环造成 |
| 工作集是否实际用大页 | 映射级页大小统计、内核映射信息 | 大页让业务一定更快 |
| TLB miss 是否是热点 | 支持且获准的 PMU/perf 事件，结合采样与工作负载 | 跨 CPU 型号事件完全同义 |
| 映射后 RSS 是否变化 | 同口径的 VIRT/RSS/PSS 时间序列 | 物理页归属、未来工作集或 GPU 显存 |
| IOMMU 是否暴露分组 | 只读 sysfs/平台设备管理信息 | 特定 DMA 的实时翻译路径 |

计时只证明某段程序在当前条件下用了多久；它不单独证明 TLB miss、page walk 或 page fault。反之，fault 数下降也不保证端到端延迟改善。

## 9. 只读观察与平台边界

配套实验 [[计算机知识/80-实践/06-计算机系统/06-地址翻译分配器与拓扑观察/README|地址翻译、分配器与拓扑观察]] 只创建最多 8 MiB 的匿名映射，读取自身 `/proc` 与 Linux sysfs；其他平台缺少相同接口时输出 `SKIP`。它不修改 affinity、NUMA policy、sysctl 或大页配置，也不声称观测到了 TLB miss。

若需要更深入的性能计数器或内核 trace，必须先确认权限、隐私、目标 PID、事件支持与采样开销。课程的默认完成不依赖这些能力。

## 练习

1. 画出以下三条不同路径：TLB hit；TLB miss 后 walk 成功；TLB miss 后触发按需匿名页 fault。标出哪条路径必然进入内核。
2. 假设某 TLB 对一种页大小有 512 个有效条目，分别计算 4 KiB 与 2 MiB 页的理想 reach；再写出至少三项让实际覆盖与收益偏离这个乘法的因素。
3. 为“文件映射首次扫描变慢”列出 TLB miss、缓存冷、minor fault、major fault、存储预取五个候选解释，并为每个解释选择更直接的证据。
4. 画出网卡 DMA 的 CPU 虚拟地址、IOVA 与主存物理地址，说明为什么驱动必须建立映射，而不是把任意用户指针直接交给设备。

## 成功标准

- 能用一句话准确说明：TLB miss 可能只触发 page walk，并不必然 page fault；
- 能解释 minor/major fault 是 OS 处理路径分类，不是“轻微/严重程序 bug”；
- 能同时列出大页的 reach 收益与碎片、分配、CoW/回收成本；
- 不会把 CPU、GPU 与 IOMMU 翻译域合并成一张想象中的全局页表；
- 报告实验时区分“实际读到的 OS 快照”和“没有直接测得的硬件事件”。
