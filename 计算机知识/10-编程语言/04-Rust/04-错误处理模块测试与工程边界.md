# Rust：错误作为数据，测试作为契约证据

> 阅读定位：基础示例兼容 Rust 2021 edition；不把 edition 等同于编译器版本。返回 [[计算机知识/00-开始/课程地图/03-Rust-课程地图|Rust · 课程地图]]；全域入口 [[计算机知识/00-开始/全局导航/00-总学习地图|计算机知识库 · 总学习地图]]。

## 错误类型要保留可行动的信息

`Option<T>` 表示缺少值，不必然是失败。`Result<T,E>` 让错误保留类型与上下文，调用者可决定重试、向用户解释或终止。`?` 是沿返回类型传播失败的语法，不是把错误吞掉。过早把所有错误转成 String 会丢失结构，使调用者难以区别非法输入、暂时不可用和内部不变量损坏。

```rust
#[derive(Debug, PartialEq)]
enum InputError { NotInteger, OutOfRange }

fn parse_count(s: &str) -> Result<u32, InputError> {
    let n: u32 = s.parse().map_err(|_| InputError::NotInteger)?;
    if n > 1000 { return Err(InputError::OutOfRange); }
    Ok(n)
}
```

这里负数、溢出与语法错误被刻意归入 NotInteger，适合简单接口但精度有限；业务需要区分时应保留更细的解析错误。`unwrap()` 适合你已经证明条件成立的受控位置，不该成为所有外部输入失败的默认处理。

## panic 与清理

panic 常表示当前操作无法继续或程序逻辑出错，并不保证在所有构建策略中都进行栈展开。Rust 的内存安全不意味着程序不会 panic、不会泄漏、不会死锁。析构负责资源释放，但进程突然终止、强制退出等场景仍有边界；跨 FFI 边界的 unwinding 规则必须按 ABI 明确处理。

恢复错误时注意事务性：把一个对象改了一半再返回 Err，可能留下语义不一致的状态。可以先构造新状态并验证，再一次性交换；也可用守卫在失败时回滚。这个问题与 C++ 异常安全和数据库事务直接相连。

## 测试分层

单元测试靠近内部逻辑，集成测试只通过公开 API，文档测试让文档示例参与检查。常规例、边界例、故意错误例都需要。属性测试检查“不变量对很多生成输入成立”，差分测试与简单参考实现比较；二者不能替代证明，也受输入生成分布限制。

包管理需要区分依赖范围与实际解析版本、feature 合并与运行时开关、构建脚本与普通源代码。构建脚本和过程宏会在构建过程中执行代码，对不可信项目不能只因为后缀是 `.rs` 就认定它没有副作用。不要在不了解项目时运行任意下载脚本。

## 工程自检

一个库应回答：哪些类型稳定公开，错误怎样分类，是否创建线程或访问网络，调用是否阻塞，内存与输入长度上限是什么。练习把解析器做成库，二进制只负责 I/O。写出 0、1000、1001、空串、负数、尾随垃圾的预期结果，且不要让不同错误在测试中全部只被检查为“不是 Ok”。
