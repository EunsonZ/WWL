## 直觉：上线前的试题与上线后的信号回答不同问题

离线评测用冻结、可审阅的用例回答“这次改动是否使已知任务退化”；线上可观测性用聚合信号回答“当前系统在哪里慢、贵、错或被拒绝”。两者都需要版本和边界，谁也不能单独证明真实世界中的所有答案正确。

## 先拆开测：检索、生成、端到端

| 层 | 受测对象 | 典型指标 | 诊断价值 |
| --- | --- | --- | --- |
| 检索 | chunking、embedding、过滤、索引、重排 | Recall@k、MRR、nDCG、ACL 拒绝率 | gold 证据有没有进入候选；无法证明回答正确 |
| 生成 | 模型、chat template、prompt、采样、Schema | 任务正确性、依据充分性、引用精度、拒答/格式通过率 | 候选证据给定时能否正确使用；不能证明搜索没有遗漏 |
| 端到端 | 所有层和程序编排 | 场景成功率、人工审阅缺陷率、p50/p95 延迟、错误率 | 用户路径是否工作；需要下钻前两层定位根因 |

对 RAG，把 `gold_chunk_ids` 与 gold answer/判分规则分开保存。若 `gold` 从未出现在 top-k，主要是检索失败；若已召回但答案漏引或编造，主要是生成、prompt 或校验失败。评测统计、样本量和区间见 [[数学/30-概率与统计/05-统计估计置信度与模型评测|统计估计、置信度与模型评测]]；交叉熵/KL 的概念边界见 [[数学/50-信息论/01-熵交叉熵KL散度与互信息|熵、交叉熵、KL 散度与互信息]]。

## 一个可回归的离线工作流

1. **冻结代表集：** 按任务、语言、长度、风险和失败模式分层；剔除未获准的个人/生产敏感数据，并保留 source/标签/评审规则版本。
2. **锁定候选版本：** 模型 revision、tokenizer/template、prompt、embedding、chunk 配置、索引、Schema、评测脚本和运行环境逐项写入结果记录。
3. **运行并分层比较：** 新旧版本在同一用例和预算下比较；设定绝对阈值和回归阈值，不只看平均分掩盖长尾。
4. **审查差异：** 先看检索候选、再看最终输出和验证器决定；将错误归类为数据、权限、检索、生成、解析或基础设施。
5. **决定与恢复：** 不满足 gate 就停止发布，或用上一个已验证的模型/prompt/index/schema revision 回滚；保存失败摘要以便复现。

`02_最小RAG_Schema与评测.py` 内的 `evaluate` 是一个很小的示范：它对三条固定 query 计算 `retrieval_recall_at_2`、引用子集率和中位延迟。它不是通用 benchmark，尤其没有覆盖真实 embedding、并发、上下文截断、对抗输入或统计显著性。

## Trace、日志、延迟与 token 使用

每个请求使用随机 request/trace ID，并让检索、重排、LLM、校验和下游动作使用 span ID 关联。建议记录**最小必要元数据**：

| 信号 | 用来回答 | 隐私/安全边界 |
| --- | --- | --- |
| request/trace ID、部署版本、模型/索引/schema revision | 是哪次改动引起异常？ | 使用随机 ID；不要用邮箱、token 或原始用户 ID 充当 trace ID |
| 各 span 延迟（检索、LLM、校验）与 p50/p95/p99 | 慢发生在哪一层？ | 聚合时间与状态码，不默认记录 prompt/回答正文 |
| 输入/输出 token 计数、上下文截断、重试次数、队列长度 | 成本和容量为何变化？ | token 数不是内容本身，但结合时间/租户仍需访问控制和保留期 |
| 检索 chunk ID/索引版本、命中/空召回 | 召回为什么改变？ | ID 应可在权限受控系统中解析；日志不能反向泄漏文档内容 |
| 解析/Schema/业务错误码、拒绝原因类别 | 哪个保护层在阻止坏输出？ | 错误原因去敏；不写完整输入、凭据、支付/健康资料 |

LLM 供应商或本地运行时如何统计 token、缓存 token、工具调用 token 与计费均为**易变接口**，本页的核验基础日为 **2026-09-01**；真实接入必须在当天按照 [[AI/90-资源/05-官方资料与版本核验记录|官方资料账本]] 锁定运行时版本和字段语义。不要将“模型很快”当成端到端延迟：排队、检索、网络、校验和数据库也在用户等待路径上。

## 风险、告警与恢复

- **指标诱导：** 只优化平均 latency 可能通过删掉检索/缩短输出来伤害正确性；告警应同时看质量 gate、拒绝率、错误率和尾延迟。
- **评测泄漏：** 不把测试答案放进 prompt、向量库或训练数据；严格区分开发集、验证集、上线监测样本。
- **日志泄密：** 设置字段 allowlist、采样率、访问控制、保留期和删除流程；调试需要正文时使用获准的脱敏样本和短期隔离位置。
- **告警风暴：** 对错误率和 p95 用时间窗口、最低样本数和分级；告警附带版本/trace 聚合而非海量原文。
- **恢复：** 每次发布允许独立回退模型、prompt/template、embedding/index、Schema 或服务配置；回滚后重跑冻结用例，确认指标回到基线，而不是只看服务恢复 200。

## 练习与成功标准

为“依据公司政策回答退款问题”定义六条离线样本：至少一条空召回、一条过时文档、一条无权限文档、一条格式失败和两条正常检索。为每条标注 gold chunks、期望的生成/拒答条件和风险级别。成功标准是：你能从一次失败的 trace 判断它先发生在检索还是生成，报告 p95 与 token 用量但不暴露用户正文，并指明可回滚的精确 revision。
