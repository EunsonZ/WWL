# uv 项目依赖与工具管理

> [!note] 核对时点
> 本课的概念和命令已按 Astral uv 官方文档核对至 **2026-09-01**。uv 发展很快；默认项目模板、预览功能、命令选项和 CI Action 版本都可能改变。复制到长期项目或 CI 前，请再查 [uv 官方文档](https://docs.astral.sh/uv/)和[CLI 参考](https://docs.astral.sh/uv/reference/cli/)。

## 本课目标

学完后，你应该能够：

1. 说清 uv 是什么，以及它不替代什么；
2. 区分 `uv venv`、`uv pip`、uv 项目命令和 `uv tool` 四条工作流；
3. 理解 `pyproject.toml`、`uv.lock`、`.venv` 各自记录什么；
4. 用 `uv add/remove/sync/run` 完成一个可恢复的最小项目实验；
5. 把同一份锁文件用在本地与 CI，而不在 CI 中悄悄重新解析依赖。

## 1. uv 是什么？

uv 是 Astral 用 Rust 实现的 Python 开发工具。它把原本常由多个工具承担的工作收拢在一个命令行程序中：

- 发现、下载和选择 Python 解释器；
- 创建虚拟环境；
- 用 pip 兼容接口安装或编译 requirements；
- 用 `pyproject.toml` 管理项目及依赖；
- 产生并同步 `uv.lock`；
- 隔离运行或安装 Ruff、Black 这类 Python CLI 工具；
- 管理单仓库内的多个 Python package（workspace）。

uv 不只是“更快的 pip”。`uv pip` 确实提供 pip 风格的环境操作，但 uv 项目工作流还会管理项目声明、锁定结果和项目环境。

### uv 不是什么

| 不是 | 原因 |
| --- | --- |
| Python 语言或解释器本身 | uv 可发现或下载 Python，真正执行 `.py` 的仍是 CPython、PyPy 等解释器。 |
| PyPI 这样的包索引 | uv 是客户端；包仍来自 PyPI 或你配置的索引、Git、URL、本地路径。 |
| 安全审计器 | 锁定版本不等于依赖无漏洞，也不证明包的供应链可信。 |
| Conda 的完整替代品 | uv 主要处理 Python 解释器、Python 包和工具；Conda 还能管理非 Python 库和更广的二进制环境。 |
| 自动容器或操作系统隔离 | `.venv` 只隔离 Python 包，不会隔离网络、文件系统、GPU 驱动或系统库。 |

## 2. uv 管理的 Python 与“非 uv 管理的 Python”

官方文档的术语是 **managed Python** 和 **system Python**：

- **uv-managed Python**：由 uv 下载和安装的 Python。可用 `uv python install 3.12`、`uv python list`、`uv python dir` 管理或定位。
- **system Python**：对 uv 而言，凡是不由 uv 安装的解释器都归入这一类。它可能来自操作系统、Homebrew、pyenv，甚至其他工具。“system”并不等于“操作系统自带”。

因此，常见的“managed / unmanaged”说法最好理解为“由 uv 管理 / 不由 uv 管理”；uv 官方把后者统称为 system Python。

```bash
uv python list --only-installed
uv python find
uv python pin 3.12
```

- `uv python pin 3.12` 会写入 `.python-version`，表达默认解释器请求。
- `pyproject.toml` 中的 `requires-python` 表达项目支持的 Python 范围。两者角色不同：例如项目可以支持 `>=3.11`，而团队本地默认使用 `3.12`。
- 大多数 uv 命令接受 `--python 3.12` 这类显式请求。
- 默认情况下，找不到合适的 Python 时 uv 可自动下载。需要禁止网络下载或必须使用现有 Python 时，查看 `--no-python-downloads` 和 `--no-managed-python`。
- `--managed-python` 表示只使用 uv-managed Python；`--no-managed-python` 表示排除 uv-managed Python。这两个名字不是“开启/关闭所有 Python 管理”的总开关。

> [!warning] 不要动系统 Python
> 不要用 `sudo pip install`，也不要手动删除 macOS、Linux 发行版或组织管理的 Python。uv 下载的 Python 可以由 uv 卸载；其他 Python 应交还给安装它的工具管理。

## 3. 四条工作流：不要混用概念

### 3.1 `uv venv`：只创建虚拟环境

```bash
uv venv --python 3.12
```

默认创建 `.venv`。它对应标准 `python -m venv .venv` 的职责：创建隔离的 Python 环境。它本身不会把项目依赖写入 `pyproject.toml`，也不会自动建立项目锁文件。

### 3.2 `uv pip`：pip 风格的环境接口

```bash
uv venv
uv pip install requests
uv pip freeze
```

`uv pip install`、`uv pip sync`、`uv pip compile` 适合保留 requirements 工作流、替换 pip/pip-tools 的执行层，或与只认 `requirements.txt` 的系统集成。它默认要求虚拟环境，而不会像 `uv add` 一样把直接依赖写进项目元数据。

> [!warning] 两种“sync”不是同一个入口
> `uv pip sync requirements.txt` 按 requirements 文件同步环境；`uv sync` 按当前 uv 项目的 `pyproject.toml` 与 `uv.lock` 同步。

### 3.3 uv project：声明、锁定、环境一起管

```bash
uv init --no-package demo
cd demo
uv add requests
uv run python -c "import requests; print(requests.__version__)"
```

项目工作流围绕 `pyproject.toml`、`uv.lock` 和项目 `.venv` 运作。优先用 `uv add` / `uv remove` 表达“这是项目依赖”，而不是先 `uv pip install` 再手工补文件。

### 3.4 `uv tool`：隔离的 Python 命令行工具

```bash
uvx ruff@latest --version
uv tool install ruff
uv tool list
uv tool uninstall ruff
```

- `uvx` 与 `uv tool run` 等价；工具环境被缓存，但可丢弃并自动重建。
- `uv tool install` 会把工具安装到独立环境，并把可执行文件链接到 uv 的工具 bin 目录；可用 `uv tool dir --bin` 查看该目录。只有该目录已在 `PATH` 中时，其他程序才能直接找到命令；若 uv 给出 `PATH` 警告，可审阅后运行 `uv tool update-shell` 并重开 shell。它更像 pipx。
- 临时检查优先 `uvx`；只有在其他程序也必须直接找到该命令时，才需要安装。
- 不要进入工具环境再用 pip 手动改包；用 `uv tool upgrade`、重装或卸载表达变更。

## 4. 项目的三份核心状态

```text
pyproject.toml  --解析/锁定-->  uv.lock  --同步-->  .venv
  意图与范围                   确切解析结果             本机可重建环境
```

### `pyproject.toml`：人维护的项目意图

`pyproject.toml` 是 Python 生态的标准项目配置文件，不是 uv 私有格式。一个简化例子：

```toml
[project]
name = "weather-note"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = [
  "httpx>=0.28,<1",
]

[dependency-groups]
dev = [
  "pytest>=8",
]
```

- `[project].dependencies` 是运行项目所需的直接依赖。
- `[dependency-groups].dev` 是开发依赖组；uv 默认同步 `dev` 组。
- `requires-python` 会影响解释器选择和依赖解析，应写真正支持的范围。
- 开发者可直接审阅此文件，但日常增删依赖优先用 `uv add` / `uv remove`，让元数据、锁文件和环境一起更新。

### `uv.lock`：uv 维护的确切解析结果

`uv.lock` 是人类可读的 TOML，但它由 uv 生成和管理，**不要手工编辑**。它是跨平台（universal）锁文件，可表示不同 Python、操作系统和架构的 marker 分支。

- 应将 `uv.lock` 和 `pyproject.toml` 一起提交到版本控制。
- 它是 uv 项目接口的特定格式，其他工具不一定能直接消费。需兼容下游时可了解 `uv export`。
- 它锁定解析结果，但不能让两个底层不兼容的操作系统变成相同，也不会锁定 GPU 驱动、系统库或未写入项目的外部服务。

### `.venv`：本机生成物

uv 项目默认在项目或 workspace 根目录下使用 `.venv`。它应被 Git 忽略，不应提交。当 `pyproject.toml` 和 `uv.lock` 健全时，`.venv` 应该能被删除后通过 `uv sync --locked` 重建。

## 5. 六个项目命令的职责

| 命令 | 主要效果 | 要记住的边界 |
| --- | --- | --- |
| `uv add httpx` | 向 `pyproject.toml` 添加直接依赖，同时更新 lock 和环境 | 包含 `<` / `>` 的版本约束在 shell 中要加引号，如 `uv add 'httpx>=0.28,<1'`。 |
| `uv add --dev pytest` | 加入 `dev` 依赖组 | 测试工具不必成为运行时依赖。 |
| `uv remove httpx` | 移除直接依赖并更新 lock 与环境 | 不要通过手删 `.venv` 中的包代替声明变更。 |
| `uv lock` | 创建或更新 `uv.lock` | `uv lock --check` 只检查锁文件是否最新；不安装环境。 |
| `uv sync` | 从 lock 安装到项目环境 | 默认是 exact sync，会移除 lock 中没有的额外包。不要指向一个存放其他工作的共享环境。 |
| `uv run <command>` | 在项目环境中运行命令；运行前自动 lock/sync | 默认是 inexact sync，不会清掉所有额外包。不要把它误当作“环境里绝对只有 lock 内容”的证明。 |

`uv run --locked ...` 会要求 lock 与项目元数据相符，不符就失败。`--frozen` 则使用现有 lock，不检查它是否过期。所以 CI 通常更适合 `--locked`；不要因为想“更严格”就盲目换成 `--frozen`。

## 6. 最小项目实践

> [!important] 实验边界
> 先用 `uv --version` 确认 uv 已安装。在一个可丢弃、不含个人数据的练习目录中执行；不要把 `uv-demo` 建在现有项目里，也不要对已有 `pyproject.toml` 的目录盲目运行 `uv init`。

### 第 1 步：创建可预期的练习项目

```bash
uv --version
uv init --no-package uv-demo
cd uv-demo
```

当前 uv 的 `uv init` 默认会创建带构建系统的应用项目；这是 0.12 之后需要注意的默认变化。本实验显式用 `--no-package`，生成更易观察的 `main.py` 项目。

### 第 2 步：添加运行与开发依赖

```bash
uv add 'rich>=13,<15'
uv add --dev pytest
```

观察：

1. `pyproject.toml` 出现 `rich` 与 `dev` 组的 `pytest`；
2. 项目根目录出现 `uv.lock`和 `.venv`；
3. `uv.lock` 中还有间接依赖，数量通常多于 `pyproject.toml` 的直接依赖。

### 第 3 步：在锁定环境中运行

```bash
uv run --locked python -c "from rich import print; print('[green]uv works[/green]')"
uv lock --check
```

预期看到彩色的 `uv works`，且 `uv lock --check` 成功退出。

### 第 4 步：练习可审阅的移除

```bash
uv remove rich
uv sync
uv lock --check
```

再检查 `pyproject.toml`：`rich` 已从直接依赖中移除，相关的不再需要的间接依赖也会从锁定和环境中消失。

### 成功标准

- [ ] 能指出 `pyproject.toml`、`uv.lock`、`.venv` 中哪两个应进入 Git，哪一个不应进入；
- [ ] `uv run --locked ...` 在移除 `rich` 之前成功；
- [ ] `uv lock --check` 成功，且检查过 `uv.lock` 没有手工编辑；
- [ ] 能解释为什么项目依赖用 `uv add rich`，而一次性执行工具用 `uvx ruff`；
- [ ] 能解释 `uv sync` 默认会移除 lock 外额外包，不会把它指向未确认的共享环境。

### 恢复与重置

1. **撤销某个依赖**：使用 `uv remove <包名>`，不要手动改 `.venv`。
2. **环境损坏或想验证可重建**：先确认 `pyproject.toml` 和 `uv.lock` 在版本控制中，然后将 `.venv` 移到废纸篓，运行 `uv sync --locked`。
3. **清理练习项目**：先 `cd ..` 离开项目，确认目标精确是练习用 `uv-demo`，再通过文件管理器移到废纸篓。不要复制范围不清的递归删除命令。
4. **清理缓存**：优先 `uv cache prune`；仅某个包异常时可用 `uv cache clean <包名>`。不要手动进入缓存目录删文件。

## 7. 缓存：加速层，不是项目真相来源

uv 会缓存下载、构建产物、Git 依赖等，并尽量把缓存中的文件高效链接到环境。

```bash
uv cache dir
uv cache prune
uv cache clean ruff
uv sync --refresh-package ruff
```

- 缓存应当可删可重建；项目意图仍来自 `pyproject.toml` 和 `uv.lock`。
- `uv cache prune` 会移除未使用的缓存条目；若启用了 `centralized-project-envs` 预览功能，还会移除可重建的集中式项目环境。它不会删除项目源码目录，官方认为可定期执行。
- 遇到缓存疑问时，通常先用 `--refresh` 或 `--refresh-package`，而不是一上来全部清空。
- `uvx` 的工具环境在缓存中，清掉后会重建；`uv tool install` 的持久工具环境不是同一类生命周期。

## 8. 与 pip、venv、pipx、Poetry、Conda 的边界

| 工具 | 主要职责 | uv 中最接近的部分 | 何时不要硬迁移 |
| --- | --- | --- | --- |
| pip | 把 Python 包安装进某个环境 | `uv pip` | 平台或发布流程只支持 pip，现有 requirements 流程稳定且暂不需要项目管理时。 |
| `venv` | 创建 Python 虚拟环境 | `uv venv` 或 uv 项目 `.venv` | 只需标准库、强调最小外部工具或教学环境要求纯标准流程时。 |
| pipx | 隔离安装 Python CLI | `uv tool install`；临时运行对应 `uvx` | 团队已统一 pipx 运维，或某工具的安装指南只验证过 pipx 时。 |
| Poetry | 项目元数据、解析、锁定、构建/发布工作流 | uv project | 现有 Poetry 插件、配置、锁文件和发布自动化有关键价值，但还没有一项项验证替代时。 |
| Conda | Python 与非 Python 包、二进制库、跨语言环境 | uv 只覆盖其中的 Python 部分 | 需要 CUDA、GDAL、MKL、R 包、特定系统库或机构维护的 Conda channel 时。 |

同一项目里可以组合工具，但必须只有一个清晰的“依赖真相来源”。需要特别注意：**uv project 默认使用项目的 `.venv`，不会仅因你先运行了 `conda activate` 就把该 Conda environment 当作项目环境。** 因此“Conda 提供 Python/原生库，uv project 再管 Python 依赖”默认会形成两层环境，不能假定内层 `.venv` 自动继承 Conda 包、激活脚本或原生库边界。

若团队确实要让 uv project 直接写入一个指定环境，必须根据 [uv 项目环境官方说明](https://docs.astral.sh/uv/concepts/projects/config/) 显式配置目标，并记住 `uv sync` 默认是 exact sync，可能删除 `uv.lock` 之外的额外包。这种工作流必须有独立可丢弃的项目环境、明确的锁文件责任和 CI 重建测试；否则优先使用 Conda `environment.yml` 的 `pip:` 子列表，或将 Conda 与 uv 责任完全分层。不要让 Conda、pip 和 uv 各自悄悄改同一环境。

## 9. 从旧项目迁移：先建立可比对基线

### requirements 项目迁到 uv project

官方迁移指南给出的基本入口是：

```bash
uv init
uv add -r requirements.in
```

如果希望首次迁移尽量保留已锁定的版本，将已经使用的 `requirements.txt` 作为 constraints：

```bash
uv add -r requirements.in -c requirements.txt
uv add --dev -r requirements-dev.in -c requirements-dev.txt
```

迁移不是“命令返回 0 就完成”：

1. 迁移前保留 Git 基线，记录 Python 版本、直接依赖和测试结果；
2. 区分未锁定的 `.in` 文件与已锁定的 `.txt` 文件，避免把所有间接依赖都误认为直接依赖；
3. 比对 `uv.lock` 与原有锁定结果，处理平台 marker、私有索引、Git/URL/本地依赖和开发组；
4. 用一个全新的 `.venv` 执行单元测试、命令行入口和构建测试；
5. 先在 CI 新分支上验证，再删旧 lock/requirements 文件；不要让两套宣称可编辑的依赖声明长期并行。

### Poetry 项目

uv 官方迁移索引在核对时并没有提供完整的“Poetry 到 uv”逐项指南。不要声称可无损一键迁移。至少要人工核对：

- `[tool.poetry]` 元数据到 PEP 621 `[project]` 的映射；
- 依赖组、extras、本地/Git 源、私有索引和平台 marker；
- build backend、脚本入口、Poetry 插件和发布流程；
- 从空环境安装后的测试与构建产物。

## 10. CI 中如何复现

要复现的不只是“能安装”，而是确认 CI 没有改写团队已审阅的 lock：

```bash
uv sync --locked
uv run --locked pytest
```

完整原则：

- 提交 `pyproject.toml`、`uv.lock`，以及团队需要时的 `.python-version`；不提交 `.venv`。
- CI 中固定 uv 版本，并按官方建议使用 `astral-sh/setup-uv`。Action 的 commit SHA、大版本和 uv 版本会变，应从官方[GitHub Actions 集成指南](https://docs.astral.sh/uv/guides/integration/github/)选择并由依赖更新机制定期审阅，不要从旧笔记盲抄版本。
- 用 `--locked` 在 lock 缺失或过期时失败；不要允许 CI 默默更新并使用未审阅的解析。
- 若有 extras 或非默认 dependency groups，需显式用 `--all-extras`、`--group <name>` 或团队约定的选项。不要假设一条 `uv sync` 会安装所有可选集合。
- 缓存键至少应包含 `uv.lock` 的变化。缓存只是加速；删除缓存后仍应能通过。CI 末尾可按官方指南评估 `uv cache prune --ci`。
- 如果使用私有索引，凭据放在 CI secret 中，不写入 `pyproject.toml`、`uv.lock`、命令日志或缓存键。

> [!tip] `--locked` 与更新依赖分开
> 普通 CI 只验证已审阅 lock。依赖更新应是另一个可见流程：例如开发者运行 `uv lock --upgrade-package <包名>`，审阅 `uv.lock` diff，测试后才合并。

## 11. Workspace 只作入门

workspace 是“在同一个仓库里一起管理的一个或多个 package”。每个 member 有自己的 `pyproject.toml`，但整个 workspace 共享一份 `uv.lock`，使内部包使用一致的依赖解析。

```toml
[tool.uv.workspace]
members = ["packages/*"]
exclude = ["packages/experimental"]
```

- `uv lock` 作用于整个 workspace。
- `uv sync` 和 `uv run` 默认作用于 workspace 根 package，可用 `--package <member>` 指定成员。
- workspace 适合同仓库的多个应用/库需要一致解析时。如果项目需要不同的 Python 范围、彼此冲突的依赖版本或独立发布节奏，先读完整[Workspace 文档](https://docs.astral.sh/uv/concepts/projects/workspaces/)，不要仅为减少 lock 数量就强行合并。

## 12. 决策速查

```text
只创建虚拟环境？        -> uv venv
保留 requirements/pip 工作流？ -> uv pip
管理当前项目的依赖？   -> uv add / remove / sync / run
临时运行 Python CLI？       -> uvx（uv tool run）
要让 CLI 长期出现在 PATH？ -> uv tool install
需要非 Python 二进制环境？ -> 先评估 Conda/系统包/容器
```
