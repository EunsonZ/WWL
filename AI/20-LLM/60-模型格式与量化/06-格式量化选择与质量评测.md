# 格式、量化选择与质量评测

<!-- deep-review-02 -->
> [!tip] 本轮深化：从当前概念继续追问
> 校准集与最终评测集应分开。权重误差相同可以导致不同输出误差，平均分相近也可能掩盖少数关键任务退化，需要配对回归和失败样本。 深化与验证：[[AI/20-LLM/60-模型格式与量化/08-量化误差传播校准目标与端到端评测|量化误差传播校准目标与端到端评测]]；[[AI/20-LLM/70-工程应用与工具链/10-LLM评测污染裁判偏差与统计检验|LLM评测污染裁判偏差与统计检验]]。


## 本课目标

- 按“任务 → 运行时/硬件 → 容器 → 量化 → 验收”选择产物；
- 将文件字节数、RAM/VRAM 峰值、prefill/decode 性能与质量退化分开测量；
- 设计高精度基线与多个量化候选的配对比较；
- 将统计不确定性、失败切片、来源/许可证与可回滚性写进发布门。

## 1. 选择顺序：先问能否正确运行，再问是否更小

一个稳健的决策顺序是：

1. **任务是训练、继续训练还是推理？** 训练 checkpoint 需 optimizer/RNG 等状态；纯推理 GGUF 不是完整训练恢复点。
2. **目标运行时识别什么？** `llama.cpp`、Transformers+bitsandbytes、GPTQ/AWQ 引擎的容器、元数据 schema、打包布局与 kernel 不同。
3. **目标架构与 tokenizer 是否被该固定版本支持？** 家族名相同不等于 MoE/长上下文/聊天模板变体可用。
4. **硬件的稀缺资源是什么？** 磁盘、RAM、VRAM、内存带宽、计算单元、电力/散热可能各自主导。
5. **可接受多少质量退化？** 必须针对任务和失败切片定义，不用“肉眼看不出”代替。
6. **来源与许可允许什么？** 技术上能转换不代表允许下载、修改、商用或再分发。

如果第 2 或第 3 步不成立，换成更小的量化标签不会修复兼容性。

## 2. 常见目标的候选起点

| 目标 | 优先候选 | 不该当作默认 |
| --- | --- | --- |
| 框架中保留通用权重，便于再微调/转换 | 同 revision 的 config + tokenizer + safetensors 高精度权重 | 只保留一个量化 GGUF 当可逆源文件 |
| bitsandbytes/QLoRA 微调 | 目标 GPU/库组合实测支持的 NF4 基座 + LoRA 适配器 | 把 GGUF `Q4_K_M` 直接当成 QLoRA 基座 |
| 固定 `llama.cpp` 后端本地推理 | 先做 F16/BF16 GGUF 基线，再比较 `Q8_0`、`Q5_0`/K-quant、`Q4_K_M`、适用 IQ | 根据文件名或他人的速度表直接选最低 bit |
| 固定 GPTQ/AWQ 服务引擎 | 引擎文档指定的精确 schema、group/zero 设置、打包和 kernel | 因同为 4-bit 就把 NF4/GGUF 文件当成可直接替换 |
| 高保真或回归基线 | 上游高精度权重或经验证的高精度 GGUF | 用已量化候选当“真值”评价更低 bit |

同一个候选在 CPU、Metal、CUDA、Vulkan 或混合 offload 上可有不同顺序。兼容性和性能必须在最终后端上检查，不能由容器格式单独推断。

## 3. 先建 manifest，再跑候选

每个评测对象用一份不含密钥的 manifest 固定：

| 类别 | 必须记录的字段 |
| --- | --- |
| 模型身份 | 发布者/仓库 ID、revision/commit、模型卡核验日、许可证与可接受使用条款 |
| 文件 | 源/产物精确文件名、字节数、哈希、分片索引、输入→输出系谱 |
| 语义配套 | config、tokenizer、special tokens、chat template 的哈希，固定测试文本的 token IDs |
| 转换/量化 | 工具 commit、实际帮助输出版本、参数、校准/imatrix 来源、输出 tensor type 统计 |
| 环境 | OS/架构、CPU/GPU、RAM/VRAM、后端、线程、offload、上下文、batch、KV cache dtype |
| 生成 | prompt/chat 模板、seed（如适用）、sampler、temperature/top-p/top-k、最大 token、stop 条件 |
| 评测 | 数据集版本/哈希、切片、指标定义、重复次数、预热、统计区间与验收阈值 |

高精度基线与量化候选除“被评测的权重表示”外尽可能保持一致。如果候选必须使用不同 kernel 或后端，把它记为“格式+运行时组合”的系统比较，不将全部差异归因于量化算法。

## 4. 文件尺寸：用字节和 tensor type 组成回答

记录文件精确字节数，再按 tensor type 汇总：

- 张量个数与元素数；
- 每种实际 dtype/quant type 的数据字节；
- scale/min/zero/codebook 等 block 开销；
- metadata、tensor infos、alignment padding 和分片开销。

如果只有参数数 $P$ 和名义 bpw $b$，$Pb/8$ 只能作为计划级估算。文件大小减少比例用精确字节比计算，不把文件系统显示的 GB/GiB 混用。

## 5. RAM/VRAM：分开测量权重、KV cache 和 workspace

至少报告三个时刻：运行时初始化后、模型加载后、目标上下文生成期间峰值。主机 RAM 和设备 VRAM 分别测量，并记录 mmap/page cache、GPU offload 层数与是否有权重临时拷贝。

| 构成 | 主要影响因素 | 与权重量化的关系 |
| --- | --- | --- |
| 权重 resident/offload | tensor type、是否原生内核、分层位置 | 通常直接受影响，但可能有解包/拷贝 |
| KV cache | 层数、KV heads、head dimension、context、batch/并发、cache dtype | 通常不随权重 `Q4_K_M` 按同比例下降 |
| compute/workspace | 后端、batch、图、attention/kernel 实现 | 可能因量化内核更大或更小 |
| tokenizer/程序/其他 | 运行时、并发、日志和缓存 | 基本不随权重 bit 数线性变化 |

内存失败门应使用最终目标上下文和并发，并保留系统安全余量；“空 prompt 加载成功”不是部署容量证据。

## 6. 速度：分开 prefill、decode、首 token 和总体验

对每个候选报告：

- 冷启动加载时间和热启动加载时间；
- time to first token（TTFT）；
- prompt processing/prefill tokens/s；
- text generation/decode tokens/s；
- 固定请求的端到端延迟，服务场景还报 p50/p95 和吞吐；
- 重复多次的中位数与离散程度，而不只保留最快一次。

必须控制的变量包括后端/commit、电源模式、热状态、线程/affinity、GPU offload、batch、context、prompt token 数、output token 数、采样和其他前台负载。如果改了 tokenizer 使 prompt token 数不同，速度比较已不是单一量化变量。

## 7. 质量：先比较转换基线，再比较量化损失

将质量诊断拆成两个差：

```text
上游高精度框架输出 → 高精度 GGUF 输出：检查架构/tokenizer/转置/元数据转换
高精度 GGUF 输出 → 量化 GGUF 输出：检查量化近似带来的附加误差
```

如果第一个差已经很大，不应通过调量化档位“治疗”；先修复转换。

### 评测层次

| 层次 | 例子 | 主要作用 | 限制 |
| --- | --- | --- | --- |
| 结构/语义 | tensor 数/shape/type、token IDs、special tokens、chat template | 捕获转换错误 | 不能证明模型质量 |
| 数值 | 固定 token 序列的 logits 差、KL/排名变化、perplexity | 高密度感知全局预测分布漂移 | 与用户任务成功不是一对一 |
| 任务 | 准确率、代码测试、格式遵循、RAG 引用正确率 | 对齐真实使用目标 | 数据泄漏、评分器和覆盖偏差 |
| 失败切片 | 中文、数学、代码、长上下文、结构化输出、重复/幻觉例 | 避免平均分数隐藏关键退化 | 切片样本少时不确定性大 |
| 人工配对 | 盲化两个输出的错误类型与可接受性 | 捕捉自动指标遗漏 | 昂贵，需评审准则与一致性 |

验评保留每个样本的配对差，对差值而不是对两组独立分数做统计。报告置信区间或配对 bootstrap 区间，并将数据泄漏、评分器偏差、分布漂移与多次试验挑最好结果列为非抽样误差。完整定义见 [[数学/30-概率与统计/05-统计估计置信度与模型评测|统计估计、置信度与模型评测]]。

### 一条可追溯的配对记录

下面是字段形状，不是实测数据：

```yaml
case_id: zh-structured-output-0042
input_token_ids_sha256: <same-for-both-candidates>
reference_next_token_ids: [<ids>]
baseline:
  artifact_sha256: <high-precision-gguf>
  nll: <value>
  task_pass: true
candidate:
  artifact_sha256: <quantized-gguf>
  nll: <value>
  task_pass: false
paired_delta:
  nll: <candidate-minus-baseline>
  forbidden_failure: schema-amount-field
```

困惑度的计算可写成 $\mathrm{PPL}=\exp(\frac{1}{N}\sum_i -\log p(x_i\mid x_{<i}))$，但本页不重复推导；它只强调两个候选必须对同一 token 序列计分。若 tokenizer/chat template 改变导致 token IDs 不同，该记录先标记“不可比”，不直接计算“量化损失”。数学定义与区间估计仍回到上述数学权威页。

## 8. 一个可观察的候选报告

下表是**虚拟格式示例**，数值不代表任何真实模型或硬件：

| 候选 | 文件 GiB | 峰值 RAM GiB | decode tok/s（中位数） | 任务配对差 | 关键失败 | 决策 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| F16 GGUF 基线 | 10.0 | 12.5 | 8.0 | 0 | 0/120 | 作为转换/质量基线 |
| Q8_0 | 5.4 | 7.8 | 11.0 | -0.2 pp | 0/120 | 候选 |
| Q4_K_M | 3.1 | 5.6 | 15.0 | -0.8 pp | 1/120 | 若失败不在禁区且区间通过，可候选 |
| IQ2 | 2.0 | 5.0 | 12.0 | -4.5 pp | 8/120 | 因质量门失败而拒绝 |

这个表不能只凭平均分数做决定。如果 Q4_K_M 的唯一失败是“结构化输出中金额字段错”而该字段属于账务禁区，即使总分只降 0.8 个百分点也必须拒绝。验收门应在看结果前定义，避免为喜欢的候选事后改标准。

## 9. 发布门与决策记录

| 门 | 通过条件 | 失败时的动作 |
| --- | --- | --- |
| 来源/许可 | 上游 revision、哈希、模型卡、权重/工具/数据许可完整 | 不加载、不转换或不发布；补齐权利证据 |
| 结构 | safetensors/GGUF 长度、偏移、对齐、shape/type 与必需 metadata 全部通过 | 隔离产物，从受信输入重建；不就地修权重 |
| 语义 | 架构、token IDs、special tokens、chat template、高精度最小输出与上游对齐 | 修复转换而不调整量化档 |
| 容量 | 目标 context/并发下 RAM/VRAM/磁盘有明确余量 | 减小 context/并发、调整 offload 或选另一候选，明确行为变化 |
| 性能 | TTFT、prefill、decode、端到端延迟/吞吐的重复统计达标 | 分析后端和 kernel，不假定降 bit 必然修复 |
| 质量 | 全局、切片、禁区和统计区间均达预先阈值 | 拒绝候选或选更高精度；保留失败例 |

“发布”不必然是对外上传，也可是把候选标记为本地可用。一旦涉及对外分发、对外服务、gated 条款、付费资源或上传，必须另行取得明确授权。

## 练习：设计一份不需真实模型的评测协议

选一个虚拟场景（例如“16 GB RAM 的 CPU 中文问答”），用表格写出：

1. 高精度 GGUF 基线与至少三个量化候选。
2. 完全相同的 tokenizer/chat template、prompt 集、context、sampler、后端与线程参数。
3. 文件大小、加载后/生成峰值 RAM、TTFT、prefill/decode tok/s 和至少两类质量指标。
4. 一个不能由平均分数补偿的禁区失败。
5. 各门的阈值、重复次数、统计区间与回滚动作。

### 成功标准

- [ ] 我的比较只改变候选权重表示，或明确标注了无法控制的后端差异。
- [ ] 我分开记录文件、RAM、VRAM、prefill、decode、TTFT 和端到端体验。
- [ ] 我先验证高精度 GGUF 与上游框架对齐，再评估量化损失。
- [ ] 我报告配对差异和不确定性，并检查关键失败切片。
- [ ] 我在看结果前写好接受/拒绝门，未通过时不发布产物。

## 许可证、不可信边界与恢复

- 量化、换容器、改文件名或补 metadata 都不会改变基础模型的权利；发布前分别审查模型、工具、校准/评测数据和派生产物。
- 模型文件、tokenizer、聊天模板、imatrix 与评测器都是不可信输入；使用无密钥/无个人数据、有磁盘/RAM/超时限制、默认无网络的隔离环境。
- 永不就地覆盖上游权重或高精度基线。候选失败时，保留 manifest/失败报告，删除可重建的派生文件，回到上一个已验证哈希。
- 工具命令、支持架构、量化预设和性能会变；实施时从 [[AI/90-资源/05-官方资料与版本核验记录|官方资料与版本核验记录]] 进入官方规范/工具，锁定 commit 后才使用。2026-09-02 的固定入口见 [[AI/20-LLM/60-模型格式与量化/07-一手来源快照与现场复核清单|一手来源快照与现场复核清单]]。本页没有下载、转换、量化、构建、推理或发布任何模型。

要把“同一后端”落到 CUDA 证据，还要记录 driver/Toolkit/GPU 架构、实际 tensor placement、显存峰值与 kernel 活动；只看 `nvidia-smi` 一行或构建日志不够。详见 [[计算机知识/40-并行与异构计算/01-CUDA/10-PyTorch扩展-Triton与llama.cpp后端|PyTorch 扩展、Triton 与 llama.cpp 后端]] 和 [[AI/20-LLM/50-实现/04-llama.cpp构建后端与调用链|llama.cpp 构建、后端与调用链]]。
