# 教师改了电话，课表里该改哪一份？

学生打开“本学期课表”，要看到自己选了哪些课和任课教师**当前**的联系电话。同一位教师教两门课，电话在两个位置出现。改号之后，两个位置若一个显示新号、一个显示旧号，读者并不会因为数据“都是合法 JSON”就接受它。但若另一个字段记录的是**选课时**的电话，把旧号全部抹掉，又会破坏历史事实。

本课用同一选课对象比较关系表、文档嵌入和文档引用：先回答同一个查询，再跟踪一次改号及一次漏更新。随后用 MongoDB Community **7.0** 的四份固定文档，区分缺字段、显式 `null`、空数组和重复元素。具体查询规则属于这个引擎与版本；SQL 的 NULL 和其他非关系引擎仍按各自规则解释。

从 [[计算机知识/55-数据库/10-系统课程/08-数据库工程安全与扩展专题#分区、分片和不同数据模型|数据库工程中的模型选择]] 来这里，把“读课表、改教师电话、保存历史”三个动作分开推演；读完带着需要维护的副本数和原子边界回到该页的 [[计算机知识/55-数据库/10-系统课程/08-数据库工程安全与扩展专题#迁移要允许新旧版本短期共存|迁移步骤]]。本课先完成文档模型这段解释，键值协议、图路径和宽列/时序模型仍需各自的完整课程。

## 先确定一行和一个电话各指什么

工作负载是给定 `student_id` 和 `term`，返回按课程编号排序的 `(course_id, current_phone)`；同一课程只出现一次。练习同时显示 `teacher_phone_at_enrollment`，用来检查当前与历史有没有混淆。教学学期固定为 T1；S1 选 C10、C20，S2 选 C10，三条选课都由 T7 任教。T7 选课时和初始当前电话都是 `555-0100`。

| 对象 | 初始数据 | 标识与成立条件 |
| --- | --- | --- |
| Student | S1：Lin；S2：Mei | `student_id` 唯一；姓名是学生的当前资料 |
| Teacher | T7：`555-0100` | `teacher_id` 唯一；本例每位教师恰有一个当前电话 |
| Enrollment | S1/T1/C10/T7/A；S1/T1/C20/T7/B；S2/T1/C10/T7/A | 一行是一名学生在一个学期选一门课；没有分班、重修次数或共同授课 |
| 选课电话快照 | 三条各为 `555-0100` | 属于这一次选课；不是教师当前电话的另一个名称 |

这里沿用 [[计算机知识/55-数据库/03-函数依赖范式与模式分解#冗余为何会变成更新异常|函数依赖的选课对象]]，保留其 `student_id → student_name` 和某一当前合法实例中的 `teacher_id → teacher_phone`。该页的 `course_id → teacher_id` 在本例**固定 T1、每门课单教师**的条件下成立；它不是跨学期不变的保证。若 C10 下学期改由 T8 教，就应建模为 `(term, course_id) → teacher_id`；若同学期分班或共同授课，这个决定因素也不够。选课键相应使用 `(student_id, term, course_id)`，原页忽略学期时的二元键只适用于它原先的简化世界。三个样本都满足依赖，只能检查样本，不能由此证明业务永远满足它们。

下面仍把 `teacher_id` 保留在 Enrollment 中，便于逐项对应已有例题。若另有 CourseOffering 维护 `(term, course_id)` 的教师安排，写入 Enrollment 时还必须保证教师与安排一致，或通过安排键取得教师；只给 `teacher_id` 加外键并不能检查这项一致性。SQL 可用声明约束和合适模式维护这些不变量；文档字段里出现 `teacherId` 字符串也不会自动成为外键。本课的有限输入事先满足引用存在和上述业务依赖，没有实现完整选课写入服务。

“当前”在下列顺序实验中指：电话更新已经成功返回，且下一次查询期间没有并发改号。在副本延迟、并发修改和缓存下，存成引用也不自行保证“总是读到刚确认的新号”，还要规定读取来源、读写关注级别与业务观察时点。

## 三种表示回答同一个查询

### 关系表：电话由教师行提供

拆成 `Student(student_id,name)`、`Teacher(teacher_id,phone)` 和 `Enrollment(student_id,term,course_id,teacher_id,grade,teacher_phone_at_enrollment)`。最后一列是为本课增加的历史事实；当前电话仍只在 Teacher 中存一份。示例没有学生姓名过滤，所以查询无需再连接 Student。

```sql
SELECT e.course_id, t.phone AS current_phone,
       e.teacher_phone_at_enrollment
FROM Enrollment AS e
JOIN Teacher AS t ON t.teacher_id = e.teacher_id
WHERE e.student_id = 'S1' AND e.term = 'T1'
ORDER BY e.course_id;
```

先取 S1/T1 的两行，再各匹配 Teacher 的唯一 T7 行，得到 C10、C20 各一行，当前电话和快照均为 `555-0100`。Teacher 键唯一和引用存在是这个行数判断的前提；若右侧有多个同键记录，连接会放大行数；若引用不存在，内连接会丢失相应选课。回 [[计算机知识/55-数据库/02-SQL连接聚合子查询窗口与NULL#先按逻辑含义理解查询|SQL 的连接基数]] 核对这个前提，再返回比较文档 `$lookup` 的匹配数组。[PostgreSQL 17 的连接规则](https://www.postgresql.org/docs/17/queries-table-expressions.html) 是此处 SQL 示例的实现依据。

### 嵌入文档：把常一起读取的信息放进课表

MongoDB 文档可含子文档和数组。用一份学生—学期文档装课表，S1 的初始 `schedules` 文档是：

```javascript
{ _id: "S1/T1", studentId: "S1", term: "T1", enrollments: [
  { courseId: "C10", teacherId: "T7", grade: "A",
    currentPhone: "555-0100", teacherPhoneAtEnrollment: "555-0100" },
  { courseId: "C20", teacherId: "T7", grade: "B",
    currentPhone: "555-0100", teacherPhoneAtEnrollment: "555-0100" }
] }
```

S2/T1 是另一份文档，数组只有 C10/T7/A，两个电话字段初始也都是旧号。以 `studentId`、`term` 找到整份课表，就能从同一文档读取课程及嵌入的电话；若要与 SQL 一样输出一课一行，可以展开数组并投影：

```javascript
lab.schedules.aggregate([
  {$match: {studentId: "S1", term: "T1"}},
  {$unwind: "$enrollments"},
  {$project: {_id: 0, courseId: "$enrollments.courseId",
    currentPhone: "$enrollments.currentPhone",
    teacherPhoneAtEnrollment: "$enrollments.teacherPhoneAtEnrollment"}},
  {$sort: {courseId: 1}}
])
```

`lab` 是后文脚本为本次实验创建的数据库对象。这里的一次聚合从本集合取得所需信息，无须再访问教师集合；它仍有数组展开、投影和排序工作，不能把“一条命令”当成零成本。将经常一起取的子项放在同一文档是 [MongoDB 7.0 嵌入模型](https://www.mongodb.com/docs/v7.0/data-modeling/embedding/) 的用途；一个文档的 BSON 大小上限是 16 MiB，不能把无限增长的历史课表都装进它。实际性能还取决于数据大小、索引、访问比例和更新竞争，本例没有测速度。

### 引用文档：选课保留教师身份，读取时取得电话

另一种表示将三条 Enrollment 各存一份文档，使用驼峰字段名；教师另在 `teachers` 中存 `{_id:"T7", currentPhone:"555-0100"}`。例如：

```javascript
{ _id: "E1", studentId: "S1", term: "T1", courseId: "C10",
  teacherId: "T7", grade: "A", teacherPhoneAtEnrollment: "555-0100" }
```

应用可先读选课，再按去重后的教师 ID 读教师；也可让 `$lookup` 完成匹配。后者仍是一条发给服务器的聚合命令，但访问了两个集合：

```javascript
lab.enrollments.aggregate([
  {$match: {studentId: "S1", term: "T1"}},
  {$lookup: {from: "teachers", localField: "teacherId",
    foreignField: "_id", as: "teacher"}},
  {$unwind: "$teacher"},
  {$project: {_id: 0, courseId: 1, currentPhone: "$teacher.currentPhone",
    teacherPhoneAtEnrollment: 1}},
  {$sort: {courseId: 1}}
])
```

`$lookup` 加的是匹配文档的**数组**；本例教师 `_id` 唯一且引用存在，所以每个数组恰有一个元素，`$unwind` 后仍各一行。缺教师会得到空匹配数组，并被这里默认的 `$unwind` 去掉；如需保留，应另规定缺引用结果及展开选项，不能悄悄把它当正常课表。[MongoDB 7.0 引用模型](https://www.mongodb.com/docs/v7.0/data-modeling/referencing/) 和 [`$lookup` 定义](https://www.mongodb.com/docs/v7.0/reference/operator/aggregation/lookup/) 支持这一表示与查询；引用减少电话副本维护，却增加查找工作。内置 `_id` 唯一性保障教师身份，脚本另给引用选课建立三字段唯一索引；嵌入数组内课程不重复在本例是输入条件，没有由一个数组字段自动保证。

三种表示在初始数据上都输出 `(C10,555-0100)`、`(C20,555-0100)`。等价的是给定条件下的业务结果；不能从结果相同推断存储方式、物理执行或并发保证相同。

## 一次改号与一次漏更新

先问应改哪项事实：T7 的**当前**电话变为 `555-0199`。关系表示执行 `UPDATE Teacher SET phone='555-0199' WHERE teacher_id='T7'`；引用表示执行 `lab.teachers.updateOne({_id:"T7"}, {$set:{currentPhone:"555-0199"}})`。两者都只改一份当前教师资料，下一次顺序查询取新号。三条 Enrollment 的选课快照都不改。

嵌入表示共有三处当前电话副本：S1 的 C10、C20 以及 S2 的 C10，分属两份课表。教师主文档改号不会自动传播到这些字段。现在故意写错传播条件，只改 S1/C10：

```javascript
lab.schedules.updateOne({_id: "S1/T1"},
  {$set: {"enrollments.$[e].currentPhone": "555-0199"}},
  {arrayFilters: [{"e.teacherId": "T7", "e.courseId": "C10"}]});
```

这是一次成功的单文档写；条件漏掉 S1/C20 和 S2 仍然是业务错误。对当前电话做三次状态观察：

| 观察时点 | 关系 JOIN／引用查询 S1 的 C10,C20 | 嵌入查询 S1 的 C10,C20 | 嵌入查询 S2 的 C10 |
| --- | --- | --- | --- |
| 改号前 | `0100,0100` | `0100,0100` | `0100` |
| 教师主资料改号后，未传播 | `0199,0199` | `0100,0100` | `0100` |
| 故意只改 S1/C10 | `0199,0199` | `0199,0100` | `0100` |
| 完整传播完成后 | `0199,0199` | `0199,0199` | `0199` |

表中省略共同前缀 `555-`；每一行的三条历史快照始终为 `555-0100`。漏改时，S1 同一页给同一 T7 显示两种“当前电话”，已经违反本课教师当前事实唯一的业务条件。数据能写入、文档能原子修改，并不能证明传播条件正确。

修完整个有限例子需要匹配所有含 T7 的课表，再修改其中所有 T7 子项：

```javascript
lab.schedules.updateMany({"enrollments.teacherId": "T7"},
  {$set: {"enrollments.$[e].currentPhone": "555-0199"}},
  {arrayFilters: [{"e.teacherId": "T7"}]});
```

这次命令完成后两份课表均有修改；`modifiedCount=2` 计的是文档，不是数组元素数。目标集合里有三处相关当前电话，其中 S1/C10 已是新号，所以修复实际改变另两处旧值。这里未更新 `teacherPhoneAtEnrollment`；快照若原录入有误，需要另有更正理由与记录，不能因教师今天改号就“修正”过去的电话。回 [[计算机知识/55-数据库/03-函数依赖范式与模式分解#分解需要两个检查|范式页的当前价格与成交价格]] 比较：保存不同时间的事实之前，先分清依赖的对象与观察时期。

## 原子写的边界在哪里

MongoDB 7.0 的单文档写是原子的，包含在该写中修改的多个字段或数组子项。若一次正确的 `updateOne` 更新 S1 文档的两处 T7 当前电话，这两处属于同一文档写。上面的故意漏改只把一处纳入写集合，原子性不会补出遗漏的另一处。[官方写原子性说明](https://www.mongodb.com/docs/v7.0/core/write-operations-atomicity/) 还明确：`updateMany` 的**每份文档**修改原子，整个多文档操作并非原子，其他操作可以交错。因此它顺序执行后的结果全对，不证明查询在执行期间看不到 S1 新、S2 旧的中间状态。

若要求两份课表和教师当前资料一起全有或全无，就需要把这些写纳入合适的多文档事务或改用减少副本的表示。在 MongoDB 7.0 中，多文档事务需要副本集或分片集群，standalone 不支持；主节点使用 WiredTiger，FCV 至少分别为 4.0／4.2，仍须满足部署的其余事务限制。事务会引入协调、重试和资源成本，提交后的新旧观察还受读写关注级别和缓存影响。[MongoDB 7.0 事务部署条件](https://www.mongodb.com/docs/v7.0/core/transactions-production-consideration/) 是这些条件的来源。本课使用临时 standalone 做顺序查询与更新，没有实施事务或并发原子性实验。

引用把当前电话集中到教师文档，消除了本例三份电话副本同步的需要；如果课程、教师安排、成绩等多个事实也必须在同一时点一起观察，仍要定义跨文档读写协议。读到一个最新电话号码，和读到整份课表的同一事务快照，是不同要求。

## 缺字段 null 空数组与重复元素

现在只检查 `prereqCases` 四份文档。这里 `prereqs` 表示课程先修列表；本课业务约定：缺字段表示该文档未提供先修资料，显式 `null` 表示提供了字段但列表未知，`[]` 表示已确认无先修，`["C1","C1"]` 保存两次 C1，作为重复输入的反例。业务含义由这项约定赋予，MongoDB 不会替使用者认证“没有先修”。

```javascript
{_id: 1}
{_id: 2, prereqs: null}
{_id: 3, prereqs: []}
{_id: 4, prereqs: ["C1", "C1"]}
```

查询统一写成 `lab.prereqCases.find(过滤条件).sort({_id:1})`，下面给全部命中的 `_id`，没有省略未命中者。每一结果也可按四输入逐项手推：

| 过滤条件 | 命中 `_id` | 在这四条输入上检查什么 |
| --- | --- | --- |
| `{prereqs: {$exists:false}}` | `[1]` | 字段未出现 |
| `{prereqs: null}` | `[1,2]` | 此引擎的 null 等值查询也匹配缺字段 |
| `{prereqs: {$type:10}}` | `[2]` | BSON Null 类型；10 为类型编号 |
| `{prereqs: {$exists:true}}` | `[2,3,4]` | 字段存在，包括值为 null |
| `{prereqs: {$type:"array"}}` | `[3,4]` | 字段为数组，包括空数组 |
| `{prereqs: []}` | `[3]` | 与这个空数组精确相等 |
| `{prereqs: "C1"}` | `[4]` | 数组含匹配元素；返回文档一次 |
| `{prereqs: ["C1","C1"]}` | `[4]` | 与完整数组相等，长度与顺序参与比较 |
| `{prereqs: ["C1"]}` | `[]` | 两元素数组不等于单元素数组 |
| `{prereqs: {$size:2}}` | `[4]` | 数组长度为 2，不因值重复而缩为 1 |

前四行依据 [MongoDB 7.0 的 null 查询](https://www.mongodb.com/docs/v7.0/tutorial/query-for-null-fields/) 与 [`$exists`](https://www.mongodb.com/docs/v7.0/reference/operator/query/exists/)，数组类型依据 [`$type`](https://www.mongodb.com/docs/v7.0/reference/operator/query/type/)，后几行依据 [数组查询](https://www.mongodb.com/docs/v7.0/tutorial/query-arrays/) 与 [`$size`](https://www.mongodb.com/docs/v7.0/reference/operator/query/size/)。这张表限定四输入：若以后允许嵌套数组或数组里的 null，还要重新计算类型与元素匹配结果，不能把此表当成覆盖任意文档的分类器。

重复元素有两个层次。`find({prereqs:"C1"})` 返回第 4 份文档一次；对同一文档做 `{$unwind:"$prereqs"}`，会得到两行 `{prereqs:"C1"}`。因此成员查询命中一次不代表数组存储自动去重，展开后计数也不是唯一先修课程数。`["C1","C1"]` 的反序仍是自身，无法单凭这个例子检验顺序差别；若换成 `["C1","C2"]`，要按数组顺序相等规则重新手推。

对照 [[计算机知识/55-数据库/02-SQL连接聚合子查询窗口与NULL#外连接与 NULL 的具体反例|SQL NULL]]：SQL `column = NULL` 不得到 true，判断使用 `IS NULL`；这里 `{prereqs:null}` 却可命中缺字段。它们的语法和规则不同，不能因为都有一个 `null` 字样就共用真值表；“非关系”这个类别也没有为各引擎规定一套统一语义。

## 改变条件后重新选择

先独立回答，再展开答案。不要只写“嵌入快、引用一致”，要指出一次读、一次改号各需要取得或维护哪些事实。

1. 电话每月才改一次，课表访问很多，几乎每次都要课程加电话；业务允许改号后十分钟内刷新显示，学生每学期课程数量有界。怎样表示当前电话与选课快照？为所选方案增加哪项维护成本？
2. 改为教师频繁改号，要求每次更新确认后，后续页面按规定的观察时点显示同一个当前电话。课表读取仍很多。是否继续把当前电话复制进每份课表？需要承担哪些查询与一致性成本？
3. 同学期一门课允许两个班由不同教师授课；需求只要当时选课的电话，不再显示当前联系信息。原决定因素、选课键和电话更新行为分别怎样变？

<summary>参考推演：从访问模式与事实含义给出理由</summary>

**第一题。** 可以保留有界学生—学期课表，嵌入当前电话与独立的历史字段，以减少常用页面查找教师的工作。但接受延迟并没有免除维护责任：教师改号后须找全副本，在十分钟上限内刷新并校验遗漏，记录失败并可重新从教师当前资料修复。历史字段不参与刷新。一次改号维护的副本数随选课数增长，不是只写教师一行；索引、复制空间、修复协议和同一课表更新竞争均有成本。关系 JOIN 或文档引用同样能满足需求，如果真实测量并未显示读取收益足以覆盖这些成本，就没有仅因这个读多条件迁移到嵌入的理由。本题给的是选择条件，没有提供性能测量。

**第二题。** 倾向让当前电话只在教师实体维护：关系 Teacher 加 JOIN，或文档 teachers 加引用读取；保留选课快照。一次改号不再更新全部课表副本，代价是教师查找、索引访问或应用附加读取。文档嵌入仍能实现要求，但若坚持即时统一，就必须为所有副本的完整传播和原子观察付费，单次 `updateMany` 不足以论证它。引用表示也须落实“更新确认”和“观察时点”的协议：读取哪个节点、采用何种读写关注级别、如何处理缓存与并发改号；本课顺序 standalone 实验仅覆盖没有并发改号的下一次查询。不能把这里正确的新号输出当成部署在任意拓扑上的即时一致性认证。

**第三题。** 给班次一个 `offering_id`，以 `(term,offering_id)` 或全局唯一 offering_id 决定教师；course_id 相同已不能决定 teacher_id。若允许同学生同学期选不同班，选课键也要纳入 offering_id；若业务禁止，还需另有课程层面的唯一约束。只问当时电话时，选课文档可以直接保存那个历史事实，不需要为了查当前电话而 JOIN／lookup，教师今天改号也不触碰它。这里减少读取是因为查询目标改变了，不能把历史号当成当前号回答原问题。

规范源码是 [[计算机知识/_labs/round3/DB/document_model_checks.js|document_model_checks.js]]。输入与期望均内嵌，下面是完整镜像；脚本创建随机名称的本次数据库，核十个四文档查询及重复展开，再运行引用／嵌入的改号轨迹，最后只删除自己创建的数据库。失败也执行该清理，因此保留外部 stdout／stderr 才能追溯失败。重复运行使用新名字，不重置已有数据库。

只在专用临时、回环 MongoDB 7.0.x standalone 上运行。下面 `MONGOD`、`MONGOSH` 是已取得的官方二进制路径，`PORT` 是本次空闲本地端口；这些 shell 变量由操作者明确赋值。`labdir` 每次由 mktemp 新建。两个终端分别执行：

**2026-10-12 的有限实际执行。** 在 macOS arm64 的临时回环 standalone 上，官方 MongoDB Community 7.0.43 与 mongosh 2.5.8 实跑同一完整源码两次，均退出 0、`PASS 23`；第三次独立检查在正常清理前读取实际集合内容，核对后仍清理。独立核查先建立 SQLite 关系 JOIN 的基线和四文档手算结果，再比较数据库实际输出，未仅复述源码内嵌期望。关系运行基线是 SQLite；前面的 PostgreSQL 17 方言示例未另在 PostgreSQL 上实跑。
