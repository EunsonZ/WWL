## TCP 不知道“这一条 JSON”在哪里结束

一次 `send` 可能被多次 `recv` 取出，多次 `send` 也可能被一次 `recv` 读到。这不是 TCP 把消息“粘坏了”，而是应用给字节流强加了未声明的消息边界。长度前缀、分隔符配合转义、固定长度、协议语法自身可判定边界，都是可用方案。

设协议为四字节大端无符号长度，随后跟 UTF-8 JSON，最大消息 1 MiB。解析器首先等满 4 B，再检查长度是否超限，然后等满正文，最后解码和校验对象结构；不能读到一半就尝试 JSON 解码并当成协议失败。下面是增量分帧核心，语义校验应在其后执行：

```python
class Frames:
    def __init__(self, limit=1024 * 1024):
        if type(limit) is not int or limit < 0:
            raise ValueError("invalid limit")
        self.buf = bytearray()
        self.limit = limit
    def feed(self, chunk: bytes) -> list[bytes]:
        self.buf.extend(chunk)
        out = []
        while len(self.buf) >= 4:
            n = int.from_bytes(self.buf[:4], "big")
            if n > self.limit:
                raise ValueError("frame too large; close connection")
            if len(self.buf) < 4 + n:
                break
            out.append(bytes(self.buf[4:4+n]))
            del self.buf[:4+n]
        return out
    def finish(self) -> None:
        if self.buf:
            raise EOFError("truncated frame")
```

这是教学版：大批量处理时反复删除缓冲头部会移动数据，可用游标加周期压缩优化；上游还必须限制单次读取大小、连接总缓存和未处理消息数。仅限制单个帧长不能防止攻击者通过无限多合法帧耗尽内存。

## 背压是一条完整的责任链

当数据库每秒处理 100 项，而连接每秒输入 1000 项，无界队列只是把失败推迟成内存耗尽。应设定队列上限，高水位时暂停读取或拒绝请求，低水位后恢复；发送端也要处理部分写与暂不可写。就绪通知只说明可以尝试 I/O，不保证能一次读写全部请求。

非阻塞接口的 EAGAIN 与连接断开不是同一错误；`recv` 返回 0 表示对端有序关闭其发送方向。事件循环若在回调中做长 CPU 计算，会让其他连接无法及时获得服务；线程池和进程池又有自己的队列及取消边界。

## 超时需要区分阶段与总预算

DNS、建连、握手、首字节、空闲读和总请求截止时间解决不同问题。每层都重新给 30 秒可能让总耗时远超预期；可传播同一个单调时钟截止时间，每次操作计算剩余预算。取消等待不证明服务器撤销了已经提交的副作用。

重试只对被协议允许的错误与操作进行，加入退避和抖动，并限制总次数或总预算。所有客户端在同一个时间点同步重试会制造新的负载尖峰。

## 排障顺序与证据

先记录目标、时间、地址族、错误阶段、重试次数和请求标识；再依次检查解析、路由、端口、握手、协议和后端依赖。抓包需要授权并处理敏感数据；只观察包时间不能直接知道应用内部锁等待。应把客户端耗时、服务端日志与分布式追踪对齐，注意各机器时钟误差。

**练习**：把两帧编码后，在每一个可能的字节位置切开，分两次 feed；所有切法都应得到相同的两条消息。再测试长度超过上限、正文不完整和最后一个字节缺失。协议实现最有价值的测试常常是这些边界，而不是一次理想网络上的成功演示。
