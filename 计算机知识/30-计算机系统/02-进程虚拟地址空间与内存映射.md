# 进程虚拟地址空间与内存映射

## 本课目标

学完后，你应该能够：

- 区分虚拟地址、虚拟映射、物理页和后备存储；
- 解释代码、静态数据、堆、栈和文件映射的典型职责，但不把示意图当成固定地址表；
- 用按需分页、页缓存、共享映射和写时复制解释“映射大小不等于物理占用”；
- 区分 TLB hit、TLB miss、页表遍历与 page fault，不把所有地址翻译开销都叫“缺页”；
- 说明 `mmap` 模型为何适合大型只读模型文件，也说明它不保证数据已在 RAM 中；
- 区分内存泄漏、分配器保留、地址空间碎片、缺页和工作集过大。

Linux 课程已经从操作系统角度介绍进程与虚拟内存，本课继续追踪进程内部的映射语义。系统分层入口见 [[计算机知识/20-操作系统/01-Linux/01-计算机系统与Linux分层|计算机系统与 Linux 分层]]。

## 1. 地址空间是一张“每个进程自己的地图”

程序中的指针通常保存虚拟地址。CPU 执行加载或存储时，内存管理单元依据当前进程的页表，把虚拟页翻译到物理页；若映射不存在、权限不允许或页面尚未就绪，就触发异常交给内核处理。

> [!important] TLB miss 不等于 page fault
> 常见处理器会先在 TLB（translation lookaside buffer）中查找近期虚拟页到物理页的翻译。TLB hit 可复用已缓存的翻译；TLB miss 往往只需硬件或软件遍历页表并补入 TLB，不必进入内核的缺页处理。只有当映射、权限或页面就绪状态需要内核介入时，才会进入相应 page-fault 路径。页表遍历本身也可能访问多级页表页并命中或未命中 CPU cache，因此“数据已驻留”也不表示地址翻译没有成本。

```text
进程 A 的虚拟地址 0x... ─┐
                           ├─ 地址区间与权限记录 ─→ 当前是否应有映射、后备对象是什么
进程 B 的虚拟地址 0x... ─┘                         ↓
                         已驻留时：页表项 ─→ 物理页
                         未驻留时：缺页处理依据映射记录准备物理页，再更新页表
```

两个进程可以在相同虚拟地址看到不同数据，也可以通过不同虚拟地址共享同一个物理页。地址数字相同不等于对象相同；地址数字不同也不排除共享底层页。

## 2. 典型地址空间有哪些区域

一个原生进程常出现下列映射，但顺序、地址、增长方向和命名都受平台、ABI、加载器、安全随机化和运行时影响：

| 典型区域 | 常见内容 | 常见权限或特点 |
| --- | --- | --- |
| 可执行代码 | 机器指令 | 读、执行；通常不写 |
| 只读数据 | 字符串常量、只读表 | 读；通常不写不执行 |
| 已初始化/零初始化静态数据 | 全局变量、静态存储期对象 | 常可读写 |
| 堆及匿名映射 | 动态分配的大块数据、运行时状态 | 按需扩展或由分配器管理 |
| 文件映射 | 可执行文件、共享库、模型、数据库页 | 可只读、私有或共享 |
| 线程栈 | 调用帧、局部自动对象、返回信息 | 每线程各有映射和保护边界 |

“堆向上、栈向下”的图适合建立直觉，却不是可移植契约。大型分配也可能由独立匿名映射完成，不一定落在一段连续增长的传统堆中。

## 3. 映射以页为管理单位

虚拟内存通常按页管理。页表项编码硬件翻译所需的物理页与状态，内核还维护更高层的虚拟地址区间、权限和文件后备关系；“未驻留文件页”并不是页表直接指向磁盘文件。常见页大小可能是 4 KiB，也可能支持更大的页；不要把一个平台的页大小写进通用文件格式或算法假设。

映射一段 4 GiB 文件并不意味着内核立刻读取 4 GiB：

1. 先在地址空间中建立文件区间与权限关系；
2. 程序首次触碰某页时发生缺页；
3. 若页不在内存，内核从后备存储读取；若已在页缓存，可能复用现有页；
4. 页表更新后，指令重新执行并获得数据。

**缺页不是必然错误。** 按需装入产生的轻微缺页是正常机制；访问未映射区域或违反权限的缺页才可能导致进程终止。

## 4. 私有、共享与写时复制

- **共享映射**允许多个映射看到对同一后备对象的修改，具体可见性与持久化仍受 API、同步和文件系统规则约束；
- **私有映射**中的写入不会直接回写为其他映射可见的同一文件内容，常配合写时复制；
- **写时复制（copy-on-write）**让多个地址空间先共享只读物理页，直到某方写入时才为它复制页。

这解释了为什么创建子进程或同时运行多个使用相同共享库的程序，不一定立即复制全部内存。但只要各进程大量写入原本共享的页，物理占用仍会增长。

## 5. VSZ、RSS 与“这个程序用了多少内存”

单个数字很难回答内存问题：

| 指标直觉 | 能说明什么 | 不能单独说明什么 |
| --- | --- | --- |
| 虚拟大小（VSZ/VIRT） | 进程保留或映射了多少虚拟地址范围 | 当前有多少物理 RAM 真正驻留 |
| 常驻集（RSS） | 此进程当前映射且驻留在主存的页的总量；共享页会在每个映射它的进程 RSS 中出现 | 其中多少页与其他进程共享、最终应归谁“付费” |
| 按比例常驻集（PSS） | 在 Linux 的 `/proc/<pid>/smaps` 按映射列出的快照统计：私有驻留页全计，某共享驻留页按当时 map count 分摊给每个映射者 | 真实的资源账单、未来工作集、历史峰值或 GPU/其他设备内存 |
| 独占常驻集（USS / private resident） | 没有与其他进程共享的、当前归该进程独占的驻留页；工具常由 private clean + private dirty 等项汇总，具体口径须看工具文档 | 一个跨平台、跨工具完全一致的内核指标，或进程的全部虚拟/设备内存 |

例如四个进程都映射同一份 4 GiB 只读模型，不应直接得出“必然占用 16 GiB 物理内存”。实际占用取决于触碰了哪些页、页缓存是否共享、是否发生私有写入，以及内核回收压力。

`PSS` 是 **Linux `smaps` 中围绕当前 VMA/映射的归因快照**，不是硬件计数器，也不是“这项服务真正占了多少 RAM”的永久结论；共享关系、驻留状态和映射数变化后，下一次采样可不同。`RSS`、`PSS`、`USS/private resident` 都在讨论 CPU 主存中的进程映射：它们不包括独立 GPU 显存，也不自动给出进程生命周期的峰值。要回答峰值，应使用单独的时间序列或峰值指标，并注明采样间隔与口径。

## 6. 文件映射为什么适合大型模型

llama.cpp 一类本地推理程序可以把模型文件映射进地址空间，让操作系统按访问需要调入页面。这样做的优势包括：

- 不必先把整个文件额外复制到一个同样大小的用户缓冲区；
- 文件页可以利用操作系统页缓存；
- 未访问部分不必立刻驻留；
- 多个只读使用者可能共享文件后备页。

但映射不是“零成本魔法”：首次访问可能等待存储 I/O；随机访问可能造成大量缺页；内存压力会驱逐页面；把数据送到独立 GPU 显存仍可能需要传输或设备侧映射机制。

把这张系统图对应到实际程序的装载与后端选择，见 [[AI/20-LLM/50-实现/04-llama.cpp构建后端与调用链|llama.cpp 构建、后端与调用链]]。

## 7. CPU 地址与 GPU 地址不能想当然地互换

独立 GPU 常有自己的设备内存和地址转换。CUDA 的统一虚拟寻址或统一内存能提供更统一的编程视图，却不意味着所有数据始终位于同一物理存储，也不保证迁移没有成本。

分析一次 CPU/GPU 推理时，至少分开问：

1. 模型文件是否映射到 CPU 进程地址空间？
2. 当前工作集哪些页驻留在主存？
3. 哪些张量已复制或迁移到设备显存？
4. CPU 与 GPU 是否在同一数据上等待同步？

CUDA 的具体执行与内存路线见 [[计算机知识/40-并行与异构计算/01-CUDA/01-CPU与GPU异构执行模型|CPU 与 GPU 异构执行模型]]。

## 8. 六种常被混淆的问题

- **内存泄漏**：程序失去释放某些仍被占用资源的路径，长期运行时占用可能持续增长；
- **分配器保留**：对象已经 `free`/`delete`，但通用分配器可能仍把 arena、size class 或线程缓存留给本进程复用；RSS 不立即下降不能单独证明仍有可达的 live object，也不能排除真实泄漏；
- **地址空间碎片**：空闲区间存在但不满足某次连续虚拟范围或分配器要求；
- **缺页抖动**：工作集大于可用内存，页面频繁换入换出；
- **口径混淆**：分配器的 live/requested bytes、已保留或 retained 的虚拟范围、平台/工具所称 committed/backed 容量、当前 resident 页和峰值不是同一数字；`commit` 的精确定义还随系统而变，讨论“用了多少内存”必须先标出平台、工具与口径；
- **越界/悬空访问**：程序访问不属于有效对象生命周期或映射的地址，属于正确性问题，不是“内存不够”的同义词。

C++ 对象生命周期与指针规则见 [[计算机知识/10-编程语言/02-C++/03-指针引用const与生命周期|指针、引用、const 与生命周期]]。

## 练习

1. 画出两个进程各自的虚拟地址空间，让它们共享一页只读库代码，同时各自拥有一页私有栈。标明“地址相同/不同”与“物理页相同/不同”是两组独立问题。
2. 一份 8 GiB 模型被映射后，进程只顺序读取前 512 MiB。列出“映射大小”“已触碰工作集”“可能常驻量”三个概念，说明为什么不能仅凭 8 GiB 推断 RSS。
3. 比较“读取文件到新缓冲区”和“只读文件映射”各自可能发生的数据复制、缺页和共享机会。
4. 为一次 GPU 推理画出 SSD → 页缓存/主存 → GPU 显存 → 计算单元的路径，并在每条箭头旁标记潜在等待。
5. 对“第一次访问某个已驻留页”分别画出 TLB hit 与 TLB miss + page-table walk 两条路径；再说明哪些条件才会变成 page fault。

## 成功标准

- 你能明确说出指针通常持有虚拟地址，而非可直接观察的物理地址；
- 你不会把文件映射大小、RSS、私有物理占用和 GPU 显存混成一个数字；
- 你能解释按需分页与写时复制为什么既节省复制，也可能引入首次访问成本；
- 你不会把 TLB miss、page-table walk 和 page fault 当成同一个事件；
- 你能区分 live allocation、allocator reserve、虚拟映射、RSS 与历史峰值；
- 你能用“对象生命周期问题”而非“虚拟内存坏了”描述典型悬空指针错误。
