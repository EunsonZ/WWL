# 图像表示、色彩空间、采样与图像编码

## 本课目标

学完后，你应该能够：

- 从宽、高、通道数和每通道位深估算未压缩图像大小；
- 区分像素数、显示尺寸、空间分辨率、色彩精度和动态范围；
- 解释线性光 RGB 与带传递函数的 RGB 为什么不能混着做插值、滤波和合成；
- 区分 RGB、工程上常说的 YUV 与数字图像中的 YCbCr；
- 读懂 `4:4:4`、`4:2:2`、`4:2:0` 的采样含义和边缘风险；
- 说明 straight alpha 与 premultiplied alpha 的不同；
- 按机制和使用边界比较 JPEG、PNG、WebP 与 AVIF；
- 把像素数据、编码位流、容器和元数据分开审计。

本课关注静态光栅图像的工程表示。卷积、二维频域和 Patch 的数学入口在 [[数学/70-信号处理与多模态数学/01-空间几何Patch卷积与频域|空间几何、Patch、卷积与频域]]；图像模型如何消费这些像素属于 AI 域，而不是本页的编码结论。

> [!tip] 首读 20 分钟
> 先读像素与未压缩大小、RGB/YCbCr、4:2:0 和 JPEG/PNG/WebP/AVIF 的机制边界，目标是能解释“分辨率一样但颜色或边缘不一样”。二读再展开线性光/传递函数、straight/premultiplied alpha、chroma siting 与 HDR/色彩元数据。

## 1. 像素不是“一个颜色数字”

光栅图像把二维区域离散成像素网格。一个像素通常含多个**样本**：例如 RGB 三个颜色样本，或 RGBA 三个颜色样本加一个透明度样本。必须同时记录：

| 字段 | 回答的问题 | 常见误读 |
| --- | --- | --- |
| 宽 × 高 | 有多少像素位置 | 把它当成物理尺寸或清晰度的全部 |
| 通道/分量 | 每个位置记录什么 | 看到三通道就断言一定是 RGB |
| 每样本位深 | 每个分量有多少离散码值 | 把 `8 bit/channel` 误写成 `8 bit/pixel` |
| 数值范围 | full range、limited range，整数还是浮点 | 只看位深，不看黑白点和偏置 |
| 色彩描述 | primaries、白点、传递函数、矩阵 | 把同一组三元组当成跨色彩空间的同一颜色 |
| 布局 | packed/planar、通道顺序、行跨度 | 把文件字节直接当成紧密排列的 RGB |

未压缩、紧密排列且无行填充时，大小近似为：

$$
\text{bytes}=W\times H\times C\times\frac{b}{8},
$$

其中 $W,H$ 是宽高，$C$ 是通道数，$b$ 是每通道位数。1920×1080、RGB、8 bit/通道约为：

$$
1920\times1080\times3=6\,220\,800\ \text{bytes}\approx5.93\ \text{MiB}.
$$

这不是 PNG/JPEG 文件大小，也没有计入行对齐、调色板、mipmap、容器和元数据。

### 分辨率与位深各管什么

- **像素尺寸** 例如 1920×1080，只描述采样网格。
- **空间分辨率** 还与镜头、传感器、对焦、运动模糊、缩放核和显示尺寸有关。把模糊的 640×480 放大到 4K 不会重获细节。
- **位深** 控制每个样本的码值数量。8 bit 样本有 256 个可能码值；10 bit 有 1024 个，但这不自动等于更宽色域或 HDR。
- **色域与动态范围** 取决于 primaries、白点、传递函数、编码范围和显示映射；它们不能由“10 bit”单独推出。

> [!example] 同样的三元组不一定是同一种颜色
> `RGB=(128,64,32)` 若没有说明 sRGB、Display-P3 或其他 primaries/传递函数，就不是完整的色彩描述。解码器成功读出三个整数，只证明语法解析成功，不证明显示颜色正确。

## 2. 线性光与 gamma 编码值

传感器接收和物理光能混合更接近**线性光**运算；存储与显示信号常经过非线性传递函数，使有限码值更符合视觉敏感度或显示系统约定。日常口语会把许多非线性传递函数统称为“gamma”，但 sRGB 的传递函数并不是单一幂函数；HDR 的 PQ、HLG 也不能用一个普通 gamma 数代替。

设 $E$ 是归一化线性光强，编码值为 $V=f(E)$：

```text
场景/线性光 E ──传递函数 f──> 非线性编码值 V ──量化与存储
显示线性化   E <──逆传递函数── V
```

以下操作原则上应在线性光域进行，再编码回目标传递函数：

- 光能相加、半透明合成；
- 物理意义上的曝光缩放；
- 希望保持光度正确的缩放、模糊和插值。

直接平均两个 sRGB 码值通常不会得到线性光上“各占一半”的亮度。非线性域处理有时是有意的视觉效果或旧工作流兼容选择，但必须明确，而不是误以为码值就是光强。

> [!failure] 反例：8 bit RGB 就一定是 sRGB
> 错。RGB 只给出分量坐标形式；primaries、白点和传递函数仍需约定。缺少或被软件忽略的 ICC/CICP/sRGB 等元数据，会让相同像素码值出现不同外观。

## 3. RGB、YUV 与 YCbCr

### 3.1 RGB

RGB 用三个基色分量描述颜色，适合显示和许多图像处理。但“RGB”不是唯一色彩空间：不同的 primaries、白点、传递函数和范围会定义不同 RGB 空间。

### 3.2 YUV 是常被泛化使用的历史术语

严格说，YUV 源自模拟电视信号。数字图像和视频文件里更常见的是 **YCbCr**：

- $Y'$ 是由**非线性** $R'G'B'$ 计算的 luma（亮度信号），撇号提醒分量已经过传递函数；
- $C_b$、$C_r$ 是蓝差和红差色度分量；
- 变换系数、full/limited range、采样位置必须由具体规范或元数据决定。

$Y'$ 不等于物理光度学中的 luminance $Y$。因此只写“YUV 文件”仍不够：需要问是哪个矩阵、范围、位深、chroma siting 和打包方式。

从 RGB 转 YCbCr 的一个抽象形式是：

$$
\begin{bmatrix}Y'\\C_b\\C_r\end{bmatrix}
=M
\begin{bmatrix}R'\\G'\\B'\end{bmatrix}
+\text{offset}.
$$

矩阵 $M$ 和 offset 不是普适常量。套错 BT.601/BT.709 类矩阵或把 limited range 当 full range，会造成色偏、黑位抬升或高光裁剪。

## 4. 色度子采样：少记颜色位置，不等于少记亮度位置

人眼通常对亮度细节比色度细节敏感，编码系统因此可以降低色度的空间采样率。常见记法的核心直觉如下：

| 格式 | luma $Y'$ | 横向色度 | 纵向色度 | 典型影响 |
| --- | --- | --- | --- | --- |
| 4:4:4 | 每像素 | 不降采样 | 不降采样 | 彩色细线与文字最稳，数据更多 |
| 4:2:2 | 每像素 | 减半 | 不减半 | 横向色度分辨率降低 |
| 4:2:0 | 每像素 | 减半 | 通常也减半 | 每 2×2 luma 区域约一组 Cb/Cr，压缩更强 |

`4:2:0` 的“0”不是“没有色度”，也不是每四个像素随便挑一个颜色。实际色度样本位于网格何处（chroma siting）以及如何滤波，下采样和上采样实现必须一致。

### 可观察例子：为什么彩色 UI 容易受伤

红色的一像素竖线放在灰色背景上时，luma 变化可能不大但色度变化剧烈。4:2:0 会把邻近像素共享的色度平均，解码上采样后边缘可能出现彩色模糊或渗色。自然照片的纹理往往更能容忍这种处理；像素画、屏幕文字、图表和科学伪彩色图则可能不适合。

> [!failure] 反例：4:2:0 等于“画质变成四分之一”
> 错。luma 网格通常仍保留全分辨率，降低的是两个色度分量的空间采样；最终损伤还取决于内容、滤波器、位深和码率。它也不是无损变换：被滤掉的高频色度不能从上采样凭空恢复。

## 5. Alpha：透明度不是第四种颜色

Alpha 常表示覆盖率或不透明度：$\alpha=0$ 全透明，$\alpha=1$ 全不透明。两种内存/格式约定必须区分：

- **straight / unassociated alpha**：存原始颜色 $C$ 和 $\alpha$；
- **premultiplied / associated alpha**：存 $C_p=\alpha C$ 和 $\alpha$。

前景 over 背景在线性光、premultiplied 表示下可写为：

$$
C_{out}=C_{p,fg}+(1-\alpha_{fg})C_{p,bg},
$$

$$
\alpha_{out}=\alpha_{fg}+(1-\alpha_{fg})\alpha_{bg}.
$$

PNG 文件中的 alpha 是 unassociated，且 alpha 本身不做 gamma 校正；图形 API 的内存表面却可能采用 premultiplied alpha。若导入导出时忘记转换，边缘会出现黑边、白边或颜色泄漏。完全透明像素的 RGB 仍可能携带数据，但某些编码器会为压缩修改它；不能把透明区域当作可靠的秘密存储。

## 6. JPEG、PNG、WebP、AVIF 的机制与定位

下表的规范和当前版本入口已于 **2026-09-03** 核验。实现支持、编码器默认值、浏览器/系统兼容性和性能会变化，部署当天仍需用目标解码器实测。

| 格式 | 主要机制 | 有损/无损 | Alpha | 适合与边界 |
| --- | --- | --- | --- | --- |
| JPEG（JPEG-1 常见 DCT 路线） | 常先做颜色变换/可选色度子采样，把块变换系数量化，再熵编码 | 主要为有损；标准家族含多种过程，日常 JPEG 不等于所有 JPEG 标准 | 常见 JPEG-1 文件无通用 alpha | 兼容广、照片常用；高压缩时有块效应、振铃、渐变断层，不宜反复编辑保存 |
| PNG | 逐行滤波预测后用 DEFLATE 无损压缩；支持灰度、真彩、索引色 | 无损 | 支持 alpha 或 `tRNS` 透明信息 | 图标、文字、截图、需要精确像素时稳妥；照片不一定小，且“像素无损”不保证元数据被保留 |
| WebP | lossy 路线使用 VP8 帧内预测/变换；lossless 路线使用预测、颜色变换、LZ77、前缀编码和颜色缓存；RIFF 容器可带动画/元数据 | 两者都有 | 支持，lossy RGB 可配独立 alpha | Web 分发灵活；必须说明 lossy/lossless、alpha、动画和元数据处理，不要只写 `.webp` |
| AVIF | 在 HEIF/ISOBMFF 中存 AV1 图像项；可用 AV1 的预测、变换、量化等工具，alpha 可作辅助图像 | 可有损，也可按相应 AV1/AVIF 约束做无损 | 支持 | 支持 SDR/HDR、WCG、多位深和序列；编码成本、具体 profile 与目标解码器能力需现场验证 |

### 6.1 JPEG 不是“直接删掉高频像素”

典型 baseline JPEG 的理解路径是：

```text
像素 → 颜色变换 → 可选色度子采样 → 分块 → DCT
     → 量化（主要有损点） → 系数重排/差分 → 熵编码
```

DCT 本身是可逆变换思路；不可逆主要来自量化、色度子采样、舍入和范围转换。熵编码只是在不改变已量化符号的前提下缩短表示。JPEG 的“quality=85”不是跨软件统一尺度，不能据此精确复现另一个编码器。

### 6.2 PNG 无损的对象是解码后的样本

PNG 用行滤波让相邻样本的差异更容易压缩，再以 DEFLATE 编码。解码能精确恢复 PNG 规定的图像样本；但导出程序可能在进入 PNG 之前已经把 16 bit 降到 8 bit、把广色域转为 sRGB、预合成 alpha，或丢弃 EXIF/ICC/文本块。**无损 codec 不等于整个编辑流程无损。**

### 6.3 WebP 和 AVIF 都不能只用后缀判断画质

它们容纳的编码模式、位深、alpha、色度采样和元数据不同。一个高码率 4:4:4 文件与低码率 4:2:0 文件，即使同后缀也不是同一质量条件。格式比较必须固定：源图、尺寸、色彩管理、alpha、编码器版本/参数、文件大小和评价方法。

## 7. 元数据与安全边界

图像文件可能同时包含：

- 像素尺寸、位深、色彩 profile/CICP、方向；
- EXIF 的拍摄时间、设备、镜头、GPS 等；
- XMP/IPTC 的作者、版权、编辑工作流；
- 缩略图、评论、动画时序、HDR mastering/内容亮度信息。

必须把三个问题分开：

1. **位流能否解码？** 只证明编码数据语法可用。
2. **显示是否正确？** 还依赖方向、色彩空间、alpha 和显示映射。
3. **分享是否安全？** 还要审计 EXIF/XMP/缩略图等隐私字段。

“移除元数据”也不是视觉中立操作：删除方向可能让图像旋转错误，删除 ICC/CICP 可能改变颜色解释，删除 HDR 元数据可能改变 tone mapping。正确做法是按发布目的建立保留/删除清单，重新解码检查显示，再用独立工具核查元数据；不要用改后缀或截图当作可靠清理证明。

## 8. 选择格式的决策顺序

1. 先问是否必须逐样本可逆，是否要继续编辑或保存科学/医学证据。
2. 再问是否需要 alpha、动画、HDR/WCG、10 bit 以上或特定元数据。
3. 列出必须支持的浏览器、系统、硬件解码器和工作流软件。
4. 用代表性源图固定参数做 A/B：照片、文字、渐变、彩色细线、透明边缘分别检查。
5. 同时记录编码时间、解码时间、内存、文件大小和质量；不要只追求最小字节数。
6. 若文件要公开，最后单独做隐私元数据审计。

## 练习

1. 计算 3840×2160、RGBA、16 bit/通道、紧密排列图像的未压缩大小，分别写出 byte 和 MiB。
2. 解释为什么把一张 8 bit sRGB 图像只改容器标签为 10 bit 或 Display-P3，不会创造更平滑的原始渐变或更宽的真实色域。
3. 为“透明 UI 图标”“相机照片网页分发”“需要逐像素复核的分割掩码”各选一种候选格式，并写出必须实测的条件。
4. 画出 4×2 个 luma 样本在 4:4:4、4:2:2、4:2:0 下大约需要多少组 Cb/Cr；说明 chroma siting 为什么仍需另行规定。
5. 一张图片转码后像素看起来相同但 GPS 消失，这是不是“PNG/JPEG 编码错误”？请从像素与元数据两层回答。

## 成功标准

- [ ] 得到 RGBA16 4K 大小为 $3840\times2160\times4\times2=66\,355\,200$ byte，约 63.28 MiB，且说明未计行填充和元数据。
- [ ] 能完整写出 primaries、白点、传递函数、矩阵/范围中至少三项，而不把“RGB”或“10 bit”当成完整色彩空间。
- [ ] 能解释线性光合成、luma 与 luminance、4:2:0 以及两种 alpha 表示。
- [ ] 能把变换、量化、预测和熵编码分别定位，不把所有压缩步骤都叫“丢信息”。
- [ ] 能按内容、透明度、色彩、兼容性、性能、元数据六个维度比较格式。
- [ ] 能说明 codec 解码成功、视觉正确和隐私安全是三层不同证据。

## 官方来源与核验边界

以下入口于 **2026-09-03** 核验；用于支持格式机制和语义，不代表本机所有编码器/解码器已兼容或跑通：
