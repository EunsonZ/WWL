# 安全重构与链接维护

> [!goal] 你将学会
> 在移动、重命名、拆分或合并之前识别影响面；通过 Backlinks、Outgoing links、unresolved links、Undo、File recovery 与版本差异降低损失风险。

## 重构前后最短闭环

```text
确认目标 → 查看入链与出链 → 做一个小改动 → 立即验证 → 再继续
```

大规模整理最危险的不是“操作慢”，而是连续做了几十步后才发现链接、属性或目录约定被破坏。

## 移动与重命名

在 Settings → Files and links 中确认 **Automatically update internal links** 的行为。用 File explorer 或 Obsidian 的 Rename/Move 命令移动文件，让 Obsidian 有机会更新内部链接；自动化也应传精确路径并使用 Obsidian 的语义命令。

不要用系统文件管理器直接批量重命名一组正在被引用的文件，除非你已经准备好检查并修复全部链接。

## 链接影响面

对准备重命名的文件，至少查看：

- **Backlinks / Linked mentions**：哪些文件真正链接到当前文件；
- **Unlinked mentions**：哪些地方只出现了相同文本，尚未形成链接；
- **Outgoing links**：当前文件链接出去的目标；
- **Search**：别名、标准 Markdown 链接和代码块中可能还有文本引用；
- **Properties**：`related`、`project` 等字段里的 wikilink 是否更新。

> [!important] 反向链接不是复制的文本
> Backlinks 是 Obsidian 根据索引计算的视图。它不会在目标笔记正文里自动写回一条“来源链接”。是否需要在正文中保留显式导航，由你的工作流决定。

## 一次安全重命名练习

1. 新建 `Obsidian知识/30-实践/01-实验区/重构目标-旧名称.md`，写入一个 H1。
2. 新建 `Obsidian知识/30-实践/01-实验区/重构来源.md`，写入 `[[Obsidian知识/30-实践/01-实验区/重构目标-旧名称]]`。
3. 打开目标，确认 Backlinks 能看到来源。
4. 在 Obsidian 内把目标改名为 `重构目标-新名称`。
5. 打开来源，确认链接文本或目标已更新且可点击。
6. 搜索 `重构目标-旧名称`，判断剩余结果是真正的旧链接，还是本课程代码示例。

这里最后一步很重要：搜索命中并不总是断链。代码块、引用或历史说明也可能有意保留旧名称。

## 拆分与合并的属性冲突

拆分时要决定哪些属性属于新文件：

- `created` 可以是提取日期，也可以保留原始捕获日期；
- `source`、`related` 往往需要保留；
- `status` 与 `type` 可能需要改为新文件的类型；
- `tags` 不应无脑复制全部父笔记标签。

合并时要处理：

- 同名属性值冲突；
- 两个 H1、两个摘要或重复段落；
- aliases 是否仍有意义；
- 旧文件名是否应成为目标的 alias；
- Base 过滤结果是否因为 `type/status/path` 改变。

## 恢复工具的边界

| 工具 | 最适合 | 边界 |
| --- | --- | --- |
| Undo | 刚发生的编辑或命令 | 关闭窗口、长操作链后不一定可靠 |
| File recovery | 找回 Obsidian 保存的本地快照 | 不是完整备份，也有保留期限 |
| 系统废纸篓 | 恢复被普通删除的文件 | 永久删除后不可依赖 |
| Git | 审计多文件 diff、回到已提交版本 | 未提交改动需要额外小心 |
| 云同步历史 | 多设备事故恢复 | 同步不是备份，冲突策略因服务而异 |

## 检查结果

重命名练习成功时：来源链接仍可打开新目标；新目标 Backlinks 仍显示来源；没有真正的 unresolved link。完成后删除两篇练习文件，或保留在 `Obsidian知识/30-实践/01-实验区/` 继续实验。

## 安全底线

- 覆盖、删除、合并、批量重命名之前先确认范围。
- 不直接修改 `.obsidian/workspace.json` 或插件运行时状态来“修链接”。
- 不同时启用多个没有冲突策略的同步写入源。
- 看到错误先停止扩大变更，再读取最新文件与差异。
