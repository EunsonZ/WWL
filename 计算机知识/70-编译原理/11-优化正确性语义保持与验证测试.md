# 优化正确性、语义保持与验证测试

## 本课目标

学完后，你应该能够：

- 用可观察行为描述 observational equivalence，并用 refinement 处理未定义行为与非确定性；
- 指出整数溢出、浮点、并发、异常和副作用为何会破坏“代数上显然成立”的改写；
- 区分 IR verifier、翻译验证、形式化证明和各种测试各自能证明什么、不能证明什么；
- 设计 unit、property、differential、metamorphic 与 fuzz 测试的组合，并在失败后用 reducer 生成最小复现；
- 为一个优化 Pass 写出可执行的证据计划，而不是把“测试通过”误说成完整正确性证明。

## 1. 正确性问题不是“输出数字一样”

程序的**可观察行为**可能包括：

- 正常返回值与退出状态；
- 标准输出、文件、网络等外部 I/O；
- 可观察的内存写入、volatile 或原子操作；
- 抛出的异常、异常类型及发生顺序；
- 是否终止，或允许哪些非确定执行轨迹；
- 在语言契约要求下可观察的浮点环境、资源释放与同步关系。

因此，比较源程序 `S` 与优化后程序 `T`，不能只在几个输入上比较最终整数。更有用的抽象是执行轨迹：

```text
observe(execute(program, input, environment))
    = return_value
    + external_effect_trace
    + exception_or_termination
    + allowed_concurrency_observations
```

哪些事件属于观察，必须由源语言、IR 层次和编译契约共同决定。

## 2. Observational equivalence 与 refinement

### 2.1 观察等价

若把程序放进所有被允许的上下文中，两者产生相同的可观察行为集合，就称它们在该语义下**观察等价（observationally equivalent）**。

```text
for every allowed context C and defined input x:
    observations(C[S], x) = observations(C[T], x)
```

这是强而清晰的目标，但真实语言可能包含非确定性、未定义行为和实现允许的多种结果，简单的“唯一输出相等”不够。

### 2.2 精化

**Refinement** 更常表述为：对于源程序具有已定义语义的输入，目标程序不能引入源程序不允许的新行为；在允许非确定性的模型里，目标行为集合通常应包含于源行为集合，并满足进展、终止或资源方面另行声明的条件。

```text
if source_is_defined(S, x):
    assert behaviors(T, x) subset_of behaviors(S, x)
```

这不是授权优化器在任意时刻“利用 UB”。关键边界是：只有源执行确实越过语言规定的未定义行为前提时，源语义才不再提供普通行为承诺；不能把一个本来定义良好的执行改造成陷阱、额外 I/O 或数据竞争。

## 3. 五类最容易被忽略的语义边界

### 3.1 未定义行为与带前提的改写

考虑把除法改为移位：

```text
candidate:
    x / 2  ->  x >> 1
```

它是否正确取决于负数舍入、右移规则、整数宽度和溢出语义。一个优化规则应显式写条件：

```text
if x_is_nonnegative and division_rounds_toward_zero and shift_matches_width:
    replace(x / 2, x >> 1)
```

“在我测试的正数上都相等”不是普遍证明。

### 3.2 整数溢出

不同语言或 IR 会把溢出定义为模回绕、抛异常、饱和、产生 poison，或在特定条件下未定义。例如：

```text
(x + 1) > x  ->  true
```

只有在排除最大值溢出，或语义允许基于无溢出前提推理时才成立；对模回绕整数，在最大值处为假。优化规则必须绑定到准确的类型与 flags，不能只看操作名。

### 3.3 浮点

浮点加法通常不满足实数加法的结合律：

```text
(a + b) + c  !=  a + (b + c)   // for some finite values
```

NaN、正负零、无穷、舍入模式、异常标志和 fused operation 都可能可观察。只有 fast-math 一类明确放宽契约的模式，才能采用相应重结合；即便合法，也要评估数值误差与可重复性。

### 3.4 并发

编译器不能只保持单线程内的最终值，还要保持语言内存模型允许的 happens-before、原子顺序与同步行为。

```text
data = 42
release_store(ready, true)
```

若把数据写移动到 release 发布之后，另一个 acquire 读取者可能看到 `ready` 却看不到新数据。普通 CSE、DCE 与代码移动必须识别原子和内存 effect；有数据竞争即 UB 的语言仍不能破坏无竞争程序的定义行为。

### 3.5 异常与副作用顺序

```text
print("start")
y = may_throw(x)
print("done")
```

把 `may_throw` 提到第一个输出之前，会改变异常发生时的 I/O 轨迹；把它延后又可能多打印 `done`。短路求值、析构、finally、边界检查、空指针检查、volatile 与外部调用都可能形成顺序约束。

## 4. IR verifier 只检查“形状合法”

IR verifier 常检查：

- 指令操作数与类型匹配；
- SSA 定义支配使用；
- 基本块终结指令和 CFG 边一致；
- phi 参数与前驱对应；
- 调用签名、属性和元数据满足结构约束。

```text
verify(ir):
    check_types()
    check_ssa_dominance()
    check_cfg_well_formed()
    check_instruction_invariants()
```

它能快速阻止畸形 IR 进入后续阶段，却通常不能证明优化前后语义相同。把 `add` 误改为 `subtract` 仍可能生成结构完美的 IR。应把 verifier 理解为必要的结构防线，而不是语义等价检查器。

## 5. 三种更强的正确性路线

### 5.1 翻译验证

**Translation validation** 不必预先证明整个优化器实现，而是在每次编译时验证这一对输入/输出 IR 的关系。

```text
before = snapshot(ir)
after = optimize(copy(before))

proof_or_counterexample = validate_refinement(before, after)
if validation_failed:
    reject_or_report(after)
```

优势是能约束复杂、持续变化的优化器；困难在于循环、内存、浮点、并发和大程序使等价检查昂贵或不完备。验证器本身也属于可信计算基。

### 5.2 形式化证明

形式化路线给出语言/IR 语义、优化规则与机器可检查证明。可以证明单条 rewrite，也可以验证优化器或通过 proof-producing compilation 携带证据。

它提供比测试更强的全称保证，但不自动覆盖未建模的解析器、代码生成器、运行库、硬件缺陷或错误的规范。**证明的是模型中的命题**，所以规范质量与可信基边界必须明确。

### 5.3 测试

测试不能穷尽所有程序，却擅长发现实现错误、规格遗漏与组合问题。实践中最有效的策略不是只选一种，而是让 verifier、规则证明/验证器与多层测试互相补位。

## 6. 测试组合与各自的 oracle

| 方法 | 生成什么 | 如何判定 | 擅长发现 | 主要盲区 |
| --- | --- | --- | --- | --- |
| Unit | 手工构造的小 IR | 精确输出或不变量 | 单条规则、边界分支 | Pass 组合与未知输入 |
| Property | 满足约束的随机 IR | 语义属性、结构属性 | 大量参数组合 | 属性本身可能太弱 |
| Differential | 同一程序的两种编译/执行 | 观察轨迹对比 | 误编译、后端差异 | 两边可能同错，UB 会污染 oracle |
| Metamorphic | 对输入程序做已知关系变换 | 结果应满足关系 | 缺少标准答案时的异常 | 关系设计错误或覆盖有限 |
| Fuzz | 语法/类型正确的随机程序或 IR | 崩溃、超时、差分、不变量 | 未预料组合与健壮性 | 可读性差、UB 过滤困难 |

### 6.1 Unit 与 property

单元测试要覆盖正例与“差一点就合法”的反例：

```text
property_constant_fold(expr, env):
    assume expr is defined under env
    folded = fold(expr)
    assert interpret(expr, env) == interpret(folded, env)
```

还应验证 Pass 声称保持的结构性质，以及对不满足前提的候选保持不变。

### 6.2 Differential

差分测试可以比较 `optimization_off` 与 `optimization_on`，也可以比较解释器、参考后端和被测后端：

```text
program = generate_defined_program(seed)
reference = run(compile(program, optimization = off))
candidate = run(compile(program, optimization = on))
assert same_observation(reference, candidate)
```

关键是生成器或动态检查必须尽量排除 UB，并规范化地址、时间、线程调度等本就不稳定的观察。否则差异不一定是误编译。

### 6.3 Metamorphic

当没有可信参考实现时，可构造变形关系。例如给纯表达式加入一个确知无用的局部值，结果不应变化：

```text
p2 = insert_unused_pure_computation(p1)
assert observation(compile_and_run(p1))
       == observation(compile_and_run(p2))
```

关系本身必须经过语义审查。加入“无用”除法若可能除零，或加入分配会改变可观察资源行为，就不是安全变形。

### 6.4 Fuzz 与 reducer

Fuzzer 负责探索巨大输入空间；失败后 reducer 在保持复现条件的前提下删除函数、块、指令和类型复杂度：

```text
while exists smaller_candidate_that_still_fails:
    failing_program = choose_smallest_failing_candidate()
return failing_program
```

reducer 不是美化工具，而是调试与回归测试的桥梁。最小复现应记录 seed、编译选项、目标、环境、观察差异和是否依赖未定义行为。

## 7. 为一个 Pass 建立证据阶梯

以 LICM 为例，可以按以下层次验证：

1. verifier：每次变换后 IR 结构仍合法；
2. unit：纯运算可外提，可能写别名位置、条件陷阱、volatile 与原子不能错误外提；
3. property：随机生成小循环，用解释器比较外提前后的定义行为；
4. differential：优化开/关在多个后端、多个优化组合下比较观察轨迹；
5. metamorphic：改变无关块名、插入纯死计算、拆分不影响语义的块，结果应稳定；
6. fuzz：生成带控制流、异常边和内存操作的合法 IR；
7. reduce：任何失败最小化后固化为回归测试；
8. 高风险规则：增加翻译验证或形式化证明。

这是一条证据链，不是“测试数量越多越正确”。每层都应写明 oracle、假设和遗漏面。

## 8. 反例：差分结果相同仍可能不够

- 两个后端都忽略了同一浮点异常标志，因此结果一致但都违反规范。
- 测试程序触发源语言 UB，优化开关产生不同结果，但不能直接判定优化器错误。
- 只比较返回值，漏掉了多执行一次 I/O、异常顺序变化或资源未释放。
- 并发测试碰巧每次采用同一调度，没有探索被错误重排后新增的行为。
- reducer 在缩减时引入 UB，使最小样例不再证明原故障。

所以失败分类与测试夹具本身也要审查。

## 练习

1. 为 `(x + 1) > x -> true` 分别在模回绕整数、溢出陷阱整数和“有 no-overflow 前提”的 IR 下判断合法性。
2. 构造一个浮点重结合反例，写明 NaN、舍入或有穷大数中的至少一个影响因素。
3. 设计一个优化前后返回值相同、但异常或 I/O 轨迹不同的样例；说明只比较 stdout 或只比较返回值各会漏掉什么。
4. 为 DCE 写测试矩阵：纯指令、可能陷阱指令、未知调用、volatile、原子和永不执行块。
5. 设计一个生成“无 UB 小程序”的差分测试器伪代码，并列出仍需规范化的非确定观察。
6. 给一次 fuzz 失败设计 reducer 顺序；解释为何每次缩减都必须重新确认故障谓词和定义行为。

## 成功标准

- 你能明确写出比较的是返回值、effect trace、异常、终止还是并发行为集合；
- 你不会把 IR verifier 通过称为语义保持证明；
- 你能解释 refinement 为何比“所有输入输出逐点相等”更适合带 UB 与非确定性的语言；
- 你能为一个 Pass 组合至少四种互补测试，并说明各自 oracle；
- 你能把 fuzz 失败最小化为保留定义行为、选项和观察差异的回归用例。
