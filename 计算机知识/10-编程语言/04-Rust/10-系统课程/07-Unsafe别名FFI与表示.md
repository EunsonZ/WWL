# unsafe 审计：安全封装必须让所有安全调用都成立

> **学习位置**：[[计算机知识/00-开始/课程地图/03-Rust-课程地图|Rust课程地图]] · **适用边界**：Rust 2021 edition 兼容示例；2024 edition 差异另行标识。

## unsafe 不取消 Rust 的语义要求

裸指针解引用、调用某些外部函数和访问某些底层设施需要 unsafe，因为编译器无法从现有信息证明前提。作者仍要保证非空与有效范围、对齐、初始化、生命周期、别名和线程同步等要求。

一个安全函数如果内部执行 unsafe，却要求调用者默默遵守类型签名没有体现的安全前提，可能是不健全的封装。合理方案是验证前提，把不可验证前提放到显式 unsafe API 的 Safety 文档，或改变类型让非法调用无法构造。

## `from_raw_parts` 不只是拼接地址和长度

从裸指针构造切片时，长度和地址必须描述同一合法分配内的有效元素区域，还要满足对齐、初始化、别名及大小等契约。长度为零也不代表可以随意使用空或未对齐指针；应查具体接口的非空、对齐要求。

把 `*const T` 转成 `&T` 会建立比“某次数值地址存在”更强的语义承诺。不能先造出无效引用，之后再在安全代码里检查并补救。检查必须发生在构造引用之前。

## 初始化与析构要一起设计

`MaybeUninit<T>` 允许管理尚未初始化的存储，但 `assume_init` 要求已经确实构造出有效 T。全零字节不对所有类型都是有效值，例如某些引用、枚举或具有不变量的类型。

部分初始化数组若中途失败，要清理已经初始化的元素而不能析构未初始化部分。`ManuallyDrop` 允许控制析构时机，但不自动防止重复析构、泄漏或泄露无效内部状态。越接近手写容器，越需要逐步维护初始化元素计数。

## 表示属性与跨语言 ABI

`repr(C)` 对适用类型施加 C 兼容的布局规则，但不会把 String、Vec、trait object 的内部表示变成稳定跨语言接口。`repr(transparent)` 适用于特定包装场景，也仍有类型有效值与语义约束。

FFI 常用不透明句柄、指针加长度、明确整数宽度和成对释放函数。Rust 获得外部缓冲区前要确认分配器与释放协议；不能对来自任意 C 分配器的指针直接使用错误的 Rust 拥有容器析构。

实作消费见 [[计算机知识/10-编程语言/04-Rust/10-系统课程/12-Cargo组件工程与测量任务流#窄 C ABI：谁拥有缓冲，什么检查不能替你完成|测量组件的窄C ABI]]：调用方持有state/input/output，Rust只临时借用；形态与重叠检查在构造slice之前，但不能证明分配寿命或竞争访问。本机C调用与repr(C)布局实际核对后，回本节列出仍由外部调用者承担的前提。

## 字符串、回调和异常边界

`CString` 拥有无内嵌零字节、带终止符的 C 字符串；`CStr` 借用相应对象。UTF-8 合法性与零结尾是两种独立要求，外部 C 字符串不一定是 UTF-8，转换应处理失败而非无条件断言。

回调注册必须规定线程、次数、是否重入、取消后是否仍可能到达，以及 context 指向的数据何时销毁。跨边界的 panic/unwind 必须遵守 ABI；不能凭“本次没有 panic”证明设计安全。

## 别名模型与工具的证据强度

Rust 低层内存模型的部分细节还需参考语言文档和相关模型工作，不能把某个解释器检查模型当成最终标准的全部内容。保守、安全的 API 设计比利用灰色边缘更稳妥。

Miri 等工具可发现某些未定义行为，但目标支持、FFI、设备和并发模型有边界。Sanitizer、fuzzing 和代码审计是互补证据；没有报警不是形式化健全性证明。

## 练习：安全包装一个 C 缓冲区

外部 API 返回 `(pointer,length)` 并要求用专用 `release` 释放。包装类型应独占拥有句柄，构造时检查文档允许的空状态与长度；读取方法只返回借用；Drop 调用匹配释放；复制默认禁止或采用明确深复制；线程能力只能按外部库保证决定。

答案还必须考虑：释放函数是否可失败、是否要求特定线程、库卸载后是否仍能调用、回调是否可能再访问缓冲区。资源协议比一个 `unsafe { ... }` 块更大，但审计时应把这些关系尽量集中表达。
