# 结构化输出、Schema 与错误恢复

<!-- deep-review-02 -->
> [!tip] 本轮深化：从当前概念继续追问
> schema 只检查结构，不证明事实正确、权限充分或动作已完成。执行超时应进入结果未知的状态，再查幂等记录或实际状态，而非盲目重试。 深化与验证：[[AI/20-LLM/70-工程应用与工具链/09-Agent状态机幂等执行与提示注入边界|Agent状态机幂等执行与提示注入边界]]；[[AI/20-LLM/70-工程应用与工具链/10-LLM评测污染裁判偏差与统计检验|LLM评测污染裁判偏差与统计检验]]。


## 直觉：把自由文本放在“候选”一侧，把决定留给程序

让 LLM 输出 JSON、工具调用参数或表单字段，是为了让程序能稳定读取它，而不是让模型变成数据库或可信执行器。一个稳健流程将模型输出视为不可信字节：先限制大小，解析，再按 Schema/业务规则校验，最后才把**已验证字段**交给下游。

```text
LLM 原始文本
  → 长度/编码限制 → JSON 解析 → Schema 校验 → 业务/权限校验 → 人工确认或受限执行
                         │                  │                    │
                    格式失败             值不合法/越权          有副作用
                         └── 有界重试/降级 ──┴── 拒绝并记录原因 ──┴── 不由模型直接执行
```

## 精确定义：三层“有效”不同

| 层次 | 问题 | 示例 | 不能证明 |
| --- | --- | --- | --- |
| 语法有效 | 能否解析？ | 文本是 JSON | 字段齐全、类型正确或内容真实 |
| Schema 有效 | 形状是否符合约束？ | 必有 `answer/citations/confidence`，置信度在 0–1 | 引用支持结论、调用者有权访问资料 |
| 业务/权限有效 | 这个值在当前状态下可否使用？ | 工单 ID 属于当前租户；金额在限额内；动作需二次确认 | 结果符合用户真实意图或无安全后果 |

最小例子的 `validate_answer` 同时演示精确字段集合、类型/范围和“citation 必须来自已检索候选”的检查，见 [[AI/20-LLM/70-工程应用与工具链/02-Embedding-Chunking与最小RAG|最小 RAG]]。生产环境可使用 JSON Schema/Pydantic 等工具，但库名不是安全边界；固定 Schema 版本和自己的业务校验才是。

## 从上页候选回答到两种新任务

上一页的退款问句只走到一个有限终点：词袋检索先选出 `refund-1`，确定性 stub 把“处理时间通常为 3 个工作日”作为候选回答，`validate_answer()` 再确认结构及 citation 属于本次候选集合。它没有判断改写后的句子是否被原文蕴含，没有核实具体订单，也没有提交退款；因此这里将它当作“已有的 RAG 与 Schema 演示结果”承接，不再把 02 说成缺少引用或 Schema 校验。

接下来是两个对象不同的任务。**会议纪要提取**把一段纪要转成待办候选与未知项；即使 JSON 合格，日期仍须是真实日期、负责人仍须属于项目成员，写入前还要预览和由负责的人确认。**创建退款申请**则从事实回答切到有副作用的动作：现有练习字段 `order_id`、`reason`、`confirm` 不能替代服务端对订单归属、退款期限、重复申请和调用权限的检查。两者不必强行沿用同一篇资料或同一个 LLM 示例。

如果动作请求可能重试，幂等身份要绑定同一资源、目标状态和所依据的版本/条件；不能只复用一个 key 就把不同参数误认成同一请求。现成的受限行动合同见 [[AI/80-实践/05-RAG评测与私有服务/02-有引用的回答与可交付行动#从回答到行动：pending 不等于提交完成|有引用的回答与可交付行动]]：那里的教学 `FakeStore` 用 `(record_id, new_value, etag)` 元组与 receipt 演示精确重试，不是本页实现、真实退款 API 或密码学 fingerprint。Schema 错误可在有限预算内修正格式；业务/权限拒绝应停止，网络超时须查同一请求的结果，避免重复副作用。只有在该实践页的内存假状态中，已核验权限且取得实际物化 receipt 才标为 `materialized`；本页的 RAG 答案和有效 JSON，或行动处于 `pending`，都不算退款完成。失败会带来人工复核、重读版本或有界重试成本，具体由失败类别决定。

## 实际例子：提取待办而不把猜测写进系统

给定会议纪要，要求：

```json
{
  "tasks": [{"owner": "string|null", "action": "string", "due": "YYYY-MM-DD|null"}],
  "unknowns": ["string"]
}
```

程序还应检查 `due` 是真实日期、`owner` 属于该项目成员、action 长度受限并无 HTML/命令注入内容。没有明确负责人时用 `null` 并列入 `unknowns`，不是让模型补全一个人名。即使 JSON 完全合格，写入任务系统仍属于有副作用动作：展示预览、让负责的人确认、用服务端权限再次核验。

## 错误分类与恢复策略

| 失败 | 典型原因 | 可做什么 | 不该做什么 |
| --- | --- | --- | --- |
| 请求前失败 | 输入过大、未认证、禁止内容或配置缺失 | 直接拒绝；提示可修复输入；记录无敏感错误码 | 把原始敏感输入无限写入日志 |
| 瞬时调用失败 | 超时、限流、临时网络/服务错误 | 有上限的指数退避；使用 idempotency key；必要时切换已批准的降级路径 | 无限制重试或把同一写操作执行多次 |
| 解析/Schema 失败 | 截断、额外 prose、字段/枚举不合法 | 保留机器可读失败原因；一次或少数重试，明确要求只返回合约 | 默默“猜”字段或直接用正则修补高风险数据 |
| 业务/权限失败 | 引用不在候选、资源不属于调用者、金额越限 | 停止并返回可解释拒绝；要求人工/上游修正 | 把失败输入再交给模型来决定是否越权 |
| 语义不确定 | Schema 正确但事实无证据、动作歧义 | 要求补充来源/输入，或进入人工复核队列 | 用较高 `confidence` 数字当作真实性证明 |

重试必须有**预算**（例如最多两次）、**条件**（只对可恢复类别）、**幂等性**（下游写入附带请求 ID）和**可观测性**（记录结果类别而不是完整秘密）。每次重试要保留相同的权限与数据边界；“换一个 prompt 再试”不能绕过校验。

## 风险与恢复

- **Schema 漂移：** 输出合约、prompt、应用解析器和下游接口必须版本化。上线新字段前做兼容读取/双写或显式迁移，不让旧客户端把未知字段当成功。
- **注入与反序列化：** JSON 字符串可以携带 SQL、HTML 或命令样式内容；使用参数化查询、allowlist 枚举和安全渲染，绝不从模型文本拼接 shell/SQL。
- **记录与隐私：** 日志保存 schema 版本、错误码、字段长度、hash/匿名 ID、延迟和重试次数；默认不保存 prompt、完整回答、凭据或个人资料。
- **恢复：** 保留旧 Schema 和解析器直到请求耗尽；一旦错误率上升，关闭新特性或回滚到已验证合约，并隔离失败请求供脱敏复现。

## 练习与成功标准

给“创建退款申请”设计 Schema，包含 `order_id`、`reason` 和 `confirm`；列出哪些规则必须由服务端验证（订单归属、退款窗口、重复申请、权限），哪些只由模型协助提取。成功标准是：你能为五类失败各指定“拒绝、重试、降级或人工复核”之一，并说明为什么 Schema 通过仍不可自动执行退款。
