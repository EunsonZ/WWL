# TypeScript：泛型、类型运算与结构化兼容

> 阅读定位：严格类型检查；运行时语义属于 JavaScript，宿主 API 另行区分。返回 [[计算机知识/00-开始/课程地图/05-TypeScript-课程地图|TypeScript · 课程地图]]；全域入口 [[计算机知识/00-开始/全局导航/00-总学习地图|计算机知识库 · 总学习地图]]。

## 泛型保留输入输出关系

`function identity<T>(x:T):T` 不是“用 any 接受一切”，而是保留同一个 T 的关系。`keyof T` 提取键集合，`T[K]` 表示对应属性类型，合起来可以写一个不丢失类型信息的读取函数。

```typescript
function get<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}
const record = { id: 7, name: "Ada" };
const name = get(record, "name");
```

约束 `extends` 表达类型关系，不是让 T 在运行时继承某个构造器。结构化类型主要按成员形状判断兼容；但新对象字面量的额外属性检查、私有成员等规则会影响具体结果，不能概括为“只要看起来差不多就行”。

## 类型运算不是运行时变换

mapped types 可以逐属性变换；conditional types 可以按类型关系分支；infer 从模式中提取类型；模板字面量类型构造受约束字符串集合。`Partial`、`Required`、`Readonly`、`Pick`、`Omit`、`Record`、`ReturnType`、`Awaited` 是这些机制的常见应用。

`Readonly<T>` 常是浅层约束，深层对象不因此冻结；`Omit<T,"secret">` 只是静态去掉字段，并不会在 JSON 响应中删除真实 secret。需要去敏时必须实际构造新的运行时对象。类型定义越复杂，越应问它是否提高 API 使用者理解，而不是仅证明作者会写递归类型。

## 变型从读写方向理解

只读生产者输出 T，适合协变思考；消费者接受 T，涉及逆变；既读又写的可变容器通常需要更严格关系。TypeScript 为兼容 JavaScript 存在有意的非完全健全之处，方法和函数类型等规则也有细节。严格模式能排除部分错误，不代表语言提供形式化的全程序安全证明。

## 常见设计取舍

有限异构数据用判别联合，公共能力用 interface，组合类型用 type alias。函数重载表达不同调用形状，但实现签名必须能正确处理所有公开重载；很多场景一个联合参数加显式收窄更清晰。`satisfies` 检查某种约束而尽量保留表达式自身类型，不能代替外部数据校验。

进阶主题包括 declaration merging、ambient declarations、品牌类型、const 断言、递归条件类型、类型级测试和声明文件发布。品牌类型适合区分 UserId 与 OrderId，但通过断言伪造仍可能绕开；不可信输入必须经构造函数或解析器。

练习：设计一个按事件名选择 payload 类型的 API，然后添加一个未知事件测试和一个 payload 错误测试。不要把“编译拒绝了错误示例”和“运行时一定不会收到错误数据”混为一谈。
