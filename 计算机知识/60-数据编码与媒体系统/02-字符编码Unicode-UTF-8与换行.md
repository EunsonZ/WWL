# 字符编码、Unicode、UTF-8 与换行

## 本课目标

学完后，你能沿着“字节 → 代码单元 → 码点 → 字素簇 → 字形”的链条排查文本问题；能手工辨认基本 UTF-8 字节模式；也能在比较、搜索、正则、文件交换和 LLM 输入时明确正规化、BOM、换行与错误处理策略。

## 直觉：屏幕上的一个“字符”不是一个固定大小的东西

人看到 `é` 或 `👩🏽‍💻`，通常把它当作一个可编辑单位。底层却可能是一个码点、两个码点，或由肤色修饰符、零宽连接符连接的多个码点。字体与排版系统再把它们画成字形。因此“长度为 1”“删一个字符”“正则 `.` 匹配一个字符”都必须先说明自己在哪一层计数。

| 层 | 是什么 | `é` 的一个可能例子 |
| --- | --- | --- |
| 字节（byte） | 传输/存储的 8-bit 单元 | UTF-8：`C3 A9` |
| 代码单元（code unit） | 某种编码的基本单位 | UTF-8 的 8-bit 单元；UTF-16 的 16-bit 单元 |
| 码点（code point） | Unicode 分配的抽象编号 | 预组合 `U+00E9` |
| 字素簇（grapheme cluster） | 用户通常感知为一个书写单位 | `U+0065 U+0301` 也可显示为 `é` |
| 字形（glyph） | 字体实际绘制的图形 | 由字体、脚本与排版规则决定 |

Unicode 是字符集合、属性和文本处理规则的标准；UTF-8、UTF-16、UTF-32 是把码点编码为代码单元/字节的不同方式。Unicode 不是 UTF-8 的同义词。

## 1. 码点与 UTF-8：变长，但有明确边界

UTF-8 对 ASCII 保持兼容：`U+0000` 到 `U+007F` 各用一个相同值的字节。较大的码点用两到四个字节；续字节一律以 `10` 开头，首字节说明总长度。

| 码点范围 | UTF-8 位模式 | 首字节十六进制范围 |
| --- | --- | --- |
| `U+0000..U+007F` | `0xxxxxxx` | `00..7F` |
| `U+0080..U+07FF` | `110xxxxx 10xxxxxx` | `C2..DF` |
| `U+0800..U+FFFF` | `1110xxxx 10xxxxxx 10xxxxxx` | `E0..EF` |
| `U+10000..U+10FFFF` | `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx` | `F0..F4` |

例如 `中` 是 `U+4E2D`，UTF-8 为 `E4 B8 AD`：

```text
U+4E2D 的二进制：0100 1110 0010 1101
三字节载荷：      0100 | 111000 | 101101
UTF-8：           11100100 10111000 10101101
十六进制：         E4       B8       AD
```

合法 UTF-8 不只要求“前缀看上去对”。解码器还必须拒绝孤立续字节、截断序列、过长编码、代理码点和超过 `U+10FFFF` 的值。无效输入时采用报错、替换字符还是保留原始字节，是业务与安全边界；不可悄悄把损坏文本当作已验证的身份、路径、代码或证据。

## 2. UTF-16 与“一个码点占两个单元”

UTF-16 的基本代码单元是 16 bit。基本多文种平面中的许多码点可用一个单元表示；`U+10000` 以上的码点要用一对代理项（surrogate pair）。因此即使没有组合附加符号，一个 emoji 在 UTF-16 API 的 `length` 中也可能计为 2。UTF-32 以 32-bit 单元表示码点，概念直接但通常更占空间。

这不是“UTF-16 错了”；它说明 API 返回的可能是**代码单元数**。跨 API 传位置、截取范围或为限制输入长度时，须约定使用字节、代码单元、码点还是字素簇，以及越界时怎样拒绝。

## 3. 正规化：看起来一样，不代表字节一样

可见的 `é` 至少有两种常见 Unicode 序列：

```text
预组合：U+00E9             → UTF-8 C3 A9
分解式：U+0065 U+0301      → UTF-8 65 CC 81
```

它们可显示相近，字节比较却不相等。Unicode 正规化给出可复现的变换形式：

| 形式 | 主要含义 | 适合先问的问题 |
| --- | --- | --- |
| NFC | 尽量合成为规范等价的组合形式 | 我要比较一般自然语言文本吗？ |
| NFD | 分解为规范等价成分 | 下游是否要求分解形式？ |
| NFKC / NFKD | 还合并兼容等价形式 | 改写全角、圈号、单位等会不会损失业务语义？ |

正规化不是免费的“清洗”。密码、签名原文、程序标识符、法律证据、搜索索引和显示文本可能需要不同策略。常见可靠做法是：保留原始字节/原文；在明确的比较或索引边界生成声明过形式的派生值；记录 Unicode 版本与规则；不把派生值冒充原始证据。

> [!warning] 同形字与双向文本风险不靠 NFC 自动解决
> 不同字符可能看起来相似；控制字符可改变显示方向。正规化只能处理定义的等价关系，不能证明用户名、域名、代码标识符或文件名“人眼上没有欺骗性”。高风险标识需采用受限字符集、明确显示/转义策略和针对目标协议的验证。

## 4. 字素簇：编辑与展示要面向用户，而不是猜码点数

组合重音、旗帜、家庭 emoji 与某些文字脚本都说明：码点数也未必等于“用户看到几个字符”。需要按用户可见单位移动光标、截断摘要或计费时，应使用平台提供的 Unicode 字素分段算法，而不是对 UTF-8 字节切片或假设一个码点一个字符。

正则通常运行在已解码字符串上，但 `.`、`\w`、边界和量词在代码单元/码点层的行为取决于引擎与标志。实践对照与跨引擎差异见 [[编程知识/10-基础/01-正则表达式/07-Unicode与引擎差异|Unicode 与引擎差异]]。模型的 token 也不是字素簇：一个字素可变成多个 token，一个 token 也可能只是一段字节，见 [[AI/20-LLM/10-原理/01-文本Unicode-Token与词表|文本、Unicode、Token 与词表]]。

## 5. BOM 与换行：隐形字节也属于格式

**BOM（byte order mark）**是 `U+FEFF` 在某些 Unicode 编码开头的特殊用途标记。UTF-16/UTF-32 中它可指示字节序；UTF-8 中没有字节序问题，开头的 `EF BB BF` 虽被某些工具用作签名，但并非每个协议都接受它。若文本开头意外出现不可见字符，可能使第一个键名、shebang、CSV 列名或配置指令不匹配。协议规定无 BOM 时，读取器应按协议拒绝或明确报告，而不是在任何位置盲删 `U+FEFF`。

换行同样是约定，而非“显示上的自动折行”：

| 名称 | 字节/转义 | 常见来源 |
| --- | --- | --- |
| LF | `0A` / `\n` | Unix、现代 macOS、许多网络文本 |
| CRLF | `0D 0A` / `\r\n` | Windows 与部分文本协议 |
| CR | `0D` / `\r` | 旧系统或遗留数据 |

编辑器的视觉换行不写入任何换行字节。将 CRLF 统一为 LF 是可能合理的版本控制策略，但会改变字节哈希、签名输入、精确 offset、token 序列和某些协议语义。请在输入边界声明“接受哪些行尾、内部保存哪一种、输出保留还是转换”，并用 CRLF、LF、末行无换行和混合行尾样本测试。

## 练习

1. 写出 `A中` 的 UTF-8 十六进制字节，并说明为什么以字节数限制为 3 时不能安全地在 `E4` 后截断。
2. 两个用户名显示都是 `é`，却有不同 UTF-8 字节。分别为“保留原始内容”“相等比较”“账户标识”提出策略，并写出你还需要确认的产品规则。
3. 一个接口把字符串长度限制为 10。列出它至少可能指“10 字节、10 UTF-16 代码单元、10 码点、10 字素簇”的四种不同含义。
4. 某 CSV 第一列名显示为 `name`，程序却找不到它。列出 BOM、编码、换行与不可见字符中你会先检查的证据。

## 成功标准

- 我能区分字节、代码单元、码点、字素簇和字形，不用“字符”掩盖歧义。
- 我知道 UTF-8 是变长编码，且能说明合法性验证不只是检查续字节前缀。
- 我会把正规化形式、Unicode 版本、原始文本与派生比较值分开记录。
- 我不会把 BOM、行尾转换或正则 Unicode 行为当作不可见的小事；它们是可测试的格式契约。
