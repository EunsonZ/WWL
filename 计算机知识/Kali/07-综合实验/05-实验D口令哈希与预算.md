# 实验D口令哈希与预算

**先修关系：** [[计算机知识/Kali/07-综合实验/01-离线实验准备与夹具说明|离线实验准备与夹具说明]]；[[计算机知识/Kali/05-密码无线与专门领域/02-HashcatJohn与离线审计|HashcatJohn与离线审计]]。

## 将猜测过程缩到可以手工核对

目标不是比 GPU 速度，而是证明候选、编码、摘要格式和缓存如何影响恢复结果。输入只有两条 SHA-256 与五项公开候选；不需要个人数据，也不需要大字典。先阅读 [[计算机知识/Kali/05-密码无线与专门领域/01-哈希口令KDF与估算|成本模型]]，明确这些快速无盐摘要只服务教学。

```bash
cd "$HOME/kali-lab/code"
python3 offline_lab.py --fixtures "$HOME/kali-lab/fixtures"
```

摘要匹配部分预期 `targets=2`、`candidates=5`、`matches=2`。程序没有打印实际明文结果，但候选本来就是公开教学资料。验证器使用标准库 SHA-256，并以常见 `abc` 已知摘要作独立测试；这不是一个口令存储实现，也不是 Hashcat 速度测试。

## 改变候选集合，解释阴性结果

复制候选表到 output，删除其中 `Cedar-7!`。使用 `match_toy_hashes` 读取新表时只应匹配一条。再传入空候选表，结果为零；这不表示两个摘要都强，只表示没提交任何候选。非法长度/非十六进制的摘要必须报输入错误，不能混入“没找到”的计数。

换 Hashcat 或 John 重做时，按 [[计算机知识/Kali/05-密码无线与专门领域/02-HashcatJohn与离线审计|工具章节]] 指定单独 potfile 并记录旧缓存是否存在。已找到的结果可能由缓存直接显示，因此对照“字典减少但结果不变”要先排除缓存。把复制的候选表摘要与执行命令一并保留。

## 预算练习

设目标均匀分布在 10,000 个候选中，每秒恰能验证100个，且无重复猜测；平均检查位置是5000.5，不是固定5000，平均时间50.005秒。实际非均匀口令、多个盐、KDF参数和在线限制破坏这些假设。你应能解释每个假设对应哪个系统环节，而不是只算乘除。

不要记录一个未实际测得的“本机速度”。使用工具时，给定温度/资源预算，关注实际候选完成数和退出原因。缺少硬件后端是未运行，不是速度为零；中止只支持预算内的结果。

## 合格的报告表述

“对两条合成原始 SHA-256，五项指定候选经 UTF-8 编码计算后找到两项匹配”比“破解成功，系统密码很弱”更准确。后者既没有真实系统，也没有 KDF 成本与人群样本依据。修复建议应回到真实存储算法和认证策略，不把演示快哈希直接迁移到生产。

> [!question] 自检
> 加了唯一盐后，攻击者能否用相同口令给每条记录分别计算？能；盐主要改变跨记录复用，不使猜测本身不可能。为何还需要 KDF 成本，见 [[计算机知识/Kali/05-密码无线与专门领域/01-哈希口令KDF与估算|哈希理论]]。
