# 实验 I：多租户、字段与动作授权

> [!warning] 这是第二个明确版本的教学模型
> 原实验 C 的 v1 模型是 Alice 拥有 17、Bob 拥有 18，只检查读权限。本实验是独立的 `reasoning-v2.0` 模型，增加租户、角色、字段和状态，数据定义如下；不能把两版相同的编号混成同一个对象历史。

## 1. 为什么只验证“能否读取对象”不够

同一对象可能允许读摘要，却不允许看私密字段；允许编辑草稿，却不允许编辑已提交对象；允许审核他人的同租户报告，却不允许审核自己的。由此得到一个共同问题：可信主体在当前状态下，对哪个资源执行哪个动作、获得哪些字段？这连接 [[计算机知识/Kali/03-Web与API安全/08-认证会话越权与API测试|身份与对象授权]] 和 [[计算机知识/Kali/03-Web与API安全/12-现代API业务逻辑与并发边界|业务状态与现代 API]]。

本实验没有 HTTP 服务、JWT、Cookie 或登录。函数参数 identity 必须由假定已经完成认证的可信调用方提供；直接接受浏览器自报的 `bob` 并调用该函数会破坏这个前提。测试通过不构成认证正确的证据。

## 2. 唯一政策与数据定义

可信注册表包含 Alice：red 租户、author 角色；Bob：red、reviewer；Carol：blue、reviewer。报告的固定状态如下。

| 编号 | 租户 | 所有者 | 状态 |
| --- | --- | --- | --- |
| 17 | red | Alice | draft |
| 18 | red | Alice | submitted |
| 19 | blue | Carol | submitted |
| 20 | red | Bob | submitted |
| 21 | red | Alice | approved |

所有动作先要求主体和对象存在且同租户。read 允许所有者或该租户 reviewer；edit、submit 只允许 draft 的所有者；approve 只允许 reviewer 审核同租户、非本人拥有且处于 submitted 的对象。未列出的动作拒绝。

投影函数返回新字典，基础字段为 `id`、`title`、`status`；只有所有者额外得到 `private_note`。reviewer 的读权限不是整行数据库记录的访问权限。返回新字典也避免调用方修改响应对象时改变注册表；这不是数据库隔离或并发事务的实现。

## 3. 按单变量顺序验证

```bash
cd "$HOME/kali-lab/code"
PYTHONDONTWRITEBYTECODE=1 python3 - <<'PYCODE'
from reasoning_lab import allowed, project_report
cases = [
    ('alice', 17, 'edit'),
    ('bob', 17, 'edit'),
    ('bob', 18, 'approve'),
    ('bob', 20, 'approve'),
    ('carol', 18, 'read'),
    ('alice', 21, 'submit'),
]
for case in cases:
    print(case, allowed(*case))
print('reviewer fields:', sorted(project_report('bob', 18)))
print('owner fields:', sorted(project_report('alice', 18)))
PYCODE
```

六项预期依次为 True、False、True、False、False、False。先比较 Alice 与 Bob 对草稿的编辑，再比较 Bob 对他人/本人已提交对象的审核；最后比较租户与状态边界。Bob 能审核 18，但不能审核 20，表明政策检查了职责分离，而不只是角色是否为 reviewer。

Bob 读取 18 的字段应恰为 id、status、title；Alice 还得到 private_note。检查字段**缺失**与值为 null 不同，不能仅断言“没有显示秘密字符串”。未知对象读取会抛 `PermissionError`，不是返回成功的空字典。

## 4. 反例应针对错误假设

删除租户条件后，Carol 可能因 reviewer 角色而跨租户读取。删除所有者不同条件后，Bob 可能自行审核 20。只在前端隐藏 private_note、却仍将其序列化到响应中，不满足字段政策。将 `True` 当作对象编号整数也会掩盖类型错误，因此接口显式拒绝布尔型编号。

运行 `python3 -m unittest -v test_reasoning_lab.PolicyTests test_reasoning_lab.FixtureV2Tests.test_authorization_cases`，再给每条允许测试配一个只改变相关条件的拒绝测试。失败不仅要说明“结果不符”，还要指出是身份来源、租户、所有权、角色、状态还是输出字段出了问题。

## 5. 迁移到 API 时还必须补什么

本实验没有状态写入，所以不能验证“检查权限与更新状态原子化”；没有并发请求，所以不能验证竞态；没有缓存和分页，所以不能验证所有返回路径都应用字段投影。迁移时，需要把检查落实到实际服务端动作，并测试列表、详情、导出、异步任务和 WebSocket 消息等入口。

来源边界：本页政策、数据及预期是原创教学设计，不代表任何产品的内置权限规则。通用身份和授权机制的官方来源在上面的先修页；实际运行证据定位于 [[计算机知识/Kali/90-来源与维护/05-v3深度审阅与变更记录|v3 验收记录]]。

## 从本页继续：策略判断不等于已经执行变更

本页读取既定对象状态，返回允许或拒绝以及可见字段，不向数据库提交新状态。`submit`、`approve` 在这里是待判定动作，不是已经发生的持久事件。改变输入对象状态再调用函数，可以验证状态条件，但不能证明并发原子性。
