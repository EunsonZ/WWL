# 寄存器分配、指令调度与目标代价模型

## 本课目标

学完后，你应该能够：

- 从活跃性结果构造 interference graph，并解释相邻值为何不能共享同一物理寄存器；
- 比较 graph coloring 与 linear scan 的输入、决策和复杂度取舍；
- 判断 move coalescing 是否安全，并追踪 spill、reload、live-range splitting 与 rematerialization；
- 处理 register class、固定寄存器、子寄存器别名和调用 clobber；
- 用 dependency DAG 和资源约束安排指令顺序；
- 分开讨论 latency、throughput、code size 和 register pressure，而不是把“成本”压成一个无条件通用的数字。

## 1. 直觉：值很多，寄存器很少，顺序也不是任意的

机器 IR 可以拥有任意多的虚拟寄存器：

```text
v_a = INPUT_A
v_b = INPUT_B
v_c = ADD v_a, v_b
v_d = LOAD address_p
v_e = MULTIPLY v_c, v_d
RETURN v_e
```

真实 target 只有有限物理寄存器，部分操作还只接受某一类寄存器。若两个值在程序某一点都必须保留，它们不能占同一个物理位置；若同时活跃值太多，就要把某些值暂存到栈或重新计算。

即便寄存器位置已经合法，原顺序也不一定高效。`LOAD` 结果可能几周期后才可用，而旁边有与它无关的运算可以提前。调度器尝试填补等待时间，但不能跨过真实数据依赖、可能别名的内存访问、异常/控制边界或资源冲突。

## 2. 从 liveness 到 interference

### 活跃性的精确定义

若某值在程序点 `p` 之后的某条可达路径上会被使用，并且从 `p` 到该使用之间没有被重新定义，则该值在 `p` **live**。对基本块 `B`，经典后向方程为：

```text
live_out[B] = union(live_in[S] for every successor S of B)
live_in[B]  = use[B] union (live_out[B] minus def[B])
```

需要迭代到不动点，因为循环会把后继信息传回前驱。详细框架见 [[计算机知识/70-编译原理/09-数据流分析格不动点活跃性与到达定义|数据流分析、格、不动点、活跃性与到达定义]]。

### interference 的精确定义

两个虚拟值的 live ranges 若在某个程序点重叠，就不能在该点共享同一个物理寄存器；称它们**干涉**。Interference graph 中：

- 每个节点代表一个要分配的虚拟值；
- 一条无向边 `u—v` 表示 `u` 与 `v` 不能被分到同一物理寄存器；
- 给图做 `K` 着色，对应使用 `K` 个可用物理寄存器且相邻节点颜色不同。

在常见构造法中，扫描一条“定义 `d`”的机器指令时，把 `d` 与该指令之后仍 live 的每个值连边。move 指令可有特殊处理，因为若源与目标最终同色，move 可以消失。

## 3. 手算例：两只寄存器为什么会迫使 spill

考虑一个基本块：

```text
1: v_a = INPUT_A
2: v_b = INPUT_B
3: v_c = ADD v_a, v_b
4: v_d = MULTIPLY v_c, v_b
5: v_e = ADD v_d, v_a
6: RETURN v_e
```

从末尾反向计算，指令后的 live set 为：

| 指令后 | live values | 原因 |
| --- | --- | --- |
| 6 后 | `{}` | 函数结束 |
| 5 后 | `{v_e}` | 返回要读取 `v_e` |
| 4 后 | `{v_a, v_d}` | 第 5 行需要两者 |
| 3 后 | `{v_a, v_b, v_c}` | 第 4 行要 `v_c,v_b`，第 5 行还要 `v_a` |
| 2 后 | `{v_a, v_b}` | 第 3 行需要两者 |
| 1 后 | `{v_a}` | 第 2 行尚未定义 `v_b` |

`v_a`、`v_b`、`v_c` 在第 3 行之后同时 live，形成三节点 clique：

```text
v_a ----- v_b
 \         /
  \       /
    v_c
```

只有两只通用寄存器时，这个 clique 不可二着色；至少要拆分、重算或 spill 一个值。一种选择是暂存 `v_a`：

```text
R0 = INPUT_A
SPILL slot_0, R0
R1 = INPUT_B
R0 = RELOAD slot_0
R0 = ADD R0, R1
R0 = MULTIPLY R0, R1
R1 = RELOAD slot_0
R0 = ADD R0, R1
RETURN R0
```

这只是合法方案，不保证最便宜。若 `INPUT_A` 是可低成本重算的常量或地址，rematerialize 可能优于一次 spill store 加两次 reload load（共三次显式访存），但须比较重算成本与完整 store/load 成本；若第 5 行处于冷分支，可把 reload 只放到该分支；若允许交换/改写指令，另一个值也许更适合 spill。

### 分配后必须复查

对上例至少验证：

1. 每次 use 都读到对应 definition 的值；
2. 同时 live 且同属一个 register class 的干涉值未共享物理寄存器；
3. spill slot 不与仍在使用的其他 slot 错误重叠；
4. reload 支配其使用，且没有被可能别名的写入破坏；
5. 插入的 spill/reload 自身可编码，并纳入栈帧和调度。

## 4. Graph coloring：把资源冲突显式做成图

一个简化的 coloring allocator：

```text
build interference graph G; retain original adjacency for reverse coloring
while G has nodes:
    if exists node with degree < K:
        remove node and push it on simplify_stack
    else:
        choose a spill_candidate
        remove it and push (node, potential_spill=true) on simplify_stack

while simplify_stack is not empty:
    node = pop simplify_stack
    choose a physical register not used by colored neighbors
    if no register is available:
        mark node for actual spill
    else:
        assign chosen register

if actual spills exist:
    rewrite program with spill/reload or rematerialization
    rebuild liveness and repeat
```

`degree ≥ K` 不证明节点一定会 spill：移除其他节点后，它仍可能找到颜色。因此 spill candidate 是启发式猜测；最终回填才知道。

取 K=2，颜色 R0/R1。每次移除的节点都恰好入栈一次，回填检查原图中已经着色的邻居：

| 原图 | 移除顺序/栈底→顶 | 逆序回填 | 结论 |
| --- | --- | --- | --- |
| 三角 a-b-c-a | a（potential）、b、c | c=R0，b=R1，a 无色 | a 成为 actual spill |
| 四环 a-b-c-d-a | a（potential）、b、c、d | d=R0，c=R1，b=R0，a=R1 | potential a 最终有色 |
| 路径 a-b-c | a、b、c | c=R0，b=R1，a=R0 | 无 spill |

低 degree 判定在当前简化图中进行，回填使用原干涉关系；未着色节点不能凭空消失。这里是可手推的启发式示例，不承诺最优着色。

还要区分“没有大团”与“确实可着色”。[[数学/12-离散数学与逻辑/30-组合与图论/01-着色团独立集与奇环#同一五环：三个数分别怎么确定|C5 的完整上下界证明]] 给出团数2、独立数2、色数3：若它就是只允许两个同类寄存器的完整干涉图，最大团只有2仍不能认证可分配。返回本节时，spill/reload 或 live-range 改写后须重新计算 liveness、重建干涉图，且仍受寄存器类、别名、预着色和指令约束限制。[[数学/12-离散数学与逻辑/30-组合与图论/03-Mantel与Turan极值定理#存在性结论与算法证书各自负责什么|极值边数阈值]] 只提供某些必有大团的充分证据，低于阈值不保证可着色，也不代替这里的实际回填。

### spill 代价不能只数 use 次数

一种概念化评分：

```text
spill_cost(value) =
    weighted_use_and_definition_count(value)
    / max(1, current_interference_degree(value))
```

其中 loop 内的 use 可按估计执行频率加权；函数调用附近、不可折叠地址、需要特殊寄存器的值也可能有额外成本。该公式只是启发式，不是语义定理。

## 5. Linear scan：按区间快速分配

linear scan 通常把 live range 近似为按程序顺序排列的区间，依起点扫描：

```text
sort intervals by start position
active = empty

for interval in sorted intervals:
    expire active intervals whose end is before interval.start
    if a compatible free register exists:
        assign it and add interval to active
    else:
        choose interval to spill or split
```

它实现简单、速度快，适合 JIT 或大函数；graph coloring 往往能利用更完整的干涉结构，可能减少 move/spill，但编译时间和实现复杂度更高。两者都不是固定质量等级：现代实现会加入 interval holes、splitting、priority、coalescing、register hints 和局部分配。

| 维度 | Graph coloring | Linear scan |
| --- | --- | --- |
| 核心对象 | 干涉图 | 按指令位置排序的 live intervals |
| 典型优势 | 全局冲突关系显式，便于 coalescing | 扫描快、内存开销较小 |
| 典型风险 | 图大、启发式复杂、需反复重写 | 区间近似会掩盖 holes，可能较早 spill |
| 常见场景 | AOT 优化后端 | JIT、快速编译层；也可用于 AOT |

不要把表格当作实现承诺；应查看具体编译器、配置和工作负载。

## 6. Coalescing：删 move，但不能制造不可着色冲突

若机器 IR 中有：

```text
v_y = MOVE v_x
```

且 `v_x` 与 `v_y` 不干涉、register class 兼容，就有机会把两者分到同一物理寄存器，使 move 消失。但合并节点会把双方邻居集合并，可能让图更难着色。

```text
safe_to_coalesce(x, y):
    reject if x interferes with y
    reject if register classes have no common legal register
    accept only if a conservative criterion predicts merged node remains colorable
```

预着色节点（例如参数已经要求在固定物理寄存器）尤其敏感：不能把另一个值合并到它不允许占据的位置。实际 coalescing 是收益与 spill 风险的权衡，不是“看到 move 就删”。

## 7. Spill、reload、splitting 与 rematerialization

### Spill / reload

spill 把值写入栈帧中的 spill slot；后续 use 前用 reload 取回。代价可能包括：

- 增加 load/store 指令和内存流量；
- 扩大栈帧并改变 frame offset；
- 新指令继续占用地址寄存器、调度槽和编码空间；
- 在循环内被重复执行；
- 触发新的 register pressure，迫使再次分配。

### Live-range splitting

不必把一个值整个生命周期都 spill。可以把它切成几段：热区保留寄存器，冷区或跨调用区放栈，再在边界插入 copy/reload。

```text
hot_loop_range -> physical_register
rare_error_path_range -> spill_slot
bridge_at_edge -> store_or_reload
```

### Rematerialization

若值能便宜、无副作用地重建，例如小常量或某些 frame address，可以在 use 前重新生成而非 reload：

```text
v_constant = MATERIALIZE 0
...
use MATERIALIZE 0 again
```

不能对 load、随机数、时钟、volatile 访问或可能抛出异常的计算任意 rematerialize；“表达式短”不等于可安全重复。

## 8. Register class、固定约束与别名

“有 16 个寄存器”往往是错误简化。目标可能区分：

- 整数、地址、浮点、向量、谓词或特殊状态寄存器；
- 某条指令要求输入/输出在固定寄存器；
- 两地址指令要求 `destination` 与某个 source 是同一位置；
- 一个宽寄存器与其低位子寄存器物理别名；
- 成对或连续寄存器约束；
- 调用会 clobber 一组 caller-saved 寄存器。

于是合法颜色不是统一集合，而是：

```text
allowed_colors(v) =
    registers_in_required_class(v)
    minus forbidden_fixed_or_reserved_registers
    minus colors_used_by_interfering_values
```

跨 call 仍 live 的值若留在 caller-saved 寄存器，要在调用周围保存/恢复；放进 callee-saved 寄存器又可能迫使当前函数增加序言/尾声。分配器需要比较局部 copy/spill 与整个函数 save/restore 的代价。

## 9. 指令调度：在依赖偏序中选择一个合法线性序列

### 依赖 DAG

节点是机器指令，边表示必须先后执行：

| 边 | 含义 | 例子 |
| --- | --- | --- |
| RAW / true dependence | 后者读取前者产生的值 | `LOAD → ADD loaded_value` |
| WAR / anti-dependence | 后者写的位置仍要被前者读取 | 物理寄存器复用引出的假依赖 |
| WAW / output dependence | 两次写同一位置必须保持最终写顺序 | 两条指令写同一物理寄存器 |
| memory dependence | 可能别名或强顺序内存操作 | `STORE p → LOAD q`，若 `p` 可能等于 `q` |
| control / exception constraint | 不能越过会改变是否执行或异常顺序的边界 | 分支、调用、可能陷阱的操作 |

寄存器重命名可消除部分 WAR/WAW 假依赖，但不能消除 RAW 真依赖。内存 alias 分析越精确，调度器越可能证明两个访问独立；保守未知时必须保留顺序。

### 资源约束

即使 DAG 中两个节点独立，也可能争用同一类执行资源或发射带宽。概念化 list scheduling：

```text
ready = all nodes whose predecessors are scheduled
for each cycle_or_position:
    among ready nodes, choose candidates whose resources are available
    prioritize critical-path nodes, latency hiding, or size goal
    schedule chosen nodes
    update ready set and resource reservations
```

这是静态模型。真实 CPU 可能乱序执行、推测执行或有不同微架构资源；在顺序执行 target 上，静态调度影响更直接，在乱序核心上仍可影响依赖链、解码宽度、端口竞争与寄存器压力。

## 10. 手排一个 latency-hiding 例子

假设：

- `LOAD` 的结果延迟为 3 个周期；
- `ADD` 延迟为 1；
- 每周期最多发射一个内存操作和一个算术操作；
- `v_x` 的计算与 load 独立。

原顺序：

```text
v_loaded = LOAD address_p
v_sum = ADD v_loaded, 1
v_x = ADD v_a, v_b
v_result = ADD v_sum, v_x
```

一种更好的概念顺序：

```text
v_loaded = LOAD address_p
v_x = ADD v_a, v_b
wait only if v_loaded is still unavailable
v_sum = ADD v_loaded, 1
v_result = ADD v_sum, v_x
```

第二条 ADD 填入 load 等待窗口，但它可能延长 `v_x` 的 live range。若同时已有很多 live 值，调度后 register pressure 增大，可能触发 spill，抵消延迟收益。这正是寄存器分配与调度互相耦合的原因。

### 调度发生在分配前还是分配后

- **pre-register-allocation scheduling** 有更多虚拟寄存器自由，可隐藏延迟，却可能抬高 register pressure；
- **post-register-allocation scheduling** 已知真实寄存器和假依赖，可处理物理约束，但移动空间更小；
- 工业后端常两者都做，并配合 pressure-aware heuristics。

## 11. 代价模型是多目标、带上下文的近似

### 四个必须分开的量

| 目标 | 它测什么 | 常见冲突 |
| --- | --- | --- |
| latency | 一条依赖链从输入可用到输出可用要多久 | 为降低链长可能复制计算、增大代码 |
| throughput | 稳态单位时间能完成多少工作 | 高吞吐序列未必有最低单次延迟 |
| code size | 编码字节数、指令数或布局体积 | 更短代码可能使用慢指令，或需要额外数据访问 |
| register pressure | 某点同时需要多少、哪些类别的寄存器 | 提前计算可隐藏延迟，却让值活得更久 |

还可能包含能耗、前端解码、分支概率、缓存行为、代码布局和编译时间。一个简化成本向量：

```text
cost(candidate, context) = {
    estimated_latency_on_critical_path,
    estimated_reciprocal_throughput,
    encoded_size,
    peak_pressure_by_register_class,
    estimated_spill_cost,
    compile_time_cost
}
```

优化模式再根据目标选择权重或词典序。例如 `optimize_for_size` 可能先比较字节数，热点循环则更看吞吐和 spill 风险。不存在一组对所有程序、CPU、输入和部署目标都最优的固定权重。

### latency 不是 throughput

若某乘法延迟为 4 周期但处理器每周期可开始一条独立乘法，则一条依赖链每步仍要等约 4 周期，而四条互不依赖的链可以形成高吞吐。反过来，一条单周期操作若每两周期才可发射一次，延迟短但吞吐受限。

### 静态估计不是运行证据

目标描述中的代价表通常针对某个 CPU 家族的抽象模型；缓存未命中、数据相关分支、系统负载、频率和输入分布会改变真实结果。编译器成本模型用于做决策，不是 benchmark 报告。性能证据方法见 [[计算机知识/30-计算机系统/15-性能分析可观测性与系统设计|性能分析、可观测性与系统设计]]。

## 12. 正确性不变量与验证层次

### 分配不变量

1. 每个机器操作数位于它允许的 register class 或合法内存位置；
2. 任意程序点上，相互干涉的 live values 不占同一物理寄存器；
3. 固定、保留和子寄存器别名约束得到满足；
4. 调用 clobber 两侧的 live value 被放在安全位置或正确保存/恢复；
5. spill/reload、edge copy 和 phi elimination 保留原数据流；
6. 栈槽大小、对齐和生命周期满足 frame layout。

### 调度不变量

1. 所有 true dependence 的生产者先于消费者；
2. 未证明无别名的内存访问保持必要顺序；
3. volatile、atomic、fence、call、异常和控制边界不被非法跨越；
4. 每一位置的指令满足 target 发射/资源和 bundle 约束；
5. 重排后基本块终结、fallthrough 和调试/异常映射仍一致。

### 证据层次

```text
allocator/scheduler verifier passes
    proves selected structural invariants only

differential execution on generated cases
    samples semantic equivalence for tested inputs and environments

target assembler accepts output
    proves encodability, not semantic correctness or performance

benchmark on named machine and workload
    measures that configuration, not every target or input
```

## 13. 常见失败与适用边界

- **把“最后一次文本 use”当成完整 liveness。** CFG 分支、循环、phi edge use 和异常边都会改变范围。
- **相邻节点同色。** 会让一个仍需保留的值被另一值覆盖，属于静默错编译。
- **过度 coalesce。** move 少了，却制造高 degree 节点和更多 spill。
- **spill 后不重跑分析。** 新的 reload 临时值和栈操作改变 liveness、pressure 与调度。
- **忽略 register class。** 图可 `K` 着色并不表示每个节点都能使用任意颜色。
- **忽略 subregister alias。** 宽窄寄存器看似不同，物理上却可能重叠。
- **把 load 任意跨 store。** 若地址可能别名，结果可能改变；原子与 volatile 还有更强约束。
- **只追求最短 latency。** 提前计算导致 live ranges 变长和 spill，端到端反而更慢。
- **只数机器指令。** 编码大小、uop 分解、资源、缓存与分支行为都可能不同。
- **把某一 CPU 代价外推为 ISA 定律。** 同 ISA 的微架构也可有不同 latency/throughput。

## 练习

### 练习 1：手算 liveness 与干涉图

对下面程序逐行写 live-after 集合，并画 interference graph：

```text
v1 = INPUT_1
v2 = INPUT_2
v3 = INPUT_3
v4 = ADD v1, v2
v5 = MULTIPLY v4, v3
v6 = ADD v5, v2
RETURN v6
```

用三只同类物理寄存器着色；若你的图不可三着色，选择一个 spill candidate，写出 spill/reload 后的伪机器 IR，再重新检查 liveness。

### 练习 2：比较 coloring 与 linear scan

把练习 1 的 live ranges 画成区间，按 linear scan 分配。然后构造一个带分支的例子，使某值的 range 有大段 hole；解释把它近似成连续区间可能为何增加 spill。

### 练习 3：安全 coalescing

给出：

```text
v_b = MOVE v_a
v_c = ADD v_b, v_d
v_e = ADD v_a, v_c
```

先计算 `v_a` 与 `v_b` 是否干涉，再说明它们 register class 不兼容或其中一方预着色时，为什么不能只凭“这是 move”就合并。

### 练习 4：依赖 DAG 与调度

为以下操作画 RAW、memory 和 control 边：

```text
v_a = LOAD address_p
v_b = ADD input_x, input_y
STORE address_q, v_b
v_c = MULTIPLY v_a, 3
BRANCH_IF_ZERO v_c, exit
```

分别在“已证明 `p` 与 `q` 不别名”和“别名未知”两种条件下给出合法调度。比较关键路径、live range 长度和 register pressure。

### 练习 5：代价不应只有一个答案

对两个候选序列建立成本表：候选 A 为 2 条指令、关键链 6 周期、体积 8 字节、峰值压力 2；候选 B 为 4 条指令、关键链 3 周期、体积 16 字节、峰值压力 5。分别为冷错误路径、热点循环、极小嵌入式固件选择方案，并说明还缺哪些真实 target 数据。

## 成功标准

- 我能从机器 IR 手算 live sets，并从重叠关系画出 interference graph；
- 我能在有限寄存器下完成 coloring 或 linear scan，并逐个解释 spill/reload 的位置；
- 我能判断一次 coalescing 是否满足非干涉、register class 与保守可着色条件；
- 我能为指令建立 dependency DAG，区分 RAW、WAR、WAW、memory 与 control 约束；
- 我能同时报告 latency、throughput、code size、register pressure，且不会把静态模型冒充真实 benchmark。
