# 作用域、名称解析与符号表

## 本课目标

学完后，你应该能：

- 精确区分声明、定义、binding、scope、visibility 与 lifetime；
- 为每个声明分配稳定的 symbol identity，把每个名称使用解析为 use-def 边；
- 用作用域栈和符号表解释遮蔽、重复声明、前向引用与递归；
- 说明模块导入、命名空间和分离编译为何不能只靠“字符串名字相同”；
- 在未解析、歧义和错误节点存在时继续分析，而不制造大面积级联误报。

本课只用**伪代码与手算表**。真实语言的可见性规则、宏卫生、重载与链接名各有细节，本课建立可以逐条实例化的核心模型，不做语言关键字百科。

## 直觉：名字只是拼写，symbol 才是“它指的那个实体”

下面三个 `x` 拼写完全相同，却可能是三个不同实体：模块变量、函数参数、内层局部变量。反过来，别名导入 `short` 与原模块导出 `very_long_name` 拼写不同，却可能指向同一个导出 symbol。

因此名称解析的产物不应只是“这个名字存在”，而是：

```text
NameUse(source_span, spelling="x")
    resolves_to SymbolId(module_id, declaration_id)
```

后续类型检查、重命名、跳转定义、未使用变量警告和代码生成都应使用 symbol identity；若它们每次重新按字符串猜测，遮蔽、导入别名和增量编译会让结果漂移。

## 1. 六个容易混淆的概念

| 概念 | 精确定义 | 不等于 |
| --- | --- | --- |
| 声明 declaration | 向某个命名环境引入实体及其部分契约 | 一定分配存储或给出函数体 |
| 定义 definition | 提供该实体在本语言规则下所需的完整实现/存储实例 | 第一次出现的所有声明 |
| binding | 在特定环境中建立“名字/模式 → symbol 或值位置”的关联 | 源文本里相同的拼写 |
| scope | 某个 binding 可被无资格名称解析规则考虑的程序区域 | 对象在运行时仍活着的时间 |
| visibility | 在当前位置，访问控制、导入、命名空间等规则是否允许看见实体 | 内存是否存在 |
| lifetime | 运行时对象或资源从开始存在到结束存在的区间 | 词法源代码区域 |

一条外部函数原型可以是声明而非定义；局部变量的词法 scope 可能覆盖整个块的一部分，而对象 lifetime 只从初始化成功后开始。静态变量可在函数调用结束后继续生存，但它的无资格名字仍只在词法 scope 内可见。生命周期与资源所有权可继续阅读 [[计算机知识/10-编程语言/02-C++/03-指针引用const与生命周期|指针、引用、const 与生命周期]]。

## 2. 环境、作用域与符号身份

设环境 $\Gamma$ 是从名字到候选 symbol 的映射，并带有指向父环境的边。每个 symbol 至少保存：

```text
Symbol:
    id                  // 稳定身份，不由显示名独自决定
    name
    kind                // variable, function, type, module, field, ...
    declaration_span
    defining_scope_id
    visibility
    declared_type_or_signature
    definition_state
```

“稳定”是相对编译会话或增量数据库契约而言：可以由模块身份、语法节点稳定 ID 与命名空间组成；不能用当前数组下标冒充跨重新解析稳定的身份，也不能仅用 `name`，因为同名实体合法存在。

### 作用域栈的核心操作

```text
enter_scope(kind, owner):
    push Scope(fresh_scope_id, parent=current_scope, bindings={})

declare(name, kind, span):
    if current_scope.bindings contains conflicting name in same namespace:
        report duplicate declaration with note to previous span
        return ErrorSymbol(fresh_id, name, span)
    symbol = Symbol(fresh_id, name, kind, span, current_scope.id)
    current_scope.bindings[name].append(symbol)
    return symbol

resolve_unqualified(name, use_span):
    scope = current_scope
    while scope exists:
        candidates = visible_candidates(scope.bindings[name], use_span)
        if candidates is unambiguous:
            return candidates.single
        if candidates is ambiguous:
            report ambiguity with candidate spans
            return ErrorSymbol(fresh_id, name, use_span)
        scope = scope.parent
    report unresolved name
    return ErrorSymbol(fresh_id, name, use_span)

leave_scope():
    pop current scope
```

这里“同一命名空间是否冲突”必须由语言规定。类型名与值名是否能同名、函数是否形成重载集合、字段是否只在成员查找中参与，都不能由哈希表结构自行决定。

## 3. 遮蔽不是覆盖：外层 symbol 仍然存在

考虑伪代码：

```text
module M
    let x = 10

    function f(x):
        let y = x
        begin
            let x = y + 1
            use(x)
            use(y)
        end
        use(x)
```

给声明分配 identity：

| SymbolId | 声明 | 定义作用域 |
| --- | --- | --- |
| `M::decl1` | 模块变量 `x` | module `M` |
| `M::f::param1` | 参数 `x` | function `f` |
| `M::f::local1` | 局部变量 `y` | function `f` |
| `M::f::block1::local1` | 内层变量 `x` | inner block |

逐个 use 的解析：

| 使用位置 | 拼写 | 解析到 | 原因 |
| --- | --- | --- | --- |
| `let y = x` 的右侧 | `x` | `M::f::param1` | 最近可见 binding 是参数 |
| `let x = y + 1` 的右侧 | `y` | `M::f::local1` | 内层未声明 `y`，向父环境查找 |
| 内层 `use(x)` | `x` | `M::f::block1::local1` | 内层声明遮蔽参数与模块变量 |
| 内层 `use(y)` | `y` | `M::f::local1` | 向父环境查找 |
| 块后 `use(x)` | `x` | `M::f::param1` | 内层 binding 已离开 scope |

遮蔽只改变一段区域内的查找结果，不删除外层 symbol。编译器可以对容易误读的遮蔽发 warning，但不能在语言允许时把它当作重复声明。相反，同一 scope 中两个不允许重载的 `let x` 通常是重复声明。

### 声明点之前能否使用？

“同一块中能找到声明”不代表声明前可用。语言可能规定：

- 整个块预先收集函数/类型声明，允许相互递归；
- 局部变量只从声明点之后可见；
- 名字在声明点起进入 scope，但初始化式中处于未初始化状态；
- 某些声明必须先有原型才允许跨文件使用。

解析器或 resolver 必须记录 use 的源位置并应用该规则。把块中所有名字一次性塞入 map 后无条件可见，会错误接受“声明前使用”。

## 4. 两阶段名称解析：先收集可前向引用者，再解析主体

支持函数互递归时，按源顺序看到函数体就立即解析会让第一个函数找不到后面的函数。常见策略：

```text
resolve_module(module_ast):
    module_scope = enter_scope(module)

    // Phase 1: collect module-level declarations and signatures
    for declaration in module_ast.declarations:
        collect_header(declaration, module_scope)

    // Phase 2: resolve bodies with all permitted headers visible
    for declaration in module_ast.declarations:
        resolve_body(declaration, module_scope)

    leave_scope()
```

这不是让所有实体都可任意前向引用。`collect_header` 只收集语言规则允许提前可见的内容；局部顺序、初始化依赖与循环仍由各自规则检查。

### 手算互递归

```text
function even(n): return n == 0 or odd(n - 1)
function odd(n):  return n != 0 and even(n - 1)
```

第一阶段分配 `SymbolId(even)` 与 `SymbolId(odd)` 并登记签名；第二阶段中 `odd(...)` use 解析到已经存在的 `odd` identity，反向亦然。如果先完整处理 `even` 再声明 `odd`，就会得到依赖源顺序的假错误。

## 5. use-def 图：让后续阶段不再重复猜名字

名称解析后，每个 use 保存到 definition/declaration symbol 的边：

```text
ResolvedNameUse:
    use_span
    spelling
    symbol_id
```

由此可以构建：

- definition → uses：重命名、查找引用、未使用诊断；
- use → definition：跳转定义、类型查询、代码生成；
- scope → symbols：补全、作用域可视化、离开作用域时的清理；
- module export → import uses：跨模块依赖与增量失效。

**反例：文本替换式重命名。** 把所有 `x` 替换为 `count` 会同时修改注释、字符串和不同 symbol 的同名变量；正确重命名以目标 SymbolId 的 use-def 集为范围，还要检查新名字是否在各 use 位置造成捕获或歧义。

### 按 SymbolId 改名并检查捕获

回到第3节的表，选择 `M::f::param1`，将参数 x 改名为 arg。改动范围恰为：参数声明、`let y = x` 的右侧、块后 `use(x)`。内层 `M::f::block1::local1` 的声明及内层 `use(x)` 保持原拼写；它们属于另一个 SymbolId。模块 `M::decl1` 也不改。表中的 use-def 边保持，说明“外层改名不跨遮蔽”；仅列出相同字符串则无法得到这个范围。

身份圈对以后，还须检查新名字。看这个只用词法查找的伪例，binding 从参数处及局部声明后可见，内层只覆盖自己的块：

```text
module N
    let count = 10            // N::outer
    function f(x):            // N::param
        use(count)            // → N::outer
        begin
            let x = 20        // N::inner
            use(x)            // → N::inner
        end
        use(x)                // → N::param
```

将 `N::param` 的声明与它的 use 改为 arg，三条边仍分别指向 outer、inner、param。若新名选 count，原来 `use(count)→N::outer` 在重新名称解析时会变成 `use(count)→N::param`：相对函数参数原为外层引用的 use 被捕获。即使这行没有进入所选 SymbolId 的改名集合，绑定范围扩大也改变了它；必须另选名字或拒绝此重命名。只检查“被改的 use 仍指向目标”不够，还要检查受影响区域原有其他 use 没有被改向。

正式绑定规则见[[计算机知识/70-编译原理/13-操作语义求值策略与程序等价#绑定身份与观察对象的对照|FV 与合法 α 改名的范围]]；带着“哪条自由引用边被内部绑定接走”读同页[[计算机知识/70-编译原理/13-操作语义求值策略与程序等价#同一闭合上下文怎样区分捕获结果|闭合后的同一调用反例]]，再返回本例定位 `use(count)` 的旧、新身份。第13课按纯 Bool 规则观察 false/true，本页只验伪代码的名称解析边；不能从该 Bool 例推出真实语言所有重命名都安全。若困惑同型为何不够，读[[计算机知识/70-编译原理/14-类型安全替换引理与进展保持#同型反例与三种不同的保持承诺|类型保持与行为保持的条件]]再回来解释：名称解析成功、类型检查成功各自不能替代引用身份保全。这些表是手算模型，没有执行 IDE 重命名或真实编译器。

## 6. 名称空间、成员查找与重载集合

无资格名称 `x`、资格名称 `M::x`、成员 `value.field` 可能使用不同查找机制：

- lexical lookup 沿父 scope 查找；
- qualified lookup 先解析模块/类型，再在其导出或成员表中查找；
- member lookup 可能依赖接收者类型，需与类型阶段协作；
- overload lookup 可返回候选集合，而非立刻选出一个函数。

因此 resolver 的结果有时是一个 symbol，有时是候选集或待类型信息补全的查询。把重载选择提前为“选择同名列表第一项”会让结果依赖声明顺序。重载如何结合类型约束见 [[计算机知识/70-编译原理/06-类型系统约束求解泛型与语义检查|类型系统、约束求解、泛型与语义检查]]。

## 7. 模块、导入与可见性

模块为 symbol identity 和可见性提供边界。一个简化模型包含：

```text
ModuleInterface:
    module_id
    exported_symbols: map(exported_name -> symbol_signature)
    interface_version_or_hash
```

导入 `import Math::sum as add` 时，本模块建立名字 `add` 的 import binding，但它指向 `Math` 接口中 `sum` 的导出 identity。别名不创建第二个函数定义。

需要独立处理：

- 导出：实体是否进入模块接口；
- 导入：本模块是否声明依赖及本地别名；
- 访问控制：实体虽可定位，当前位置是否有权使用；
- 歧义：两个通配导入提供同名实体时不能按加载顺序碰运气；
- 循环依赖：允许接口级循环不等于允许运行时初始化循环。

### 分离编译为何需要接口

编译模块 A 时，模块 B 的实现 AST 可能不可用；A 应依赖 B 的已验证接口：导出 symbol identity、种类、类型签名、可见性和必要 ABI 属性。接口变化决定哪些使用者需重编译；仅看源文件时间或显示名可能漏掉签名变化。

源语言 symbol 与链接器 symbol 也不是同一层：编译器可能通过 name mangling 把模块、命名空间、类型参数与调用约定编码进外部链接名。两个源级实体可以有不同 identity，即使最终因 ABI 错误碰撞成同一链接名；这应是可诊断的冲突，而不是自动合并。静态/动态链接细节见 [[计算机知识/10-编程语言/02-C++/01-编译链接与CMake|编译、链接与 CMake]]。

## 8. scope 与 lifetime 必须分开检查

```text
function make_ref():
    begin
        let local = 42
        return reference_to(local)
    end
```

在 `return` 表达式处，`local` 的名字在 scope 内、visibility 也允许，名称解析完全可以成功；但函数返回后对象 lifetime 结束，返回引用可能悬空。名称解析只证明“use 指向哪个声明”，不能证明运行时引用安全。

反方向也成立：模块静态对象可能在整个进程中存在，但私有名字在其他模块不可见。不要用“对象还活着”解释为什么名字可访问，也不要用“名字离开 scope”断言对象必已销毁。

## 9. 错误容忍：ErrorSymbol 是隔离层，不是合法声明

遇到未解析名称时，若后续每个阶段都再次报告，`unknown + 1` 可能产生“未定义名称”“没有类型”“不存在加法”“无法选择重载”等一串同根错误。可返回带来源的 `ErrorSymbol`：

```text
resolve(name_use):
    candidate = lexical_or_qualified_lookup(name_use)
    if candidate not found:
        diagnostic = report_unresolved(name_use.span, name_use.spelling)
        return ErrorSymbol(origin=diagnostic, span=name_use.span)
    return candidate
```

后续阶段看到 ErrorSymbol 时传播 error type，并默认不重复主诊断。候选歧义则应列出有限个候选及来源；不要随机选一个继续，否则后续类型与代码生成会建立在虚假 identity 上。

## 常见反例

1. **同名就是同一实体。** 遮蔽、重载、模块和命名空间都允许同名不同 identity。
2. **查到名字就说明可用。** 还要检查可见性、声明点、访问控制、初始化状态和上下文种类。
3. **scope 就是 lifetime。** 前者是名称查找区域，后者是运行时存在区间。
4. **符号表就是一个全局 map。** 单 map 会丢失嵌套、遮蔽、候选集和模块边界。
5. **通配导入冲突时取最后一个。** 结果会依赖导入顺序，应报告歧义或要求资格名。
6. **分离编译只需要外部名字。** 使用者还需要经过版本化/哈希化的接口契约与 ABI 相关信息。

## 练习

1. 对本课 `module M` 例子，为每个 `x` use 写出 SymbolId；再把内层 `let x` 删除，重算 use-def 边。
2. 设计一个包含“声明但未定义”“定义”“binding 别名”的三行伪程序，逐项说明差别。
3. 为一个块作用域手工维护 scope 栈：进入函数、进入块、声明同名变量、离开块；每一步列出可解析的最近 binding。
4. 写出两个互递归函数，比较单遍立即解析与“两阶段收集 header + 解析 body”的结果；指出哪些局部变量仍不应前向可见。
5. 模块 A 与 B 都导出 `parse`，模块 C 通配导入二者。给出错误诊断、两种修复方案，以及为什么不能按加载顺序选择。
6. 构造一个“名称解析成功但 lifetime 错误”的例子，和一个“对象仍存活但名字不可见”的例子。
7. 说明 IDE 重命名为什么必须以 SymbolId/use-def 为单位；给出只做字符串替换会误改的最小反例。

## 成功标准

- 我能用一句互不循环的定义区分 declaration、definition、binding、scope、visibility 与 lifetime；
- 我能为嵌套作用域手算解析结果，并说明遮蔽为何不删除外层 symbol；
- 我能构建 use → definition 与 definition → uses 的稳定关系，不依赖名字拼写唯一；
- 我能解释前向引用、互递归、重载候选和模块导入各需要哪种解析阶段；
- 我能说明分离编译依赖接口与 symbol identity，并把源级 identity 与链接名区分开；
- 我会用 ErrorSymbol 隔离根因，避免名称错误在类型阶段重复爆炸。
