> [!tip] 本轮深化：从当前概念继续追问
> 选择工具前先固定兼容性、质量和预算条件。历史矩阵只提供判断维度，动态版本和后端支持必须现场核验。 深化与验证：[[AI/20-LLM/60-模型格式与量化/08-量化误差传播校准目标与端到端评测|量化误差传播校准目标与端到端评测]]；[[AI/20-LLM/80-研究拓展/03-从论文主张到可复现实验|从论文主张到可复现实验]]。


这张矩阵先分清“要完成什么工作”，再选择格式和工具。文件扩展名不能单独说明 tokenizer、chat template、量化方式、许可证或模型是否能被某个运行时正确加载。

> [!important] 适用范围
> 本矩阵目前为已交付的 LLM 路线服务。VLM、语音/音频、扩散虽已有核心正文，但真实模型工具未实测，因此本页不把 LLM 的格式、服务框架或量化术语外推为它们的默认工具选择；未来补充必须先在 [[AI/90-资源/05-官方资料与版本核验记录|官方一手资料账本]] 固定来源、版本与证据级别。

## 按目标选格式和工具

| 目标 | 常见输入/输出 | 默认工具路线 | 选择理由 | 现场必须复核 |
| --- | --- | --- | --- | --- |
| 用 PyTorch / Transformers 继续训练 | config、tokenizer、safetensors 或受信任 checkpoint | Transformers + PyTorch | 保留训练图、optimizer 和 PEFT 生态 | revision、依赖版本、远程代码、模型许可 |
| SFT / LoRA / QLoRA | Hugging Face 模型 + 数据集 → adapter 或合并权重 | 直接 Transformers/TRL、Unsloth 或 LLaMA-Factory | 在透明度、易用性和显存之间选择 | 数据格式、目标模块、dtype、resume、导出 |
| `llama.cpp` 本地推理 | Hugging Face 权重 → GGUF → 可选量化 GGUF | 官方转换脚本 + quantize + `llama.cpp` | GGUF 与 ggml 后端和混合 CPU/GPU 推理结合 | 固定 commit、metadata、tokenizer、量化预设、生成回归 |
| 高吞吐 GPU 服务 | Hugging Face 模型格式 | vLLM 或 SGLang | continuous batching、KV cache 管理和调度 | 支持架构、dtype、显存、服务安全、版本 |
| 最小桌面工作流 | 工具管理的本地模型 | Ollama | 降低首次运行门槛 | 实际后端、模型来源、模板、监听地址、存储位置 |
| 检查不可信权重文件 | safetensors / GGUF | 专用安全读取器、header/metadata 检查 | 避免把任意 pickle 当数据解析 | 文件哈希、大小上限、metadata、解析器版本 |

## `llama.cpp` 格式闭环

```text
模型配置 + tokenizer + safetensors 权重
              ↓ 转换并核对 metadata
            GGUF（高精度或原始精度）
              ↓ 量化并保留原文件
        Q4_K_M / Q5_K_M / Q8_0 等 GGUF
              ↓ 固定 commit 的运行时
      llama.cpp CPU / CUDA / 混合 offload
```

每个箭头都要验证：

- 文件哈希、大小和磁盘余量；
- 模型架构、context、tokenizer、BOS/EOS 与 chat template；
- 代表提示的 token id 和生成回归；
- 峰值内存、TTFT、TPOT 和吞吐；
- 量化前后困惑度或任务指标，而不只比较肉眼样例。

详见 [[AI/20-LLM/60-模型格式与量化/03-GGUF结构转换与验证]] 与 [[AI/80-实践/03-safetensors到GGUF与量化/00-safetensors到GGUF与量化]]。

## Unsloth、LLaMA-Factory 与直接调用

| 路线 | 更适合 | 主要优点 | 主要代价 |
| --- | --- | --- | --- |
| Transformers + PEFT + TRL | 想看清每个对象、写定制训练循环 | 透明、易调试、与原生 API 对齐 | 配置和显存优化需要自己承担 |
| Unsloth | 单机 LoRA/QLoRA、希望减少显存并保持常见工作流 | 针对支持范围做集成和优化 | 支持矩阵与导出流程需要按版本复核 |
| LLaMA-Factory | 配置驱动的数据、训练、恢复、评测和导出 | 统一 CLI/WebUI 与多种训练配方 | 抽象层更高，必须读清生成配置和日志 |

不要把“工具能启动”当作“训练正确”。三条路线都要保存解析后的配置、数据样例、版本、随机种子、checkpoint 和评测证据。

## 服务工具定位

| 工具 | 主要定位 | 不是 |
| --- | --- | --- |
| `llama.cpp` | C/C++ 跨平台推理、GGUF、CPU/GPU 混合 | 通用分布式训练框架 |
| Transformers | 模型定义、加载、训练与生成的 Python 生态入口 | 默认的高吞吐生产调度器 |
| vLLM | GPU 推理服务和批处理调度 | 模型格式转换器 |
| SGLang | 结构化推理程序与服务运行时 | 权重许可或安全边界的替代品 |
| Ollama | 本地模型获取与服务体验层 | 可复现 benchmark 的充分证据 |

比较课程：[[AI/20-LLM/40-推理/05-推理引擎与服务选择]]。

## 练习与成功标准

假设某个 24 GB / 7B QLoRA 场景已经按 [[AI/90-资源/03-GPU显存与资源预算表|GPU 显存与资源预算表]]在目标硬件上短跑测得可行，且训练后要在 CPU + GPU 混合环境服务。画出训练格式、adapter/合并权重、GGUF 转换、量化和服务的五个产物，并为每个产物写一个校验点。这个假设不保证任意 7B 模型、上下文、batch、优化器和 kernel 组合都能装入 24 GB；成功标准是不会把 QLoRA 的 NF4 训练表示误写成 GGUF 的 `Q4_K_M`。
