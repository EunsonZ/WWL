# 模块、包、导入与项目结构

当程序从一个文件长成多个文件时，真正困难的往往不是“怎么写 `import`”，而是弄清楚：**Python 从哪里找代码、以什么身份执行它，以及项目目录怎样设计才不会只在自己的电脑上碰巧可用。**

本课会建立一条完整的因果链：

> 启动方式 → `sys.path` → 找到模块或包 → 建立模块对象并登记到 `sys.modules` → 执行顶层代码 → 成功后复用缓存

学完后，你应该能：

- 区分模块、普通包、命名空间包、可导入包与分发包；
- 解释当前工作目录、脚本目录、`sys.path` 和 `python -m` 的关系；
- 正确选择绝对导入或显式相对导入；
- 看懂 `__name__`、`__init__.py` 和 `pyproject.toml` 的职责；
- 为一个小项目搭建 `src` 布局；
- 根据报错和导入链定位循环导入，而不是靠反复改路径碰运气。

## 1. 先建立三个层次

### 1.1 模块：一个独立的命名空间

最常见的模块是一个 `.py` 文件。例如：

```text
temperature.py
```

```python
# temperature.py
FREEZING_POINT = 0

def celsius_to_fahrenheit(value: float) -> float:
    return value * 9 / 5 + 32
```

导入模块时：

```python
import temperature

print(temperature.FREEZING_POINT)
print(temperature.celsius_to_fahrenheit(20))
```

`import temperature` 通常只把名字 `temperature` 绑定到当前命名空间；函数和常量仍留在模块自己的命名空间中。这也是 `temperature.celsius_to_fahrenheit` 比裸写 `celsius_to_fahrenheit` 更容易追踪来源的原因。

> [!note] “模块就是 `.py` 文件”是实用的入门近似
> Python 还能导入内建模块、扩展模块等。更准确地说，导入系统产生的是模块对象；`.py` 文件只是模块最常见的来源。

### 1.2 包：能包含子模块的特殊模块

普通包通常是一个含有 `__init__.py` 的目录：

```text
weather/
├── __init__.py
├── convert.py
└── report.py
```

它给模块建立了层级名称：

```python
import weather.convert
from weather import report
```

可以把 `weather.convert` 理解成“模块的完整地址”，而不仅是文件系统中的某个路径。准确地说，**所有包都是模块，但并非所有模块都是包**；包具有用于寻找子模块的 `__path__`。

### 1.3 项目：源码、测试、配置和文档的共同边界

项目不是 Python 语法概念。它是一个工程边界，可以包含一个或多个可导入包，还可以包含测试、文档、构建配置和其他资源。不要把“项目目录”“可导入包”“发布到包索引上的分发包”混成同一个东西。

## 2. `import` 到底做了什么

第一次执行 `import weather.convert` 时，可以先用下面的简化模型理解：

1. 查看 `sys.modules`：这个完整名称是否已经加载过？
2. 若没有，导入系统通过查找器寻找对应模块；内建、冻结模块和基于路径的模块都可能被找到。
3. 对基于文件路径的导入，查找会使用模块搜索路径；顶层模块通常沿 `sys.path` 查找，包内子模块沿包的 `__path__` 查找。
4. 创建模块对象，先登记到 `sys.modules`，再执行模块的顶层语句。
5. 导入成功后，后续相同导入通常复用缓存中的同一个模块对象，而不是再次执行全部顶层代码。

第 4 步很关键：Python 在执行模块代码前就先登记模块，是为了处理递归导入；但这也意味着循环导入中可能看到一个**只初始化了一半的模块**。

可以观察模块来自哪里：

```python
import json

print(json.__name__)
print(json.__file__)
print(json.__package__)
print(json.__spec__)
```

不是每个模块都一定有可用的 `__file__`，所以诊断时不要把它当作绝对前提。

## 3. `sys.path`、脚本目录与当前工作目录

`sys.path` 是模块搜索路径列表，但它不是“所有导入规则”的完整替代品。查看它：

```python
from pathlib import Path
import sys

print("cwd:", Path.cwd())
print("sys.path[0]:", sys.path[0])
print("all paths:")
for path in sys.path:
    print("  ", path)
```

启动 Python 时，搜索路径会结合启动方式、环境、标准库位置、当前环境的 `site-packages` 等信息初始化。最容易混淆的是第一项：

| 启动方式 | `sys.path` 的第一项通常代表什么 |
| --- | --- |
| `python path/to/run.py` | 输入脚本所在目录 |
| `python -m some_package.tool` | 当前工作目录 |
| `python -c "..."` 或交互模式 | 当前工作目录（常表现为空字符串 `''`） |

当前工作目录（current working directory，CWD）是进程处理相对文件路径时的起点：

```python
from pathlib import Path

Path("data/input.txt")  # 相对于 CWD，不是天然相对于本 .py 文件
```

因此，“文件明明在同一项目里却导入失败”与“相对路径找不到数据”可能是两个不同问题：前者看模块搜索路径，后者先看 `Path.cwd()`。

> [!warning] 不要把长期修改 `sys.path` 当作项目结构
> 在程序里 `sys.path.insert(...)` 或全局设置 `PYTHONPATH` 有时适合临时诊断，但很容易掩盖安装、目录或启动方式错误。`PYTHONPATH` 还会影响多个 Python 环境。正常项目应优先使用清楚的包结构、正确安装和稳定的入口命令。

还要防止同名遮蔽：如果项目中有 `json.py`、`logging.py` 或 `typing.py`，它可能抢在标准库或第三方包之前被找到。诊断时打印 `module.__file__`，并检查当前目录和脚本目录中的同名文件。

## 4. 为什么包内代码更适合用 `python -m`

假设有：

```text
demo/
└── weather/
    ├── __init__.py
    ├── convert.py
    └── report.py
```

`report.py` 使用包内导入：

```python
from .convert import celsius_to_fahrenheit

def main() -> None:
    print(celsius_to_fahrenheit(20))

if __name__ == "__main__":
    main()
```

在 `demo/` 中直接运行叶子文件：

```bash
python weather/report.py
```

很可能得到：

```text
ImportError: attempted relative import with no known parent package
```

因为这次 Python 把 `report.py` 当成一个顶层脚本，而不是 `weather.report`；它不知道前面的点 `.` 指向哪个包。应当在包的父目录 `demo/` 中运行：

```bash
python -m weather.report
```

`-m` 的意思是：先按导入系统寻找给定的模块名称，再把找到的代码作为顶层程序执行。这样，`weather.report` 的包身份仍然清楚，显式相对导入才能正确解析。

### `__name__` 为什么会变化

模块被普通导入时：

```python
import weather.report
# weather.report 内部的 __name__ == "weather.report"
```

模块作为顶层入口执行时，无论通过脚本文件还是 `-m`：

```python
# 入口模块内部的 __name__ == "__main__"
```

所以常见入口保护是：

```python
def main() -> None:
    ...

if __name__ == "__main__":
    main()
```

它让“定义函数、类和常量”可以安全地被导入，而“解析命令行、打印结果、启动服务”等入口行为只在直接执行时发生。注意：模块的其他顶层语句在首次导入时仍会执行；保护块不是“阻止整个文件运行”的开关。

包还可以提供 `__main__.py`：

```text
weather/
├── __init__.py
├── __main__.py
└── report.py
```

此时可执行：

```bash
python -m weather
```

## 5. 绝对导入与显式相对导入

假设当前模块是 `weather/report.py`：

```python
# 绝对导入：从顶层包名开始
from weather.convert import celsius_to_fahrenheit

# 显式相对导入：从当前包开始
from .convert import celsius_to_fahrenheit
```

选择原则：

- 跨包或应用层代码优先绝对导入，完整来源更明确，也更容易搜索；
- 同一个包内部结构紧密、顶层包名可能变化时，显式相对导入能表达“这是同级模块”；
- 一个点 `.` 表示当前包，两个点 `..` 表示父包；层级太深通常提示目录职责需要重新审视；
- Python 3 中不要依赖含糊的“隐式相对导入”；要么写完整顶层名称，要么明确写点；
- 不要用 `from module import *` 省事，它会让名称来源、静态分析和循环依赖更难理解。

相对导入依据的是模块的包身份，而不是“两个文件在磁盘上挨着”。这正是直接运行包内叶子文件经常失败的根源。

## 6. `__init__.py` 应该放什么

对于普通包，`__init__.py` 用来标记包，并在导入包时执行。它可以为空，也可以谨慎地定义包的公共入口：

```python
# weather/__init__.py
from .convert import celsius_to_fahrenheit

__all__ = ["celsius_to_fahrenheit"]
```

于是调用方可以写：

```python
from weather import celsius_to_fahrenheit
```

但不要把大量业务初始化、网络访问、文件读写或“顺手导入所有子模块”塞进 `__init__.py`。因为导入 `weather` 就会触发这些副作用，还会增加启动时间和循环导入概率。对初学项目，**空文件或只暴露少数稳定 API** 是很稳健的默认选择。

`__all__` 主要规定 `from package import *` 暴露哪些名称；它不是访问控制，也不会自动阻止别人显式导入其他名称。

### 没有 `__init__.py` 就一定不是包吗？

不一定。Python 3 支持原生命名空间包：同一个逻辑包的不同“部分”可以分布在多个搜索路径，甚至由多个分发包分别提供。例如两个分发项目分别提供：

```text
distribution-a/src/acme/weather/...
distribution-b/src/acme/maps/...
```

若 `acme/` 是原生命名空间包，它不放普通的 `acme/__init__.py`；安装二者后可分别导入 `acme.weather` 与 `acme.maps`。这是插件生态、大型组织共享命名空间时有用的高级能力。

普通教学项目不要因为“省一个空文件”而无意创建命名空间包。明确使用普通包通常更直观；只有确实需要跨多个位置或分发包合并同一命名空间时，再有意识地采用命名空间包，并确保各分发项目的约定一致。

## 7. 进阶预览：一个稳健的最小 `src` 项目

> [!info] 先理解结构，安装练习稍后再做
> `src` 布局需要把项目安装到明确的 Python 环境中才能正常导入。本节先解释“为什么这样组织”；请完成 [[计算机知识/10-编程语言/01-Python/08-pip与PyPI依赖管理|pip 与 PyPI 依赖管理]] 和 [[计算机知识/10-编程语言/01-Python/09-venv与虚拟环境原理|venv 与虚拟环境原理]] 后，再执行第 8 节的 editable install 扩展练习。

推荐练习树：

```text
greeting-lab/
├── pyproject.toml
├── README.md
├── src/
│   └── greeting_lab/
│       ├── __init__.py
│       ├── __main__.py
│       └── message.py
└── tests/
    └── test_message.py
```

这里故意出现两个相似但不同的名称：

- `greeting-lab`：分发包（distribution package）名称，供安装工具和项目元数据使用；
- `greeting_lab`：可导入包（import package）名称，必须适合写进 `import greeting_lab`。

两者相同只是惯例，不是强制规则。著名例子是安装分发包 `Pillow` 后导入 `PIL`。一个分发包也可能提供多个可导入包；反过来，不能看到陌生代码里的 `import foo` 就盲目执行 `pip install foo`，二者名称未必对应，这还可能带来供应链风险。

### 为什么多一层 `src/`

如果把 `greeting_lab/` 直接放在项目根目录，Python 从项目根运行时可能直接导入工作区源码，即使项目的构建配置漏掉了某些文件也不易察觉。`src` 布局把“仓库根目录”和“可导入源码根目录”分开：

- 更不容易误导入尚未安装的工作副本；
- 测试更接近用户安装后的真实行为；
- README、构建脚本等仓库文件不会意外进入导入路径；
- 代价是开发前通常需要安装项目，常用可编辑安装把源码变更映射到当前环境。

这不是说所有单文件脚本都必须使用 `src`；它更适合准备长期维护、测试或分发的项目。

### `pyproject.toml` 的角色

一个可练习的最小示例：

```toml
[build-system]
requires = ["setuptools>=77"]
build-backend = "setuptools.build_meta"

[project]
name = "greeting-lab"
version = "0.1.0"
description = "A tiny package for learning Python imports"
readme = "README.md"
requires-python = ">=3.10"
```

`pyproject.toml` 是项目级配置入口，但它不会参与每一次普通 `import` 的路径搜索。这里：

- `[build-system]` 告诉构建前端用什么构建后端以及构建时需要什么；
- `[project]` 保存标准化的项目/分发元数据，如名称、版本、Python 要求和依赖；
- `[tool.some-tool]` 可保存特定工具自己的配置；
- 具体构建后端负责发现 `src/greeting_lab` 并把它纳入构建结果；不同后端的细节可能不同。

它也不是“放进项目根目录就自动让 `src/` 可导入”的魔法文件。项目仍需被当前 Python 环境正确安装。安装行为与来源边界见 [[计算机知识/10-编程语言/01-Python/08-pip与PyPI依赖管理|pip 与 PyPI 依赖管理]]，环境隔离见 [[计算机知识/10-编程语言/01-Python/09-venv与虚拟环境原理|venv 与虚拟环境原理]]。

## 8. 扩展练习：从导入失败到稳定入口（完成 08、09 后）

在一个无个人数据、可随时删除的练习目录中创建上面的项目树。以下命令都从 `greeting-lab/` 根目录执行。

> `pip install --editable .` 会读取 `pyproject.toml`，可能访问当前 pip 配置的索引、下载 `setuptools>=77` 等构建依赖，并执行构建后端代码。先完成第 08、09 课，确认解释器、索引与隔离环境；只在这个无敏感数据的临时项目中执行。来源或配置不清楚时先停止，不要用 `sudo` 或全局安装绕过问题。

def greet(name: str) -> str:

# src/greeting_lab/__init__.py
from .message import greet

__all__ = ["greet"]
```

# src/greeting_lab/__main__.py
from pathlib import Path
import sys

from .message import greet

def main() -> None:
    print(greet("Python"))
    print("cwd:", Path.cwd())
    print("module:", __name__)
    print("package:", __package__)
    print("path[0]:", sys.path[0])

if __name__ == "__main__":
    main()
```

`README.md` 可以只写一行标题：

```markdown
# Greeting Lab
```

## 9. 循环导入：为什么“明明有这个名字”却拿不到

考虑：

```python
# a.py
from b import describe_b

NAME_A = "A"

def describe_a() -> str:
    return describe_b()
```

```python
# b.py
from a import NAME_A

def describe_b() -> str:
    return f"B knows {NAME_A}"
```

导入 `a` 时，Python 先创建并登记 `a`，然后执行第一行去导入 `b`。`b` 又回头从 `a` 取 `NAME_A`，但 `a` 还没执行到定义它的那一行，于是常见报错会提到 `partially initialized module`，或表现为 `ImportError` / `AttributeError`。

### 排错顺序

1. **从 traceback 最底部向上看**：先找真正失败的名称和文件，不要只看最后一句“可能是循环导入”。
2. **写出导入箭头**：例如 `cli → service → model → cli`。能画成环，才是循环依赖的核心证据。
3. **检查模块顶层执行顺序**：被读取的类、函数或常量是否尚未定义？模块导入不仅“声明名字”，还会执行顶层语句。
4. **确认实际导入对象**：打印 `module.__file__`，排除同名文件遮蔽；不要把同名问题误判为循环导入。
5. **优先修正职责边界**，最后才考虑局部导入。

### 常见修复，从根本到权宜

- 把双方都需要的数据类型、协议或纯函数移到更低层的第三个模块，例如 `common.py` 或 `models.py`；
- 让依赖方向单向：界面层依赖业务层，业务层不要反过来导入界面层；
- 传入回调或对象，而不是由底层模块导入上层模块；
- 若只是类型标注造成运行时导入，可结合 `from __future__ import annotations` 与 `if TYPE_CHECKING:`，让类型检查导入不在运行时发生；
- 仅当依赖本身合理、只是初始化时机冲突时，才把导入局部放进函数。局部导入会延迟问题，也可能让依赖更难发现，不应成为默认补丁。

例如抽出共同数据：

```python
# names.py
NAME_A = "A"
```

```python
# a.py
from b import describe_b

def describe_a() -> str:
    return describe_b()
```

```python
# b.py
from names import NAME_A

def describe_b() -> str:
    return f"B knows {NAME_A}"
```

真正的目标不是“让报错消失”，而是让模块职责和依赖方向能够被一句话说清楚。

## 10. 常见误区速查

| 误区 | 更准确的理解 |
| --- | --- |
| `import` 会从整个硬盘搜索 | 它通过导入系统和受控搜索路径查找，不会任意遍历硬盘 |
| 当前工作目录就是脚本目录 | 二者可以完全不同；一个看启动位置，一个看脚本位置 |
| 同目录文件一定能互相导入 | 取决于包身份、启动方式和搜索路径 |
| 每个包都必须有 `__init__.py` | 普通包通常需要；原生命名空间包是有意的例外 |
| `pyproject.toml` 会自动修改 `sys.path` | 它描述构建、元数据与工具配置；项目仍需正确安装 |
| `pip install x` 以后一定 `import x` | 分发包名和可导入包名没有强制一一对应 |
| 修改 `sys.path` 是正常安装方式 | 更适合短期诊断；长期应修正结构、安装或入口 |
| 循环导入只要把 import 移进函数就算解决 | 这可能只是延迟执行；应先检查职责与依赖方向 |
